Implement step 1: GitHub reader and derived state

Build order step 1 (plan section 9): derive the full state of an Objective
from GitHub alone.

Structure follows section 1's governing idea. state.ts is pure -- no I/O, no
stored state, no clock -- so the whole state machine is testable without a
network and "resume" and "start" are literally the same code path. github.ts
reads and never writes, never classifies. types.ts mirrors GitHub primitives
rather than inventing Factory vocabulary.

The relationships the design depends on were verified against the live GraphQL
schema before coding: subIssues, blockedBy, and
closedByPullRequestsReferences all exist, so the "no sidecar state" claim in
section 3.1 holds. One query per cycle.

Notable derivation decisions, each traceable to measured behavior:

- No-op detection is the load-bearing classifier. PROBE-001 measured an
  impossible task returning conclusion: success, so outcome is read from the
  artifact: empty diff and no commit beyond "Initial plan". The diff wins over
  the commit list, since a squash can hide real work behind the plan commit.
- for_review accepts draft PRs. Agents never undraft and never self-merge, so
  requiring ready-for-review would stall every item forever.
- An active session outranks PR inspection; judging a moving artifact judges
  an intermediate state.
- PR evidence outranks assignment, because a PR proves work began whereas an
  assignee only proves work was requested.
- A red check is for_review, not failed. That is a review signal, and
  integration decides.
- Attempts are counted from linked PRs. No counter is stored.

34 tests cover the state machine including mutual deadlock, escalation
handoff, retry counting, and determinism. Typecheck clean under strict mode
with noUncheckedIndexedAccess and exactOptionalPropertyTypes.

esbuild produces a single 99.9 kB dist/factory.js, confirming the bundling
constraint in section 15.5 is satisfiable: install is a copy, with no
lifecycle scripts and no dependency resolution on the adopter's machine.

Step 1 ends in something runnable, per section 9: the CLI is a read-only
inspector, verified live against a real Objective.
