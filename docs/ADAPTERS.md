# Third-party adapters

Every third-party service Factory uses sits behind an adapter contract: one module per vendor, one shape for all of them. Reason: a second vendor is then one new module, not a refactor, and no stage knows a vendor's SDK.

## Cloud sandbox

Contract: `plugin/scripts/lib/adapters/sandbox.mjs`. Vendors: `vercel` (`sandbox-vercel.mjs`, on `@vercel/sandbox`, pinned in `plugin/package.json`). Proof: `bench/sandbox-conformance.mjs` against the real vendor; no fake vendor exists.

What this route supports: a stage runs in one sandbox session of `timeout_minutes` plus about 16 minutes, up to the plan's session cap (24 hours on Vercel Pro; Fresh session per stage, under Stage in the sandbox), proven end to end with Claude Code and Copilot. Codex in the sandbox is unproven.

| Operation | Does |
| --- | --- |
| `create({image \| snapshot, vcpus, timeoutMs, tags, network})` → `{id, expiresAt}` | A running sandbox, and when the vendor ends its session (null when it does not say). `network` is `"all"`, `"none"` or `{allow: [host, "*.host"]}`. At most 5 tags. |
| `run(id, {argv, cwd, env, user, timeoutMs, onStdout, onStderr})` → `{exitCode, timedOut, durationMs}` | One command; output streams to the callbacks as it is written. |
| `addUser(id, name)` → `{name, home}` | An unprivileged Linux user: no sudo, its own home. |
| `writeFiles(id, [{path, content, mode}])`, `readFile(id, path)` → `Buffer \| null` | Files in and out, as the default user, absolute paths. |
| `stop(id)`, `resume(id)` → `{expiresAt}` | Stop ends the VM and keeps the files and users; resume brings them back in a new session and says when it ends. |
| `extend(id, ms)` → `{expiresAt}` | The running session ends `ms` later; the plan caps the total. A stage gets its budget this way at each start, as far as the plan allows. |
| `account()` → `{account, plan, status}` | The account the credentials act for (a name, never an id) and its plan as the vendor reports them. The launcher logs it once per start: the plan sets the session's ceiling. |
| `destroy(id)` | The sandbox and its saved state, gone. A missing sandbox is not an error. |
| `list({tag: [key, value]})` → `[{id, state, tags, createdAt}]` | By one tag, for sweeping what a crashed job left. |
| `usage(id)` → `{wallMs, activeCpuMs, vcpus, memoryMb, egressBytes, ingressBytes, storedBytes, usd, basis, rates}` | Totals across sessions, priced at dated list rates; `basis` says how. `storedBytes` is the saved state a resume boots from (the stop snapshot), whose storage the vendor bills while the sandbox is stopped; null when there is none. |
| `rates` (a property) | The vendor's list rates, with the date and the page they were read from: `activeCpuHour`, `memoryGbHour`, `memoryMinMs` (the memory billing increment), `memoryMbPerVcpu`, `creation`, `snapshotGbMonth`. The one place a vendor's prices live; `openSandbox` refuses an adapter without them. |
| `snapshot(id)` → `{snapshot, sizeBytes, usdPerMonth, usage}` | The sandbox's files as a create source (`create({snapshot})`), its storage priced at list rates, and the sandbox's `usage`. The sandbox stays, stopped and tagged `snapshot=<id>`, and nothing runs in it again. Sandboxes made from the snapshot stop, resume and go without touching it. `destroy(id)` deletes it. |
| `snapshots(id)` → `[{snapshot, state, createdAt, sizeBytes}]` | The snapshots this project lists for the sandbox `id`; `state` is `ready`, `deleted` or `failed`. |
| `storage()` → `{snapshots, bytes, limitBytes}` | Every ready snapshot in this project (all repositories sharing it), counted and summed as the vendor bills its storage, and the plan's storage limit when the vendor's API states one (null otherwise; Vercel's does not, and its HTTP 402 is the only sign). |
| `baseImage(node)` → image | The vendor's image an image build starts from, for the adopter's Node.js version. |

Rules:

- **The id and the tags are the only vendor-side state.** Factory records the id in GitHub and finds strays by tag. Reason: GitHub is the only database.
- **Errors are `SandboxError` with a `code`** from `ERROR_CODES` (`invalid`, `auth`, `not_found`, `conflict`, `rate_limited`, `quota`, `unsupported`, `unavailable`, `vendor`). Callers decide on the code, never the message.
- **Users.** `user` absent is the sandbox's default user, which may sudo: Factory's own process. `"root"` is root. Any other name is a user from `addUser`: the harness. Reason: the same uid split as on Actions (`lib/agent.mjs`).
- **Env values never go on a command line.** As another user, only variable names are on the sudo line; the values travel in the environment, and the user's command sees only the names its run passed (plus `PATH`, `LANG`, `TERM`, `HOME`, `USER`, `LOGNAME`). Reason: every user in the VM can read every command line. There is no sandbox-wide env for the same reason.
- **The network policy is per sandbox, not per user.** Factory and the harness reach the same hosts.
- **Credentials come from env and are never printed.** Vercel: `VERCEL_TOKEN`, `VERCEL_TEAM_ID`, `VERCEL_PROJECT_ID`.
- **The SDK loads only when an adapter opens.** Nothing else in Factory needs an install; the sandbox backend runs `npm ci --ignore-scripts` in `plugin/`.
- **An image is a stopped sandbox and its tags,** found by tag in this project's listing. A snapshot is only ever deleted through its source sandbox: a snapshot id alone is valid team-wide.

Vercel specifics: the id is the sandbox's name; sandboxes are persistent and keep only the latest stop's snapshot, and `destroy` deletes it. Any call on a stopped sandbox resumes it (`capabilities.autoResume`). vCPUs are 1 or even, up to the plan's cap, with 2 GB of memory each. The managed images are Ubuntu with passwordless sudo for the default user (`ubuntu`, home `/vercel`) and sudo keeping the caller's environment. Cost is computed from Pro list rates in `iad1`, kept with the date and page they were read from in one place, `VERCEL_RATES`: active CPU, provisioned memory for wall time in one-minute increments, creations, and snapshot storage per GB-month, for an image and for the stop snapshot a persistent sandbox keeps while it is stopped (Vercel bills each automatic snapshot as Snapshot Storage). Data transfer is not priced: included on Pro, and downloads are free. An image is a Vercel snapshot (create from it: about 1.4 to 3 s), not a container image in Vercel's registry: the setup command runs in the same VM a stage runs in (sudo, `service`, no systemd), with no Dockerfile and no registry login. `baseImage` is `vercel/sandbox/node:<major>` for Node.js 22, 24 and 26, else `vercel/sandbox/universal`. A snapshot expires 30 days after its last use.

Run the proof: `npm ci --ignore-scripts --prefix plugin && node bench/sandbox-conformance.mjs --vendor vercel`, with the credentials in env. It creates a 1-vCPU sandbox, checks every operation and the uid split, prints a pass/fail table and destroys what it made, on failure too.

## Decision model

Contract: `plugin/scripts/lib/adapters/decider.mjs`. Vendors: `ai-gateway` (`decider-ai-gateway.mjs`, Vercel AI Gateway's `/v1/decisions`, plain `fetch`, no SDK). Used by red-check triage (`lib/triage.mjs`) and the drift advisory (`lib/drift.mjs`), each with its own model setting.

| Operation | Does |
| --- | --- |
| `decide(input, question)` → `{verdict, confidence, error?}` | One `choice` question about `input`. `verdict` is one of the question's values or null; `confidence` is the model's, or null. Never throws. |

Rules:

- **No vendor-side state.** Each question is one stateless call.
- **Errors are codes** from `DECIDER_ERRORS` (`auth`, `rate_limited`, `unavailable`, `invalid`, `refused`, `no_answer`, `vendor`), with no verdict. Callers decide on the verdict and the code, never a message.
- **The key never leaves Factory's process.** On Actions it is the `ai_gateway_api_key` input; locally only the file `~/.config/factory/ai-gateway-key`. `scrubbedEnv` keeps it out of every child.

## Launcher (`mode: launch`)

With `FACTORY_SANDBOX` set (setup `--sandbox vercel`), the workflow has launch jobs instead of the work and review jobs: each turns one event into at most one stage start in the Objective's sandbox and exits in about thirty seconds. The runner is never the sandbox. Without it, the rendered workflow is the runner one, line for line.

| Event | Jobs | Outcome |
| --- | --- | --- |
| The dispatcher's pick, or its sweep re-launching a lost event | `launch (<n>)`, after `dispatch` | `work` for a Running Objective with no work start since it became Running; `review` for a `factory:review` PR with no review start since its label |
| A maintainer's comment on a Question (`issue_comment`) | `launch gate`, then `launch (<n>)` | back to Queued and a dispatcher tick: the dispatcher starts it under its caps |
| CI finished on `factory/<n>`: `workflow_run` (CI on Actions) or `check_suite` (an App's CI) | `launch gate`, then `launch (<n>)`, or `merge tick (<n>)` | the stage the record says waits on checks for that head, while it is still the branch's head; with no stage waiting and the Objective In review, a dispatcher tick so its merge pass runs now |
| `factory:review` on the PR, or a person marking it ready | `launch gate`, then `launch (<n>)` | `review` |
| The running stage asks for fresh tokens (`repository_dispatch` `factory-stage`, `want: token`) | `launch gate`, then `launch (<n>)` | its tokens handed over (the session is not extended: the stage was fitted to it at the start) |
| The stage ended (`want: ended`) | `launch gate`, then `launch (<n>)` | its usage uploaded as the artifact, the sandbox stopped; a stage due next (the review after the work) starts in a fresh session |

Rules:

- **The gate decides outside any concurrency group.** An event job decides first in `launch gate` (no group, no install, no sandbox call); the start job joins the Objective's group, `factory-launch-factory/<n>` (the gate's `issue` output, the Action's `issue_number`), only when the gate said start; launches of different Objectives never wait for or replace each other. Reason: GitHub keeps one pending job per group and a newer one replaces it, so a stranger's comment or a fork's CI in the group would cancel a real launch. The gate's `if:` also drops comments by bots, by authors with no association to the repository and Factory's own marker comments. Pinned maintainers who show as contributors still reach the gate's trust check.
- **Lost events are swept.** A pending launch can still be replaced by another real one, and GitHub drops events. The dispatcher (with `FACTORY_SANDBOX`) names a Running Objective with no work start since it became Running, and a labelled PR with no review start since its label, after a three-minute grace. A Running Objective is alive while its record says a stage runs within its lease (the heartbeat renews it; a record with no lease counts `timeout_minutes` from its last write), not by a work job.
- **Caps live only in the dispatcher.** An answered Question goes back to Queued and the job ticks the dispatcher, which applies `max_concurrent` and `daily_usd` under `factory-dispatch`. Each stage carries `max_usd` as its budget, less its sandbox session's most (Vendor cost, below).
- **A launch that does not start its stage ticks the dispatcher itself.** Both launch jobs end with a `workflow_dispatch` tick when the launcher failed or was cut off, Blocked, requeued the Objective, deferred its stage to a retry time or started nothing (`skipped`), so a freed slot or a retry never waits for GitHub's cron. A failed launch's tick names its Objective (`failed_launch`), and the dispatcher wakes at the end of that Objective's launch grace instead of leaving it to the cron. Each stage carries `max_usd` as its budget, less its sandbox session's most (Vendor cost, below).
- **The record is claimed before any sandbox call that changes anything.** Vendor reads (the image's, the account's) may run beside the claim's write; nothing is created, resumed, run or stopped until the claim is written. The claim comment, marker `<!-- factory:<n>:sandbox -->`, is written only by Factory, under the Objective's record lock (Records, below). The launcher writes it `running` with a claim nonce and a ten-minute lease, only over the record its decision read, and starts nothing when the record changed since (another launcher's claim, a stage, the sweep's claim). The stage's heartbeat renews the lease every two minutes in its own comment; a stage that dies frees the Objective when its lease runs out. Three real failed starts in one Running stint (or one review request) Block it; a vendor's transient failures never do (below).
- **Only the recorded sandbox is adopted:** the recorded `factory-` id, when the vendor lists it with this Objective's tags (`factory=objective`, `factory-repo=<repository id>`, `factory-issue=<n>`) and stopped or running. Otherwise a new one is created and unrecorded tag matches are ignored. The id is recorded even when the command fails.
- **GitHub comments carry codes and times only.** The record and a Blocked reason hold exit codes, `SandboxError` codes and HTTP statuses; command output and vendor messages go to the job log. The record's JSON escapes `<` and `>`.
- **Transient vendor errors are retried, not Blocked.** On `rate_limited` or `unavailable` the launch exits `deferred`: a work stage stays Running and a review stays labelled. The dispatcher tries again 2, 4, 8 and 16 minutes after each failure, then every 30 minutes (its `start-retry` wake, armed on every repository), and picks no new Objective on this route while any Objective's last starts were refused this way, at most four in a row (about 30 minutes of backoff), so an outage does not drain the queue into failures. Past four, the refusal looks like that Objective's own: its tries go on every 30 minutes and new picks resume. A deferred stage says so on its issue in one note (marker `<!-- factory:<n>:deferred -->`: the vendor's code, the tries in a row, the next try, whether it holds the route), written at the first deferral and at each 30-minute try, and deleted when a stage starts. A launcher cut off in its vendor calls (`timeout`, below) is retried on the same pause but holds no picks, and three in a row Block: a launch that always runs past the job's limit is a real problem.
- **Every launch attempt ends as a stored entry in the record's `launches`:** `{ok: true}` for a start, `{ok: false, code}` for a failed one. Nothing is counted from an absence except at one conversion point, `settleStale` (lib/logic.mjs), which every claim-comment write applies before its own change (writeSandboxRecord) and every reader counts through, so a later write never erases an attempt and the count only grows:
  - As the dispatcher names a stage (a pick or a relaunch) it appends a starting marker (`ok: null`) under the record lock, and lists a `start-retry` deadline at the marker's expiry, so that run owns the launch even when its launcher ticks nothing; the launcher's claim or its failure settles it, and a launch that skips drops its own run's marker (no attempt, no strike). No marker is written over a live claim: a launcher already holds the record, so the named launch would skip. A marker older than 10 minutes (the launch job's limit and its runner wait) is stored as `{ok: false, code: "lost"}`: its job never started, threw in its first reads, or could not write its failure. A real strike.
  - A launcher's claim (work or review) whose lease ran out with no start since it was made (its `claimedAt`, not the record's `at`, which a started stage's beats move) is stored as `{ok: false, code: "timeout"}` and the record says `failed`: its launcher was cut off in its vendor calls.
  - Times: `since` (the Running label, the review request) is GitHub's clock and an entry's `at` the writing runner's, so entries up to a minute before `since` count as the stint's.
  - A marker younger than that is a launch in flight: the dispatcher names it again only once the marker turns into an outcome (its `start-retry` wake).
  - A launcher that throws after its decision writes its failed start itself, under the record lock (Records, below). Entries from before codes were recorded are not counted.
  - Every failure gets the growing pause. Three real failures (anything but `rate_limited`, `unavailable` and `timeout`) in a stint or a review request Block, and so do three `timeout`s in a row; a dispatcher's marker written between a launcher's read and its claim refuses that claim, and the named launch recovers on its own.
- **A quota refusal waits, then Blocks.** On `quota` (Vercel's HTTP 402, snapshot storage on the trial and Hobby plans), the launcher runs the sweep at once (below; usage still to come out waits for the sweep job), writes a note on the issue (marker `<!-- factory:<n>:quota -->`: the code, what the sweep destroyed, this repository's storage, the next try's time) and records the streak in the sandbox record (`quota: {since, tries, retryAt}`). A work stage goes back to Queued (the launch exits `queued`), a review stays labelled (the launch exits `deferred`), the launch job ticks the dispatcher, and the dispatcher picks neither before `retryAt`: 5, then 10, then every 20 minutes. A try refused again 90 minutes or more after the first refusal, or the eighth refusal, Blocks, naming the quota; a late try does not restart the wait. Another start failure that is tried again keeps the streak; a streak over 24 hours old is a past one, and a refusal starts a new one. A start clears the streak and deletes the note; every stage write drops it too, so it stays cleared whichever writer lands last. A Queued Objective named by hand (`workflow_dispatch` with its issue) does not wait.
- **Any other error Blocks.**
- **CI on Actions fires no `check_suite` event** (GitHub drops it to prevent recursion), so the workflow also listens on `workflow_run` for the CI workflow setup found (`--ci-workflow` names another); doctor checks the name exists.
- **The SDK is installed for the sandbox jobs only** (launch, image, sweep): `npm ci --ignore-scripts` in the Action's `plugin/`, from the lockfile, no install scripts. The launcher starts it itself, once the secrets are out of its environment, and waits for it only before its first vendor call, so the install runs beside the token mint and the GitHub reads. The gate installs nothing.
- **A launch is timed per sub-step.** The job log's `launch timing` line and each launch entry in the record (`ms`) hold the milliseconds of each step in order: `mint`, `read`, `open` (the SDK and the lock's base); for a stage's end `end.lock`, `end.reread`, `end.collect`, `end.stop`, `end.book`, `end.destroy` (a closed Objective), `end.record`; for a start `start.lock`, `start.reread`, `start.claim` (the CI token check, the image and the account are read beside it), `start.doctor`, `start.list`, `start.image` or `start.stop`, `start.usage`, `start.create` or `start.resume`, `start.extend`, `start.probe`, `start.upload`, `start.command`, `start.lost` (an earlier stage's usage its lost end never collected) and `start.record`. The progress comment's cost line of an ended stage is written beside the next stage's start. Dispatch latency counts from the event to the stage command's start, so it also holds GitHub's queue and the jobs before the launcher. The dispatcher's `dispatch timing` line does the same for a tick.
- **Credentials:** the vendor's secrets reach the launcher only (`vercel_*` inputs) and never the sandbox. The launcher deletes every secret, under every name it can have, from its environment once read, and the App key from memory after minting. The SDK runs in the launcher's process. The child-env scrub drops `VERCEL_TOKEN` and `VERCEL_OIDC_TOKEN`.

## Stage in the sandbox (`plugin/scripts/stage.mjs`)

The launcher starts the stage detached in the Objective's sandbox, as its default user, and exits; the stage is the same `worker.mjs` or `review.mjs` the Actions jobs run, with the Actions split.

- **Who holds what.** Factory's process (the default user) holds the App's write token and a read-only token, both minted by the launcher for this stage and passed in the start command's environment, then moved into memory; fresh ones before the hour is out come over a 600 socket in a 700 directory and reach the worker over its IPC channel. None is ever in a file. The harness runs as `factory-agent` with the read-only token in its own home and its model credential per run, as on Actions. Only the stage's harness's credential enters the sandbox; the App key and the vendor's credentials never do. Codex and Copilot keep that credential out of the commands their model runs, as on every route; Claude Code does not off local mode (PLAN.md, Credentials and billing). The start command's package steps (apt, npm and their install scripts) and the CLI's version check run with only `HOME` and `PATH`: the image's sudo keeps the caller's environment, so only the stage itself gets its tokens and the harness's credential.
- **Where there is no systemd** (the Vercel VM: its PID 1 is the vendor's init), the agent is confined by `unshare`, `setpriv` and a cgroup v2 group (`proc.mjs` `NAMESPACE_WRAP`). Every mount is remounted read-only, nosuid and nodev (`/dev` keeps its devices), except `/proc`, `/dev/pts`, the agent's home (nosuid, nodev) and private `/tmp`, `/var/tmp`, `/dev/shm` and `/run/lock`. The agent gets its own PID namespace (every process it left dies with the command), no new privileges, no capabilities and umask 077; the reap kills the cgroup. As root the wrapper touches only what root owns. The working directory is entered and the temp directory made after `setpriv`, as the agent (a symlinked temp directory or home is refused), because the agent can swap either path for a symlink. Proof: `FACTORY_CHECK_AGENT=1 node bench/sandbox-check.mjs --agent` in a throwaway VM. Each attack is a row with a control that replays the pattern the wrapper must not use (plain `sudo -u`, root `cd` then drop, root `install -d`).
- **What the VM leaves open to every uid, the agent's too**: the kernel lets an unprivileged user create user namespaces, inside the wrapper too, and has no netfilter (no nftables, no iptables), so no per-uid network rule is possible. Something outside the guest answers HTTP on TCP port 23456 for every uid (404 on every path tried). Not reachable: the vendor's init socket (600 in a 750 directory), `/dev/vsock` (root 600) and any metadata address. Factory does not block that port: it would need a network namespace with userspace egress.
- **Fresh session per stage, fitted to what the vendor grants.** Every stage starts in a fresh session (a running sandbox is stopped and resumed first). A create asks for the stage's whole need: `timeout_minutes` plus the reserve and ten minutes for the start. A plan that caps sessions lower refuses it (HTTP 400 with Vercel's `bad_request`, "`timeout` should be <= 45m"): the launcher asks once more at the cap the answer states (45 minutes when it states none) and extends toward the rest, and a resumed sandbox is extended the same way; it decides on the status and the code, and reads only the retry's size from the message. The session's end is the vendor's answer (`expiresAt` from create, resume or extend), and the stage's wall clock is cut to end six minutes before it (the watchdog's grace, then packing and the end's announcement). The stage cuts it again from the same end when it starts the worker, after its clone; a stage the session cut that reaches its time cap Blocks naming the vendor's cap. Doctor does not check `timeout_minutes` against a session cap: the cap is the plan's, and only the vendor's answer at the start shows it. The job log names the vendor account and plan (`account()`). Probed 2026-11-09 at 2:44 PM PST on the clockgrove team on paid Pro (plan `pro`, status `active`): creates of 120 and 1440 minutes are granted, and so is an extend from 45 to 130 minutes; a session past 1440 minutes (24 hours, Vercel's documented Pro maximum) is refused (create: HTTP 400, `bad_request`, "`timeout` should be <= 1d"; extend: HTTP 400, `sandbox_timeout_invalid`). So a stage there gets its full `timeout_minutes`, up to about 24 hours less the reserve and the start. A stage that needs longer than one session does not fit.
- **From the image.** A new sandbox starts from the adopter's image when one is built and its snapshot is there, else from the vendor's base image with a cold setup. The worker re-runs the setup either way (a snapshot keeps files, not processes), with the image's saved exports seeded into `GITHUB_ENV`. The image's clone is Factory's tree of the default branch, fetched to its current head; the agent clones for itself, as on Actions (it cannot read the default user's home), so the image's dependency install is not reused by the agent's install.
- **Waits.** The sandbox is stopped at every wait between stages (a Question, a human's review, a send-back, the merge queue): a stage that ends says so, and the launcher stops it. A wait inside a stage (its required checks) keeps it running: an idle 2-vCPU sandbox costs about $0.085 an hour in memory, and stopping would wipe and re-set up the agent's checkout on resume. Stopped, it costs its stop snapshot's storage (Vendor cost, below).
- **Spend.** The stage records its model dollars in its progress comment (one per stage, keyed by the launch run and the stage's claim), which `daily_usd` counts at once. The usage artifact uploaded when it ends (or by the next launch, when its end was never answered) is marked `spendInProgress`, so it is not counted twice; with `FACTORY_SANDBOX` set the dispatcher downloads no usage artifact at all, so its spend read does not grow with the day's artifacts (runner jobs' artifacts from earlier on the day a repository switched to the sandbox are not counted). The launcher adds the sandbox's own cost at the stage's end, to the artifact and in a vendor comment of its own (Vendor cost, below). The harness's own usage output is what is counted for the model: the agent could misreport it.
- **The stage's log** (`~/factory/logs`, 700, files 600) holds no secret: masking lines (`::add-mask::`, which carry the value) are not written in a sandbox stage.
- **Default-branch setup runs with sudo** and what it installs persists in the image and every stage: it is trusted like CI on the default branch (the image build's privileged-config check is the guard).
- **Lifecycle guards.** The heartbeat runs one beat at a time, never after the stage ends, so a late beat cannot undo "ended". Each beat writes the stage's own comment (one list read and one write), only while the claim comment carries the stage's claim; otherwise the claim is lost (another launcher holds the sandbox) and the worker is ended. A watchdog ends the worker at its wall clock plus three minutes, and never later than three minutes before the session ends; the stage then reaps the agent's processes, masks the harness stream and Blocks the Objective (`stage: the work passed its wall clock`) before it records the end. A review stage starts only with its PR's number (the launcher finds the Objective's open PR when the event has none). A sandbox that fails to stop at a stage's end is recorded `stopped` with `stopError`; the next start stops it. A stage's end on a closed Objective still stops the sandbox; a record without the sandbox's id stops what its tags find.

## Vendor cost

Dollars per merged Objective count the sandbox too. The launcher holds the vendor's credentials, so it prices each stage; the stage in the VM never sees them. Code: `adapters/sandbox.mjs` (`sessionCeilingUsd`, `stageVendorCost`, `storedUsd`, pure), `launch.mjs` (`startInSandbox`, `bookVendor`).

| When | What |
| --- | --- |
| Start | A resumed sandbox's usage totals are read before the resume (after stopping it, if it was running): the stage's baseline. A created one starts at zero and pays its creation. The record keeps the baseline, the session's ceiling, the stopped stretch and the progress comment's key (`meter`, `progress`). The stage gets the sandbox's id, its home, `meter`, the image it started from, the session's end, `progress`, the start's time, its `deadlineAt` and the start's launch entry in its start environment, and writes them with every heartbeat and its end; a launch entry already in the record (the launcher's, one per cue and run) is kept. The stage writes them in its own comment and the launcher in the claim comment, so whichever lands first, the record keeps the launcher's entry with its step timings and the image. |
| Start: the cap | The session's ceiling is every vCPU busy and its memory provisioned until the vendor ends the session, plus a creation. With the stopped stretch's storage it comes off `max_usd` (`harnessBudgetUsd`, the one place the cap is split), and the harness gets the rest as its budget (`FACTORY_MAX_USD` in the stage). The vendor ends the session at its end, so the stage's model and vendor dollars together stay under `max_usd`. A cap the ceiling eats starts nothing: the sandbox is stopped and the Objective Blocked (`budget`). |
| End | After the stop, the totals again; the difference is priced at the adapter's `rates`, memory rounded up to the billing increment. A usage read that fails, a partial one, or a stop that failed (the session's totals cannot have settled) counts the ceiling instead, marked an upper bound. A vendor error never Blocks here. |
| Stopped | The stop snapshot's storage from the record's `stoppedAt` (the end's stop) to the next start's resume, at its size then (`storedBytes`), is booked on that next stage. |
| Booked | Once per stage (`vendorBooked` in the record): `vendor` in the stage's `result.json` beside the harness's dollars (a record of its own when the stage left none, so the artifact still carries it; marked `spendInProgress` like the stage's, so `daily_usd` counts the stage once, from its comment); and the stage's vendor comment (`<!-- factory:<n>:vendor:<stage>:<key> -->`, the progress comment's key), with a line of the sandbox's state, active CPU and wall seconds, vCPUs and memory, the dated list rates and the dollars, and a spend line of the vendor's dollars (`{usd, vendorUsd}`; with `modelUsd` too for a stage that left no progress comment), which `daily_usd` sums beside the progress comments'. The booker takes the stage's book lock (`<stage>-book-<claim>`, kept until stale), so while that lock lasts (`LOCK_STALE_MS`, 15 minutes) exactly one of the launcher, a later start and the sweep writes it. After that the record's `vendorBooked` is the guard: each books only a stage the record does not show booked, and a booking again (its record write lost) rewrites the same vendor comment, never adds one. The sandbox record's line shows the stage's sandbox cost. An end never answered is booked by the next start or by the sweep, from the totals read before the start resumes the sandbox, before the sweep destroys it, or after the sweep stops it. |

The bench sums `vendor.usd` beside the model's dollars, one booking per stage claim (a booking two artifacts carry counts once): the row's `cost.vendorUsd`, `cost.vendor` (stages, upper bounds, the rates' date) and `cost.totalUsd`; the table's cost cell reads `model + sandbox = total`, and the baseline has `sandbox $` and `total $`.

Not counted, and why:

- **The stretch after a stage no later stage follows.** A sandbox stopped after an Objective's last stage is destroyed when the Objective closes (the sweep on the close or the merge, else hourly), or after `sandbox_idle_days` stopped. No progress comment is still open to book it on, and editing an old one would count its whole spend again on the day of the edit. Bound: its stop snapshot's storage for that stretch (at Vercel's rate, a 2 GB snapshot for seven idle days is about $0.04).
- **A start that failed after its sandbox was running.** That session runs until the next start stops it, or until the vendor ends it; nothing books it. Bound: one session's ceiling, the stage's `timeout_minutes` plus 16 minutes (about $0.26 for a 45-minute session at 2 vCPUs), and three failed starts Block the Objective.
- **The image's storage.** It is the repository's, not an Objective's: the image record carries its size and monthly cost.
- **Data transfer.** Included on Vercel Pro; downloads are free.

A booking writes the vendor comment minutes after the stage's last line, so a stage that ends across midnight UTC counts its vendor dollars toward the next day's `daily_usd`, as a long stage's model dollars already do. A booking by the sweep of an end never answered can land on a later day and count that stage again there: an over-count, never an under-count.

## Launch lock

`plugin/scripts/lib/lock.mjs`: a create-only git ref, `refs/factory-launch/<n>/<stage>-<cue>`, taken before any sandbox call by every launcher (the dispatcher's `launch` job and `launch-event`).

- **The cue is the same whichever process or event sees it.** A stage waiting on CI: the head it waits for. A review: when it was last asked for, read from the PR's timeline (the `factory:review` label, or a person marking the PR ready, whichever is later), so `labeled` and `ready_for_review` for one request, and the sweep's re-launch of it, meet at one lock. A swept work start, or one after a stage's end: the Running stint.
- **GitHub refuses to create a ref that exists (HTTP 422),** so exactly one creator holds it. The others start nothing. A 422 with no ref there afterwards is an error, not a held lock.
- **The holder decides again on what GitHub says now.** A launcher that read before another's start was recorded does not start the same stage twice: the record shows that cue started, or a review started since it was asked for.
- **The ref points at a commit of its own** (no parents, the default branch's tree, author Factory, message the ref) whose date is when it was taken.
- **It is held for the launcher call only,** seconds, and released once the start is recorded. A lock older than 15 minutes (`LOCK_STALE_MS`, above the launch jobs' 5-minute limit) has no live holder: the next launcher takes it over and the dispatcher's tick releases it.
- **Take-over and release are compare-and-swap** (GraphQL `updateRefs` from the oid that was read), so two launchers that read one stale lock cannot both take it, and a release never drops a lock someone else holds now. Each outcome is decided on a read of the ref afterwards.
- **It needs the App's contents write,** which Factory already has. The refs appear in no branch or tag list, and no ruleset can protect them.
- **Anyone who can push can take or drop a lock; that is maintainer trust already.** The harness cannot: it holds no write token. The dispatcher's tick releases a lock Factory did not make (not a commit by Factory whose message is the ref) and logs `foreign lock`.
- **A running stage's own requests lock too.** A token hand-over takes `<stage>-token-<claim>-<ask>` (`ask`: when the stage asked) and keeps it until stale, so each request is answered once. A stage's end takes `<stage>-ended-<claim>` while its usage comes out and the sandbox stops. The stage due next then starts under its own cue's lock: the review after the work meets the PR's `labeled` event at one `asked-` cue, and a work start the Running stint's.
- **The record's claim stays as the state the dispatcher and the sweep read,** and is still written (under the record lock) before any sandbox call, but it is not what keeps two launchers apart.

## Records

Every record comment has one writer, so no write lands over another's. Readers merge the parts.

| Comment | Marker | Writer |
| --- | --- | --- |
| Claim | `<!-- factory:<n>:sandbox -->` | launchers and the sweep, one at a time under the record lock |
| Stage part | `<!-- factory:<n>:stage:<claim> -->` | the stage holding `claim` (stage.mjs), alone |
| Progress | `<!-- factory:<n>:progress:<stage>:<key> -->` | the stage's (or job's) progress reporter, alone |
| Vendor cost | `<!-- factory:<n>:vendor:<stage>:<key> -->` | the one booker holding the stage's book lock |

- **The sandbox record is read merged** (logic.mjs `sandboxRecord`): the claim comment, and, while it says `running`, the stage part of its claim over it: the stage's lease, state, start fields and launch entry, and a quota streak over. A claim comment written later (a stop, a failed start) folds the part in, and the part is read no more.
- **The stage writes one part,** by its comment's id from its first write on, so a fresh part still missing from the list is never posted twice. Should two parts of one claim exist, the one written last (its `at`) is read.
- **The claim comment is the one part with several writers,** because claiming is how launchers and the sweep exclude each other. Each write holds the Objective's record lock, `refs/factory-launch/<n>/record-sandbox` (lib/lock.mjs: a create-only ref, held for the write only, cleared by the dispatcher's tick when left stale), reads the record, writes over what it read only when its precondition holds (a claim over the record its decision read; any later write only while the record carries its claim), and reads its write back before it releases the lock, since a fresh comment can lag the list. A writer that finds the lock held tries again a few times, seconds apart, then reports.
- **The vendor comment has one writer per stage** by the book lock, `refs/factory-launch/<n>/<stage>-book-<claim>`, taken before the write and kept until stale; past that, the record's `vendorBooked` keeps a stage from being booked again, and a repeat booking rewrites the same comment. The progress comment is the stage's alone: no booking edits it.
- **API calls per write.** A progress line: one list read and one write, unchanged. A beat: one list read and one write. A claim comment write (a few per stage): the lock's create (2), a list read, the write, a read-back list (up to 4 while the list lags) and the lock's release (2), so 7 to 10 calls. A booking (once per stage): a list read, the book lock (2) and the write.

## Sandbox image (`mode: image`)

Every stage's sandbox starts from the adopter's image: a snapshot of a sandbox that ran the adopter's own setup command, never one made by hand. Contract: `plugin/scripts/lib/image.mjs`; build: `plugin/scripts/image.mjs`.

| Step | Does |
| --- | --- |
| Base | A fresh sandbox from `baseImage(FACTORY_NODE_VERSION)`, 2 vCPUs, full network, tagged `factory=image`, `factory-image=<repository id>`, `sha=<head>`. |
| Clone | The default branch's head into `/opt/factory/<repo>`, from a git bundle the job's checkout makes. origin is the plain `https://github.com/<repo>.git`; no credential is in the git config or the home. |
| Base packages | git-lfs, gh and getcap (libcap2-bin) from the base's apt, as root, so no stage installs them at start. Before the privileged-config baseline. |
| Setup | `FACTORY_SETUP` in the clone, with `CI=true` and `GITHUB_ENV` / `GITHUB_PATH` files. What it exports is kept at `/opt/factory/setup-env.json`. |
| Dependency store | The worker's install command (`FACTORY_INSTALL`, `auto` from the lockfile), online, so a stage's offline install finds everything. |
| Harness CLIs | Claude Code, Codex and Copilot at `harness_version`, installed globally; each must answer `--version`. npm 10 (on `node:22`) ignores `--allow-scripts` and runs every install script, as on the runner. |
| Privileged config | Fails the build when setup changed, from what the base had, any of:<br>- files hashed whole: `/etc/sudoers` and `sudoers.d`, `/etc/ld.so.preload`, `/etc/gitconfig`, `/etc/environment`, PAM (`/etc/pam.d`, `/etc/security`), `/etc/claude-code`, `/etc/codex`, the default user's git config, and the clone's `.git/config` and `.git/hooks`;<br>- every setuid or setgid file (hashed);<br>- file capabilities (`getcap`);<br>- the accounts that grant privilege: uid 0, the members of the privileged groups, and accounts with a password or an empty one.<br>A package's own system user (postgres) passes. So do setuid or setgid programs, file capabilities and PAM or limits files that an installed dpkg package owns and `dpkg --verify` finds unmodified: setup installing software (PostgreSQL pulls in cron and dbus) is not setup granting privilege. Sudoers, the preload list, git config and hooks, `/etc/environment`, the harnesses' config and accounts are never exempt. A package setup installs is trusted as its CI would trust it. |
| Snapshot | `snapshot(id)`: the sandbox stays, stopped, tagged with the snapshot. That sandbox is the image's vendor-side record. |
| Record | A marker comment the Factory App writes on Factory's image issue (label `factory:image`; made by the App the first time, closed and locked), with a token minted for that alone: issues write on this repository. One JSON line, the newest 30 builds first (vendor, snapshot, source sandbox, head, time, milliseconds, size, cost), then one human line. A failed build is recorded too, with no snapshot. If recording fails, the image is destroyed. |
| Prune | Before the build, images the sweep would destroy (below) go, so the build has room under the vendor's storage quota. After it, images beyond the newest two, found in the vendor's listing (this project, the repository's tag), are destroyed with their snapshots. The sweep then takes the repository down to the current image. |

Rules:

- **Two records, each checked against the other.** GitHub's, the index, counts only when it is Factory's own: the issue must be opened by Factory's login with the exact title `Factory: sandbox image` (the label only helps find it) and, on Actions, be locked; the comment must be by Factory's login too. This is the same rule as the progress and sandbox records. The vendor's, the proof, is the image sandbox in Factory's own project, stopped and tagged with the repository id, the head and the snapshot. A build's snapshot is used only when that project-scoped listing shows it, with the recorded source, head and snapshot, and lists the snapshot ready. That listing is also the only source of what a build destroys.
- **`currentImage(adapter, repo, {token, repoId})`** returns `{snapshot, sha, checkout, envFile, builtAt}` for `create({snapshot})`, or null. It is the newest build Factory recorded that the vendor confirms, whose snapshot is ready and whose head is on the default branch. With null, a stage creates from `baseImage` and runs setup cold. `token` is the App's, and Factory's login must be known (`setSelf`, as `appToken` does). `checkout` and `envFile` are constants.
- **Only merged code becomes the image.** Builds by hand run only on the default branch (the job's `if:`) and only at its head now. Other builds need a commit on it.
- **The image holds no secret.** The build sandbox gets no credential: the vendor's credentials and the App key stay in the build's process, which drops them from its environment (the key also from memory once minted), and the clone comes from a bundle. The build fails if the clone's git config has a credential helper, an extra header or an `insteadOf`, or if origin is not the plain URL. The build's streamed output runs under `::stop-commands::`, so no workflow command in it is honoured.
- **Setup is trusted like CI on the default branch, and it runs as root into every stage.** The privileged-config check catches the system-wide places a harness or sudo reads. `setup` adds every repository file the setup command names to `FACTORY_PROTECTED_PATHS` on every route, anchored at the root (`/scripts/ci/setup.sh`), so a worker's commit cannot change it; doctor FAILs while one is unprotected. A file is a word with a directory, an extension or a leading `./`, or the script after `bash`, `sh`, `node`, `python` and the like. A file the named one reads (a `Makefile` for `make setup`, `package.json` for `npm run setup`) is not detected; list it with `--protected-paths`. Setup warns, with a sandbox, when the command names no such file.
- **One Vercel project per trust domain.** Every adopter whose sandboxes share a project shares its listing and its credentials, and the image check is only as strong as the project's boundary. Give each adopter, or each group of repositories with the same owners, its own project and token.
- **Refresh.** `FACTORY_IMAGE_REFRESH: merge` (default) builds on each push to the default branch until today's recorded builds (failed ones included) reach `FACTORY_IMAGE_DAILY_MINUTES` (default 5). After that, the nightly build (cron `41 10 * * *` UTC) makes the day's last one. A merge still builds past the cap when no build was even tried since the last nightly time, failed ones included, because GitHub's cron does not always fire; that attempt closes the window. `nightly` builds only on that cron. A head already built, with its snapshot still ready, is not built again, except by hand (`workflow_dispatch` with `image: true`). An expired snapshot is rebuilt on the next trigger.
- **One build at a time** (group `factory-image`, never cancelled by Factory). Any run in the repository can join that group with `cancel-in-progress` and cancel a build; Actions cannot prevent it. The next build destroys any sandbox with the repository's tag that is not a finished image.
- **A stage still runs setup.** A snapshot keeps files, not processes, so services start again. On the image, the setup command is the idempotent fast path.
- **Build minutes per day** are summed from Factory's record, failed builds included. Each build's job summary shows the day's total, the size and the monthly storage cost.

## Sweep

Two kinds of lost work, picked up on the dispatcher's next tick (an event's, a wake's, or the cron's as the backstop) and the sweep job:

- **Lost events (the dispatcher, every tick, `FACTORY_SANDBOX` set).** The sweep names an Objective again, after a three-minute grace for the event's own launch:
  - a Running Objective with no work start since it became Running;
  - a `factory:review` PR with no review start since its label;
  - a stage whose record waits on CI (`waiting: "checks"`) for the branch's current head, once the checks on that head are done (`FACTORY_CI_CHECKS`, else the required checks).

  The launcher re-reads the head and the checks before it starts anything. A Question answered by a maintainer (write access, as `objectiveDecisions` reads it) after the Question was asked, whose requeue was lost, goes back to Queued as the launcher would have put it.
- **Sandboxes and images no live Objective needs (`mode: sweep`, `plugin/scripts/sweep.mjs`).** The `sweep` job runs hourly, by hand (`workflow_dispatch` with `sweep: true`), when an issue labelled `factory:objective` closes, when an issue is labelled `factory:blocked`, and when a `factory/<n>` PR merges; a launch the vendor refused for its quota runs it too. It lists Factory's Objective sandboxes in the vendor's project by tag: `factory=objective`, `factory-repo=<repository id>`, `factory-issue=<n>`, and a `factory-` id. Image sandboxes and anything without those tags are never listed. It destroys one when:
  - its Objective is closed, or there is no issue by that number;
  - the Objective's record names another sandbox, or none;
  - it has been stopped longer than `FACTORY_SANDBOX_IDLE_DAYS` (default 7, counted from the record's last write), with the Objective neither Running nor In review.

  It stops the record's own sandbox, without destroying it, when the sandbox is running, no stage holds it (no live lease) and the Objective is neither Running nor In review: a Block for a vanished stage, a stage that died, a stop that failed. That is an end never answered: its uncollected usage comes out, the sandbox stops, its vendor cost is booked from the totals after the stop, and the record says `stopped`, so `daily_usd` sees the cost on the day it is spent. The stopped sandbox then waits out `FACTORY_SANDBOX_IDLE_DAYS` like any other.

  A live Objective's recorded sandbox stays however long it is stopped. Then this repository's images (found by its tag in the vendor's listing, never another repository's): the current one (the one stages start from: the newest build Factory recorded that the vendor confirms and lists ready, from a commit on the default branch) stays. An older recorded one stays for 15 minutes after a newer build's record superseded it (a stage uses an image only between its launcher's read and its create, inside one five-minute launch job; a sandbox made from it never needs it again), and the rest go. With no confirmed current image, no image goes.

  So the vendor holds, per repository, the current image (and the previous one briefly) and the stop snapshots of Objectives still open. The job log and summary show this repository's snapshot count and size, and the vendor project's, before and after; doctor shows the same when the vendor's credentials are in its run.

Rules for the destroying sweep:

- **At most `FACTORY_SWEEP_MAX_DESTROYS` (default 5) a run;** the rest wait for the next one.
- **A sandbox a stage holds is left alone, and so is one younger than 15 minutes that no record names.** A launcher may be between creating it and recording it. The record's own sandbox is judged at once, so a short Objective's sandbox goes when it closes.
- **An Objective's end destroys its sandbox.** When a stage ends and the issue is closed, the launcher collects its usage, books its vendor cost and destroys the sandbox instead of stopping it; the record says `destroyedAt` and names no sandbox. When the usage read fails (an error, not a missing file), the sandbox only stops and the record says `collected: false`, so the sweep collects the usage and then destroys it.
- **The record's own sandbox is claimed first,** as a launcher claims it (written `running` with a nonce under the record lock, over the record read). A launch that starts meanwhile wins, and the sweep leaves that sandbox. Each later write goes over the record as it is then, while it carries the sweep's claim, so a launch attempt stored meanwhile stays stored. Once the sandbox is destroyed the record names none, so the next launch creates one.
- **Usage the launcher never collected comes out first.** That is a record with a `claim`, a `home` and `collected` not true. The stage's `<home>/factory/out/usage-<claim>.tgz` is unpacked on the runner and uploaded as `factory-usage-<n>` (or `-review`), as the launcher uploads it. Three such slots a run (none in a launcher's quota sweep); a sandbox whose usage, or whose vendor cost still to book, waits for a slot waits for the next run.
- **GitHub gets codes only.** The record keeps its shape. The job summary lists each sandbox with what was done and why, in Factory's words; vendor messages go to the job log.
