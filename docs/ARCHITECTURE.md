# Factory architecture

Factory turns a GitHub issue that describes an outcome (an **Objective**) into merged, validated pull requests. It compiles the Objective into a graph of **Work Items**, runs coding agents on them in parallel, checks each exact result independently, delivers through GitHub, and validates the integrated result before closing the Objective.

Factory is a plugin and CLI installed for one target repository. It is not a hosted service and not a dependency of the target. It refuses to run against its own source repository.

## Core flow

```text
Objective issue
  → compile: pinned sources → Work Item graph → independent plan review
  → project: Work Item issues with native dependencies
  → schedule: ready items with no conflicting paths, up to the concurrency limit
  → execute: agent works in an owned worktree at an exact base
  → validate: commands run on the exact result tree, then independent result review
  → deliver: pull request, required checks, merge
  → finalize: commands and review on the integrated default branch, then close
```

Each step has one owner in the code:

| Step     | Code                                          | What it does                                                                                               |
| -------- | --------------------------------------------- | ---------------------------------------------------------------------------------------------------------- |
| Compile  | `src/compiler.ts`, `src/compiler-wire.ts`     | Pins the Objective and cited sources, asks the planning model for a graph, validates it, runs plan review. |
| Project  | `src/github.ts`                               | Creates or reconciles Work Item issues, labels, sub-issues and dependencies.                               |
| Schedule | `src/scheduler.ts`, `src/phase-admission.ts`  | Orders the graph, finds ready items, reserves capacity per phase.                                          |
| Execute  | `src/execution/`                              | Runs one attempt through an `ExecutionDriver` and collects an exact change.                                |
| Validate | `src/validation.ts`, `src/review-evidence.ts` | Runs validation commands on the result tree and asks an independent reviewer to judge acceptance criteria. |
| Deliver  | `src/delivery/`                               | Publishes and merges pull requests, one at a time or as a native linear stack.                             |
| Finalize | `src/completion.ts`, `src/qa.ts`              | Validates the integrated head, checks coverage of every criterion, seals acceptance, closes issues.        |
| Run      | `src/runner.ts`                               | Coordinates the steps, owns the state snapshot and handles restart, pause and cancel.                      |

## Planning

The planner receives a **pinned source packet**: the Objective body, the base commit, and the exact content of every repository file it cites. Planning, review and activation all bind to the packet's digest, so a changed source or base is detected rather than silently used.

The model makes semantic choices; code fills in facts. The planner picks, by index, which source line authorizes a command or which criterion an item covers. Factory then derives identities, digests and exact command text itself. _Because_ models copy text unreliably, anything the controller already knows is never asked of the model.

Every Objective acceptance criterion must be covered by a typed proof: a result or integrated command, a semantic review, a required CI check, or final review. A plan with an uncovered criterion is rejected before it runs.

Every planning provider shares one prompt, schema and decoder per phase; only the transport differs. `StructuredPlanningModel` in `src/compiler.ts` owns prompts, bounded review retries, parsing and observations. A `PlanningTransport` runs one provider attempt: Codex SDK (`src/compiler.ts`) or Claude Agent SDK (`src/claude-planning.ts`). A transport may adapt a schema to its provider's supported subset; Factory's decoders still enforce the full contract. Codex planning runs tool-free under a scratch `CODEX_HOME` with Factory's own config (`src/codex-planning-isolation.ts`) and a link to the operator's login, so the operator's `config.toml` and `AGENTS.md` never shape a plan.

An independent model reviews the complete plan once. A concrete finding allows one evidenced revision; after that, an unresolved question goes to the operator.

## Work Items

A Work Item declares:

- **owned paths**: literal files or directory prefixes ending in `/` that it may change;
- **dependencies** on other Work Items, and optional exclusive **resources**;
- **acceptance criteria**, **non-goals** and source **citations**;
- **validation commands**, each either observed in the base repository or declared literally in a pinned source;
- a **brief** for the agent, with the cited source sections attached.

Items whose owned paths overlap, or that claim the same resource, never run at the same time. A `qa` item runs checks without an agent or PR. An `aggregate` item joins its children's results and has no agent or PR of its own.

## Execution

An `ExecutionDriver` starts, observes, cancels and collects one attempt. Three kinds exist:

| Driver  | Where the agent runs                                      | Status                                    |
| ------- | --------------------------------------------------------- | ----------------------------------------- |
| Local   | A Factory-owned worktree on this machine                  | Supported                                 |
| Managed | A provider's hosted agent (OpenAI Agents, Claude Managed) | Implemented; hosted qualification pending |

The local driver runs an `AgentHarness`: Codex SDK by default, with optional Claude Agent SDK and GitHub Copilot SDK harnesses, or a registered third-party adapter. **Execution profiles** let the planner assign each Work Item one of several configured harness/model choices.

The harness works only inside its worktree, must not move `HEAD`, and never receives Factory's GitHub credentials. Factory collects the changed files itself, checks ownership and scans for secrets. _Because_ the controller alone publishes, an agent cannot push, merge or change another item's work.

## Validation and review

Validation runs in a fresh worktree checked out at the exact result tree:

1. Hydrate any selected Git LFS content from the local content store.
2. Run each validation command in order and record a receipt: command, exit code, tree.
3. Confirm the worktree is unchanged afterwards; a command that writes tracked or unignored files fails validation.

An independent reviewer model then judges each acceptance criterion against the change, the receipts and the cited sources. It must cite evidence; a criterion it cannot support from complete evidence stays pending for the operator.

## Delivery

The `regular` strategy publishes and merges one pull request at a time. The `native-stack` strategy groups each unbranched chain of Work Items into a GitHub stacked pull request; forks and joins start new stacks after their predecessors merge.

Before merging, Factory checks the exact PR head, the target's branch protection, and every CI check the plan requires before integration. Pending checks wait. A failing required check, whether the source, branch protection or a ruleset requires it, is a wrong result (`work`): it is repaired within allowances, and the new attempt republishes with a lease. _Because_ GitHub only blocks a merge for checks its rules require, Factory enforces source-required checks itself.

## Final acceptance

After all Work Items are integrated, Factory runs the Objective's final commands and final review on the current default-branch head, rechecks that every criterion has accepted proof, records a sealed acceptance of that exact commit and graph, and closes the Objective. Closing every Work Item is not enough on its own.

## State and recovery

Each Objective has one atomic JSON snapshot at `$XDG_STATE_HOME/clockgrove-factory/repositories/OWNER/REPO/objectives/N/state.json`, written with write-then-rename. Configuration lives at `$XDG_CONFIG_HOME/clockgrove-factory/config.json`. Nothing is stored in the target checkout. One controller owns a repository's Objectives at a time, through `controller.lock` and a private `control.sock` in the repository's state directory; `status`, `pause` and `cancel` talk to that owner.

Recovery is one loop: **effect → repeat → reconcile**. Every external effect runs inside a step that is correct when repeated from the top. A restart re-reads the snapshot and GitHub and repeats the current step. _Because_ every effect has an identity, Factory never needs to know whether an interrupted call succeeded.

Diagnostics (`factory diagnostics`, with its `--logs`, `--captures` and `--analyze` modes) are a private timeline of observations. They never drive lifecycle decisions.

### Faults

Only adapters classify errors: the GitHub gateway, the git wrapper, each model adapter, and each execution driver and sandbox provider. They attach a `Fault` (`src/fault.ts`) to the error they throw. Runners read `faultOf(error).kind` and never inspect status codes or messages; an error no adapter classified is a `defect`. _Because_ only the adapter knows whether a 404 means lag, lost access or real absence.

| Kind        | Meaning                      | Examples                                                                                       | Result                                                    |
| ----------- | ---------------------------- | ---------------------------------------------------------------------------------------------- | --------------------------------------------------------- |
| `transient` | Repeat later                 | network, 5xx, rate or usage limit, read-after-write lag, lost response, confirmed-dead worker  | The step repeats                                          |
| `decision`  | Needs the operator           | edited or closed Objective, foreign push or PR edit, PR closed unmerged, paid bound reached    | The scope waits for `factory retry` or `factory cancel`   |
| `work`      | The produced result is wrong | validation failed, criterion refused, worker reported failure, failed required check, conflict | The attempt fails; repair or retry                        |
| `config`    | Setup is wrong               | credentials, permissions, merge commits not allowed, a refused leased push                     | The scope waits; after the named fix the next run retries |
| `defect`    | An invariant broke           | unclassified error, a postcondition still false after the lag window                           | Stop and report                                           |
| `cancelled` | The operator cancelled       |                                                                                                | Stop quietly                                              |

A `transient` fault carries `outcomeUnknown` (the effect may have happened or been paid for) and an optional `retryAt`.

### The step primitive

`step(state, { scope, name, paid }, body, { save, signal, pause })` in `src/step.ts` runs one repeatable effect. The rules for writing a body are in that file's header.

- **Scope.** A step's record lives in `state.repeats` under `item/<id>/<name>` or `objective/<name>`. A `decision` or `config` fault waits in its own scope; siblings keep running. Only cancel stops other items' workers.
- **Body.** Observe first, create idempotently, confirm. "Already exists" is read back and counts as success. `ctx.pending(wait)` reports "not yet" (CI, capacity), which is never a fault.
- **Backoff.** A transient fault repeats with a persisted backoff, 1 s doubling to a 5-minute cap, or at `retryAt`; a restart resumes from the saved record. `ctx.progress()` after any successful call ends the run of faults. _Because_ a long poll that keeps answering is healthy, not an outage.
- **Paid bound.** A paid step (model turn, worker start) wraps its paid call in `ctx.paid`. Only that call's faults with `outcomeUnknown` and no `retryAt` count; a crash during the call counts once on restart; a worker the driver confirmed dead counts through `ctx.paidLost`. The fourth counted fault becomes a `decision`. Records are keyed by item, not attempt, so rotating the attempt never resets the bound; success, `work`, `defect` and `factory retry` do. _Because_ free effects cost nothing to repeat and paid ones cost tokens.
- **Pause.** Pause, drain or handoff ends a wait between tries with `StepPaused`, which is not a fault: nothing is charged, the record stays, and the next run resumes the step.
- **Outage.** Status shows an outage once a run of faults has lasted a minute (at once for a distant `retryAt`). After 24 hours of running time, status offers `factory cancel`; the step keeps repeating. Controller downtime never counts.
- **End.** Success deletes the record; `work` and `defect` clear it too. A `decision` stays in the record, and the body is not called again until `factory retry` clears the scope's records. A `config` fault becomes a `prerequisite` wait naming its fix; the next run clears it and tries again. A step never overwrites another step's unanswered wait.

### Charges

Only a wrong result uses a repair allowance: a `work` fault on an item that is not yet integrated and while no cancellation is unresolved (`cancelError`), or plan review findings. Any other fault, including `transient` and `config`, is never charged. Each charge is recorded once in `state.charges` under its failure event, and consumption is derived from that ledger: `item/<id>/<step>/<round>` for a Work Item failure (`round` counts earlier attempts), `objective/plan/<round>` for a plan revision, `objective/amend/<amendment id>` for an amendment. _Because_ the key names the event, repeating it after a restart or a lost response is free, and a new failure is always charged. Diagnosis is a paid step, so a lost answer repeats within the paid bound and is never charged twice.

### What each stop tells the operator

`factory status` names one command per stop (or none, when Factory acts on its own), and that command continues the Objective or, where noted, ends it with `factory cancel`. Most reasons end with `then factory run` unless a run is known to be active, _because_ the command alone does not restart the run. Repair is available when `repairClasses` includes `implementation` and an implementation allowance fits (a failure event already charged does). A replacement of a rejected graph amendment is admissible when the rejection is a generated one the validator knows (an operator-supplied graph is never replaced), `repairClasses` includes a planning class, a planning revision fits (the rejected attempt's own charge is not carried over, so the default `planningRevisions: 1` is already spent), and ownership is settled (no stop besides the rejection, no Work Item running or published, no recorded subprocess). A rejection holds the coordinator paused: a drain, a handoff or a resume leaves it paused (`setCoordinatorMode` in `src/state.ts`), _because_ the replacement and `factory cancel` both need it, and submitting the replacement lifts the hold. Status computes these from the same functions the commands apply (`src/amendment-admission.ts`, `implementationRepairable` in `src/repair-policy.ts`), so it never names a command they refuse. Permanent refusals (checked before ownership) name `factory cancel` with the reason; a refusal a command settles names that command. A planning that stopped because the base, the Objective body or the sources changed is recorded by the run (`changedSincePlanning`), _because_ status reads neither GitHub nor the checkout, and status then names the commands for a changed configuration.

### Scoreboards

Three suites prove recovery end to end against a strict GitHub HTTP fake (`test/support/github-http-fake.mjs`). They judge the end state from GitHub's request log, the repository and status, not from Factory's internal objects. Dead ends writes state overlays to reach its starting states, and interleavings read each Work Item's status from the run report. _Because_ then they survive refactors of the code they test.

| ------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------- |
| Fault matrix  | A crash before or after, a lost response, or an unavailable burst at every effect boundary of a reference run still reaches its end state. The consistency suite adds lag, rate limits, merge refusals, pagination and other actors.                                                                                                                                                                           | `test/fault-matrix-*.test.mjs`, `test/github-consistency-*.test.mjs` (suite body `test/support/github-consistency.mjs`) |

`test/paid-bounds.test.mjs` drives every paid step the reference run reaches (plan, plan review, result review, final review, execute) to its bound and answers it with the command status names. Diagnose and amend never run in an uninterrupted run: the diagnose bound is tested in `test/charges.test.mjs`, the amend bound in `test/graph-amendments.test.mjs`. The known-bug lists (`test/support/fault-known.mjs`, `D` and `KNOWN` in `test/dead-ends.test.mjs`, `test/support/interleave-known.mjs`) are empty. Fixed races stay in `PINNED` as regressions. A bug you cannot fix yet becomes an inverted entry with a diagnosis that matches only that bug and an open P0 issue; the test fails once the bug is fixed, and then the entry goes. Never loosen an invariant to make a case pass. `test/fault-guards.test.mjs` checks each diagnosis and that the boundary snapshot (`test/support/fault-boundaries.json`) changes only on purpose.

To add a case: a new effect needs only a regenerated snapshot (`FACTORY_UPDATE_FAULT_BOUNDARIES=1`); new GitHub behaviour is a scenario in `test/support/github-consistency.mjs` (run by `test/github-consistency-*.test.mjs`); new persisted state is an overlay in `OVERLAYS` (`test/support/dead-ends.mjs`); a new race is a pinned schedule in `PINNED` (`test/support/interleave-known.mjs`).

## Media and large files

A harness can return several candidate **AssetSets**: groups of files with provenance. Factory stores the bytes by SHA-256, pauses for a human to select one whole set, and delivers it through ordinary validation and delivery. The target's `.gitattributes` decides which files use Git LFS; Factory verifies pointers, uploads, and hydration from a fresh clone.

## Autonomous operation

`factory run --objective N` is the one command: it plans, saves the plan and its review in the Objective's state, and runs a clean or human-accepted plan until the Objective completes, fails or needs a human decision. Running is the consent for that Objective. A rerun resumes from state and never plans an existing plan again. Within each run:

- **Limits**: the optional `autonomy` section of the configuration sets bounded allowances (planning revisions, implementation repairs, result rereviews), per-Work-Item limits, the enabled repair classes and required worker environment. Defaults are on and bounded. Each Objective snapshots its limits when it starts; allowances never reset.
- **Repair**: a diagnosed wrong result uses an allowance instead of stopping. Only a wrong result is charged (see Charges under State and recovery). Diagnosis reads the files the failed result and its merged predecessors own. When the file at fault is owned by a merged predecessor (by the accepted graph's `ownedPaths`) and not by the failing item, no repair is spent: the allowance is given back and the item stops with a decision that names the predecessor, its PR and the file. The named file must be a regular file of the failed result tree. Such a stop counts as a wrong result: `factory retry` starts a new attempt on the integrated head, even if the item has a PR, because resuming the same head would fail and be blamed again. The blame records the graph digest it was made on. The decision quotes the model's diagnosis (capped) and names the working sequence: `factory propose-amendment` (accepted while the Objective is stopped; the next run reviews and projects it) adds a Work Item that depends on the predecessor and takes over the file, `factory run` (if no run is active) merges it, then `factory retry --item` and `factory run`; `factory status` carries the same hint, with the command that works first as `nextAction.command` (`factory propose-amendment`; the retry is in the reason, since a retry before the fix is blamed again). It is judged in one order that the stored decision shares: a pending amendment first (what settles it; a rejected one names `factory cancel` when no replacement is admissible), then whether the graph changed since the blame (an amendment landed: while its Work Items are unmerged, `factory run` when no run is active, `factory resume` when a live owner is paused or draining, and nothing when the owner is running and merging them; else `factory retry --item`), and only then the planning allowance, because the amendment that fixes the predecessor takes the last revision itself. The stored decision is rewritten when an amendment is submitted, rejected or projected. An amendment takes a planning revision, so `propose-amendment` refuses up front when none is left, and the decision then names `factory cancel` instead (limits are recorded per Objective, so a raised limit applies to a new one). Ownership of a path a done item owns can pass to a new item of an amendment; the blame goes to its latest merged owner. A stop that gives back its repair releases only the implementation-repair charge.
- **Amendments** use a planning revision each, charged once under `objective/amend/<amendment id>`.
- **Graph amendments**: a worker can propose missing work; it is compiled, independently reviewed, and added without restarting running items.
- **Queue and supervision**: a `systemd` user service runs explicitly selected Objectives one at a time and keeps running after the terminal closes. It can watch GitHub for new candidate Objectives, but each still needs explicit selection before any model is called.

An exhausted allowance or an undelegated decision stops for the operator.

## Extension points

Seven interfaces in `src/contracts.ts` are the only planned variation points:

| Interface          | Purpose                                  | Implementations                          |
| ------------------ | ---------------------------------------- | ---------------------------------------- |
| `PlanningModel`    | Compile, review plans and review results | Codex SDK, Claude Agent SDK              |
| `ExecutionDriver`  | Run one Work Item attempt                | Local, managed                           |
| `AgentHarness`     | The coding agent inside a local run      | Codex, Claude Agent, Copilot, registered |
| `DeliveryStrategy` | Publish and merge                        | Regular, native stack                    |
| `ContentStore`     | Immutable bytes by digest                | Local                                    |
| `GitHubGateway`    | Issues, PRs, checks, merges              | Octokit                                  |

The runner, scheduler, validator, state store and Git model are deliberately concrete. Add an implementation behind an interface; do not add a new abstraction layer.

## Safety invariants

1. **Workers never get controller credentials.** Only the controller publishes or merges. _Because_ the agent runs untrusted model output.
2. **Validation uses the exact tree.** Every receipt names the tree it ran on, and delivery checks the PR head matches. _Because_ "tests passed" means nothing for a different commit.
3. **Commands need authority.** A validation command must be observed in the base repository or declared in a pinned source. _Because_ the model must not invent what counts as passing.
4. **Owned paths are enforced.** A result that changes files outside its ownership is rejected. _Because_ parallel items must not overwrite each other.
5. **Every effect is safe to repeat.** Issues, PRs and merges are found by stable identities before they are created, and model calls have no side effects. _Because_ recovery is then just "re-read and continue", an interrupted run never needs manual reconciliation.
6. **Failures stop; retries are explicit or within configured limits.** _Because_ the operator controls rework and spending.
7. **Acceptance is proven, not assumed.** Every criterion needs supplied evidence, and the Objective closes only after final validation on the integrated head. _Because_ closed child issues do not prove the outcome.
8. **The target repository is the authority** for requirements, commands, branch protection and acceptance. Factory does not change the target's protection rules.
9. **One active Objective per installation**, one execution mode, and no state migration between incompatible versions. _Because_ these keep recovery simple.
