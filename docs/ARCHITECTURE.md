# Factory architecture

Factory turns an approved Objective in a target repository into a reviewed Work Item graph, exact-tree results and guarded GitHub delivery. It is a plugin and CLI, not a hosted service. Never execute it against its own source repository.

This is a conceptual map. Update it when subsystem ownership or the lifecycle changes, not for ordinary fixes. Exact interfaces and validation rules live in the code; commands and recovery instructions live in the [user guide](USER-GUIDE.md).

## Delivery flow

```text
Objective + pinned sources → compile and review → project Work Item graph
  → schedule → execute → validate exact tree → review acceptance
  → deliver → validate integrated result → seal acceptance → close Objective
```

The target owns requirements, validation commands, permissions, protection rules and acceptance. Factory coordinates that work under the approved configuration and recorded limits; it never grants itself deployment, provider, retry or spending authority.

## Planning and evidence

Pin the Objective, default-branch commit and complete cited source contents. Models select semantic choices; code derives canonical identities, hashes, command text and relationships. Providers share the same grounding and validation rules.

The transient compiler wire separates ordinary work from staged media outputs. Ordinary work omits output-media fields; the decoder supplies the canonical empty roles and zero candidates. Media output requires nonempty roles and a positive decimal candidate-count string, strictly decoded to a safe integer in the WorkGraph. This uses provider-supported array and string constraints rather than numerical bounds that some structured-output transports discard. Source assets remain available in either form. Retained items keep their original canonical fields, and semantic media validation remains authoritative.

Adaptive planning requires both bounded `planningContext` configuration and an explicit Objective declaration:

```markdown
## Adaptive workflow

enabled
```

An absent or `disabled` declaration retains static planning even when configuration is present. Enabled without configuration refuses before provider calls. The declaration is bound by the pinned Objective body digest; changing it cannot switch a retained run's mode. Retrieval uses the existing PlanningModel seam, with `providerAttemptAdmission: "controller-checkpoint-v1"` required for controller-owned dispatch checkpointing and accounting. Opaque adapters refuse before paid calls. Complete required Sources remain independent of optional retrieval. The controller exposes only literal authorized Git selectors and eligible repository memory; repository, visibility, Objective/path scope and source applicability are checked before ranking and supporting-body reads. Planning can return a context request, graph or explicit human dependency. Required unresolved facts prevent graph compilation, while optional stale or unavailable context keeps its actual disposition. Catalogs describe availability rather than supplying missing content or authority.

The existing planning recovery record retains exact automatic results and request batches, immutable content packet references, elapsed lookup accounting, provider calls and consumed result/byte bounds. Frozen scope and bounds bind a planner session across lookup rounds; each admitted turn additionally binds its exact current packet. Independent graph review receives that same retained context, and recovery authenticates it rather than refetching a replacement. Discovery/retrieval execution and preparation snapshots use versions 9/10 and candidate version 4. Expansion graphs use execution/preparation versions 11/12 and candidate version 5. Declared condition candidates use version 6 and preparation version 14. Execution version 13 admits conditional routing, retained workflow reflection and advanced pending graph semantics before their first durable save; its active graph remains unchanged until reviewed projection settles. Pinned recipe candidates use version 7 and execution/preparation versions 15/16, retaining the original recipe admission binding through later graph amendments. Prior snapshots and candidates remain readable under their original semantics. Version guards prevent adaptive work from silently entering a legacy static route.

Versioned workflow recipes are typed advisory workflow contracts, resolved from an exact regular repository Git blob or the installed package assets. A pinned Objective declaration and configured adaptive admission select them. The controller validates arguments, selector scope and actual prerequisites before retaining original and resolved bytes in ContentStore; compiler and independent graph review receive the same resolved contract. Candidate and continuation bind its original base, configuration, source packet, graph and review identities. Restart loads authenticated retained bytes rather than the latest definition. Recipes constrain declared stages, discovery roles, conditions, expansions and integration dependencies while ordinary source/command/ownership/acceptance rules still apply. Pure preview reports finite ceilings and prerequisite gaps, without inventing task counts, price or latency. Recipe changes and Dream proposals never silently replace an active pin.

Dream uses the same scoped repository retrieval for a bounded selection of settled experience. It retains a complete input packet, included/deferred identities and immutable selection checkpoint before its single explicit provider submission, with a separate active-guidance byte budget. Original episodes, prior guidance, proposals, exact reviewed drafts, decisions and provider receipts remain attributable; accepted proposals retain checkpoint ancestry. Missing completion leaves an unresolved submitted call and prevents blind new consolidation. Routine learning capture has no paid call or background daemon, and guidance promotion remains explicit. Native compaction stays adapter-owned.

Repository memory stores immutable canonical manifests and supporting bodies in existing private ContentStore storage. Provenance distinguishes authority, advisory observations, source identities and versions, applicability, validity, completeness and unknown availability. Approved human decisions retain their verified question/answer bindings; historical verdicts and failure/correction leads never become current acceptance. SQLite/FTS is a derived catalog rebuilt from retained manifests, with eligible manifest scanning when SQLite is unavailable, including early Node 22. Catalog rebuilding changes neither lifecycle state nor acceptance, and native session/worktree disposal does not delete required memory. Without an explicit archive binding these files provide local durability only. The Git checkpoint layer uses typed closure extraction, exact immutable originals and normal guarded fast-forward publication. Independently fetched body verification defines remote acknowledgement; SQLite, derived reports and host resources are not the backup. Neither GitHub progress nor a content digest supplies lost bytes or proves foreign ownership has ended.

Discovery is a distinct Work Item kind with selectors, output role/schema, completeness and finite allowances. Deterministic inventory belongs to the controller; semantic classification requires `ExecutionDriver.readonlyDiscovery: "selector-bound-read-only-v1"` and actual adapter preflight enforcement of a read-only harness profile, initially Codex. Unsupported profiles refuse before paid calls. Its private export contains only the selected immutable source bytes, without Git metadata, network or child-agent access. Output authentication binds producer, exact commit/tree, selectors, body references and completeness. Explicit consumer role/field selection supplies information through ordinary dependency edges without making discovery a code base. Discovery creates no code result, QA proof or delivery authority. Discovery output can drive pinned workflow recipes; portable Git-backed recovery is tracked separately.

Reviewed `WorkGraph.expansions` declarations bind a complete discovery role/schema to literal ownership selectors, a migration or cross-cutting work template, exhaustive selection rules, eligible configured profiles/resources, finite child and batch bounds, dependencies and named integration barriers. The controller groups related regular files into deterministic batches and derives child identities from the exact retained envelope, producer manifest/body and batch. Templates pass the same source, command and profile admission as executable work. They are not independently dispatched. A classified inventory needs explicit included/excluded labels for every in-scope entry; unknown classification, partial input, ownership conflict or excess children stops materialization rather than dropping work.

Each envelope materializes once from an immutable input; changed inputs or semantic choices outside that envelope use supported reviewed amendments or successors. The atomic snapshot retains the exact input packet, desired graph, projected mappings and authenticated settlement. GitHub gateways must implement `projectionMutationAdmission: "controller-checkpoint-v1"`: each expansion projection write is saved before submission, and uncertain submitted effects reconcile through authenticated reads without replay. Initial projection of an expansion plan uses the same fence. Existing static projection retains its established contract.

Both delivery modes hold declared integration barriers and their real dependency descendants until authenticated settlement, then rebuild the graph pass to include every concrete child. Materialization adds actual producer/child dependency edges while preserving the original Objective coverage mapping. Started or completed nodes cannot be rewritten. A complete empty inventory settles the expansion with no children; it does not satisfy or waive substantive implementation, QA or final acceptance. Exact-tree checks, independent result/final review and original repair accounting remain authoritative.

Both schedulers preserve completion and explicit priority, then rank remaining dependency critical paths using one common basis: complete declared duration estimates when all unfinished paths have them, otherwise dependency-stage counts. Estimates are advisory and never grant capacity or alter deadlines. Existing ownership, named-resource, host phase reservations, provider slots and operator holds still determine admission. Diagnostics report those actual blockers, observed whole-item elapsed times and delivery-head replacements; missing queue and provider measurements remain unknown. Shared interfaces, package metadata, lockfiles and configuration have one owner, with dependencies only for actual required changed outputs.

Adaptive implementation requests require `childAgents: "disabled"` through the existing driver/harness seams. Supporting adapters enforce the requested native prohibition; unsupported selected adapters refuse before preparation or provider dispatch. The Codex override participates in its retained-session binding, while static requests omit this policy. Factory continues to schedule independent DAG workers within recorded controller capacity. Existing descendant telemetry is an observation, not shared child admission, complete accounting or proof of cessation. No parent budget is copied to an unreported child.

Role-specific adaptive context is selected automatically at expansion, dispatch, diagnosis and review. Required typed outputs, settled interface bodies, sources and decisions stay complete. Expanded workers receive their bound batch entries instead of the whole discovery inventory. Optional retained memory is scoped and ranked before supporting-body reads, uses the recorded lookup bounds, and preserves current/historical/stale/unavailable dispositions without transferring acceptance. Supplied and shared bodies are reused by exact identity. The existing snapshot retains immutable packet identities, dispositions and ContentStore bytes before dispatch; fresh sessions authenticate the same attributable context, while operational state alone governs progress and effects. Native compaction stays adapter-owned. Cache coordination uses existing native-session capabilities and observed cache counters; no paid cache warm-up is currently supported or claimed.

Declared `WorkGraph.conditions` select already reviewed Work Items through `condition: {conditionId, when}`. Supported predicates are complete inventory emptiness and a semantic classification with exhaustive `otherClassifications`. They require a direct unconditional discovery dependency and authenticated producer, attempt, source and body bindings. Missing, incomplete or unrecognized facts remain held. The existing snapshot retains the exact input packet and selected/skipped disposition before closure; a skip supplies no result, command receipt, acceptance verdict or integration. Original coverage owners, discovery producers and expansion barriers remain unconditional. Final review receives condition facts once, referenced by each routed item, and still proves the original acceptance.

Bounded workflow reflection observes useful settled events through current ownership and receipts. It reuses existing critical-path admission, diagnosis and reviewed amendments; it creates no reflection daemon, mandatory model call, new controller or allowance. Proposals retain the observation, suspected cause, eligible pending scope, expected progress/quality effects, remaining limits and reassessment. Missing timing and causal attribution remain unknown. Active records are bounded, with prior immutable ContentStore references retained for attributable experience; reflection never drives recovery from diagnostics or rewrites started work.

Compilation plans a useful execution DAG rather than minimizing item count. Substantial independently implementable and verifiable components become first-class Work Items with disjoint ownership and settled shared contracts; dependency edges name actual required outputs, not shared decisions or a later combined check. Each feature owner completes its relevant implementation, tests and documentation with acceptance and real proof achievable at its own stage. Shared files have one responsible owner. Full end-to-end obligations normally use authorized integrated validation and one independent final Objective review; final-review coverage may belong to an implementation item without claiming an early pass. Feature owners can author combined checks against settled interfaces, while sibling-dependent execution waits for integration. A downstream implementation item needs an identified deliverable that actually consumes completed peer outputs. Read-only QA supplies named required evidence or material-risk proof absent from final validation/review, including source-required late named CI, rather than duplicating final checks. Required runtime layers, orderings, negative controls and complete evidence remain mandatory. Aggregate children express hierarchy with explicit dependencies. Compiler output contains a short sufficient contract without repeating source bodies or other fields, never truncating required facts. Small cohesive changes remain one item when splitting would not improve the useful critical path; graph review needs concrete grounds to flag avoidable serialization.

Work Item repair distinguishes an actual failed-command capture from an explicitly produced semantic acceptance refusal. The existing recovery failure retains the rejected finding or operator decision against its exact tree and criterion, bound to separately retained passing validation receipts. Diagnosis must ground an owned correction in that refusal and complete candidate contents. Missing failed commands do not select the semantic path; unknown evidence remains stopped. Both paths preserve the original attempt and finite repair charge. For a self-contained model refusal after passing validation, diagnosis may omit historical worker input bodies and unrelated pinned source bodies only after authenticating the retained refusal, command authority and complete owned current files against the exact candidate tree. It delivers the original failure and validation, complete owned candidate bodies, relevant authority sources and indexed omission identities inline; tool-free diagnosis does not resolve worker substring selectors. Missing mappings, prerequisites, dependency context or current file evidence use the complete request. Canonical graph inputs, repair evidence, indices, digests and readiness remain unchanged; an omitted body cannot ground actionable repair. Quiet structured-response timeouts surface a retained decision on the first call rather than automatically replaying the unchanged prompt; bounded capacity retries and the existing inactivity limits remain unchanged.

Commands need exact source or verified base authority. Ownership is literal and enforced. Existing acceptance scripts and package-manager/security metadata retain their fixed constraints unless the Objective explicitly authorizes the supported change. Review cannot invent prerequisites, repair quotes into evidence or approve missing facts.

Readiness coverage selects an exact probe and, when supplied sources require it, ordered prerequisite validation rows before that probe. Preparation is authenticated separately in every fresh preflight, worker and final validator checkout; ignored installs and historical receipts do not transfer. The local worker uses the shared validator executor before its provider starts, and drivers unable to authenticate their actual environment refuse such work. Read-only QA executes its authorized setup, probe and checks once in the receipt-owning validator checkout. Preparation receipts never replace semantic acceptance.

Validation runs the approved commands against the exact candidate tree and records its identity and outcomes. Acceptance review starts with its criteria, exact base/result identities and an evidence map. Complete authenticated source and controller evidence remain available in the private read-only workspace; large bodies and historical records need not enter the initial prompt. The reviewer investigates with search and targeted reads, obtaining sufficient evidence for every criterion rather than loading a prescribed repository-wide read set. Claims about absence or preservation may require broader or complete-scope inspection. Missing, incomplete or invalid evidence stays missing, incomplete or invalid; an evidence descriptor or passing unrelated checks does not replace semantic proof.

Installation `reviewArtifacts` selectors are empty by default. An explicit selector binds an exact passed, non-preparation validation command to its JSON stdout receipt, a regular PNG beside that receipt and a tracked candidate file. Before the owned validation checkout is cleaned, the controller authenticates containment, raw-byte size bounds, receipt/PNG digests and the observed candidate digest against the exact result tree, then retains complete bytes in ContentStore with command and tree provenance. Review transports attach those authenticated pixels directly to the existing configured provider input; they add no tools, browser or network permissions. Unsupported transports refuse before dispatch. Final Objective review prefers its own fresh validation images. When none are supplied for a selector, it may inspect retained accepted Work Item pixels only if their original exact result tree equals the final tree and completion, command, artifact and integration bindings remain verified. Their original Work Item provenance stays explicit; they are never relabeled as a fresh final execution, and earlier verdicts do not determine Objective acceptance. Different-tree images supply no current observation. Selection is part of the configuration digest, so changed selectors require a fresh correctly bound Objective.

The canonical review packet retains complete bytes, digests, provenance and completeness flags. When the reviewer has an exported read-only evidence workspace, rendered bodies over 2,048 bytes use authenticated files in its existing root: pinned authority/source bodies under `pinned/`, controller records under `evidence/`, and exact current-tree files separately under `candidate/`. Small records can remain inline; calls without exported files retain inline delivery. This threshold changes delivery, not evidence completeness or the finding schema. Reviewers may inspect ranges or structured keys and explain the file/range supporting a finding, while citing the existing packet-local evidence index. A descriptor proves availability and identity; it does not establish that a criterion passed.

Compilation derives material risks from the Objective's flows and planned architecture and assigns their proof responsibility without adding acceptance requirements or prescribing an implementation. Item review investigates its contract and those risks in current source; the source map supplies leads without restricting relevant discovery. Final review checks every original criterion on the integrated source, concentrating investigation on current interactions and unmet proof obligations rather than treating earlier verdicts as acceptance. When pending asynchronous work can outlive selection or navigation, trace whether success, error and cleanup completions still belong to the current intent. Distinguish static source proof from runtime ordering/state-transition coverage; passing happy-path checks do not prove unexercised orderings.

Successful Work Item review retains bounded complete literal evidence actually cited by its findings in the existing validation snapshot. Final review can retrieve those findings, designs and bodies through the evidence map with their original references and exact result/candidate tree relationship. Sharing identical evidence bytes with matching provenance avoids duplicate delivery; prior verdicts remain advisory. A result already at the final tree supplies exact path, mode, blob and ownership descriptors without repeating its patch text. Original source references retain their pinned-source meaning. Verified source bodies and command receipts may be reused only within their authenticated scope; missing legacy or bounded-out bodies require ordinary source/evidence reads. Compilation may settle useful shared interfaces and state ownership within the Objective's constraints so independent components can proceed without repeatedly inventing their contract.

An accepted human planning answer retains its original question, answer, actor, reason, time and graph/packet/review binding in the active continuation. The shared derived worker brief and Work Item/final review observations supply that same verified context for both CLI and GitHub answers. It resolves the named choice within the Objective; it does not change the immutable graph, grant source or command authority, or prove that the app implemented the choice. Review observations use the existing literal controller-evidence grounding path. Historical absent context stays unavailable.

## State and recovery

Each Objective has one atomic local continuation snapshot outside the target repository. An exclusive verified owner controls mutations; resource and configuration identities bind operations to the run. Diagnostics and optional captures observe the run and retain actual available usage, but never reconstruct or control lifecycle state.

The sequential background queue freezes an optional whole elapsed deadline in its acknowledged Git owner claim before first dispatch. Restart and re-enqueue reuse that exact binding, including an explicit uncapped admission; configuration changes apply only to fresh Objectives. Human wait and unavailable-host time count toward the deadline. The existing runner owns expiry and resource cancellation, and an expired admission without continuation cannot start provider work.

Optional GitHub progress comments project validated continuation state into bounded, append-only snapshots. Meaningful changes are coalesced; timestamps alone never trigger publication. Exact creation intent is retained before the sole dispatch, and an uncertain response permits only read-only matching reconciliation. Publication failure degrades tracking independently of app acceptance. These comments supply observations and links, not lifecycle authority. See the explicit disclosure and decision contracts in [GitHub management](GITHUB-MANAGEMENT.md).

An independently enabled remote decision channel accepts one exactly bound, acceptable pending planning question from an explicitly allowlisted human GitHub account. It authenticates the comment node, literal body, author and edit metadata, then rechecks current plan, ownership, control mode and deadline before atomic consumption. A passive question hold preserves the existing controller; deliberate pause/drain and unresolved effects cannot be cleared by a comment. Remote result acceptance, refusal, retry, repair, cancellation, merges and limit changes remain outside that channel.

Optional Project projection updates only an existing Objective card's explicitly Factory-managed Status field. Verified state determines its configured option; accepted status requires actual accepted Objective closure. A retained prewrite intent permits one mutation, with an original returned response distinguished from later read-only observations. An uncertain submitted write fences later writes to that field; a proven not-sent attempt retains its accounting without creating submission uncertainty. Projection failures do not become app acceptance or authorize recovery.

Prospective controller diagnostics identify each observer session and each formal step body or diagnostic span attempt. Pending polls settle a body attempt without claiming phase success; invalid answers, semantic review refusals and lost workers remain observations even if a later attempt succeeds. Actual readiness command failures bind their enclosing formal attempt; worker readiness and stopped-worker observations retain the original worker identity. Session start and closure bind the configuration and observer source bytes, with monotonic sequence and write/loss counters. The read-only formal-history summary requires a closed, continuous session and paired attempt terminals. A missing closure, write failure, observation after closure or unmatched attempt makes completeness unknown. Supported controller handoff settles its formal controller attempt as paused with `controllerDisposition: handed-off` and closes the observer session with lifecycle `handed-off`, without a fault class. The Objective remains unaccepted; ordinary errors and earlier failure observations remain failed. These receipts describe observed history, not acceptance, permission to retry, billing completeness or resource cessation. Existing logs without these fields remain unknown; no operational snapshot migration or historical backfill is performed.

Resume from supported recorded state. Preserve accepted results, rejected responses, artifacts, failures, usage and spent allowances. A terminal run remains terminal. Never manually edit state, introduce a new root to evade a fence, or replay an external mutation whose outcome is unknown.

Pause, drain, handoff and cancellation follow owned-process and safe-point rules. An aborted execution pass settles its owned work, then leaves cancellation finalization to the controller outside the pass's aborted process scope. The controller closes cancelled Work Item issues, releases settled agent sessions and records terminal cancellation only after those operations succeed; genuine unresolved cancellation remains a fence. Before replacement work, verify the predecessor is terminal where required and that its owned controllers, workers and resources have ceased. Retry, repair and graph amendment use their supported lifecycle operations and recorded finite limits; there is no implicit extra attempt or provider fallback.

Final acceptance checks graph coverage, the integrated candidate and the current remote head before atomic sealing and closure. Publication and integration preserve exact commit/tree/head checks and target branch protection. A changed head is observed and validated through the supported path, never silently accepted.

See [stopping and recovery](USER-GUIDE.md#stopping-and-recovery) for the operator commands. Their implementation and status output are the authority for the next supported action.

### Git durability boundary

The existing atomic snapshot remains the lifecycle authority. Synchronous local saves mark checkpoint data dirty; awaited effect admission publishes the exact intent and charged allowances before external dispatch. A separate transport receipt records the observed archive base, attempted candidate, independently verified acknowledgement and pending loss window. It supplies durability facts, not a second queue, scheduler or external-effect outcome. Private archive binding is explicit and destination visibility is verified before private body publication.

Checkpoint closure traverses validated state and learning schemas, never arbitrary objects that resemble content references. Complete original learning proposals, reviewed drafts, decisions and Dream input checkpoints accompany exact memory bindings; import does not deduplicate them into new observations. Required bodies and unavailable historical data retain their actual disposition. Private-history checkpoints preserve exact source/result Git objects where the target has not independently retained them. Repository-knowledge checkpoints retain eligible selected source bodies and their original Git identities, without source/result Git packs or operational continuation. Native homes, credentials and foreign live-control material are excluded.

Normal Git commits retain immutable predecessors. Publication never force pushes; ambiguous transport holds the exact attempted identities for read reconciliation. Acknowledgement verifies independently fetched bytes rather than a branch name or digest alone. With private-history configured, static and adaptive Objectives use the same storage boundary. Repository-knowledge archives exclude operational continuation. Supported restoration verifies the full closure before installing replicas and records original snapshots and a checked host-layout binding in the existing atomic continuation. Restored work is held before adapter calls or process observation; explicit reconciliation requires authoritative settlement. Latest-tip baseline adoption is a distinct verified-restoration receipt in the existing transport journal, never a fabricated push response. Historical selection cannot grant publication over a newer archive. Queue admission and service activation remain separate lifecycle responsibilities; archive observations grant neither.

The existing controller owns a private remote-only verifier for its lifetime; a foreground operation owns a bounded disposable verifier. Nested operations borrow only a matching repository, configuration, authority and destination binding, and serialize access. The verifier starts empty and obtains objects only from the configured remote, never from the publisher, target checkout, worker or ContentStore. Settled resources are cleaned when their owner closes; an unsettled subprocess quarantines the verifier and retains ownership uncertainty. Publication and baseline adoption use cancellation-aware asynchronous exclusion across processes, separate from the short synchronous guard used to mutate checkpoint metadata.

Each acknowledgment freshly observes and fetches the configured ref, checks `FETCH_HEAD` and expected ancestry, and verifies the current required manifest, bodies and bounds. Initial cache validation authenticates the complete Git object store; strict fetches authenticate additions, and altered or missing previously verified object files refuse reuse. Immutable ancestry and witness summaries can be reused only at their exact captured identities and validation binding; new ancestry still checks sequence, competing ownership, original claims, continuations and cumulative capacity. Current body and retained witness reads authenticate their exact bytes. Previously authenticated immutable body identities can be reused only while the exact opened-file or verified Git-object fingerprint and validation binding remain unchanged; new, changed or missing material follows full validation. Rebuildable caches grant neither live ownership nor acceptance, and eviction or a miss uses full validation. Every external effect retains its distinct pre-effect acknowledgment. Its exact response joins the next pre-effect payload, or the final response and operation completion share one terminal payload.

A successful explicit unchanged-closure synchronization can resolve its current synchronization error only after fresh independent exact remote acknowledgment verification and unchanged journal sequence, acknowledgment and completed transport identity. Holds, changed paths, retention gaps, unknown submissions and Objective/queue history remain intact; successful revalidation never completes the original failed caller.

Read-only queue target preparation can reuse a clean current acknowledgment while independently verifying remote history. Pending local changes still synchronize before the read; each subsequent mutation saves its own intent and requires its full closure and independent pre-effect acknowledgment. An explicit unchanged-payload comparison checks exact closure and remote acknowledgment identity before materializing a second copy of every retained body. Changed publication materializes only the necessary new body bytes after authenticating the complete reference collection.

Background startup performs full archive, Project and retained Objective checks once under the controller’s exclusive lease, before readiness or dispatch. The caller checks local registration, credentials, restored-state holds and ownership, then reports the actual bounded readiness outcome; it does not repeat that full startup scan.

A forwarded queue command carries one finite request identity and deadline. Its actual controller produces a request/configuration-bound completion receipt only after the command's terminal Git acknowledgment. The forwarding CLI can consume that exact receipt without another publication when it has made no later durable write. A later controller operation advancing the archive does not invalidate the earlier completed command. Lost replies preserve submission uncertainty and never permit foreground replay. Local status and cessation acknowledgment remain available independently of slow remote synchronization; neither proves remote completion or resource cessation.

The Project queue reads current membership, order and controls from its explicit GitHub binding. Private checkpoints retain original operation and owner receipts, never a pending-ID list or current queue copy. Admission binds the exact Issue body and host-independent semantic configuration; execution keeps its original configuration and allowance bindings. Queue and Project-bound foreground dispatch share independently acknowledged Git fast-forward ownership claims. Project field writes have no conditional-version protection and settle only from their validated original responses. Versioned queue IPC refuses legacy mutation handlers. Local queue files remain ignored historical bytes, and uncertain foreign ownership cannot become a fresh run.

Project observations paginate all cards and select only the two bound scheduling fields. Complete field catalogs authenticate their unique current names; returned field IDs must match the explicit binding. Matching Issue bodies are hydrated in repository-scoped batches, and foreign cards remain metadata-only. Queue mutations use a distinct current control/target inspection authenticated against complete retained history, rather than a complete roadmap observation. New append order follows the highest authenticated successful historical allocation; a retained admission keeps its place. Current access and the exact target are checked before each effect, and each original validated response supplies only its complete returned facts. Command replies explicitly describe target scope and retain the complete observation’s actual freshness. Incomplete or uncertain responses invalidate reuse. Dispatch, list and sync still require a fresh complete Project observation and exact current contents. Authenticated commands preempt only read-only background polling and retain the controller's checkpoint context across IPC; their cancellation and deadlines remain separate.

An explicit stopped-operator retirement can preserve one unknown metadata withdrawal of an already permanently abandoned pre-snapshot admission. It authenticates the exact original operation, approved producer, abandoned claim, configuration, acknowledged archive, source and ceased owner, and permits only the literal prior queued or requested withdrawn target metadata. The original effect remains unknown and uncompleted; no response, Project mutation, acceptance or replay is created. Only that exact historical admission becomes remote-uncertain and permanently ineligible. Archive validation authenticates the retained retirement and original bindings before applying that narrow exception; all other unknowns remain fenced.

Accounting records observe existing admissions; they neither schedule work nor drive recovery. Final seals bind an immutable subset of original accounting refs and coverage, so subsequent observations cannot rewrite historical totals. Whole-workflow billing and unobserved descendant inclusion stay unproven. Required accounting retention failures hold checkpoint acknowledgment until the exact originals authenticate; missing historical counters remain unknown. Local capture opt-in alone does not authorize archive payload retention. Explicit inspection reports materialized checkpoint bytes separately from reachable logical Git history, without claiming physical remote allocation or authorizing deletion.

Rejected collection records the exact admitted attempt, original fault and permitted source, staging and media observations before checkout disposal. It grants no implementation acceptance or reuse authority. ## Execution, isolation and media

Local workers operate in owned worktrees with private credential-free scratch homes and the configured network/secret policy. Toolchain visibility, commands and writes remain bounded by the approved attempt and ownership. Provider-specific APIs and credentials stay inside their adapters and outside target repositories.

### Conversation continuity and Objective knowledge

Conversation continuity is an optional role-scoped capability at AgentHarness, ExecutionDriver and PlanningModel/PlanningTransport, declared through `sessionCapabilities.resumeRoles`. Factory owns repository, Objective/run, configuration and role bindings and allocates logical session identities. Implementation and result-review sessions also bind the graph and Work Item; Objective-review sessions bind the graph. A planner's immutable input binding survives graph revisions, while each turn binds the current graph and request. Adapters own opaque native references, private storage, current workspace/permission rebinding, accounting and disposal. Receipts persist in the existing atomic snapshot; superseded receipts remain historical. Ready, in-flight, unavailable and released distinguish usable context, unresolved work, unusable context and completed disposal. A native thread is never an acceptance or permission receipt.

The planner can continue from preparation through compilation, correction, diagnosis and graph amendment. Its turns are serialized and explicitly bounded; graph review starts an independent fresh conversation. Implementation, result review and Objective review remain separate roles. Each review can access complete authoritative evidence for the current candidate through its compact evidence map; available bytes are not automatically loaded context. Previous paths, findings and packet-local indices remain historical until current facts establish their applicability. Native agent loops, compaction and working-context management remain the harness's responsibility; continuity adds no attempt allowance or permission.

Local Codex supports planning, independent result/Objective-review and implementation continuity. Claude declares planning continuity only; its implementation and result/Objective-review paths remain fresh pending installed live qualification. Their native reconciliation, history and disposal remain available for existing receipts, preserving active/unknown-turn fences. Copilot and managed execution stay fresh across attempts. Copilot continuation is implemented but disabled pending live account, restart, workspace and accounting qualification. Codex structured tool-free compilation, graph review and diagnosis use `planning.codex.transport`, defaulting to `exec`. Opt-in `app-server` uses an owned stdio client and private native storage; tree result/Objective reviews are explicitly routed to exec with their candidate-only offline permission profile, and SDK workers are unchanged. Routing is selected before dispatch, never as fallback after a transport error. Upstream labels app-server experimental and unsupported for production; see the [user guide](USER-GUIDE.md#retained-conversations).

Before dispatch, the existing snapshot records the bounded turn's invocation, request and evidence identities, plus its optional immutable neutral `deadlineAt`. Expired admission is checked before native dispatch, including after asynchronous startup; local worker limits are unchanged. Older receipts without the field remain valid historical state, and unfinished old turns remain fenced rather than acquiring a deadline through replay. Submitted or uncertain turns cannot automatically replay. Adapter reconciliation may establish active, unknown or settled work; recovered exact final bytes still pass ordinary decoding and grounding against the current request. Diagnostics, process absence and transcript inspection cannot manufacture a settled receipt. Disposal follows owned resource cessation through the adapter, preserving accounting and result artifacts. Elapsed expiry requests cancellation but supplies no native terminal fact: a submitted turn without one stays in-flight even when its local resources settle. Reconciliation retains its separate bounded read/cleanup window and cannot renew the original generation budget.

First turns, legacy tool-free sessions and unsupported adapters keep their existing sufficient inline delivery. New runs admit `exact-request-v1` publication. The existing atomic snapshot retains up to 64 request intents per Work Item, separate from replaceable attempt state.
