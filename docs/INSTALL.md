# Install, tune, upgrade, uninstall

What Factory adds to a repository, how to set it up and check it, the inputs that tune cost, and how to upgrade or remove it. The README has the short version; [USAGE.md](USAGE.md) covers filing and following Objectives, and [LOCAL.md](LOCAL.md) covers local mode.

## Requirements

- A GitHub repository you administer (rulesets need admin), with a CI workflow that runs on `pull_request`.
- The `gh` CLI, logged in, and Node 22 or newer on the machine you run setup from.
- A model credential for the harness you choose: Claude Code, Codex or GitHub Copilot (the table below).
- A merge queue is used where GitHub offers one: repositories an organization owns, public ones and private ones on Enterprise Cloud. Elsewhere Factory runs on strict required checks (the table below), and setup makes the ruleset without a queue.

## Where Factory runs

Every stage runs behind three interfaces: trigger, sandbox and gate (`plugin/scripts/lib/backend.mjs`). GitHub holds every Objective's state on every backend: the branch, the PR, the issue's comments and labels, the board and the usage artifact. The cloud sandbox keeps only its sandbox, its id and tags, and its snapshots at the vendor.

- **Actions (the default):** every job runs on a GitHub-hosted runner, fresh for each job, unless you name your own runner (`--runs-on`). On your own runner Factory installs no packages and loads no AppArmor profile, but it does create a `factory-agent` user, add it to `/etc/cron.deny` and `/etc/at.deny`, and make the runner's home and temp directory mode 700; those outlast the job. It installs the adopter's toolchain, runs the harness, pushes, waits for the required checks, and is discarded. The install is this Action plus the App's two secrets.
- **Local mode:** the same worker and reviewer on a developer's own machine, started by `factory serve` or `factory run <issue>` (the plugin's `bin/`; `/factory:factory-serve` and `/factory:factory-run` in a session). The harness runs on its own login. Every command the model runs, and every command Factory runs on the clone, goes through a sandbox; Factory's own push and Git LFS upload run outside it, from a mirror no sandbox can write. That means no credential stores, writes only in the Objective's clone, the stage's temp directory and its package caches (and, for the harness, the parts of its own state its run needs), and the network limited to GitHub and an allow-list. Its GitHub reach is one fine-grained token for this repository (plus, optionally, the Factory App's key for Blocked and Question notices). An Objective labelled `factory:local` is the local loop's, and the Action leaves it alone. Linux and WSL2 with Claude Code, Codex and Copilot; macOS with Claude Code and Codex only (no Copilot), sandbox verified, not run end to end. See [LOCAL.md](LOCAL.md).
- **Cloud sandbox (opt-in):** one pausable cloud sandbox per Objective on Vercel Sandbox, started from an image built by the adopter's own setup command. Short Action jobs start each stage in it on GitHub events and exit within about thirty seconds; the sandbox stops at every wait between stages, and its cost is booked in a vendor-cost comment on the issue, beside the stage's progress comment, and counts toward `daily_usd`. Turn it on with setup's `--sandbox vercel` and the `VERCEL_TOKEN`, `VERCEL_TEAM_ID` and `VERCEL_PROJECT_ID` secrets. Limits: a stage runs in one sandbox session, which Factory asks to be `timeout_minutes` plus about 16 minutes; Vercel Pro grants up to 24 hours, and on a plan that caps sessions lower the stage is cut to the session granted and Blocks naming the cap if it outruns it; Claude Code, Copilot and Codex (through the Vercel AI Gateway) are proven there. See [ADAPTERS.md](ADAPTERS.md).

The rest of this page is the Actions route; the other two have their own pages.

## Install footprint

| Added | What |
| --- | --- |
| `.github/workflows/factory.yml` | About 190 lines (about 350 with the cloud sandbox), written by `/factory:factory-setup` from the plugin's `workflow-template.yml`: a `dispatch` job, a `queue-watch` job, a `wake` job, a `work` job matrixed over ready Objectives and a `review` job (on the sandbox route, launch, image and sweep jobs instead of work and review, with two short wake jobs for the sweep). Triggers: a `*/10` cron as the backstop, manual dispatch, an issue opened or labelled `factory:objective` or any issue closed, `pull_request` (the App labels a PR `factory:review`, a human marks a Question draft ready, a Factory PR merges, the merge queue drops one), and CI finishing on a `factory/` branch (`workflow_run`, `check_suite`). The worker, review and launch jobs fire the next dispatch at their end, and a `wake` job sleeps to the next deadline only time ends; on the sandbox route the sweep arms its own wakes of minutes and the dispatcher's tick runs an owed image build (docs/PLAN.md). Never from a fork. |
| A Factory GitHub App | Two secrets, `FACTORY_APP_ID` and `FACTORY_APP_PRIVATE_KEY`. Permissions, one list: contents, pull requests, issues, projects: write; checks, commit statuses: read; actions: read, optional (cloud-sandbox logs and session restore); nothing else, never workflows. Checks and commit statuses are how Factory reads required checks; actions read lets a cloud-sandbox stage, which has no job token, read a red job's log. Every push, PR, label, board move and enqueue uses its short-lived installation token, minted for this one repository. |
| A model credential | Claude: `ANTHROPIC_API_KEY` (or workload identity federation with `id-token: write`). Codex: `FACTORY_CODEX_GATEWAY_KEY`, a Vercel AI Gateway key passed as `codex_gateway_key` (Codex then runs through the gateway and bills its credits; it wins over `CODEX_API_KEY`), or `CODEX_API_KEY`; either passed only to the harness step. Copilot: `COPILOT_GITHUB_TOKEN`, a fine-grained token with only the Copilot Requests permission from a user with a Copilot seat, passed as `copilot_github_token` to the harness step only and billed to that seat; doctor checks it cannot write to the repository. `credential: plan` with `CLAUDE_CODE_OAUTH_TOKEN` is allowed for your own repository only. |
| Merge queue, branch protection, label, Project board | GitHub settings, not files. `node <factory clone>/plugin/scripts/setup.mjs --repo OWNER/NAME --yes --ci-checks "<your CI check names>"`, run in your repository's clone, applies them with your `gh` login (rulesets need admin) and creates the labels and, on a repository an organization owns, the board (five columns). GitHub offers a merge queue only on repositories an organization owns (public ones, and private ones on Enterprise Cloud); elsewhere setup makes the ruleset without one and Factory runs on strict required checks. There, a PR that only fell behind is brought up to date by GitHub's update-branch, with no worker run, and one that conflicts goes back to the worker for a rebase each time other PRs merged since its last one, under the Merge rules in PLAN.md. |
| A CI workflow on `pull_request` and `merge_group` | Most repositories have one; add `merge_group:` under `on:` if yours lacks it. |

What each credential can do:

- **The job token:** `contents: read`, `issues: write`, `actions: read` (usage artifacts and the CI workflow's triggers), and on the jobs that tick the dispatcher `actions: write` (work and review also use it to rerun flaky CI jobs); it never writes code. Set your repository's default workflow token to read-only: doctor requires it.
- **The harness:** it holds no GitHub write access: on Actions it runs as its own uid with a read-only token (the runner needs passwordless sudo, as GitHub's hosted runners have); Factory makes every write.
- **Secrets:** they are scrubbed from every non-harness child and masked in the uploaded event log.
- **Cost:** it is capped by `max_usd` per job ($25 by default) and `daily_usd` per day ($100 by default); `max_concurrent` is 3 and `timeout_minutes` 240 unless set; Claude (`--max-budget-usd`) and Copilot (`--max-ai-credits`) enforce the per-job cap inside the run; Codex is checked after each run.
- **What persists:** the worker runs on an ephemeral runner; what persists is the branch, the PR, the plan comment and a usage artifact.

## Set it up

With the plugin, ask a session in your repository's clone to set up Factory (the factory-setup skill, `/factory:factory-setup`): it walks every step below, waits for a yes before each change, and opens the pull request that adds the workflow file. Without it, the steps are:

1. **The workflow file and the GitHub settings.** Clone Factory at its latest release, then run setup in your repository's clone:

   ```sh
   git clone --depth 1 --branch "$(gh release view --repo clockgrove/factory --json tagName --jq .tagName)" \
     https://github.com/clockgrove/factory.git <factory clone>

   node <factory clone>/plugin/scripts/setup.mjs --repo OWNER/NAME --ci-checks "<your CI check names>"        # preview: prints each step, changes nothing
   node <factory clone>/plugin/scripts/setup.mjs --repo OWNER/NAME --ci-checks "<your CI check names>" --yes  # apply
   ```

   It writes `.github/workflows/factory.yml` pinned to the latest release, and creates the labels, the Project board (on a repository an organization owns) and the `factory` ruleset with your `gh` login. `--apply labels|project|protection|workflow` runs one step; repeat it (or give `a,b`) for several. If your CI workflow lacks `merge_group:` under `on:`, add it.
2. **The GitHub App.** Open `https://github.com/settings/apps/new` (or your organization's `/organizations/<org>/settings/apps/new`). Uncheck webhooks and grant exactly the permissions in the table above: projects is under Organization permissions, the rest under Repository permissions. On a repository a user owns, skip projects: no GitHub App can reach a personal account's board, so setup makes none and the labels carry each Objective's state. Create it, generate a private key, note its App ID, and install it on this repository only.
3. **The secrets.** `gh secret set FACTORY_APP_ID`, `gh secret set FACTORY_APP_PRIVATE_KEY < path.pem`, and your model credential from the table above.
4. **Land the workflow file.** Commit `.github/workflows/factory.yml` on a branch and merge it to the default branch through a pull request; its cron and triggers start then.

## The plugin and the Action are one tree

`plugin/` holds the skills the worker and reviewer follow, the agent definitions (model pinned for Claude Code and Codex; Copilot's only when `subagent_model` or `reviewer_model` is set), the task card, the scripts and the workflow template. The Action (`action.yml` at the repository root) runs those scripts from beside it; `/factory:factory-run <issue>` in your own Claude Code or Codex session runs the same worker on your login. Install the plugin with `claude plugin marketplace add https://github.com/clockgrove/factory.git` then `claude plugin install factory@clockgrove` (Codex: `codex plugin marketplace add clockgrove/factory`, `codex plugin add factory@clockgrove`; GitHub Copilot CLI: `copilot plugin marketplace add clockgrove/factory`, `copilot plugin install factory@clockgrove`). Commands: `/factory:factory-file`, `/factory:factory-stop`, `/factory:factory-restart`, `/factory:factory-run`, `/factory:factory-serve`, `/factory:factory-review`, `/factory:factory-score`, `/factory:factory-queue`, `/factory:factory-doctor`, `/factory:factory-setup`. The marketplaces install the plugin from `main`, so a session's commands follow `main`, not the tag your Action pins. An installed plugin stays at the version it was installed at until you update it; doctor (outside a job) and `factory serve` at its start warn when it is older than the release the workflow pins, and name the update: Claude Code `claude plugin marketplace update clockgrove && claude plugin update factory@clockgrove`, Codex `codex plugin marketplace upgrade clockgrove && codex plugin add factory@clockgrove`, Copilot `copilot plugin update factory@clockgrove`, then a new session.

## Check and run

```sh
# in your repository's clone
node <factory clone>/plugin/scripts/doctor.mjs --repo OWNER/NAME --checkout .   # PASS/WARN/FAIL per check with the fix; changes nothing
node <factory clone>/plugin/scripts/setup.mjs  --repo OWNER/NAME --yes --ci-checks "quality"   # GitHub fixes and the workflow file
gh workflow run factory.yml -f issue=811                              # one Objective now; the cron and the ticks do the rest
```

Each job uploads `factory-usage-<issue>` (and `factory-usage-<issue>-review`) with `events.jsonl` and `result.json` (`{harness, harnessVersion, model, ran: {worker, subagent, reviewer, labels}, usd, tokens: {input, output, cached, written}, models, basis, exit, turns, …}`, `ran` being the three models the stage ran on and the harness and model labels that chose them); `bench/score.mjs` turns them, the progress comments and the PR into the scorecard: walk-away, quality, operator minutes, cost by component, minutes per phase, turns, runs and sessions.

## Inputs that tune cost

`harness`, `model`, `subagent_model` and `reviewer_model` (`FACTORY_HARNESS` and the three `FACTORY_*_MODEL` settings in the workflow's env block) are the repository's defaults. An Objective overrides any of them for itself with a label (`factory:harness:<name>`, `factory:model:<id>`, `factory:subagent-model:<id>`, `factory:reviewer-model:<id>`), so a small change can run on a cheaper model and a hard one on the strongest without editing the workflow: [USAGE.md](USAGE.md), Choose the harness and models.

More optional inputs on the Action; each row gives its default. Every Claude call also shares one cached system-prompt prefix across runs.

| Input | What it does |
| --- | --- |
| `effort` | The worker's effort level, for every harness, its answer pass after the review included; pinned to `medium` for Claude so a CLI default change cannot move cost silently. |
| `reviewer_effort` | The reviewer's effort level, passed on every reviewer call except Claude's rerun after a missed review, which always runs on `claude-opus-5-5` at `xhigh`; `high` for Codex as its reviewer agent file says, Claude and Copilot keep their CLI default unless you set one; the job log says `reviewer on <model> at <effort>` and the run's event record carries it. |
| `compaction_window` | The context size in tokens at which the worker and reviewer sessions compact; Claude and Codex, since Copilot has no such setting; the CLI default when empty, a measured lever for large Objectives. |
| `sibling_hold` | `on` by default: a hand-off to review waits while a sibling Objective whose PR conflicts with it is ahead of it, and waiting PRs then go one at a time, each rebasing once (USAGE.md, Siblings that touch the same files); `off` holds no hand-off and says nothing, and overlapping PRs rebase when they conflict (still in the release order), which suits a repository where most Objectives touch the same few files. Scheduling only, so a repository variable may set it; `serve` takes a change at its next tick. |
| `decision_route` | `auto` by default: Factory's decision calls (red-check triage, the drift advisory, the answer gate, the finding check, the rebase check, the answer check) ask the AI Gateway's decision models with `ai_gateway_api_key`, else the stage's own harness on its own subscription or key, on the stage's model (the reviewer's in the review stage). On the harness they cost, all counted toward `max_usd`: one call per failing CI job at a red, a drift check every two minutes while a worker runs, one answer-gate call per review stage whose passes committed, one call per answered reviewer finding, one per file a send-back's conflict pass left other than the branch's, one per new writer comment on a Question when the stage it resumes starts, and a premium request per call on Copilot. `gateway` uses the gateway only (no key: no decision call). `off` runs none, so every red goes to the fix pass, no drift check runs, every answer and fix pass that commits after the review gets a review pass (the answer gate), a reply resolves its reviewer finding unjudged (the finding check), a send-back's conflict pass is checked by matching commits rather than by content (the rebase check), and a writer's comment on a Question resumes it unjudged (the answer check) (docs/ADAPTERS.md, Decision model). |
| `resume_policy` | `fresh` by default: a review fix pass, an answer pass and a conflicting rebase start a fresh session; `fix-passes` resumes the worker's saved session for them, which on Objectives of about 30 turns cost three to seven times more at equal outcomes, so it is for adopters measuring larger ones; every harness, on Actions and in local mode. |
| `prompt_cache_ttl` | Claude only; `off`, the CLI default, until measured: `auto` asks Claude Code for a one-hour prompt cache on the main conversation when the run bills an API key, which otherwise gets five minutes and so re-writes the prefix after every CI wait; `1h` or `5m` force one; the usage record's `cache` shows the writes after each wait, see bench/README.md. |
| `harness_version` | The npm version of the harness CLI; `latest` by default, and the version actually installed is recorded in the usage record. It pins the harness the workflow's env block names only: another harness, chosen by an Objective's label, a run's override or a repository variable, installs its latest. |
| `allowed_domains` | The hosts the harness's sandboxed commands (Claude Code, Codex or Copilot) may reach on Actions and in a cloud sandbox beyond GitHub and the npm and Yarn registries, comma or space separated, `*.example.com` for its subdomains, for every Objective: the counterpart of local mode's `FACTORY_LOCAL_DOMAINS`; PLAN.md, Credentials and billing. One Objective's own host goes in its `factory:host:<host>` label (USAGE.md, Open a network host for one Objective). |

## Settings in layers

A repository's Factory settings resolve in layers, each over the one below:

1. Factory's defaults (each input's description in `action.yml`).
2. The workflow's `env:` block on the default branch: the reviewed baseline, changed through a pull request.
3. Repository variables named `FACTORY_<NAME>` (Settings, Secrets and variables, Actions, Variables; or `gh variable set FACTORY_MAX_CONCURRENT --body 6`), for a change that needs no pull request. Anyone who can push to the repository can set them (write access on an organization's repository, any collaborator on a personal one), as can a token granted Variables write: they change these settings with no pull request and no review. Only the repository's own variables count (below). Every route reads the same variables: the Action's jobs through the workflow's `vars` input, a cloud sandbox's stages from the launcher that starts them, and local mode through its token (LOCAL.md).
4. In local mode, the machine's own environment: the `FACTORY_LOCAL_*` settings, and the harness, models and session settings (LOCAL.md, Configuration).

These stay in the reviewed workflow file only, since they steer trust, where money goes, whom Factory answers and what gates a merge, what a stage may reach or receive, or how it is set up, which binaries it runs and on which Node.js: `FACTORY_CREDENTIAL`, `FACTORY_AUTO_MERGE`, `FACTORY_NOTIFY`, `FACTORY_MAINTAINERS`, `FACTORY_THIRD_PARTY_REVIEWERS`, `FACTORY_CI_CHECKS`, `FACTORY_PROTECTED_PATHS`, `FACTORY_ALLOWED_DOMAINS`, `FACTORY_LOCAL_DOMAINS`, `FACTORY_WORKER_SECRETS`, `FACTORY_LOCAL_ENV`, `FACTORY_SANDBOX`, `FACTORY_HARNESS_VERSION`, `FACTORY_SETUP`, `FACTORY_INSTALL`, `FACTORY_BUDGET_COMMAND`, `FACTORY_LOCAL_SETUP`, `FACTORY_LOCAL_DB`, `FACTORY_PG_BIN`, `FACTORY_NODE_VERSION`, and the ids the credentials go with and the dispatcher's own value (`FACTORY_APP_ID`, `FACTORY_ANTHROPIC_OIDC_EXCHANGE_URL`, `FACTORY_VERCEL_TEAM_ID`, `FACTORY_VERCEL_PROJECT_ID`, `FACTORY_IMAGE_OWED`). A variable with one of those names, a `FACTORY_*` name that is no setting, or a value Factory would not take as given (a cap that is not a number, a harness that is not `claude`, `codex` or `copilot`, a `FACTORY_RESUME_POLICY` that is neither `fresh` nor `fix-passes`) is named in the job log, `serve`'s log and doctor, and ignored. Caps, money, the harness, models and effort, the validation commands (`FACTORY_VALIDATION`, `FACTORY_LOCAL_VALIDATION`, `FACTORY_LOCAL_DB_INIT`) and the sweep's settings may be variables.

- A variable that sets another harness than the workflow's drops the workflow's models and effort for that harness's defaults, unless variables set those too; the jobs install that harness at its latest version, since `FACTORY_HARNESS_VERSION` pins the workflow's own harness.
- On Actions a variable can lower `FACTORY_TIMEOUT_MINUTES` but not raise it past the workflow's value: the runner jobs' own `timeout-minutes` is the file's.
- Factory's variables are the repository's own: set them on the repository. An organization-level `FACTORY_*` variable is not supported. The Action cannot tell the two apart (its `vars` context holds both, and the job token cannot list the repository's own), so there an organization variable the repository does not override would apply; local mode lists only the repository's own. `factory serve` and doctor (with `--local`, or a login that can read them) name each organization `FACTORY_*` variable shared with the repository.
- The workflow passes the variables only once it is rendered with `vars` on every Factory step: re-render it (Upgrade, below). An older file has no variable layer on Actions.
- `doctor` prints each effective setting and its layer (`settings`), and `factory serve` does at its start; a running `serve` takes a variable's change as it takes the workflow's (LOCAL.md, Settings and repins while `serve` runs).

## Third-party reviewers

A reviewer App outside Factory, such as Greptile, can be part of each PR's review. Name it by its login in the workflow's env block on the default branch (or `third_party_reviewers` under `with:`), comma-separated for more than one:

```yaml
env:
  FACTORY_THIRD_PARTY_REVIEWERS: greptile-apps[bot]
```

The App must already review the repository's PRs; Factory only reads its reviews. Factory waits up to 20 minutes for that login's review of the head Factory's reviewer read, and the answer pass fixes or rebuts each of its line comments and replies in its thread, as for Factory's own reviewer; its text is untrusted review input, never instructions. The wait holds no runner, sandbox or local slot: after posting its own review, the review stage records the wait in a comment on the PR, takes `factory:review` off and ends (`exit: waiting` on its progress comment). The dispatcher puts the label back once that review exists or the 20 minutes have passed, and the review goes on without running Factory's reviewer again. A reviewer that posts no review of that head in time is left out: the progress comment says `third-party review: ... going on without it`, and the stage goes on to the merge. The workflow's `pull_request_review` trigger ticks the dispatcher when an App's review arrives (a person's review ticks nothing, so name Apps here); a workflow rendered before it waits for the cron, and doctor names it (re-run `setup --apply workflow`). When the reviewer posts nothing, the 20 minutes' end is a wake on a public repository; on a private one it waits for the next event that ticks the dispatcher or GitHub's cron, which can run late, since a sleeper there would bill the minutes the wait frees. Local mode reads the same setting from the env block, and `serve` resumes the review itself. PLAN.md, Review and merge, has the details.

Code scanning needs no setting: its alerts on a PR's lines (`github-advanced-security[bot]`, CodeQL's say) go to the answer pass on every repository, as untrusted input, and Factory resolves each thread it answered (a person's reply alone does not answer one). An alert posted after the answer pass sends the PR back to review, at most twice before the Objective Blocks naming the alerts. With a rule that requires resolved conversations (a ruleset's, or branch protection's), any other unresolved thread Blocks the merge with a reason naming its author, file and line.

## Several accounts

A repository can give GitHub Actions and the cloud sandbox several accounts of a harness, and a person pins an Objective to one with `factory:account:<name>`, as local mode does with a machine's accounts (LOCAL.md, Accounts). Declare their names in the workflow's env block, a JSON object of each harness's accounts in order:

```yaml
env:
  FACTORY_ACCOUNTS: '{"claude": ["claude", "claude-2"], "codex": ["codex-2"]}'
```

- **Names here, credentials as secrets.** The names steer which credential a stage runs on, so only the reviewed workflow file sets them, never a repository variable. Each account's credential is its own secret: the harness's usual secret name with `_` and the account's name upper-cased, each hyphen an underscore (`claude-2`: `ANTHROPIC_API_KEY_CLAUDE_2`, or `CLAUDE_CODE_OAUTH_TOKEN_CLAUDE_2` with `credential: plan`; `codex-2`: `CODEX_API_KEY_CODEX_2` or `FACTORY_CODEX_GATEWAY_KEY_CODEX_2`; a Copilot account: `COPILOT_GITHUB_TOKEN_<NAME>`). An account named after its harness (`claude`) uses the usual secrets, so a second account needs no change to the first. `credential` (`api` or `plan`) applies to every Claude account, so mixing plan-token and API-key Claude accounts is not supported. Accepted: Claude subscription tokens and API keys, Codex API keys and gateway keys, Copilot tokens. A ChatGPT login for Codex (an `auth.json` or its access token) is refused on these routes, as OpenAI advises an API key for CI; run such an account in local mode. A stage on an account runs on that account's secret alone, passed to its step as the input: no job-level credential variable (a bare one or a `FACTORY_<NAME>` in the env block, which doctor names), and no Claude workload identity federation. Every missing-credential fix names the account's own secret.
- **Which account:** a harness's first account is its default. A trusted `factory:account:<name>` label pins the Objective to that account of its harness: it counts only when the person who last applied it can push or is a maintainer the workflow names, and it is never an edit. With no account label on the issue, the pin is the newest one someone who can push (or a maintainer the workflow names) applied and has not removed since; applying one while an earlier pin is already off the issue replaces it, so a replaced pin never comes back. A person who cannot push can neither move the pin nor take it away; with no such pin, the default. A label naming no account of the Objective's harness, or applied by someone who cannot push, Blocks the stage (cause `setup`). Two account labels never Block: no stage starts until one is left. The dispatcher leaves a Queued Objective unpicked; a review that meets them takes `factory:review` off its PR and records the wait there, and the dispatcher puts the label back once one label or none is left; a work stage that meets them (a second label added as it started) goes back to Queued, or, sent back with an open PR, to In review, and the dispatcher sends no PR back to a work stage while two are on.
- **Only that account's secret reaches the stage.** Setup renders the declared accounts into the workflow. Each work, review and launch job has an `account` step first (the Action's `account` mode: it reads the issue's labels and the labeler with a read-only App token, and no secret). Each credential input of the stage's step names every declared account's secret by its fixed name and passes the one of the account that step picked (`(steps.account.outputs.account == 'claude-2' && secrets.ANTHROPIC_API_KEY_CLAUDE_2) || …`), so no other account's secret is in that step's environment, the harness's, a child's or the cloud sandbox's. The workflow never looks a secret up by a computed name: GitHub would then send the runner every repository and organization secret. Only the secrets the workflow names reach the runner, and only the ones a step names reach that step. The stage, and the launcher before it starts a sandbox, read the labels again and Block if they pick another account by then. A Codex ChatGPT login is refused there too, before any sandbox is started.
- **Automatic choice, off by default:** with `FACTORY_AUTO_ACCOUNT: "1"` in the same env block, a stage with no account pin starts on a free account of its harness, and a usage limit holds only the account that met it. It steers which credential a stage runs on, so only the workflow file sets it, never a repository variable; unset, empty or `0` is off, and any other value is named by doctor and leaves it off. It applies to a harness with two or more declared accounts; with it off, or with one account, every stage runs exactly as above. The rendered workflow names both settings in a comment above its env block.
  - **Holds on GitHub:** a usage limit with a reset records a hold on that account until the reset, as one comment by Factory's App on Factory's own holds issue (`Factory: account holds`, label `factory:holds`, made at the first limit, closed and locked), so every later job reads it, with no state on any machine. Only Factory's own comments there count, and only as written: a record edited since holds nothing. A person who can push lifts an account's holds with `factory hold release <account> --repo OWNER/NAME` from a clone (`factory hold list --repo OWNER/NAME` shows them): it posts their release record there with their own token (local mode's, else their `gh` login), which ends every hold and guess of that account recorded before it, and its back-off count, for the next job whose workflow pins this Factory release or later (a job on an earlier one still holds it until its reset). The command reads its comment back as a job would and exits 1, saying why, when it will not count (a token that is no person's, or a person who cannot push). A release counts only from a person who can push (their association, else their permission read) and only as written; it is deleted with the records it could end, nine days on. Deleting a hold's comment lifts that hold too; unlocking the issue, retitling it or taking its label off drops every hold on it until Factory's next limit, whose writer finds its own issue again and puts the label back. Two jobs meeting their first limit at once can each open one; both count until a later writer copies the newer one's holds to the oldest and retitles and closes it, as it does an unlocked one a failed lock left (never one opened in the last ten minutes, which another job may still be locking). A provider that refuses again past the reset it stated gets a growing floor (2, 5, 10, then 15 minutes), and a usage limit or quota with no reset reported (Copilot's always, Codex's when its rate-limit snapshot names none) is recorded as a guess the choice passes over for an hour, four hours after a second in a row, then a day. A hold's comment is deleted an hour after it ends, a guess's a day after, by the next job that records one, so a limit again within that day counts as one in a row. Nothing is written for a served pass, so a back-off count or a guess ends that way, not at the next served pass as in local mode.
  - **Which account:** the `account` step reads the holds with its read-only token (one labelled issues query, and that issue's comments once it exists) and picks, of the harness's accounts no hold or guess covers, the account the Objective's previous stage ran on while that stage's prompt cache is still warm (below), since a move would lose the cache; else by quota (below): first one never measured, then those with a reading, the most quota left first for the Objective's models (the step does not know which stage it picks for, so every model the Objective's stages run counts: Claude Code's `seven_day_opus` and `seven_day_sonnet` windows only when one of them is of that family or a harness default, its `overage` window never), last those that ran a stage and reported nothing; then, within a group and for equal shares, the one whose last usage limit was met longest ago (one with none recorded first), then the Objective's turn (a hash of its number over the accounts in declared order, so Objectives spread across them whatever their numbers). Within each quota group, the account with the fewest stages started since its reading goes first, so stages that start before the next reading spread over the accounts. These routes write no start record of their own: the step counts each stage's progress comment on its Objective, Factory's own, created after the account's newest reading, whose harness line names the account (one more read: the newest page of the repository's issue comments). A stage still setting up has not named its account there yet, and past one page (100 comments) the counts are lower bounds; if the read fails, it weighs none and the log says so. With every account held, it picks the one whose hold ends first, and the stage runs as with one account: it waits for the reset in place when that falls within its time, else Blocks, cause `provider-quota`, naming the reset. A pin, a label or one a removal left standing, wins, held or not; with the setting on, each stage reads the Objective's timeline once to tell such a pin from the step's own pick, since a pinned stage never moves. If the holds cannot be read, it picks as if none is held, and the log says so.
  - **Quota left:** at its end, each stage with the setting on writes its account's quota reading to the holds issue as a comment of its own (pinned or not), and deletes that account's earlier reading and any reading every window of which has reset: a read of the issue and a write per stage. The reading is how much of each usage window the harness reported used during the stage and when each resets: on these routes only Claude Code on a subscription (`CLAUDE_CODE_OAUTH_TOKEN`) reports one, in its `rate_limit_event` lines. An Anthropic API key, Codex's keys (Codex reports its windows only on a ChatGPT login) and Copilot report none: a stage the provider served there writes that fact instead, which puts the account after every one with a reading. An unchanged silent record is not written again unless it has a warm cache to add. The reading also keeps until when each Objective's last stage on the account keeps its prompt cache warm (its last pass's end plus the cache lifetime Factory sets, `prompt_cache_ttl`, else Claude Code's own: an hour on a plan token, five minutes on an API key; none for Codex and Copilot). A writer also deletes the readings of accounts `FACTORY_ACCOUNTS` no longer declares. An account's share left is its tightest window's; a window counts only until its reset. The `account` step logs the share left of the account it picks, or that the Objective's cache is warm there. Only Factory's own comments count, as written, as for holds.
  - **A limit mid-stage:** a stage that meets its usage limit while another account of its harness is free waits for the reset in place only when it is at most an hour away, since a stage that moves starts fresh on the other account from the branch (its session does not carry over on these routes). Past that it does not Block: it records the hold and ends `waiting`, and the Objective goes on on the free account, the work back to Queued (In review with an open PR, as a send-back) for the dispatcher to start again, a review taking `factory:review` off its PR with a note there, which the dispatcher's next tick puts back. With no account free it waits within its time or Blocks as with one account, cause `provider-quota`, naming the reset and the other accounts' first. A usage limit or quota with no reset reported goes the same way at once when another account is free: its guess is recorded and the Objective goes on on a free account, which the one it left is not while its guess lasts. With none free it Blocks, cause `provider-quota`, naming each other account's hold or guess. Each such move holds the account it leaves, so an Objective's moves end once every account is held. Every limit a harness reports as structure counts. A Codex limit with no rate-limit snapshot in its rollout (one met during a compaction) is reported in prose alone, which Factory does not decide on, so it is no limit here: the stage ends as that failure does, with no guess and no move. A pinned stage never moves: its hold or guess is recorded for other Objectives, and it waits or Blocks as with the setting off. A hold that cannot be written, or a move GitHub refuses, leaves the stage to Block as with the setting off.
- **Recorded by name:** the progress comment's harness line, the usage record's `ran.account` and the scorecard name the account each stage ran on; a stage that went on on another account is counted as that account's usage-limit pause.
- **Doctor** checks the declaration and each account's secret by name, never its value, that the workflow was rendered for the declared accounts, names the automatic setting, and with it on warns about more than one holds issue or an unlocked one. On every workflow it FAILs an expression that reads secrets by a computed name or whole.
- **With no `FACTORY_ACCOUNTS`** the `account` step is skipped and every job names and runs on the usual secrets; an account label then does nothing, and the progress comment says so once.

The accounts are rendered into the workflow, so adding, removing or reordering one means re-rendering it (`/factory:factory-setup`, or `setup.mjs --apply workflow`, which keeps the `FACTORY_ACCOUNTS` line) and merging it. Until then the `account` step picks no account, each stage Blocks asking for the re-render, and doctor names it. Automatic choice needs no other permission than the App's: its records are issue comments, and its issue is made, closed and locked with the same issues permission every Objective's comments use.

## Upgrade

1. Read the release notes between your tag and the new one.
2. Re-render the workflow with that release's setup: in your repository's clone, `node <factory clone at vX.Y.Z>/plugin/scripts/setup.mjs --repo OWNER/NAME --apply workflow --action clockgrove/factory@vX.Y.Z --yes`. It keeps your settings, moves the pin and brings the template's jobs to that release. Re-render on every upgrade: the template belongs to its release, and an older file misses jobs the new Action expects (doctor names some, such as `merge ticks`).
3. Commit the file on the default branch, then run doctor. A running `factory serve` started from a release takes a later pin at its next stage boundary, without a restart (LOCAL.md, Settings and repins while `serve` runs); to go back to an older release, start `serve` from it yourself. Until then the file lacks the newer jobs' events: a file from before the lifecycle labels, for one, ticks the dispatcher on a removed `factory:objective`, an applied `factory:restart` or a changed `factory:draft` only on its ten-minute cron.
4. If you accepted setup's offer to commit Factory's skills into the repository, copy them again from the new release: committed copies never update, and they override the plugin's.
5. Update the plugin on each machine whose sessions or `factory serve` work this repository, then start a new session: Claude Code `claude plugin marketplace update clockgrove && claude plugin update factory@clockgrove`, Codex `codex plugin marketplace upgrade clockgrove && codex plugin add factory@clockgrove`, Copilot `copilot plugin update factory@clockgrove`. Doctor and `factory serve` warn while the installed plugin is older than the pin.

## Uninstall

Delete `.github/workflows/factory.yml`, the App and its two secrets, and any model key. Optionally delete the `factory` ruleset, the labels and the Project. For local mode, also delete `~/.config/factory` (the tokens), `~/.cache/factory`, the `.factory/` directory in each clone that ran it, and the `factory:local` label. For the cloud sandbox, also delete the three `VERCEL_*` secrets, the Vercel project's sandboxes and snapshots, the image issue and the `factory:image` label. If you accepted setup's offer to commit Factory's skills, delete them too (`.agents/skills/`, `.claude/skills/`, and `.claude/agents/`, `.codex/agents/` or `.github/agents/`), and on your own runner remove the `factory-agent` user. Nothing else is installed.
