# Install, tune, upgrade, uninstall

What Pendulum adds to a repository, how to set it up and check it, the inputs that tune cost, and how to upgrade or remove it. The README has the short version; [USAGE.md](USAGE.md) covers filing and following Objectives, and [LOCAL.md](LOCAL.md) covers local mode.

## Requirements

- A GitHub repository you administer (rulesets need admin), with a CI workflow that runs on `pull_request`.
- A public repository, or a private one on GitHub Pro, Team or Enterprise Cloud: Pendulum needs at least one required check on the default branch, and GitHub Free offers branch rules on public repositories only.
- The `gh` CLI, logged in, and Node 22 or newer on the machine you run setup from.
- A model credential for the harness you choose: Claude Code, Codex or GitHub Copilot (the table below).
- A merge queue is used where GitHub offers one: repositories an organization owns, public ones and private ones on Enterprise Cloud. Elsewhere Pendulum runs on strict required checks (the table below), and setup makes the ruleset without a queue.

## Where Pendulum runs

Every stage runs behind three interfaces: trigger, sandbox and gate (`plugin/scripts/lib/backend.mjs`). GitHub holds every Objective's state on every backend: the branch, the PR, the issue's comments and labels, the board and the usage artifact. The cloud sandbox keeps only its sandbox, its id and tags, and its snapshots at the vendor.

- **Actions (the default):** every job runs on a GitHub-hosted runner, fresh for each job, unless you name your own runner (`--runs-on`). On your own runner Pendulum installs no packages and loads no AppArmor profile, but it does create a `pendulum-agent` user, add it to `/etc/cron.deny` and `/etc/at.deny`, and make the runner's home and temp directory mode 700; those outlast the job. It installs the adopter's toolchain, runs the harness, pushes, waits for the required checks, and is discarded. The install is this Action plus the App's two secrets.
- **Local mode:** the same worker and reviewer on a developer's own machine, started by `pendulum serve` or `pendulum run <issue>` (the plugin's `bin/`; `/pendulum:pendulum-serve` and `/pendulum:pendulum-run` in a session). The harness runs on its own login. Every command the model runs, and every command Pendulum runs on the clone, goes through a sandbox; Pendulum's own push and Git LFS upload run outside it, from a mirror no sandbox can write. That means no credential stores, writes only in the Objective's clone, the stage's temp directory and its package caches (and, for the harness, the parts of its own state its run needs), and the network limited to GitHub and an allow-list. Its GitHub reach is one fine-grained token for this repository (plus, optionally, the Pendulum App's key for Blocked and Question notices). An Objective labelled `pendulum:local` is the local loop's, and the Action leaves it alone. Linux and WSL2 with Claude Code, Codex and Copilot; macOS with Claude Code and Codex only (no Copilot), sandbox verified, not run end to end. See [LOCAL.md](LOCAL.md).
- **Cloud sandbox (opt-in):** one pausable cloud sandbox per Objective on Vercel Sandbox, started from an image built by the adopter's own setup command. Short Action jobs start each stage in it on GitHub events and exit within about thirty seconds; the sandbox stops at every wait between stages, and its cost is booked in a vendor-cost comment on the issue, beside the stage's progress comment, and counts toward `daily_usd`. Turn it on with setup's `--sandbox vercel` and the `VERCEL_TOKEN`, `VERCEL_TEAM_ID` and `VERCEL_PROJECT_ID` secrets. Limits: a stage runs in one sandbox session, which Pendulum asks to be `timeout_minutes` plus about 16 minutes; Vercel Pro grants up to 24 hours, and on a plan that caps sessions lower the stage is cut to the session granted and Blocks naming the cap if it outruns it; Claude Code, Copilot and Codex (through the Vercel AI Gateway) are proven there. See [ADAPTERS.md](ADAPTERS.md).

The rest of this page is the Actions route; the other two have their own pages.

## Install footprint

| Added | What |
| --- | --- |
| `.github/workflows/pendulum.yml` | About 190 lines (about 350 with the cloud sandbox), written by `/pendulum:pendulum-setup` from the plugin's `workflow-template.yml`: a `dispatch` job, a `queue-watch` job, a `wake` job, a `work` job matrixed over ready Objectives and a `review` job (on the sandbox route, launch, image and sweep jobs instead of work and review, with two short wake jobs for the sweep). Triggers: a `*/10` cron as the backstop, manual dispatch, an issue opened or labelled `pendulum:objective` or any issue closed, `pull_request` (the App labels a PR `pendulum:review`, a human marks a Question draft ready, a Pendulum PR merges, the merge queue drops one), and CI finishing on a `pendulum/` branch (`workflow_run`, `check_suite`). The worker, review and launch jobs fire the next dispatch at their end, and a `wake` job sleeps to the next deadline only time ends; on the sandbox route the sweep arms its own wakes of minutes and the dispatcher's tick runs an owed image build (docs/PLAN.md). Never from a fork. |
| A Pendulum GitHub App | Two secrets, `PENDULUM_APP_ID` and `PENDULUM_APP_PRIVATE_KEY`, and the repository variable `PENDULUM_APP_ID`, the same numeric id (no secret: GitHub shows it on every comment the App writes), by which `pendulum report` tells the App's comments from another App's ([REPORT.md](REPORT.md)). Permissions, one list: contents, pull requests, issues, projects: write; checks, commit statuses: read; actions: read, optional (cloud-sandbox logs and session restore); nothing else, never workflows. Checks and commit statuses are how Pendulum reads required checks; actions read lets a cloud-sandbox stage, which has no job token, read a red job's log. Every push, PR, label, board move and enqueue uses its short-lived installation token, minted for this one repository. |
| A model credential | Claude: `ANTHROPIC_API_KEY` (or workload identity federation with `id-token: write`). Codex: `PENDULUM_CODEX_GATEWAY_KEY`, a Vercel AI Gateway key passed as `codex_gateway_key` (Codex then runs through the gateway and bills its credits; it wins over `CODEX_API_KEY`), or `CODEX_API_KEY`; either passed only to the harness step. Copilot: `COPILOT_GITHUB_TOKEN`, a fine-grained token with only the Copilot Requests permission from a user with a Copilot seat, passed as `copilot_github_token` to the harness step only and billed to that seat; doctor checks it cannot write to the repository. Claude on your subscription instead: `credential: plan` with `CLAUDE_CODE_OAUTH_TOKEN`, for your own repository only ([Claude on your subscription](#claude-on-your-subscription)). |
| Merge queue, branch protection, label, Project board, read-only default workflow token | GitHub settings, not files. The default workflow token is its own step, run only when named (below). `node <pendulum clone>/plugin/scripts/setup.mjs --repo OWNER/NAME --yes --ci-checks "<your CI check names>"`, run in your repository's clone, applies them with your `gh` login (rulesets need admin) and creates the labels and, on a repository an organization owns, the board (five columns). GitHub offers a merge queue only on repositories an organization owns (public ones, and private ones on Enterprise Cloud); elsewhere setup makes the ruleset without one and Pendulum runs on strict required checks. There, a PR that only fell behind is brought up to date by GitHub's update-branch, with no worker run, and one that conflicts goes back to the worker for a rebase each time other PRs merged since its last one, under the Merge rules in PLAN.md. |
| A CI workflow on `pull_request` and `merge_group` | Most repositories have one; add `merge_group:` under `on:` if yours lacks it. |

What each credential can do:

- **The job token:** `contents: read`, `issues: write`, `actions: read` (usage artifacts and the CI workflow's triggers), and on the jobs that tick the dispatcher `actions: write` (work and review also use it to rerun flaky CI jobs); it never writes code. Your repository's default workflow token must be read-only, which doctor requires and setup's `default-token` step sets (below).
- **The harness:** it holds no GitHub write access: on Actions it runs as its own uid with a read-only token (the runner needs passwordless sudo, as GitHub's hosted runners have); Pendulum makes every write.
- **Secrets:** they are scrubbed from every non-harness child and masked in the uploaded event log.
- **Cost:** `max_usd` caps each job ($25 by default). `daily_usd` ($100 by default) gates new stages: once the UTC day's spend reaches it, the dispatcher starts and relaunches no stage until the next day, while running stages, review stages and answer passes go on, so a day can end above it. Every stage, on every route, writes its spend so far into its progress comment, and that line is what the day, the finish card and `max_objective_usd` count; a usage artifact is read for its dollars only for a stage whose comment has no spend line, and the finish card reads one for its model alone for a stage whose harness line names none (Copilot at its default model). `max_objective_usd` (unset by default: no cap) caps one Objective across all its stages and parts: every work and review stage checks it before any pass, and once the Objective's known spend reaches it, the stage starts nothing and the Objective Blocks naming the cap and the total (cause `max-objective-usd`); raise or unset it, then re-apply `pendulum:objective`. It counts, since the Objective's last `pendulum:restart` or reopening (a restart starts the count over), the known dollars of every stage of Pendulum's on the issue (its spend line, else its own workflow run's usage artifact), the cloud sandbox's vendor cost, and the decision calls made outside any stage that Pendulum's comments on the issue record (a line in a comment written since then, or dated after that day). A stage on another route Pendulum cannot match to itself, and every run of unknown cost, count nothing. A stage's own spend counts once its spend line is written, so the stage that crosses the cap finishes. `max_concurrent` is 3 and `timeout_minutes` 240 unless set; setup's `--preset first-run` sets `max_usd` 5, `max_concurrent` 1 and `auto_merge` false for a first run; Claude (`--max-budget-usd`) and Copilot (`--max-ai-credits`) enforce the per-job cap inside the run; Codex is checked after each run. A job's passes get `max_usd` less its drift reserve (10% of `max_usd`, at least $0.30, at most `max_usd`), which only the drift advisory spends (`decision_route` below). The caps count only spend a harness, Copilot, the AI Gateway or the sandbox vendor reported (or API-reported tokens at the published rate). A run whose cost was not reported (killed or crashed before it reported, a zeroed Claude result, a resumed Claude Code session before 2.1.277, a Codex model with no price row, a Copilot run whose AI credits were not reported, a relayed gateway call or a gateway decision call the gateway never priced) is shown as unknown, "plus N runs of unknown cost", in the progress comment, the exit line, `result.json`, the day's total and the scorecard; it is not counted against `max_usd`, `daily_usd` or `max_objective_usd` and the job goes on, so a cap can be exceeded by unreported spend. Only the provider's own budget or limit bounds that. Each figure also says how it is billed (`billing` and `usdByBilling` in `result.json` and the spend line), decided on a positive sign only, from the environment the harness gets and what the harness reports:
  - **Billed per use, shown bare:** an Anthropic API key (`ANTHROPIC_API_KEY`, an `apiKeyHelper`, a Console login), workload identity federation, a bearer token to a gateway or proxy (`ANTHROPIC_AUTH_TOKEN`), Bedrock or Vertex (`CLAUDE_CODE_USE_BEDROCK`, `CLAUDE_CODE_USE_VERTEX`), a Codex API key or API auth mode, the AI Gateway key (its decision calls, in a stage or outside one), and a relayed worker key's calls.
  - **"API-equivalent at list prices, on the subscription":** Claude Code's `total_cost_usd` on `credential: plan` (`CLAUDE_CODE_OAUTH_TOKEN`) or on a local login whose Claude Code reports a subscription's rate-limit windows, and Codex tokens priced from the API table on a ChatGPT auth mode (or a local login whose rollout carries a ChatGPT plan's rate limits).
  - **"Copilot AI credits, billed to the seat":** Copilot's credits at `copilot_credit_usd`.
  - **"billing not recorded":** anything else, such as an `ANTHROPIC_BASE_URL` of your own with no key, another `CLAUDE_CODE_USE_*` provider, a key source Claude Code names that Pendulum does not know, a Claude pass that ran on paid extra usage past the plan's limit (its `rate_limit_event` says `isUsingOverage`), or a login with neither sign.

  A stage that mixes them shows each part, in the exit line, the progress comment, the day's total and the scorecard. Both caps count the figure whatever its billing. Claude Code's own `costBasis` is kept on each model in `models`: `list` is its built-in list prices, `managed` your organization's managed-settings pricing, `unknown` a model it had no price for.
- **What persists:** the worker runs on an ephemeral runner; what persists is the branch, the PR, the plan comment and a usage artifact.

## Set it up

With the plugin, ask a session in your repository's clone to set up Pendulum (the pendulum-setup skill, `/pendulum:pendulum-setup`): it walks every step below, waits for a yes before each change, and opens the pull request that adds the workflow file. Without it, the steps are:

1. **The workflow file and the GitHub settings.** Clone Pendulum at its latest release, then run setup in your repository's clone:

   ```sh
   git clone --depth 1 --branch "$(gh release view --repo clockgrove/pendulum --json tagName --jq .tagName)" \
     https://github.com/clockgrove/pendulum.git <pendulum clone>

   node <pendulum clone>/plugin/scripts/setup.mjs --repo OWNER/NAME --ci-checks "<your CI check names>"        # preview: prints each step, changes nothing
   node <pendulum clone>/plugin/scripts/setup.mjs --repo OWNER/NAME --ci-checks "<your CI check names>" --yes  # apply
   ```

   It writes `.github/workflows/pendulum.yml` pinned to the latest release (the other actions it calls are pinned to full commit SHAs, each with its version in a comment, which Dependabot's `github-actions` updates understand; a re-render takes the release's pins again, and its report names each pin it moves), and creates the labels, the Project board (on a repository an organization owns; its node id goes into the workflow as `PENDULUM_PROJECT` when the workflow step runs too, by which every route finds the board; Pendulum uses a recorded board only when it is linked to this repository) and the `pendulum` ruleset with your `gh` login. `--apply default-token` sets the repository's default workflow token to read-only (Settings, Actions, General, Workflow permissions), which doctor requires. It runs only when named, never as part of `all`, so a plain `setup --yes` (a repin, a migration) never changes a setting your other workflows run on. Its preview names each workflow that sets no `permissions:` of its own and so gets a read-only token from then on, a reusable workflow such a job calls that asks for write (which then fails), the ones that set their own, which it leaves alone, and listed workflows not on the default branch, which run from other branches on the same default; give a workflow that writes with `GITHUB_TOKEN` (a push, a comment, a release) its own `permissions:` first. It changes no workflow file. Only `--ci-checks` sets the required checks and `PENDULUM_CI_CHECKS` (`--ci-checks=` clears them). Without it, the protection step keeps the default branch's existing required checks, else requires none, and its preview lists candidates for you to name: the checks that passed on the latest pull request, else the job names of your workflows on pull_request, each marked when its workflow has no `merge_group` trigger (a queued pull request would wait for it until the queue times out) or a `paths` filter (a pull request outside those paths could never merge). `--apply labels|project|protection|default-token|workflow` runs one step; repeat it (or give `a,b`) for several. `--apply app` (the next step) also runs only when named. `--preset first-run` renders the workflow with `max_usd` 5, `max_concurrent` 1 and `auto_merge` false for a first run (`daily_usd` keeps its value); a flag beside it wins, setup warns when a repository variable sets one of those caps over it, and a re-render with the flag (or, for the caps, a repository variable, Settings in layers below) raises them later. If your CI workflow lacks `merge_group:` under `on:`, add it.
2. **The GitHub App.** In your repository's clone, run setup's App step:

   ```sh
   node <pendulum clone>/plugin/scripts/setup.mjs --repo OWNER/NAME --apply app --yes
   ```

   Before anything opens, it checks that the secrets can be saved and that none would be lost: `gh` is logged in, your login is an admin of the repository, and neither secret exists yet (`--replace` overwrites them). Then it prints an address on `127.0.0.1` and opens it in your browser (`$BROWSER` when set). That page sends GitHub a pre-filled App definition (GitHub's [App Manifest flow](https://docs.github.com/en/apps/sharing-github-apps/registering-a-github-app-from-a-manifest)): named `Pendulum (<repo>)` (GitHub App names are unique across GitHub; change it there if it is taken), private to your account or the organization that owns the repository, its webhook inactive, with exactly the permissions in the table above (no projects on a repository a user owns: no GitHub App can reach a personal account's board, so setup makes none and the labels carry each Objective's state). Click Create. GitHub sends the browser back to setup, which turns GitHub's one-time code into the App's id and private key, checks the App GitHub made is the one asked for (its owner, the permissions above with none beyond them, no events), and saves them as the repository's `PENDULUM_APP_ID` and `PENDULUM_APP_PRIVATE_KEY` secrets with `gh secret set`, each value on gh's standard input: the key is never printed, logged or written to a file, and the webhook and client secrets GitHub also returns are dropped. It saves the App's id as the repository variable `PENDULUM_APP_ID` too (`gh variable set`), and as a readable local copy, `~/.config/pendulum/repos/OWNER/NAME.json`, which `pendulum report` takes when its token may not read the variable (LOCAL.md, Set it up). The browser then lands on the App's install page: install it on this repository only. `--secret-scope org` saves them as the organization's secrets instead, shared with this one repository; it needs an organization owner's login with the `admin:org` scope (`gh auth refresh -s admin:org`), and it refuses an organization secret of either name that other repositories already use (saving it for this one would take it from them) or a repository secret of either name (which would win over the organization's). An organization secret pair serves every repository it is granted to; each of them needs the App installed too.

   Setup waits 30 minutes for GitHub's redirect and takes only one that carries the random `state` of this run. If the browser cannot reach `127.0.0.1` after you click Create (setup on a remote machine over SSH, or WSL with localhost forwarding turned off), its error page shows the address GitHub sent it to: paste that address into setup's terminal and press Enter, or open it with `curl '<address>'` on the machine setup runs on. It must reach setup within the hour GitHub gives the whole flow. A redirect whose code GitHub does not turn into an App is given back and setup keeps waiting; the page names your GitHub Apps settings, where one GitHub made anyway is deleted (Advanced, Delete GitHub App). If saving a secret fails after GitHub made the App, setup names the App's settings page: Generate a private key there and save it with `gh secret set PENDULUM_APP_PRIVATE_KEY --repo OWNER/NAME < key.pem` (or `--org <org> --repos <repo>`). The step works with github.com only; on GitHub Enterprise Server, create the App by hand.

   By hand instead: open `https://github.com/settings/apps/new` (or your organization's `/organizations/<org>/settings/apps/new`). Uncheck webhooks and grant exactly the permissions in the table above: projects is under Organization permissions (none on a repository a user owns), the rest under Repository permissions. Create it, generate a private key, note its App ID, install it on this repository only, then `gh secret set PENDULUM_APP_ID`, `gh secret set PENDULUM_APP_PRIVATE_KEY < path.pem` and `gh variable set PENDULUM_APP_ID --body <the App ID>`.
3. **The model credential.** Your model credential from the table above, with `gh secret set` (for Claude on your subscription, [Claude on your subscription](#claude-on-your-subscription)).
4. **Land the workflow file.** Commit `.github/workflows/pendulum.yml` on a branch and merge it to the default branch through a pull request; its cron and triggers start then.

## Claude on your subscription

On a repository of your own, Claude Code can run on your Claude subscription (Pro, Max, Ultra, Team or Enterprise) instead of an API key: the `plan` credential.

1. **Get a token.** On your own machine, run `claude setup-token`. It opens the same browser sign-in as `/login`, then prints a long-lived OAuth token (a year, per Claude Code's Authentication docs) to the terminal and saves it nowhere.
2. **Save it as a secret.** In your repository's clone, run `gh secret set CLAUDE_CODE_OAUTH_TOKEN` and paste the token at its prompt, which does not echo it; `--body` would leave it in your shell history. On a declared account other than `claude`, the secret is `CLAUDE_CODE_OAUTH_TOKEN_<NAME>` ([Several accounts](#several-accounts)).
3. **Select it.** Render the workflow with setup's `--credential plan`, which writes `PENDULUM_CREDENTIAL: plan` into its env block, or change that line through a pull request. Only the workflow file sets it: a `PENDULUM_CREDENTIAL` repository variable is ignored ([Settings in layers](#settings-in-layers)). The workflow already passes the secret to every stage.

With `plan`, every Claude stage (the worker, the reviewer, and decision calls on the harness) gets `CLAUDE_CODE_OAUTH_TOKEN` and no other model credential, so an `ANTHROPIC_API_KEY` secret beside it goes unused. A pass that meets the plan's usage limit waits in place for its reset, up to `usage_limit_waits` times (above), before the stage ends on it. doctor fails without the secret: from your shell its `secrets` row names it, in a job its `claude credential` row.

**Your own repository only.** Pendulum does not check this: no check of the repository's owner, its visibility or the token's account gates `plan`, which runs wherever the workflow sets it. The limit is your Claude plan's terms, which cover ordinary individual use: use the token only where the work is your own, never for a product. Every Objective Pendulum works in the repository runs on your subscription, whoever filed it. Outside local mode, doctor's `claude credential` row warns of this whenever `plan` is set. `credential: login` (the CLI's own login) is refused on Actions; local mode runs on the harness's own login ([LOCAL.md](LOCAL.md)).

## The plugin and the Action are one tree

`plugin/` holds the skills the worker and reviewer follow, the agent definitions (model pinned for Claude Code and Codex; Copilot's only when `subagent_model` or `reviewer_model` is set), the task card, the scripts and the workflow template. The Action (`action.yml` at the repository root) runs those scripts from beside it; `/pendulum:pendulum-run <issue>` in your own Claude Code or Codex session runs the same worker on your login. Install the plugin with `claude plugin marketplace add https://github.com/clockgrove/pendulum.git` then `claude plugin install pendulum@clockgrove` (Codex: `codex plugin marketplace add clockgrove/pendulum`, `codex plugin add pendulum@clockgrove`; GitHub Copilot CLI: `copilot plugin marketplace add clockgrove/pendulum`, `copilot plugin install pendulum@clockgrove`). Commands: `/pendulum:pendulum-file`, `/pendulum:pendulum-status`, `/pendulum:pendulum-stop`, `/pendulum:pendulum-restart`, `/pendulum:pendulum-run`, `/pendulum:pendulum-serve`, `/pendulum:pendulum-review-here`, `/pendulum:pendulum-kick`, `/pendulum:pendulum-handover`, `/pendulum:pendulum-score`, `/pendulum:pendulum-report`, `/pendulum:pendulum-doctor`, `/pendulum:pendulum-setup`. The marketplaces install the plugin from `main`, so a session's commands follow `main`, not the tag your Action pins. An installed plugin stays at the version it was installed at until you update it; doctor (outside a job) and `pendulum serve` at its start warn when it is older than the release the workflow pins, and name the update: Claude Code `claude plugin marketplace update clockgrove && claude plugin update pendulum@clockgrove`, Codex `codex plugin marketplace upgrade clockgrove && codex plugin add pendulum@clockgrove`, Copilot `copilot plugin update pendulum@clockgrove`, then a new session.

## Check and run

```sh
# in your repository's clone
node <pendulum clone>/plugin/scripts/doctor.mjs --repo OWNER/NAME --checkout .   # PASS/WARN/FAIL per check with the fix; changes nothing
node <pendulum clone>/plugin/scripts/setup.mjs  --repo OWNER/NAME --yes --ci-checks "quality"   # GitHub fixes and the workflow file
gh workflow run pendulum.yml -f issue=811                              # one Objective now; the cron and the ticks do the rest
```

Each job uploads `pendulum-usage-<issue>` (and `pendulum-usage-<issue>-review`) with `result.json` (`{harness, harnessVersion, model, ran: {worker, subagent, reviewer, labels}, usd, tokens: {input, output, cached, written}, models, basis, exit, turns, sessions, usdByPass, …}`, `usdByPass` being the stage's known dollars by pass kind (work, review, answer, fix and conflict passes, named from each pass's label), `ran` being the three models the stage ran on and the harness and model labels that chose them, `sessions` the harness calls and sessions in its event stream) and the harness's event stream and saved sessions: on a public repository sealed in `transcript.sealed` unless `publish_transcripts` is on, readable otherwise ([PRIVACY.md](PRIVACY.md), What goes to GitHub); `bench/score.mjs` turns them, the progress comments and the PR into the scorecard: walk-away, quality, operator minutes, cost by component, minutes per phase, turns, runs and sessions.

A job cancelled while its stage runs still uploads `result.json`: the stage writes it on the runner's stop signal (`exit` `cancelled`, its finished passes' dollars, the pass it stopped as a run of unknown cost), then stops the agent's harness: its systemd units and processes, which run outside the step's process tree, so on a self-hosted runner the runner's own kill would not reach them. A stage killed with no stop signal first leaves none, and so does a review job cancelled before it has read its PR (it has not yet run anything); the scorecard and `daily_usd` count each as one run of unknown cost.

## Inputs that tune cost

`harness`, `model`, `subagent_model` and `reviewer_model` (`PENDULUM_HARNESS` and the three `PENDULUM_*_MODEL` settings in the workflow's env block) are the repository's defaults. An Objective overrides any of them for itself with a label (`pendulum:harness:<name>`, `pendulum:model:<id>`, `pendulum:subagent-model:<id>`, `pendulum:reviewer-model:<id>`), so a small change can run on a cheaper model and a hard one on the strongest without editing the workflow: [USAGE.md](USAGE.md), Choose the harness and models.

More optional inputs on the Action; each row gives its default. Every Claude call also shares one cached system-prompt prefix across runs.

| Input | What it does |
| --- | --- |
| `effort` | The worker's effort level, for every harness, its answer pass after the review included; pinned to `medium` for Claude so a CLI default change cannot move cost silently. |
| `reviewer_effort` | The reviewer's effort level, passed on every reviewer call except Claude's rerun after a missed review, which always runs on `claude-opus-5-5` at `xhigh`; `high` for Codex as its reviewer agent file says, Claude and Copilot keep their CLI default unless you set one; the job log says `reviewer on <model> at <effort>` and the run's event record carries it. |
| `compaction_window` | The context size in tokens at which the worker and reviewer sessions compact; Claude and Codex, since Copilot has no such setting; the CLI default when empty, a measured lever for large Objectives. |
| `sibling_hold` | `on` by default: a hand-off to review waits while a sibling Objective whose PR conflicts with it is ahead of it, and waiting PRs then go one at a time, each rebasing once (USAGE.md, Siblings that touch the same files); `off` holds no hand-off and says nothing, and overlapping PRs rebase when they conflict (still in the release order), which suits a repository where most Objectives touch the same few files. Scheduling only, so a repository variable may set it; `serve` takes a change at its next tick. |
| `decision_route` | `auto` by default: Pendulum's decision calls (red-check triage, the drift advisory, the answer gate, the finding check, the rebase check, the answer check, the fix-progress check, the edit check, the fence check, the comment check, the plan-answer check) ask the AI Gateway's decision models with `ai_gateway_api_key`, else the stage's own harness on its own subscription or key, on the stage's model (the reviewer's in the review stage). ## Settings in layers

A repository's Pendulum settings resolve in layers, each over the one below:

1. Pendulum's defaults (each input's description in `action.yml`).
2. The workflow's `env:` block on the default branch: the reviewed baseline, changed through a pull request.
3. Repository variables named `PENDULUM_<NAME>` (Settings, Secrets and variables, Actions, Variables; or `gh variable set PENDULUM_MAX_CONCURRENT --body 6`), for a change that needs no pull request. Anyone who can push to the repository can set them (write access on an organization's repository, any collaborator on a personal one), as can a token granted Variables write: they change these settings with no pull request and no review. Only the repository's own variables count (below). Every route reads the same variables: the Action's jobs through the workflow's `vars` input, a cloud sandbox's stages from the launcher that starts them, and local mode through its token (LOCAL.md).
4. In local mode, the machine's own environment: the `PENDULUM_LOCAL_*` settings, and the harness, models and session settings (LOCAL.md, Configuration).

These stay in the reviewed workflow file only, since they steer trust, where money goes, whom Pendulum answers and what gates a merge, what a stage may reach or receive or what it publishes, or how it is set up, which binaries it runs and on which Node.js: `PENDULUM_CREDENTIAL`, `PENDULUM_AUTO_MERGE`, `PENDULUM_PUBLISH_TRANSCRIPTS`, `PENDULUM_NOTIFY`, `PENDULUM_MAINTAINERS`, `PENDULUM_THIRD_PARTY_REVIEWERS`, `PENDULUM_THIRD_PARTY_WAIT_MINUTES`, `PENDULUM_CI_CHECKS`, `PENDULUM_CROSS_OS_WORKFLOW`, `PENDULUM_CROSS_OS_CHECKS`, `PENDULUM_CROSS_OS_WAIT_MINUTES`, `PENDULUM_PROTECTED_PATHS`, `PENDULUM_ALLOWED_DOMAINS`, `PENDULUM_LOCAL_DOMAINS`, `PENDULUM_WORKER_SECRETS`, `PENDULUM_LOCAL_ENV`, `PENDULUM_SANDBOX`, `PENDULUM_HARNESS_VERSION`, `PENDULUM_SETUP`, `PENDULUM_INSTALL`, `PENDULUM_BUDGET_COMMAND`, `PENDULUM_LOCAL_SETUP`, `PENDULUM_LOCAL_DB`, `PENDULUM_PG_BIN`, `PENDULUM_NODE_VERSION`, `PENDULUM_PROJECT` (the board setup made), and the ids the credentials go with and the dispatcher's own value (`PENDULUM_APP_ID`, `PENDULUM_ANTHROPIC_OIDC_EXCHANGE_URL`, `PENDULUM_VERCEL_TEAM_ID`, `PENDULUM_VERCEL_PROJECT_ID`, `PENDULUM_IMAGE_OWED`). A variable with one of those names, a `PENDULUM_*` name that is no setting, or a value Pendulum would not take as given (a cap that is not a number, a harness that is not `claude`, `codex` or `copilot`, a `PENDULUM_RESUME_POLICY` that is neither `fresh` nor `fix-passes`) is named in the job log, `serve`'s log and doctor, and ignored. Caps, money, the harness, models and effort, the validation commands (`PENDULUM_VALIDATION`, `PENDULUM_LOCAL_VALIDATION`, `PENDULUM_LOCAL_DB_INIT`) and the sweep's settings may be variables.

- A variable that sets another harness than the workflow's drops the workflow's models and effort for that harness's defaults, unless variables set those too; the jobs install that harness at its latest version, since `PENDULUM_HARNESS_VERSION` pins the workflow's own harness.
- A layer that names another `PENDULUM_TRIAGE_MODEL` (the default resolved) drops the layers below's `PENDULUM_TRIAGE_MIN_CONFIDENCE`, unless it sets that too: a confidence floor belongs to the model it was set for (PLAN.md, Red-check triage).
- On Actions a variable can lower `PENDULUM_TIMEOUT_MINUTES` but not raise it past the workflow's value: the runner jobs' own `timeout-minutes` is the file's.
- Pendulum's variables are the repository's own: set them on the repository. An organization-level `PENDULUM_*` variable is not supported. The Action cannot tell the two apart (its `vars` context holds both, and the job token cannot list the repository's own), so there an organization variable the repository does not override would apply; local mode lists only the repository's own. `pendulum serve` and doctor (with `--local`, or a login that can read them) name each organization `PENDULUM_*` variable shared with the repository.
- The workflow passes the variables only once it is rendered with `vars` on every Pendulum step: re-render it (Upgrade, below). An older file has no variable layer on Actions.
- `doctor` prints each setting that is set and its layer (`settings`), and `pendulum serve` does once its start checks pass; the settings left at Pendulum's defaults are named only with `--verbose`; a running `serve` takes a variable's change as it takes the workflow's (LOCAL.md, Settings and repins while `serve` runs).

## Third-party reviewers

A reviewer App outside Pendulum, such as Greptile, can be part of each PR's review. Name it by its login in the workflow's env block on the default branch (or `third_party_reviewers` under `with:`), comma-separated for more than one:

```yaml
env:
  PENDULUM_THIRD_PARTY_REVIEWERS: greptile-apps[bot]
```

The App must already review the repository's PRs; Pendulum only reads its reviews. Pendulum waits up to 20 minutes (`PENDULUM_THIRD_PARTY_WAIT_MINUTES`, or `third_party_wait_minutes` under `with:`, at most 1440, 24 hours; workflow file only, since it gates a merge) for that login's review of the head Pendulum's reviewer read, going on as soon as it is posted, and the answer pass fixes or rebuts each of its line comments and replies in its thread, as for Pendulum's own reviewer; its text is untrusted review input, never instructions. The wait holds no runner, sandbox or local slot: after posting its own review, the review stage records the wait in a comment on the PR, takes `pendulum:review` off and ends (`exit: waiting` on its progress comment). The dispatcher puts the label back once that review exists or the wait has passed, and the review goes on without running Pendulum's reviewer again. A reviewer that posts no review of that head in time is left out: the progress comment says `third-party review: ... going on without it`, and the stage goes on to the merge. The workflow's `pull_request_review` trigger ticks the dispatcher when an App's review arrives (a person's review ticks nothing, so name Apps here); a workflow rendered before it waits for the cron, and doctor names it (re-run `setup --apply workflow`). When the reviewer posts nothing, the wait's end is a wake on a public repository; on a private one it waits for the next event that ticks the dispatcher or GitHub's cron, which can run late, since a sleeper there would bill the minutes the wait frees. Local mode reads the same setting from the env block, and `serve` resumes the review itself. PLAN.md, Review and merge, has the details.

Code scanning needs no setting: its alerts on a PR's lines (`github-advanced-security[bot]`, CodeQL's say) go to the answer pass on every repository, as untrusted input, and Pendulum resolves each thread it answered (a person's reply alone does not answer one). An alert posted after the answer pass sends the PR back to review, at most twice before the Objective Blocks naming the alerts. With a rule that requires resolved conversations (a ruleset's, or branch protection's), any other unresolved thread Blocks the merge with a reason naming its author, file and line.

## Cross-OS CI

Off by default. A repository whose CI runs macOS and Windows legs only in the merge queue can have the work stage run them before review, as part of its validation: name the CI workflow file and the legs that count in the workflow's env block on the default branch (or `cross_os_workflow` and `cross_os_checks` under `with:`; workflow file only, since they gate a merge and spend runner minutes):

```yaml
env:
  PENDULUM_CROSS_OS_WORKFLOW: ci.yml
  PENDULUM_CROSS_OS_CHECKS: |
    test (macos-26, 1/1)
    test (windows-2025, 1/1)
```

- **The legs:** one check name per line, exactly as GitHub reports it (a matrix leg's name holds commas). Only those count; Pendulum never infers a leg from a job's name, and a workflow or a list left empty while the other is set Blocks the stage, and doctor FAILs, naming the gap.
- **The run:** on each head the work stage validates, after its other validation (the commands, or the required checks) is green or handed off, Pendulum dispatches the workflow on `pendulum/<issue>` (`workflow_dispatch`) and waits for those legs in that one run: the run GitHub names in its answer, or else the head's dispatched run of that workflow created since the dispatch, which must be on the head Pendulum pushed. When GitHub made it on another head (the branch moved between the push and the dispatch), the stage Blocks and the run is left to finish: Pendulum cancels no run it dispatched, on any route. Only the check runs of that run count, so a check of the same name from another workflow or a `pull_request` run never stands for a leg. A dispatched run already on the head, not cancelled, is waited for instead of a new one. The workflow needs a `workflow_dispatch:` trigger, with the legs running on that event.
- **A red leg** goes back to the worker like any validation red: triage, the fix pass with the failing job's log, the progress check. Once the fix pass commits, the new head gets the other validation first, then the legs; the progress check judges the first red there against the one the fix pass was given, so a Windows fix that breaks Linux is weighed like any red after a fix. A red that was fixed and comes back later in the stage (Linux, then Windows, then the same Linux failure) is no progress, and the stage Blocks; a new red after green validation goes to its own fix pass. The progress comment names each leg's result on each head (`cross-OS CI (ci.yml) on <sha>: <leg>: success; <leg>: failure`).
- **A skipped or neutral leg** did not run, so it is never green: the stage Blocks naming it, and names the run's failing job when one skipped it (a `needs:` failure).
- **The wait** on a head is bounded by `PENDULUM_CROSS_OS_WAIT_MINUTES` (60 by default, at most 1440, 24 hours) from the head's first wait, a triage rerun included, and by the stage's wall clock; a leg not finished by then Blocks the stage, naming the bound.
- **What a dispatched run differs in:** it runs the branch tip's copy of the workflow (`.github/` is a protected path, so a worker cannot change it), with `github.event_name == 'workflow_dispatch'` and `github.ref` `refs/heads/pendulum/<issue>`, so steps conditioned on the event run and an OIDC token's `sub` names that branch (`repo:<owner>/<name>:ref:refs/heads/pendulum/<issue>`), not a pull request; a cloud role trusting `pull_request` subjects does not match it. Because the branch's code runs in it, Pendulum refuses to dispatch, and doctor FAILs, when the workflow's `permissions:` grant write at the top or on any job, naming the grant: any scope at `write` (`id-token` and `packages` included), `write-all`, or any value but `read` and `none` for a scope and `read-all` or `{}` for the whole; unset permissions take the repository's default token, which doctor requires to be read-only.
- **The token:** the dispatch needs Actions write. On Actions the work job's `actions: write`, which the template gives it; in local mode the repository token's Actions read and write (as triage's rerun). A cloud sandbox stage holds only the App's token, which has no Actions write, and Pendulum's App does not ask for one: the stage asks its launcher instead, as it asks for fresh tokens (a `pendulum-stage` repository dispatch, `want: cross-os`, naming the workflow, its branch and the head), and the `launch-event` job dispatches with its own `actions: write`, which the template gives it, then hands the run's id back into the stage, which waits on that run's legs as on the other routes. The launcher dispatches only the workflow `cross_os_workflow` names, only on the stage's own `pendulum/<issue>` branch and only while the branch is at the head the stage asked for; it checks the workflow at that head as the stage does (no write permissions), reuses a dispatched run already on the head, and refuses anything else, which the stage Blocks on. A GitHub read or dispatch that fails for now (a 5xx, the network, a rate limit) is no refusal: the stage asks again, and so does one whose answer named no run it can wait on yet; an ask with no answer is made again every five minutes. With no run within 20 minutes, or the stage's wall clock if that is sooner, the stage Blocks.
- **Where it runs:** on the heads the work stage validates. Not on a send-back's rebase that Pendulum made itself with no conflict, which changes no line of the branch's own, and not on the heads the review stage's answer pass commits: for both, the merge queue's run of the repository's CI on the integrated head is the check.
- **Cost:** macOS and Windows runner minutes bill at a higher per-minute rate than Linux minutes (GitHub's Actions pricing), and the legs run on every head the work stage validates, a fix pass's included. Doctor's `cross-OS CI` row says so while it is on.

## Several accounts

A repository can give GitHub Actions and the cloud sandbox several accounts of a harness, and a person pins an Objective to one with `pendulum:account:<name>`, as local mode does with a machine's accounts (LOCAL.md, Accounts). Setup declares their names in the workflow's env block, a JSON object of each harness's accounts in order:

```yaml
env:
  PENDULUM_ACCOUNTS: '{"claude": ["claude", "claude-2"], "codex": ["codex-2"]}'
```

To add an account:

1. **Render it into the workflow** with setup, which names each account's secret in the jobs, and merge it through a pull request: `/pendulum:pendulum-setup` ("add a second Claude account"), or `setup.mjs --repo OWNER/NAME --apply workflow --add-account claude-2 --auto-account on` (a preview; add `--yes` to write).
2. **Save its credential** as its own secret, named as below and in setup's note: `gh secret set ANTHROPIC_API_KEY_CLAUDE_2`, pasting the key at the prompt. Save it before the pull request merges: a stage on the account, pinned by its label or picked by automatic choice, Blocks naming that secret until it is saved.
3. **Check it:** doctor names any account whose secret is missing.

To run one Objective on it, apply `pendulum:account:<name>` to its issue. Setup's options:

- `--add-account NAME` adds an account of the workflow's harness, `--add-account HARNESS:NAME` one of another (`codex:codex-2`). Adding to a harness that declares none puts its usual account, named after it, first, so that one stays the default on the usual secrets.
- `--remove-account NAME` removes one. A harness left with only its usual account is taken out, which is what declaring none for it means, unless the file already declares it so; with no harness left, the line goes.
- `--accounts JSON` sets the whole declaration, and `--accounts=` clears it.
- `--auto-account on|off` sets automatic choice (below).

Each of `--add-account` and `--remove-account` may repeat or take a comma list. Setup checks the result as the jobs read it and refuses a set they would refuse, with the same line. Its note names the accounts, each new secret to save (a harness's usual one only if not already set), and the secrets the rendered jobs no longer name. When the result names the same accounts as the file, and with none of these options, a re-render keeps the file's `PENDULUM_ACCOUNTS` line as it is, and `PENDULUM_AUTO_ACCOUNT` too unless `--auto-account` is given.

- **Names here, credentials as secrets.** The names steer which credential a stage runs on, so only the reviewed workflow file sets them, never a repository variable. Each account's credential is its own secret: the harness's usual secret name with `_` and the account's name upper-cased, each hyphen an underscore (`claude-2`: `ANTHROPIC_API_KEY_CLAUDE_2`, or `CLAUDE_CODE_OAUTH_TOKEN_CLAUDE_2` with `credential: plan`; `codex-2`: `CODEX_API_KEY_CODEX_2` or `PENDULUM_CODEX_GATEWAY_KEY_CODEX_2`; a Copilot account: `COPILOT_GITHUB_TOKEN_<NAME>`). Save each with `gh secret set NAME`, pasting the value at its prompt, which does not echo it; `--body` would leave it in your shell history. An account named after its harness (`claude`) uses the usual secrets, so a second account needs no change to the first. `credential` (`api` or `plan`) applies to every Claude account, so mixing plan-token and API-key Claude accounts is not supported. Accepted: Claude subscription tokens and API keys, Codex API keys and gateway keys, Copilot tokens. A ChatGPT login for Codex (an `auth.json` or its access token) is refused on these routes, as OpenAI advises an API key for CI; run such an account in local mode. A stage on an account runs on that account's secret alone, passed to its step as the input: no job-level credential variable (a bare one or a `PENDULUM_<NAME>` in the env block, which doctor names), and no Claude workload identity federation. Every missing-credential fix names the account's own secret.
- **Which account:** a harness's first account is its default. A trusted `pendulum:account:<name>` label pins the Objective to that account of its harness: it counts only when the person who last applied it can push or is a maintainer the workflow names, and it is never an edit. With no account label on the issue, the pin is the newest one someone who can push (or a maintainer the workflow names) applied and has not removed since; applying one while an earlier pin is already off the issue replaces it, so a replaced pin never comes back. A person who cannot push can neither move the pin nor take it away; with no such pin, the default. A label naming no account of the Objective's harness, or applied by someone who cannot push, Blocks the stage (cause `setup`). Two account labels never Block: no stage starts until one is left. The dispatcher leaves a Queued Objective unpicked; a review that meets them takes `pendulum:review` off its PR and records the wait there, and the dispatcher puts the label back once one label or none is left; a work stage that meets them (a second label added as it started) goes back to Queued, or, sent back with an open PR, to In review, and the dispatcher sends no PR back to a work stage while two are on.
- **Only that account's secret reaches the stage.** Setup renders the declared accounts into the workflow. Each work, review and launch job has an `account` step first (the Action's `account` mode: it reads the issue's labels and the labeler with a read-only App token, and no secret). Each credential input of the stage's step names every declared account's secret by its fixed name and passes the one of the account that step picked (`(steps.account.outputs.account == 'claude-2' && secrets.ANTHROPIC_API_KEY_CLAUDE_2) || …`), so no other account's secret is in that step's environment, the harness's, a child's or the cloud sandbox's. The workflow never looks a secret up by a computed name: GitHub would then send the runner every repository and organization secret. Only the secrets the workflow names reach the runner, and only the ones a step names reach that step. The stage, and the launcher before it starts a sandbox, read the labels again and Block if they pick another account by then. A Codex ChatGPT login is refused there too, before any sandbox is started.
- **Automatic choice, off by default:** with `PENDULUM_AUTO_ACCOUNT: "1"` in the same env block (setup's `--auto-account on`; `off` takes the line out), a stage with no account pin starts on a free account of its harness, and a usage limit holds only the account that met it. It steers which credential a stage runs on, so only the workflow file sets it, never a repository variable; unset, empty or `0` is off, and any other value is named by doctor and leaves it off. It applies to a harness with two or more declared accounts; with it off, or with one account, every stage runs exactly as above. The rendered workflow names both settings in a comment above its env block.
  - **Holds on GitHub:** a usage limit with a reset records a hold on that account until the reset, as one comment by Pendulum's App on Pendulum's own holds issue (`Pendulum: account holds`, label `pendulum:holds`, made at the first limit, closed and locked), so every later job reads it, with no state on any machine. Only Pendulum's own comments there count, and only as written: a record edited since holds nothing. A person who can push lifts an account's holds with `pendulum hold release <account> --repo OWNER/NAME` from a clone (`pendulum hold list --repo OWNER/NAME` shows them): it posts their release record there with their own token (local mode's, else their `gh` login), which ends every hold and guess of that account recorded before it, and its back-off count, for the next job whose workflow pins this Pendulum release or later (a job on an earlier one still holds it until its reset). The command reads its comment back as a job would and exits 1, saying why, when it will not count (a token that is no person's, or a person who cannot push). A release counts only from a person who can push (their association, else their permission read) and only as written; it is deleted with the records it could end, nine days on. Deleting a hold's comment lifts that hold too; unlocking the issue, retitling it or taking its label off drops every hold on it until Pendulum's next limit, whose writer finds its own issue again and puts the label back. Two jobs meeting their first limit at once can each open one; both count until a later writer copies the newer one's holds to the oldest and retitles and closes it, as it does an unlocked one a failed lock left (never one opened in the last ten minutes, which another job may still be locking). A provider that refuses again past the reset it stated gets a growing floor (2, 5, 10, then 15 minutes), and a usage limit or quota with no reset reported (Copilot's always, Codex's when its rate-limit snapshot names none) is recorded as a guess the choice passes over for an hour, four hours after a second in a row, then a day (`guess_hours`, above). A hold's comment is deleted an hour after it ends, a guess's a day after, by the next job that records one, so a limit again within that day counts as one in a row. Nothing is written for a served pass, so a back-off count or a guess ends that way, not at the next served pass as in local mode.
  - **Which account:** the `account` step reads the holds with its read-only token (one labelled issues query, and that issue's comments once it exists) and picks, of the harness's accounts no hold or guess covers, the account the Objective's previous stage ran on while that stage's prompt cache is still warm (below), since a move would lose the cache; else by quota (below): first one never measured, then those with a reading, the most quota left first for the Objective's models (the step does not know which stage it picks for, so every model the Objective's stages run counts: Claude Code's `seven_day_opus` and `seven_day_sonnet` windows only when one of them is of that family or a harness default, its `overage` window never), last those that ran a stage and reported nothing; then, within a group and for equal shares, the one whose last usage limit was met longest ago (one with none recorded first), then the Objective's turn (a hash of its number over the accounts in declared order, so Objectives spread across them whatever their numbers). Within each quota group, the account with the fewest stages started since its reading goes first, so stages that start before the next reading spread over the accounts. These routes write no start record of their own: the step counts each stage's progress comment on its Objective, Pendulum's own, created after the account's newest reading, whose harness line names the account (one more read: the newest page of the repository's issue comments). A stage still setting up has not named its account there yet, and past one page (100 comments) the counts are lower bounds; if the read fails, it weighs none and the log says so. With every account held, it picks the one whose hold ends first, and the stage runs as with one account: it waits for the reset in place when that falls within its time, else Blocks, cause `provider-quota`, naming the reset. A pin, a label or one a removal left standing, wins, held or not; with the setting on, each stage reads the Objective's timeline once to tell such a pin from the step's own pick, since a pinned stage never moves. If the holds cannot be read, it picks as if none is held, and the log says so.
  - **Quota left:** at its end, each stage with the setting on writes its account's quota reading to the holds issue as a comment of its own (pinned or not), and deletes that account's earlier reading and any reading every window of which has reset: a read of the issue and a write per stage. The reading is how much of each usage window the harness reported used during the stage and when each resets: on these routes only Claude Code on a subscription (`CLAUDE_CODE_OAUTH_TOKEN`) reports one, in its `rate_limit_event` lines. An Anthropic API key, Codex's keys (Codex reports its windows only on a ChatGPT login) and Copilot report none: a stage the provider served there writes that fact instead, which puts the account after every one with a reading. An unchanged silent record is not written again unless it has a warm cache to add. The reading also keeps until when each Objective's last stage on the account keeps its prompt cache warm (its last pass's end plus the cache lifetime Pendulum sets, `prompt_cache_ttl`, else Claude Code's own: an hour on a plan token, five minutes on an API key; none for Codex and Copilot). A writer also deletes the readings of accounts `PENDULUM_ACCOUNTS` no longer declares. An account's share left is its tightest window's; a window counts only until its reset. The `account` step logs the share left of the account it picks, or that the Objective's cache is warm there. Only Pendulum's own comments count, as written, as for holds.
  - **A limit mid-stage:** a stage that meets its usage limit while another account of its harness is free waits for the reset in place only when it is at most an hour away (`usage_limit_move_minutes`), since a stage that moves starts fresh on the other account from the branch (its session does not carry over on these routes). Past that it does not Block: it records the hold and ends `waiting`, and the Objective goes on on the free account, the work back to Queued (In review with an open PR, as a send-back) for the dispatcher to start again, a review taking `pendulum:review` off its PR with a note there, which the dispatcher's next tick puts back. With no account free it waits within its time or Blocks as with one account, cause `provider-quota`, naming the reset and the other accounts' first. A usage limit or quota with no reset reported goes the same way at once when another account is free: its guess is recorded and the Objective goes on on a free account, which the one it left is not while its guess lasts. With none free it Blocks, cause `provider-quota`, naming each other account's hold or guess. Each such move holds the account it leaves, so an Objective's moves end once every account is held. Every limit a harness reports as structure counts. A Codex limit with no rate-limit snapshot in its rollout (one met during a compaction) is reported in prose alone, which Pendulum does not decide on, so it is no limit here: the stage ends as that failure does, with no guess and no move. A pinned stage never moves: its hold or guess is recorded for other Objectives, and it waits or Blocks as with the setting off. A hold that cannot be written, or a move GitHub refuses, leaves the stage to Block as with the setting off.
- **Recorded by name:** the progress comment's harness line, the usage record's `ran.account` and the scorecard name the account each stage ran on; a stage that went on on another account is counted as that account's usage-limit pause.
- **Doctor** checks the declaration and each account's secret by name, never its value, that the workflow was rendered for the declared accounts, names the automatic setting, and with it on warns about more than one holds issue or an unlocked one. On every workflow it FAILs an expression that reads secrets by a computed name or whole.
- **With no `PENDULUM_ACCOUNTS`** the `account` step is skipped and every job names and runs on the usual secrets; an account label then does nothing, and the progress comment says so once.

The accounts are rendered into the workflow, so adding, removing or reordering one means re-rendering it (`/pendulum:pendulum-setup`, or `setup.mjs --apply workflow` with the options above) and merging it. Until then the `account` step picks no account, each stage Blocks asking for the re-render, and doctor names it. Automatic choice needs no other permission than the App's: its records are issue comments, and its issue is made, closed and locked with the same issues permission every Objective's comments use.

## Upgrade

1. Read the release notes between your tag and the new one.
2. Re-render the workflow with that release's setup: in your repository's clone, `node <pendulum clone at vX.Y.Z>/plugin/scripts/setup.mjs --repo OWNER/NAME --apply workflow --action clockgrove/pendulum@vX.Y.Z --yes`. It keeps your settings, moves the pin and brings the template's jobs to that release. Re-render on every upgrade: the template belongs to its release, and an older file misses jobs the new Action expects (doctor names some, such as `merge ticks`).
3. Commit the file on the default branch, then run doctor. A running `pendulum serve` started from a release takes a later pin at its next stage boundary, without a restart (LOCAL.md, Settings and repins while `serve` runs); to go back to an older release, start `serve` from it yourself. Until then the file lacks the newer jobs' events: a file from before the lifecycle labels, for one, ticks the dispatcher on a removed `pendulum:objective`, an applied `pendulum:restart` or a changed `pendulum:draft` only on its ten-minute cron.
4. If you accepted setup's offer to commit Pendulum's skills into the repository, copy them again from the new release: committed copies never update, and they override the plugin's.
5. Update the plugin on each machine whose sessions or `pendulum serve` work this repository, then start a new session: Claude Code `claude plugin marketplace update clockgrove && claude plugin update pendulum@clockgrove`, Codex `codex plugin marketplace upgrade clockgrove && codex plugin add pendulum@clockgrove`, Copilot `copilot plugin update pendulum@clockgrove`. Doctor and `pendulum serve` warn while the installed plugin is older than the pin.

## Uninstall

Delete `.github/workflows/pendulum.yml`, the App and its two secrets, and any model key. Optionally delete the `pendulum` ruleset, the labels and the Project. For local mode, also delete `~/.config/pendulum` (the tokens), `~/.cache/pendulum`, the `.pendulum/` directory in each clone that ran it, and the `pendulum:local` label. For the cloud sandbox, also delete the three `VERCEL_*` secrets, the Vercel project's sandboxes and snapshots, the image issue and the `pendulum:image` label. If you accepted setup's offer to commit Pendulum's skills, delete them too (`.agents/skills/`, `.claude/skills/`, and `.claude/agents/`, `.codex/agents/` or `.github/agents/`), and on your own runner remove the `pendulum-agent` user. Nothing else is installed.
