# Local mode

Factory's worker and reviewer, run on your own machine instead of a GitHub runner. Same task card, same skills, same exits, same GitHub state; only the sandbox differs. Use it when your tests need your machine (a database, a GPU, a big toolchain), when you want runs to bill your own harness login, or to try Factory before you install the App.

## What runs where

- The harness CLI (Claude Code, Codex or Copilot) runs on your machine on its own login. Every command the model runs goes through that harness's own sandbox: bubblewrap on Linux and WSL2, Seatbelt on macOS.
- **Copilot runs locally only inside the outer sandbox below**, so only on Linux and WSL2 hosts where it starts: Copilot's own sandbox applies its file policy best-effort, so the outer sandbox is its hard line. Elsewhere (macOS included) local mode refuses `FACTORY_HARNESS=copilot`; run Copilot Objectives on the Action.
- Factory's own commands (setup, install, validation) run in `srt`, Anthropic's sandbox runtime, with the same reach as the model, since they run on a tree the model edited.
- In every sandbox:
  - **Credential stores are unreadable:** `~/.ssh`, `~/.aws`, `~/.config/gh`, the harness logins, `~/.config/factory`, and the rest.
  - **Credentials are not in a command's environment:** Claude Code's sandbox unsets every model, runner and Factory credential name (`sandbox.credentials.envVars`), as Codex's and Copilot's own flags do. Claude Code's sandbox holds the same bar on Actions and in a cloud sandbox (PLAN.md, Credentials and billing).
  - **Writes are limited:** the Objective's clone, the stage's temp directory and its own package caches (npm, pnpm, Bun, Yarn, Corepack) only. The clone's `.git/hooks`, `.git/config`, `.git/info/attributes`, its harness configuration (`.claude`, `.codex`, `.agents`, `.github/hooks`, `.github/copilot`, `.github/agents`, `.github/skills`, `.mcp.json`) and the stage's usage directory (Factory's record, event log and helpers) are read-only. Factory keeps its own temporary files in a 700 directory under `.factory/<issue>/.private`, which no sandbox can reach, and holds validation output in memory. `TMPDIR` and `XDG_RUNTIME_DIR` point at the stage's private temp directory, in a mode-700 directory of your own: `~/.cache/factory/s` on Linux, `/private/tmp/fct-<uid>` on macOS (Claude Code keeps its sockets there and needs that path short). No stage can write another's, and the sandboxes' `/tmp/claude` is read-only. Both temp directories are removed when the stage ends; one a killed loop left (its holder's pid, recorded beside it, is gone) is removed by the next stage that makes one there, and a live stage's never is.
  - **The network is limited:** GitHub (with Git LFS's download hosts, `github-cloud.githubusercontent.com` and `media.githubusercontent.com`) and the npm and Yarn registries, plus your `FACTORY_LOCAL_DOMAINS`. A worker that stops because a sandbox denied a host it needs names the host in its exit record (`deniedHosts`), and the Blocked comment names it with the fix: add it to `FACTORY_LOCAL_DOMAINS` (`serve` reads it when it starts), then re-apply `factory:objective`. Allowing it stays your decision.
- **Git LFS media is uploaded by Factory, not the sandbox:** each stage fetches the LFS objects the clone's store lacks into Factory's mirror and hands them to the clone (a warning if it fails), so a reused clone downloads only new media. Factory's own checkouts in the clone leave LFS files as pointers until then, so a resumed clone never asks LFS storage for media it lacks. The sandbox cannot reach LFS storage, so the harness commits media and stops. Factory's own push copies every object the new commits point to from the clone's store, checks its bytes against its pointer, uploads it from the host, then updates the branch. That push goes to the repository's own GitHub LFS endpoint whatever `.lfsconfig` says, offers the token to github.com only, and Blocks when the branch's media since the default branch exceeds `FACTORY_LOCAL_MEDIA_MAX_MB` (default 500).
- **No harness loads code-running configuration from the clone:** settings, hooks, helpers and MCP servers there could run outside every sandbox. Claude Code runs with Factory's own settings only (no user, project or local settings, hooks off); the repository's `CLAUDE.md` still loads, and Factory's skills and agent definitions, with the repository's own, are loaded from a copy in the stage's usage directory (so a skill is `factory:<name>`). Codex treats the clone as an untrusted project and Copilot as an untrusted folder, which skip its config, hooks and MCP servers. Before every harness start Factory also restores the clone's harness settings and hooks to the commit (`.claude/settings*.json`, `.claude/hooks`, `.codex/config.toml`, `.codex/hooks.json`, `.github/hooks`, `.github/copilot`) and removes anything else there. The package caches are writable to commands but are no harness's added directory, so no `CLAUDE.md`, agent or skill is read from them.
- **The harness's own git reads only the clone's git directory:** each harness CLI runs `git status` or `git diff` on the host as it starts, and Copilot again after every tool call. `.git/commondir` is `.` (the clone's own `.git`) and read-only in every sandbox, like `.git/config`, `.git/hooks` and `.git/info/attributes` (made empty where absent, so the sandboxes protect a real file; a setup command that writes it, such as `nbstripout --install --attributes`, fails there). Before every start Factory removes from `.git` what else could point git at another directory (`gitdir`, `config.worktree`, `worktrees`), drops gitlinks HEAD does not have, leaves no submodule checked out (each gitlink's `.git` and `.git/modules` removed; Factory never initialises one), and refuses to start the harness when git would still read another directory. The harness runs with `diff.ignoreSubmodules=all`, `submodule.<name>.ignore=all` for each name in `.gitmodules` (which is read-only in every sandbox), `core.fsmonitor=false`, `status.submoduleSummary=false` and `submodule.recurse=false` in its git environment, so no git it runs enters a submodule: `git status` and `git diff` in a local run do not show submodule changes. The first `git` on the harness's PATH is Factory's guard: it refuses once the clone's `.git` is not the directory Factory checked, since on macOS Copilot's sandbox lets a command rename `.git` and put another in its place (on Linux it binds `.git` apart, below). Factory records the clone's `.git` (its inode and birth time) when it clones, outside every sandbox's reach, and every stage and harness start refuses a `.git` that is not that directory or not on the filesystem of the Objective's directory (the device number is not compared: it changes across a WSL2 restart); a stage that finds another `.git` Blocks the Objective (`git-identity`) until you remove its `.factory/<issue>` directory, takes `factory:review` off its PR so `serve` does not pick the review again, and updates one Blocked comment if it finds the same clone again; after its own git setup each stage also records a hash of `.git/config`, `.git/commondir`, `.git/info/attributes` and the hooks, and refuses a harness start when they changed. A refused harness start Blocks the stage with a fixed reason (`git-identity`, `git-state` or `git-clear`); the detail is in the stage log. `serve` reviews no draft PR and no Blocked Objective's PR.
- **On Linux, Claude Code, Codex and Copilot run in an outer sandbox too:** the whole harness process runs in `srt`, so what it runs on the host itself (its git, a hook, a config a future version loads) cannot read the credential stores, write outside the clone, the stage's directories and its own state (`~/.claude` and `~/.claude.json`, `~/.codex`, or the stage's Copilot home), or reach hosts beyond the sandboxes' list and its own API hosts. Codex runs in it where its own sandbox starts inside it: a stage checks that once per machine and Codex, bubblewrap and `srt` version (cached in `~/.cache/factory/outer-probe.json`). It does with bubblewrap 0.11.1 on WSL2, and not on GitHub's Ubuntu 24.04 and 26.04 runners (bubblewrap 0.9.0); where it does not, `serve` says so once and Codex runs with the guards above. The harness's own sandbox runs inside it, which needs nested user namespaces and unix sockets in `srt`; the read-only paths inside its writable ones still hold against code that makes its own user namespace (`srt`'s mounts are locked there). The harness's own login stays readable inside it. Copilot's sandbox gives each command a private network namespace through slirp4netns, which needs `/dev/net/tun`; `srt` makes a fresh `/dev` without it, so Copilot's outer sandbox runs bubblewrap through a small Factory wrapper that adds the host's `/dev/net/tun` (a process can make an interface only in a network namespace it owns, so nothing leaves except through `srt`'s proxy). Its commands then reach the network through Copilot's own proxy, which applies the host list and connects on through `srt`'s. A stage checks that once per machine (the device, `slirp4netns`, `nsenter`, `unshare`, `ip`, `iptables`, `ip6tables`, `iptables-restore`, `ip6tables-restore`, and `slirp4netns` wiring a namespace inside `srt`), and checks a failure once more at once, so one slow check does not count; where it fails both, `serve` refuses to start with `FACTORY_HARNESS=copilot` and says why, and a stage that finds it failing later (a new version probed again) Blocks the Objective (`outer-sandbox`) and takes `factory:review` off its PR. Copilot's binary unpacks the release it runs into its cache (`~/.cache/copilot`); only its `--version` in `srt` may write there, and the cache is read-only in the outer sandbox. On Linux Copilot's sandbox binds the clone's `.git` on its own, so a command cannot rename or replace it; elsewhere the git guard above holds. macOS has none: Seatbelt cannot start a sandbox inside another, and each harness's own sandbox is one. Inside it the host's unix sockets are out of reach: the session and system buses, container daemons, snapd, the X server, WSLg's sockets, WSL's interop sockets (which start Windows programs), the ssh and gpg agents, each socket or directory holding one directly under `/run`, `/mnt/wslg` and `/tmp/.X11-unix`, each `ssh-*`, `gpg-*` and `tmux-*` directory directly under `/tmp`, and every socket bound on the machine when the stage starts. In the harness's own state (`~/.claude`, `~/.codex`, the stage's Copilot home) it writes only what its run needs: its login's refresh, its own project or the last days' sessions, caches, logs, and Codex's state and log databases. Everything else there is read-only, even where absent: settings, hooks, MCP servers (`~/.claude.json`), plugins, skills, instructions, installed releases, your other projects and sessions, Claude Code's shell snapshots, session environments, daemon, jobs, dev mods, scheduled tasks, their locks, keybindings, plans, release notes and model catalog, Codex's memories, shell snapshots, app server and update record, Copilot's `settings.json` (also its sandbox's policy), `config.json` (its trusted folders), MCP and LSP servers, permissions, plugins, extensions and `pkg`, and any name a later version adds. Claude Code's `~/.claude/projects` is read-only as a whole, so a run makes no new project there (whose memory a later session of yours in that directory would read): the clone's own project is a link Factory makes to `.factory/<issue>/claude-project`, removed with the Objective's directory. Factory writes Copilot's `settings.json`, `config.json` and `mcp-config.json` afresh before every stage. An absent settings or config file there is made empty first (`~/.codex/config.toml`, `hooks.json` and the like, `~/.claude/settings.json`, Copilot's `config.json`), so the sandbox protects a real file. The harness's `--version`, for the outer probe and for each stage's usage record, runs in `srt` too.
- The harness holds no GitHub token at all: what it needs from GitHub is in `$FACTORY_IN`. Factory's own calls use one fine-grained token for this one repository, never your `gh` login; the token reaches each stage on a pipe it reads once, never its environment or a file, and Factory's own git gets it by per-process env config. No sandbox can read `/proc` (Claude Code and `srt`; Codex runs in its own pid namespace). Copilot's sandbox runs each command in a pid namespace of its own too, whose pid 1 is the bubblewrap Copilot starts with its whole environment, the token included (#100); on Linux Factory's own `bwrap`, first on Copilot's PATH, starts the real one with an empty environment, and bubblewrap sets each command's environment itself. Copilot also writes each command's network rules into its own `TMPDIR` before it loads them, and opens that directory to every command, so a command could rewrite the next one's rules and reach past Copilot's proxy to `srt`'s (whose list adds Copilot's API hosts). On Linux Copilot therefore runs with a `TMPDIR` of its own, in the stage's usage directory, made afresh before every start and denied to its commands, and writes no logs (Copilot opens its log directory to every command whatever its policy says); Factory's `bwrap` gives each command the stage's temp directory as its `TMPDIR`. Copilot's sandbox binds only the system's own directories (`/usr/bin`, `/usr/lib`, `/etc` and the like) into each command, so a node your version manager keeps in your home (nvm, mise, asdf, Volta) would be out of its commands' reach (#111). The stage's node is the first `node` on your PATH, by its real path (where that is a version manager's shim, the node the shim chose, which runs Factory). Its install prefix (`bin`'s parent, so npm comes too) is read-only in each command's sandbox, with its `etc` (a global npmrc) denied, and Factory's `bwrap` puts its `bin` first on each command's PATH, after Factory's git. Nothing else of your home is bound. The prefix is never your home or a directory above it, nor in or above a credential store, this repository's `.factory` directory or the stages' temp directories, where a sandbox could swap it for a link. The same holds for the repository's package manager, and for Claude Code too, whose sandbox likewise shows nothing of your home but its working and added directories (#137): a repository whose `packageManager` (else its lockfile) names pnpm or yarn gets the one your PATH resolves to (corepack's shim, its own install, or, behind a version manager's shim, the version `packageManager` pins in that manager's installs: mise's and asdf's `installs/pnpm/<version>`, Volta's `tools/image/pnpm/<version>`; Factory never runs the manager, which would read the clone's own configuration), linked from a `toolbin` directory in the stage's usage directory, which no sandbox may write, and first on each command's PATH (Copilot through Factory's `bwrap`, Claude Code through `CLAUDE_ENV_FILE`). Only the npm package it belongs to (corepack, pnpm) is readable, read-only, else the executable alone; corepack's downloads live in the Objective's own `COREPACK_HOME`. Codex's sandbox reads the whole system but the credential stores, so its commands find both as you do. Before every Copilot start a probe checks all of this: a Copilot session in the outer sandbox, with the stage's policy and no credential, against a model Factory serves on that sandbox's own loopback (no network, no bill), runs one command. That command must find a random marker Copilot holds in no environment it can read, Copilot's network rules nowhere it can list, Copilot's `TMPDIR` read-only and no Copilot log it can read, nothing it writes in your home, the probe's Copilot home or Copilot's release left there, the clone's `.git/config` read-only, the stage's temp directory writable and a host off the list refused; the stage's node must be the `node` it finds, and it, the `npm` beside it and the repository's pnpm or yarn must run (else the stage Blocks with `the stage's toolchain does not run in a command`); and it must end with its pass line. A broken rule Blocks the stage (`sandbox`) before any command runs; a probe that leaves no result is tried once more, then Blocks. It takes a second or two. Claude Code on Linux gets the same probe before every start (it has no command that runs one command in its sandbox either): a Claude Code session launched as the run is, with a throwaway config directory in the usage directory, a stand-in key and no credential of yours, against a stand-in for the Anthropic API on its outer sandbox's own loopback (no network, no bill), runs one command. That command must find and run the stage's node and the repository's pnpm or yarn, find a random marker Claude Code holds in no environment it can read, leave nothing it writes in your home or the usage directory, find the clone's `.git/config` read-only, the stage's temp directory writable and a host off the list refused, and end with its pass line; a broken rule Blocks the stage (`sandbox`) with the rule. `doctor.mjs --local` runs it too (`claude sandbox: start`, around a throwaway clone with your checkout's `package.json`), and names what local mode resolves: `node: v24.20.0 → /usr/bin/node`, `package manager: pnpm 12.18.0 (corepack) → …/corepack/dist/pnpm.js`; a pinned package manager it cannot resolve is a FAIL.
- Each Objective gets its own clone under `<your clone>/.factory/<issue>/`, which is git-excluded. `serve` removes it once the issue is closed; a Blocked Objective keeps its directory so a re-label picks up where it stood. Its installed dependencies (ignored files) carry over between stages and runs, but nothing unpushed does: each stage starts on the branch exactly as GitHub has it, and removes the untracked files, uncommitted changes and stopped rebase an earlier stage or run left there. It also removes the git lock files (`.git/*.lock`, `.git/refs/**/*.lock`) a run interrupted by a reboot or a killed `serve` left, and logs each: a lock older than the machine's last boot always goes; a newer one goes only where `/proc` shows no process with its working directory or an open file in the clone (Linux; on macOS only the boot rule applies). Otherwise the lock stays and the log names it.
- GitHub holds all state. A claim comment with a heartbeat marks an Objective a local loop is running, so the Action and other loops leave it alone.
- Each local run writes its dollars into its progress comment, so the `daily_usd` cap counts local and Actions spend together, on any machine. Every stage writes one: $0 when it ran no harness pass. While a stage runs, each write of its comment carries the spend Factory has read so far, marked `usdLowerBound` (`usdUpperBound` when part of it is priced at a price table's dearest rates, for a model with no row), so a stage that is killed or loses its machine still counts what it spent. A stage stopped by a signal (Ctrl-C, SIGTERM or SIGHUP, or its loop stopping) writes that reading once more as it stops, after its harness is killed, when it is more than the line shows, waiting at most 5 s for GitHub. The reading is what the harness has reported so far: Claude Code reports each model response and Copilot each usage checkpoint, so their passes killed before the next write still count; Codex reports usage only when a turn ends, so a Codex pass killed before its turn ends adds nothing for that pass. After each such write lands, the stage records in its usage directory (`session-totals.json`) the session totals that line counted; a stage that resumes the live session after a killed one starts from them, so what the killed stage's line counted is not counted again and what it missed is counted by the resuming stage. The stopping write records them when it landed or may have (a 5xx answer, or no answer in 5 s, which includes a connection still being opened then), so it is never counted twice; one that may have landed but did not leaves that part uncounted. When it certainly did not land (the connection refused or its host not found at once, or a refusal), nothing is recorded and the resuming stage counts that part. Two exceptions: a reading priced at a table's dearest rates is not recorded, so the resuming stage counts that pass again (an over-count, never an under-count); and a stage killed after its result.json but before its last write keeps its last interim line, and the stage after it starts from that result.json. A `--here` run writes no spend line; it stays unmetered.

## Platforms

| Platform | Supported | Needs |
| --- | --- | --- |
| Linux, WSL2 | yes | `bubblewrap`, `socat`, `ripgrep`; for Copilot also `slirp4netns`, `iptables`; unprivileged user namespaces that AppArmor leaves alone (below) |
| macOS | sandbox verified, not run end to end; Claude Code and Codex only (no Copilot, above) | `ripgrep` (Seatbelt is built in); no `FACTORY_LOCAL_DB` (its sandbox shares the machine's network) |
| Windows | inside WSL2 only | native Windows has no sandbox for the harness; local mode refuses and says so |

`node bench/sandbox-check.mjs` probes the sandbox on your machine for each harness and exits non-zero if any check fails.

## Set it up

1. Install `git`, `gh`, Node 22 or newer, the harness CLI you use (logged in), and `srt`: `npm i -g @anthropic-ai/sandbox-runtime`. Add the platform packages above, for example `sudo apt-get install -y bubblewrap socat ripgrep`.
   On Ubuntu 24.04 and later, AppArmor keeps srt's and Claude Code's sandboxes from starting; local mode names what it finds before it runs anything. Allow unprivileged user namespaces (`sudo sysctl -w kernel.apparmor_restrict_unprivileged_userns=0`, kept in `/etc/sysctl.d`), and where the `bwrap-userns-restrict` profile is loaded (Ubuntu 26.04), unload it (`sudo apparmor_parser -R /etc/apparmor.d/bwrap-userns-restrict`, kept off with `sudo ln -s /etc/apparmor.d/bwrap-userns-restrict /etc/apparmor.d/disable/`). That profile takes every capability from what bubblewrap starts, and srt's sandbox, which Claude Code's is built on, needs some there. WSL2 has no AppArmor.
2. Create a fine-grained token on GitHub (Settings, Developer settings, Fine-grained tokens):
   - **Repository access:** this one repository only.
   - **Permissions:** Contents, Issues and Pull requests read and write; Actions read (read and write if you use red-check triage, below, which reruns failed CI jobs).
   - **Optional, for the Project board:** when the repository belongs to an organization, make the organization the token's resource owner and add Organization permissions → Projects: Read and write. Local runs then move board cards the way the Action does; without it, labels carry the state and doctor says so.

   Save it with `mkdir -p ~/.config/factory/tokens/OWNER && (umask 077; read -rsp 'token: ' t && printf '%s' "$t" > ~/.config/factory/tokens/OWNER/NAME)`, or export `FACTORY_LOCAL_TOKEN`. Local mode refuses a classic token or `gh` login, and refuses a token that can write to any other repository. When GitHub refuses the token later (401: expired or revoked), `factory serve` starts no new work and says once where the token comes from; a new token saved in that file is taken at the next tick, after the same checks (an exported `FACTORY_LOCAL_TOKEN` needs serve started again). The refused token is tried again once a minute, so a 401 GitHub gave for a moment ends by itself.
3. For Copilot only: create a fine-grained token with the Copilot Requests permission (Read) from a user with a Copilot seat, and save it to `~/.config/factory/copilot-token`, or export `COPILOT_GITHUB_TOKEN`. Copilot's sandbox reads its policy from a home Factory owns, so your own `copilot login` is not used there.
4. Optional, red-check triage and the drift advisory (PLAN.md): save a Vercel AI Gateway key to `~/.config/factory/ai-gateway-key` (chmod 600). That file is the only place local mode reads it from: Factory's own process reads it, no sandbox can (the sandboxes hide `~/.config/factory`), and it is in no process's environment, even when `FACTORY_LOCAL_ENV` names it. Like the App's key, it must be a regular file with one link and no group or world bits, in a `~/.config/factory` that is no symlink and inside no harness home (`CLAUDE_CONFIG_DIR`, `CODEX_HOME`, `COPILOT_HOME`), which the harness's outer sandbox can read; `factory serve` refuses to start while the file sits in such a home. Without a usable key, the first red of each stage says `triage: off (<code>)` in the log and the progress comment (`no-key`, `key-dir-exposed`, `key-dir-symlink`, `key-file-not-regular`, `key-file-links`, `key-file-mode`, `key-file-empty`, or `key-file-<errno>` for any other file error, such as `key-file-eacces`). The rerun needs the token's Actions read and write: with read only, GitHub refuses it (403, `no permission to rerun jobs`), every red on that Objective goes to the fix pass, and a Block on the last red says triage's verdict and the refused rerun; after a fix pass that commits nothing, the Block names the refused rerun at once. With a key in place, `doctor.mjs --local` makes a dry rerun: it asks GitHub to rerun the failed jobs of workflow run 0, which no repository has, so nothing reruns. A 403 means the token lacks Actions write and doctor warns with the fix; any other answer leaves it not verified (a warning too), since GitHub may answer 404 with or without the permission. `FACTORY_TRIAGE_MODEL` picks another decision model. The same key turns on the drift advisory (PLAN.md); `FACTORY_DRIFT_MODEL` picks its model.
5. Run it from a clone of the repository: `factory serve` (the plugin's `bin/`, on PATH in Claude Code; elsewhere `node <factory>/plugin/bin/factory serve`), or `/factory:factory-serve` in a session. On its first start it creates the `factory:local` label.

## Run it

```sh
factory serve [--once] [--all] [--interval 30]   # a loop: the dispatcher's rules, every 30 s (/factory:factory-serve)
factory run <issue> [--wait]                     # one Objective, from the stage its state calls for (and, with --wait, to merged) (/factory:factory-run)
factory review <pr> [--wait]                     # a review re-run
factory issue <issue> [--out FILE]               # the issue for a session (/factory:factory-run --here, /factory:factory-review), only when its author and last editor can push
factory deliver <issue> [--out DIR]              # Factory's half of /factory:factory-run --here: push, PR, plan, replies, exit
factory post-review <pr> <findings.json>         # post a /factory:factory-review pass made in a session
```

Every command takes `--repo OWNER/NAME` and `--dir CLONE` too. `--help` or `-h` prints its usage and exits 0; an unknown flag, a flag without its value, a non-number for `--interval` or a missing or non-numeric `<issue>` or `<pr>` exits 64 with the usage, before anything starts. `factory-db --help` prints its own usage.

- **Where `run` starts:** from the Objective's state on GitHub, as `serve`'s resume decides: an open, non-draft PR labelled `factory:review` goes to the review stage; a Running issue to the work stage; an In-review issue whose PR is reviewed waits for its merge (followed with `--wait`); anything else starts the work stage. When `run` stops following a PR that is not merged yet (without `--wait`, or after `--wait`'s two hours), its last line says who tends the merge now: for a `factory:local` Objective nothing does until `factory serve` runs for the repository, so start it.
- **Factory's push:** the harness pushes nothing. Factory takes the branch as a bundle the sandbox writes to a pipe, checks it in a mirror under `.factory/<issue>/.private/` (which no sandbox can write), pushes it with a lease on the head it last saw, and reads GitHub's head back. Factory runs no git command on the clone outside a sandbox: preparing the branch, Git LFS, handing over the default branch (as a bundle) and its own rebase (made in the mirror) all run in `srt`, so nothing planted in the clone's `.git` runs on your machine; srt's protected paths and the clone's package-cache folders are made there too. When a harness run ends, its process group and every process carrying its run tag are killed (one that left the group with `setsid` included), before Factory reads what it left. Factory merges the reviewed head itself once its required checks are green; `factory run --wait` does that merge while it waits.
- **Hand-off:** the harness writes nothing to GitHub. It reads what Factory rendered into `$FACTORY_IN` and leaves its plan, PR text, replies, note and exit record in `$FACTORY_OUT`, both under the stage's temp directory; Factory reads them inside the same sandbox, then pushes and posts. `deliver` and `post-review` do the same for a session's own work, with the local token, else your `gh` login. A session reads the issue only through `factory issue`, and `deliver` and `post-review` check its author and last editor again, as every stage does: an issue a person who cannot push wrote or last edited is refused (deliver Blocks it, nothing pushed). `deliver` also delivers nothing when the issue's title or body changed after `factory issue` wrote it for the session: read it again and plan from the new text.
- **Routing:** label an Objective `factory:local` and the local loop takes it, while the Action leaves it alone. `--all` (or `FACTORY_LOCAL_ALL=1`) takes every Objective. The loop's sweep (stale Running, Done) touches only the Objectives it takes, and a Running one a local loop claimed; before its Done pass removes a closed Objective's state labels under your login, it posts a `done` marker naming them, which the scorer reads as Factory's.
- **Questions and Blocks:** an Objective whose stage ends on this machine with a Question or a Block waits for you. No `serve` tick takes it again while its stage runs, or after it ends on a GitHub read that does not show the stop yet; it starts again only after a trusted answer, the same as on the Action (re-applying its label, or marking a Question's draft PR ready). If the stop never reached GitHub (a fresh read of the issue shows it Queued), it runs again, as on the Action, and the tick line names every Objective it holds.
- **Stopping and pausing:** stop `serve`, `run` or `review` with Ctrl-C, SIGTERM or SIGHUP (a closed terminal, a parent session ending) and its Objectives pause: they stay Running with their claims. The `factory` front end passes each signal on; the loop ends every stage process, and each stage kills its harness's whole process group and writes its spend so far (at most 5 s) before it exits, since the harness runs in a group of its own that no terminal signal reaches. A second signal a second or more after the first exits at once. The same pause happens when the machine sleeps or shuts down. The next `serve` on the same machine resumes them first, before reviews and new work, and `factory run <issue>` takes one up the same way: an open PR waiting for review goes to review; Running work starts a fresh work pass in the Objective's clone, on the branch as GitHub has it (a killed pass's session and unpushed commits are not carried over). Other machines and the Action leave a paused Objective alone; the dispatcher Blocks one only after a day away, and re-applying its label brings it back.
- **What a start finds left over:** each stage names its own process and its harness's (pid, start time, the harness's run tag) in its usage directory while they run. Before a stage starts, and before `run`, a resume or the cleanup of a closed Objective, a harness that a dead stage of the same Objective left running (its loop killed with SIGKILL, say) is killed. Factory signals it only when the process is still the one recorded, by its start time, and its group still carries the run's tag; never by matching command lines. A stage still running on this machine is not run twice: `run` refuses and `serve` skips that Objective, naming the pid to stop. When the machine cannot tell whether the recorded pid is still that stage (its start time unreadable), it refuses too and names the record file: delete it once you have checked that pid is no Factory worker.
- **Keeping `serve` running after the terminal closes:** `nohup` does not help, because Node resets an ignored SIGHUP when it starts. Start it in a session of its own instead: on Linux `setsid -f factory serve >serve.log 2>&1 </dev/null`; on macOS, which has no `setsid`, `factory serve >serve.log 2>&1 </dev/null &!` in zsh (`&` then `disown` in bash); anywhere, inside `tmux` or `screen`. Stop it with `kill <pid>`, which pauses its Objectives as above. On WSL2, Windows may shut the distribution down after its idle timeout once no WSL terminal is attached, and a detached `serve` does not prevent that: keep one WSL window open (with `serve` in `tmux` there, say) or raise the idle timeout in `.wslconfig`. Nothing restarts `serve` after a reboot; start it again.
- **Claims and deadlines:**
  - A claim's age is GitHub's update time on its comment, so a machine clock that is off never makes it stale.
  - A claim the dispatcher cannot read, or whose author it cannot check, is unread: that tick leaves the Objective alone and reads again, since no Block may rest on one failed read. A read that keeps failing Blocks it, naming the read (cause `factory`), only once a day has passed since the Objective began waiting and the issue shows no sign of a live stage in that day: no comment created or updated by Factory's login, or carrying a Factory marker by a person with push access (a stage's progress comment changes every few minutes), no label change by Factory's login, and no claim comment updated by either. When that evidence cannot be read either, it keeps waiting. A runner job steps aside from an Objective whose claim comment it sees but whose author it cannot check; a comments read that keeps failing counts as not claimed, as before, so the job runs (only an Objective without `factory:local` is checked this way).
  - A stage that ends without an exit record (killed, crashed) keeps its claim, and the same `serve` resumes it once. A second such end in a row Blocks it there, naming the stage, its exit code or signal and its log on the machine (cause `factory`). The same holds for a review stage. A `serve` that stopped instead leaves the claim for the next `serve` on that machine, as a pause does.
  - A `factory:local` Objective no loop claims waits a day, Running or in review with its review owed, then Blocks naming the fix: start `factory serve` on the machine that runs it (cause `setup`; an expired claim's Block names its loop too). In review, the day counts from the later of its entering In review and the PR's last `factory:review` label, so a re-review owes a new day. A review `serve` is about to run, or waits for a slot for, is never Blocked by its own tick.
  - A reviewed PR waiting on checks or the merge queue has no local deadline: the merge pass tends it, with the queue's own drop and hang rules. `serve` runs that pass on every interval (`run --wait` while it follows the PR); the Action's dispatcher leaves `factory:local` PRs to it, so with no `serve` running such a PR waits.
  - A start never runs beside a stage of the same Objective still running on the machine (an earlier `serve`'s): it does nothing and leaves the claim. A start that fails before its stage runs (the claim, the clone, a directory) logs the error. When the claim was this loop's, the Objective goes back to Queued. When the claim could not be read, or is another loop's, nothing on GitHub changes at first; after the backoff the loop reads the claim again and puts the Objective back to Queued once no other loop holds it live. Either way that loop leaves the Objective for 5 minutes, then 10, doubling up to an hour, and the third failed start in a row Blocks it once with the error (cause `setup`). So a fault on the machine (disk full, a broken sandbox) neither Blocks the whole queue at once nor relabels it every tick. A start that gets its stage running clears the count, which lives only in that loop's memory.

## Configuration

Local mode reads the repository's `.github/workflows/factory.yml` `env:` block as committed on the default branch: harness, models, validation, protected paths, budgets. It fetches the default branch first (offline, the last fetched commit) and never reads the working tree's copy, whatever branch is checked out, as the Action runs the reviewed workflow: a branch's own workflow cannot widen what a stage may do on your machine (`FACTORY_LOCAL_ENV`, `FACTORY_LOCAL_DOMAINS`, `FACTORY_LOCAL_SETUP`). Where the working tree's settings differ, `serve` names them at start and doctor warns (`workflow source`): commit the change to the default branch to use it. With no workflow there, local mode uses none of its settings. It takes only the settings there: the Action's inputs as `FACTORY_<INPUT>` (not a secret's, nor `FACTORY_MODE`, `FACTORY_ISSUE` or `FACTORY_PR`, which each run gives) and the `FACTORY_LOCAL_*` and `FACTORY_PG_BIN` settings below, except `FACTORY_LOCAL_TOKEN`, `FACTORY_LOCAL_APP_ID` and `FACTORY_LOCAL_APP_KEY`, which only your shell sets. The file is repository content, and any other `FACTORY_*` name is one Factory reads as its own control, so local mode leaves it out of every stage, names it in the log, and doctor warns. Your own environment wins for these:

| Variable | Effect |
| --- | --- |
| `FACTORY_HARNESS`, `FACTORY_MODEL`, `FACTORY_SUBAGENT_MODEL`, `FACTORY_REVIEWER_MODEL`, `FACTORY_REVIEWER_EFFORT`, `FACTORY_EFFORT` | pick another harness or model; another harness drops the workflow's models for its own defaults |
| `FACTORY_RESUME_POLICY`, `FACTORY_COMPACTION_WINDOW`, `FACTORY_PROMPT_CACHE_TTL` | the session settings, as on the Action |
| `FACTORY_LOCAL_DOMAINS` | more hosts the sandboxes may reach, space or comma separated. Write host names (`example.com`) or `*.` ones; Codex's and Copilot's sandboxes get only those (no port, IP address or `localhost`): Copilot drops its whole network policy for a `host:port` entry and Codex's proxy ignores the port, admitting every port of the host, so serve leaves any other entry out of their policies and logs it, and doctor warns |
| `FACTORY_LOCAL_ENV` | names of more variables the stage may see (the stage env is an allow-list, not your shell) |
| `FACTORY_WORKER_SECRETS` | the secrets the worker's shell gets, `NAME` or `NAME=SOURCE` each (PLAN.md, Worker secrets); this shell's `SOURCE` variables hold the values. The workflow's env block sets it too |
| `FACTORY_LOCAL_SETUP` | the setup command for your machine (the workflow's assumes a fresh runner) |
| `FACTORY_LOCAL_VALIDATION` | the validation commands local mode runs, when some of the workflow's cannot run in a sandbox; the required checks on GitHub still run the full set before a merge |
| `FACTORY_LOCAL_DB=1`, `FACTORY_LOCAL_DB_INIT`, `FACTORY_PG_BIN` | a throwaway Postgres per validation command (below) |
| `FACTORY_LOCAL_APP_ID`, `FACTORY_LOCAL_APP_KEY` | the Factory App's id and the path of its private key. Blocked and Question notices then post as the App, so their @mention reaches the `FACTORY_NOTIFY` user even when that is you: GitHub notifies no one of their own mention, and doctor warns when that would happen. The key must be a real file under `~/.config/factory` (no sandbox reads there; not a symlink, one hard link, mode 600, and no `CLAUDE_CONFIG_DIR`, `CODEX_HOME` or `COPILOT_HOME` that holds it, since the harness reads its own home): move the downloaded `.pem` there, don't copy it, so none is left in `~/Downloads`. Only the `run` or `serve` process holds the key: each stage asks it for a notice token (this one repository, issues write only) over Node's IPC channel, never an env variable or a file, and nothing a stage starts inherits the channel. `deliver` posts with your own token. The App must be installed on the repository. The key itself can mint whatever the App's installations grant: Factory's own App works, and an App with only Issues read and write, installed only on the repositories you run locally, keeps that reach narrower. |
| `FACTORY_LOCAL_MAX_CONCURRENT` | how many Objectives (work or review) this machine runs at once; default a quarter of its CPU threads, at most one per 8 GB of memory. The workflow's `max_concurrent` still caps the repository as a whole |

Local mode runs the validation commands itself, so their order is its wall time. Mark a command `parallel:` (for example `parallel: pnpm test`) when it may run at the same time as the marked commands beside it, and quote the whole value in the workflow's env block (`FACTORY_VALIDATION: 'pnpm check, parallel: pnpm test'`), since an unquoted `: ` makes it a YAML mapping and GitHub then runs none of the workflow: each run of consecutive marked commands starts together, and the next command waits for all of them. Unmarked commands run one at a time, in order. Each command gets its own sandbox and, with `FACTORY_LOCAL_DB=1`, its own Postgres. When a group fails, the fix run gets every failed command's tail and the path of its whole output.

## Worker secrets

A worker that must spend through a key of the repository's own (a paid image step, say) gets it only when the repository opts it in (PLAN.md, Worker secrets): `FACTORY_WORKER_SECRETS: AI_GATEWAY_API_KEY=WORKER_AI_GATEWAY_API_KEY` in the workflow's env block (or this shell), and `export WORKER_AI_GATEWAY_API_KEY=...` in the shell that runs `factory serve` (one line; a running `serve` reads it when it restarts). An AI Gateway key goes through the gateway relay (PLAN.md, The gateway relay): the worker's shell gets a relay token as `AI_GATEWAY_API_KEY` and the relay's address as `FACTORY_GATEWAY_URL`, so the gateway's host needs no entry in `FACTORY_LOCAL_DOMAINS`, and `socat` and `bwrap` must be installed. Any other worker secret reaches the worker's harness as it is, and its provider's host goes in `FACTORY_LOCAL_DOMAINS`. Only the worker's harness gets them: the work stage's passes and the review stage's fix and answer passes; setup, install, validation and the reviewer never do. A worker secret's NAME or SOURCE that `FACTORY_LOCAL_ENV` also names is left out of every stage's environment (doctor warns), since `FACTORY_LOCAL_ENV` would hand it to every command of every stage. Use a dedicated key with a budget the gateway enforces, never the one in `~/.config/factory/ai-gateway-key`: Factory's key is refused as a SOURCE by name, and a worker value equal to it is withheld (doctor warns).

## Databases

A sandbox has no route to the machine's services. With `FACTORY_LOCAL_DB=1` (Linux and WSL2), each validation command runs through `plugin/bin/factory-db`. It works in five steps:
1. starts a fresh Postgres on the sandbox's own loopback, with no unix socket;
2. sets `DATABASE_URL` and the `PG*` variables;
3. runs `FACTORY_LOCAL_DB_INIT`, for example `psql -qc 'create extension if not exists vector'`;
4. runs the command;
5. removes the database.

The task card tells the model to do the same. It needs the Postgres server binaries (`initdb`, `pg_ctl`). `run` and `serve` warn at start (and `doctor.mjs --local`) when the repository uses Postgres and `FACTORY_LOCAL_DB` is off. When `FACTORY_LOCAL_VALIDATION` is set, the warning names the commands it still runs locally, so you can confirm none of them needs the database. On macOS, `FACTORY_LOCAL_DB=1` stops `run` and `serve` from starting (doctor warns), since it runs on Linux and WSL2 only. The check keys on structure only, and it detects only Node clients and CI service containers: a `package.json` at the root or in a declared npm, Yarn or pnpm workspace that depends on a Postgres client (`pg`, `pg-native`, `pg-promise`, `postgres`, `slonik`), a CI job with a Postgres service container (image `postgres`, `postgresql`, `pgvector`, `postgis`, `timescaledb`), or `FACTORY_LOCAL_DB_INIT` in the workflow. A repository that reaches Postgres another way (docker compose, psycopg, the pg gem, pgx) gets no warning. In local mode the validation commands run first and the required checks after, so the heavy suites run on your machine and CI stays light.

## Known limits

- Local mode runs while `serve` runs: a machine that sleeps or shuts down pauses its Objectives until `serve` runs there again (Blocked after a day). A paused Objective keeps its place in the repository's `max_concurrent`. Your machine's size sets how many run at once (`FACTORY_LOCAL_MAX_CONCURRENT`).
- Without the optional Projects permission, the token cannot move Project cards, so labels carry the state.
- `FACTORY_LOCAL_DB` is Linux and WSL2 only.
- No sandbox may create a unix socket (srt's seccomp filter; Codex's sandbox likewise). A suite that starts a server on one, such as a test Postgres with `listen_addresses=` and a socket directory, cannot run locally: leave it out of `FACTORY_LOCAL_VALIDATION`, and the required checks run it on GitHub. A server on `127.0.0.1` works, since each sandbox has its own loopback.
- `/tmp` is read-only in the sandboxes, and Copilot's gives each command an empty one of its own: Copilot opens the temp directory it is started with, which Factory sets to the stage's, never the host's `/tmp`. Temp files go to `$TMPDIR`. A tool that drops `TMPDIR` from its children falls back to `/tmp` and fails there: Turborepo's strict mode does, unless the repository's `turbo.json` lists `TMPDIR` in `globalPassThroughEnv`.
- srt write-protects shell, git and editor settings in the clone (`.bashrc`, `.gitconfig`, `.mcp.json`, `.vscode`, `.claude/agents` and the like), and every sandbox the harness configuration above. Factory creates the absent ones empty, and git-excludes the files, so the sandbox protects a real path and a tool walking the tree sees ordinary empty files and directories. A command that must change a tracked file there (a `git rebase` across a commit that changed `.claude/skills`) fails in the sandbox; those paths are protected paths, which a run may not change anyway. Claude Code's own sandbox also stands in for its settings under `.claude/` (`settings.json`, `skills`, `hooks` and others, varying by version) with `/dev/null`, which cannot be opened there: a repository check that walks `.claude/` must skip what is not a regular file or directory, or walk `git ls-files`.
- A nested git checkout in the clone (a directory with its own `.git`, not a submodule) stays writable on Linux, so a setup, install or the worker can remove and replace it on a resumed stage. srt and Claude Code's sandbox would bind its hooks and config read-only when it exists as a command starts; Factory gives both a ripgrep that leaves a nested repository's `.git` out of their scan for protected names. It fails closed: it is checked as each stage starts (a failed check Blocks the stage), and whenever ripgrep, its filter or the node that runs the filter fails, the sandbox gets ripgrep's whole list and protects the nested checkout as before. ripgrep runs from a directory of Factory's, so a version manager's shim never reads tool versions from the clone; an `rg` on PATH inside the clone or another directory a sandbox may write is refused. Those binds guarded nothing: a command can always make a new repository, and nothing outside a sandbox runs git in one. The clone's own `.git/hooks` and `.git/config` stay read-only. On macOS the sandboxes still refuse writes to a nested repository's hooks and config.
- Each Objective downloads its packages into its own caches, since a cache shared between Objectives would let one plant code in another. Your own caches are not used. pnpm's store and Bun's cache sit in the clone's `node_modules`, so their packages are hardlinked, not copied. Proven with pnpm 12.9, Bun 1.4 and Yarn 1; Yarn 4 is untested.
- A pnpm of its own install (neither corepack's nor a version manager's) must be the version the repository pins in `packageManager` (pnpm 12.9 or newer): inside the sandbox it can neither download nor switch to another version. Corepack fetches the pinned version into the Objective's own `COREPACK_HOME`; behind a version manager, the pinned version must be installed in that manager.
