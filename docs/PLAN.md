# Factory: design and contracts

Factory is a GitHub Action, a harness plugin and a bench, sharing one set of skills and a short task card. An adopter adds one workflow file, a GitHub App and a model credential, and labels an issue `factory:objective`; a worker builds it, a reviewer comments on it, and Factory merges it through the adopter's own required checks and merge queue. The human reads the Project board's Blocked column and, when they choose, the merged diffs. This page is the design as it is now; git holds its history.

## Design rules

- **No planner, compiler or Work Items.** The worker session plans in a comment on the issue and implements with pinned sub-agents. Reason: a stock harness given the brief merged the same Objectives without stops, where a separate planner added holds about Factory's own machinery.
- **Factory merges on its own** (`auto_merge`, on by default). The gate is CI on the reviewed head and on the integrated commit, the comment-only reviewer pass and the merge queue's own re-run; no human reads the diff first. Reason: taking the human out of the loop is the product. `auto_merge: false` gives ready-for-review PRs instead.
- **The only stops are Blocked and Question, and neither stops the queue.** Reason: with many Objectives in flight, every hold is multiplied by the queue.
- **GitHub is the only database, and the Action the only controller on every backend.** The install is the Action plus the App's two secrets; no server, database or vendor platform is ever required. Reason: nothing to host, and the state is where the adopter already looks.
- **Every stage runs behind three interfaces** (trigger, sandbox, gate: `plugin/scripts/lib/backend.mjs`), and every third-party service behind an adapter contract (`docs/ADAPTERS.md`). Reason: a new backend or vendor is one module, not a refactor.
- **Claude Code, Codex and Copilot are peers:** same task card, same skills, each with its own credential.
- **No knowledge loop.** Factory learns through skills people edit and a bench that scores each edit. A correction that repeats across adopters becomes a line in a Factory skill; one that repeats for one adopter goes in a skill in their repository.
- **Skills are capped and measured.** Each skill is at most a page (`bench/skills.mjs` enforces it) and versioned by hash in `bench/skills.json`, whose digest is on every scorecard row. A skill's text changes only with its instrument run: the reviewer replay set (`bench/review-replay.mjs`) for review-pr, the medium drill set (`bench/drill.mjs --set medium`) for the worker skills. Reason: one reasonable line at a time is how a rubric grows past usefulness.
- **No adopter has a code path.** Runner and toolchain are the `runs-on` and `setup` lines in the adopter's file; a need those cannot express is a Factory bug.
- **Factory never builds itself.** Objectives and drills run on scratch adopter repositories, never on this one; the `run` skill refuses it.
- **The App and the Project board are required.** The App is the only identity that both triggers the adopter's CI on Factory's PRs and gets a merge-queue run (below); the board is the dashboard.
- **Adopters take releases by exact tag**, on their own cadence (README, Versioning).

## Job one and how it is measured

Job one: file an Objective, walk away, and come back to correct, merged work at a reasonable cost. Factory is judged on four numbers per Objective, taken by the bench from the issue, the PR, the job log and the harness's usage output.

| Measure | Job-one part | Taken from |
| --- | --- | --- |
| Walk-away: merged with zero human input after the label | Operator walks away | Binary. Any human push, comment or edit on the branch or issue after the label breaks it; a Blocked card is a miss. |
| Solution quality | Correct work | The bench's blind pairwise judge where there is a comparison; the owner's read of the merged diff when they choose to read it; escapes found after merge count against it. |
| Operator minutes | Operator walks away | Minutes spent on Blocked cards and on re-filing, from a stopwatch; zero on a clean merge. |
| Dollars per merged Objective | Reasonable cost | Per harness: Claude's headless output carries total\_cost\_usd and per-model usage with sub-agents included; Codex's JSONL carries the thread's running token counts (a resumed pass counts only its own share), priced from a table, with sub-agent totals possibly folded in; Copilot bills GitHub AI Credits and its usage file reports them per run, so its column is those credits at GitHub's published $0.01 each (configurable), with the premium requests beside them. Runner minutes beside it. Wall time reported, never alone. |

The standing scorecard is one row per Objective, kept by the bench (`bench/score.mjs`, `/factory:score`).

## 0.9.x releases

Factory is at 0.9.x, the release candidate for 1.0, run on real work: its surface is expected to hold and its releases to be fixes underneath, with no stability promise until 1.0. Later 0.9.x releases are batched fixes that ship on CI and the review. 0.9.0 itself was tagged once one frozen candidate tag met this bar:

- **Five in a row per harness.** Claude Code, Codex and Copilot each merge five consecutive Objectives of the scratch medium set (`bench/drill.mjs --set medium`) as walk-aways.
- **Every route covered.** Together those runs cover the Actions, local and cloud-sandbox routes.

Counting rules:

- Any Factory change means a new candidate tag, and every count starts again. Reason: the bar proves one exact tag.
- An answer, un-block, hand-started run or re-run by anyone, an owner's agent session included, is operator input: that row is not a walk-away and the streak breaks.
- A P1 defect found later in a counted merge breaks the streak. The owner reads the counted diffs.
- The streak is counted by `node bench/score.mjs --streak --repo OWNER/NAME --since <candidate tag>` (bench/README.md, The streak): a stall, an unmerged end or an input source the scorer could not read resets it too.

## The 1.0 bar

1.0.0 is tagged when five consecutive real Objectives merge with zero operator input, pooled across the real adopters:

- **Real adopters only:** `clockgrove/clockgrove`, `clockgrove/assetforge` and `clockgrove/raccoon-world` together, never the scratch drill repositories.
- **One pooled streak:** the Objectives of all three, ordered by when each ended, on any harness (Claude Code, Codex or Copilot). Any miss on any of them resets it.
- **It spans 0.9.x releases:** the streak counts from v0.9.0 and keeps counting when the adopters move to a later 0.9.x release; only a miss resets it.
- **The same counting rules as above:** any human input (an answer, un-block, hand-started run or re-run by anyone, an owner's agent session included), a Blocked card, a stall, an unmerged end, an input source the scorer could not read, or a P1 defect found later in a counted merge breaks the streak. The owner reads the counted diffs.

Counting it: the scorer runs per repository and keeps a streak per harness, so the pooled streak is not one command. Run `node bench/score.mjs --streak --since v0.9.0 --repo <adopter> --out <adopter>.json` for each of the three adopters, then merge by hand: take every entry of each file's `streak.harnesses.*.sequence` (`{issue, endedAt, ok, why}`), keep one per adopter and issue (a row of unknown harness is listed under `unknown`, and under every other harness when it breaks), order them all by `endedAt`, and count the `ok` entries since the last one that is not. Five is the bar. An Objective in flight (`inFlight`) has not ended and does not count yet.

At 1.0 the surface README's Versioning section proposes (input names, labels, markers, the App's permission set, the template's jobs) freezes for 1.x.

What 0.9 claims beyond the candidate bar:

- The cloud-sandbox route runs a stage in one sandbox session of `timeout_minutes` plus about 16 minutes (up to 24 hours on Vercel Pro; a plan that caps sessions lower cuts the stage to the session granted, and it Blocks naming the cap if it outruns it), with Claude Code and Copilot proven; Codex in the sandbox is not yet proven.
- Local mode on macOS is sandbox verified, not run end to end.
- Dozens of Objectives in flight at once is the design target (Scale), not a 0.9 claim.

## Credentials and billing

Unattended runs bill API credentials by default (`credential: api`):

- **Claude:** workload identity federation (the job's OIDC token exchanged for a short-lived Anthropic credential, `id-token: write`) or `ANTHROPIC_API_KEY`.
- **Codex:** `CODEX_API_KEY`, passed only to the step that runs the harness, never a job-level variable.
- **Copilot:** `copilot_github_token`, a fine-grained token with only the Copilot Requests permission from a user with a Copilot seat, passed to the harness step only and billed to that seat; never the job's own token, which can write. Doctor fails without it.

The model's own commands never see a credential, on every route. Codex runs with `shell_environment_policy.exclude` and Copilot with `--secret-env-vars`, each naming every model, runner and Factory credential (`SHELL_SECRET_KEYS` in `lib/harness.mjs`; Copilot also masks their values in its JSON output). Claude Code runs every command in its own bubblewrap sandbox, which unsets the same names (`sandbox.credentials.envVars`, [sandboxing](https://code.claude.com/docs/en/sandboxing#protect-credentials)) and gives each command its own PID namespace, so no command reads another process's environment either. Package installs never see one: in a cloud sandbox the start command runs apt, npm (their install scripts included) and the CLI's version check with only `HOME` and `PATH`, and only the stage gets the start environment (`launch.mjs` `START`). Reason: the model runs the repository's code and its dependencies, and a package's install scripts run too; none of them may read the key that bills the run or Factory's tokens.

Claude Code's sandbox on Actions and in a cloud sandbox VM holds local mode's bar (`lib/local.mjs` `claudeRunnerSettings`, `lib/harness.mjs` `claudeRunner`, `lib/claude-runner.mjs`), so every command's writes and network follow its lists there:
- **Writes:** the checkout, `$TMPDIR` (with `$FACTORY_IN` and `$FACTORY_OUT`), Claude Code's own command temp directory and the package caches in the agent's home (`.npm`, `.cache`, `.local/share/pnpm`, `.bun`, `.yarn`); nothing else in the agent's home, and never the checkout's git hooks, config and harness configuration. File edits stay in the checkout and `$TMPDIR` (`acceptEdits`, writes outside the working directories blocked).
- **Network:** GitHub (Git LFS's download host included) and the npm and Yarn registries (`LOCAL_DOMAINS`), plus the workflow's `allowed_domains` input, the counterpart of local mode's `FACTORY_LOCAL_DOMAINS`. A worker that stops because the sandbox denied a host names it (`deniedHosts`), and the Blocked comment names the fix.
- **Nothing the agent can write is read or run by Claude Code's own start-up:** the repository's install and validation run as the agent outside Claude's sandbox, so they could write anything in the agent's home and the checkout's `.git`. So Claude Code runs with a HOME Factory owns (`/var/lib/factory-claude`: no shell start-up file, no git config, only an env file and Factory's skills and agents, which the agent reads and never writes) and a PATH with nothing of the agent's home; its shell snapshot (`bash -c -l`) therefore sources no file of the agent's. Its own `TMPDIR` is `/tmp`, which its unit (or `NAMESPACE_WRAP`) mounts afresh for every start; a directory in the agent's home would sit outside its working directories, where its sandbox cannot read it, and its commands would lose all network (#61). Its config directory is made afresh before every start, with only the session Factory captured right after the previous run put back (so a resume and the saved transcript use Factory's copy). The checkout's `.git` config, commondir, info/attributes and hooks are put back to what Factory left before the repository's install ran, and a replaced `.git` refuses the start. Its commands get the agent's own HOME and TMPDIR back inside the sandbox (`CLAUDE_ENV_FILE`), so caches and the agent's read-only `gh` login work as before. It starts with Factory's flag settings only (`--setting-sources ""`, hooks off, `--strict-mcp-config`) and its own git with no fsmonitor, and the checkout's harness settings are restored to the commit before every start (`lib/local.mjs` `clearHarnessConfig`): a hook or MCP server would run outside the sandbox as the same uid as Claude Code, which can read its process's environment.
- **What the routes change for it:** on GitHub's hosted runners the Action installs bubblewrap, socat and ripgrep and loads an AppArmor profile that lets `/usr/bin/bwrap` alone make user namespaces (not the global sysctl), unloading Ubuntu 26.04's `bwrap-userns-restrict` profile, which takes the capabilities the sandbox needs. It changes nothing on a self-hosted runner, where both would outlast the job and change the whole host: doctor fails until bwrap, socat and rg are installed and, where AppArmor restricts user namespaces, names the one-time admin step (the same profile, and `bwrap-userns-restrict` unloaded and disabled). A cloud sandbox's start and its image build install the packages; its VM has no AppArmor. Claude Code refuses to start where its sandbox cannot (`failIfUnavailable`): no command ever runs unsandboxed.
- **The services setup started are reachable at their usual ports, and nothing else on the machine is:** on Linux a sandboxed command's `localhost` is its own network namespace. Factory notes the TCP ports listening on IPv4 loopback or every address (IPv4-mapped forms included) before the repository's `setup` runs, and before each Claude start offers the ones that appeared since, never a socket the agent uid owns (at most 20; the log names any the cap drops): each `127.0.0.1:<port>` joins the sandbox's allowed hosts, and the env file Claude Code sources inside the sandbox before every command starts a relay on the command's own `127.0.0.1` and `::1` at that port, through the sandbox's proxy (HTTP CONNECT with its per-session login), so `localhost:5432` in `DATABASE_URL` reaches the database setup started. The task card names the ports offered, and says nothing about services when none are. Nothing outside the sandbox runs anything for it: the relay (`socat`) runs inside, and Claude Code's proxy only connects to the allowed `127.0.0.1` ports. A service that was already listening before setup, one listening on another address, or `::1` only, stays out of reach; a command that needs one of those ports for a server of its own finds it taken. Setup's loopback services are trusted: one that offers code execution (`node --inspect`, a Docker TCP API, a database with `COPY ... PROGRAM`) is a path out of the sandbox to the credential-holding uid, the same exposure the validation commands already have. (`excludedCommands` was no option: it would run the command outside the sandbox, credential included.)
- **Trade-off:** Claude Code's systemd unit on the runner runs without `ProtectKernelTunables` (`lib/claude-runner.mjs` `asClaudeAgent`): its read-only mounts over parts of `/proc` keep a user namespace from mounting a fresh `/proc`, so bubblewrap cannot start under it. The agent stays unprivileged, with no new privileges and no capabilities, so `/proc/sys` and `/sys` stay root's to write; every other command the agent runs keeps the setting. `NAMESPACE_WRAP` in a cloud sandbox needs no change.
- **Why not `CLAUDE_CODE_SUBPROCESS_ENV_SCRUB`:** in Claude Code 2.1.322 it also forces the default permission mode and makes the working directory's `package.json`, lockfiles, `.npmrc` and `.env*` read-only to commands (so `npm install <package>` fails with EROFS) and leaves empty placeholders for the absent ones in the checkout. None of that is documented or can be turned off, and it would stop a worker changing dependencies. An `apiKeyHelper` is no option either: Claude Code runs it as the model's own uid and again every five minutes by default ([settings](https://code.claude.com/docs/en/settings-reference#apikeyhelper)), so whatever it reads, the model's commands can read.

`credential: plan` with `CLAUDE_CODE_OAUTH_TOKEN` is allowed on a developer's own repository only; doctor warns that plan limits assume ordinary individual use. `credential: login` (the CLI's own login) is for a developer's machine and is refused inside Actions. Local mode and `/factory:run` run on the developer's own harness login. Factory never stores, brokers or pools a subscription token. Reason: API billing makes `max_usd` and `daily_usd` real numbers, and the vendors' terms limit plan tokens to ordinary individual use.

## The product

| Piece | Form | What it does |
| --- | --- | --- |
| Worker | `plugin/scripts/worker.mjs` on the Claude Code, Codex and Copilot CLIs | Takes an issue number and the task card; plans in a comment on the issue, implements with pinned sub-agents, rebases, validates with the repository's commands and leaves its outputs as files. Factory then pushes and opens the one PR. Runs on a runner, in a cloud sandbox or on the developer's machine. |
| Action | `clockgrove/factory@vX.Y.Z`, called from `.github/workflows/factory.yml`, which `/factory:setup` renders from `plugin/workflow-template.yml` | The `dispatch` job finds ready Objectives and starts up to `max_concurrent` `work` jobs under `daily_usd`; the `review` job runs the one comment-only review, the answer pass and the merge; `queue-watch` watches merge-queue commits. On the sandbox route, `launch` jobs start each stage in the Objective's sandbox, and `image` and `sweep` keep its images. |
| Plugin | The same tree for Claude Code and Codex (each through its plugin marketplace) and Copilot (skills and agent definitions written into the checkout) | `/factory:run <issue>`, `/factory:serve`, `/factory:review <pr>`, `/factory:score`, `/factory:queue`, `/factory:doctor`, `/factory:setup`. The Action runs the plugin's own scripts, so a session and the Action are one source. |
| Bench | `bench/` | The scorecard, the blind pairwise judge, the auto-grader, the reviewer replay set, the drills and the skill digests. |

One worker, three routes: a GitHub runner (the default), the developer's own machine (local mode: `factory serve`, every command in a sandbox, `docs/LOCAL.md`), or one cloud sandbox per Objective (`docs/ADAPTERS.md`). Without a workflow file, `/factory:queue` starts a scheduled task in the harness vendor's cloud instead; Claude's cloud ignores repository-declared plugins but loads committed `.claude/` directories, which is why setup offers to commit the skills. State lives in the issue, the PR, the Project card and the job log.

## How an Objective flows

1. **File.** A writer opens an issue stating the Objective (goal, acceptance entries under an Acceptance heading, sources, context, recorded decisions) and a maintainer applies `factory:objective`. The Project card is Queued. Blocked-by relations on the issue are the only dependency graph; an issue closed by any route counts as done.
2. **Dispatch.** The dispatcher, ticked by events (any issue closing among them, since it may block an Objective) and by Factory's own jobs, with GitHub's `*/10` cron as the backstop, picks ready Objectives by priority label and starts work up to `max_concurrent`, stopping at `daily_usd`. The card moves to Running.
3. **Work.** The worker checks out the default branch, runs `setup`, installs offline from the lockfile, renders the task card and starts the harness with the issue text verbatim. The harness writes its plan, implements, rebases, validates and commits, and leaves its plan, PR text and exit record as files. Factory posts the plan, pushes `factory/<issue>` and opens the one PR. The card moves to In review.
4. **Review.** The reviewer posts findings as PR review comments. The worker gets them once and addresses or rebuts each in a reply file; Factory pushes its commits, posts the replies, and validation runs again.
5. **Merge.** Factory merges the reviewed head once its required checks are green, through the merge queue where there is one. A conflict or a red integrated run goes back to the worker once; a second failure is Blocked. A PR that conflicts when its review reaches the merge (a sibling landed first) is the same case on every route: nothing is enqueued, it stays delivered, and the send-back takes it (`factory run --wait` does the send-back itself). The card moves to Done and the issue closes.
6. **Blocked.** The PR becomes a draft, the card moves to Blocked, and one comment states the reason (validation failed twice, reviewer findings unaddressed, dollar or time cap reached, worker died twice, integration failed twice). The queue does not wait. A human fixes it by pushing to the branch or editing the issue and re-applying the label; a local Block on hosts the sandbox denied names them and its own fix (Exit: blocked, below).

## The task card and the skills

The worker's instructions are a short task card (`plugin/templates/task-card.md`, rendered per run: issue, budget, the three exits, what to leave where, no questions) plus skills loaded when their step is reached: `objective-plan` (the plan comment, assumptions, the Question rule), `implement-split` (implementer sub-agents, disjoint-file parallelism, sequential PRs for large Objectives), `prove-acceptance` (real-path proof, no weakened tests, the base-failure rule, the budget command), `deliver-pr` (rebase, the PR body, reviewer replies), `review-pr` (the reviewer's own) and `scoring`. All three harnesses read the Agent Skills format. Agent definitions are written three ways from one source (`plugin/agents/source.json`, `node plugin/agents/render.mjs`): Markdown for Claude Code (with a pinned `model`) and Copilot (a `model` only when `subagent_model` or `reviewer_model` is set), TOML for Codex. Where a model is pinned, it is in the file, never passed at spawn time, because Codex drops a spawn-time model for role agents. An adopter overrides a skill by placing one of the same name in their repository, and adds their own.

## The worker contract

|  |  |
| --- | --- |
| Inputs | The rendered brief (validation and budget commands, base commit, issue number, dollar and time budget filled in); the issue body verbatim; the repository at the default branch, fetched, with `setup` run and dependencies installed offline; `$FACTORY_IN`, what GitHub holds for this stage, rendered by Factory before each pass; the pinned implementer and reviewer agent definitions written into the checkout; on every route the harness's environment, which the commands it runs inherit (credentials excluded), carries `FACTORY_ISSUE` (the Objective's issue number) and `FACTORY_BRANCH`, a stable contract a repository's own tooling may read, for example to key per-Objective spend limits. |
| Outputs | Commits on `factory/<issue>` and the hand-off files in `$FACTORY_OUT` (plan, PR title and body, replies, blocked note, exit record); the usage record the harness emits, which the job uploads as an artifact for the scorecard. Factory reads each file as the agent through a pipe (a regular file under a size cap, never through a symlink), escapes every `<!--`, strips closing keywords, neutralises @-mentions and a leading `/`, adds its own markers and the issue link, and makes every GitHub write: the push, the PR, the plan comment, the replies, the note, labels and the exit. |
| Allowed | Any file not on the protected list (`.github/`, `CODEOWNERS`, `.agents/skills/`, `.claude/`, `.codex/`, the files the `setup` command names, plus the repository's `protected_paths`). Any command the runner allows. Sub-agents on the pinned model. Network as the runner has it. |
| Not allowed | Asking. Editing a test to pass it unless the issue asks. Touching a protected path (the job refuses the commit, Factory refuses to push it). A stage answers only for what changes after it starts: what a maintainer pushed to the branch before it, and what a rebase takes from the default branch, are not its own; reverting a maintainer's change is. In a fix pass (after a red, or the answer pass after the review), changing toolchain, lockfile or CI configuration (version pins, package-manager config, including a `pnpm-workspace.yaml` change other than to its `packages` list alone, or one that does not parse, lockfiles, CI files outside `.github/`, containers and devcontainers, git hook managers, a `*toolchain*` file or one under a `toolchain/` directory, a file the `setup` or an explicit `install` command names, other than a manifest, lockfile or requirements file it reads) that the branch had not changed before the stage's first fix pass, that the plan as it stood then does not name (the plan is read once per stage: a fix pass that edits it widens a later stage's scope, never its own stage's), and that the issue, a maintainer decision, the red's failure window or the comment answered does not name either (a lockfile is in scope when its own manifest beside it is: changed before, named, or changed by the same pass, as when the fix adds a dependency, so `package.json` brings `package-lock.json`, `pnpm-lock.yaml` or `yarn.lock`, `pyproject.toml` brings `uv.lock` or `poetry.lock`, `Cargo.toml` brings `Cargo.lock`, and nothing else; in a workspace, a member's manifest changed before or by the same pass brings the workspace's root lockfile, and only it: `pnpm-lock.yaml` for a `pnpm-workspace.yaml`, the npm, yarn or bun lockfile for `package.json` `workspaces`, `uv.lock` for `[tool.uv.workspace]`, `Cargo.lock` for Cargo `[workspace]`, members as that declaration listed them when the fix passes began, exclusions honoured; a lockfile changed without its manifest or a member's in scope is refused): the pass gets one turn to put those files back, and what it keeps is refused (Factory pushes none of it, posts no PR body, reply or thread resolution from that pass, and the stage Blocks with the files named). A turn that puts them back and asks a Question in its exit record ends the stage with that Question; no further fix pass runs. Any write to GitHub: no push, PR, comment, reply or label. |
| Exit: delivered | PR open and not a draft; validation green; reviewer pass done. The merge queue takes it. |
| Exit: question | The worker hit an assumption that would change or remove an existing public contract, contradict a recorded decision or grant new access (a permission, a credential, a newly exposed service); any other addition that leaves every existing use working is an assumption. Each question in the exit record names its test (`contract`, `decision` or `access`) and the existing contract, the decision or the access granted; a question exit that names none is checked once by the harness, which keeps what meets a test and records the rest as assumptions. The PR stays a draft with the question in its body; everything else is finished. The card moves to In review with a question marker; the queue continues. A human answers in a comment, review or line comment on the PR or the issue and marks the PR ready; the review job runs, and its answer pass applies what was said since the question even when the PR was already reviewed; with nothing new, the PR goes back to a Question. On Actions, when a maintainer both answers and marks the PR ready while the review job that raised the Question is still running, that job leaves the PR ready, and the review job the ready mark started applies the answer. Comments by people with write access reach every worker, reviewer and answer pass as the maintainers' decisions. One Question comes before the work: Factory works in one repository per Objective, so a plan that needs a change in another repository (its `Needs-Repository: OWNER/NAME` line) stops after the plan (Factory stops the harness when the line appears in its plan.md, read every two minutes), and Factory runs no validation or fix pass and asks on the issue, naming the repository and how to answer: split the Objective into one per repository and re-apply the label, or say in a comment on the issue how to do the work in this repository alone (not by marking a PR ready). An issue body that names another repository for Factory to change (its `Factory-Repository: OWNER/NAME` line) is asked before any harness runs, and is answered only by taking the line out of the body: while it stays, each rerun asks again, with no harness started. A value that is no OWNER/NAME (`none`, `N/A`, a parenthesis) is no need, and a repository the plan needs that a maintainer's comment names after Factory asked about it is not asked about again. |
| Exit: blocked | Validation red after Factory's last pass (two, plus one when the required checks are first red on the second, plus one for each merge of the default branch Factory made itself before a push (Review and merge, below) whose validated head is red: that pass is not the change's, so it never takes the last one; decided on the commit id Factory recorded for its merge); each fix run after a required-check red gets every failing job's whole log as a file (aggregates included, required jobs first, none left out for an optional one; at most ten) and the two-dot diff from the PR's last green head (or why none could be made), and, as evidence and never as an instruction, how many of the default branch's newest runs of each job are red and their failure lines beside this run's; a red whose every failing job fails exactly the same way steadily on the default branch (same job, same failure signature, failure lines and the repository files they point at, on its newest run there and on at least two of its newest three, attempts included) is handed back at once as a base failure (`base failure: <jobs> fail the same way on <branch>@<sha>`), with no fix run; a single red run on the default branch (a flake, an outage) hands nothing back; a required check whose Actions job GitHub never started (completed as failed with no step and no runner: a billing lock, a spending limit, a runner label nothing serves; the job itself, or one a failing required aggregate gathers when every failing job that aggregate gathers never started) Blocks at once with no triage, rerun or fix run (`GitHub did not start the required job <name>: <GitHub's annotation>`), decided on those fields and never on the annotation's words; reviewer findings unaddressed after the one pass; integration failed twice; dollar or time cap reached; worker process died twice; the model provider refused a harness call outright (a 4xx other than a timeout, conflict or rate limit, or a quota, billing or authentication type or code, read from the harness's own structured error: Claude Code's result `api_error_status`, Codex's `turn.failed` JSON error body, Copilot's `session.error`; never from the message's words), which is never retried or counted as a death and Blocks at once naming the harness, the status, type and code and the provider's message shortened (`<harness> was refused by its provider (HTTP 400 <type> <code>): …`), the fix being the credential's account or the settings; doctor's `--probe` fails on the same refusal. Draft PR, card to Blocked, one comment with the reason and the fix. A worker's own reason, like a Question's, is shortened past 200 characters on a word boundary and ends in `…`. A worker that stops because its sandbox denied a host it cannot do without lists the host names in its exit record's `deniedHosts` (values that are not a DNS host name are dropped; at most ten); in local mode the comment names each host the sandboxes do not already allow and gives that fix instead of a push or an edit: add them to `FACTORY_LOCAL_DOMAINS`, then re-apply `factory:objective`. Factory never allows a host itself. |

The Question exit does not stop the Objective's other work or the queue, and costs the worker nothing to raise, so it is raised only when the card's test is met.

Trust. Factory acts on an Objective's text only when the issue's author and, once the body was edited, its last editor can push or are pinned maintainers. The worker and the review job check it before any harness on every route (Actions, local mode, a cloud-sandbox stage), acting on the body read with those people; a session reads the issue only through `factory issue`, and `deliver` and `post-review` check it again. Otherwise the stage Blocks before a harness sees the text. Factory acts on a marker (validated, rebase, review, spend, decisions-read, a local claim) only from its own login or from a person with push access. Its own login comes from its token, never from a comment's author: the App's bot on Actions, the token's owner in local mode. No other App counts, the job token's `github-actions[bot]` included. The workflow's `notify` and `maintainers` are written `login#id` and trusted by the numeric id, so a login renamed away is a stranger; doctor warns about a bare one and names the id to add.

Split Objectives. A part's exit record lists the checklist items left; its PR says `Refs #N` instead of `Closes #N`, and Factory records the part on the issue. When it merges and the issue stays open, the dispatcher deletes `factory/N` and queues the Objective again; the next part starts from the default branch with the plan and the merged parts' PRs in `$FACTORY_IN`. One PR is open at a time, and an Objective that needs more than six parts Blocks.

Git LFS: in a repository whose `.gitattributes` uses LFS, every worker and review job fetches the branch's LFS objects before the harness (a failed fetch is a warning, not a Block); that spends LFS bandwidth per job in exchange for validation and the model seeing real media. In local mode the harness's sandbox cannot reach LFS storage, so the model commits media and Factory's own push uploads it from the host, to the repository's own GitHub endpoint whatever `.lfsconfig` says, with the token offered to github.com only; a branch carrying more than `FACTORY_LOCAL_MEDIA_MAX_MB` (500) of media since the default branch Blocks.

## Review and merge

Factory merges on its own (`auto_merge`, on by default); the gate is CI green on the integrated head, the reviewer's one pass and the merge queue's re-run. The owner reads merged diffs when they choose, and the bench's judge samples them. A defect the reviewer flagged and the worker rebutted stays visible on the merged PR; a repeated class becomes a reviewer-skill change scored on the replay set.

The reviewer is one model call per PR on the top model, after validation passes. It gets the Objective text, the diff and the PR body, and it posts review comments tied to lines, each naming the acceptance entry or repository rule it concerns, with assumptions that change behaviour flagged explicitly. It also judges every acceptance entry, met or not, with the line that shows it: Factory lists the issue's entries in the prompt, puts the judgments in the review body, names any entry left unjudged, and turns an entry judged not met into a comment the worker must answer. A call that fails (a crash, a non-zero exit, a cap) or an answer that holds no JSON or judges none of the entries is a missed pass: it reruns once in a fresh session on every harness, on the fallback reviewer where the harness has one. When neither call produced a review, nothing is posted and the Objective Blocks with how each call ended: no placeholder stands in for a review that did not happen, and Factory never merges past the review. A rerun that answered but judged none of the entries is posted, and its placeholder says it is not a clean pass. Entries left unjudged are recorded on the review, not enforced: they do not hold the merge. It has no verdict and no refuse path: a reviewer that can stop a run turns every false positive into a hold. The worker gets the comments once and addresses or rebuts each; Factory pushes, posts the replies, and validation runs again; rebutted findings stay visible on the merged PR.

Factory's push and merge. The harness pushes nothing. Factory takes the branch as a git bundle the agent writes to a pipe, indexes its pack into a mirror only Factory can write (a mkdtemp directory under Factory's own 700 temp directory) with `git index-pack --strict`, so every object is fsck-checked whatever the git version, and checks it there: the paths changed since the stage started (GitHub's head before any harness ran), Git LFS pointers, the local media cap, and each LFS object's bytes against its pointer. It then pushes with an explicit lease on the head it last saw, to `refs/heads/factory/<issue>` only, and reads GitHub's head back. Before a push, when the default branch on GitHub changed a file under `.github/workflows/` since the branch's base, Factory merges it into the branch in the mirror (its own merge commit, from `git merge-tree`) and the checkout fast-forwards to it (one that cannot, with uncommitted edits in the way, keeps the branch on that merge: the next push merges the checkout's new commits onto it, so the branch only moves forward): GitHub refuses a token without the Workflows permission, the App's or the local one, a branch whose workflow file is a version no branch has any more, which is what a run cut before such a change carries. A new branch that conflicts with that merge is not pushed; the harness resolves the conflict once, as a send-back's conflict pass does, and Factory pushes again. That pass answers like the work pass: a cap it reaches Blocks with that cap, and a death, or a rebase or merge it leaves in progress in the checkout, Blocks with nothing pushed. A push GitHub refuses for a workflow file Blocks with that cause, in Factory's words; any other refused push Blocks with git's status word and the exit code, and GitHub's own text goes to the job log only. A refused or rejected push, or a head that is not the one checked, Blocks. Nothing is armed for later: the review job records the head it reviewed and validated as mergeable, and merges exactly that head (the merge endpoint's `sha`, or enqueue with `expectedHeadOid` on a merge queue) once its required checks are green, the review is done and no maintainer decision is unread; otherwise the dispatcher's merge pass does it on a later tick. A merge or enqueue GitHub refuses because another pass already merged the PR, or queued it at the reviewed head, counts as done; that is read from the PR again, never from GitHub's words. The dispatcher's tick comes from events, never only from GitHub's cron: CI finishing on a Factory PR's head (the launch gate's merge tick on the sandbox route; the dispatcher's own `workflow_run` and `check_suite` triggers without one), a Factory PR merging, the queue dropping one (`pull_request` `dequeued`), and the queue watch. A PR the queue drops unmerged (its checks failed or timed out on the queue's commit) is enqueued once more, and the issue gets one line saying so with the queue's code and time; dropped again, the Objective Blocks with the queue's reason codes, read from the PR's timeline. Only drops after the latest of the review the merge rests on, the head's commit (GitHub keeps no push time for a branch push) and the issue's last re-entry or Block count, so a re-entry starts the count over even when its head keeps the earlier review. When GitHub never started the required job on a dropped entry's merge_group commit (no step, no runner: a billing lock, a spending limit), the Block says so as infrastructure, quoting GitHub's annotation, as validation does, rather than pointing at the checks. A queue commit on which CI never begins in 10 minutes counts as a drop too, and so does one on which CI began but a required check makes no progress. Progress is read from the check's Actions job: its steps, each one starting and completing (a running job's log is not readable, so it is not used). The job is stalled when the step running now has run past max(3 × that step's normal duration, that duration + 15 minutes), so never under 15 minutes (16 for a step that normally takes 1); the normal duration is the longest the same step of the same job took in the workflow's last 15 green runs on the default branch or in the merge queue, read with the job token once per dispatcher tick or queue watch, and only once a step has run 15 minutes. A step with no history, a running step GitHub gives no start time (counted from the check run's start), a check that is no Actions job, or a job Factory cannot read falls back to a time bound from the job's own start: the queue's check timeout (`check_response_timeout_minutes`, from the ruleset; setup's 60 when unread) less 10 minutes, at least half of it and at least 20 minutes, so 50 minutes at 60. A job queued or waiting for a runner, or with no steps yet, is never stalled. A required check not reported at all (an aggregate behind `needs:`) is judged by its upstream jobs' progress, and by the fallback from CI's first start when nothing runs there. The notice names the stuck step and its times, e.g. `` `Quality` / `Run scripts/ci/setup.sh` running 16 min, normally ~1 min ``. On the local route the Factory App has no Actions permission, so Factory reads no job steps or history there and the hung rule is the time fallback only, read once per merge pass. Factory takes the PR out and puts it back once, which restarts CI, and the second time Blocks naming the check. A removal Factory made reads its reason back from Factory's own requeue comment on the issue, which records it, since GitHub's timeline cannot say why Factory removed a PR. CI has begun once a check run or status named like a required check exists on it, or a check run or suite from the integration that provides the required checks (Actions when the ruleset names none), so an aggregate required job behind `needs:` that starts late is not a stall; another app's run, such as code scanning's, does not count. Any run from that integration counts, required or not (a `push` workflow that fires on the queue's branch, another `merge_group` workflow, a startup failure); one that never produces the required check is bounded by that rule and the drop handling. When the required checks cannot be read, any check run, any status, or any suite with a run counts. The queue-watch job, started by the dispatcher whenever its merge pass leaves a PR in the queue, reads the entry every 30 seconds until the PR leaves the queue, merged or dropped, or stalls there, and then ticks the dispatcher with its own `workflow_dispatch`; after 12 minutes it ticks anyway, and that run starts a new watch. Recovery from a drop never depends on the `dequeued` run: GitHub attributes that event to `github-merge-queue[bot]` and, under a strict approval policy for outside contributors, holds it for approval, while a `workflow_dispatch` by the job token is never held. The `dequeued` run stays a faster path where it runs; the merge pass reads the queue and the PR's timeline each time, so the two never enqueue a PR twice. Local mode's loop runs the merge pass every interval itself. A person's own removal from the queue is a hold, not a drop: Factory leaves the PR out until they enqueue it again, or it is reviewed again, gets a new head or re-enters. Doctor names an installed workflow rendered before these ticks (re-run `setup --apply workflow`), and, with a merge queue, warns when the repository's approval policy can hold the `dequeued` run (or cannot be read, which needs admin), saying recovery runs from the queue watch. The squash commit carries the PR's title and Factory's closing line, never the branch's commit messages; on a merge queue, setup sets the repository's squash default to the PR's title and body, and doctor checks it. A PR that fell behind gets GitHub's update-branch merge; that new head is accepted only when it is a merge of the recorded head and a default-branch commit, committed and signed by GitHub's web-flow key, with exactly the tree Factory's own `git merge-tree` of the two gives. Any other new head goes back to review. Factory's git runs only in its mirror, with hooks off and no global or system config; the agent's checkout gets the default branch, the branch and Factory's own clean rebase as bundles, and every git command there runs in the agent's sandbox. Only the commit Factory's rebase made keeps the review; a head the harness made (a resolved conflict, a fix) is reviewed again, and so is a rebase Factory then merged a workflow change into before pushing.

The merge queue is GitHub's. It serializes merges and re-runs CI on the integrated head, which is what makes dozens of concurrent workers safe without owned paths: a PR that was green on its branch and conflicts after a sibling merges is caught there, sent back to its worker once with the conflict, then Blocked. Two mechanics decide how it is wired. First, a PR opened, pushed or enqueued with the job's `GITHUB_TOKEN` gets no `merge_group` workflow run, so its required checks never report and the queue evicts it at the timeout; every push, PR creation and enqueue therefore uses an installation token from the adopter's Factory GitHub App, and the job token stays read-only. Second, the queue needs its checks reported on the queue's own commit, so the repository's CI is a separate workflow triggered on `pull_request` and `merge_group`, never a step inside the worker job; the worker job's own validation run is the worker's feedback, and the CI workflow is the gate. Branch protection requires the queue and those checks, so neither a worker nor a stray push bypasses them. A required check that is skipped counts as passed, so aggregator jobs use `always()`.

## Scale

The design target is dozens of Objectives queued and in flight with nobody watching. It is not yet drilled at that size and is not among the 0.9 claims.

- **The dispatcher is the only scheduler logic.** Ready = labeled, not blocked by an open issue, not Running, In review, Blocked, Question or Done. Order = `P0`, `P1`, `P2`, then issue number. Start up to `max_concurrent`; stop for the day at `daily_usd`.
- **Factory owns its ticks; GitHub's cron is only the backstop.** GitHub fires a schedule late or not at all under load: on the scratch repositories the `*/10` cron fired for under 3% of its slots over a week, hours apart. So every wait has an owner that ticks the dispatcher with `workflow_dispatch` (the job token's, never held for approval): an event (a label, an issue closing, a merge, CI finishing, a queue drop; a closed issue that was no Objective and blocks none ends its run after minting the token and at most one listing, so it costs a job start and seconds), the job that freed a slot or failed a launch, or, for a wait only time ends, the `wake` job. Each dispatcher run lists its deadlines (`{issue, kind, at}`, in its log) and arms one wake for the earliest of five kinds: a sandbox stage's lease end plus a minute (a stage that died silently), a quota retry the launcher handed over, the next try of a failed start (2, 4, 8, 16, then every 30 minutes; a vendor's refusals never Block and hold the route's new picks for at most four in a row, three real failures or three cut-offs in a row Block; every attempt ends as a stored entry, docs/ADAPTERS.md), the next 00:00 UTC when `daily_usd` held Queued work back, and one quick retry of a read that failed (never two in a row). The other kinds it lists (`launch-grace`, `review-grace`, `checks-grace`, `answer-grace`, `local-pause`) are their event's or the local loop's, with the cron behind them; a stale Running Objective on the runner route is bounded by its job's `timeout-minutes`. A wake arms only when no wake already queued or sleeping fires before its deadline or within a minute after it (read from the `wake (<kind> <iso>)` job names), joins no concurrency group, and is never cancelled, so a duplicate only ticks twice; a run a wake started never arms that same deadline again, and dry runs and runs named for one issue arm none. Which kinds a repository arms follows its visibility, read from the event's repository payload (one repository read only when a schedule run has a long wait to decide; unknown counts as private). Cost: a wake sleeps on a hosted runner and holds one of the account's concurrent-job slots while it sleeps.
  - **Public repository:** Actions minutes are free, so it arms all five kinds. On the sandbox route a lease wake sleeps through each stage (the heartbeat moves the lease on), and a capped day's turn is reached in hops of up to 350 minutes, each a plain tick.
  - **Private repository:** each sleeper bills about $0.36 an hour (a 2-core Linux runner at $0.006 a minute), so it arms only `quota`, `start-retry` and `retry`, minutes each: about 5 to 20 billed minutes per quota retry, 2 to 30 per failed start and 2 per read retry. Each launch the dispatcher names also arms a `start-retry` wake for its marker's expiry, about 10 billed minutes (about $0.06) per named launch unless an earlier wake covers it, so a normal Objective costs about 10 to 20 sleeper minutes (its work and its review). A stage's lease end and the day's turn stay in `deadlines[]` and wait for events and the cron; doctor says so on a private repository.
  - **The sandbox sweep and image build no longer wait for their crons.** GitHub's hourly sweep cron and nightly image cron are backstops only (on a scratch repository the sweep's fired twice in about 40 hours; the nightly build was skipped one day and ran 7.5 hours late the next). No sleeper waits hours for either:
    - **The sweep arms its own `sweep` wakes, minutes each, on every repository.** Each sweep run arms its next one for what it left: a stage that said it ended moments ago (its launcher's end answers first; 10 minutes), a sandbox created moments ago (15), an older image a stage may still be starting from (15 minutes after a newer build is recorded; the image job arms this after each build that leaves one), the rest of a run that reached `sweep_max_destroys` or its collection slots (10 minutes on, after a run that destroyed or stopped one; with nothing destroyed, a cap of 0 among others, the rest waits for events and the cron), and once what a failure left (never from a `sweep` wake's own run). Each is a minute after its wait ends (about 16 minutes at most), through a wake job of its own (`sweep-wake`, `image-wake`, named `wake (sweep <iso>)`), whose tick runs the sweep and the dispatcher. Only an armed `sweep` wake covers a sweep deadline. A stopped sandbox's `sandbox_idle_days` (days, not minutes) get no wake: the next sweep an event runs (an Objective closing, merging or Blocking) destroys it, or the hourly cron's.
    - **An owed image build runs on the UTC day's first dispatcher tick.** A head an earlier day left unbuilt (today's `image_daily_minutes` used up, or `image_refresh: nightly`) is owed once today's turn allows a build: under today's minutes for `merge`, none tried yet today for `nightly`. Every dispatcher tick on the sandbox route checks (three reads: Factory's image record and the default branch's head commit) and, when one is owed, sets `image_owed`, and the image job builds the default branch's head in that run (on any event but a pull request's). A merge after 00:00 UTC builds on its own push as before. Every build records its attempt on the image record before its first vendor change, and an owed build before anything that can fail; the build's own entry replaces it. Any recorded build of the head (built, failed, or only started: a crash, a 45-minute timeout, a vendor or token error, a refusal) ends the owing, so the next merge or the nightly cron tries again, never another tick. An owed build's job re-checks the record when it starts, so a job a tick queued during another build of the head builds nothing. The image job needs the dispatcher only for this: a push, the cron and a manual build's run skip the dispatcher by its own `if:`, and the image job still runs (`!cancelled()`).
    - Cost on a public repository: none in minutes; each sleeper holds a concurrent-job slot. A `sweep` sleeper is 11 to 16 minutes, about one per image build that leaves an older image and per stage that Blocks itself, so about 30 to 60 minutes a day on a busy repository and none on a quiet one. A private repository pays the same, about $0.07 to $0.10 per wait.
- **Workers do not know about each other.** Coordination is the rebase plus the merge queue. Two Objectives that keep conflicting on one file produce two Blocked cards with the same reason, which is the signal to re-file them or order them (`blocked_by`), not a reason for a planner.
- **Cost is the only cap.** No cap on merges or Objectives per day. Dollars are capped by `daily_usd` on the dispatcher and `max_usd` per job, with `timeout_minutes` as the time cap. `max_concurrent` is a runner-capacity and conflict-pressure control: a matrix with `max-parallel` over the ready issues, since an Actions concurrency group cannot cap at N, and a concurrency group per issue so a repeat trigger dedupes rather than cancels a sibling. Hosted runners cap a job at 6 hours; `timeout_minutes` sits under that.
- **The board is the dashboard.** Queued, Running, In review (with a question marker), Blocked, Done, moved by the jobs.
- **Runner choice is a line in the file.** Hosted by default; self-hosted where an adopter wants their own toolchain or hardware, with `setup` as the only place a toolchain is named.

## Security

What the workflow file makes visible, and what is true:

- `permissions:` gives the job's own token `contents: read`, `issues: write` and `actions: read`; the jobs that tick the dispatcher get `actions: write` (work and review also use it for triage's rerun of failed CI jobs), and `id-token: write` is uncommented only for Claude federation. Every write to code goes through the App's installation token, minted for that one repository. No org scope, no PAT, no stored subscription token.
- The harness holds no GitHub write access. On Actions it runs, with the install and the validation, as a separate uid, `factory-agent`, created with sudo per runner: no groups, no sudo, no cron, at or lingering session, its own 700 home, always `/home/factory-agent` and wiped before each job (doctor fails if a `factory-agent` user has any other home), holding its clone and a read-only installation token. Each command runs in a transient systemd unit (`systemd-run`), or, where there is no systemd, in its own namespaces and a cgroup v2 group, with the system read-only, every other home hidden, a private `/tmp` and no new privileges, so it cannot read the runner's home, Factory's temp directory or Factory's process environment, nor write outside its home. Commands start with a fixed `PATH` and no system or global git config. The unit's processes are killed with it after each run, before Factory reads what it left. The write token lives only in Factory's memory (GitHub calls through `fetch`, Factory's git by per-process env config). `setup`, which may need sudo, runs as the runner on a clean default-branch tree Factory made, with Factory's own temp directory. `FACTORY_APP_TOKEN`, when an adopter supplies a fixed token, is Factory's write token; the agent then gets no token and can clone a public repository only; a private one needs the App's id and key. Copilot always runs with its built-in GitHub MCP server off and is never given folder trust, so the repository's own Copilot configuration does not load. Doctor parses every workflow and fails closed: the repository's default workflow token must be read-only (or, when doctor cannot read the default, every workflow must set read-only `permissions:`), no `pull_request` or `merge_group` workflow may ask for write, since branch code runs there, and the Copilot token must be refused on an issue, a pull request and a file write. It checks `sudo -n` and the agent launcher on the runner.
- `.github/` is on the protected list, so Factory refuses to push a workflow change; the App has no workflows permission, so GitHub refuses one as well.
- `auto_merge` on means code lands without a human read; the file says so in its header comment, beside the gate.
- Cost is capped in the file (`daily_usd`, `max_usd`, `timeout_minutes`), and Claude's `--max-budget-usd` and Copilot's `--max-ai-credits` enforce the per-job cap inside the run; Codex is checked after each run.
- The prompt-injection surface is the Objective text and the comments Factory reads. Factory acts on the Objective text only when its author and last editor can push or are pinned maintainers, checked before every stage on every route (otherwise the stage Blocks before a harness sees it, and a session's `factory issue` refuses to hand it over). Only a maintainer can apply the label; comments count as decisions only from people with write access or the maintainers the workflow names (Trust, above). Secrets are masked in logs, the task card forbids printing them, and the Codex key is step-scoped so repository code never sees it.

Notifications. GitHub Mobile notifies on subscriptions, so a comment on an issue the owner authored, or a PR they are requested on or @mentioned in, reaches their phone whichever identity posted it. `notify` names the handle: the Blocked comment @mentions it and a Question draft PR requests it as reviewer. Merges and plan comments stay quiet unless the owner watches the repository.

Why the App is in the footprint at all: it is the one thing GitHub makes unavoidable. Workflows do not run on events the job token causes, and the merge queue attributes its run to whoever enqueued, so an App (or a PAT, which Factory does not support) is the only identity that both triggers CI on the PR and gets a merge-queue run. The cost is one setup screen and two secrets; the gain is that the adopter's existing CI runs on Factory's PRs unchanged, and commits carry the App's name.

## Doctor

The same checks run as `/factory:doctor` before the workflow is enabled and as the first step of every worker job, so a misconfigured repository Blocks with a one-line reason instead of spending a run. Each line is PASS, WARN or FAIL with its fix, and `/factory:setup` offers to apply the GitHub ones. Credentials: the harness's credential is present (for Copilot, `copilot_github_token`, refused on an issue, a pull request and a file write); a plan token is a warning. GitHub (the workflow file read from the default branch on GitHub): the App's installation token mints for this repository with its one permission list (README, Install footprint; a missing read fails) and no workflows; the job token is read-only on code; the merge queue and required checks are on the default branch and the CI workflow listens on `pull_request` and `merge_group`; the labels; the five Project columns; `notify` and `maintainers` pinned as `login#id`. Repository: `setup` runs clean, the validation commands exist, the lockfile installs offline, protected paths are present and cover every repository file the `setup` command names (setup adds them root-anchored, as `/scripts/ci/setup.sh`), repository skills parse and fit the cap, git-lfs is installed when `.gitattributes` uses Git LFS. Runner: `runs-on` resolves and matches the Linux runner of the CI workflow on `pull_request` (a warning), the harness CLI installs, `timeout_minutes` fits the runner's ceiling, and for Claude Code bwrap, socat and rg are present where the job runs, AppArmor lets bwrap make user namespaces on a self-hosted runner, and every `allowed_domains` entry is a host name (a warning names each one dropped; Credentials and billing).

## Red-check triage and the drift advisory

Optional, with the `AI_GATEWAY_API_KEY` secret passed as `ai_gateway_api_key` (local mode: `docs/LOCAL.md`).

Red-check triage. When a required check is red, Factory asks a decision model (Vercel AI Gateway's decisions endpoint, `triage_model`, default `perplexity/pplx-decider-v1.2`) one question per failing CI job: did the change break it, or is it a flake or infrastructure? Only when every failing job reads flaky at confidence 0.7 or more does Factory rerun the failed jobs (with the job token's `actions: write`) and wait again, with no fix pass and no pass counted; anything else goes to the fix pass as before. A required job GitHub never started is never asked (the blocked exit, above). A failing job is never asked when its failure lines name a path, file name or test the PR changes (an intermittent defect the change brought passes on a rerun too), and a required job is left out of the questions only when it is structurally an aggregate (in the same workflow run as another failing job, started after it completed) and its own log has no failure line. Each job's verdict, confidence and failure signature (a hash of the sorted failure lines a runner, compiler or tool printed anywhere in the log and of the repository files they and their stack frames point at; a log with no failure line has no signature and matches nothing) go on the run's progress comment, with a hidden record of the heads and signatures rerun and of a refused rerun: one rerun per head, a signature already rerun once is never rerun again on that Objective, a refused rerun (not a rate limit) is not tried again on it, and a rerun that turns green is said on the progress comment. Each failing job's log window and the PR's file list are sent to the gateway. The same key turns on the drift advisory: while the worker's harness runs (the work, fix and answer passes), at most once every two minutes and only after 12 activity entries, Factory asks a decision model (`drift_model`, default `baseten/elephant-1`) whether the agent is `on_task`, in `scope_creep` or `looping`, from the plan's checklist items, its last 12 activity entries (commands, edits, sub-agents, messages, read from the harness's own event stream) and the repository files it has edited. A `scope_creep` or `looping` answer at confidence 0.7 or more writes one line on the progress comment and in the job log, at most once per harness run; every answer's label and confidence go to the job log. It is advice only: it never stops, pauses, blocks or redirects a run. Those inputs go to the gateway. Factory's own process makes the call; the key reaches no harness or command. Each triage line goes to the job log as well. Without a key, every red goes to the fix pass as before and no drift check runs, and the first red of each stage says `triage: off (<code>)` (local mode's key-file codes: LOCAL.md).

## Cost tiers and parallelism

The planner-high, worker-medium split survives one level down. The worker session runs on the strong model and does the planning, the integration and the PR; each checklist item goes to an implementer sub-agent on the cheaper model, pinned by the agent definition the job writes into the checkout (`.claude/agents/implementer.md` with `model: claude-sonnet-5-5`; `.codex/agents/implementer.toml` for Codex; Copilot's carries a model only when `subagent_model` is set) so the worker cannot drift up. Where the harness reports sub-agent usage (Claude does; Codex folds it in; Copilot reports none), the caps and the scorecard see it. The strong model stays in the loop for the whole Objective instead of handing a compiled brief to a weaker one and leaving.

Parallelism has two levels and the brief owns the inner one: implementers for items on disjoint files run at the same time, then one integration and one validation. The outer level is the dispatcher's `max_concurrent`. A worker that sees the whole Objective can tell which parts are independent without a graph review to say so.
