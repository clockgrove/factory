# Factory: design and contracts

Factory is a GitHub Action, a harness plugin and a bench, sharing one set of skills and a short task card. An adopter adds one workflow file, a GitHub App and a model credential, and labels an issue `factory:objective`; a worker builds it, a reviewer comments on it, and Factory merges it through the adopter's own required checks and merge queue. The human reads the Project board's Blocked column and, when they choose, the merged diffs. This page is the design as it is now; git holds its history.

## Design rules

- **No planner, compiler or Work Items.** The worker session plans in a comment on the issue and implements with pinned sub-agents. Reason: a stock harness given the brief merged the same Objectives without stops, where a separate planner added holds about Factory's own machinery.
- **Factory merges on its own** (`auto_merge`, on by default). The gate is CI on the reviewed head and on the integrated commit, the comment-only reviewer pass and the merge queue's own re-run; no human reads the diff first. Reason: taking the human out of the loop is the product. `auto_merge: false` gives ready-for-review PRs instead.
- **The only stops are Blocked and Question, and neither stops the queue.** Reason: with many Objectives in flight, every hold is multiplied by the queue.
- **GitHub is the only database, and the Action the only controller on every backend.** The install is the Action plus the App's two secrets; no server, database or vendor platform is ever required. Reason: nothing to host, and the state is where the adopter already looks.
- **Every stage runs behind three interfaces** (trigger, sandbox, gate: `plugin/scripts/lib/backend.mjs`), and every third-party service behind an adapter contract (`docs/ADAPTERS.md`). Reason: a new backend or vendor is one module, not a refactor.
- **Claude Code, Codex and Copilot are peers:** same task card, same skills, each with its own credential.
- **No knowledge loop.** Factory learns through skills people edit and a bench that scores each edit. A correction that repeats across adopters becomes a line in a Factory skill; one that repeats for one adopter goes in a skill in their repository.
- **Skills are capped and measured.** Each skill is at most a page (`bench/skills.mjs` enforces it) and versioned by hash in `bench/skills.json`, whose digest is on every scorecard row. A skill's text changes only with its instrument run: the reviewer replay set (`bench/review-replay.mjs`) for review-pr, the medium drill set (`bench/drill.mjs --set medium`) for the worker skills. Reason: one reasonable line at a time is how a rubric grows past usefulness.
- **No adopter has a code path.** Runner and toolchain are the `runs-on` and `setup` lines in the adopter's file; a need those cannot express is a Factory bug.
- **Factory never builds itself.** Objectives and drills run on scratch adopter repositories, never on this one; the `run` skill refuses it.
- **The App and the Project board are required.** The App is the only identity that both triggers the adopter's CI on Factory's PRs and gets a merge-queue run (below); the board is the dashboard.
- **Adopters take releases by exact tag**, on their own cadence (README, Versioning).

## Job one and how it is measured

Job one: file an Objective, walk away, and come back to correct, merged work at a reasonable cost. Factory is judged on four numbers per Objective, taken by the bench from the issue, the PR, the job log and the harness's usage output.

| Measure | Job-one part | Taken from |
| --- | --- | --- |
| Walk-away: merged with zero human input after the label | Operator walks away | Three buckets. Walk-away: merged with no human push, comment or edit on the branch or issue after the label. External: every stop was a Block outside Factory and outside the work (Factory's `max_usd` cap, the AI Gateway's budget or credits, a provider's quota, plan limit or billing: the model provider, GitHub's Git LFS storage or the sandbox vendor's plan; a provider or GitHub outage Factory handled by its rules), and the only human input answered those Blocks. Miss: anything else, a Blocked card of any other cause included. Each Block records its cause as a code (bench/README.md, Block causes), so the bucket is decided on structure. |
| Solution quality | Correct work | The bench's blind pairwise judge where there is a comparison; the owner's read of the merged diff when they choose to read it; escapes found after merge count against it. |
| Operator minutes | Operator walks away | Minutes spent on Blocked cards and on re-filing, from a stopwatch; zero on a clean merge. |
| Dollars per merged Objective | Reasonable cost | Per harness: Claude's headless output carries total\_cost\_usd and per-model usage with sub-agents included; Codex's JSONL carries the thread's running token counts (a resumed pass counts only its own share), priced from a table, with each sub-agent thread's own counts read from its rollout and priced at its model; Copilot bills GitHub AI Credits and its usage file reports them per run, so its column is those credits at GitHub's published $0.01 each (configurable), with the premium requests beside them. Runner minutes beside it. Wall time reported, never alone. |

The standing scorecard is one row per Objective, kept by the bench (`bench/score.mjs`, `/factory:score`).

## 0.9.x releases

Factory is at 0.9.x, the release candidate for 1.0, run on real work: its surface is expected to hold and its releases to be fixes underneath, with no stability promise until 1.0. Later 0.9.x releases are batched fixes that ship on CI and the review. 0.9.0 itself was tagged once one frozen candidate tag met this bar:

- **Five in a row per harness.** Claude Code, Codex and Copilot each merge five consecutive Objectives of the scratch medium set (`bench/drill.mjs --set medium`) as walk-aways.
- **Every route covered.** Together those runs cover the Actions, local and cloud-sandbox routes.

Counting rules:

- Any Factory change means a new candidate tag, and every count starts again. Reason: the bar proves one exact tag.
- An answer, un-block, hand-started run or re-run by anyone, an owner's agent session included, is operator input: that row is not a walk-away and the streak breaks.
- A P1 defect found later in a counted merge breaks the streak. The owner reads the counted diffs.
- An External Objective (Job one) is skipped: it neither counts toward the streak nor resets it. Reason: nothing Factory, the Objective or the repository's setup did could have avoided its stops.
- The streak is counted by `node bench/score.mjs --streak --repo OWNER/NAME --since <candidate tag>` (bench/README.md, The streak): a stall, an unmerged end or an input source the scorer could not read resets it too.

## The 1.0 bar

1.0.0 is tagged when five consecutive real Objectives merge with zero operator input, pooled across the real adopters:

- **Real adopters only:** `clockgrove/clockgrove`, `clockgrove/assetforge` and `clockgrove/raccoon-world` together, never the scratch drill repositories.
- **One pooled streak:** the Objectives of all three, ordered by when each ended, on any harness (Claude Code, Codex or Copilot). Any miss on any of them resets it.
- **It spans 0.9.x releases:** the streak counts from v0.9.0 and keeps counting when the adopters move to a later 0.9.x release; only a miss resets it.
- **The same counting rules as above:** any human input (an answer, un-block, hand-started run or re-run by anyone, an owner's agent session included), a Blocked card, a stall, an unmerged end, an input source the scorer could not read, or a P1 defect found later in a counted merge breaks the streak; an External Objective is skipped. The owner reads the counted diffs.

Counting it: `node bench/score.mjs --streak --since v0.9.0 --repo <adopter> --repo <adopter> --repo <adopter>` prints each adopter's streak per harness, then the pooled streak and the sequence it counted: every finished Objective of the three, ordered by when it ended, on any harness, each a walk-away (`yes`), skipped as External, or the miss that reset it. Five is the bar. An Objective in flight has not ended and does not count yet. A parked Objective (its label removed while it waits on other work) is still scored: it counts once it ends, and a Blocked one is a miss. `--out` writes the rows and both streaks (bench/README.md, The streak).

At 1.0 the surface README's Versioning section proposes (input names, labels, markers, the App's permission set, the template's jobs) freezes for 1.x.

What 0.9 claims beyond the candidate bar:

- The cloud-sandbox route runs a stage in one sandbox session of `timeout_minutes` plus about 16 minutes (up to 24 hours on Vercel Pro; a plan that caps sessions lower cuts the stage to the session granted, and it Blocks naming the cap if it outruns it), with Claude Code, Copilot and Codex (through the Vercel AI Gateway) proven.
- Local mode on macOS is sandbox verified, not run end to end.
- Dozens of Objectives in flight at once is the design target (Scale), not a 0.9 claim.

## Credentials and billing

Unattended runs bill API credentials by default (`credential: api`):

- **Claude:** workload identity federation (the job's OIDC token exchanged for a short-lived Anthropic credential, `id-token: write`) or `ANTHROPIC_API_KEY`.
- **Codex:** a Vercel AI Gateway key, `FACTORY_CODEX_GATEWAY_KEY` (the `codex_gateway_key` input), or `CODEX_API_KEY`; either passed only to the step that runs the harness, never a job-level variable. With both set the gateway key wins and `CODEX_API_KEY` stays out of the harness's environment and the cloud sandbox. The gateway key is its own secret: never `AI_GATEWAY_API_KEY`, which is Factory's own (triage and drift, `FACTORY_SECRET_KEYS`). Through the gateway Codex runs a `vercel` provider on the gateway's Codex endpoint (`lib/harness.mjs` `codexGatewayArgs`: `https://ai-gateway.vercel.sh/codex/v1`, the Responses wire API, the key from `FACTORY_CODEX_GATEWAY_KEY`), the model as `openai/<id>` on every pass, resumes included, and an `x-session-id` header that is one opaque id per Objective per Running stint (`gatewaySession`), so the gateway keeps the stint's passes on the provider credential that wrote the thread. Usage bills to the team's AI Gateway credits at the provider's list price, cache writes included (`cache_write_input_tokens`, priced at the model's write rate). A resume the provider refuses because the thread was written through another credential (HTTP 400 or no status, with `invalid_encrypted_content` or `organization_mismatch`, read from the error's structure) runs once as a fresh thread with the full card, where the pass has one to give (the exit-record ask has none, so there the refusal Blocks), and the log says so. A Codex model with no row in the price table runs unmetered: `max_usd` and `daily_usd` cannot stop it, only the key's own budget, and doctor and the progress comment say so. Doctor checks the key for free against the gateway's Codex model list with `--probe`.
- **Copilot:** `copilot_github_token`, a fine-grained token with only the Copilot Requests permission from a user with a Copilot seat, passed to the harness step only and billed to that seat; never the job's own token, which can write. Doctor fails without it.

The model's own commands never get a credential in their environment, on every route, but the worker secrets a repository opts in to (Worker secrets, below). Codex runs with `shell_environment_policy.exclude` and Copilot with `--secret-env-vars`, each naming every model, runner and Factory credential (`SHELL_SECRET_KEYS` in `lib/harness.mjs`; Copilot also masks their values in its JSON output). Claude Code runs every command in its own bubblewrap sandbox, which unsets the same names (`sandbox.credentials.envVars`, [sandboxing](https://code.claude.com/docs/en/sandboxing#protect-credentials)) and gives each command its own PID namespace, so no command reads another process's environment either. Codex and Copilot do the same on every route but a developer's own session: in local mode, on Actions and in a cloud sandbox, every command runs in its own sandbox, which keeps every process outside it from being read (below). Package installs never see one: in a cloud sandbox the start command runs apt, npm (their install scripts included) and the CLI's version check with only `HOME` and `PATH`, and only the stage gets the start environment (`launch.mjs` `START`). Reason: the model runs the repository's code and its dependencies, and a package's install scripts run too; none of them may read the key that bills the run or Factory's tokens.

Claude Code's sandbox on Actions and in a cloud sandbox VM holds local mode's bar (`lib/local.mjs` `claudeRunnerSettings`, `lib/harness.mjs` `claudeRunner`, `lib/claude-runner.mjs`), so every command's writes and network follow its lists there:
- **Writes:** the checkout, `$TMPDIR` (with `$FACTORY_IN` and `$FACTORY_OUT`), Claude Code's own command temp directory and the package caches in the agent's home (`.npm`, `.cache`, `.local/share/pnpm`, `.bun`, `.yarn`); nothing else in the agent's home, and never the checkout's git hooks, config and harness configuration. File edits stay in the checkout and `$TMPDIR` (`acceptEdits`, writes outside the working directories blocked).
- **Network:** GitHub (Git LFS's download host included) and the npm and Yarn registries (`LOCAL_DOMAINS`), plus the workflow's `allowed_domains` input, the counterpart of local mode's `FACTORY_LOCAL_DOMAINS`. A worker that stops because the sandbox denied a host names it (`deniedHosts`), and the Blocked comment names the fix. A worker secret's provider (an API host the pipeline calls with it) needs its host there too; an AI Gateway key goes through the gateway relay (Worker secrets), which needs none.
- **Nothing the agent can write is read or run by Claude Code's own start-up:** the repository's install and validation run as the agent outside Claude's sandbox, so they could write anything in the agent's home and the checkout's `.git`. So Claude Code runs with a HOME Factory owns (`/var/lib/factory-claude`: no shell start-up file, no git config, only an env file and Factory's skills and agents, which the agent reads and never writes) and a PATH with nothing of the agent's home; its shell snapshot (`bash -c -l`) therefore sources no file of the agent's. Its own `TMPDIR` is `/tmp`, which its unit (or `NAMESPACE_WRAP`) mounts afresh for every start; a directory in the agent's home would sit outside its working directories, where its sandbox cannot read it, and its commands would lose all network (#61). Its config directory is made afresh before every start, with only the session Factory captured right after the previous run put back (so a resume and the saved transcript use Factory's copy). The checkout's `.git` config, commondir, info/attributes and hooks are put back to what Factory left before the repository's install ran, and a replaced `.git` refuses the start. Its commands get the agent's own HOME and TMPDIR back inside the sandbox (`CLAUDE_ENV_FILE`), so caches and the agent's read-only `gh` login work as before. It starts with Factory's flag settings only (`--setting-sources ""`, hooks off, `--strict-mcp-config`) and its own git with no fsmonitor, and the checkout's harness settings are restored to the commit before every start (`lib/local.mjs` `clearHarnessConfig`): a hook or MCP server would run outside the sandbox as the same uid as Claude Code, which can read its process's environment.
- **What the routes change for it:** on GitHub's hosted runners the Action installs bubblewrap, socat and ripgrep and loads an AppArmor profile that lets `/usr/bin/bwrap` alone make user namespaces (not the global sysctl), unloading Ubuntu 26.04's `bwrap-userns-restrict` profile, which takes the capabilities the sandbox needs. It changes nothing on a self-hosted runner, where both would outlast the job and change the whole host: doctor fails until bwrap, socat and rg are installed and, where AppArmor restricts user namespaces, names the one-time admin step (the same profile, and `bwrap-userns-restrict` unloaded and disabled). A cloud sandbox's start and its image build install the packages; its VM has no AppArmor. Claude Code refuses to start where its sandbox cannot (`failIfUnavailable`): no command ever runs unsandboxed.
- **The services setup started are reachable at their usual ports, and nothing else on the machine is:** on Linux a sandboxed command's `localhost` is its own network namespace. Factory notes the TCP ports listening on IPv4 loopback or every address (IPv4-mapped forms included) before the repository's `setup` runs, and before each Claude start offers the ones that appeared since, never a socket the agent uid owns (at most 20; the log names any the cap drops): each `127.0.0.1:<port>` joins the sandbox's allowed hosts, and the env file Claude Code sources inside the sandbox before every command starts a relay on the command's own `127.0.0.1` and `::1` at that port, through the sandbox's proxy (HTTP CONNECT with its per-session login), so `localhost:5432` in `DATABASE_URL` reaches the database setup started. The task card names the ports offered, and says nothing about services when none are. Nothing outside the sandbox runs anything for it: the relay (`socat`) runs inside, and Claude Code's proxy only connects to the allowed `127.0.0.1` ports. A service that was already listening before setup, one listening on another address, or `::1` only, stays out of reach; a command that needs one of those ports for a server of its own finds it taken. Setup's loopback services are trusted: one that offers code execution (`node --inspect`, a Docker TCP API, a database with `COPY ... PROGRAM`) is a path out of the sandbox to the credential-holding uid, the same exposure the validation commands already have. (`excludedCommands` was no option: it would run the command outside the sandbox, credential included.)
- **Trade-off:** Claude Code's systemd unit on the runner runs without `ProtectKernelTunables` (`lib/claude-runner.mjs` `asClaudeAgent`): its read-only mounts over parts of `/proc` keep a user namespace from mounting a fresh `/proc`, so bubblewrap cannot start under it. The agent stays unprivileged, with no new privileges and no capabilities, so `/proc/sys` and `/sys` stay root's to write. Copilot's unit runs without it too (below); every other command the agent runs keeps the setting. `NAMESPACE_WRAP` in a cloud sandbox needs no change.
- **Why not `CLAUDE_CODE_SUBPROCESS_ENV_SCRUB`:** in Claude Code 2.1.322 it also forces the default permission mode and makes the working directory's `package.json`, lockfiles, `.npmrc` and `.env*` read-only to commands (so `npm install <package>` fails with EROFS) and leaves empty placeholders for the absent ones in the checkout. None of that is documented or can be turned off, and it would stop a worker changing dependencies. An `apiKeyHelper` is no option either: Claude Code runs it as the model's own uid and again every five minutes by default ([settings](https://code.claude.com/docs/en/settings-reference#apikeyhelper)), so whatever it reads, the model's commands can read.

Codex's sandbox on Actions and in a cloud sandbox VM holds the same bar (#90): local mode's profile fitted to the agent (`lib/codex-runner.mjs` `codexRunnerConfig`, `lib/harness.mjs` `codexRunner`, `lib/local.mjs` `codexLocalConfig`), in place of `--dangerously-bypass-approvals-and-sandbox`. Reason: the agent uid holds the credential in Codex's environment, and Codex starts git with its whole environment, so a command outside a sandbox read it from `/proc` (#87). No command can read the environment of a process outside Codex's sandbox, and `shell_environment_policy.exclude` still keeps every credential name out of its own. The mechanism: Codex's sandbox (bubblewrap and seccomp) runs each command in a user namespace of its own without `CAP_SYS_PTRACE`, so the kernel refuses its read of another process's environment (`cap_ptrace_access_check`), Codex's and its git processes' included. In the cloud sandbox VM bubblewrap also mounts a fresh `/proc` in a PID namespace of the command's own, so it sees only the sandbox's processes. Under the systemd unit on Actions (`ProtectKernelTunables`) it cannot, and Codex silently retries without one: `/proc` then lists the machine's processes, the reads are still refused (checked with fake credentials: 0 of 178 readable, and 0 hits from a reader racing Codex's git processes), and the host's world-readable `/proc` entries (`cmdline`, `status`, `net`) stay visible, a low exposure: other processes' command lines and the machine's sockets, never an environment. Codex 0.167 does not make its own process unreadable (non-dumpable), so the refusal is the sandbox's, which the probe below checks with a decoy before every start. The runner's profile does not also deny `/proc`, as local mode's does: under the systemd unit that deny takes `/dev/fd` with it, which broke bash's process substitution (Factory's own pre-commit hook uses it) and `/dev/stdin` in Codex's commands. Behaviour that changes for Codex adopters:
- **Writes:** the checkout (its `.git` too, for commits), `$TMPDIR` (with `$FACTORY_IN` and `$FACTORY_OUT`) and the package caches in the agent's home (`.npm`, `.cache`, `.local/share/pnpm`, `.bun`, `.yarn`); nothing else in the agent's home, and never the checkout's git hooks, config, commondir, info/attributes or harness configuration. Reads stay open, `/proc` included (local mode denies it). The sandbox's writable directories must be real: before every start a link at the temp directory or a package cache (one the repository's install or validation planted) is replaced by a directory, and one that cannot be (a link higher up its path) refuses the start (`roots`, naming the path under the home), as for Claude Code. Each is compared with where it sits under the agent's home as the system resolves it, so a home under a linked ancestor (`/home -> /var/home`) is no refusal.
- **Network:** through Codex's proxy, `LOCAL_DOMAINS` plus the workflow's `allowed_domains` input, as for Claude Code, and the Vercel AI Gateway's host (`ai-gateway.vercel.sh`) when it is Codex's provider (`codex_gateway_key`). A denied host is named in the worker's `deniedHosts`, and the Blocked comment names the `allowed_domains` fix.
- **The services setup started are out of its commands' reach:** a command's `localhost` is its sandbox's own network namespace, and Codex has no hook that could start a relay inside it as Claude Code's env file does. The task card says so and leaves those commands to Factory's validation, which runs after the worker exits and hands a failure back with its output.
- **Nothing the agent can write is read or run by Codex's own start-up:** Codex runs with a HOME Factory owns (`/var/lib/factory-codex`, empty, read-only to the agent), so its shell snapshot (`bash -lc`, run with the credential in its environment) sources no file of the agent's, a PATH with nothing of the agent's home, and its own `TMPDIR` (`/tmp`, private to each start). Its `CODEX_HOME` (`~/.factory-codex/home`) is made afresh and empty before every start, with only the sessions Factory captured right after each run put back, and `--ignore-user-config` besides, so no planted `config.toml` (a `notify` hook, an MCP server) loads. The checkout's `.git` config, commondir, info/attributes and hooks are put back as Factory pinned them before every start (a replaced `.git` refuses it), its harness configuration is restored to the commit, the project is never trusted, and Codex's own git runs no fsmonitor. Its commands get the agent's HOME and TMPDIR back (`shell_environment_policy.set`), so caches and the agent's read-only `gh` login work as before.
- **What the routes change for it:** on GitHub's hosted runners the Action installs bubblewrap and loads the same AppArmor profile as for Claude Code (Codex's sandbox uses `/usr/bin/bwrap`; without the profile it fails with `RTM_NEWADDR`). A self-hosted runner needs the same one-time admin step, and doctor names it. A cloud sandbox's start installs bubblewrap. Codex's unit keeps `ProtectKernelTunables` (its sandbox starts under it, checked on both launchers). Before every start Factory runs a confinement probe in Codex's sandbox as the agent, with the run's own profile (`codex sandbox ... -- sh -c <probe>`): Codex's process and a decoy beside it outside the sandbox (a plain `sleep` of the agent's uid, which nothing but the sandbox stops a command reading) hold a random marker in their environment, as a run's Codex and its git processes hold the credential, and no environment the probe can read under `/proc` may show it, the decoy's above all (so a Codex release that only made its own process unreadable while loosening the sandbox fails); the agent's home and the checkout's `.git/config` must refuse a write, the temp directory must take one, and a host off the allow-list must be refused. Where the sandbox starts and does not confine (a Codex release that changed what its profile means, since the Action installs the version the workflow names), the stage Blocks with the rule before any command runs; where it does not start, it is tried once more, and a second failure Blocks. The probe runs `codex sandbox` and the run `codex exec`: the same profile and the same sandbox code, but a different entry point, so a release that sandboxed the two differently would pass the probe; Factory does not pin Codex's version, and the decoy probe is the guard; a link to nothing at one of the checkout's protected paths Blocks naming it. Codex itself would only fail each command. Doctor runs the same probe in the job (`codex sandbox: bwrap`, `codex sandbox: start`), and `doctor --probe` runs Codex in the run's own sandbox where the agent exists.
- **A developer's own session** (`/factory:run --here`, no agent uid, no local sandbox) keeps the CLI's own permissions skip; the routes that run unattended all sandbox Codex's commands.

Copilot's sandbox on Actions and in a cloud sandbox VM holds the same bar (#87): `copilot --sandbox` (MXC's bubblewrap backend) under local mode's policy fitted to the agent (`lib/copilot-runner.mjs` `copilotRunnerSettings`, `lib/harness.mjs` `copilotRunner`, `lib/local.mjs` `copilotLocalSettings`), in place of `--allow-all`. Reason: as for Codex, the agent uid holds the token in Copilot's environment, and Copilot starts git with its whole environment after every tool call, so a command outside a sandbox read it from `/proc` (#87). Each command runs in a user namespace, a PID namespace with a fresh `/proc`, and a network namespace whose only way out is Copilot's proxy (slirp4netns, with Copilot's iptables rules), so it sees no process outside its sandbox: not Copilot, not its git processes. `--secret-env-vars` still keeps every credential name out of the command's own environment. Copilot 1.0.109's sandbox misses three things, which Factory adds (`lib/copilot-runner.mjs`):
- **The token in the sandbox's pid 1.** Copilot starts bubblewrap with its whole environment, the token included, and bubblewrap stays in each command's sandbox as its pid 1, so every command could read the token from `/proc/1/environ` (checked with fake credentials on both launchers, in a cloud sandbox and on WSL2). Factory's own `bwrap` (`bwrapShim`), first on Copilot's PATH, starts the real one with an empty environment; bubblewrap sets each command's environment itself (`--clearenv`, `--setenv`), so nothing else changes.
- **Its commands' HOME and TMPDIR.** Copilot gives its commands its own. The same shim gives them the agent's, so package caches, the agent's read-only `gh` login and `$FACTORY_IN` and `$FACTORY_OUT` work as before.
- **Its own TMPDIR, out of its commands' reach.** Copilot binds the TMPDIR it starts with into every command's sandbox, and writes each command's iptables rules there (`mxc-bwrap-proxy-*/rules.v4.000`) before it loads them into that command's network namespace. So with `/tmp` as its TMPDIR, a background command could rewrite the next command's rules and open its network to every host (found in review). Copilot's TMPDIR is `/tmp/factory-copilot` (`COPILOT_TMP`), made by its launch in the `/tmp` private to each start and denied to commands in its policy.

Behaviour that changes for Copilot adopters:
- **Writes:** the checkout (its `.git` too, for commits), `$TMPDIR` and the package caches in the agent's home (`.npm`, `.cache`, `.local/share/pnpm`, `.bun`, `.yarn`); never the checkout's git hooks, config, commondir, info or harness configuration. A write anywhere else lands in the sandbox's own throwaway root and is gone when the command ends. The writable directories must be real, as for Codex (`roots`).
- **Reads:** the system's directories (Copilot binds `/usr/bin`, `/usr/lib`, `/etc` and their like itself, nothing more), the stage's toolchain (each directory on the PATH Copilot gets that its sandbox does not bind, as its install prefix for a `bin` directory: Actions' `/opt/hostedtoolcache/node/<version>/x64`, `/usr/local`; read-only; only those the agent can reach and cannot change: neither the directory nor any above it, by its path or its real path, is the agent's or writable by it (bubblewrap binds by path at each command's start, so one the agent could swap for a link would bind whatever the link names); never in or above the agent's home, Factory's HOME for Copilot, its TMPDIR, Factory's own HOME, temp, workspace and usage directories, `/proc`, `/sys`, `/dev` or `/run`; `lib/copilot-runner.mjs` `toolchainDirs`, `TOOLCHAIN_CHECK`, #105), the checkout, `$TMPDIR`, the caches and the agent's read-only GitHub login (`~/.gitconfig`, `~/.config/gh`, `~/.factory`); nothing else of the agent's home, and not Copilot's TMPDIR. Copilot binds its logs directory into every command's sandbox whatever its policy says, so it runs with `--log-level none` and the directory stays empty. Each command gets a fresh, empty `/tmp` of its own; `$TMPDIR` is what carries files from one command to the next.
- **Network:** through Copilot's proxy, `LOCAL_DOMAINS` plus the workflow's `allowed_domains` input; a direct connection to an address is refused. A denied host is named in the worker's `deniedHosts`, and the Blocked comment names the `allowed_domains` fix.
- **The services setup started are out of its commands' reach,** as for Codex: the task card says so and leaves those commands to Factory's validation.
- **Nothing the agent can write is read or run by Copilot's own start-up:** Copilot runs with a HOME Factory owns (`/var/lib/factory-copilot`, read-only to the agent), holding the shim and the release Copilot's binary unpacks and runs (`COPILOT_CACHE_HOME`, unpacked by Factory before the agent starts; until now it was unpacked into the agent's `~/.cache`, where the repository's code could replace it), a PATH with nothing of the agent's home, and its own TMPDIR (`/tmp/factory-copilot`, above), in the `/tmp` private to each start. It runs with `--no-auto-update`, so it never fetches a release Factory did not unpack. Its `COPILOT_HOME` (`~/.factory-copilot/home`) is made afresh before every start with Factory's settings (its sandbox's policy, no trusted folder, no MCP server), and only the sessions Factory captured right after each run put back. The harness configuration of the agent's temp directory, an added directory whose `.github` agents and skills Copilot loads, is removed. The checkout's `.git` config, commondir, info/attributes and hooks are put back as Factory pinned them before every start (a replaced `.git` refuses it), its harness configuration is restored to the commit, the folder is never trusted, and Copilot's own git runs no fsmonitor. File tools stay in the checkout and `$TMPDIR` (no `--allow-all-paths`), and refuse a link that points outside them.
- **What the routes change for it:** on GitHub's hosted runners the Action installs bubblewrap and slirp4netns and loads an AppArmor profile, factory-unshare, that lets `/usr/bin/unshare` alone make user namespaces: Copilot makes its sandbox's namespaces with util-linux `unshare` and bubblewrap joins them, so unshare's is the grant it needs (the factory-bwrap profile is not loaded for Copilot). Ubuntu's `bwrap-userns-restrict` and, from 25.04, `unshare-userns-restrict` profiles are unloaded where loaded. A self-hosted runner needs the same once, and doctor names it (`copilot sandbox: apparmor` fails while factory-unshare is missing under the restriction, or either restricting profile is loaded). Copilot's systemd unit runs without `ProtectKernelTunables`, as Claude Code's does (bubblewrap mounts a fresh `/proc`). A cloud sandbox's start installs bubblewrap, slirp4netns, iptables and iproute2, and changes three things in the VM, which is the Objective's own: `/dev/net/tun` becomes usable by every user (the VM's is root's alone, the usual mode elsewhere); where the VM's nf_tables cannot add an IPv6 table (Vercel's kernel has no IPv6 family) `ip6tables` becomes the legacy backend; and its lock, `/run/xtables.lock`, is made (root's). Over it `NAMESPACE_WRAP` binds a private lock the agent can take, from the `/run/lock` private to each launch: Copilot loads its rules into network namespaces of its own, so nothing on the host needs to share that lock.
- **The probe before every start.** Copilot has no command that runs one command in its sandbox (Codex has `codex sandbox`), so the probe is a Copilot session started as the run's is (its flags, HOME, PATH and unit, with the run's settings in a COPILOT_HOME of its own) against a model Factory serves on the machine's loopback (Copilot's offline provider mode: no network, no bill), which asks for one shell call. That call runs the confinement probe beside a decoy, as for Codex: Copilot and the decoy hold a random marker, which no environment the probe can read may show (bubblewrap's pid 1 would, without the shim), nor the first process's command line; Copilot's TMPDIR must be neither listed (no `mxc-bwrap-proxy-*`, there or in `/tmp`) nor writable, and its logs hold nothing a command can read; a file it tries to make in the agent's home, the probe's COPILOT_HOME, Factory's HOME for Copilot or its release must not be there afterwards; the checkout's `.git/config` must refuse a write, `$TMPDIR` take one, and a host off the allow-list be refused; and the stage's `node` (the first on the stage's PATH) must be the one a command finds, and it and the `npm` beside it must run there, so a toolchain the sandbox does not give its commands Blocks before the run (`the stage's toolchain does not run in a command`) instead of leaving the worker unable to run the repository's validation. A pass is exit 0 with the probe's own last line, and a missing probe script or decoy is a broken rule, so an empty one cannot pass unchecked. A broken rule Blocks with the rule before any command runs; a probe that left no result (the sandbox did not start) is tried once more, then Blocks. It takes a few seconds. Residual risk: the probe runs offline, so managed settings or experiment flags Copilot receives only online are not what it checks; the run's own policy is Factory's settings file either way. Doctor runs the same probe in the job (`copilot sandbox: bwrap`, `slirp4netns`, `apparmor` on a self-hosted runner, `start`).
- **Sessions:** Copilot's commands can write its session's `files/` directory, which Factory captures after each run; the capture is bounded (two minutes, 512 MB, the archive stopped past that), so a file that never ends cannot hold the stage, and such a session is not captured.
- **A developer's own session** (`/factory:run --here`, no agent uid, no local sandbox) keeps `--allow-all`; the routes that run unattended all sandbox Copilot's commands.

### Worker secrets

Off by default. A repository whose Objectives run a paid pipeline (image or 3D generation through an AI gateway) may give the worker's shell secrets of its own: `worker_secrets` (`FACTORY_WORKER_SECRETS` in the workflow's env block, which local mode reads too) names them, each `NAME` or `NAME=SOURCE`, and the shell gets SOURCE's value as NAME. On Actions and in a cloud sandbox the values come from the `worker_secret_values` input, `SOURCE=value` lines that the template passes from the one repository secret `FACTORY_WORKER_SECRET_VALUES` in the work, review and launch jobs (so a re-render of the workflow keeps it); in local mode from the shell that runs `factory serve` (`docs/LOCAL.md`). For example `FACTORY_WORKER_SECRETS: AI_GATEWAY_API_KEY=WORKER_AI_GATEWAY_API_KEY`, with `WORKER_AI_GATEWAY_API_KEY=<a dedicated key>` in that secret, gives a pipeline that reads `AI_GATEWAY_API_KEY` the adopter's own key, through the gateway relay (below), which meters it against the Objective's caps.

- **The risk:** any code the worker runs, the repository's and its dependencies' included, can read the key and spend through it, and the worker can print it into a file or a commit. Use a dedicated key with a budget the gateway enforces (a Vercel AI Gateway key's spend limit), never a key shared with anything else, and rotate it if a run looks wrong.
- **Never Factory's own key or credentials:** a name that is a model credential, one of Factory's or the runner's tokens (`MODEL_SECRET_KEYS`, `RUNNER_SECRET_KEYS`, `GITHUB_TOKEN_KEYS`), a name Factory, the runner or a harness reads (`FACTORY_`, `GITHUB_`, `GH_`, `ACTIONS_`, `RUNNER_`, `ANTHROPIC_`, `CLAUDE_`, `CODEX_`, `OPENAI_`, `COPILOT_`), or one that changes how commands run (`PATH`, `NODE_OPTIONS`, `LD_*`, `GIT_*`, proxies) is refused, and so is Factory's own `AI_GATEWAY_API_KEY` as a SOURCE: Factory's drift and triage key keeps its name and stays in Factory's process. A worker value equal to Factory's key is withheld (compared in constant time in Factory's process, never printed), and doctor warns about it, about each refused entry and about each SOURCE with no value (`lib/worker-secrets.mjs`, `doctor.mjs` `workerSecretChecks`).
- **Only the worker's shell:** the work lineage's harness runs get them: the work stage's (the work, conflict, fix and exit-record passes) and the review stage's fix and answer passes (with their scope and exit-record turns), which continue the worker's session, on every route and harness. They are carried to the harness process alone and removed from every other process's environment (`scrubbedEnv`): the repository's setup, install and validation and Factory's own git never see them. The reviewer never does: its calls are marked as the reviewer's, and `runHarness` gives such a call no worker secret and no variable holding an opted-in value, whatever environment it is handed (`lib/worker-secrets.mjs` `harnessShell`). The review stage's process holds the values while it runs, as the work stage's does, under the same redaction and push scan. In the model's commands an opted-in name is left out of the lists that hide credentials (Claude Code's `sandbox.credentials.envVars`, Codex's `shell_environment_policy.exclude`, Copilot's `--secret-env-vars`); the model's credential stays on every list. Local mode leaves a NAME or SOURCE that `FACTORY_LOCAL_ENV` also names out of every stage's environment.
- **Never posted, stored or pushed by Factory:** Factory's process holds every opted-in value of eight characters or more (a shorter one would mask ordinary text, so it is not protected, and doctor warns about it by name) and redacts each one, in every form a text can carry it (itself, JSON-escaped, URL-encoded with upper- or lower-case hex, base64 at each byte offset), from every GitHub request body (the Blocked reason and its last output, questions, the plan, the PR body, replies, notes, the progress comment), the usage record, the drift advisory's input and its own log. The job log masks them (`::add-mask::`), and the uploaded harness stream and transcript are masked in the same forms. A `missingSecrets` entry equal to a value is dropped. A push whose commits (a change or a message) carry a value is refused before anything is sent, and the stage Blocks with Factory's own reason, which never quotes it. A mis-pasted key is never printed: names with a known key prefix (`vck_`, `ghp_`, `github_pat_`, `sk-`, `xox…`, and the like) are refused, the log and doctor name a NAME only, and never quote an entry over 40 characters.
- **A missing key Blocks with the opt-in named:** a worker that stops because its shell lacks a secret lists the variable names in its exit record's `missingSecrets` (names only; at most ten), and the Blocked comment names the fix: opt it in with `worker_secrets` and where its value goes on that route, or that it is opted in but had no value. A name no worker may have gets no such fix.

#### The gateway relay

An opted-in AI Gateway key (the NAME `AI_GATEWAY_API_KEY`) is never handed to the sandbox. Factory's stage process holds it and runs a metering relay for the stage (`lib/gateway-relay.mjs`, `lib/worker-relay.mjs`). A worker secret under any other name whose value has a gateway key's shape (`vck_…`), or `AI_GATEWAY_API_KEY` in another case, is withheld, and doctor warns: a gateway key is only ever relayed.

- **What the worker's shell gets:** `AI_GATEWAY_API_KEY` holds a per-stage relay token, not the key. `FACTORY_GATEWAY_URL` holds the relay's address (`http://127.0.0.1:<port>`). The AI SDK reads no base-URL variable, so a pipeline sets it itself: `createGateway({ apiKey: process.env.AI_GATEWAY_API_KEY, baseURL: process.env.FACTORY_GATEWAY_URL ? `${process.env.FACTORY_GATEWAY_URL}/v4/ai` : undefined })` (`/v4/ai` is `@ai-sdk/gateway`'s own default path). An OpenAI- or Anthropic-compatible client takes `${FACTORY_GATEWAY_URL}/v1`.
- **What it forwards:** only the gateway's generation calls (POST `/v<n>/ai/{language,image,embedding,decision,reranking}-model`, and the OpenAI- and Anthropic-compatible `/v1/chat/completions`, `/v1/responses`, `/v1/embeddings`, `/v1/messages`, `/v1/images/generations`, `/v1/images/edits`) and its model list (GET `/v1/models`, `/v<n>/ai/config`), only to `https://ai-gateway.vercel.sh`, with the key in place of the token. Every other path or method (`/v1/credits`, `/v1/generation`, a query string, a method override) is refused (403), as is a call without the run's token (401). Only an allowlist of request and response headers passes, and the key is cut out of every response in each form a text can carry it. An image edit's body (multipart form data with its reference images, as the AI SDK's OpenAI provider or `fetch` with `FormData` sends it, or JSON with data URLs) passes as sent, its content-type and boundary untouched, up to 128 MB (base64 reference photos add up: a four-photo turnaround is 38.5 MiB); the other calls take up to 64 MB. A body over its cap is refused (413), before it waits its turn when its declared length shows it. A body is read whole before anything is sent and must arrive within 5 minutes of being read; a call waiting its turn under a cap has no deadline while it waits.
- **Every call is priced from what the caller cannot write:** the gateway's own `providerMetadata.gateway.cost` (a string such as `"0.007"`) at the top level of an AI SDK answer, or on a stream's `finish` event, and the generation's cost looked up with the same key (`/v1/generation`) by the answer's top-level `generationId` or a stream's `x-generation-id` header; the larger counts. A reported cost is booked at once and the lookup reconciles it aside, since the gateway records a generation some seconds after the answer (retried for about a minute; a record that never comes leaves the reported cost standing). An image edit's answer is priced the same way from the gateway's `providerMetadata.gateway` at its top level when it adds one, and otherwise as an OpenAI- or Anthropic-compatible answer, which waits for the lookup by its top-level generation id or the `x-generation-id` header, as does one that reports no cost; an answer with neither fails closed (below). A request body the gateway echoes back (a tool's schema, a tool call's input) is never read. The gateway's refusals before any model ran (400, 401, 403, 404, 413, 422, 429) are not billed; the 402, 4xx and 5xx cases below cost $0 too.
- **The gateway's own budget or credits refusal is $0 and named:** a 402 whose body carries the gateway's error type for a spent budget (`quota_for_entity_exceeded`: a team, project, key or user budget) or no credits (`insufficient_funds`), at `error.type` or at the top level, is a refusal before any model ran, so it costs a known $0. The worker gets the gateway's answer as it came, the key cut. Every later billable call in the stage gets 402 at once, with the gateway's type, its message and `source: "ai-gateway"`, never sent. The pass is not over budget for it: the worker decides how to finish. If the stage Blocks, its reason and the progress line name the refusal first (`AI Gateway refused: quota_for_entity_exceeded (Team budget exceeded…)`, the message on one line, clipped, the key cut), and `result.json`'s `workerKey.gatewayRefused` records its type and message. Any other 402 is priced as any failed call (below). Factory's own cap refusal is a 402 of type `factory_max_usd` whose message says it is Factory's cap, not the gateway's budget.
- **A failed call is priced where it can be, never as $0:** once a call is sent it is billed whatever the client does, so it runs to its end (with 20 minutes for the whole call) and is priced then, never aborted on a hang-up. Each call has a connection of its own whose socket probes the gateway once a minute (TCP keepalive): Node's own agent probes every second, and Vercel's edge stops answering after about 27 probes in a silent stretch, which ended a call still being worked on with ETIMEDOUT about 38 s in. Any other 4xx whose `error.type` says the gateway refused it before any model ran (`authentication_error`, `invalid_request_error`, `rate_limit_exceeded`, `model_not_found`, `not_found`, `forbidden`, `customer_verification_required`; never its status alone, never a type elsewhere in the body) costs $0. A 5xx whose `error.type` says no generation ran (`service_unavailable_error`, `overloaded_error`, `rate_limit_exceeded`, `rate_limit_error`) and that names no generation costs $0 too (`unavailable` in the call log), and is no unknown cost toward the shutdown below; any other 5xx (`internal_server_error`, `failed_dependency`, an unknown or missing type) is priced as below. Any other failed call that names its generation (the error body's top-level `generationId` or `id`, or the `x-generation-id` header, also on a broken stream) is priced by the `/v1/generation` lookup.
- **A complete answer that cannot be priced shuts the gateway:** a whole 2xx answer that names no cost and no generation, whose generation has no record, or too large to read its cost depends on the route and the request's shape, which the caller chooses, so it never gets an estimate: the gateway shuts for the stage at once, as below, and the Block names it (`gateway relay shut: a complete answer could not be priced (<why>)`).
- **A failure of unknown cost (Kirk's decision, #142):** a call that failed after it was sent, which no caller can cause (a network error, a broken or truncated answer, a timeout, an error status without a pre-model type) and that no source prices, is booked at an upper bound against `max_usd`: the larger of the dearest call priced so far in the stage and $0.25. The stage's dollars are marked `usdUpperBound`, the stage log says so, and relaying goes on. The estimate counts toward the live cap like any spend, so a pass near the cap can still get a 402. A second such call in the same stage shuts the gateway for the stage: the pass ends over budget, so the stage Blocks there, the dollars are also marked a lower bound, and the relay refuses every later call, the model list included. The Block reason and the progress line name it first (`gateway relay shut: 2 calls in this stage could not be priced (<why>); Factory's max_usd was not reached`); only an actual `max_usd` overrun reads "dollar cap reached". Nothing has to persist across stages: the Block stops the Objective until a person re-applies it.
- **The call log:** each call the relay answers is one JSON line in the stage's usage directory (`relay-calls.jsonl`, which no sandbox writes, mode 600): its time, method, relayed path, model (the allowlisted model header, else a JSON body's or a form's `model`, kept only with a model id's shape: `provider/name`, at most 80 characters), status, the dollars booked and how (`reported`, `lookup`, `refused`, `unavailable`, `gateway-refused`, `estimate`, `shut`), its generation id, why it was not priced, or why the relay refused it (a route it does not relay is `refused: route`, never the path asked for). Never a body, a header's value, a message or the key, and the stage's held secrets are masked in it when the stage ends, as in `events.jsonl`. At most 2,000 lines; one closing line counts the calls past them. A later lookup that raises a reported cost adds a line of its own. `result.json`'s `workerKey` summarises it: the estimate (`estimated`, `estimatedUsd`), the shutdown (`shut`: calls, why, and `complete` for a complete answer) and `callLog` (the file, its line count and any calls left out).
- **The cap is live and shared with the harness:** calls are relayed only while a pass runs. With a cap, billable calls go one at a time (at most 8 wait their turn, more get 429; a pass's end refuses those still waiting), each only once the one before it is priced, and only while the pass's spend through the key plus the harness's own spend in the pass so far is under what `max_usd` left when the pass started; past it the relay answers 402 with a message the worker sees, and the pass counts as over budget, so the stage stops or Blocks as when the harness reaches its own cap. Model spend plus key spend can pass the cap by about one call. The harness's own spend is read live (`lib/live-spend.mjs`): Claude Code's per-message usage from its stream, priced from `lib/claude-prices.json` (an unlisted model at the dearest row); Codex's newest thread rollout (its `token_usage_record` lines, one per model response) and its turns, priced from the Codex table (an unset or unlisted model at its dearest rates), sub-agent threads once the pass ends; Copilot's usage checkpoints (its running AI credits). A live figure that cannot be read refuses the call (503) rather than count as $0. A parallel pipeline is serialised while a cap is on: N concurrent calls take about N times one call's time.
- **How commands reach it:** the relay listens on a Unix socket in a directory the agent cannot write (a directory of the stage's own under `/var/lib/factory-relay` on a runner and in a cloud sandbox, the socket group-readable by the agent at 660, removed when the stage ends; the stage's usage directory locally, 600). Claude Code's and Codex's sandboxes start every command with the `bwrap` first on PATH. Factory puts its shim there (`lib/relay-shim.mjs`, `bash -p`, builtins only), which starts a forwarder on the command's own network namespace's `127.0.0.1:<port>` to the socket before the command runs; it walks bubblewrap's options by their arity, so only `--unshare-net` before the command's separator marks a command sandbox. The harness's network policy, proxy and seccomp filter are unchanged; the forwarder carries one port to the relay alone, and the commands themselves cannot open the socket (both harnesses' filters refuse Unix sockets). Copilot's own bwrap shim (`lib/copilot-runner.mjs` `bwrapShim`, already first on its PATH) hands each call to the relay's shim for Copilot, at a path in the stage's own relay directory written into Copilot's shim for the stage (on a runner and in a cloud sandbox once the relay opens, locally by `serve`), never read from an environment; concurrent stages on one host each hand to their own, and a Copilot stage removes the one shared path an earlier Factory used. For a Copilot command sandbox that shim also binds the socket's directory read-only and sets `NO_PROXY`/`no_proxy` to `127.0.0.1`, so loopback stays off Copilot's proxy and reaches the namespace's own forwarder. `allowLocalNetwork` stays false and Copilot's host allow-list is unchanged. Copilot's filter lets commands open a Unix socket, so a Copilot command can reach the relay's socket directly too: it is the same relay behind the same token check. The worker needs no egress to the gateway's host. Locally the outer sandbox keeps the relay's directory readable, never writable.
- **Probes and fail-closed starts:** before a stage's first relayed Codex pass, Codex's own sandbox (`codex sandbox`, the run's profile, the shim on PATH) must reach the relay's ping, or the stage Blocks (`relay`) before the run. Copilot's probe before every start (Copilot's sandbox, above) gets a rule of its own: a command in Copilot's sandbox reaches this relay's ping through the forwarder, or the stage Blocks (`relay`). Each command sandbox's forwarder pings the relay when it comes up, and a pass whose commands ran with no ping is logged. On a machine without `bwrap` or `socat` the stage Blocks before any run, with the key out of the shell. Factory never falls back to handing the key over.
- **Other opted-in secrets** keep the behaviour above: they reach the worker's shell as they are, and rely on their provider's own cap.

#### The worker's state directory

`FACTORY_STATE_DIR` names a directory outside the checkout for the worker's own state: `factory-state` in the temp directory its commands share, which every sandbox lets them write and which lasts the stage. A pipeline may keep a ledger there, but such a ledger is advisory. The model can write it too, and Factory's own count above is what caps spend.

`credential: plan` with `CLAUDE_CODE_OAUTH_TOKEN` is allowed on a developer's own repository only; doctor warns that plan limits assume ordinary individual use. `credential: login` (the CLI's own login) is for a developer's machine and is refused inside Actions. Local mode and `/factory:run` run on the developer's own harness login. Factory never stores, brokers or pools a subscription token. Reason: API billing makes `max_usd` and `daily_usd` real numbers, and the vendors' terms limit plan tokens to ordinary individual use.

## How an Objective flows

1. **File.** A writer opens an issue stating the Objective (goal, acceptance entries under an Acceptance heading, sources, context, recorded decisions) and a maintainer applies `factory:objective`. The Project card is Queued. Blocked-by relations on the issue are the only dependency graph; an issue closed by any route counts as done.
2. **Dispatch.** The dispatcher, ticked by events (any issue closing among them, since it may block an Objective) and by Factory's own jobs, with GitHub's `*/10` cron as the backstop, picks ready Objectives by priority label and starts work up to `max_concurrent`, stopping at `daily_usd`. The card moves to Running.
3. **Work.** The worker checks out the default branch, runs `setup`, installs the versions the lockfile pins (online, with no credential in its environment; npm, pnpm and yarn skip install scripts), renders the task card and starts the harness with the issue text verbatim. The harness writes its plan, implements, rebases, validates and commits, and leaves its plan, PR text and exit record as files. Factory posts the plan, pushes `factory/<issue>` and opens the one PR. The card moves to In review.
4. **Review.** The reviewer posts findings as PR review comments. The worker gets them once and addresses or rebuts each in a reply file; Factory pushes its commits, posts the replies, and validation runs again.
5. **Merge.** Factory merges the reviewed head once its required checks are green, through the merge queue where there is one. A conflict or a red integrated run goes back to the worker once; a second failure is Blocked. A PR that conflicts when its review reaches the merge (a sibling landed first) is the same case on every route: nothing is enqueued, it stays delivered, and the send-back takes it (`factory run --wait` does the send-back itself). The card moves to Done and the issue closes.
6. **Blocked.** The PR becomes a draft, the card moves to Blocked, and one comment states the reason (validation failed twice, reviewer findings unaddressed, dollar or time cap reached, worker died twice, integration failed twice). The queue does not wait. A human fixes it by pushing to the branch or editing the issue and re-applying the label; a local Block on hosts the sandbox denied names them and its own fix (Exit: blocked, below).

## The task card and the skills

The worker's instructions are a short task card (`plugin/templates/task-card.md`, rendered per run: issue, budget, the three exits, what to leave where, no questions) plus skills loaded when their step is reached: `objective-plan` (the plan comment, assumptions, the Question rule), `implement-split` (implementer sub-agents, disjoint-file parallelism, sequential PRs for large Objectives), `prove-acceptance` (real-path proof, no weakened tests, the base-failure rule, the budget command), `deliver-pr` (rebase, the PR body, reviewer replies), `review-pr` (the reviewer's own) and `scoring`. All three harnesses read the Agent Skills format. Agent definitions are written three ways from one source (`plugin/agents/source.json`, `node plugin/agents/render.mjs`): Markdown for Claude Code (with a pinned `model`) and Copilot (a `model` only when `subagent_model`, or for the reviewer `reviewer_model` or `model`, is set), TOML for Codex. Where a model is pinned, it is in the file, never passed at spawn time, because Codex drops a spawn-time model for role agents. An adopter overrides a skill by placing one of the same name in their repository, and adds their own.

## The worker contract

|  |  |

The Question exit does not stop the Objective's other work or the queue, and costs the worker nothing to raise, so it is raised only when the card's test is met.

Trust. Factory acts on an Objective's text only when the issue's author and, once the body was edited, its last editor can push or are pinned maintainers. The worker and the review job check it before any harness on every route (Actions, local mode, a cloud-sandbox stage), acting on the body read with those people; a session reads the issue only through `factory issue`, and `deliver` and `post-review` check it again. Otherwise the stage Blocks before a harness sees the text. Factory acts on a marker (validated, rebase, review, spend, decisions-read, a local claim) only from its own login or from a person with push access. Its own login comes from its token, never from a comment's author: the App's bot on Actions, the token's owner in local mode. No other App counts, the job token's `github-actions[bot]` included. The workflow's `notify` and `maintainers` are written `login#id` and trusted by the numeric id, so a login renamed away is a stranger; doctor warns about a bare one and names the id to add.

Split Objectives. A part's exit record lists the checklist items left; its PR says `Refs #N` instead of `Closes #N`, and Factory records the part on the issue. When it merges and the issue stays open, the dispatcher deletes `factory/N` and queues the Objective again; the next part starts from the default branch with the plan and the merged parts' PRs in `$FACTORY_IN`. One PR is open at a time, and an Objective that needs more than six parts Blocks.

Git LFS: in a repository whose `.gitattributes` uses LFS, every worker and review job fetches the branch's LFS objects before the harness (a failed fetch is a warning, not a Block); that spends LFS bandwidth per job in exchange for validation and the model seeing real media. Factory's own git commands that move the agent's checkout (onto the branch, onto its own rebase, onto its catch-up merge) never fetch LFS content there: they leave pointer files (`GIT_LFS_SKIP_SMUDGE=1`), and the objects then come from Factory's mirror, fetched with its token, followed by `git lfs checkout`. A reused local clone keeps the filters an earlier stage installed, and its git has no credential, so a smudge there would fail the checkout. The hand-over covers every commit a git in the checkout can check out that stage: the branch's head, the default branch as handed over, and the branch's commits beyond it, again whenever the default branch moves (a catch-up merge, or one that conflicts), so the harness's own rebase or merge in a conflict pass downloads nothing either. Only objects the checkout's store lacks, matched by each pointer's oid and size, are downloaded and copied, within the stage's remaining time (a hand-over the time cuts short says so, `git lfs checkout` included). The hand-over delivers the whole working set whatever its size: `FACTORY_LOCAL_MEDIA_MAX_MB` caps only the media a branch pushes. LFS routing that arrives after the stage set the checkout up (a rebase or merge brings the first `.gitattributes` pattern) is named in the log: Factory leaves the checkout's pinned git config alone, so the objects go to its store and the files stay pointers until the next stage. In local mode the harness's sandbox cannot reach LFS storage, so the model commits media and Factory's own push uploads it from the host, to the repository's own GitHub endpoint whatever `.lfsconfig` says, with the token offered to github.com only; a branch carrying more than `FACTORY_LOCAL_MEDIA_MAX_MB` (500) of media since the default branch Blocks.

## Review and merge

Factory merges on its own (`auto_merge`, on by default); the gate is CI green on the integrated head, the reviewer's one pass and the merge queue's re-run. The owner reads merged diffs when they choose, and the bench's judge samples them. A defect the reviewer flagged and the worker rebutted stays visible on the merged PR; a repeated class becomes a reviewer-skill change scored on the replay set.

The reviewer is one model call per PR on the top model, after validation passes. It gets the Objective text, the diff and the PR body, and it posts review comments tied to lines, each naming the acceptance entry or repository rule it concerns, with assumptions that change behaviour flagged explicitly. It also judges every acceptance entry, met or not, with the line that shows it: Factory lists the issue's entries in the prompt, puts the judgments in the review body, names any entry left unjudged, and turns an entry judged not met into a comment the worker must answer. A call that fails (a crash, a non-zero exit, a cap) or an answer that holds no JSON or judges none of the entries is a missed pass: it reruns once in a fresh session on every harness, on the fallback reviewer where the harness has one. When neither call produced a review, nothing is posted and the Objective Blocks with how each call ended: no placeholder stands in for a review that did not happen, and Factory never merges past the review. A rerun that answered but judged none of the entries is posted, and its placeholder says it is not a clean pass. Entries left unjudged are recorded on the review, not enforced: they do not hold the merge. It has no verdict and no refuse path: a reviewer that can stop a run turns every false positive into a hold. The worker gets the comments once and addresses or rebuts each; Factory pushes, posts the replies, and validation runs again; rebutted findings stay visible on the merged PR.

Factory's push and merge. The harness pushes nothing. Factory takes the branch as a git bundle the agent writes to a pipe, indexes its pack into a mirror only Factory can write (a mkdtemp directory under Factory's own 700 temp directory) with `git index-pack --strict`, so every object is fsck-checked whatever the git version, and checks it there: the paths changed since the stage started (GitHub's head before any harness ran), Git LFS pointers, the local media cap, and each LFS object's bytes against its pointer. It then pushes with an explicit lease on the head it last saw, to `refs/heads/factory/<issue>` only, and reads GitHub's head back. Before a push, when the default branch on GitHub changed a file under `.github/workflows/` since the branch's base, Factory merges it into the branch in the mirror (its own merge commit, from `git merge-tree`) and the checkout fast-forwards to it (one that cannot, with uncommitted edits in the way, keeps the branch on that merge: the next push merges the checkout's new commits onto it, so the branch only moves forward): GitHub refuses a token without the Workflows permission, the App's or the local one, a branch whose workflow file is a version no branch has any more, which is what a run cut before such a change carries. A new branch that conflicts with that merge is not pushed; the harness resolves the conflict once, as a send-back's conflict pass does, and Factory pushes again. That pass answers like the work pass: a cap it reaches Blocks with that cap, and a death, or a rebase or merge it leaves in progress in the checkout, Blocks with nothing pushed. A push GitHub refuses for a workflow file Blocks with that cause, in Factory's words; any other refused push Blocks with git's status word and the exit code, and GitHub's own text goes to the job log only. A refused or rejected push, or a head that is not the one checked, Blocks. Nothing is armed for later: the review job records the head it reviewed and validated as mergeable, and merges exactly that head (the merge endpoint's `sha`, or enqueue with `expectedHeadOid` on a merge queue) once its required checks are green, the review is done and no maintainer decision is unread; otherwise the dispatcher's merge pass does it on a later tick. A merge or enqueue GitHub refuses because another pass already merged the PR, or queued it at the reviewed head, counts as done; that is read from the PR again, never from GitHub's words. The dispatcher's tick comes from events, never only from GitHub's cron: CI finishing on a Factory PR's head (the launch gate's merge tick on the sandbox route; the dispatcher's own `workflow_run` and `check_suite` triggers without one), a Factory PR merging, the queue dropping one (`pull_request` `dequeued`), and the queue watch. A PR the queue drops unmerged (its checks failed or timed out on the queue's commit) is enqueued once more, and the issue gets one line saying so with the queue's code and time; dropped again, the Objective Blocks with the queue's reason codes, read from the PR's timeline. Only drops after the latest of the review the merge rests on, the head's commit (GitHub keeps no push time for a branch push) and the issue's last re-entry or Block count, so a re-entry starts the count over even when its head keeps the earlier review. When GitHub never started the required job on a dropped entry's merge_group commit (no step, no runner: a billing lock, a spending limit), the Block says so as infrastructure, quoting GitHub's annotation, as validation does, rather than pointing at the checks. A queue commit on which CI never begins in 10 minutes counts as a drop too, and so does one on which CI began but a required check makes no progress. Progress is read from the check's Actions job: its steps, each one starting and completing (a running job's log is not readable, so it is not used). The job is stalled when the step running now has run past max(3 × that step's normal duration, that duration + 15 minutes), so never under 15 minutes (16 for a step that normally takes 1); the normal duration is the longest the same step of the same job took in the workflow's last 15 green runs on the default branch or in the merge queue, read with the job token once per dispatcher tick or queue watch, and only once a step has run 15 minutes. A step with no history, a running step GitHub gives no start time (counted from the check run's start), a check that is no Actions job, or a job Factory cannot read falls back to a time bound from the job's own start: the queue's check timeout (`check_response_timeout_minutes`, from the ruleset; setup's 60 when unread) less 10 minutes, at least half of it and at least 20 minutes, so 50 minutes at 60. A job queued or waiting for a runner, or with no steps yet, is never stalled. A required check not reported at all (an aggregate behind `needs:`) is judged by its upstream jobs' progress, and by the fallback from CI's first start when nothing runs there. The notice names the stuck step and its times, e.g. `` `Quality` / `Run scripts/ci/setup.sh` running 16 min, normally ~1 min ``. On the local route the Factory App has no Actions permission, so Factory reads no job steps or history there and the hung rule is the time fallback only, read once per merge pass. Factory takes the PR out and puts it back once, which restarts CI, and the second time Blocks naming the check. A removal Factory made reads its reason back from Factory's own requeue comment on the issue, which records it, since GitHub's timeline cannot say why Factory removed a PR. CI has begun once a check run or status named like a required check exists on it, or a check run or suite from the integration that provides the required checks (Actions when the ruleset names none), so an aggregate required job behind `needs:` that starts late is not a stall; another app's run, such as code scanning's, does not count. Any run from that integration counts, required or not (a `push` workflow that fires on the queue's branch, another `merge_group` workflow, a startup failure); one that never produces the required check is bounded by that rule and the drop handling. When the required checks cannot be read, any check run, any status, or any suite with a run counts. The queue-watch job, started by the dispatcher whenever its merge pass leaves a PR in the queue, reads the entry every 30 seconds until the PR leaves the queue, merged or dropped, or stalls there, and then ticks the dispatcher with its own `workflow_dispatch`; after 12 minutes it ticks anyway, and that run starts a new watch. Recovery from a drop never depends on the `dequeued` run: GitHub attributes that event to `github-merge-queue[bot]` and, under a strict approval policy for outside contributors, holds it for approval, while a `workflow_dispatch` by the job token is never held. The `dequeued` run stays a faster path where it runs; the merge pass reads the queue and the PR's timeline each time, so the two never enqueue a PR twice. Local mode's loop runs the merge pass every interval itself. A person's own removal from the queue is a hold, not a drop: Factory leaves the PR out until they enqueue it again, or it is reviewed again, gets a new head or re-enters. Doctor names an installed workflow rendered before these ticks (re-run `setup --apply workflow`), and, with a merge queue, warns when the repository's approval policy can hold the `dequeued` run (or cannot be read, which needs admin), saying recovery runs from the queue watch. The squash commit carries the PR's title and Factory's closing line, never the branch's commit messages; on a merge queue, setup sets the repository's squash default to the PR's title and body, and doctor checks it. A PR that fell behind gets GitHub's update-branch merge; that new head is accepted only when it is a merge of the recorded head and a default-branch commit, committed and signed by GitHub's web-flow key, with exactly the tree Factory's own `git merge-tree` of the two gives. Any other new head goes back to review. Factory's git runs only in its mirror, with hooks off and no global or system config; the agent's checkout gets the default branch, the branch and Factory's own clean rebase as bundles, and every git command there runs in the agent's sandbox. Only the commit Factory's rebase made keeps the review; a head the harness made (a resolved conflict, a fix) is reviewed again, and so is a rebase Factory then merged a workflow change into before pushing.

The merge queue is GitHub's. It serializes merges and re-runs CI on the integrated head, which is what makes dozens of concurrent workers safe without owned paths: a PR that was green on its branch and conflicts after a sibling merges is caught there, sent back to its worker once with the conflict, then Blocked. Two mechanics decide how it is wired. First, a PR opened, pushed or enqueued with the job's `GITHUB_TOKEN` gets no `merge_group` workflow run, so its required checks never report and the queue evicts it at the timeout; every push, PR creation and enqueue therefore uses an installation token from the adopter's Factory GitHub App, and the job token stays read-only. Second, the queue needs its checks reported on the queue's own commit, so the repository's CI is a separate workflow triggered on `pull_request` and `merge_group`, never a step inside the worker job; the worker job's own validation run is the worker's feedback, and the CI workflow is the gate. Branch protection requires the queue and those checks, so neither a worker nor a stray push bypasses them. A required check that is skipped counts as passed, so aggregator jobs use `always()`.

## Scale

The design target is dozens of Objectives queued and in flight with nobody watching. It is not yet drilled at that size and is not among the 0.9 claims.

- **The dispatcher is the only scheduler logic.** Ready = labeled, not blocked by an open issue, not Running, In review, Blocked, Question or Done. Order = `P0`, `P1`, `P2`, then issue number. Start up to `max_concurrent`; stop for the day at `daily_usd`.
- **Factory owns its ticks; GitHub's cron is only the backstop.** GitHub fires a schedule late or not at all under load: on the scratch repositories the `*/10` cron fired for under 3% of its slots over a week, hours apart. So every wait has an owner that ticks the dispatcher with `workflow_dispatch` (the job token's, never held for approval): an event (a label, an issue closing, a merge, CI finishing, a queue drop; a closed issue that was no Objective and blocks none ends its run after minting the token and at most one listing, so it costs a job start and seconds), the job that freed a slot or failed a launch, or, for a wait only time ends, the `wake` job. Each dispatcher run lists its deadlines (`{issue, kind, at}`, in its log) and arms one wake for the earliest of five kinds: a sandbox stage's lease end plus a minute (a stage that died silently), a quota retry the launcher handed over, the next try of a failed start (2, 4, 8, 16, then every 30 minutes; a vendor's refusals never Block and hold the route's new picks for at most four in a row, three real failures or three cut-offs in a row Block; every attempt ends as a stored entry, docs/ADAPTERS.md), the next 00:00 UTC when `daily_usd` held Queued work back, and one quick retry of a read that failed (never two in a row). The other kinds it lists (`launch-grace`, `review-grace`, `checks-grace`, `answer-grace`, `local-pause`) are their event's or the local loop's, with the cron behind them; a stale Running Objective on the runner route is bounded by its job's `timeout-minutes`. A wake arms only when no wake already queued or sleeping fires before its deadline or within a minute after it (read from the `wake (<kind> <iso>)` job names), joins no concurrency group, and is never cancelled, so a duplicate only ticks twice; a run a wake started never arms that same deadline again, and dry runs and runs named for one issue arm none. Which kinds a repository arms follows its visibility, read from the event's repository payload (one repository read only when a schedule run has a long wait to decide; unknown counts as private). Cost: a wake sleeps on a hosted runner and holds one of the account's concurrent-job slots while it sleeps.
  - **Public repository:** Actions minutes are free, so it arms all five kinds. On the sandbox route a lease wake sleeps through each stage (the heartbeat moves the lease on), and a capped day's turn is reached in hops of up to 350 minutes, each a plain tick.
  - **Private repository:** each sleeper bills about $0.36 an hour (a 2-core Linux runner at $0.006 a minute), so it arms only `quota`, `start-retry` and `retry`, minutes each: about 5 to 20 billed minutes per quota retry, 2 to 30 per failed start and 2 per read retry. Each launch the dispatcher names also arms a `start-retry` wake for its marker's expiry, about 10 billed minutes (about $0.06) per named launch unless an earlier wake covers it, so a normal Objective costs about 10 to 20 sleeper minutes (its work and its review). A stage's lease end and the day's turn stay in `deadlines[]` and wait for events and the cron; doctor says so on a private repository.
  - **The sandbox sweep and image build no longer wait for their crons.** GitHub's hourly sweep cron and nightly image cron are backstops only (on a scratch repository the sweep's fired twice in about 40 hours; the nightly build was skipped one day and ran 7.5 hours late the next). No sleeper waits hours for either:
    - **The sweep arms its own `sweep` wakes, minutes each, on every repository.** Each sweep run arms its next one for what it left: a stage that said it ended moments ago (its launcher's end answers first; 10 minutes), a sandbox created moments ago (15), an older image a stage may still be starting from (15 minutes after a newer build is recorded; the image job arms this after each build that leaves one), the rest of a run that reached `sweep_max_destroys` or its collection slots (10 minutes on, after a run that destroyed or stopped one; with nothing destroyed, a cap of 0 among others, the rest waits for events and the cron), and once what a failure left (never from a `sweep` wake's own run). Each is a minute after its wait ends (about 16 minutes at most), through a wake job of its own (`sweep-wake`, `image-wake`, named `wake (sweep <iso>)`), whose tick runs the sweep and the dispatcher. Only an armed `sweep` wake covers a sweep deadline. A stopped sandbox's `sandbox_idle_days` (days, not minutes) get no wake: the next sweep an event runs (an Objective closing, merging or Blocking) destroys it, or the hourly cron's.
    - **An owed image build runs on the UTC day's first dispatcher tick.** A head an earlier day left unbuilt (today's `image_daily_minutes` used up, or `image_refresh: nightly`) is owed once today's turn allows a build: under today's minutes for `merge`, none tried yet today for `nightly`. Every dispatcher tick on the sandbox route checks (three reads: Factory's image record and the default branch's head commit) and, when one is owed, sets `image_owed`, and the image job builds the default branch's head in that run (on any event but a pull request's). A merge after 00:00 UTC builds on its own push as before. Every build records its attempt on the image record before its first vendor change, and an owed build before anything that can fail; the build's own entry replaces it. Any recorded build of the head (built, failed, or only started: a crash, a 45-minute timeout, a vendor or token error, a refusal) ends the owing, so the next merge or the nightly cron tries again, never another tick. An owed build's job re-checks the record when it starts, so a job a tick queued during another build of the head builds nothing. The image job needs the dispatcher only for this: a push, the cron and a manual build's run skip the dispatcher by its own `if:`, and the image job still runs (`!cancelled()`).
    - Cost on a public repository: none in minutes; each sleeper holds a concurrent-job slot. A `sweep` sleeper is 11 to 16 minutes, about one per image build that leaves an older image and per stage that Blocks itself, so about 30 to 60 minutes a day on a busy repository and none on a quiet one. A private repository pays the same, about $0.07 to $0.10 per wait.
- **Workers do not know about each other.** Coordination is the rebase plus the merge queue. Two Objectives that keep conflicting on one file produce two Blocked cards with the same reason, which is the signal to re-file them or order them (`blocked_by`), not a reason for a planner.
- **Cost is the only cap.** No cap on merges or Objectives per day. Dollars are capped by `daily_usd` on the dispatcher and `max_usd` per job, with `timeout_minutes` as the time cap. `max_concurrent` is a runner-capacity and conflict-pressure control: a matrix with `max-parallel` over the ready issues, since an Actions concurrency group cannot cap at N, and a concurrency group per issue so a repeat trigger dedupes rather than cancels a sibling. Hosted runners cap a job at 6 hours; `timeout_minutes` sits under that.
- **The board is the dashboard.** Queued, Running, In review (with a question marker), Blocked, Done, moved by the jobs.
- **Runner choice is a line in the file.** Hosted by default; self-hosted where an adopter wants their own toolchain or hardware, with `setup` (and `node_version`) as the only places a toolchain is named.

## Security

What the workflow file makes visible, and what is true:

- `permissions:` gives the job's own token `contents: read`, `issues: write` and `actions: read`; the jobs that tick the dispatcher get `actions: write` (work and review also use it for triage's rerun of failed CI jobs), and `id-token: write` is uncommented only for Claude federation. Every write to code goes through the App's installation token, minted for that one repository. No org scope, no PAT, no stored subscription token.
- The harness holds no GitHub write access. On Actions it runs, with the install and the validation, as a separate uid, `factory-agent`, created with sudo per runner: no groups, no sudo, no cron, at or lingering session, its own 700 home, always `/home/factory-agent` and wiped before each job (doctor fails if a `factory-agent` user has any other home), holding its clone and a read-only installation token. Each command runs in a transient systemd unit (`systemd-run`), or, where there is no systemd, in its own namespaces and a cgroup v2 group, with the system read-only, every other home hidden, a private `/tmp` and no new privileges, so it cannot read the runner's home, Factory's temp directory or Factory's process environment, nor write outside its home. Commands start with a fixed `PATH` and no system or global git config. The unit's processes are killed with it after each run, before Factory reads what it left. The write token lives only in Factory's memory (GitHub calls through `fetch`, Factory's git by per-process env config). `setup`, which may need sudo, runs as the runner on a clean default-branch tree Factory made, with Factory's own temp directory. `FACTORY_APP_TOKEN`, when an adopter supplies a fixed token, is Factory's write token; the agent then gets no token and can clone a public repository only; a private one needs the App's id and key. Copilot always runs with its built-in GitHub MCP server off and is never given folder trust, so the repository's own Copilot configuration does not load. Doctor parses every workflow and fails closed: the repository's default workflow token must be read-only (or, when doctor cannot read the default, every workflow must set read-only `permissions:`), no `pull_request` or `merge_group` workflow may ask for write, since branch code runs there, and the Copilot token must be refused on an issue, a pull request and a file write. It checks `sudo -n` and the agent launcher on the runner.
- A harness session is archived as the agent when it is captured, and a held one, like the Git LFS objects handed to the checkout, is unpacked as the agent, both in its confinement and by Factory's own code (`lib/untar.mjs`), not GNU tar. On Ubuntu 26.04 tar goes through `openat2` for each directory it extracts into and for each member name with a slash, with no fallback when that fails, and the agent's systemd unit (`RestrictSUIDSGID`) answers `openat2` with ENOSYS, so no session could be captured with a nested name or put back there (#102). The unpacker takes directories and regular files only (links, devices and the rest are skipped), refuses absolute and `..` names, a size that is not a whole number of bytes and an archive without its end block, makes each path one segment at a time through real directories only, keeps permission bits only (no setuid or setgid), and writes file data as it streams in. `RestrictSUIDSGID` stays on. Doctor checks the round trip where the agent exists (`session restore`).
- `.github/` is on the protected list, so Factory refuses to push a workflow change; the App has no workflows permission, so GitHub refuses one as well.
- `auto_merge` on means code lands without a human read; the file says so in its header comment, beside the gate.
- Cost is capped in the file (`daily_usd`, `max_usd`, `timeout_minutes`), and Claude's `--max-budget-usd` and Copilot's `--max-ai-credits` enforce the per-job cap inside the run; Codex is checked after each run.
- The prompt-injection surface is the Objective text and the comments Factory reads. Factory acts on the Objective text only when its author and last editor can push or are pinned maintainers, checked before every stage on every route (otherwise the stage Blocks before a harness sees it, and a session's `factory issue` refuses to hand it over). Only a maintainer can apply the label; comments count as decisions only from people with write access or the maintainers the workflow names (Trust, above). Secrets are masked in logs, the task card forbids printing them, and the model credential is step-scoped, so the repository code Factory runs (setup, install, validation) never sees it; what the model's own commands can reach is in Credentials and billing.

Notifications. GitHub Mobile notifies on subscriptions, so a comment on an issue the owner authored, or a PR they are requested on or @mentioned in, reaches their phone whichever identity posted it. `notify` names the handle: the Blocked comment @mentions it and a Question draft PR requests it as reviewer. Merges and plan comments stay quiet unless the owner watches the repository.

Why the App is in the footprint at all: it is the one thing GitHub makes unavoidable. Workflows do not run on events the job token causes, and the merge queue attributes its run to whoever enqueued, so an App (or a PAT, which Factory does not support) is the only identity that both triggers CI on the PR and gets a merge-queue run. The cost is one setup screen and two secrets; the gain is that the adopter's existing CI runs on Factory's PRs unchanged, and commits carry the App's name.

## Doctor

The same checks run as `/factory:doctor` before the workflow is enabled and as the first step of every worker job, so a misconfigured repository Blocks with a one-line reason instead of spending a run. Each line is PASS, WARN or FAIL with its fix, and `/factory:setup` offers to apply the GitHub ones. Credentials: the harness's credential is present (for Copilot, `copilot_github_token`, refused on an issue, a pull request and a file write); a plan token is a warning. GitHub (the workflow file read from the default branch on GitHub): the App's installation token mints for this repository with its one permission list (README, Install footprint; a missing read fails) and no workflows; the job token is read-only on code; the merge queue and required checks are on the default branch and the CI workflow listens on `pull_request` and `merge_group`; the labels; the five Project columns; `notify` and `maintainers` pinned as `login#id`. Repository: `setup` is present (and runs clean with `--run-setup`), the validation commands exist, a lockfile is recognised (or `install` is set), protected paths are present and cover every repository file the `setup` command names (setup adds them root-anchored, as `/scripts/ci/setup.sh`), repository skills parse and fit the cap, git-lfs is installed when `.gitattributes` uses Git LFS. Runner: `runs-on` resolves and matches the Linux runner of the CI workflow on `pull_request` (a warning), the harness CLI installs, `timeout_minutes` fits the runner's ceiling, and for Claude Code bwrap, socat and rg are present where the job runs, AppArmor lets bwrap make user namespaces on a self-hosted runner, and every `allowed_domains` entry is a host name (a warning names each one dropped; Credentials and billing); for Codex bwrap and its sandbox starting and confining where the job runs, with AppArmor on a self-hosted runner; for Copilot bwrap, slirp4netns and its sandbox starting and confining, with AppArmor for unshare on a self-hosted runner (Credentials and billing). Sessions: where the agent exists, a held session's round trip as the agent (`session restore`, Security). Worker secrets (when `worker_secrets` names any): a warning for each refused entry, each SOURCE with no value and each value equal to Factory's own AI Gateway key (Worker secrets, above).

## Red-check triage and the drift advisory

Optional, with the `AI_GATEWAY_API_KEY` secret passed as `ai_gateway_api_key` (local mode: `docs/LOCAL.md`).

Red-check triage. When a required check is red, Factory asks a decision model (Vercel AI Gateway's decisions endpoint, `triage_model`, default `perplexity/pplx-decider-v1.2`) one question per failing CI job: did the change break it, or is it a flake or infrastructure? Only when every failing job reads flaky at confidence 0.7 or more does Factory rerun the failed jobs (with the job token's `actions: write`) and wait again, with no fix pass and no pass counted; anything else goes to the fix pass as before. A job whose failed steps are only its set-up (GitHub's first step) or a checkout step of its workflow (`uses: actions/checkout@…` in the file at the head, matched by the step's name in the jobs API) ran no code of the change: it is not asked, and counts as a flake for that rerun. Each question names the job's first failed step. A required job GitHub never started is never asked (the blocked exit, above). A failing job is never asked when its failure lines name a path, file name or test the PR changes (an intermittent defect the change brought passes on a rerun too), and a required job is left out of the questions only when it is structurally an aggregate (in the same workflow run as another failing job, started after it completed) and its own log has no failure line. Each job's verdict, confidence and failure signature (a hash of the sorted failure lines a runner, compiler or tool printed anywhere in the log, Git LFS's batch and download errors included, and of the repository files they and their stack frames point at; a log with no failure line has no signature and matches nothing) go on the run's progress comment, with a hidden record of the heads and signatures rerun and of a refused rerun: one rerun per head, a signature already rerun once is never rerun again on that Objective, a refused rerun (not a rate limit) is not tried again on it, and a rerun that turns green is said on the progress comment. Each failing job's log window and the PR's file list are sent to the gateway. The same key turns on the drift advisory: while the worker's harness runs (the work, fix and answer passes), at most once every two minutes and only after 12 activity entries, Factory asks a decision model (`drift_model`, default `baseten/elephant-1`) whether the agent is `on_task`, in `scope_creep` or `looping`, from the plan's checklist items, its last 12 activity entries (commands, edits, sub-agents, messages, read from the harness's own event stream) and the repository files it has edited. A `scope_creep` or `looping` answer at confidence 0.7 or more writes one line on the progress comment and in the job log, at most once per harness run; every answer's label and confidence go to the job log. It is advice only: it never stops, pauses, blocks or redirects a run. Those inputs go to the gateway. Factory's own process makes the call; the key reaches no harness or command. Each triage line goes to the job log as well. Without a key, every red goes to the fix pass as before and no drift check runs, and the first red of each stage says `triage: off (<code>)` (local mode's key-file codes: LOCAL.md).

## Cost tiers and parallelism

The planner-high, worker-medium split survives one level down. The worker session runs on the strong model and does the planning, the integration and the PR; each checklist item goes to an implementer sub-agent on the cheaper model, pinned by the agent definition the job writes into the checkout (`.claude/agents/implementer.md` with `model: claude-sonnet-5-5`; `.codex/agents/implementer.toml` for Codex; Copilot's carries a model only when `subagent_model` is set) so the worker cannot drift up. Where the harness reports sub-agent usage (Claude does; Codex's sub-agent threads are read from their rollouts; Copilot reports none), the caps and the scorecard see it. The strong model stays in the loop for the whole Objective instead of handing a compiled brief to a weaker one and leaving.

Parallelism has two levels and the brief owns the inner one: implementers for items on disjoint files run at the same time, then one integration and one validation. The outer level is the dispatcher's `max_concurrent`. A worker that sees the whole Objective can tell which parts are independent without a graph review to say so.
