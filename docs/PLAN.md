# Pendulum: design and contracts

Pendulum is a GitHub Action, a harness plugin and a bench, sharing one set of skills and a short task card. An adopter adds one workflow file, a GitHub App and a model credential, and labels an issue `pendulum:objective`; a worker builds it, a reviewer comments on it, and Pendulum merges it through the adopter's own required checks and merge queue. The human reads the Project board's Blocked column and, when they choose, the merged diffs. This page is the design as it is now; git holds its history.

## Design rules

- **No planner, compiler or Work Items.** The worker session plans in a comment on the issue and implements with pinned sub-agents. Reason: a stock harness given the brief merged the same Objectives without stops, where a separate planner added holds about Pendulum's own machinery.
- **Pendulum merges on its own** (`auto_merge`, on by default). The gate is CI on the reviewed head and on the integrated commit, the comment-only reviewer pass and the merge queue's own re-run; no human reads the diff first. Reason: taking the human out of the loop is the product. `auto_merge: false` gives ready-for-review PRs instead.
- **The only stops are Blocked and Question, and neither stops the queue.** Reason: with many Objectives in flight, every hold is multiplied by the queue.
- **GitHub is the only database, and the Action the only controller on every backend.** The install is the Action plus the App's two secrets; no server, database or vendor platform is ever required. Reason: nothing to host, and the state is where the adopter already looks.
- **Every stage runs behind three interfaces** (trigger, sandbox, gate: `plugin/scripts/lib/backend.mjs`), and every third-party service behind an adapter contract (`docs/ADAPTERS.md`). Reason: a new backend or vendor is one module, not a refactor.
- **Claude Code, Codex and Copilot are peers:** same task card, same skills, each with its own credential.
- **No knowledge loop.** Pendulum learns through skills people edit and a bench that scores each edit. A correction that repeats across adopters becomes a line in a Pendulum skill; one that repeats for one adopter goes in a skill in their repository.
- **Skills are capped and measured.** Each skill is at most a page (`bench/skills.mjs` enforces it) and versioned by hash in `bench/skills.json`, re-recorded and committed with every skill change (CI runs `node bench/skills.mjs --check`); the scoring checkout's digest is on every scorecard row. A skill's text changes only with its instrument run: the reviewer replay set (`bench/review-replay.mjs`) for pendulum-review-pr, the medium drill set (`bench/drill.mjs --set medium`) for the worker skills. Reason: one reasonable line at a time is how a rubric grows past usefulness.
- **No adopter has a code path.** Runner and toolchain are the `runs-on` and `setup` lines in the adopter's file; a need those cannot express is a Pendulum bug.
- **Pendulum never builds itself.** Objectives and drills run on scratch adopter repositories, never on this one; the `pendulum-run` skill refuses it.
- **The App and the Project board are required.** The App is the only identity that both triggers the adopter's CI on Pendulum's PRs and gets a merge-queue run (below); the board is the dashboard.
- **Adopters take releases by exact tag**, on their own cadence (README, Versioning).

## Dependencies

Pendulum uses an existing SDK or library before writing its own (AGENTS.md). The plugin runs with nothing installed, from a Claude Code plugin install and from the Action's checkout, so a runtime library ships inside it:

- **Vendored, byte for byte:** `plugin/vendor/<name>/` holds the files the library itself published, as `tools/deps/package-lock.json` pins them, never rebuilt. `node tools/deps/sync.mjs` copies them after an `npm ci --ignore-scripts --prefix tools/deps`, and CI checks the copy matches, each library's folder (and a scope's, `plugin/vendor/@scope/`) a real directory, never a link. Dependabot bumps the pin; the bump's PR stays red until `sync.mjs` is run on it and the copy committed. Today: `yaml` (workflows, `pnpm-workspace.yaml`, agent frontmatter), `smol-toml` (Cargo and uv workspace members), `unbash` (the `setup`, `install` and validation commands, read by bash's grammar for the files and package.json scripts they run and, in doctor, their first command), `tldts` (the Public Suffix List, for a `pendulum:host:` label's wildcard: its API for whether a name is a suffix, and its published rule data, `dist/cjs/src/data/trie.js`, for whether a rule lies below one, which no API of it answers; its self-contained CommonJS build), `canonicalize` (RFC 8785's canonical JSON, the form of the usage record a sealed session's associated data hashes) and `@actions/expressions`, GitHub's own expression parser (a red job's `continue-on-error`), under `plugin/vendor/@actions/expressions/`.
- **Installed for one job:** the cloud-sandbox jobs install `@vercel/sandbox` from `plugin/package-lock.json` (docs/ADAPTERS.md).
- **CI only:** the Quality workflow checks every skill with the Agent Skills standard's reference validator, `skills-ref`, installed from `tools/deps/requirements-skills.txt` with hashes, wheels only, through `tools/deps/skills-validate.py`, which also takes the one harness field the standard does not define that Pendulum sets: Claude Code's `user-invocable: false`, on the internal stage skills (`bench/skills.mjs` checks each harness's hide setting on them). It lints plugin/, bench/ and tools/ with ESLint for correctness only (`tools/deps/eslint.config.mjs`), from the `tools/deps` lockfile's devDependencies, which `sync.mjs` never vendors.

What stays Pendulum's own code, and why:

- **`lib/untar.mjs`:** runs as an inline script inside the agent's confinement, where no installed package is readable, and unpacks only Pendulum's own archives, skipping every link, device and FIFO. GNU tar fails there on Ubuntu 26.04 (#102).
- **`lib/app-token.mjs`:** `node:crypto` signs the App's token; the rest is Pendulum's permission narrowing and doctor's gap checks.
- **`lib/seal.mjs`:** a public repository's usage artifact carries the agent's event stream and sessions sealed (PRIVACY.md, What goes to GitHub). `node:crypto` does the cryptography: HKDF-SHA256 derives the key from the App's private key, AES-256-GCM seals a gzipped tar of them (the system `tar`). The file is a fixed 8-byte tag, the 12-byte nonce, the ciphertext and the GCM tag; the additional data binds it to its Objective, stage and session. An `age` or JWE library (`jose`) would be a new runtime library for what one `node:crypto` AEAD stream does.
- **`lib/github.mjs`:** GitHub calls go through `gh api`, GitHub's own CLI.
- **Closing what harness text leaves open, in `lib/handover.mjs`:** it only appends closers (a fence, `</details>` and the like) after a line scan by CommonMark's fence rule; the plugin vendors no markdown parser, and adding one (`micromark`) for that would be a new runtime library.
- **Diff reading in `lib/logic.mjs`:** `parse-diff` misreads the quoted names `git diff` prints, and the review needs the new-side line map GitHub's review API takes.
- **Glob matching in `lib/logic.mjs` and `doctor.mjs`:** the patterns come from files a worker can edit, so the matcher runs in linear time. A brace or character-class pattern matches nothing there; at worst a fix pass's lockfile change is refused and the stage Blocks with the reason.
- **The harness runners, decision calls and usage parsing:** Pendulum drives each vendor's own CLI through its documented headless mode, and owns that launch (the outer sandbox, the agent uid, the process group it kills, the event file it meters). The Claude Agent, Codex and Copilot SDKs start the same CLIs and price nothing Pendulum does not.
- **The machine's stage slots in `lib/machine.mjs`:** a counting budget shared by processes, freed when a holder dies, which a file lock library does not give: `proper-lockfile` is one mutex per file whose stale lock is judged by its age, so a dead holder's slot would stay taken until it aged out, and Node has no `flock`. Each slot is a numbered file of its holder's process record (pid, start time, boot), checked as `lib/proc.mjs` checks its other records; a slot is taken by creating its next generation's file with a hard link, which only one process can do, so no clock or listing order decides who holds it.
- **`lib/adapters/decider-ai-gateway.mjs`:** the AI SDK's decision model is experimental; the call and its pricing (the relay's own generation lookup) are about 125 lines behind the decider adapter contract.
- **`lib/app-manifest.mjs`:** GitHub's App Manifest flow is a form post, one redirect to a listener on 127.0.0.1 and one REST call, through `lib/github.mjs`; `gh` saves the secrets. Probot carries the flow only inside its server framework and writes the new App's key to a `.env` file, which Pendulum never does. The browser is opened with the platform's own opener (`$BROWSER`, `open`, `wslview` or `explorer.exe`, `xdg-open`), a few lines beside the `open` package, which would be a new runtime library for one spawn.
- **`lib/adapters/github-status.mjs`:** Atlassian Statuspage publishes no SDK for a page's public status API, and GitHub's own clients (`gh`, Octokit) do not cover githubstatus.com; the read is one `fetch` of `summary.json`.

## Job one and how it is measured

Job one: file an Objective, walk away, and come back to correct, merged work at a reasonable cost. Pendulum is judged on four numbers per Objective, taken by the bench from the issue, the PR, the job log and the harness's usage output.

| Measure | Job-one part | Taken from |
| --- | --- | --- |
| Walk-away: merged with zero human input after the label | Operator walks away | Three buckets. Walk-away: merged with no human push, comment or edit on the branch or issue after the label. External: every stop was a Block outside Pendulum and outside the work (Pendulum's `max_usd` cap, the AI Gateway's budget or credits, a provider's quota, plan limit or billing: the model provider, GitHub's Git LFS storage, GitHub's API rate limit or the sandbox vendor's plan; a provider or GitHub outage Pendulum handled by its rules), and the only human input answered those Blocks. Miss: anything else, a Blocked card of any other cause included. Each Block records its cause as a code (bench/README.md, Block causes), so the bucket is decided on structure. |
| Solution quality | Correct work | The bench's blind pairwise judge where there is a comparison; the owner's read of the merged diff when they choose to read it; escapes found after merge count against it. |
| Operator minutes | Operator walks away | Minutes spent on Blocked cards and on re-filing, from a stopwatch; zero on a clean merge. |
| Dollars per merged Objective | Reasonable cost | Per harness: Claude's headless output carries total\_cost\_usd and per-model usage with sub-agents included; Codex's JSONL carries the thread's running token counts (a resumed pass counts only its own share), priced from a table, with each sub-agent thread's own counts read from its rollout and priced at its model; Copilot bills GitHub AI Credits and its usage file reports them per run, so its column is those credits at GitHub's published $0.01 each (configurable), with the premium requests beside them. Runner minutes beside it. Wall time reported, never alone. |

The standing scorecard is one row per Objective, kept by the bench (`bench/score.mjs`, `/pendulum:pendulum-score`).

## 0.10.x releases

Pendulum is at 0.10.x, the release candidate for 1.0, run on real work: its surface is expected to hold and its releases to be fixes underneath, with no stability promise until 1.0. 0.10.x releases are batched fixes that ship on CI and the review. A candidate tag on the scratch drill meets this bar:

- **Five in a row per harness.** Claude Code, Codex and Copilot each merge five consecutive Objectives of the scratch medium set (`bench/drill.mjs --set medium`) as walk-aways.
- **Every route covered.** Together those runs cover the Actions, local and cloud-sandbox routes.

Counting rules:

- Any Pendulum change means a new candidate tag, and every count starts again. Reason: the bar proves one exact tag.
- An answer, un-block, hand-started run or re-run by anyone, an owner's agent session included, is operator input: that row is not a walk-away and the streak breaks.
- A P1 defect found later in a counted merge breaks the streak. The owner reads the counted diffs.
- An External Objective (Job one) is skipped: it neither counts toward the streak nor resets it. Reason: nothing Pendulum, the Objective or the repository's setup did could have avoided its stops.
- The streak is counted by `node bench/score.mjs --streak --repo OWNER/NAME --since <candidate tag>` (bench/README.md, The streak): a stall, an unmerged end or an input source the scorer could not read resets it too.

## The 1.0 bar

1.0.0 is tagged when five consecutive real Objectives merge with zero operator input, pooled across the real adopters:

- **Real adopters only:** `clockgrove/clockgrove`, `clockgrove/assetgrove` and `clockgrove/raccoon-world` together, never the scratch drill repositories.
- **One pooled streak:** the Objectives of all three, ordered by when each ended, on any harness (Claude Code, Codex or Copilot). Any miss on any of them resets it.
- **It spans 0.10.x releases:** the count before the rename to Pendulum is recorded on clockgrove/pendulum#465, and the streak goes on from it, counted from v0.10.0 (`--since v0.10.0`); it keeps counting when the adopters move to a later 0.10.x release, and only a miss resets it.
- **The same counting rules as above:** any human input (an answer, un-block, hand-started run or re-run by anyone, an owner's agent session included), a Blocked card, a stall, an unmerged end, an input source the scorer could not read, or a P1 defect found later in a counted merge breaks the streak; an External Objective is skipped. The owner reads the counted diffs.

Counting it: `node bench/score.mjs --streak --since v0.10.0 --repo <adopter> --repo <adopter> --repo <adopter>` prints each adopter's streak per harness, then the pooled streak and the sequence it counted: every finished Objective of the three, ordered by when it ended, on any harness, each a walk-away (`yes`), skipped as External, or the miss that reset it. Five is the bar. An Objective in flight has not ended and does not count yet. A parked Objective (its label removed while it waits on other work) is still scored: it counts once it ends, and a Blocked one is a miss. `--out` writes the rows and both streaks (bench/README.md, The streak).

**What freezes at 1.0 (proposed):** the Action's input names, the labels (`pendulum:objective`, `pendulum:running`, `pendulum:in-review`, `pendulum:question`, `pendulum:blocked`, `pendulum:review`, `pendulum:restart`, `pendulum:draft`, `pendulum:handover`, `pendulum:local`, `pendulum:image`, `P0` to `P2`), the markers Pendulum writes on issues and PRs, the App's permission set (docs/INSTALL.md, Install footprint) and the workflow template's jobs (`dispatch`, `queue-watch`, `work`, `review`; on the sandbox route `launch`, `launch-gate`, `launch-event`, `launch-tick`, `image`, `sweep`). From 1.0, a 1.x release renames or removes none of them and asks the App for no new permission; it may add an optional input. Before 1.0, a 0.10.x release may still change one of them as the exception, and its release notes call the change out.

What 0.9 claims beyond the candidate bar:

- The cloud-sandbox route runs a stage in one sandbox session of `timeout_minutes` plus about 16 minutes (up to 24 hours on Vercel Pro; a plan that caps sessions lower cuts the stage to the session granted, and it Blocks naming the cap if it outruns it), with Claude Code, Copilot and Codex (through the Vercel AI Gateway) proven.
- Local mode on macOS is sandbox verified, not run end to end.
- Dozens of Objectives in flight at once is the design target (Scale), not a 0.9 claim.

## Credentials and billing

Unattended runs bill API credentials by default (`credential: api`):

- **Claude:** workload identity federation (the job's OIDC token exchanged for a short-lived Anthropic credential, `id-token: write`) or `ANTHROPIC_API_KEY`.
- **Codex:** a Vercel AI Gateway key, `PENDULUM_CODEX_GATEWAY_KEY` (the `codex_gateway_key` input), or `CODEX_API_KEY`; either passed only to the step that runs the harness, never a job-level variable. With both set the gateway key wins and `CODEX_API_KEY` stays out of the harness's environment and the cloud sandbox. The gateway key is its own secret: never `AI_GATEWAY_API_KEY`, which is Pendulum's own (triage and drift, `PENDULUM_SECRET_KEYS`). Through the gateway Codex runs a `vercel` provider on the gateway's Codex endpoint (`lib/harness.mjs` `codexGatewayArgs`: `https://ai-gateway.vercel.sh/codex/v1`, the Responses wire API, the key from `PENDULUM_CODEX_GATEWAY_KEY`), the model as `openai/<id>` on every pass, resumes included, and an `x-session-id` header that is one opaque id per Objective per Running stint (`gatewaySession`), so the gateway keeps the stint's passes on the provider credential that wrote the thread. Usage bills to the team's AI Gateway credits at the provider's list price, cache writes included (`cache_write_input_tokens`, priced at the model's write rate). A resume the provider refuses because the thread was written through another credential (HTTP 400 or no status, with `invalid_encrypted_content` or `organization_mismatch`, read from the error's structure) runs once as a fresh thread with the full card, where the pass has one to give (the exit-record ask has none, so there the refusal Blocks), and the log says so. A Codex model with no row in the price table runs at unknown cost (`usdUnknownWhy` `no-price`): neither `max_usd` nor `daily_usd` counts it, only the key's own budget bounds it, and doctor and the progress comment say so. Doctor checks the key for free against the gateway's Codex model list with `--probe`.
- **Copilot:** `copilot_github_token`, a fine-grained token with only the Copilot Requests permission from a user with a Copilot seat, passed to the harness step only and billed to that seat; never the job's own token, which can write. Doctor fails without it.
- **Several accounts** (INSTALL.md, Several accounts): the workflow's `PENDULUM_ACCOUNTS`, which setup's `--add-account`, `--remove-account` and `--accounts` set (`setup.mjs` `accountSettings`, checked as the jobs read it), names each harness's accounts, and each account's credential is a secret of its own, the usual name with the account's suffix. A job's `account` step (`scripts/objective-account.mjs`) picks the stage's account, its harness's default or a trusted `pendulum:account:<name>` label's, and the stage's step gets only that account's secrets: setup renders the declared accounts into the workflow, each credential input naming every account's secret by its fixed name and passing the picked account's (`lib/accounts.mjs` `routeCredentialRef`; never a computed `secrets[...]` lookup, which would send the runner every secret), so a change to `PENDULUM_ACCOUNTS` needs a re-render, and the step picks none until then (`rendered_accounts`); the stage, and the launcher before any sandbox spend, Block when its labels pick another by its start (`lib/objective-trust.mjs` `accountGate`, `routeAccountCheck`); two account labels make a stage wait, never Block (`lib/account-wait.mjs`). On an account only its step-scoped credential counts (no job-level variable, no federation), and a missing one is named as that account's secret. A Codex ChatGPT login is refused there, the launcher included, decided on the credential's shape (an `auth.json` or a JWT). With `PENDULUM_AUTO_ACCOUNT` on (workflow file only) and two or more accounts of the harness, the step picks a free account for a stage with no pin (`lib/route-holds.mjs` `pickRouteAccount`, holds.mjs's choice with a hash of the Objective's number for the turn), from usage-limit holds Pendulum's App keeps as its own unedited comments on its own closed, locked holds issue (`readHolds`, `writeHold`: holds.mjs's semantics over GitHub records, one comment per limit, no new permission); an unpinned stage that meets a limit more than an hour from its reset (`usage_limit_move_minutes`) with another account free records the hold and ends `waiting`, the work back to Queued and a review's label off until the dispatcher's next tick, so the next stage starts on the free account (`routeLimits`, account-wait.mjs); it Blocks `provider-quota` only when every account is held.

The model's own commands never get a credential in their environment, on every route, but the worker secrets a repository opts in to (Worker secrets, below). Codex runs with `shell_environment_policy.exclude` and Copilot with `--secret-env-vars`, each naming every model, runner and Pendulum credential (`SHELL_SECRET_KEYS` in `lib/harness.mjs`; Copilot also masks their values in its JSON output). Claude Code runs every command in its own bubblewrap sandbox, which unsets the same names (`sandbox.credentials.envVars`, [sandboxing](https://code.claude.com/docs/en/sandboxing#protect-credentials)) and gives each command its own PID namespace, so no command reads another process's environment either. Codex and Copilot do the same on every route but a developer's own session: in local mode, on Actions and in a cloud sandbox, every command runs in its own sandbox, which keeps every process outside it from being read (below). Package installs never see one: in a cloud sandbox the start command runs apt, npm (their install scripts included) and the CLI's version check with only `HOME` and `PATH`, and only the stage gets the start environment (`launch.mjs` `START`). Reason: the model runs the repository's code and its dependencies, and a package's install scripts run too; none of them may read the key that bills the run or Pendulum's tokens.

Claude Code's sandbox on Actions and in a cloud sandbox VM holds local mode's bar (`lib/local.mjs` `claudeRunnerSettings`, `lib/harness.mjs` `claudeRunner`, `lib/claude-runner.mjs`), so every command's writes and network follow its lists there:
- **Writes:** the checkout, `$TMPDIR` (with `$PENDULUM_IN` and `$PENDULUM_OUT`), Claude Code's own command temp directory and the package caches in the agent's home (`.npm`, `.cache`, `.local/share/pnpm`, `.bun`, `.yarn`); nothing else in the agent's home, and never the checkout's git hooks, config and harness configuration. File edits stay in the checkout and `$TMPDIR` (`acceptEdits`, writes outside the working directories blocked).
- **Network:** GitHub (Git LFS's download host included) and the npm and Yarn registries (`LOCAL_DOMAINS`), plus the workflow's `allowed_domains` input, the counterpart of local mode's `PENDULUM_LOCAL_DOMAINS`, and the hosts the Objective's own approved `pendulum:host:` labels name (`lib/local.mjs` `openStageHosts`). A worker that stops because the sandbox denied a host names it (`deniedHosts`), and the Blocked comment names both fixes: the host label for this Objective, the setting for every Objective. A worker secret's provider (an API host the pipeline calls with it) needs its host there too; an AI Gateway key goes through the gateway relay (Worker secrets), which needs none.
- **Nothing the agent can write is read or run by Claude Code's own start-up:** the repository's install and validation run as the agent outside Claude's sandbox, so they could write anything in the agent's home and the checkout's `.git`. So Claude Code runs with a HOME Pendulum owns (`/var/lib/pendulum-claude`: no shell start-up file, no git config, only an env file and Pendulum's skills and agents, which the agent reads and never writes) and a PATH with nothing of the agent's home; its shell snapshot (`bash -c -l`) therefore sources no file of the agent's. Its own `TMPDIR` is `/tmp`, which its unit (or `NAMESPACE_WRAP`) mounts afresh for every start; a directory in the agent's home would sit outside its working directories, where its sandbox cannot read it, and its commands would lose all network (#61). Its config directory is made afresh before every start, with only the session Pendulum captured right after the previous run put back (so a resume and the saved transcript use Pendulum's copy). The checkout's `.git` config, commondir, info/attributes and hooks are put back to what Pendulum left before the repository's install ran, and a replaced `.git` refuses the start. Its commands get the agent's own HOME and TMPDIR back inside the sandbox (`CLAUDE_ENV_FILE`), so caches and the agent's read-only `gh` login work as before. It starts with Pendulum's flag settings only (`--setting-sources ""`, hooks off, `--strict-mcp-config`) and its own git with no fsmonitor, and the checkout's harness settings are restored to the commit before every start (`lib/local.mjs` `clearHarnessConfig`): a hook or MCP server would run outside the sandbox as the same uid as Claude Code, which can read its process's environment.
- **What the routes change for it:** on GitHub's hosted runners the Action installs bubblewrap, socat and ripgrep and loads an AppArmor profile that lets `/usr/bin/bwrap` alone make user namespaces (not the global sysctl), unloading Ubuntu 26.04's `bwrap-userns-restrict` profile, which takes the capabilities the sandbox needs. It changes nothing on a self-hosted runner, where both would outlast the job and change the whole host: doctor fails until bwrap, socat and rg are installed and, where AppArmor restricts user namespaces, names the one-time admin step (the same profile, and `bwrap-userns-restrict` unloaded and disabled). A cloud sandbox's start and its image build install the packages; its VM has no AppArmor. Claude Code refuses to start where its sandbox cannot (`failIfUnavailable`): no command ever runs unsandboxed.
- **The services setup started are reachable at their usual ports, and nothing else on the machine is:** on Linux a sandboxed command's `localhost` is its own network namespace. Pendulum notes the TCP ports listening on IPv4 loopback or every address (IPv4-mapped forms included) before the repository's `setup` runs, and before each Claude start offers the ones that appeared since, never a socket the agent uid owns (at most 20; the log names any the cap drops): each `127.0.0.1:<port>` joins the sandbox's allowed hosts, and the env file Claude Code sources inside the sandbox before every command starts a relay on the command's own `127.0.0.1` and `::1` at that port, through the sandbox's proxy (HTTP CONNECT with its per-session login), so `localhost:5432` in `DATABASE_URL` reaches the database setup started. The task card names the ports offered, and says nothing about services when none are. Nothing outside the sandbox runs anything for it: the relay (`socat`) runs inside, and Claude Code's proxy only connects to the allowed `127.0.0.1` ports. A service that was already listening before setup, one listening on another address, or `::1` only, stays out of reach; a command that needs one of those ports for a server of its own finds it taken. Setup's loopback services are trusted: one that offers code execution (`node --inspect`, a Docker TCP API, a database with `COPY ... PROGRAM`) is a path out of the sandbox to the credential-holding uid, the same exposure the validation commands already have. (`excludedCommands` was no option: it would run the command outside the sandbox, credential included.)
- **Trade-off:** Claude Code's systemd unit on the runner runs without `ProtectKernelTunables` (`lib/claude-runner.mjs` `asClaudeAgent`): its read-only mounts over parts of `/proc` keep a user namespace from mounting a fresh `/proc`, so bubblewrap cannot start under it. The agent stays unprivileged, with no new privileges and no capabilities, so `/proc/sys` and `/sys` stay root's to write. Copilot's unit runs without it too (below); every other command the agent runs keeps the setting. `NAMESPACE_WRAP` in a cloud sandbox needs no change.
- **Why not `CLAUDE_CODE_SUBPROCESS_ENV_SCRUB`:** in Claude Code 2.1.322 it also forces the default permission mode and makes the working directory's `package.json`, lockfiles, `.npmrc` and `.env*` read-only to commands (so `npm install <package>` fails with EROFS) and leaves empty placeholders for the absent ones in the checkout. None of that is documented or can be turned off, and it would stop a worker changing dependencies. An `apiKeyHelper` is no option either: Claude Code runs it as the model's own uid and again every five minutes by default ([settings](https://code.claude.com/docs/en/settings-reference#apikeyhelper)), so whatever it reads, the model's commands can read.

Codex's sandbox on Actions and in a cloud sandbox VM holds the same bar (#90): local mode's profile fitted to the agent (`lib/codex-runner.mjs` `codexRunnerConfig`, `lib/harness.mjs` `codexRunner`, `lib/local.mjs` `codexLocalConfig`), in place of `--dangerously-bypass-approvals-and-sandbox`. Reason: the agent uid holds the credential in Codex's environment, and Codex starts git with its whole environment, so a command outside a sandbox read it from `/proc` (#87). No command can read the environment of a process outside Codex's sandbox, and `shell_environment_policy.exclude` still keeps every credential name out of its own. The mechanism: Codex's sandbox (bubblewrap and seccomp) runs each command in a user namespace of its own without `CAP_SYS_PTRACE`, so the kernel refuses its read of another process's environment (`cap_ptrace_access_check`), Codex's and its git processes' included. In the cloud sandbox VM bubblewrap also mounts a fresh `/proc` in a PID namespace of the command's own, so it sees only the sandbox's processes. Under the systemd unit on Actions (`ProtectKernelTunables`) it cannot, and Codex silently retries without one: `/proc` then lists the machine's processes, the reads are still refused (checked with fake credentials: 0 of 178 readable, and 0 hits from a reader racing Codex's git processes), and the host's world-readable `/proc` entries (`cmdline`, `status`, `net`) stay visible, a low exposure: other processes' command lines and the machine's sockets, never an environment. Codex 0.167 does not make its own process unreadable (non-dumpable), so the refusal is the sandbox's, which the probe below checks with a decoy before every start. ### Worker secrets

Off by default. A repository whose Objectives run a paid pipeline (image or 3D generation through an AI gateway) may give the worker's shell secrets of its own: `worker_secrets` (`PENDULUM_WORKER_SECRETS` in the workflow's env block, which local mode reads too) names them, each `NAME` or `NAME=SOURCE`, and the shell gets SOURCE's value as NAME. On Actions and in a cloud sandbox the values come from the `worker_secret_values` input, `SOURCE=value` lines that the template passes from the one repository secret `PENDULUM_WORKER_SECRET_VALUES` in the work, review and launch jobs (so a re-render of the workflow keeps it); in local mode from the shell that runs `pendulum serve` (`docs/LOCAL.md`). For example `PENDULUM_WORKER_SECRETS: AI_GATEWAY_API_KEY=WORKER_AI_GATEWAY_API_KEY`, with `WORKER_AI_GATEWAY_API_KEY=<a dedicated key>` in that secret, gives a pipeline that reads `AI_GATEWAY_API_KEY` the adopter's own key, through the gateway relay (below), which meters it against the Objective's caps.

- **The risk:** any code the worker runs, the repository's and its dependencies' included, can read the key and spend through it, and the worker can print it into a file or a commit. Use a dedicated key with a budget the gateway enforces (a Vercel AI Gateway key's spend limit), never a key shared with anything else, and rotate it if a run looks wrong.
- **Never Pendulum's own key or credentials:** a name that is a model credential, one of Pendulum's or the runner's tokens (`MODEL_SECRET_KEYS`, `RUNNER_SECRET_KEYS`, `GITHUB_TOKEN_KEYS`), a name Pendulum, the runner or a harness reads (`PENDULUM_`, `GITHUB_`, `GH_`, `ACTIONS_`, `RUNNER_`, `ANTHROPIC_`, `CLAUDE_`, `CODEX_`, `OPENAI_`, `COPILOT_`), or one that changes how commands run (`PATH`, `NODE_OPTIONS`, `LD_*`, `GIT_*`, proxies) is refused, and so is Pendulum's own `AI_GATEWAY_API_KEY` as a SOURCE: Pendulum's drift and triage key keeps its name and stays in Pendulum's process. A worker value equal to Pendulum's key is withheld (compared in constant time in Pendulum's process, never printed), and doctor warns about it, about each refused entry and about each SOURCE with no value (`lib/worker-secrets.mjs`, `doctor.mjs` `workerSecretChecks`).
- **Only the worker's shell:** the work lineage's harness runs get them: the work stage's (the work, conflict, fix and exit-record passes) and the review stage's fix and answer passes (with their scope and exit-record turns), which continue the worker's session, on every route and harness. They are carried to the harness process alone and removed from every other process's environment (`scrubbedEnv`): the repository's setup, install and validation and Pendulum's own git never see them. The reviewer never does: its calls are marked as the reviewer's, and `runHarness` gives such a call no worker secret and no variable holding an opted-in value, whatever environment it is handed (`lib/worker-secrets.mjs` `harnessShell`). The review stage's process holds the values while it runs, as the work stage's does, under the same redaction and push scan. In the model's commands an opted-in name is left out of the lists that hide credentials (Claude Code's `sandbox.credentials.envVars`, Codex's `shell_environment_policy.exclude`, Copilot's `--secret-env-vars`); the model's credential stays on every list. Local mode leaves a NAME or SOURCE that `PENDULUM_LOCAL_ENV` also names out of every stage's environment.
- **Never posted, stored or pushed by Pendulum:** Pendulum's process holds every opted-in value of eight characters or more (a shorter one would mask ordinary text, so it is not protected, and doctor warns about it by name) and redacts each one, in every form a text can carry it (itself, JSON-escaped, URL-encoded with upper- or lower-case hex, base64 at each byte offset), from every GitHub request body (the Blocked reason and its last output, questions, the plan, the PR body, replies, notes, the progress comment), the usage record, the drift advisory's input and its own log. The job log masks them (`::add-mask::`), and the uploaded harness stream and transcript are masked in the same forms. A `missingSecrets` entry equal to a value is dropped. A push whose commits (a change or a message) carry a value is refused before anything is sent, and the stage Blocks with Pendulum's own reason, which never quotes it. A mis-pasted key is never printed: names with a known key prefix (`vck_`, `ghp_`, `github_pat_`, `sk-`, `xox…`, and the like) are refused, the log and doctor name a NAME only, and never quote an entry over 40 characters.
- **A missing key Blocks with the opt-in named:** a worker that stops because its shell lacks a secret lists the variable names in its exit record's `missingSecrets` (names only; at most ten), and the Blocked comment names the fix: opt it in with `worker_secrets` and where its value goes on that route, or that it is opted in but had no value. A name no worker may have gets no such fix.

#### The gateway relay

An opted-in AI Gateway key (the NAME `AI_GATEWAY_API_KEY`) is never handed to the sandbox. Pendulum's stage process holds it and runs a metering relay for the stage (`lib/gateway-relay.mjs`, `lib/worker-relay.mjs`). A worker secret under any other name whose value has a gateway key's shape (`vck_…`), or `AI_GATEWAY_API_KEY` in another case, is withheld, and doctor warns: a gateway key is only ever relayed.

- **What the worker's shell gets:** `AI_GATEWAY_API_KEY` holds a per-stage relay token, not the key. `PENDULUM_GATEWAY_URL` holds the relay's address (`http://127.0.0.1:<port>`). The AI SDK reads no base-URL variable, so a pipeline sets it itself: `createGateway({ apiKey: process.env.AI_GATEWAY_API_KEY, baseURL: process.env.PENDULUM_GATEWAY_URL ? `${process.env.PENDULUM_GATEWAY_URL}/v4/ai` : undefined })` (`/v4/ai` is `@ai-sdk/gateway`'s own default path). An OpenAI- or Anthropic-compatible client takes `${PENDULUM_GATEWAY_URL}/v1`.
- **What it forwards:** only the gateway's generation calls (POST `/v<n>/ai/{language,image,embedding,decision,reranking}-model`, and the OpenAI- and Anthropic-compatible `/v1/chat/completions`, `/v1/responses`, `/v1/embeddings`, `/v1/messages`, `/v1/images/generations`, `/v1/images/edits`) and its model list (GET `/v1/models`, `/v<n>/ai/config`), only to `https://ai-gateway.vercel.sh`, with the key in place of the token. Every other path or method (`/v1/credits`, `/v1/generation`, a query string, a method override) is refused (403), as is a call without the run's token (401). Only an allowlist of request and response headers passes, and the key is cut out of every response in each form a text can carry it. An image edit's body (multipart form data with its reference images, as the AI SDK's OpenAI provider or `fetch` with `FormData` sends it, or JSON with data URLs) passes as sent, its content-type and boundary untouched, up to 128 MB (base64 reference photos add up: a four-photo turnaround is 38.5 MiB); the other calls take up to 64 MB. A body over its cap is refused (413), before it waits its turn when its declared length shows it. A body is read whole before anything is sent and must arrive within 5 minutes of being read; a call waiting its turn under a cap has no deadline while it waits.
- **Every call is priced from what the caller cannot write:** the gateway's own `providerMetadata.gateway.cost` (a string such as `"0.007"`) at the top level of an AI SDK answer, or on a stream's `finish` event, and the generation's cost looked up with the same key (`/v1/generation`) by the answer's top-level `generationId` or a stream's `x-generation-id` header; the larger counts. A reported cost is booked at once and the lookup reconciles it aside, since the gateway records a generation some seconds after the answer (retried for about a minute; a record that never comes leaves the reported cost standing). A stream's `finish` event's cost counts however the stream ended after it: a connection cut once the cost came is still a priced call. An image edit's answer is priced the same way from the gateway's `providerMetadata.gateway` at its top level when it adds one, and otherwise as an OpenAI- or Anthropic-compatible answer, which waits for the lookup by its top-level generation id or the `x-generation-id` header, as does one that reports no cost; an answer with neither fails closed (below). A request body the gateway echoes back (a tool's schema, a tool call's input) is never read. The gateway's refusals before any model ran (400, 401, 403, 404, 413, 422, 429) are not billed; should one name a generation all the same, that is looked up aside and a cost its record gives is booked. The 402, never-sent, 4xx, 5xx and redirect cases below cost $0 too.
- **The gateway's own budget or credits refusal is $0 and named:** a 402 whose body carries the gateway's error type for a spent budget (`quota_for_entity_exceeded`: a team, project, key or user budget) or no credits (`insufficient_funds`), at `error.type` or at the top level, is a refusal before any model ran, so it costs a known $0. The worker gets the gateway's answer as it came, the key cut. Every later billable call in the stage gets 402 at once, with the gateway's type, its message and `source: "ai-gateway"`, never sent. The pass is not over budget for it: the worker decides how to finish. If the stage Blocks, its reason and the progress line name the refusal first (`AI Gateway refused: quota_for_entity_exceeded (Team budget exceeded…)`, the message on one line, clipped, the key cut), and `result.json`'s `workerKey.gatewayRefused` records its type and message. Any other 402 is priced as any failed call (below). Pendulum's own cap refusal is a 402 of type `pendulum_max_usd` whose message says it is Pendulum's cap, not the gateway's budget.
- **A sent call runs to its end:** once a call is sent it is billed whatever the client does, so it runs to its end (with 20 minutes for the whole call) and is priced then, never aborted on a hang-up. Each call has a connection of its own whose socket probes the gateway once a minute (TCP keepalive): Node's own agent probes every second, and Vercel's edge stops answering after about 27 probes in a silent stretch, which ended a call still being worked on with ETIMEDOUT about 38 s in.
- **A call that cost nothing is $0, by structure, and is no unknown cost toward the shutdown below:**
  - *Never sent* (`unsent` in the call log): the request never left the machine, because its connection was never made (a refused or unreachable host, a name that does not resolve) or its TLS handshake never finished, before which none of the request is sent. The relay reads this from the socket's state, never from an error's text. Through an operator's proxy the TLS handshake with the gateway runs over the proxy's tunnel and is waited for the same way. A socket handed over already connected (a pooled one) may carry the request at once, so such a call is never counted so. The worker gets a 502 saying nothing was billed and the call can be tried again.
  - *Refused before any model ran:* any other 4xx whose `error.type` says so (`authentication_error`, `invalid_request_error`, `rate_limit_exceeded`, `model_not_found`, `not_found`, `forbidden`, `customer_verification_required`; never its status alone, never a type elsewhere in the body).
  - *No generation ran* (`unavailable`): a 5xx whose error type says so (`service_unavailable_error`, `overloaded_error`, `rate_limit_exceeded`, `rate_limit_error`) and that names no generation. The type is read at `error.type`, or at the top level of a body with no `error` object: the gateway writes both shapes, as for its 402.
  - *A redirect* (`redirect`): the relay follows none, and the gateway ran nothing to answer with one.
- **A failed call of unknown cost is counted as unknown, and relaying goes on (#142, #163, #483):** a call that failed once it may have been sent (a network error, a broken or truncated answer, a timeout, an error status with no type above such as `internal_server_error` or `failed_dependency` or none at all, a stream that ended with an `error` event and no `finish`) and that nothing prices is a call of unknown cost: never $0, never an estimate. It adds nothing to the dollars and nothing toward `max_usd`; the pass's and the stage's relay totals count it (`unknown`), the pass's usage record is marked as having unknown spend (`usdUnknown`, why `relay`), and the stage log says so. Spend the gateway did not report is never counted against the cap, so the cap can be passed by it. No count of such calls stops the relay or the stage: the stage goes on, and only the gateway key's own budget bounds what they really cost.
  - *One that names its generation* (the error body's top-level `generationId` or `id`, the `x-generation-id` header, a stream's first or `finish` event) is of unknown cost at once, so the next call does not wait, and when the `/v1/generation` lookup finds its record (its usual tries take two minutes at most) the record's cost is booked and the call is no longer unknown. With a cap, one such call at a time waits for its record: a second failed call that names its generation holds the turn until the first's record comes or its lookup ends, for 15 s at most (`HOLD_MAX_MS`); past that it goes on as a failure that names no generation, of unknown cost and never looked up. The cap is checked against reported dollars, and a record still to come leaves its cost out, so only one may be out at a time. A record that never comes thus holds each later failure 15 s at most. Without a cap nothing is checked against it, and the lookups run side by side.
  - *At a pass's end:* the relay waits for its calls in flight to answer (each up to the 20 minutes one call may take), then gives the lookups five minutes at most (`ENDPASS_LOOKUP_MS`). A call whose record has not come by then stays of unknown cost, and the record is never read. A complete answer whose price was still being looked up is then a failed call of unknown cost. So a pass's totals are final when given.
  - *What the count leaves out:* a failed call is rarely billed, but when one is, its cost is not in Pendulum's dollars or its cap: it is shown as unknown. The cap is checked against reported dollars, so key spend can pass what `max_usd` left by the cost of the call sent last, and by whatever the calls of unknown cost really cost; the gateway key's own budget bounds what is really spent.
- **A complete answer that cannot be priced is a call of unknown cost:** a whole 2xx answer that names no cost and no generation, or whose generation has no record, was billed, so it is a call of unknown cost, like a failed one, and relaying goes on. A lookup that itself fails (a 5xx, a 429, a network error: anything but a cost or "no record") is tried on first: the relay keeps trying, holding the turn, every 15 s or as its `Retry-After` says, for ten minutes, half of what one relayed call may itself take (at a pass's end, within the five minutes above). An answer too large to read its cost is priced by its `x-generation-id` header's generation when it has one.
- **The call log:** each call the relay answers is one JSON line in the stage's usage directory (`relay-calls.jsonl`, which no sandbox writes, mode 600): its time, method, relayed path, model (the allowlisted model header, else a JSON body's or a form's `model`, kept only with a model id's shape: `provider/name`, at most 80 characters), status, the dollars booked (null for a call of unknown cost) and how (`reported`, `lookup`, `refused`, `unsent`, `redirect`, `unavailable`, `gateway-refused`, `unknown`), its generation id, why it was not priced, or why the relay refused it (a route it does not relay is `refused: route`, never the path asked for; a call whose client hung up while it waited is `refused: gone`, never sent). Never a body, a header's value, a message or the key, and the stage's held secrets are masked in it when the stage ends, as in `events.jsonl`. At most 2,000 lines; one closing line counts the calls past them. A lookup that settles later adds a line of its own, with `reconciled`, the dollars it changed the booking by: one that raises a reported cost, one that prices a refusal's generation, and the one for a failed call of unknown cost (its record's cost, or 0 when no record came and the call stays of unknown cost). `result.json`'s `workerKey` summarises it: the calls of unknown cost (`unknown`) and `callLog` (the file, its line count and any calls left out).
- **The cap is live on the key's reported spend:** calls are relayed only while a pass runs. With a cap, billable calls go one at a time (at most 8 wait their turn, more get 429 with a `Retry-After`; a pass's end refuses those still waiting, and one whose pass ended while its turn came; one whose client hung up while it waited is never sent), each only once the one before it is priced or known to be of unknown cost, and only while the pass's spend through the key, as the gateway reported it, is under what `max_usd` left when the pass started; past it the relay answers 402 with a message the worker sees, and the pass counts as over budget, so the stage stops or Blocks as when the harness reaches its own cap. The harness's own spend in a running pass is not read here: Pendulum counts only what a harness reports, when the pass ends, so the key and the model can each spend up to what was left in the same pass. Key spend can pass the cap by the call sent last and by what calls of unknown cost really cost (above). A parallel pipeline is serialised while a cap is on: N concurrent calls take about N times one call's time. With no cap nothing is serialised, and each call of unknown cost is still counted.
- **How commands reach it:** the relay listens on a Unix socket in a directory the agent cannot write (a directory of the stage's own under `/var/lib/pendulum-relay` on a runner and in a cloud sandbox, the socket group-readable by the agent at 660, removed when the stage ends). Locally, and in a developer's own session, the socket goes in a short directory of the stage's own, `/tmp/pendulum-relay-<uid>/<12 hex>`, named by a hash of the stage's usage directory: both levels 700, the socket 600. A Unix socket's path is limited to 107 bytes on Linux (103 on macOS), and the usage directory's path grows with the checkout's. `/tmp` (its real path) must be root's with the sticky bit, which alone keeps another user from swapping this user's directory there between Pendulum's checks and its listen; otherwise the stage Blocks before the run, naming why. A per-user directory that is a link, a file, another user's or open to others is refused, and the stage's socket goes in a private directory instead, `/tmp/pendulum-relay-<uid>-XXXXXX` (made by `mkdtemp`, 700). Locally `serve` makes the directory before the stage starts, records it in the stage's usage directory, names it in the outer sandbox and hands it to the stage, which takes no other; a stage that relays nothing has no socket directory reachable. After the listen the stage confirms the socket is in the very directory it checked, or Blocks before any command starts. The directory is removed when the stage ends; one a dead stage left, `serve` removes when it reaps the stage, and only if it still passes those checks at every level. A socket path that would still pass the limit Blocks the stage before the run, naming the limit. Claude Code's and Codex's sandboxes start every command with the `bwrap` first on PATH. Pendulum puts its shim there (`lib/relay-shim.mjs`, `bash -p`, builtins only), which starts a forwarder on the command's own network namespace's `127.0.0.1:<port>` to the socket before the command runs; it walks bubblewrap's options by their arity, so only `--unshare-net` before the command's separator marks a command sandbox. The harness's network policy, proxy and seccomp filter are unchanged; the forwarder carries one port to the relay alone, and the commands themselves cannot open the socket (both harnesses' filters refuse Unix sockets). Copilot's own bwrap shim (`lib/copilot-runner.mjs` `bwrapShim`, already first on its PATH) hands each call to the relay's shim for Copilot, at a path in the stage's own relay directory written into Copilot's shim for the stage (on a runner and in a cloud sandbox once the relay opens, locally by `serve`), never read from an environment; concurrent stages on one host each hand to their own, and a Copilot stage removes the one shared path an earlier Pendulum used. For a Copilot command sandbox that shim also binds the socket's directory read-only and sets `NO_PROXY`/`no_proxy` to `127.0.0.1`, so loopback stays off Copilot's proxy and reaches the namespace's own forwarder. `allowLocalNetwork` stays false and Copilot's host allow-list is unchanged. Copilot's filter lets commands open a Unix socket, so a Copilot command can reach the relay's socket directly too: it is the same relay behind the same token check. The worker needs no egress to the gateway's host. Locally the outer sandbox keeps the socket's directory reachable, never writable; it is the one socket directory it does not hide.
- **Probes and fail-closed starts:** before a stage's first relayed Codex pass, Codex's own sandbox (`codex sandbox`, the run's profile, the shim on PATH) must reach the relay's ping, or the stage Blocks (`relay`) before the run. Copilot's probe before every start (Copilot's sandbox, above) gets a rule of its own: a command in Copilot's sandbox reaches this relay's ping through the forwarder, or the stage Blocks (`relay`). Each command sandbox's forwarder pings the relay when it comes up, and a pass whose commands ran with no ping is logged. On a machine without `bwrap` or `socat` the stage Blocks before any run, with the key out of the shell. Pendulum never falls back to handing the key over.
- **Other opted-in secrets** keep the behaviour above: they reach the worker's shell as they are, and rely on their provider's own cap.

#### The worker's state directory

`PENDULUM_STATE_DIR` names a directory outside the checkout for the worker's own state: `pendulum-state` in the temp directory its commands share, which every sandbox lets them write and which lasts the stage. A pipeline may keep a ledger there, but such a ledger is advisory. The model can write it too, and Pendulum's own count above is what caps spend.

`credential: plan` with `CLAUDE_CODE_OAUTH_TOKEN` is allowed on a developer's own repository only; doctor warns that plan limits assume ordinary individual use. `credential: login` (the CLI's own login) is for a developer's machine and is refused inside Actions. Local mode and `/pendulum:pendulum-run` run on the developer's own harness login. Pendulum never stores, brokers or pools a subscription token. Reason: API billing makes `max_usd` and `daily_usd` real numbers, and the vendors' terms limit plan tokens to ordinary individual use.

## How an Objective flows

1. **File.** A writer opens an issue stating the Objective (goal, acceptance entries under an Acceptance heading, sources, context, recorded decisions) and a maintainer applies `pendulum:objective`. The Project card is Queued. An issue with `pendulum:draft` is a draft: no route runs it, its Objective label on or not, until a person takes the draft label off and applies `pendulum:objective`. `lib/stop.mjs` decides it: the dispatcher, the launcher, the worker, the review job, the merge pass and the local loop's resumes and reviews read `stopCause`; `pendulum run`, `pendulum issue` and `pendulum deliver` refuse on `isDraft`. A work stage plans by the later of the label's last application and the draft label's last removal (`objective-trust.mjs` `startedAt`), so a draft edited after an earlier plan is planned again once started. Blocked-by relations on the issue are the only dependency graph; an issue closed by any route counts as done.
2. **Dispatch.** The dispatcher, ticked by events (any issue closing among them, since it may block an Objective) and by Pendulum's own jobs, with GitHub's `*/10` cron as the backstop, picks ready Objectives by priority label and starts work up to `max_concurrent`, stopping at `daily_usd`. A pick whose known files (its open PR's changed files, its plan comment's `Files:` lines) overlap an active sibling's starts all the same, saying so on its issue: it has work of its own to write, and waiting would hold that whole stage where starting costs at most one rebase. What waits is the hand-off: a head no review has seen that conflicts with the head of a sibling ahead of it (In review, or through its own wait and rebasing, or waiting since earlier), by a trial merge of the two heads against the default branch (git merge-tree in a scratch mirror), when Pendulum merges, gets its review label only once no such sibling is ahead (for 6 hours at most from the Objective's first wait), after its rebase if it conflicts by then. Waiting PRs go one at a time in the order they began waiting, so each rebases once and two such PRs are never reviewed or queued at once (`lib/overlap.mjs`; `docs/USAGE.md` "Siblings that touch the same files"). The card moves to Running.
3. **Work.** The worker checks out the default branch, runs `setup`, installs the versions the lockfile pins (online, with no credential in its environment; npm, pnpm and yarn skip install scripts), renders the task card and starts the harness with the issue text verbatim. The harness writes its plan, implements, rebases, validates and commits, and leaves its plan, PR text and exit record as files. Pendulum posts the plan, pushes `pendulum/<issue>` and opens the one PR. With required checks configured (`ci_checks`) and a work pass that ended well, Pendulum does not wait for the checks on that head: once the push is done (on the local route, once its validation commands are green on the machine), it marks the PR ready with a hand-off marker (`<!-- pendulum:<issue>:handed-off:<sha> -->`) instead of the validated one and applies the review label, so the review starts while the head's first required-check run is still going. A send-back's rebase, and a pass whose harness ended in an error (green checks are what outweigh it), wait for the checks in the work stage. With cross-OS CI on (`cross_os_workflow`, `cross_os_checks`; INSTALL.md, Cross-OS CI), the work stage then dispatches the repository's named CI workflow on the branch (in a cloud sandbox, through its launcher job, which dispatches only that workflow on the stage's own branch and head and hands the run's id back) and waits, within `cross_os_wait_minutes`, for the macOS and Windows legs it lists, on every route; a red leg goes to the fix pass as any validation red does, a head a fix pass made gets the other validation again first, and only once the legs are green does the hand-off or the validated marker follow (`lib/cross-os.mjs`). The card moves to In review.
4. **Review.** The reviewer posts findings as PR review comments. On a head handed off with its checks running, the review stage waits for the checks beside the reviewer (Review and merge, below). The worker gets the comments once, with any red the checks showed, and addresses or rebuts each in a reply file; Pendulum pushes its commits, posts the replies, and validation runs again.
5. **Merge.** Pendulum merges the reviewed head once its required checks are green, through the merge queue where there is one. A red integrated run whose failure is in the PR's own change gets one fix pass, as a red PR check does, before any Block: one per failure class and two in all per re-entry, so the same failure red again after its fix pass Blocks. A red integrated run that is a flake, GitHub's side or the default branch's, or that cannot be read or (with triage off) named as the PR's, and any other drop, goes back to the queue once; a second is Blocked (Review and merge, below). So a repository may run a light check on the PR and its full suite only in the merge queue. A PR that conflicts because other PRs merged (when its review reaches the merge, or in the merge queue) is sent back to the worker for a rebase each time the default branch has moved since its last rebase: a new base is progress. When Pendulum merges, the PRs that conflict go back in the release order (priority, then number): one whose head conflicts, by a trial merge, with that of a sibling ahead of it in that order that will merge first (In review, or rebasing after its review) waits for that merge, since a rebase now would be undone by it, for 6 hours at most counted with any hand-off wait before it, with a record on the PR and a note on the issue (`lib/overlap.mjs` sendBackOrder). Each send-back is its own work stage, with its own `max_usd`; its notice on the PR says which rebase of the 24-hour bound it is, and its progress comment carries a `<!-- pendulum:rebase-cost -->` line (its known dollars, 0 for a clean rebase, its runs of unknown cost as its spend line carries them, and whether it was a conflict pass) beside the Objective's rebase total so far. It Blocks, as the work's, only when rebasing cannot progress, or at the bound. The worker records each rebase of Pendulum's that conflicts on the PR (the head it started from, the base and the files), and before anything of its conflict pass is pushed it checks the checkout: a rebase, merge or cherry-pick left in progress, a head that does not contain that base, or a change of the branch missing from it Blocks naming the files and each path whose change is missing (with the branch's commits that changed it, and why), with nothing pushed. That is decided on the branch's net change, its merge base with the base to its head, merges included, never on commit ids, authors or subjects, so a rebased or squashed branch, or one with a commit of the worker's joining it to the default branch, goes out when it keeps the work. The net change is replayed onto the base (`git merge-tree`, with git's rename detection, so a file the default branch renamed is checked under its new name) and merged into the head: every path that replay conflicts on and every path that merge would still change is checked, and nothing else is the branch's. Such a path is kept when the head has exactly the branch's version of it, content and file mode. The file mode is decided on its own: a mode the branch's change sets and the head lacks is named, whatever the content. A binary or Git LFS file, a submodule or symlink, and a file git cannot merge the branch's change into (one the head moved or removed, or kept with edits where the branch deletes it) are decided exactly, never by the model. A change of the branch with no hunk is decided exactly too: two different blobs (git reads one as binary, the base included) are named, a file the branch only puts under a name (one side of a rename) or adds empty is named when the head has no file there, an empty file it deletes is named when the head keeps it, and a name the branch's change does not have is no loss. Any other text file goes to the decision model (with a key, `triage_model`; else the stage's harness: Red-check triage below), four files at a time. The branch's change is, for a file the replay conflicted on, its side from their base; for a file where merging the branch's change into the head conflicts, its side of that merge; for any other, what that merge would still change there. Its hunks, whatever the size of the whole diff, go in one question with the file as the head has it: whole, or, over 32 KiB, for each hunk the 60 lines either side of where its lines are in the head (from the first line, for a file the base did not have), reaching past every line its new side has. A question holds at most 64 KiB: more goes in groups of hunks packed in order up to that, each group with the file or its hunks' lines, the groups asked at once (four questions at a time across the check). The question is whether every hunk's effect is still in the file, as written or adapted to the default branch's code, other changes and additions allowed; each part is delimited, with the path, as untrusted data the model is told not to follow. `kept` at the confidence floor or more (Red-check triage, below) keeps the file. Anything else, for a question of several hunks, asks each of its hunks alone, sent with the file or its lines again, in order, and names the file with the first hunk not kept; no further group starts. When every hunk alone is kept, the question's hunks are kept after an unsure answer for them together (`kept` or `lost` under the floor, or none), and the file still named after a `lost` at the floor or more. A hunk whose own question (the hunk with the file, or with its lines around it) is over 64 KiB is not judged: the file is named with each such hunk, and its other hunks are not asked. A path past the first 40 or the check's 3 minutes names the file. On the local route, a conflict pass the check stops is kept on the branch `pendulum/<issue>-conflict-pass` of the Objective's clone, `.pendulum/<issue>/repo` (the last one only: a later push of the branch removes it, and so does a later Block with nothing to keep, which says so), and the Block gives its full sha and how to deliver it: check that it keeps the Objective's change and touches no secret or protected path, since Pendulum's push checks did not run on it, then `git push --force-with-lease origin pendulum/<issue>-conflict-pass:pendulum/<issue>` in that clone and re-apply the Objective's label; the stages after it validate and review that head like any other. A file the branch's commits changed and then undid, which the head changes anyway, is no loss: when the branch goes out, a line on the progress comment says so for the review. With no decider (`decision_route` off, or `gateway` with no key), a path not exactly the branch's falls back to matching the branch's commits in the head by author, author time and subject (a commit git dropped because the base already has its change is no loss), as does a stage with no decider whose git is older than 2.40; with a key, such a git Blocks naming its version. The check asks whether the branch's change is still there; whether the joined code still works (a call to something the default branch renamed, a semantic clash that keeps every line) is for validation, CI and the reviewer. As a fallback, the dispatcher Blocks, naming the files, a PR that still conflicts while the default branch is the base the last pushed rebase was made onto. The bound is 5 rebases in 24 hours by default (`rebase_limit`), so two Objectives cannot chase each other forever; a batch of five parallel Objectives has at most four siblings merging ahead of one. Only Pendulum's own markers and records count, and a tick that cannot read them, or the Objective label's time, holds the PR until the next. A PR that only fell behind and whose update-branch GitHub fails for now waits for the next tick; one GitHub refuses goes to the worker under these rules. A PR the merge queue takes out for a conflict with a PR ahead of it counts as no drop: Pendulum puts it back once no PR in the queue conflicts with it, by a trial merge of the two heads against the default branch (git merge-tree in a scratch mirror), and at once when a trial merge cannot be computed (the queue then answers). Each time it goes back in, Pendulum records on the issue the queue's state then (the default branch's head and every entry's head); taken out for a conflict again, it goes back in only once that state has changed, so a conflict pairwise trials cannot see (one with the queue's merge group) never loops. This is the same on every route and harness: nothing is enqueued for a conflicting PR, it stays delivered, and the send-back takes it (`pendulum run --wait` does the send-back itself). The card moves to Done and the issue closes.
6. **Blocked.** The PR becomes a draft, the card moves to Blocked, and one comment states the reason (validation failed twice, reviewer findings unaddressed, dollar or time cap reached, worker died twice, rebasing makes no progress or reached its bound). The queue does not wait. A human fixes it by pushing to the branch or editing the issue and re-applying the label; a local Block on hosts the sandbox denied names them and its own fix (Exit: blocked, below).
7. **Stopped.** A person removes `pendulum:objective`, applies `pendulum:draft` or closes the issue. Nothing lists a stopped Objective for a start (the dispatcher, the local loop's resumes and reviews, the sandbox launcher, the review job). A running stage reads its issue once a minute and on the stop ends every harness pass (`lib/stop.mjs`), records the spend so far and exits with `exit: stopped`; from the stop on it starts no pass, command, push or PR change, and it writes its usage and spend line before any other GitHub call (at two minutes it writes what it knows at once and exits). A pass ended before it reported dollars, or still running, is a run of unknown cost, as on the spend line. A cloud sandbox stage that its launcher process ends instead (its wall clock) records the stage as a run of unknown cost too (`stage.mjs` `killedUsage`), never `max_usd` or another bound, so `daily_usd` names it without counting it. A stop racing the stage's own exit (one being applied, or its merge) ends nothing, and the merge pass reads the issue before any merge, so a stopped Objective never merges; its PR leaves the merge queue and becomes a draft without `pendulum:review`, and its state label and card go back to Queued. The dispatcher does the same for a stopped Objective In review, and for a Running one ten minutes after the stop. Re-applying the label continues it, as after a Block.
8. **Restarted.** A person who can push (or a named maintainer) applies `pendulum:restart`, in any state; anyone else's label comes off with a comment. A running stage stops as in 7; one that missed the label learns of the restart from its record, newer than its start, at its watch and before it pushes or writes its exit. The dispatcher of the Objective's route holds it while a stage of it may run, whatever its state (an Actions work or review job, a sandbox lease, a local loop's live claim; a read that fails counts as may run), for at most 10 minutes from the label; no merge or send-back touches it, and the merge pass reads the issue before any merge. Then it writes a restart record on the issue (the label's time, who applied it, the earlier PR and the branch's last commit, kept across a retry), which says first what the restart discards: the PR with its review, the branch's commits with the command that restores them, and the spend on them; takes the earlier PR out of the queue, deletes `pendulum/<issue>` (read back: a ruleset that keeps it Blocks the Objective with the fix), comments on and closes the PR, renames the plan comment's and the parts record's markers, removes the state labels and then the restart label, and queues the Objective: the next run starts from the default branch and the issue's current text. A maintainer comment, a plan comment or a parts record made before the label's time is read by no stage any more (`logic.mjs` `maintainerDecisions`, `handoff.mjs` `planOf`, `partsRecord`). Every retry and rebase count starts over with the new PR and Running stint. Until then nothing starts it: the dispatcher holds it, and the launcher, the review job, the worker and the local loop skip it.

## The task card and the skills

The worker's instructions are a short task card (`plugin/templates/task-card.md`, rendered per run: issue, budget, the three exits, what to leave where, no questions) plus skills loaded when their step is reached: `pendulum-objective-plan` (the plan comment, assumptions, the Question rule), `pendulum-implement-split` (implementer sub-agents, disjoint-file parallelism, sequential PRs for large Objectives), `pendulum-prove-acceptance` (real-path proof, no weakened tests, the base-failure rule, the budget command), `pendulum-deliver-pr` (rebase, the PR body, reviewer replies), `pendulum-review-pr` (the reviewer's own) and `scoring`. All three harnesses read the Agent Skills format. Agent definitions are written three ways from one source (`plugin/agents/source.json`, `node plugin/agents/render.mjs`): Markdown for Claude Code (with a pinned `model`) and Copilot (a `model` only when `subagent_model`, or for the reviewer `reviewer_model` or `model`, is set), TOML for Codex. Where a model is pinned, it is in the file, never passed at spawn time, because Codex drops a spawn-time model for role agents. An adopter overrides a skill by placing one of the same name in their repository, and adds their own.

## The worker contract

|  |  |
| --- | --- |
| Inputs | The rendered brief (validation and budget commands, base commit, issue number, dollar and time budget filled in); the issue body verbatim; the repository at the default branch, fetched, with `setup` run and dependencies installed from the lockfile; `$PENDULUM_IN`, what GitHub holds for this stage, rendered by Pendulum before each pass; the pinned implementer and reviewer agent definitions written into the checkout; on every route the harness's environment, which the commands it runs inherit (credentials excluded), carries `PENDULUM_ISSUE` (the Objective's issue number) and `PENDULUM_BRANCH`, a stable contract a repository's own tooling may read, for example to key per-Objective spend limits. |
| Outputs | Commits on `pendulum/<issue>` and the hand-off files in `$PENDULUM_OUT` (plan, PR title and body, replies, blocked note, exit record, and a workflow hand-over's patch, which Pendulum applies and publishes as git's own diff, never as written: Workflow hand-over, below); the usage record the harness emits, which the job uploads as an artifact for the scorecard. Pendulum reads each file as the agent through a pipe (a regular file under a size cap, never through a symlink), escapes every `<!--`, strips closing keywords, neutralises @-mentions and a leading `/`, adds its own markers and the issue link, and makes every GitHub write: the push, the PR, the plan comment, the replies, the note, labels and the exit. |
| Allowed | Any file not on the protected list (`.github/`, `CODEOWNERS`, `.agents/skills/`, `.claude/`, `.codex/`, the files the `setup` command names, plus the repository's `protected_paths`), and anything else but what the `setup` command runs (ADAPTERS.md, Setup is trusted like CI). Any command the runner allows. Sub-agents on the pinned model. Network: the hosts the harness's sandbox allows (GitHub, the npm and Yarn registries, plus `allowed_domains`; locally `PENDULUM_LOCAL_DOMAINS`). |
| Not allowed | Asking. Editing a test to pass it unless the issue asks. Workflow hand-over. Pendulum never pushes a change under `.github/workflows/`, on any route or harness: `.github/` is a protected path, and GitHub refuses a workflow file from a token without the Workflows permission, which neither the Pendulum App nor local mode's token has. Granting it is no part of this: a worker that can write workflows can run any code with the repository's Actions secrets on the next push. An Objective that needs such a change is told so, and that part goes to a person:

- **Up front.** Before any harness runs, so before any model spend, the work stage reads the issue's title and body for a path under `.github/workflows/` (the directory itself included) and, finding one, posts the hand-over notice on the issue: Pendulum will hand that part over, and to have it delivered whole instead, stop the Objective, land the workflow change yourself and start it again. That reading is a hint, not a promise: most needs are not named by path. The plan names each workflow file it needs on a `Needs-Workflow: <path>` line (pendulum-objective-plan), and Pendulum posts the same notice when it reads such a plan (it reads plan.md at most every two minutes while the harness works), so after the plan's spend, while the harness goes on with the rest, unless a notice is already there. A need found later, while working, still takes the same path below. The pendulum-file skill says it when an Objective is filed.
- **The hand-over.** The worker keeps workflow files out of its commits (the commit hook refuses one, naming the hand-over) and leaves the change as git's diff in `$PENDULUM_OUT/workflow.patch`, the reason under the PR body's `## Undone` (pendulum-deliver-pr). Pendulum never publishes the worker's text. It applies the patch for real (`git apply --cached`) to a scratch index of the branch's tree as GitHub has it (the default branch's when there is none), in its mirror, and reads the changes back from git (`git diff-index --raw -z --no-renames`). It accepts only files added, changed or deleted under `.github/workflows/`, each name of `[\w./-]` characters only with no empty, `.` or `..` segment, each a regular file before and after (mode 100644 or 100755). A rename or copy in the worker's patch (git's own `--summary`), a symlink, a submodule, a type change, any other mode and any file outside the directory are refused. What it publishes is git's own diff of those files (`git diff-index -p --no-renames`, no external diff, textconv or colour), refused when it, or the worker's patch, carries a binary change, a control character other than a newline or tab, a format character (bidi, zero-width), a line or paragraph separator (U+2028, U+2029), `<!--`, or more than 30,000 characters. A refused patch is not published and the stage Blocks with the reason (cause `work`); a session's `pendulum deliver` refuses it instead, after pushing the branch.
- **Where it goes.** The hand-over is Pendulum's own comment on the issue (`<!-- pendulum:<issue>:handover -->`, the same comment as the up-front notice): the files git checked, the patch in a fenced block, how to apply it and the same steps by hand, every value in them shell-quoted. The issue gets the `pendulum:handover` label. That comment with that label is the hand-over, never text in a pull request's body, and the only command to run for it is `pendulum handover <issue>`: the comment and the PR body's first line, Pendulum's, pointing to the comment, both say so. As best effort only, since nothing there is run, the harness's text after that line has a heading that names the workflow hand-over shown as text, and a code fence, `<details>`, `<pre>`, `<script>`, `<style>` or `<textarea>` it leaves open closed before Pendulum's closing line; Markdown has too many ways to write a heading for this to stop a forged one. A person's text in the PR body survives a publish that keeps the body. The label and the comment are put right on every publish, so a write GitHub refused is made again on the next, except that once the label is taken off after Pendulum last applied it, by Pendulum's own login (in local mode the operator, as whom Pendulum posts) or by someone whose repository permission, read now, is write, maintain or admin, the hand-over counts as applied: a pass that keeps it leaves the label off and the PR's line says the change was applied. A triager's or another bot's removal, or one whose permission cannot be read, does not count, and the label goes on again. A new hand-over puts it on again. A later pass, the review's answer pass included, gets the published patch as `$PENDULUM_IN/workflow.patch`; a pass that writes none keeps it, an empty one drops it: the label comes off, the line goes, and the comment says the PR carries none. A PR that ends with no hand-over has an up-front notice corrected the same way.
- **Applying it.** A person runs `pendulum handover <issue>` in a clone (the pendulum-handover skill does it on request). It trusts a hand-over comment by its author, who must also have applied `pendulum:handover` at some time (anyone else's labelling, a triager's relabel included, changes nothing): the Pendulum App the person names (`--app <id>`, or `PENDULUM_LOCAL_APP_ID`: the repository's `PENDULUM_APP_ID`, which the App's settings page shows; GitHub's own `performed_via_github_app` on the comment must give that id and the author must be that App's `<slug>[bot]`), or a person, never a `[bot]` login, whose repository permission, read from GitHub now, is write, maintain or admin (local mode's operator, who posts Pendulum's comments, is one). `github-actions[bot]`, which any workflow can post as, is refused outright; any other App is named only as not verified, and its id is never offered as the one to pass; a triager or anyone else is refused, and so is a permission that cannot be read. The newest trusted comment is taken. The committed `pendulum.yml` names the App's id only as a secret, which is why the person names it. It says whose comment it is before anything else, checks it again the same way against the default branch as fetched now, puts git's result on a new branch `pendulum-workflow/<issue>` from the default branch (when the branch cannot take it, the clone goes back where it was and the branch is deleted), shows `git diff --cached` and stops, with nothing committed or pushed: a workflow runs with the repository's secrets, and one that runs `on: push` runs as soon as its branch is pushed. Once they have read it, `pendulum handover <issue> --push` takes and checks the hand-over again, goes on only when the staged change is exactly that, commits with hooks off, pushes the branch and opens its pull request with `gh`, whose body names the Objective (`Refs #<issue>`, never Closes), links Pendulum's hand-over comment and says the person reviewed the workflow change before pushing it. It runs no shell, and refuses a dirty clone and an existing branch.
- **The state it ends in.** The PR is reviewed (the reviewer gets the published patch, and the pendulum-review-pr skill names what to check in a workflow: triggers, `permissions:`, secrets, unpinned actions, checkout of pull-request head code), validated and merged like any other, and the Objective's other outcomes land. Merged, the Objective is done with a person's step pending: its issue is closed and moves to Done, and keeps `pendulum:handover`, which the person removes once the patch is applied. When the harness ended well, the worker's record says delivered and there is nothing but the hand-over to push, there is no PR: the comment carries the hand-over, the issue gets the label, and the Objective Blocks with cause `setup` (the token's permissions are the owner's setting). A worker's own Question or Block, a cap or a failed harness keeps its own exit, and nothing is posted on the issue for it.
- **The scorecard.** Each merged PR whose body carries Pendulum's hand-over line (each part of a split Objective) leaves a person's step. By default, for every repository, it is normal work: with Pendulum's hand-over comment on the issue the Objective can still walk away, and the step is an owner step shown apart with its own minutes from a stopwatch; `--handover input` scores it as a person's action, asked for, instead (bench/README.md, Workflow hand-over).

Trust. Pendulum acts on an Objective's text only when the issue's author, its last editor once the body was edited, and the person who made its latest rename once the title was renamed (that rename naming the title now) can push or are pinned maintainers. The worker and the review job check it before any harness on every route (Actions, local mode, a cloud-sandbox stage), acting on the title and body read with those people; a session reads the issue only through `pendulum issue`, and `deliver` and `post-review` check it again. Otherwise the stage Blocks before a harness sees the text. Pendulum acts on a marker (validated, rebase, review, spend, decisions-read, a local claim) only from its own login or from a person with push access. Its own login comes from its token, never from a comment's author: the App's bot on Actions, the token's owner in local mode. No other App counts, the job token's `github-actions[bot]` included. The workflow's `notify` and `maintainers` are written `login#id` and trusted by the numeric id, so a login renamed away is a stranger; doctor warns about a bare one and names the id to add.

Edits. The plan comment records the Objective text its plan was made from, on its marker line, written only by Pendulum: the SHA-256 of the title and body (line ends as LF, trailing whitespace dropped, so a save that changes nothing else is no edit), the time of the latest `pendulum:objective` label event, read before the text, when a work stage last started from that text, the text itself (title, body and harness, model and host labels: an edit's before) and the edit check's verdict for each later text, by its hash, as GitHub's 65,536-character limit leaves room for them, counted in UTF-8 bytes: the verdicts go first (they are asked again), the text only when it does not fit alone. In the record, `<` and `>` are JSON escapes, so no text in it closes the comment. A write of the plan comment keeps the verdicts another process wrote on it for the same text since this one read it. The plan comment read is the newest written by Pendulum's own login or a person who can push (local mode writes as its developer). No other App's comment counts, `github-actions[bot]` included: it never stands in for that comment. Only when there is none, the earliest App comment carrying the marker (Pendulum's App, read from a local process) counts for its time, so the stage decides on edit times (below) instead of on no plan; its text and any record in it are never read. After the trust check, each work stage and review job compares the text it read with that record before anything is set up for it, and the merge pass compares the text as it stands before it merges or enqueues, and while the PR waits in the merge queue (it is taken out of it). The same text goes on. A changed text is first judged by the edit check (`lib/edit-check.mjs`), a decision call asked once per distinct new text, its verdict written on the record: given the title and body before and after, does the edit change what has to be built? `wording` (typos, formatting, rewording only) at the confidence floor (Red-check triage, below) keeps the plan and the code: the stage goes on as on the same text, says so in one line on its progress comment (the verdict, the decider that gave it and its confidence), and the record still names the text the plan was made from, so the next edit is judged against that text too, and a work pass paused in local mode is held to that text (`lib/continue.mjs`) and continues. Any other answer, or none, is the rule below. A harness, model or host label added, removed or changed is a changed requirement as it stands, never asked about. The edit check is asked only on text that passed the trust check (its author, last editor and latest title renamer). A record without its text (one written before the record kept it, or one too long for the comment), a text whose hash is not the record's, a text too long to show the decider whole, or no decider (`decision_route` off, or `gateway` with no key) is never judged; with `decision_route` off a verdict the record keeps is not used either, and any verdict is used only after the same checks on the text now. A work stage started by the Objective label applied after its plan's record asks nothing and makes the plan again, a kept edit or not: the label is a person's own word. Where it is asked: a work or review stage asks at its start, once its harness, account and credential checks pass and before anything acts on the text, on the stage's decider (the gateway with a key, else its own harness on a credential read of its own, masked in what the stage saves: a federated key comes with no expiry, so the passes read theirs as they start, never one minted before setup and install); the merge pass, which has no stage harness, asks the gateway when its process holds the key (local mode's `~/.config/pendulum/ai-gateway-key`) and the route allows, and says a kept edit on a progress comment of its own; else, when another process may judge it (a stage's harness on `auto`, or on Actions a stage job's key on `gateway`), it puts the review label back on so the review stage's start judges it (on Actions the dispatcher's job holds no key, so it always does), and otherwise (`gateway` with no key, locally) Blocks; a session's `pendulum issue` and `post-review` ask the gateway only and write no verdict, and `deliver` writes the plan with the plan's own record when the edit was kept. Otherwise a changed text Blocks (cause `work`: an edit is a person's action) and the PR becomes a draft, unless the stage is a work stage and the label was applied again after the recorded time: then the plan is made again from the new text, the earlier plan comment is not handed to the harness, and the branch and PR carry over. A plan comment whose record cannot be read (none, one that does not parse, another App's) is decided on GitHub's edit times instead: a body edit (`lastEditedAt`) or a title change after the comment was posted is a change, and the label applied after that edit plans again. There a save that changed nothing still counts as an edit, since only a record's hash can tell; a plan comment without a record gets one at the next work stage. With no plan comment, a stage uses the text as it is, and a stage that knows no record never erases one. Comments are never edits. Pendulum's own login must be known for any of this; when it cannot be read, the stage stops. On a session's route, `pendulum issue` writes `plan.md` beside `issue.md` only when the plan was made from the current text (or the edit check read the edit as wording only), `deliver` delivers nothing when the issue changed after `pendulum issue` gave it to the session and records the text it gave with the plan, and `post-review` posts nothing on an Objective edited since its plan.

Split Objectives. A part's exit record lists the checklist items left; its PR says `Refs #N` instead of `Closes #N`, and Pendulum records the part on the issue. When it merges and the issue stays open, the dispatcher deletes `pendulum/N` and queues the Objective again; the next part starts from the default branch with the plan and the merged parts' PRs in `$PENDULUM_IN`. One PR is open at a time, and an Objective that needs more than six parts (`max_parts`) Blocks; the cap bounds how many PRs, not the spend (each part's work and review jobs, its rebases, re-reviews and resumed stages are each capped by `max_usd`), and the task card names it, so a worker whose plan needs more parts Blocks before it builds any.

Git LFS: in a repository whose `.gitattributes` uses LFS, every worker and review job fetches the branch's LFS objects before the harness (a failed fetch is a warning, not a Block); that spends LFS bandwidth per job in exchange for validation and the model seeing real media. Pendulum's own git commands that move the agent's checkout (onto the branch, onto its own rebase, onto its catch-up merge) never fetch LFS content there: they leave pointer files (`GIT_LFS_SKIP_SMUDGE=1`), and the objects then come from Pendulum's mirror, fetched with its token, followed by `git lfs checkout`. A reused local clone keeps the filters an earlier stage installed, and its git has no credential, so a smudge there would fail the checkout. The hand-over covers every commit a git in the checkout can check out that stage: the branch's head, the default branch as handed over, and the branch's commits beyond it, again whenever the default branch moves (a catch-up merge, or one that conflicts), so the harness's own rebase or merge in a conflict pass downloads nothing either. Only objects the checkout's store lacks, matched by each pointer's oid and size, are downloaded and copied, within the stage's remaining time (a hand-over the time cuts short says so, `git lfs checkout` included). The hand-over delivers the whole working set whatever its size: `PENDULUM_LOCAL_MEDIA_MAX_MB` caps only the media a branch pushes. LFS routing that arrives after the stage set the checkout up (a rebase or merge brings the first `.gitattributes` pattern) is named in the log: Pendulum leaves the checkout's pinned git config alone, so the objects go to its store and the files stay pointers until the next stage. In local mode the harness's sandbox cannot reach LFS storage, so the model commits media and Pendulum's own push uploads it from the host, to the repository's own GitHub endpoint whatever `.lfsconfig` says, with the token offered to github.com only; a branch carrying more than `PENDULUM_LOCAL_MEDIA_MAX_MB` (500) of media since the default branch Blocks.

## Review and merge

Pendulum merges on its own (`auto_merge`, on by default); the gate is CI green on the integrated head, the reviewer's one pass and the merge queue's re-run. The owner reads merged diffs when they choose, and the bench's judge samples them. A defect the reviewer flagged and the worker rebutted stays visible on the merged PR; a repeated class becomes a reviewer-skill change scored on the replay set.

The reviewer is one model call per PR on the top model, and one more for each chunk of commits written after it (below), on a head whose validation is green or still running. A head without the validated marker (handed off by the worker, pushed or marked ready by a person) gets Pendulum's validation in the review stage. With required checks and a reviewer to run, the reviewer starts at the first reading that shows a check run on the head (CI has started) and no required check red, once the PR's mergeable state reads no conflict, and the wait goes on beside it: a head that conflicts, whose checks never start, or whose reading already shows a required check red gets no reviewer pass yet, but its fix passes first, as does every head when the reviewer does not run or validation is the commands alone, and a red that stays red Blocks before any review. A head handed off from the local route is not given its commands again on that first pass. A red the checks show while the reviewer runs, or after it (after triage's rerun and the base-failure check, as any red), gets no fix pass of its own: once the reviewer is done, the answer pass takes it with the reviewer's comments, its failures in the prompt and their whole logs in `$PENDULUM_IN/checks/`, and runs even when the review has no comment. A conflict, a check that never starts or a base failure ends the stage as before, ending a reviewer call still running, and its review is not posted, so the next review stage reviews the head it works on. The validated marker goes on the head the checks were green on; when the PR's head moved meanwhile (a person's push), the stage posts nothing and puts the review label back on for the new head. The reviewer's rerun and the foundation pass finish the review that started. The progress comment shows the overlap: the reviewer's line ends `beside the required checks on <sha>`, the pass's own lines meanwhile start `during the reviewer:`, and the checks' end is `required checks on <sha> green|red|settled while the reviewer runs`, or, when they outlast the reviewer, `waiting for required checks on <sha> after the reviewer`; the scorecard counts each minute once, the overlap as review beside CI (bench/README.md). It gets the Objective text, the diff and the PR body, and it posts review comments tied to lines, each naming the acceptance entry or repository rule it concerns, with assumptions that change behaviour flagged explicitly. It also judges every acceptance entry, met or not, with the line that shows it: Pendulum lists the issue's entries in the prompt, puts the judgments in the review body, names any entry left unjudged, and turns an entry judged not met into a comment the worker must answer. On a split part that leaves work for the next, the prompt says it is part N and not the last: an entry the PR body assigns to a later part is judged deferred and gets no comment, while one the body claims and the diff does not deliver is still a finding. The last part and a one-PR Objective are judged against every entry. Reason: otherwise every earlier part re-raises the entries later parts deliver, and the worker rebuts each one. A call that fails (a crash, a non-zero exit, a cap) or an answer that holds no JSON or judges none of the entries is a missed pass: it reruns once in a fresh session on every harness, on the fallback reviewer where the harness has one. A provider's refusal is not rerun, a subscription's usage limit included (below): the fallback model draws on the same subscription. When neither call produced a review, nothing is posted and the Objective Blocks with how each call ended: no placeholder stands in for a review that did not happen, and Pendulum never merges past the review. A rerun that answered but judged none of the entries is posted, and its placeholder says it is not a clean pass. Entries left unjudged are recorded on the review, not enforced: they do not hold the merge. It has no verdict and no refuse path: a reviewer that can stop a run turns every false positive into a hold. An Objective labelled `pendulum:foundation` (trusted as the harness and model labels are, and outside the plan's record, since it changes only the review) gets a second call after that one, the foundation pass: it checks each shared contract the diff adds or changes against its callers in the repository, and shared test fixtures against isolation, and returns line-tied comments only, which go up in the same review. It runs within the job's `max_usd` like any call, reruns once when it misses, and when it cannot run or never answers nothing is posted and the stage Blocks, as for the first pass. The review that includes it carries a second marker (`<!-- pendulum:<issue>:foundation -->`): a PR reviewed before the label was added gets the foundation pass alone at its next review stage, and a rebased PR keeps its review only when that marker is there. Reason: a defect in a contract later work builds on (a mapping that folds new error codes into an old one, a fixture that writes the developer's real state) passes a review of the diff alone, and every later Objective inherits it. The worker gets the comments once and addresses or rebuts each; Pendulum pushes, posts the replies, and validation runs again; rebutted findings stay visible on the merged PR. Each finding the answer pass replied to (Pendulum's reviewer's, a named reviewer's, code scanning's) then goes to the finding check (`lib/finding-check.mjs`), before another answer round is spent on it. A reply that says the finding is fixed and names a test that fails without the fix (replies.json's `fixed` and `test`: one of the validation commands exactly as listed, a single simple command, and the arguments that run only that test, at least one of them no option; the answer pass is offered `test` only when there are validation commands) has that test run through the stage's own validation path (`runValidation`: its sandbox and env), each argument shell-quoted, in the checkout itself: first on the PR's head, then, when the commit the finding was raised on (else the head the stage's review covers) is known green (Pendulum's validated marker on it, and no red the stage held there: a command that runs more than the test fails on a red commit for any red it had), on that commit's tree with the head's copy of each argument that names a file put back, after which the checkout is reset to the head and its HEAD and tracked files checked. Each run gets the stage's time left less a reserve for the exit, and none starts with under a minute of it. Failing without the fix and passing with it resolves the finding; failing on the head leaves it open (`test failed`) with no decision call. A test that passes both ways is no evidence, and one that cannot be run so is not checkable (a command that is no validation command or not one simple command, no test argument, a commit not known green, a dependency manifest or lockfile changed since that commit, a checkout not clean at the head, a run that timed out or changed tracked files, too little time): either reply goes to the decision model, its note kept for the Block. Only the named test is run: a reproduction written in a reply's prose is never run. For every other reply the decision model is asked whether the answer resolves it, `fixed` (the change shows it), `rebutted` (the reply names an acceptance entry or repository rule that permits the code), `decided` (a maintainer's recorded decision, not overruled by a later one, speaks to the very entry, rule, file or behaviour the finding concerns and settles it: it waives or changes what the finding asks, assigns that work outside the PR, such as to the owner after the merge, or permits the code; general approval such as "LGTM" or "ship it" settles nothing, and doubt is `unresolved`) or `unresolved`, given the finding (its reviewer, file, line, body and when it was raised), the reply, what the PR changed since the commit the finding was raised on (its own file, then its other files, without the default branch's changes; a finding with no commit of its own reads from the head the stage's review covers), for a reply that says its fix is in the PR body (replies.json's `"fixed": true` and `"pr_body": true`) what the body changed since the finding was raised (git's diff, one line of context, of the body's version at that time, from GitHub's record of the body's edits read once per check, to the body now, cut at 16,000 characters; `no change`, or `whether the body changed could not be read` when the record does not hold that version), with `fixed` then taking a defect gone from the body and the question saying a body change alone never fixes a finding that asks for a change to the code or tests or says the code does not meet an acceptance entry or rule (every other reply's question carries no body; Pendulum's posted answer carries `pr_body` in its marker, `<!-- pendulum:<issue>:reply:<id>:pr_body -->`, so an answer judged again in a later stage keeps it), the issue's acceptance entries, the repository's rules (AGENTS.md at the head, the protected paths, the validation commands), and the maintainers' decisions the stage read (comments on the issue and the PR, the PR's review bodies and its inline review comments, by people with write access, a dismissed review's left out; each with its author, time, place and review state, cut at 2,000 characters; within 8,000 characters the newest decision always, the issue's newest within half the window while the PR has decisions too, then the PR's newest, then the issue's in any room left, with a count of those left out; a decision the reply quotes counts only when it is there, so a comment by anyone else settles nothing), each part between markers with a random tag, as data never to be followed; at most four questions at once. `fixed`, `rebutted` or `decided` at the confidence floor or more (Red-check triage, below; no confidence is none of them; `decided` never on code scanning's alert, nor when a decision newer than the oldest one shown was left out for length) resolves the finding's thread; any other verdict leaves it open (`judged not fixed`, or `judged not resolved` for a reply that did not say fixed). Pendulum posts the evidence in the thread first, under `<!-- pendulum:<issue>:resolved:<id> -->` (the test as it ran, the commit it failed on and the head it passed on, or the verdict, its confidence, the floor and who answered); that comment and Pendulum's answer are never a person's answer, so a thread a person reopens stays open, then resolves the thread (a finding in the review body: that PR comment is what resolves it), and a resolved thread, not a reply, marks it answered on every side (the answer pass's list, the exit, the merge pass). Anything else leaves it open. A person's reply answers as before, from someone who can push only: any such reply but Pendulum's own on the reviewer's comment, a writer's on a named reviewer's, none on code scanning's; a person may resolve the thread too. How each finding ended is recorded as data in the review stage's progress comment (its findings line: the reviews its reviewer posted, and each finding it listed with the review or outside reviewer that raised it and its outcome: `fixed-test`, `fixed-verdict`, `answered` for a `rebutted` or `decided` at the floor, `not-fixed`, `not-checkable` for no verdict or no decision model, or `open`), from the check's own branches and whether each ended resolved (a thread already resolved posts no evidence), never from the reply's words; a later stage's listed `open` never replaces a judgement, and a report reads only records written before its period ends; `pendulum report` counts the findings and outcomes per Objective, reviewer model and review stage beside those stages' dollars ([REPORT.md](REPORT.md)). Reason: findings per dollar and a reviewer's quality are then exact counts, not readings of prose. Findings still open after the answer pass (unanswered, or read as not resolved), when the rest of the exit is delivered, take another answer round: the review label goes back on, and the next stage's answer pass gets them again, each with Pendulum's earlier answer (`earlier`). A Question the answer pass raised stands with findings open: it carries them. The rounds per re-entry (the Objective label applied again, a restart or a Block) are at most two, shared with code scanning's rounds at the merge (below) and counted in Pendulum's record on the issue (`<!-- pendulum:<issue>:answer-rounds -->`); past them the stage Blocks (cause `work`) naming each open finding, with what the check found on it (`test failed`, `judged not fixed` or `judged not resolved`, after `not evidence` or `not checkable` for a named test that proved nothing), and how to clear it: a fix on the branch, a reply by someone who can push or a resolved thread, or for a finding in the review body that resolved marker by someone who can push. An answer the gateway gave no verdict on (a failed call, a refused key, an answer outside the choices; once the key is refused no further question is asked in the stage) costs no answer round: it goes to no worker pass, the review label goes back on, and the next stage judges it again first (when that stage was started only for this, an answer it then reads as not resolved waits for the answer round its exit takes); the second stage in a row without a verdict Blocks naming the decider's error code (cause `setup` for a refused key, `provider-quota` for a rate limit or spent credits, else `outage`). With no decider (`decision_route` off, or `gateway` with no key) the decision model's part is off: a reply answers its finding as before unless a test it names proves the fix or fails on the head, the progress comment says `finding check: off (<code>)` once per stage, and doctor's `finding check` line warns. The reviewer reads each chunk of work once. The answer pass's and the fix passes' commits are the review's answer and get no review of their own when they do only what the review's findings and the failing checks asked. The answer gate decides it: Pendulum asks the decision model red-check triage uses (the same key, `triage_model`, below) one question, `only_asked` or `more_than_asked`, giving it the diff they wrote since the head the review read, with the default branch's changes left out (the replay below), then each finding the answer pass answered (path, line, body) and the failure lines and output's end of each red the fix passes and the answer pass were given, at most 32 KiB in one question (`ANSWER_INPUT_BYTES`). A diff too large for one question is asked about in parts, each with the findings and failures and each within that size: whole files packed in order, and a file too large alone split into its hunks, packed in order the same way, each part with the file's header; four parts at a time, none started once one is held. Only every part covered covers them, and the first part held is named (`part <n> of <m> … (<files or hunks>)`); a single hunk too large for a question is not judged, named in the hold, and no part is asked, even with no decider. Before each question, the first included, the stage's `max_usd` (in known dollars: a price still settling counts nothing) and its wall clock are read: once either is reached, that part and every later one are not judged, each named in the hold, and never covered. The question says a failing check asks only that it pass with the smallest change, so new behaviour or a feature is more than asked even when a check's output mentions it. The diff, the findings and the failures go as data (fenced, or JSON strings), with no worker secret in them. Pendulum records the head they leave in its own comment on the PR (`<!-- pendulum:<issue>:covered:<sha> -->`, edited in place), and the later of that record and its last review's `commit_id` is the head the review covers. Only `only_asked` at the confidence floor (Red-check triage, below) covers them. Anything else holds the PR: a lower or missing confidence, `more_than_asked`, a call that fails, times out or answers outside the two choices, no key, a hunk too large for a question, a diff over 16 MiB (not read whole), a file git diffs as binary (its numstat `-`, or `Binary files … differ`: a text file with one NUL byte is one, and the model would see none of it; no question is asked), or a diff that cannot be told apart. Then the record stays on the head the review read, marked as an answer's (`:answer` after the sha), the review label goes back on, and the next review stage's pass reads those commits. That pass's own answer is gated too: held again, the stage Blocks (cause `work`) naming why, the record staying on the head that pass read, and a person reviews those commits, so the gate never loops. The gate's answer goes to the job log (`answer gate (<model>): <verdict> <confidence> → …`, with `(in <m> parts)` after the confidence for a diff asked about in parts). The review goes up on the head the reviewer read (its `commit_id`), which is the head Pendulum's checkout was on when the reviewer started; when GitHub's head is no longer Pendulum's by then (someone else pushed), nothing is posted and the review label goes back on for the new head. A pass on new commits that finds nothing leaves the earlier reviews' open findings to the answer pass. A review stage whose head is that head, or only a rebase of it (the covered head's own change, replayed with `git merge-tree` onto the head's merge base with the default branch, gives exactly the head's tree: a clean rebase, GitHub's update-branch merge, Pendulum's merge of a default branch), runs no reviewer and goes on to validation and the merge. Commits written after it (the work stage's answer to a Question, a maintainer's push, a resolved conflict) get a reviewer pass before the merge, on the diff from that replay to the head, so neither the reviewed code nor the default branch's changes are in it; when the replay conflicts, the pass gets the whole PR. The prompt and the posted review name the head it follows on; the pass judges every acceptance entry as a first pass does, and a foundation Objective's foundation pass runs on the same diff. An answer pass that applied maintainers' decisions (a Question's answer, a comment no pass had read) in new commits does not merge: the stage covers the head before it (the head the review read, marked as an answer's, when the answer gate holds what the stage wrote before it), puts the review label back on, and the next review stage reviews those commits. Reason: the one-pass rule keeps the same code from being reviewed twice, and code written after the review was never reviewed.

A repository may also name third-party reviewers, reviewer Apps outside Pendulum, by login (`third_party_reviewers`, such as `greptile-apps[bot]`; `lib/third-party-review.mjs`). Their review is part of the PR's review. After Pendulum's reviewer posts, the review stage reads the PR's reviews once for each named reviewer's submitted review whose `commit_id` is the head Pendulum's reviewer read. While one is missing, the stage does not wait in place: it records the wait on the PR (a comment, marker `<!-- pendulum:<issue>:third-party {"sha", "logins", "at", "minutes"} -->`, counted only when Pendulum or someone who can push wrote it, since a local loop writes as its developer; the bound the dispatcher, `serve` and `run` wake the review at is its `minutes`, the `third_party_wait_minutes` setting of the stage that wrote it (20 by default, taken as at most 24 hours whatever the record says), from GitHub's creation time of that comment; the review stage that resumes judges the wait by its own setting), takes the `pendulum:review` label off, moves the Objective to In review when it is not there (a Question a person answered by marking the PR ready still carries `pendulum:question`) and ends with exit `waiting`, holding no local slot, runner or sandbox. The dispatcher's tick, on every route (the Action's, the sandbox's, `serve`'s), reads that record from the PR comments it already reads for send-backs. While the bound is ahead and the review is missing, it leaves the PR as it is: no merge pass, no branch update, no send-back; when it cannot read the PR's comments and third-party reviewers are named, it leaves the PR alone that tick too. Once that review of the head exists, or the bound has passed, or the PR's head is no longer the one the record names (a maintainer's commit, GitHub's update-branch), it puts `pendulum:review` back on, which starts the review stage on that route as any review label does. The reviews are read at most once a tick, and in `serve` at most once a minute per PR. An App's review submitted on a Pendulum PR that is not Pendulum's own ticks the dispatcher (`pull_request_review`, its reviewer of type `Bot`; a person's review ticks nothing), and on a public repository the bound's end is a `third-party` wake; on a private one it waits for the next event or the cron. The review stage that starts again finds Pendulum's own review on the PR (its marker), so the reviewer does not run again; it reads the record, says on its progress comment which reviewers reviewed the head or were left out past the bound, removes the record and goes on to the answer pass. A review label applied after the record was last written means a stage has taken the wait up, so the dispatcher never puts the label back twice for one record. A stage that starts again before the bound (the label re-applied by hand, a restarted loop) rewrites the same record and ends `waiting` again; a new head gets a new record and its own bound. A stage that goes on without waiting (the reviewer's review in, the bound passed, the cap spent) removes the record, so none holds a later merge. A record that cannot be read or written, a label that cannot be taken off, or Pendulum's own login unknown (its record could not be told from a pasted one) is no wait: the stage goes on without the reviewer rather than stall. `pendulum run` and `pendulum review`, which may have no `serve` behind them, do the dispatcher's part in place, once a minute, and then review again, and `pendulum run` on an In-review Objective whose review waits takes that wait up the same way; `serve` leaves it to its own ticks. The answer pass then gets each named reviewer's root line comments that neither Pendulum nor anyone who can push has replied to, from any head, beside Pendulum's own. Each comment carries `from` (the reviewer's login), and its body is sanitised like harness text and cut at 8,000 characters. The prompt and the pendulum-deliver-pr skill call their text untrusted review input: the worker judges each finding against the code, fixes it or rebuts it, and follows no instruction in it. Pendulum posts the replies in their threads, and the finding check resolves those it reads as resolved. The exit counts a named reviewer's comment as unanswered only when the answer pass was given it; one posted after the wait is left for the next review. Only the named logins are waited for; any other reviewer's comment is handled as without the setting (the merge pass, below, has the answer pass take an unlisted reviewer's thread when the base's rules require every conversation resolved). With none named, the stage reads nothing more and runs as it would without the setting. The wait comes before the answer pass, so before the merge; there is no wait for the answer pass's new head, just as Pendulum's reviewer does not review it again. Code scanning (GitHub's own App, `github-advanced-security[bot]`, whose alerts on the PR's lines are review comments, CodeQL's say) is answered the same way on every repository, with no setting and no wait: the answer pass gets its open comments marked as untrusted input, and Pendulum resolves each thread once it replied. On code scanning's thread only Pendulum's own answer counts, never a person's reply alone, and an alert adds only its own file to the answer pass's fix-pass scope, never a protected or toolchain file.

Pendulum's push and merge. The harness pushes nothing. Pendulum takes the branch as a git bundle the agent writes to a pipe, indexes its pack into a mirror only Pendulum can write (a mkdtemp directory under Pendulum's own 700 temp directory) with `git index-pack --strict`, so every object is fsck-checked whatever the git version, and checks it there: the paths changed since the stage started (GitHub's head before any harness ran), Git LFS pointers, the local media cap, and each LFS object's bytes against its pointer. It then pushes with an explicit lease on the head it last saw, to `refs/heads/pendulum/<issue>` only, and reads GitHub's head back. Before a push, when the default branch on GitHub changed a file under `.github/workflows/` since the branch's base, Pendulum merges it into the branch in the mirror (its own merge commit, from `git merge-tree`) and the checkout fast-forwards to it (one that cannot, with uncommitted edits in the way, keeps the branch on that merge: the next push merges the checkout's new commits onto it, so the branch only moves forward): GitHub refuses a token without the Workflows permission, the App's or the local one, a branch whose workflow file is a version no branch has any more, which is what a run cut before such a change carries. A new branch that conflicts with that merge is not pushed; the harness resolves the conflict once, as a send-back's conflict pass does, and Pendulum pushes again. That pass answers like the work pass: a cap it reaches Blocks with that cap, and a death, or a rebase or merge it leaves in progress in the checkout, Blocks with nothing pushed. A push GitHub refuses for a workflow file Blocks with that cause, in Pendulum's words; any other refused push Blocks with git's status word and the exit code, and GitHub's own text goes to the job log only. A fetch, Git LFS upload or push of the mirror's that got no answer from the remote (a dropped connection, DNS, TLS, an HTTP 5xx, 408 or 429: anything but the remote's answer, which is the push's porcelain line for the ref, other than git's `[remote failure]`, or an HTTP 4xx refusal; `lib/outbox.mjs` gitTransport) is tried again up to four times within a minute and the stage's real end (its deadline plus the 15 minutes kept for the exit, so a timed-out stage's last push retries too); a push whose answer was lost but whose head GitHub now has counts as pushed, and is not sent again. A refusal (a ref line in git's porcelain, an HTTP 4xx) is never retried; one git reports with no status (a missing ref, a failed authentication) stands once those tries are spent. GitHub's head is read back up to five times over about 30 seconds, and at least three times. A refused or rejected push, or a head that is not the one checked, Blocks. Nothing is armed for later: the review job records the head it reviewed and validated as mergeable, and merges exactly that head (the merge endpoint's `sha`, or enqueue with `expectedHeadOid` on a merge queue) once its required checks are green, the review is done and no maintainer decision is unread, or the unread ones ask for nothing (the comment check: the decision model, given the issue, the PR and every unread writer comment whole with what it is, reads them as asking nothing at the 0.7 floor, and a fresh read after the call finds nothing new; a writer's review requesting changes always holds the merge; they are then recorded as read on a progress comment of the merge pass's own); otherwise the dispatcher's merge pass does it on a later tick. Just before the merge, on every route, the merge pass reads the PR's review threads: it resolves the ones Pendulum handles (its reviewer's, the named reviewers' and code scanning's, and under a rule below the unlisted reviewers') that a person answered; a code scanning comment still open (posted after the answer pass, or answered and not resolved by the finding check) puts `pendulum:review` back on, so the answer pass takes it, within the answer rounds (above: at most two per re-entry, counted in `<!-- pendulum:<issue>:answer-rounds -->`), and past them Blocks (cause `work`) naming each open alert's file and line. When branch protection or an active ruleset on the base requires every conversation resolved, a named reviewer's open thread no person answered (posted after the answer pass, or answered and not resolved by the finding check) goes back the same way, and so does an unlisted reviewer's: one nobody named whose root comment is by someone who can push or by a GitHub App (a `[bot]` login, which can comment only through an installation on the repository). So under that rule every App installed with pull-request write on the repository or its organization, reviewing or not, can put text before the answer pass's model, always as untrusted data. The review stage reads the same rule on the PR's base (`lib/third-party-review.mjs` `unlistedRule`, read only when such a comment is on the PR) and takes the same threads, classified once by `github.mjs` `reviewThreads` for both passes (REST and GraphQL name some Apps differently: Copilot's reviewer is `Copilot` in one and `copilot-pull-request-reviewer[bot]` in the other). An App's comment goes to the answer pass beside the named reviewers', with `from` its author, sanitised and marked as untrusted review input, and a person's reply answers it as it does a named reviewer's. A writer's comment among the stage's kept decisions (its author's write access checked) is a maintainer's decision: the answer pass gets it with `writer` its author, its text once (under the decisions when they show it); one that is not (an author association of MEMBER or COLLABORATOR can be read-only) is untrusted input with `from`, as an App's is. Every such body is one JSON string in the prompt's list. Only the finding check's yes or a person resolving the thread settles a thread its opener's association counts as a writer's, never a reply. The finding check, the answer rounds and the thread's resolution are otherwise a named reviewer's. When a thread no answer pass takes is open too, the merge pass Blocks at once rather than spend a round. Under that rule any other unresolved thread (a stranger's; `github-actions[bot]`'s, which every workflow run in the repository posts as, one a stranger's comment or pull request starts included, so it stands for no installation and counts as a stranger; or an answered one Pendulum could not resolve) never reaches a model and Blocks (cause `work`) with a reason naming each thread's author, file and line. Without such a rule, no unlisted reviewer's thread is read for the answer pass or holds the merge. A merge GitHub refuses just after the pass resolved threads is tried once more after a moment. That is read from the threads and the rules, before the merge and again after a refusal, never from GitHub's words. Threads or rules that cannot be read leave the merge to GitHub's own rule. A merge or enqueue GitHub refuses because another pass already merged the PR, or queued it at the reviewed head, counts as done; that is read from the PR again, never from GitHub's words. The dispatcher's tick comes from events, never only from GitHub's cron: CI finishing on a Pendulum PR's head (the launch gate's merge tick on the sandbox route; the dispatcher's own `workflow_run` and `check_suite` triggers without one), a Pendulum PR merging, the queue dropping one (`pull_request` `dequeued`), and the queue watch. A PR the queue drops unmerged (its checks failed or timed out on the queue's commit) is enqueued once more, and the issue gets one line saying so with the queue's code and time; dropped again, the Objective Blocks with the queue's reason codes, read from the PR's timeline; when the queue's jobs ran and failed, the Block names the failed jobs of its newest failed run and each one's first failure line, with the cause and advice of what the review stage read the red drops as (below): GitHub's side is an `outage`, the default branch's own failure says to fix it there, a flake read each time says to steady that test, and anything else is the work's. A drop whose newest removal is a red run on the queue's commit (`failed_checks`) goes to the review stage first, once per drop: the merge pass records it on the issue (marker `<!-- pendulum:<issue>:queue-red:<time> -->`, its JSON record `{at, state, head, after, kind, sigs, tries, reads}`, `head` the PR head the drop was of) and puts `pendulum:review` back on; a record still `handed` is handed again on a later pass. Records count from Pendulum or anyone who can push, since a merge pass and a review stage of one Objective can run under different logins (`serve --all` beside the Action's dispatcher). The review stage takes the newest record when it is `handed`; one of another head than the PR's now is `superseded` and left. It reads the PR's `merge_group` runs of any status (the queue drops a PR at its first failed required job while the run's other jobs go on) created after the removal before the drop, or the drop count's bound, and at most six hours back (one page, newest first): the newest created by the drop is this drop's, never an earlier drop's. With no such run listed yet, or no failed check on it while it still runs, nothing is decided: the record stays `handed` and the next review stage reads it again; after two such stages (a failing check no Actions run carries) it is not known to be the PR's (`none`). On that run's commit it reads the failed check runs, and decides as for a red PR check: a required job GitHub never started (`not-started`), every failed job failing on GitHub's side (`infra`), triage's flaky verdict (`flaky`, asked as for a PR check, nothing rerun) and every failing job failing the same way on the default branch (`base`) are not the PR's change; a run or job logs it cannot read (`none`), and, with triage off, a failure that names no file or test the PR changes (`unclassified`), are not known to be. The record says so (`requeued`) and the merge enqueues it again or Blocks under the rule above. Anything else is the PR's own change, a deterministic failure in a job the PR's checks do not run (another OS, say) included: triage reads each job's log, not its name, and a failure that names a file or test the PR changes is never a flake. Its answer pass gets the failing jobs' lines and whole logs, marked as the queue's integrated commit, then validation runs on its new head and the merge enqueues it, whose drops count from that head. The record turns `fixed` only once that pass itself committed (the checkout's HEAD before and after it, not a merge Pendulum makes at the push) and the push went up; until then it stays `handed` with `tries` counted, so a stage that ends first (a crash, a stop, a pause, a cap, a wait for a third-party reviewer) leaves it to the next. The bound is progress, since the Objective's last re-entry (its label, `pendulum:restart` or a Block): each record keeps its failing jobs and their failure signatures, and a red after a fix pass is judged against the red that pass was handed, with every red fixed since the re-entry as the ones seen, as in the stage's own fix loop (`lib/fix-progress.mjs`, Exit: blocked, below); each record keeps its failing jobs (each one's signature and the digest of its folded failure lines with their counts) and their failure lines for the decision call, which is also given the fix pass's own commits; each stage try's end is recorded on the drop (`committed`, or `idle` when its pass ran, its harness started and returned, ok or not, and committed nothing; a try whose pass never ran, was stopped, or asked a Question records none and does not count, as the stage's own bounds cover those); no progress, or a try that ran and committed nothing, Blocks the stage (`blocked`), as the work's (an unmade judgement as Pendulum's or the outage's), naming the failure. There is no count of the queue's fix passes: while the decision model keeps reading each as closer to green, `daily_usd`, the owner's limit, is what stops them. Only drops after the latest of the review the merge rests on, the head's commit (GitHub keeps no push time for a branch push) and the issue's last re-entry or Block count, so a re-entry starts the count over even when its head keeps the earlier review. When GitHub never started the required job on a dropped entry's merge_group commit (no step, no runner: a billing lock, a spending limit), the Block says so as infrastructure, quoting GitHub's annotation, as validation does, rather than pointing at the checks. A queue commit on which CI never begins in 10 minutes (`queue_stall_minutes`) counts as a drop too, and so does one on which CI began but a required check makes no progress. Progress is read from the check's Actions job: its steps, each one starting and completing (a running job's log is not readable, so it is not used). The job is stalled when the step running now has run past max(3 × that step's normal duration, that duration + 15 minutes) (`step_stall_factor`, `step_stall_floor_minutes`), so never under 15 minutes (16 for a step that normally takes 1); the normal duration is the longest the same step of the same job took in the workflow's last 15 green runs on the default branch or in the merge queue, read with the job token once per dispatcher tick or queue watch, and only once a step has run 15 minutes. A step with no history, a running step GitHub gives no start time (counted from the check run's start), a check that is no Actions job, or a job Pendulum cannot read falls back to a time bound from the job's own start: the queue's check timeout (`check_response_timeout_minutes`, from the ruleset; setup's 60 when unread) less 10 minutes, at least half of it and at least 20 minutes, so 50 minutes at 60. A job queued or waiting for a runner, or with no steps yet, is never stalled. A required check not reported at all (an aggregate behind `needs:`) is judged by its upstream jobs' progress, and by the fallback from CI's first start when nothing runs there. The notice names the stuck step and its times, e.g. `` `Quality` / `Run scripts/ci/setup.sh` running 16 min, normally ~1 min ``. On the local route the Pendulum App has no Actions permission, so Pendulum reads no job steps or history there and the hung rule is the time fallback only, read once per merge pass. Pendulum takes the PR out and puts it back once, which restarts CI, and the second time Blocks naming the check. A removal for a hung step counts toward that only when the step really hung: its record holds each step judged hung (the required check's name, the job's id, the step's name and number, its times) and the queue's own deadline for that commit (the commit's time plus `check_response_timeout_minutes`, read once per merge pass with the hung bound; no deadline when it is unread, and such a removal always counts). When the drops would Block, Pendulum reads those jobs (with the job token; never on the local route), oldest removal first: a removal is cleared, and counts toward no try, when the judged step finished green and its job, the required check the queue waited on, concluded `success` by that deadline, so the queue would have taken that check's result. A job that failed later (a later step red), finished after the deadline, or was cancelled counts. One removal at most is cleared since the count's start; past that, every hung removal counts, so a step that is slow on every try still Blocks. While a judged job is still running before its deadline, or cannot be read then, the PR stays out of the queue and the decision waits, never past that deadline: Pendulum records that removal on the issue, and the run's end, a retry wake for a failed read, or the next tick brings the next pass. A person's removal and every other drop count as above. A removal Pendulum made reads its reason back from Pendulum's own requeue comment on the issue, which records it, since GitHub's timeline cannot say why Pendulum removed a PR. CI has begun once a check run or status named like a required check exists on it, or a check run or suite from the integration that provides the required checks (Actions when the ruleset names none), so an aggregate required job behind `needs:` that starts late is not a stall; another app's run, such as code scanning's, does not count. Any run from that integration counts, required or not (a `push` workflow that fires on the queue's branch, another `merge_group` workflow, a startup failure); one that never produces the required check is bounded by that rule and the drop handling. When the required checks cannot be read, any check run, any status, or any suite with a run counts. The queue-watch job, started by the dispatcher whenever its merge pass leaves a PR in the queue, reads the entry every 30 seconds until the PR leaves the queue, merged or dropped, or stalls there, and then ticks the dispatcher with its own `workflow_dispatch`; after 12 minutes it ticks anyway, and that run starts a new watch. Recovery from a drop never depends on the `dequeued` run: GitHub attributes that event to `github-merge-queue[bot]` and, under a strict approval policy for outside contributors, holds it for approval, while a `workflow_dispatch` by the job token is never held. The `dequeued` run stays a faster path where it runs; the merge pass reads the queue and the PR's timeline each time, so the two never enqueue a PR twice. Local mode's loop runs the merge pass every interval itself. A person's own removal from the queue is a hold, not a drop: Pendulum leaves the PR out until they enqueue it again, or it is reviewed again, gets a new head or re-enters. Doctor names an installed workflow rendered before these ticks (re-run `setup --apply workflow`), and, with a merge queue, warns when the repository's approval policy can hold the `dequeued` run (or cannot be read, which needs admin), saying recovery runs from the queue watch. The squash commit carries the PR's title and Pendulum's closing line, never the branch's commit messages; on a merge queue, setup sets the repository's squash default to the PR's title and body, and doctor checks it. A PR that fell behind gets GitHub's update-branch merge; that new head is accepted only when it is a merge of the recorded head and a default-branch commit, committed and signed by GitHub's web-flow key, with exactly the tree Pendulum's own `git merge-tree` of the two gives. Any other new head goes back to review. Pendulum's git runs only in its mirror, with hooks off and no global or system config; the agent's checkout gets the default branch, the branch and Pendulum's own clean rebase as bundles, and every git command there runs in the agent's sandbox. Only the commit Pendulum's rebase made, and only when it rebases the head Pendulum's review covers with nothing more, keeps the review and merges from the work stage; any other head (one the harness made: a resolved conflict, a fix; a rebase Pendulum then merged a workflow change into before pushing; a rebase of commits written after the review) goes back to the review stage, whose reviewer reads what it adds beyond a rebase of the covered head (above).

GitHub failing for now is retried inside Pendulum's API client (`lib/github.mjs`), on every route: a 5xx, a 429 or secondary rate limit, or no answer at all (GitHub's primary rate limit spent is waited out to its reset in the stages and `serve`: below). Up to four tries per call, waiting what GitHub asks (`Retry-After`, a minute for a rate limit that names none) or 2, 4 and 8 seconds, each spread by up to 30% (a wait GitHub asked for only upward), at most 90 seconds in all and never past a deadline the caller passes; a longer ask is not waited out, and the caller sees the error. A caller that handles a rate limit itself (the dispatcher's blocked-by reads, the five-minute launch jobs) gets it at once. Only a call that means the same sent twice is retried: a read; a PUT, PATCH or DELETE that sets a state (not a merge or an update-branch); and adding labels to an issue or PR, which keeps the ones it has. A create (any other POST: a comment, a review, a PR, a repository label, a dispatch, a rerun; a GraphQL mutation) goes again only when it provably did not land: the connection was never made, or GitHub's rate limit turned it away (a 429, or a 403 with the rate-limit headers or message; a 5xx or 422 with those headers is no rate limit); or when a read finds it absent: the caller's, or for a comment on an issue or PR a read of the comments updated since just before the call, which finds one with the same body (line ends and trailing blanks aside) by Pendulum's login, or by anyone when the body carries a Pendulum marker (a notice is posted with the notice App's token), so a comment GitHub made before its 5xx is not posted twice; after a 502 or 504 that read waits ten seconds at least, and it keeps the call's deadline. Each retry is logged once with its cause and try number. A 5xx that is still GitHub's answer once the tries are spent (or a comment whose read for it fails) is an outage of GitHub, below: its code is the status (`HTTP 500`), and the stage ends on it, never on a crash Block. A refusal (a 4xx that is no rate limit) is not retried and stays the caller's error.

This machine's own network being down is not GitHub failing (`lib/network.mjs`). In a work or review stage, and in local mode's `serve`, a request that never left the machine (DNS, a refused or unreachable connect, a connect that timed out; read from Node's error code, never its message) is no try: Pendulum probes that host, one request at a time after 5, 10, 20 and 30 seconds and then every minute, and sends the request again once the host gives any answer, a create included since it did nothing. Every other request to that host waits on the same probe rather than being sent, and the log has one line when the host is lost and one when it answers again; a host lost again within a minute of answering is the same outage, its first loss and its limit carried over and no new line logged unless it then stays down past a minute, when it gets one line then and one when it answers. Once a stage has stopped waiting, a request to a host it gave up on fails at once as that outage (its host, code and first loss), so the stage's end names it whichever call met it first. A Block that came from an outage ends on the outage instead, on any route, as below: a GitHub step of the exit (the split record, the review label, the mergeable record, the maintainers' comments read before a merge, the merge itself, the PR's first opening) that failed because its host did not answer, or because GitHub's core REST quota was spent (a spent GraphQL or search quota is no outage of a write). Any other Block stands, an outage or not: protected paths, a cap, validation, an exit record the harness wrote. While a host the stage gave up on still fails a probe, a harness pass cut off by its provider or the network (below) is no death and does not run again, and a run left with no exit record ends on the outage without the harness being asked, so its own account of a run the outage cut off never stands in for it; once the host answers again, such a pass runs again as above, and the harness is asked as ever. The App token's mint waits the same way. Any HTTP answer, a 5xx included, is the host answering and goes through the retries above, with no probe; a 5xx that outlasts them ends the stage on GitHub's outage at once, as one past the wait does (paused on the local route, where `serve` resumes it after a doubling wait for as long as GitHub's status page reports an incident: LOCAL.md; an `outage` Block elsewhere), and its reason names the request and says GitHub answered that status to every try since the first. A git fetch or push of the mirror that fails in transport while the remote's host does not answer a probe waits the same way, and its retry count starts again after. The repository's setup and install that fail while this machine's network is down run once more after it is back (`lib/checkout.mjs` `throughOutages`). Down is decided on exact facts only: an outage the stage recorded on any host while the step ran, GitHub's origin not answering a check on a fresh connection (no pooled socket stands in for it) that reaches the network as Pendulum's GitHub client does: through the proxy the stage process's own environment names when `NODE_USE_ENV_PROXY` is 1 (local mode's stages), else directly with its own DNS lookup, or one of the stage's own allowed hosts (the sandbox's built-in list, `PENDULUM_LOCAL_DOMAINS` or `allowed_domains`, and the Objective's approved `pendulum:host:` labels, as the route resolved them, those not GitHub's own first, lookups only) failing its lookup with `EAI_AGAIN`, as a resolver that still serves GitHub's names from its cache fails the rest. Nothing the step printed and nothing its checkout configures is ever probed or looked up, since the model edits both. The check connects only to GitHub's origin, the operator's own (`GITHUB_API_URL`, which may be a GitHub Enterprise Server on a private network); through a proxy, the proxy's failure to reach it (a tunnel it could not open, or its 502 for an http origin) is that origin unreached. The step waits for this machine's network, the same check, whichever host the outage was met on; such a failure is no try (an install's clean reinstall is not spent on it), a second failure while the network is down ends the stage on the outage, and so does the wait running out. A failure with the network up Blocks as before, its reason saying the network was up, that the step ran behind the local sandbox's proxy when it did, and that its first run met an outage when one did; it names no host. A harness pass whose model provider answered busy (`usage.mjs` `providerBusy`: HTTP 408, 425, 429 or a 5xx, 529 included, or with no status the AI Gateway's bare 5xx types `service_unavailable_error`, `overloaded_error` and `internal_server_error`; with no refusal type or code: a 5xx with an auth, permission, quota or billing type or code is that refusal; read from the same structured error as a refusal below, `providerError`) is no death and no network loss. Copilot's weekly and global rate limits (`user_weekly_rate_limited`, `user_global_rate_limited`) are not busy: they are usage limits with no reset reported, as its quota is. In a stage the pass waits 1, 2, 4… minutes doubling up to 30, or, when the error itself gave a time to go again and that is later, until that time: a 429's only, from its own fields (Claude Code's API error `api_error_params.rate_limit_info.resetsAt`; Copilot's `auto_mode_switch.requested` after the error with the same `errorCode`, its `retryAfterSeconds`), never an earlier or unrelated event. It then runs again from its own session (a reviewer's from its prompt) on what is left of its budget; the stage's time bounds it, not a count. A provider's time over an hour away goes through a usage limit's gate on a route with automatic account choice: another account free ends the stage as a usage limit, so the Objective moves there; else the stage's account is held until that time while it waits, so no other Objective starts on it. A wait that would end past the stage's in-place bound (fifteen minutes from the first busy answer on the local route, the work deadline elsewhere) or leave the pass under five minutes ends the stage: with the provider's time five minutes or more away, as a usage limit that resets then (its account held until that time, as any usage limit's is: paused locally, the holds record or a `provider-quota` Block elsewhere); else on the provider's host with the status as its code, as GitHub's 5xx does (paused locally, where `serve` resumes it on the same doubling; an `outage` Block elsewhere, which the dispatcher relaunches). A harness pass that fails (no cap, stop, provider refusal or busy answer) on a provider or network failure its harness reports with no status is no death: a server-error type (Claude Code's API error message `error: server_error`, which it gives a connection it could not make or a request that timed out), read from the same structured error (`providerError`), never the words. A pass whose harness reported a 4xx is no cut, whatever the network did while it ran: the provider answered and said why. Any other pass is judged on exact facts instead: one with no structured error at all (Codex prints a 5xx and a lost connection as prose only; a crash), and one whose structured error has no status and names no outage (a Copilot `session.error` with no `statusCode`, Claude Code's `unknown`). It is a cut when, between the pass's start and its end, this process met an outage of any kind on its provider's host (lost, or answering busy) or lost any host to this machine's network (a connect-level failure; a GitHub 5xx or another host's answer is none), or when its provider's API does not answer a probe now; otherwise it failed on its own. A cut pass waits, while its provider's API does not answer, as a request does; then, or at once when it answers, it runs again, from its own session when it has one (a reviewer's pass, and one with no session yet, as it was first run), on what is left of its budget and wall clock, at most twice, and its record carries every run's spend once. A stage's first steps (its token, the writers, the PR a review reads) end on an outage the same way as the rest. A stage waits in place up to fifteen minutes on the local route, where it then ends `paused` for `serve` to resume (LOCAL.md), and up to its work deadline on the Action and a cloud sandbox: still unreachable then, it stops waiting and Blocks with the External cause `outage`, naming the host, the error code and since when, if GitHub takes that one write, in a notice that mentions no one, since the dispatcher relaunches it. **A stage lost to a network failure on the Action and a cloud sandbox is relaunched** (`lib/relaunch.mjs`), being almost always transient. Two losses count. One is an `outage` Block that is the Objective's newest Blocked notice and was written after the Objective last became Running (GitHub's clock, from the issue's timeline, which the dispatcher already reads for every Blocked Objective and which carries the comments too); an older one never counts, so a later Block whose own notice did not land is not taken for it. The other is a stage that vanished with no exit because its runner or sandbox could not report: a Running Objective with no work job alive, or on the sandbox no stage within its lease, 15 minutes after its Running stint began. Those 15 minutes are for a job GitHub has not started yet: on the Action, a stint whose `work (<n>)` job GitHub's jobs API shows completed after the stint began (cancelled mid-harness, or gone with no exit) is judged at once, on the tick its job's last step fires, provided the timeline still shows the stint Running, a fresh read of the issue shows it open, `pendulum:running` and in no other state, and no restart is waiting. A job still queued or running, none shown yet, a job read that failed, or only an earlier stint's job (completed before this stint began) waits, and the dispatcher's wake ticks at the 15 minutes' end (`job-grace`), so a job that ended with no tick of its own is judged then. A stint a relaunch began has its job in the relaunch's run alone (the run its record names, when that stint began with the first Running label after the record was written). A tick that lists a live work job whose final tick step has started arms a `retry` wake, since that step's tick may read the job before GitHub marks it ended. A work job that dies after a tick saw it alive, with no final tick of its own, is judged by the next tick after GitHub ends it (at the latest its `timeout-minutes`), with the cron behind it. The stint's job is read at most once a tick per Objective, and only for one with no work job alive; the tick reads each run's jobs once, and one runs listing serves every stint that began within 15 minutes of another. A vanished stage that left a sign the network was not what ended it is not relaunched (`endedNotLost`, read from the stint's `work (<n>)` job as GitHub's jobs API gives it, its `conclusion` and `steps[]`, never a log): on the Action that job concluded `cancelled` or `timed_out` (a person, or the job's timeout: a stop, which keeps the vanished Block), or it failed before Pendulum ran, which is relaunched once (a checkout's or a token mint's 5xx, a runner not acquired, may pass), the step kept on the relaunch record, and Blocks with the cause `setup` naming the step when the relaunch's job fails at the same step (GitHub never started it: no step and no runner; or GitHub's `Set up job` failed; or a step failed before Pendulum's own work step, the step that `uses: clockgrove/pendulum@…` with `mode: work`, placed by reading the workflow file at the job's commit, one read only for a job that failed after its set-up: `Set up job` is step 1 and the job's steps follow in order, whatever they are named); on the sandbox its record says the stage ended. A job with no failed step of its own (its runner went away), whose Pendulum step failed with no exit written, or whose failed step cannot be placed because the workflow file cannot be read (the log says so) is lost. The dispatcher starts the work again as re-applying the label would: the Objective goes Running again, a new stint, and a work stage resumes its branch and PR (on a cloud sandbox, in the Objective's recorded sandbox), within `max_usd` like any stage. A relaunch spends like a pick: none starts while today's spend has reached `daily_usd` (it waits, unblocked, for the UTC day's turn, its `daily-cap` wake, or for a spend that can be read) or while `max_concurrent` is reached, and relaunches go before new picks. At most twice since a person last started the Objective (applied its label, started its draft, or restarted it), counted in a record Pendulum owns on the issue (marker `<!-- pendulum:<n>:relaunch -->`, each try naming that start), so a dispatcher that restarts keeps the count and a person's start begins a new one. So one start can spend up to 3 × `max_usd` on stages lost this way before the person is mentioned. Past that it Blocks, whatever the caps, and the notice says how many relaunches were tried: cause `outage`, the person mentioned, when the stage ended on one; a vanished stage gets the vanished Block (`worker job vanished`, cause `pendulum`) with the count. A write the relaunch needs that fails (its record, its labels, the Block) is tried again on the next tick, never turned into a Block. An Objective whose timeline the dispatcher cannot read is left as it is until a read succeeds: a vanished one stays Running, as any Running Objective whose Running time is unread does, and an outage-Blocked one stays Blocked on its stage's notice, which mentions no one; there is no fallback Block for that. On the Action, the stint's `work (<n>)` job is looked up in the run the relaunch record names (each relaunch records its dispatcher's run), else among the 10 newest runs created in the hour up to the stint's start; one not found is no sign either way, so the stage is relaunched. A stopped or draft Objective is never relaunched, nor is a restarting one (a vanished one gets the vanished Block, and its restart goes ahead). A Block whose newest notice is anything but a stage's `outage` notice is never relaunched. Every other command (the Action's dispatcher, doctor, setup, the launcher) keeps the client's bound above.

GitHub's primary rate limit spent is an outage of one quota whose end GitHub states (`lib/network.mjs`, on the same wait): a 403 or 429, or GraphQL's `RATE_LIMITED`, with `x-ratelimit-remaining: 0`, an `x-ratelimit-reset` and no `Retry-After`, when GitHub's own count of that quota, read at once from `GET /rate_limit` with the same token (not counted against the primary rate limit, though it can count toward the secondary one, so it is not read again while the process holds that quota spent until the answer's reset or later), has none remaining; its reset is the count's. The quota read is the one the answer names (`x-ratelimit-resource`). A count with some remaining is no primary limit, whatever the answer says (a secondary limit, or a 403 for another reason on the last quota point), and keeps the retries above, as a `Retry-After` does; when the count cannot be read, the answer's own headers stand, as GitHub documents them. A quota is the host, GitHub's resource for the request (REST's core, GraphQL, search, code search, read from its path) and the token, so a spent GraphQL quota holds no REST call, and the notice App's or the agent's token none of the local token's. The reset is read on this machine's clock through the answer's `Date` header. In every process the error carries the code `RATE_LIMIT_SPENT` and the reset time; the process's record of a quota's reset is its latest answer, gone once the quota answers. In a work or review stage and in `serve`, the request that meets it is no try: it, and every other request against that quota, waits until the reset plus one to ten seconds, one sleep for all callers and no probe, with one log line when the limit is met and one when it has reset; then each goes again, a create included, since the refusal did nothing. A refusal that comes after the stated reset has passed here waits 5, 10, 20, 40 and then 60 seconds instead; one within a minute of a reset whose new reset is that near is the same wait, unlogged, while a quota spent again until a later reset is a new wait with its own two lines. A reset past the stage's in-place bound (fifteen minutes on the local route, its work deadline elsewhere) is not waited for: requests against that quota fail at once until the reset, its other quotas go on, and the stage ends on the first call that cannot go on without it. On the local route it ends `paused` with the reset in its `result.json`, and `serve` resumes it once the reset has passed, without a probe (LOCAL.md). On the Action and a cloud sandbox it Blocks with the External cause `provider-quota`, naming the reset; the Block is a GitHub write too, so a stage whose reset comes before its deadline plus twelve minutes (the job keeps fifteen after its deadline, which also pay for the steps before and the upload after) waits for it first, and with a later reset the Block's one write fails, and the dispatcher, once the reset lets it read GitHub again, relaunches the stage as one lost with no exit (`lib/relaunch.mjs`, above). A `provider-quota` Block is never relaunched: it mentions the person, who re-applies the label after the reset. The App token's mint carries the same code, only when the count, read with the App's JWT, says none remaining: with no count its answer is a rate limit with no stated end, since a refusal of the mint can meet the last quota point. A spent rate limit cuts no harness pass off. `serve` waits for the reset of a quota its own reads meet with no bound, so its ticks read, resume and start nothing until then. Every other command keeps the client's bound and gets the error with its code: the Action's dispatcher then starts nothing that tick, logs one line (`GitHub's API rate limit is spent until <time>; no new stage starts until then`) and arms a `retry` wake a minute after the reset; picks it already wrote stand. A tick that met its token's REST quota spent in a read it went on without starts nothing either.

A harness pass that ends on its subscription's usage limit is no crash and nothing wrong with the Objective (`lib/usage.mjs` `providerRefusal`, `lib/harness.mjs` `runHarness`). It is read from the harness's structured fields, never its words: Claude Code's result with `is_error` and `api_error: usage_limit_reached`, its reset from the API error message's `api_error_params.rate_limit_info.resetsAt`, else from the last `rate_limit_event` whose status is `rejected`, of the error's own window (`rateLimitType`) when it names one; a Copilot quota refusal (`session.error` with a quota type or HTTP 402), which reports no reset. Codex's `exec --json` stream reports its usage limit as prose only (an `error` event's `message`, exit 1 as for any failure), and neither `exec` nor its exit code carries a code or a reset, so the limit is read from the thread's rollout instead: when the ChatGPT backend refuses with `usage_limit_reached`, Codex records that answer's rate-limit snapshot as a `token_count` event there. A Codex run whose stream ended on an error is at its usage limit when the last such snapshot of the subscription's own limit group (`limit_id` `codex` or absent) stamped since the pass started names a `rate_limit_reached_type` or holds a window (`primary`, `secondary`) at `used_percent` 100 or more, and shows no credits to go on; a workspace's credits or spend cap counts whatever its credits show. The reset is the latest `resets_at` of the full windows (of any window when a type is named and none is full), and a workspace's credits or spend cap has none. Reason for the credits rule: on credits Codex runs on past its windows, so an unrelated failure then would otherwise hold every Codex Objective until a weekly reset. Reason: Codex's app-server protocol carries the code (`codexErrorInfo: usageLimitExceeded`), but `exec` drops it, and driving the app-server instead is a different harness integration; the snapshot is structure Codex already writes where Pendulum reads each run's usage. A limit met during compaction records no snapshot, and an API key or the AI Gateway gets no ChatGPT rate-limit headers: those failures stay what the stream says. No other model runs the pass, the reviewer's fallback included, since every model of the subscription draws on the same limit. In a work or review stage with the reset known, the pass waits for it (plus a minute) in place when that falls within the stage's in-place bound with five minutes of the pass's wall clock left after it, and then runs again on the same model, from its own session when it has one, at most twice (`usage_limit_waits`): the bound is fifteen minutes on the local route (`PENDULUM_LOCAL_WAIT_MINUTES`) and the work deadline on the Action and a cloud sandbox. A wait never runs the pass again past the dollar cap: with the cap spent, the pass ends there. Past that bound, after its two waits, or with too little wall clock left, the local route ends the stage `paused` with the reset in its `result.json`, for `serve` to resume after it, a work pass continuing on its kept clone and session when the branch on GitHub, the newest restart record, the Running stint and the Objective's text are as at the pause (`lib/continue.mjs`, LOCAL.md), and the Action and a cloud sandbox Block with the External cause `provider-quota`, naming the reset. With no reset reported, the stage Blocks with `provider-quota` at once, unless automatic account choice picked its account and another is free: the account is then passed over for a guessed while and the Objective moves to a free one (LOCAL.md and INSTALL.md, automatic choice).

A harness pass whose session ended abnormally while a command the worker started in the background was still running is no Block and no crash (`lib/usage.mjs` `backgroundJobs`, `lib/harness.mjs` `runHarness`). A `-p` Claude Code session stays open while its background commands run and wakes its model when one ends, so a worker may end its turn on a long command (a foreground one is capped at 10 minutes) and finish once it is woken. What was still running is read from Claude Code's stream: the last `background_tasks_changed` set, its `local_bash` tasks, or, in a stream without that event, each `local_bash` task started in the background with no `task_notification`. Only a pass with no good end counts (killed, crashed, judged hung); one that ended with its result is left as it is. Its command ended with it (the harness's sandbox dies with its parent, and Pendulum kills what the run left), so there is nothing to wait for: the pass runs once more, resumed in the same session, on what is left of its budget and of its wall clock less the exit-record ask's share after it, and only with five minutes of that left. It is told which command was stopped (its description and command line, as JSON strings marked as its earlier text, not instructions) and, after a hang judgement, that it made no progress for a whole window: rerun it only if its result is still needed, and write the exit record only once it has finished. A pass its own cap, a stop or a provider's refusal ended keeps that end, as do a pass with no session and a reviewer call, and a rerun that again leaves a background command running is not run a third time. Codex reports no background command (one it starts with `&` is a command item that completed), and Copilot's stream gives a still-running background shell no id at its start, so neither is read for one.

The merge queue is GitHub's. It serializes merges and re-runs CI on the integrated head, which is what makes dozens of concurrent workers safe without owned paths: a PR that was green on its branch and conflicts after a sibling merges is caught there and sent back to its worker for a rebase, under the Merge step's rules. Two mechanics decide how it is wired. First, a PR opened, pushed or enqueued with the job's `GITHUB_TOKEN` gets no `merge_group` workflow run, so its required checks never report and the queue evicts it at the timeout; every push, PR creation and enqueue therefore uses an installation token from the adopter's Pendulum GitHub App, and the job token stays read-only. Second, the queue needs its checks reported on the queue's own commit, so the repository's CI is a separate workflow triggered on `pull_request` and `merge_group`, never a step inside the worker job; the worker job's own validation run is the worker's feedback, and the CI workflow is the gate. Branch protection requires the queue and those checks, so neither a worker nor a stray push bypasses them. A required check that is skipped counts as passed, so aggregator jobs use `always()`.

## Scale

The design target is dozens of Objectives queued and in flight with nobody watching. It is not yet drilled at that size and is not among the 0.9 claims.

- **The dispatcher is the only scheduler logic.** Ready = labeled, not blocked by an open issue, not Running, In review, Blocked, Question or Done. Order = `P0`, `P1`, `P2`, then issue number. Start up to `max_concurrent`; stop for the day at `daily_usd`.
- **Pendulum owns its ticks; GitHub's cron is only the backstop.** GitHub fires a schedule late or not at all under load: on the scratch repositories the `*/10` cron fired for under 3% of its slots over a week, hours apart. So every wait has an owner that ticks the dispatcher with `workflow_dispatch` (the job token's, never held for approval): an event (a label, an issue closing, a merge, CI finishing, a queue drop, an App's review on a Pendulum PR that is not Pendulum's own; a closed issue that was no Objective and blocks none ends its run after minting the token and at most one listing, so it costs a job start and seconds), the job that freed a slot or failed a launch, or, for a wait only time ends, the `wake` job. Each dispatcher run lists its deadlines (`{issue, kind, at}`, in its log) and arms one wake for the earliest of eight kinds: a sandbox stage's lease end plus a minute (a stage that died silently), a quota retry the launcher handed over, the next try of a failed start (2, 4, 8, 16, then every 30 minutes; a vendor's refusals never Block and hold the route's new picks for at most four in a row, three real failures or three cut-offs in a row Block; every attempt ends as a stored entry, docs/ADAPTERS.md), the next 00:00 UTC when `daily_usd` held Queued work back, one quick retry of a read that failed or of a work job whose final tick may have read it before it ended (never two in a row), the bound of a review stage's wait for a third-party reviewer (`third-party`, Review and merge), the bound of a hand-off's wait for a sibling on the same files (`sibling-wait`, Dispatch), and the end of a Running stint's 15-minute grace on the runners with no work job alive (`job-grace`, the vanished stage in Review and merge). The other kinds it lists (`launch-grace`, `review-grace`, `checks-grace`, `answer-grace`, `local-pause`) are their event's or the local loop's, with the cron behind them. A wake arms only when no wake already queued or sleeping fires before its deadline or within a minute after it (read from the `wake (<kind> <iso>)` job names), joins no concurrency group, and is never cancelled, so a duplicate only ticks twice; a run a wake started never arms that same deadline again, and dry runs and runs named for one issue arm none. Which kinds a repository arms follows its visibility, read from the event's repository payload (one repository read only when a schedule run has a long wait to decide; unknown counts as private). Cost: a wake sleeps on a hosted runner and holds one of the account's concurrent-job slots while it sleeps.
  - **Public repository:** Actions minutes are free, so it arms all eight kinds. On the sandbox route a lease wake sleeps through each stage (the heartbeat moves the lease on), and a capped day's turn is reached in hops of up to 350 minutes, each a plain tick.
  - **Private repository:** each sleeper bills about $0.36 an hour (a 2-core Linux runner at $0.006 a minute), so it arms only `quota`, `start-retry`, `retry` and `job-grace`, minutes each: about 5 to 20 billed minutes per quota retry, 2 to 30 per failed start, 2 per read retry, and up to 15 per Running stint a tick saw with no work job alive before its grace ended. Each launch the dispatcher names also arms a `start-retry` wake for its marker's expiry, about 10 billed minutes (about $0.06) per named launch unless an earlier wake covers it, so a normal Objective costs about 10 to 20 sleeper minutes (its work and its review). A stage's lease end, the day's turn and a third-party wait's bound stay in `deadlines[]` and wait for events and the cron (a sleeper to the bound would bill the minutes the wait frees); doctor says so on a private repository.
  - **The sandbox sweep and image build no longer wait for their crons.** GitHub's hourly sweep cron and nightly image cron are backstops only (on a scratch repository the sweep's fired twice in about 40 hours; the nightly build was skipped one day and ran 7.5 hours late the next). No sleeper waits hours for either:
    - **The sweep arms its own `sweep` wakes, minutes each, on every repository.** Each sweep run arms its next one for what it left: a stage that said it ended moments ago (its launcher's end answers first; 10 minutes), a sandbox created moments ago (15), an older image a stage may still be starting from (15 minutes after a newer build is recorded; the image job arms this after each build that leaves one), the rest of a run that reached `sweep_max_destroys` or its collection slots (10 minutes on, after a run that destroyed or stopped one; with nothing destroyed, a cap of 0 among others, the rest waits for events and the cron), and once what a failure left (never from a `sweep` wake's own run). Each is a minute after its wait ends (about 16 minutes at most), through a wake job of its own (`sweep-wake`, `image-wake`, named `wake (sweep <iso>)`), whose tick runs the sweep and the dispatcher. Only an armed `sweep` wake covers a sweep deadline. A stopped sandbox's `sandbox_idle_days` (days, not minutes) get no wake: the next sweep an event runs (an Objective closing, merging or Blocking) destroys it, or the hourly cron's.
    - **An owed image build runs on the UTC day's first dispatcher tick.** A head an earlier day left unbuilt (today's `image_daily_minutes` used up, or `image_refresh: nightly`) is owed once today's turn allows a build: under today's minutes for `merge`, none tried yet today for `nightly`. Every dispatcher tick on the sandbox route checks (three reads: Pendulum's image record and the default branch's head commit) and, when one is owed, sets `image_owed`, and the image job builds the default branch's head in that run (on any event but a pull request's). A merge after 00:00 UTC builds on its own push as before. Every build records its attempt on the image record before its first vendor change, and an owed build before anything that can fail; the build's own entry replaces it. Any recorded build of the head (built, failed, or only started: a crash, a 45-minute timeout, a vendor or token error, a refusal) ends the owing, so the next merge or the nightly cron tries again, never another tick; so does the current image's entry covering the head (a head that changes nothing the image is made from, docs/ADAPTERS.md, Sandbox image), and an owed job that finds the head covered drops its attempt. An owed build's job re-checks the record when it starts, so a job a tick queued during another build of the head builds nothing. The image job needs the dispatcher only for this: a push, the cron and a manual build's run skip the dispatcher by its own `if:`, and the image job still runs (`!cancelled()`).
    - Cost on a public repository: none in minutes; each sleeper holds a concurrent-job slot. A `sweep` sleeper is 11 to 16 minutes, about one per image build that leaves an older image and per stage that Blocks itself, so about 30 to 60 minutes a day on a busy repository and none on a quiet one. A private repository pays the same, about $0.07 to $0.10 per wait.
- **Workers do not know about each other.** Coordination is the dispatcher's ordering on known files, the rebase and the merge queue. Two Objectives that keep conflicting on one file past the rebase bound produce a Blocked card naming the files, which is the signal to re-file them or order them (`blocked_by`), not a reason for a planner.
- **Cost is the only cap.** No cap on merges or Objectives per day. Dollars are bounded by `max_usd` per job, by `daily_usd` on the dispatcher, a gate on starting stages (running stages, review stages and answer passes go on; every stage writes its spend so far into its progress comment, which the day counts), and, when set, by `max_objective_usd` per Objective, a gate every work and review stage checks before any pass against the known dollars of all the Objective's stages and parts (`lib/objective-cap.mjs`), with `timeout_minutes` as the time cap.
- **Every figure says how it is billed, on a positive sign only.** `lib/usage.mjs` `BILLING` is `api`, `subscription`, `credits` and `unknown`.
  - The stage's credential sets the start (`lib/harness.mjs` childBilling, on the environment the harness child gets): a `CLAUDE_CODE_USE_*` switch is `api` for Bedrock or Vertex, else `unknown`; `ANTHROPIC_AUTH_TOKEN` or `ANTHROPIC_API_KEY` is `api`; a non-Anthropic `ANTHROPIC_BASE_URL` with neither is `unknown`; `CLAUDE_CODE_OAUTH_TOKEN` is `subscription`; a Codex key by its auth mode (`chatgpt`, `chatgptAuthTokens`: `subscription`; `apikey`, `personalAccessToken`, `bedrock*`: `api`; any other: `unknown`); the AI Gateway key is `api`; Copilot is `credits`; a CLI's stored login is `unknown`.
  - Each pass is then decided as it ends (`passBilling`): a Claude `apiKeySource` of `ANTHROPIC_API_KEY`, `apiKeyHelper` or `/login managed key` is `api`, any other but `none` is `unknown`; a model served by Bedrock or Vertex is `api`; on an `unknown` credential, a Claude pass that reported a subscription's rate-limit windows, or a Codex pass whose rollout carried a ChatGPT plan's rate limits, is `subscription`. `none` alone proves nothing: a bearer token reports it too. A Claude pass whose `rate_limit_event` says `isUsingOverage` ran on paid extra usage and is `unknown`, whatever the credential. A Codex decision call's rollout is read for its plan limits before its files are removed, as a pass's is.
  - Records carry `billing` (a pass's kind; a stage's, the kind its passes share) and `usdByBilling` (the known dollars by kind, a relayed key's as `api`) in `result.json`, the spend line, the rebase line, the vendor comment and the scorecard; `result.json` and the spend line also carry `usdByPass`, the stage's known dollars by pass kind (work, review, answer, fix and conflict passes, from each pass's label), which the finish card breaks the stage down by, and what the stage records it ran again (`rerun`, the first stage after a Block; `judgeOnly`, a review started only to judge answers already made), which the card shows as churn. The exit line, progress comment, status line, `daily_usd`'s words and the scorecard say "API-equivalent at list prices, on the subscription", "Copilot AI credits, billed to the seat" or "billing not recorded", each part of a mix; billed spend is bare. The caps count the figure whatever its billing.
- **Dollars are real or unknown, never estimated.** A figure Pendulum records, caps on or reports is one a harness or vendor reported (Claude Code's `total_cost_usd`, Copilot's AI credits, the AI Gateway's cost, the sandbox vendor's usage) or API-reported tokens at the vendor's published per-token rate (the Codex price table). Spend with no such figure is unknown: a pass killed, crashed or hung before its harness reported, a Claude result zeroed by a crash, a resumed Claude session on Claude Code before 2.1.277 (decided on the version its stream names), a Codex model with no price row or whose promotional rate has ended, a Codex run past the long-context threshold whose requests' sizes could not be read from its rollout, a relayed gateway call or a gateway decision call the gateway never priced, a sandbox usage the vendor did not report. Each such run is recorded with `usd` as what was reported (null for none), `usdUnknown` (the count of such runs in any total) and `usdUnknownWhy` (codes, `lib/usage.mjs` `UNKNOWN_WHY`), and shown as "plus N runs of unknown cost" in the spend line, progress comment, exit line, `result.json`, `daily_usd`'s total and the scorecard. The caps compare the known dollars only and the stage goes on, so a cap can be exceeded by unreported spend; the provider's own budget is what bounds it. `max_concurrent` is a runner-capacity and conflict-pressure control: the dispatcher's matrix holds at most `max_concurrent` less the Objectives running, since an Actions concurrency group cannot cap at N, and a concurrency group per issue so a repeat trigger dedupes rather than cancels a sibling. Hosted runners cap a job at 6 hours; `timeout_minutes` sits under that.
- **The board is the dashboard.** Queued, Running, In review (with a question marker), Blocked, Done, moved by the jobs.
- **Runner choice is a line in the file.** Hosted by default; self-hosted where an adopter wants their own toolchain or hardware, with `setup` (and `node_version`) as the only places a toolchain is named.

## Security

What the workflow file makes visible, and what is true:

- `permissions:` gives the job's own token `contents: read`, `issues: write` and `actions: read`; the jobs that tick the dispatcher get `actions: write` (work and review also use it for triage's rerun of failed CI jobs), and `id-token: write` is uncommented only for Claude federation. Every write to code goes through the App's installation token, minted for that one repository. No org scope, no PAT, no stored subscription token.
- The harness holds no GitHub write access. On Actions it runs, with the install and the validation, as a separate uid, `pendulum-agent`, created with sudo per runner: no groups, no sudo, no cron, at or lingering session, its own 700 home, always `/home/pendulum-agent` and wiped before each job (doctor fails if a `pendulum-agent` user has any other home), holding its clone and a read-only installation token. Each command runs in a transient systemd unit (`systemd-run`), or, where there is no systemd, in its own namespaces and a cgroup v2 group, with the system read-only, every other home hidden, a private `/tmp` and no new privileges, so it cannot read the runner's home, Pendulum's temp directory or Pendulum's process environment, nor write outside its home. Commands start with a fixed `PATH` and no system or global git config. The unit's processes are killed with it after each run, before Pendulum reads what it left. The write token lives only in Pendulum's memory (GitHub calls through `fetch`, Pendulum's git by per-process env config). `setup`, which may need sudo, runs as the runner on a clean default-branch tree Pendulum made, with Pendulum's own temp directory. `PENDULUM_APP_TOKEN`, when an adopter supplies a fixed token, is Pendulum's write token; the agent then gets no token and can clone a public repository only; a private one needs the App's id and key. Copilot always runs with its built-in GitHub MCP server off and is never given folder trust, so the repository's own Copilot configuration does not load. Doctor parses every workflow and fails closed: the repository's default workflow token must be read-only (or, when doctor cannot read the default, every workflow must set read-only `permissions:`), no `pull_request` or `merge_group` workflow may ask for write, since branch code runs there, and the Copilot token must be refused on an issue, a pull request and a file write. It checks `sudo -n` and the agent launcher on the runner.
- A harness session is archived as the agent when it is captured, and a held one, like the Git LFS objects handed to the checkout, is unpacked as the agent, both in its confinement and by Pendulum's own code (`lib/untar.mjs`), not GNU tar. On Ubuntu 26.04 tar goes through `openat2` for each directory it extracts into and for each member name with a slash, with no fallback when that fails, and the agent's systemd unit (`RestrictSUIDSGID`) answers `openat2` with ENOSYS, so no session could be captured with a nested name or put back there (#102). The unpacker takes directories and regular files only (links, devices and the rest are skipped), refuses absolute and `..` names, a size that is not a whole number of bytes and an archive without its end block, makes each path one segment at a time through real directories only, keeps permission bits only (no setuid or setgid), and writes file data as it streams in. `RestrictSUIDSGID` stays on. Doctor checks the round trip where the agent exists (`session restore`).
- `.github/` is on the protected list, so Pendulum refuses to push a workflow change; the App has no workflows permission, so GitHub refuses one as well. A workflow change an Objective needs is handed over for a person to apply (Workflow hand-over, above).
- `auto_merge` on means code lands without a human read; the file says so in its header comment, beside the gate.
- Cost is capped in the file (`daily_usd`, `max_usd`, `max_objective_usd`, `timeout_minutes`), or in a `PENDULUM_<NAME>` repository variable over it, which anyone who can push to the repository can set, with no pull request or review (INSTALL.md, Settings in layers); a variable never sets what steers trust, whom Pendulum answers, the merge gate, what a stage may reach or receive, or its setup, which stay in the reviewed file. Claude's `--max-budget-usd` and Copilot's `--max-ai-credits` enforce the per-job cap inside the run; Codex is checked after each run.
- The prompt-injection surface is the Objective text and the comments Pendulum reads. Pendulum acts on the Objective text only when its author, last editor and latest title renamer can push or are pinned maintainers, checked before every stage on every route (otherwise the stage Blocks before a harness sees it, and a session's `pendulum issue` refuses to hand it over). Only a maintainer can apply the label; comments count as decisions only from people with write access or the maintainers the workflow names (Trust, above). Secrets are masked in logs, the task card forbids printing them, and the model credential is step-scoped, so the repository code Pendulum runs (setup, install, validation) never sees it; what the model's own commands can reach is in Credentials and billing.

Notifications. GitHub Mobile notifies on subscriptions, so a comment on an issue the owner authored, or a PR they are requested on or @mentioned in, reaches their phone whichever identity posted it. `notify` names the handle: the Blocked comment @mentions it and a Question draft PR requests it as reviewer. Merges and plan comments stay quiet unless the owner watches the repository.

Why the App is in the footprint at all: it is the one thing GitHub makes unavoidable. Workflows do not run on events the job token causes, and the merge queue attributes its run to whoever enqueued, so an App (or a PAT, which Pendulum does not support) is the only identity that both triggers CI on the PR and gets a merge-queue run. The cost is one setup screen and two secrets; the gain is that the adopter's existing CI runs on Pendulum's PRs unchanged, and commits carry the App's name.

## Doctor

The same checks run as `/pendulum:pendulum-doctor` before the workflow is enabled and in every worker job, after the issue's trust checks and for the harness the Objective runs on, so a misconfigured repository Blocks with a one-line reason instead of spending a run. The command's first line names the repository's default harness and models and says an Objective may override them (Cost tiers and parallelism). Each line is PASS, WARN or FAIL with its fix, and `/pendulum:pendulum-setup` offers to apply the GitHub ones. Credentials: the harness's credential is present (for Copilot, `copilot_github_token`, refused on an issue, a pull request and a file write); a plan token is a warning; in a job and in local mode, which decider answers the decision calls (Red-check triage and the drift advisory, below; a local key file Pendulum refuses is a warning). GitHub (the workflow file read from the default branch on GitHub): the App's installation token mints for this repository with its one permission list (README, Install footprint; a missing read fails) and no workflows; the job token is read-only on code; the merge queue and required checks are on the default branch and the CI workflow's parsed `on:` lists `pull_request` and `merge_group` (a workflow doctor cannot read or parse makes it a warning); the labels; the five Project columns; `notify` and `maintainers` pinned as `login#id`; outside a job, the installed plugin no older than the `clockgrove/pendulum@vX.Y.Z` the workflow pins (a warning naming the update; `pendulum serve` logs the same line at its start). Repository: `setup` and the validation commands parse as bash (`bash -n`, and the unbash library for their structure), a first command of exactly `npm run X` or `pnpm run X` names a `package.json` script, and bash finds each one's first simple command (`type -t`; one it does not find is a warning, as setup or the runner may provide it); doctor never runs validation and runs `setup` only with `--run-setup`, a lockfile is recognised (or `install` is set), protected paths are present and cover every repository file the `setup` command names (setup adds them root-anchored, as `/scripts/ci/setup.sh`), repository skills parse and fit the cap, git-lfs is installed when `.gitattributes` uses Git LFS. Runner: `runs-on` resolves and matches the Linux runner of the CI workflow on `pull_request` (a warning), the harness CLI installs, `timeout_minutes` fits the runner's ceiling, and for Claude Code bwrap, socat and rg are present where the job runs, AppArmor lets bwrap make user namespaces on a self-hosted runner, and every `allowed_domains` entry is a host name (a warning names each one dropped; Credentials and billing); for Codex bwrap and its sandbox starting and confining where the job runs, with AppArmor on a self-hosted runner; for Copilot bwrap, slirp4netns and its sandbox starting and confining, with AppArmor for unshare on a self-hosted runner (Credentials and billing). Sessions: where the agent exists, a held session's round trip as the agent (`session restore`, Security). Worker secrets (when `worker_secrets` names any): a warning for each refused entry, each SOURCE with no value and each value equal to Pendulum's own AI Gateway key (Worker secrets, above).

## Red-check triage and the drift advisory

Every decision call (these two, the answer gate, the finding check, the rebase check, the answer check, the fix-progress check, the edit check, the fence check, the comment check, the plan-answer check and local mode's lapse check) goes through one decision interface (`docs/ADAPTERS.md`, Decision model). With the `AI_GATEWAY_API_KEY` secret passed as `ai_gateway_api_key` (local mode: `docs/LOCAL.md`), the AI Gateway's decision models answer. Without it, the stage's own harness answers on the login the stage runs on (a subscription, or the key it already has): one short call per question with no tools, no file writes and no session, capped at $0.30 and two minutes (and two turns for Claude Code), its answer checked against the question's choices, its spend in the stage's usage. Such a call runs on the stage's model: the worker's in the work stage, the reviewer's in the review stage. A usage limit on such a call is no answer and ends that stage's decision calls. It holds no account, except when it stops the finding check with nothing else to answer, or the rebase check: then the stage pauses or is held as a pass meeting the limit does (the rebase check pushing nothing). On that route the confidence is the model's own statement, not calibrated like the gateway's, and the default floor, 0.7, applies (`triage_min_confidence` is the gateway model's). It costs the stage's own subscription or key, all counted toward max_usd: one call per failing job at a red, a drift check every two minutes while a worker runs, one answer-gate call per review stage whose passes committed (one per part of a diff too large for one question), one call per answered reviewer finding, one per file a send-back's conflict pass left other than the branch's, or per group of its hunks up to 64 KiB for a file too large for one question (and, for a question of several hunks not judged kept, one per hunk in it, each sent with the file again), one per version of the newest writer comment on a Question (first thing in the work stage it resumes, never twice for one version), one per set of unread writer comments on a reviewed, green PR about to merge, and on Copilot a premium request per call. With a max_usd, the stage sets aside a drift reserve before any pass (10% of max_usd, at least one call's cap, at most max_usd): its passes get the rest, and the drift advisory (advice only) is asked only while one call's cap fits in what is left of the reserve, on either route. Every other call still runs, since its verdict decides the stage's next step or the merge; it is paid from the passes' share and can take a stage past max_usd only once that share is spent, by its own cap (Codex's by its two minutes). With the key, each gateway call costs what the gateway reports (its own figure, else its generation's `/v1/generation` `total_cost`), or is a call of unknown cost when it reports none, and the verdict does not wait for the price: in a stage it counts in the stage's usage and toward max_usd once its price comes; outside one (the dispatcher's, the launcher's, a local loop's and the CLI's answer, comment, edit and lapse checks) its day's line goes in the record the check writes anyway, else in one decisions comment per role on the Objective's issue, which `daily_usd` and the scorecard read. No cap of Pendulum's stops an essential gateway call, which has none of its own: beyond the drift reserve, only the gateway key's own budget bounds that spend. The `decision_route` setting chooses: `auto` (default; the gateway with a key, else the stage's harness), `gateway` (the gateway only) or `off`, where every red goes to the fix pass, no drift check runs, every answer and fix pass that commits after the review gets a review pass (the answer gate), a reply resolves its reviewer finding unjudged unless a test it names proves the fix or fails on the head (the finding check), a send-back's conflict pass is checked by matching commits rather than by content (the rebase check), a writer's comment on a Question resumes it unjudged (the answer check), and a writer's comment no pass has read holds the merge unjudged until the review stage applies it (the comment check). Doctor's `decision calls` line names which one a repository uses.

Red-check triage. When a required check is red, Pendulum asks the decision model (with a key, Vercel AI Gateway's decisions endpoint, `triage_model`, default `perplexity/pplx-decider-v1.2`; else the stage's harness) one question per failing CI job: did the change break it, or is it a flake or infrastructure? However wide the red, jobs that fail the same way (the same failure lines and files, whatever the job's name, as a matrix's legs hit by one outage) share one question, asked of the first of them, and every other failure is a question of its own. The jobs are read and asked one at a time, the required ones first, and the asking stops at the first answer that decides the red whatever the others read (no verdict, or a change verdict at the confidence floor or more): the jobs after it are neither read nor asked, and the triage line says so. An answer below the floor does not stop it, so every job up to such an answer gets its verdict. Only when every failing job reads flaky at the confidence floor or more does Pendulum rerun the failed jobs (with the job token's `actions: write`) and wait again, with no fix pass and no pass counted; anything else goes to the fix pass as before. A red merge-queue run is asked the same questions, with nothing rerun: the queue has dropped the PR, so a flake there is enqueued again as any drop, and anything else gets the queue's fix pass (Review and merge). A job that failed on GitHub's side is not asked and counts as a flake for that rerun: every step that did not pass or skip is its set-up (GitHub's first step) or a checkout step of its workflow (`uses: actions/checkout@…` in the file at the head, matched by the step's name in the jobs API), the failed step's log says a server or network failure (an HTTP 5xx, a timeout, a connection error; `SERVER_SIDE` in lib/triage.mjs, the one place such words decide) and no refused or missing request (a 4xx, an object that does not exist, an invalid path, a submodule or `.gitattributes`), and its failure points at no file the PR changes. Any other checkout failure is asked like any red. Each question names the job's first failed step. A required job GitHub never started is never asked (the blocked exit, above). Nor is a job that was cancelled (its conclusion in the jobs API `cancelled`, or `timed_out`), which is never a flake and never rerun as one. A job cancelled at or after another job of its workflow run (`run_id`) concluded `failure` or stopped at its time limit is that job's consequence: it is left out of the questions, the failed job's verdict decides, and a rerun of the failed jobs reruns both. The line says "cancelled by fail-fast after <leg> failed" when the workflow file confirms it (a leg of the same matrix job, `strategy.fail-fast` not `false`), else "cancelled after <job> failed; why it was cancelled could not be read" (a matrix inside a reusable workflow, a file that cannot be read). A required check cancelled because a newer run of its workflow replaced its run on the same head (`cancel-in-progress`, a re-trigger) is still pending, and only the latest check run of each name is read. A job stopped at its time limit (`timed_out`, or `cancelled` after running, by the jobs API's start and end times, at least as long as the limit its workflow file at the run's head gives it: `timeout-minutes`, a number or an expression over its matrix leg, else GitHub's default of 360, and at most 360 on a standard GitHub-hosted runner) goes to the fix pass, and the triage line, the fix pass's ask and a Block say so ("the test (windows-2025) job was cancelled at its 20-minute limit"; in the merge queue, "ran past its 20-minute limit on the queue's commit", never the PR's own change). Any other cancelled job (a person's or the API's cancel, or one whose limit cannot be read) is one Pendulum cannot place. When every failing job of the red is a cancel (a required roll-up of the others left aside), it gets no fix pass, on a PR or in the queue: the stage Blocks as Pendulum's, saying the job was cancelled, after how long and before what limit, that it is not a flake and not known to be the PR's change. A red with any other failure goes to triage and the fix pass, which are told of the cancel. The workflow file is the one at the run's head commit: a `pull_request` run runs its merge ref's and a `pull_request_target` run the base branch's, so a limit only the base changed is read as the head has it. A failing job is never asked when its failure lines or their stack frames name a path the PR changes in full (an intermittent defect the change brought passes on a rerun too): the path itself (a stack frame's file, a Git LFS object), an absolute path ending in it (a container's or Docker's checkout), or a relative path with a directory in it that the changed path ends with (a run inside a subdirectory). A changed file or added test they only name (a bare file name another file may share, a test title, a changed path inside a longer relative one) is no veto: the question lists them for the model to weigh. With triage off, a queue failure that names a changed file or test either way counts as the PR's own. A required job is left out of the questions only when it is structurally an aggregate (in the same workflow run as another failing job, started after it completed) and its own log has no failure line. Each job's verdict, confidence and failure signature (a hash of the sorted failure lines a runner, compiler or tool printed anywhere in the log, Git LFS's batch and download errors included, and of the repository files they and their stack frames point at; a log with no failure line has no signature and matches nothing) go on the run's progress comment, with a hidden record of the heads and signatures rerun and of a refused rerun: one rerun per head, a failure already rerun once is never rerun again on that Objective (the same signature, or, for the same job's same failed step with another signature or none, the same-failure call below: only `different_failure` at the floor lets it be rerun, and an earlier log that cannot be read does not), a refused rerun (not a rate limit) is not tried again on it, and a rerun that turns green is said on the progress comment. The same-failure call answers whether two failures of one job are the same failure (already rerun once on the Objective; failing on the default branch, the base-failure rule above): it is asked only when the signatures cannot tell, that is when either run has none, or the two differ while both runs failed in the same step (the jobs API's first failed step); another failed step, or two signatures with the step not known on both, is another failure, decided without a call. It is given the job, each run's failed step, each log's failure window (at most 4,000 characters) and the failure lines each run printed that the other did not (folded: paths, hashes and numbers), between random-tag markers as data, and told that a failure only one run shows is `different_failure`; it answers `same_failure` or `different_failure`, each pair once per stage. A question over 16 KiB is not asked: the two are not the same failure, and not surely another. With no decider only the signatures decide, and a missing one matches nothing. The confidence floor: every decision call on this decider (triage, the same-failure call, the finding check, the answer gate, the answer check, the rebase check, the fix-progress check, the edit check and the fence check) counts a verdict that acts only at the floor or more: `triage_min_confidence`, a number from 0 to 1, while the AI Gateway's `triage_model` answers; 0.7 when it is empty and whenever the stage's harness answers (the no-key route, or after the gateway refused), as the setting is not that model's. The fence check reads its verdict at that floor or 0.7, whichever is higher, so a lower setting cannot weaken the fix-pass fence. 0.7 is the floor measured on `perplexity/pplx-decider-v1.2` (on Pendulum's replay set its hard change-caused reds scored 0.51 to 0.58). The setting goes with the model it was set beside: a settings layer that names another `triage_model` (the default resolved) drops the floor of the layers below it (INSTALL.md, Settings in layers), and a model a flag or the Action's `triage_model` input names takes a floor set lower down only when it is the same model. Each triage line names the model and the floor (`default floor 0.7`, or `floor <n>`) beside each verdict and its confidence, as does each same-failure verdict a line or a Block reason gives. Each failing job's failed step (the log lines the runner stamped within the step's start and end times from the jobs API, else its log cut at the step's `##[group]` boundaries; a step too long for the prompt keeps the start of its command, its first `##[error]` with the lines just before it, and its end, within the prompt's size), the PR's file list and the changed files and tests the failure names go to the decision model. The same decider (with a key, `triage_model`) judges a file a send-back's conflict pass left other than the branch's version (How an Objective flows, step 5), sending the diffs on that file. The drift advisory: while the worker's harness runs (the work, fix and answer passes), at most once every two minutes and only after 12 activity entries, Pendulum asks the decision model (with a key, `drift_model`, default `baseten/elephant-1`) whether the agent is `on_task`, in `scope_creep` or `looping`, from the plan's checklist items, its last 12 activity entries (commands, edits, sub-agents, messages, read from the harness's own event stream) and the repository files it has edited. A `scope_creep` or `looping` answer at confidence 0.7 or more writes one line on the progress comment and in the job log, at most once per harness run; every answer's label and confidence go to the job log. It is advice only: it never stops, pauses, blocks or redirects a run. Those inputs go to the decision model. The same decider (with a key, `triage_model`) answers the answer gate (Review and merge), which sends the review's findings, the failures the passes were given and the diff they wrote. Pendulum's own process makes the call; the gateway key reaches no harness or command. Each triage line goes to the job log as well, naming the model asked (the gateway's, or the stage's harness and model). The same decider answers the finding check (Review and merge): one question per finding the answer pass replied to without naming a test that proves the fix, with its finding, the reply, the PR's change since the finding was raised (its body's too, for a reply that says its fix is in the body), the issue's acceptance entries and the repository's AGENTS.md, protected paths and validation commands sent to the decision model. A question with no answer (an error, a timeout, a reply that is not one of the choices) counts as no verdict: the red goes to the fix pass, the drift check flags nothing, the finding stays open, the answer gets a review pass and a writer's comment resumes its Question. With no decider (`decision_route` off, or `gateway` with no key), every red goes to the fix pass, no drift check runs, a reply answers its finding unless a test it names proves the fix or fails on the head, a writer's comment on a Question resumes it (the answer check), every answer and fix pass that commits after the review gets a review pass (the job log says `answer gate: off (<code>)` once per stage), a send-back's conflict pass is checked by matching commits where a file is not exactly the branch's, and the first red of each stage says `triage: off (<code>)` (local mode's key-file codes: LOCAL.md).

## Cost tiers and parallelism

The planner-high, worker-medium split survives one level down. The worker session runs on the strong model and does the planning, the integration and the PR; each checklist item goes to an implementer sub-agent on the cheaper model, pinned by the agent definition the job writes into the checkout (`.claude/agents/implementer.md` with `model: claude-sonnet-5-5`; `.codex/agents/implementer.toml` for Codex; Copilot's carries a model only when `subagent_model` is set) so the worker cannot drift up. Where the harness reports sub-agent usage (Claude does; Codex's sub-agent threads are read from their rollouts; Copilot reports none), the caps and the scorecard see it. The strong model stays in the loop for the whole Objective instead of handing a compiled brief to a weaker one and leaving.

The workflow's harness and three models are the repository's defaults. An Objective chooses its own with labels (`pendulum:harness:<name>`, `pendulum:model:<id>`, `pendulum:subagent-model:<id>`, `pendulum:reviewer-model:<id>`, `lib/choice.mjs`), not with its body: GitHub records who applied each one, and Pendulum acts on a label only when that person can push or is a named maintainer. The labels are part of the text the plan's record covers (`objective-trust.mjs` `objectiveSha`), so one changed after the plan Blocks like an edit. Every route resolves them before any spend (the worker and review job's `choiceGate`, the launcher and the local loop's `objectiveInputs`); a model the harness cannot run within Pendulum's caps is refused (`choice.mjs` `modelProblem`), and a stage prepared for another harness than its labels now name Blocks (`PENDULUM_STAGE_HARNESS`). The Action's work and review jobs read the harness label before they install a harness. A `pendulum:host:<host>` label (`choice.mjs` `hostsOf`) opens one more network host to that Objective's sandboxes alone, under the same rules: it counts only when a person who can push applied it, the plan's record covers it, and a name no sandbox can enforce as written (an IP address, a port, `localhost`) is refused. The check is on the name alone: `*.` is refused over a top-level name (`*.com`) and over a name the Public Suffix List holds as a public suffix or holds one below (the vendored `tldts` library's rules, its private section included: `*.co.uk`, `*.github.io`, `*.amazonaws.com` for `s3.amazonaws.com`); a name that resolves to a loopback or link-local address is not refused; and in local mode the label lets anyone who can push open a host from the operator's machine. The person applying the label is the check on both. A stage opens its own on Actions and in a cloud sandbox (`lib/local.mjs` `openStageHosts`); local mode's loop sets the stage's sandboxes up with them, and a stage whose labels now name other hosts Blocks (`PENDULUM_STAGE_HOSTS`). Choosing a model per stage or per sub-agent, and choosing one automatically, are out of scope.

Parallelism has two levels and the brief owns the inner one: implementers for items on disjoint files run at the same time, then one integration and one validation. The outer level is the dispatcher's `max_concurrent`. A worker that sees the whole Objective can tell which parts are independent without a graph review to say so.
