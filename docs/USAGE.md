# Using Pendulum

How to write an Objective, what you see while it runs, and what to do when Pendulum hands one back to you Blocked or with a Question. [INSTALL.md](INSTALL.md) covers setup; [PLAN.md](PLAN.md) has the full contracts.

## Glossary

The Pendulum terms used across the README, this page and [LOCAL.md](LOCAL.md):

- **Objective:** a GitHub issue labelled `pendulum:objective`. Its text is the whole specification of the work (Write an Objective, below).
- **Harness:** the coding agent that runs the model: Claude Code, Codex or GitHub Copilot CLI. The workflow's `PENDULUM_HARNESS` picks it, and a `pendulum:harness:<name>` label overrides that for one Objective (Choose the harness and models, below).
- **Stage:** one job of an Objective's run. The work stage plans, builds and delivers the PR. The review stage runs the reviewer, and the worker answers its comments. Each stage runs in a sandbox, and `max_usd` caps each one on the spend its coding agent reported. A run whose cost was not reported (killed or crashed before it reported) is shown as a run of unknown cost and not counted against the cap, so a stage can pass `max_usd` by it.
- **Route:** where a stage runs: GitHub Actions (the default), local mode on your own machine, or a cloud sandbox. Every route keeps the Objective's state in GitHub.
- **Dispatcher:** the part of Pendulum that decides what runs next. It starts ready Objectives in priority order up to `max_concurrent`, follows the running ones, Blocks stale ones and tends merges. On GitHub Actions it is the workflow's `dispatch` job. In local mode, `pendulum serve` applies the same rules.
- **Tick:** one pass of the dispatcher over the queue. On GitHub Actions a tick runs on events (a label, an issue closing, Pendulum's own jobs), with a ten-minute schedule as the backstop. `pendulum serve` ticks every 30 seconds.
- **Local loop:** `pendulum serve` running in your clone. It takes the Objectives labelled `pendulum:local` (or every one with `--all`), runs their stages in sandboxes on your machine, and resumes its own paused work first ([LOCAL.md](LOCAL.md)).
- **Task card:** the short brief Pendulum gives the worker at the start of its session: the issue to complete, the budget, the skills to follow in order, the validation commands and the protected paths.
- **Decider (decision check):** a model Pendulum asks one structured question, such as whether a red check is flaky or whether your comment answers a Question. Pendulum acts only on a verdict at its confidence floor. `decision_route` picks who answers: the Vercel AI Gateway, the stage's own harness, or no one ([ADAPTERS.md](ADAPTERS.md), Decision model).
- **Blocked (a Block):** Pendulum could not finish and hands the Objective back to you. One comment on the issue gives the reason, the issue carries `pendulum:blocked`, and the PR, if any, becomes a draft (Blocked and Question, below).
- **Question:** the work depends on a decision that should be yours. The worker finishes the rest and asks in the draft PR, or on the issue before any code. The issue carries `pendulum:question` (Blocked and Question, below).
- **Hand-over:** a change under `.github/workflows/` that Pendulum never pushes. Pendulum posts the exact change on the issue and labels it `pendulum:handover`, and you apply it with `pendulum handover <issue>` (Workflow changes, below).
- **Walk-away:** an Objective that merged with no human input after its label: no push, comment, review, edit or draft/ready toggle by a person on the branch or the issue. It is the scorecard's first number ([bench/README.md](../bench/README.md)).

## Write an Objective

An Objective is a GitHub issue with the `pendulum:objective` label: a feature or an epic, which the worker plans, splits across implementer sub-agents and delivers as one or more pull requests. A quick fix is better as a direct pull request. The issue is the whole specification: write everything the work needs into it. The worker asks you something only when the work depends on a decision that should be yours (a Question, below). Ask a session to file one for you ("File a Pendulum Objective: ...", the pendulum-file skill), which starts it or saves it as a draft to refine and start later (An Objective's lifecycle, below), or write the issue yourself:

- **State the goal and what must be true when it is done.** Put the acceptance entries in a list under a heading that is exactly `Acceptance` (any level; lists under its sub-headings count too, so out-of-scope notes go in another section). The reviewer judges each entry, met or not, with the line that shows it. Without that heading, the reviewer names the entries from the issue text itself.
- **Order it after another Objective** by adding a GitHub issue dependency (blocked by) before the issue carries `pendulum:objective`, which starts it at once: the dispatcher then starts it once that issue is closed. A `Blocked by #N` line in the body is read only where GitHub's issue dependencies are unavailable.
- **Say what you have decided.** Where the issue admits more than one reading, the worker takes the simplest one that satisfies every acceptance entry and records it as an assumption in its plan and in the PR.
- **File it yourself, or have someone who can push file it.** Pendulum acts on an issue only when its author, its last editor once the body was edited, and whoever made its latest rename once the title was renamed, can push to the repository or are maintainers the workflow names. Otherwise the run Blocks before any model sees the text. A maintainer labelling someone else's issue is not enough: the author is checked on every run, so such an issue needs refiling by someone who can push.
- **Keep it to one repository** (below).
- **Route it, in local mode:** `pendulum serve` takes the Objectives labelled `pendulum:local`. Where no Action runs (GitHub lists no active `pendulum.yml` workflow for the repository), it takes every Objective and labels each `pendulum:local` as it picks it, so it stays your machine's if the Action is enabled later. With the Action active, an Objective without `pendulum:local` is the Action's: add `pendulum:local` to run it on your machine. `serve` says once per start how many queued Objectives it leaves to the Action ([LOCAL.md](LOCAL.md), Routing).

```markdown
## Goal

`mytool list` can print its records as JSON, so scripts can use them without parsing the table.

## Acceptance

- `mytool list --format json` prints a JSON array with one object per record, holding the fields the table shows, and exits 0.
- `mytool list` and `mytool list --format table` print the table as before.
- An unknown format exits 2 with an error that names the accepted values.
- Tests cover each case, and the README documents the option.

## Context

- No new dependencies.
```

Ready Objectives start in priority order (`P0` to `P2`, then the lowest issue number), up to `max_concurrent` at once; one started by hand with `gh workflow run pendulum.yml -f issue=<number>` runs even when that limit is reached. An Objective too large for one session is delivered as up to six pull requests in sequence, one open at a time.

## Choose the harness and models

The workflow file's `PENDULUM_HARNESS`, `PENDULUM_MODEL`, `PENDULUM_SUBAGENT_MODEL` and `PENDULUM_REVIEWER_MODEL` are the repository's defaults, and doctor lists them. A label on the issue overrides one of them for that Objective alone; an issue with none runs on the defaults.

| Label | Overrides |
| --- | --- |
| `pendulum:harness:<name>`: `claude`, `codex` or `copilot` | `PENDULUM_HARNESS`. The models no label names become that harness's own defaults, as with any switch of harness. |
| `pendulum:model:<id>` | `PENDULUM_MODEL`: the worker, and its fix and answer passes. |
| `pendulum:subagent-model:<id>` | `PENDULUM_SUBAGENT_MODEL`: the implementer sub-agents. |
| `pendulum:reviewer-model:<id>` | `PENDULUM_REVIEWER_MODEL`: the reviewer. |

- **Apply them when you file the issue,** with `pendulum:objective` (`gh issue create … --label pendulum:objective --label pendulum:model:claude-sonnet-5-5`; `gh label create <name>` first makes a label the repository lacks). The pendulum-file skill offers them.
- **Who applied a label counts.** Pendulum acts on one only when the person who last applied it, by the issue's timeline, can push or is a maintainer the workflow names, since GitHub lets anyone with triage access apply labels. Otherwise the Objective Blocks before any spend, naming the label. Starting an Objective is checked the same way, with another outcome: `pendulum:objective` applied (the first time, again after a stop, or re-applied to a Blocked, Question or In-review Objective), a draft started by taking `pendulum:draft` off, and `pendulum:restart` each count only from a person (never a bot or an App) who can push or is a maintainer the workflow names. Anyone else's changes nothing: the Objective stays as it was and does not run on it, one comment on the issue says it was not taken, and a refused `pendulum:restart` is taken off. Taking a label off is not checked, since GitHub does not ask who may: before the plan, a label anyone with triage access removes sends the Objective back to the repository's default; after the plan, a removal Blocks it as an edit (below).
- **A choice it cannot run Blocks before any spend,** naming the label and the fix: two labels of one kind, a harness Pendulum does not run, or a model the harness cannot run. Claude Code takes any id, since whether its login serves the model is Anthropic's answer. A main session's model (`pendulum:model:`, and `pendulum:reviewer-model:` for the review) is refused before any token is billed; a sub-agent's (`pendulum:subagent-model:`, or `pendulum:reviewer-model:` for a reviewer sub-agent) when that sub-agent first starts, where the stage stops the run, with the main model's spend so far billed. Either way the stage Blocks naming it. Codex runs a model with a row in Pendulum's Codex price table (`plugin/scripts/lib/codex-prices.json`), since without one `max_usd` could not stop its runs; a provider prefix (`openai/`) is taken only with the AI Gateway key, and Pendulum adds it itself. Copilot's model names come from its own catalog, which varies by account and which Pendulum cannot read before a run, so Pendulum checks only the form (no provider prefix or spaces): a name the account's Copilot does not offer is not caught before Copilot starts. `max_usd` and `daily_usd` apply whatever the model.
- **GitHub caps a label name at 50 characters,** so an id fits in 35 characters after `pendulum:model:` and in 26 after `pendulum:subagent-model:` or `pendulum:reviewer-model:`. Every model in Pendulum's price tables and defaults fits; GitHub refuses a longer name, so use the model's id without its date suffix, or make it the repository's default.
- **Every route honours it.** The Action's work and review jobs read the harness label before they install a harness, and install that one; the workflow hands each job every harness's secret, so the chosen harness needs its own secret (a missing one Blocks the Objective, naming it). The cloud-sandbox launcher hands the stage that harness's credential and the repository's defaults, so the stage reads the labels again, and Blocks before any sandbox call when the launch job holds none. `harness_version` pins the harness the workflow's env block names only: a harness a label, a run's override or a repository variable chooses installs its latest. Local mode (`pendulum serve`, `pendulum run`) runs another harness than its own when this machine can (its CLI and its sandbox, and for Copilot its token, as `pendulum serve` checks its own at start), else Blocks the Objective, and the loop's log names what is missing. A stage that finds its labels name another harness than the one its job, sandbox or loop prepared for Blocks; re-apply `pendulum:objective`. `/pendulum:pendulum-run --here` runs in your own session, on its harness and model, whatever the labels say.
- **A manual run's `harness` input** (`gh workflow run pendulum.yml -f issue=<number> -f harness=codex`) overrides the default for that run; a harness label on the issue wins over it.
- **A label added, removed or changed after the plan is an edit** (Edit an Objective, below): the next stage Blocks, re-applying `pendulum:objective` plans again on the new choice, and `pendulum:restart` starts over with it.
- **What ran is on the record:** the progress comment's harness line, the usage record's `ran` and the scorecard's Harness column name the harness, the worker, sub-agent and reviewer models, and the labels that chose them, and the account each stage ran on (LOCAL.md, Accounts; INSTALL.md, Several accounts).
- **The account too:** `pendulum:account:<name>` moves an Objective to another account of its harness: in local mode one the machine that runs it declares, for instance when a usage limit pauses it (LOCAL.md, Accounts); on Actions and the cloud sandbox one the workflow declares (INSTALL.md, Several accounts), where with none declared it does nothing and the progress comment says so. It is trusted like the labels above, but it is no edit: adding or removing it after the plan Blocks nothing.

## Ask for a foundation review

Label an Objective `pendulum:foundation` when later work builds on what it adds: a shared type or schema, an error table, a command registry, a file format, a test fixture other tests import. Its review then runs a second reviewer call, the foundation pass, after the usual one.

- **What it checks:** each shared contract the diff adds or changes (an exported function, type, schema, error code, CLI flag, file format, shared fixture) against its callers and readers in the repository: every value it can produce reaches the caller meant to handle it, every caller uses what it now says, and a shared test fixture keeps tests off the developer's real home, state and proxy settings (the pendulum-review-pr skill's reference.md, "Foundation review").
- **One review:** its findings are line-tied comments in the same comment-only review as the usual pass's, and the worker's answer pass answers them all. The review body counts them.
- **Within `max_usd`:** the pass is one more call on the reviewer model, as its own `foundation-reviewer` agent definition, so a foundation review costs about one more reviewer call. It starts only with budget and time left; at the cap or the time cap the stage Blocks before it, and nothing is posted, as for the usual pass. A call that fails is run once more; when neither answers, nothing is posted and the Objective Blocks with how each call ended.
- **Trusted like the harness and model labels:** it counts only when the person who last applied it can push or is a maintainer the workflow names; otherwise the Objective Blocks naming the label.
- **Not an edit:** it changes only the review, so adding or removing it after the plan Blocks nothing; the review reads it when it starts. A PR reviewed before the label was added gets the foundation pass alone, as its own review, at its next review stage (re-apply `pendulum:review`, or the rebase or resume that brings one). Add it before the PR is delivered: a PR already waiting for its checks to merge merges on its earlier review. An Objective without it is reviewed in one pass.

## Open a network host for one Objective

Every Objective's sandboxes reach GitHub, the npm and Yarn registries and the hosts the repository allows for all of them (the `allowed_domains` input; `PENDULUM_LOCAL_DOMAINS` in local mode). An Objective that needs one more host (a model hub, a vendor's API) gets it for itself with a label, `pendulum:host:<host>`: `pendulum:host:huggingface.co`, or `pendulum:host:*.hf.co` for that domain's subdomains. One label per host; apply as many as it needs.

- **It opens that host to this Objective's sandboxes alone,** on every route: the work stage, the reviewer and the fix and answer passes, on Actions, in a cloud sandbox and in local mode. No other Objective's sandbox gets it, and `/pendulum:pendulum-run --here` runs in your own session, outside Pendulum's sandboxes.
- **Who applied it counts,** as for a harness or model label: Pendulum opens the host only when the person who last applied the label can push or is a maintainer the workflow names. A label anyone else applied Blocks the Objective before any spend, naming it.
- **A host name, nothing else:** a name such as `example.com`, or `*.` and one; no scheme, port, path, IP address or `localhost`. A label naming anything else Blocks, naming it. GitHub caps a label at 50 characters, which leaves 36 for the host; a longer one goes in the repository's setting.
- **What the rule does not catch, so the person applying the label must:** the check is on the name alone. `*.` is refused over a name the Public Suffix List (its private section included) holds as a public suffix, or holds one below (`*.co.uk`, `*.github.io`, `*.amazonaws.com`, which holds `s3.amazonaws.com`), and over a top-level name alone (`*.com`); but a name that resolves to a loopback or link-local address (a service on the machine, a cloud metadata endpoint) is not refused. In local mode the label lets anyone who can push open a host from your machine, without a change to your `PENDULUM_LOCAL_DOMAINS`. Apply the narrowest host the work needs.
- **A host label added, removed or changed after the plan is an edit,** as for the other labels (Edit an Objective, below).
- **The Block for a denied host names both fixes:** the host label for this Objective, and the repository's setting for every Objective.
- **Where to see them:** the progress comment's Network line, the usage record's `ran.hosts`, and doctor's `objective hosts` line, which lists each open Objective's hosts.

## Run an experiment

To compare a model, an effort or a setting on real Objectives, run some Objectives one way and some the other, and tag each with its arm: `pendulum:experiment:<name>`, for instance `pendulum:experiment:sonnet` on the Objectives you ran with `pendulum:model:claude-sonnet-5-5` and `pendulum:experiment:opus` on the others. Then `pendulum report --compare sonnet,opus` puts the two arms side by side from Pendulum's own records ([REPORT.md](REPORT.md), Compare two arms): per arm n, and per merged Objective the median and p25..p75 of the dollars of each billing kind, the model minutes, the wall clock, the review rounds and the fix passes, with the runs of unknown cost. It claims no significance and adds nothing across kinds; every measure says its n, and each arm's rows are shown.

- **It only tags the Objective.** The label changes nothing Pendulum runs: set the arm's model, effort or setting itself (a label above, or the workflow's setting). Adding or removing it, before or after the plan, Blocks nothing.
- **Who applied it counts:** the report counts the label only when the person who last applied it, by the issue's timeline, can push or is a maintainer the workflow names. A label anyone else applied, or a bot or an App, leaves the Objective out of the arm, and the report lists it.
- **A name:** letters, digits, `.`, `_` and `-`, up to 30 characters (GitHub caps a label at 50). An Objective with both arms' labels is in neither.
- **Any two labels** can be compared too: `pendulum report --compare-label wave-6 --compare-label wave-7`, with the same check on who applied them.

## What you see on the issue

While a job runs, one comment on the issue (edited in place, one per run) reads at a glance, in the finish card's look. Its first line names the state (⏳ running, ✅ delivered, ⛔ Blocked, ❓ has a Question, ⏸️ paused or waiting, ⏹️ stopped), the stage, its PR (or the issue), how long it has run and its cost in dollars and cents; the second line gives its times, what the dollars are (API-equivalent, not billed; billed to your API key; Copilot AI credits, billed to your seat) and its AI runs of unknown cost, never counted as $0. A Blocked, Question, paused or waiting stage has a "What to do" line under it, with the reason or the question. The table has one row per kind of step (Set up, Built the change, Waited for CI, Fixed CI, Flake check, Reviewed the change, Answered N review comments, Checked the answers, AI judge calls) in order of its first time, ×N for repeats, how long it took and its own cost; a CI loop of any length stays three rows. Took comes only from recorded starts and ends (an AI run's record, a wait's own start and end), and — means no AI ran in that step. While the stage runs, its last row says which step is in progress (none between steps), and an AI run's cost shows in its own row and the headline as soon as the run ends; at the end, a Total row and a collapsed timeline chart. Times are in the Objective's zone ([INSTALL.md](INSTALL.md#time-zone), Time zone), with dates only when a run crosses midnight. A collapsed **Run details** block holds the run, the agent and models, the session, the AI judge's verdicts, what the unknown-cost runs are, and the **Full log**: the stage's header and every line with its clock (setup, install, harness, each validation pass, reviewer, answer pass, exit), as the scorecard reads them. The marker lines (harness, spend, ledger, findings) follow it, unchanged. Near GitHub's comment size limit the chart goes first, then the Step cells shorten, then Run details' explanations, then the ledger line's cut form; the Full log's middle lines go only when GitHub would refuse the comment otherwise. A cloud sandbox stage's vendor comment has the same two-line headline over its line. The review starts while the PR's first required-check run is still going: its reviewer line then ends `beside the required checks on <sha>`, and a later line says when the checks ended (`... while the reviewer runs`) or that the stage waits for them after the reviewer. The last row's live status comes from the harness's own event stream, not from its prose: elapsed minutes, turns, tool calls, the sub-agents running and what each was asked to do, when the last event arrived, tokens so far, the last tool it ran. Silence alone kills no harness. Pendulum checks a running harness every 30 minutes, and one that printed nothing across such a window is killed as hung, and retried once, only when its own state says so. With a command open in its stream, it is hung when no command process of the run used CPU or read or wrote a byte, counted from when Pendulum first finds them. A command process is any process the harness started that does not write its stream and is not a helper from the harness's own install directory, so a background server left from an earlier command counts too; a long build, test or download that prints nothing goes on until the wall clock. With none open, the harness is waiting on its model: Claude Code and Copilot print the answer as it arrives (Pendulum runs them with `--include-partial-messages` and `--stream on`, and keeps those lines out of the events file), so one silent for the window has a stalled model stream and is hung. Codex prints no such lines and ends a stalled model stream itself (its `stream_idle_timeout_ms`, then its retries), so its silence with nothing open decides nothing. Work outside the harness's own processes (a Docker daemon's containers, a daemon started before the run, a remote build) counts as no progress, and so does a command that waits on purpose. On macOS Pendulum reads no I/O counts, so an open command there is judged by its CPU alone. Whatever Pendulum cannot read decides nothing. The line says so when a harness is killed. The labels (`pendulum:running`, `pendulum:in-review`, `pendulum:blocked`, `pendulum:question`) and the board column are the state; the plan comment is the harness's own checklist, ticked as it goes; the PR carries the validation marker (or, while its first required-check run goes on beside the review, the hand-off marker) and the review.

## An Objective's lifecycle

Each step is one action on GitHub. Where a skill is named, a plain-words request to your agent takes that action after asking you.

- **Draft.** An issue with the `pendulum:draft` label is a draft: Pendulum never runs it, on any route, even with `pendulum:objective` on it too (the draft label wins: the dispatcher's log lists it as a draft, and a launch, `pendulum run` or a session's `pendulum issue` refuses it). Nothing is dispatched, claimed or spent for it. The pendulum-file skill offers it beside starting at once: it shows the issue and asks whether to start it now, save it as a draft, or keep discussing. "Let's keep working on Pendulum Objective #12" (the same skill) loads the draft from GitHub to refine it with you and saves the changes back to the issue only on your yes. Edit a draft freely: before its first plan, an edit is simply the text the run starts from.

- **Start.** Applying `pendulum:objective` starts the Objective: the dispatcher picks it up on the label's own event, else on its ten-minute cron, and in local mode on `pendulum serve`'s next tick. To start a draft, take `pendulum:draft` off and apply `pendulum:objective`, or ask "Start Pendulum Objective #12" (the pendulum-file skill): on your yes it does both, after the trust check a new Objective gets (its author, its last editor and its latest title renamer can push, or are maintainers the workflow names; otherwise it refuses and says who). Starting a draft counts as re-applying the label, whichever way it is done: an edit made while it was a draft, even after an earlier plan, is planned from. A draft started, then edited, follows the edit rules below once its plan exists.

- **Edit.** Edit the issue freely until the first work stage reads it. After its plan, an edit that only fixes typos, formatting or wording keeps the plan; any other edit Blocks the Objective at its next stage, and re-applying `pendulum:objective` plans again from the new text (Edit an Objective, below).

- **Restart.** Apply `pendulum:restart` to start over from the issue's current text, in any state: Queued, Running, In review, Blocked or a Question ("Restart Pendulum Objective #12", the pendulum-restart skill, applies it on your yes). Only someone who can push, or a maintainer the workflow names, restarts an Objective: anyone else's label is taken off with a comment (a running stage may already have stopped on seeing it; re-applying `pendulum:objective` resumes the Objective). A running stage stops first, as for a stop, its spend so far recorded, and nothing merges or starts meanwhile. Then the dispatcher writes a restart record on the issue (when the label was applied, who applied it, and what the restart discards: the earlier PR with its review, and the deleted branch's commits, whose last one `git push origin <sha>:refs/heads/pendulum/<issue>` restores), deletes the `pendulum/<issue>` branch, closes the earlier PR with a comment linking the record (its commits and review stay readable on it), sets the earlier plan and a split's part record aside, removes the state labels and the restart label, and queues the Objective; it starts from the default branch, and comments made before the label was applied do not feed it. When a ruleset keeps GitHub from deleting the branch, the Objective is Blocked with the fix instead: nothing is discarded, and its earlier PR, plan and comments stay as they were. The retry and rebase counts start over, and the scorecard counts the restart as a human action. On a stopped Objective the restart waits until `pendulum:objective` is back. A workflow file rendered before this release sees a restart only on the ten-minute cron until it is re-rendered ([INSTALL.md](INSTALL.md), Upgrade). To go on after a fix or an answer instead, re-apply `pendulum:objective`: that continues from the branch and PR.

- **Stop.** Remove the `pendulum:objective` label, or close the issue ("Stop Pendulum Objective #12", the pendulum-stop skill, removes the label on your yes). No dispatcher tick, local loop or sandbox launch picks up a stopped Objective, and your other Objectives keep running. What happens depends on its state:
  - **Running, or a review running:** the stage reads its issue once a minute. On the stop it ends its harness run, records the spend so far in its usage record (locally and in a cloud sandbox also in its progress comment's spend line, as every stage does) and exits, normally within two minutes; its progress comment's last line reads `exit: stopped`. Its PR, if it has one, becomes a draft without the `pendulum:review` label; its state label comes off and its card goes back to Queued. With the cloud sandbox the launcher then stops the sandbox. A Running Objective whose stage died before it saw the stop is tidied the same way by the dispatcher, ten minutes after the label came off.
  - **In review with no stage running:** on its next tick the dispatcher takes the PR out of the merge queue, makes it a draft without the `pendulum:review` label, removes the state label and moves the card to Queued, so neither a review nor the merge queue takes it. On Actions the label's removal ticks it (a workflow file rendered before this release waits for the ten-minute cron until it is re-rendered: [INSTALL.md](INSTALL.md), Upgrade); locally `pendulum serve` ticks every 30 seconds.
  - **Queued, Blocked or a Question:** it stays as it is.

  Applying `pendulum:draft` to an Objective stops it the same way, whatever its state, and keeps it a draft until it is started again.

  Re-apply the label to start it again: it continues from its branch and PR, as after a Block. Closing the issue stops it the same way and then counts as done: the dispatcher's Done pass removes its state label, moves its card to Done and makes a PR it left open a draft, and with the cloud sandbox the sweep destroys its sandbox.

## Edit an Objective

Edit the issue as much as you like until the worker reads it: the first work stage makes its plan from the title, the body and the harness, model and host labels as they are when it starts. After that, the plan and the code follow that text, and an edit to the title or body, or a harness, model or host label added, removed or changed, does not reach the run halfway:

- The stage running when you edit finishes on the text it read. The next one (the review, the merge, or a work stage Pendulum starts on its own, such as a rebase) first asks the decision model whether an edit to the title or body changes what has to be built, once per new text. A typo, formatting or wording-only edit keeps the plan and the code, the run goes on, and the stage's progress comment says so (`edit judged wording-only by <decider> (<confidence>); plan kept`). A harness, model or host label added, removed or changed always counts as a changed requirement. Any other edit, or one the model cannot judge (no decider: `decision_route` off, or `gateway` with no key), stops the Objective as Blocked, saying the Objective changed after its plan was made, and the PR, if there is one, becomes a draft. A PR already in the merge queue is taken out of it. Nothing goes on with a plan made from one text and an issue that says another.
- Saving the issue without changing it is no edit: line endings and trailing spaces do not count. That needs the record of its text Pendulum keeps on the plan comment: a plan comment without one (an older plan) gets it at the next work stage, and until then any save after the plan counts as an edit.
- Re-apply `pendulum:objective` to work from the new text: the work stage that starts after it makes its plan again from the text as it then is, on the same branch and PR. That holds after a kept edit too: re-applying the label is your word that the plan should be made again. An edit made while the Objective is Blocked or has a Question is used the same way once you re-apply the label. Only the label counts: starting the Objective by hand (`gh workflow run pendulum.yml -f issue=<number>`, or `pendulum run <number>` in local mode) after such an edit Blocks it again. To start over from the new text instead, with the earlier PR closed and a new branch from the default one, apply `pendulum:restart` (An Objective's lifecycle, above).
- Comments are not edits. A comment that answers a Question, or records a decision, leaves the plan as it is.
- A comment by someone who can push that no pass has read holds a reviewed PR's merge: the review stage applies it first. A review that requests changes always holds it. Otherwise, when the decision model reads the unread comments as asking for nothing (an approval, thanks, an acknowledgement), and none arrived or changed while it read them, the PR merges, and the merge's progress comment says so (`comment check: ... read as asking nothing by <decider> (<confidence>)`). With no decider, every such comment holds the merge.
- An edit is checked like the text you first wrote: when its editor cannot push and is not a maintainer the workflow names, the run Blocks (above), before any edit check.
- So is a rename: when whoever last renamed the title cannot push and is not a maintainer the workflow names, the next work or review stage Blocks on the trust check, before or after the plan, with this fix; a merge pass that comes first never judges such a rename and Blocks it as a change after the plan. A person who can push fixes it by changing the title (saving the same title records no rename), then re-applies `pendulum:objective`.
- A harness, model or host label change is never judged wording only: it counts as an edit, as above.

## Blocked and Question

A run that goes well needs nothing from you. When one needs you, Pendulum does all the work it can first and then hands the Objective back to you in one of two states. Neither holds up the queue: your other Objectives keep running.

- **Blocked** means Pendulum could not finish. One comment on the issue gives the reason, the fix and whether to resume or restart; the issue's card moves to the Blocked column (on a repository a user owns there is no board; the `pendulum:blocked` label says it), and the PR, if it opened one, becomes a draft.
- **Question** means the work depends on a decision that should be yours: one that would change or remove an existing public contract, contradict a recorded decision or grant new access. The worker takes the simplest reading, finishes everything else, and leaves a draft PR whose body asks what a human must decide. A Question about working in another repository comes earlier, on the issue itself, with no PR (One repository per Objective, below).

What to do with each ("Why is Pendulum Objective 12 Blocked?", the pendulum-status skill, reads the notice and offers the step on your yes):

- **Blocked:** fix what the comment names, then re-apply `pendulum:objective` to run the Objective again: that resumes from its branch and PR. When your fix was an edit to the issue, the worker makes its plan again from the new text. Apply `pendulum:restart` only when the work itself must be redone: it discards the PR, its review, the branch's commits and the spend on them. The comment says which fits: resume whenever the stop was outside the work. When the red was CI's, its quoted output leads with the required checks that are red, by name; failing jobs no required check counts are marked `not required`.
- **Red checks a fix pass could not change:** when a fix pass commits nothing and the required checks stay red for a reason in the code, Pendulum first gives the Objective one fresh worker pass: a new session handed the failing output, once per head in a stage, and only when what is left of `max_usd` covers what the fix pass cost and the stage has time for another pass and its checks. A Block that names both passes means a fresh session could not fix it either. One that says `no fresh worker pass` or that the fresh pass reached a cap gives the reason. Read the failing job on GitHub, fix the cause on the branch, then re-apply the label.
- **Lost to the network:** on GitHub Actions and the cloud sandbox, a stage whose runner or sandbox lost its network (its outage notice, which mentions no one, names the host) or vanished without a word is relaunched on its own, at most twice since you last started the Objective, its work resuming from its branch and PR; a Pendulum comment on the issue counts them. A relaunch waits while today's spend has reached `daily_usd` or `max_concurrent` Objectives run, and each stage spends within `max_usd`, so a start can spend up to three times `max_usd` before you hear of it. Only then is it Blocked, the notice saying how many relaunches were tried; re-apply the label once the network is back, and the count starts over. A stage cancelled on Actions (by a person or its timeout), or a sandbox stage that recorded its end, is not a network loss: it is Blocked, not relaunched. A work job that failed at a step before Pendulum's own (a checkout, GitHub's job set-up) or that GitHub never started is relaunched once; when the relaunch fails at the same step, it Blocks with the cause `setup`, naming the step. The local route pauses and resumes such a stage instead ([LOCAL.md](LOCAL.md)).
- **Question:** comment the decision on the issue or the PR (a review or a line comment works too) and mark the PR ready: the review job applies it, and with no answer since the question the PR goes back to a Question rather than merging. A Question asked on the issue (one with no PR, or the plan-time Question; its notice says to answer on the issue) needs only the comment on the issue: on every route the Objective goes back to the queue at the dispatcher's next tick (local mode: `serve`'s), and the worker runs again with the answer. A decision model reads whether your comments since the Question decide it (the answer check, PLAN.md): one that does not, such as "I'll look tomorrow", leaves the Question open, and Pendulum says so once on the issue; edit the comment or write another to answer. With no decision model (`decision_route` off, or `gateway` with no key), any comment resumes it. Re-applying `pendulum:objective` instead reruns the worker with it, unjudged, and wins over a ready mark beside it: the mark starts no review (on the Action, its review job ends at once). A review that was already under way when the label came runs to its end first, and the worker never starts beside it; re-apply the label after it if the worker should still run.

A comment counts when its author has write access to the repository or is a maintainer the workflow names (`notify`, and the optional `maintainers` list), since an App cannot always see an organization member's access.

An agent that supervises the queue for you can wait on it instead of watching logs: `pendulum wait` exits with one JSON line per Objective that Blocked, asked a Question, went In review, merged or closed since the last read, or when the queue drains, within a poll (30 seconds) of the change, on every route ([LOCAL.md](LOCAL.md), Run it). The @mention to a person stays as it is.

## Pendulum merges on its own

Code lands with no human read. The gate is your CI workflow's checks on the reviewed head and the integrated commit, the comment-only reviewer pass, and the merge queue's own re-run where you have one. Set `PENDULUM_AUTO_MERGE: false` for ready-for-review PRs instead.

The reviewer reads the PR while its first CI run is still going. A red found then is not a separate fix pass: the answer pass fixes it with the reviewer's comments. A red merge-queue run whose failure is in the PR's own change gets one fix pass too, before any Block (at most two per start of the Objective), so your CI can run a light check on the PR and the full suite only in the merge queue. Without red-check triage (`decision_route` off, or `gateway` with no AI Gateway key) a queue failure counts as the PR's own only when it names a file or test the PR changed. A flaky or infrastructure red in the queue, or one Pendulum cannot read, is enqueued again once, as any drop (a job cancelled is never read as a flake: one stopped at its time limit gets the fix pass, a red that is only a cancel by hand Blocks); the same failure red again after its fix pass Blocks, naming the failed job and its first failing line.

## The finish card

When an Objective's run ends, Pendulum posts one comment on its issue that sums the run up, in the same look as the stage's progress comment, text only (no image or badge): a headline with how it ended (✅ merged, ⛔ Blocked, ❓ Question, ⏹️ closed without merging), how long it took and what it cost, a second line with the issue and its PRs, when it ended, what the dollars are (API-equivalent, not billed; billed to your API key; Copilot AI credits, billed to your seat) and its runs of unknown cost, and, when it waited on you, how long it was on hold. A Blocked card adds what to do and why, a Question card how to answer and the question. Then a sentence on who did what, a timeline of the stages (repeated names numbered, a stage that ended Blocked or on a Question in red with its word, time on hold in grey from Pendulum's notice to the next stage's start, named by what it waited on when the notice says: you, an outage or a usage limit), the stage table that holds the timeline's figures (time, stage, how long, cost, the merge queue and a Total), where the money went (a one-colour bar chart of the recorded dollars beside its tables, the overhead Pendulum caused apart), one notes line, and Run details: what the dollars are, the unknown cost by cause, where the figures come from, how overhead is counted, and the run log. On GitHub Actions and in a cloud sandbox the merged PR's body gets the card's headline block at its top; a local loop, which acts under your login, leaves the PR body alone.

Under its marker the card carries one hidden line, its summary: the same figures and each stage's passes from its per-pass ledger, machine-readable and versioned, so `pendulum report` reads a merged Objective from that one comment ([REPORT.md](REPORT.md#the-finish-cards-summary)); and a line saying how the run ended and when. A card of an end other than a merge names that end and no merge, so no reader takes it for a merged Objective's.

One card per Objective, written in place as the run ends again: every Block or Question Pendulum applies writes it (waiting at most 20 seconds for it before going on), a later Block or Question rewrites it, and the merge or the close rewrites it once more. A Block or Question card counts only the run's own PRs: a split Objective's earlier part that merged, or a PR merged before a reopened Objective's clock, is no merge of it. A merged card is final: a reopened Objective that merges again, or Blocks, keeps it. A second close rewrites a close's card only when it is a later close. Each write reads the card again just before it writes, so one that raced another never puts an older end over a newer one, and two cards that both got posted become one again. The dispatcher's Done pass writes the card of a closed Objective that Pendulum ran (one with a state label at its close), merged or not, at the first tick that tidies it, on one route only: `pendulum serve` for an Objective with `pendulum:local`, the Action's dispatcher for any other. The other route leaves the issue's state label for the route that posts it, for up to a day after the close, since that label is what the posting route's Done pass acts on, and stops a PR still open at once (out of the merge queue, back to a draft; a PR already stopped is left alone); past that day it tidies the issue without a card. So the Action's run on a `pendulum:local` Objective's close leaves it to `serve`, and a loop run with `--all` leaves the Action's Objectives to the Action, never writing a second card beside a running Action. A card that meets a passing failure (a GitHub server error, its rate limit, the network) leaves the state label on for a later tick (the next cron tick or loop pass; no wake of its own) to try again, for up to a day after the close, a PR still open stopped meanwhile; after that, or on any other failure, the tidy goes on without it. A refused write of the PR body leaves the PR as it is and the card is written anyway. A closed Objective with no stage and no PR gets none.

Every figure comes from a record, never an estimate. The card trusts Pendulum's markers only on Pendulum's own comments: its login on this route, or its App matched by id (the Action's `app_id`, or a local loop's `PENDULUM_LOCAL_APP_ID`); no other App or bot, `github-actions[bot]` included. A stage comment written by someone else who can push, or through a GitHub App other than GitHub Actions (another route's login or App, after an Objective moved between routes, including the Action's App when a local loop has no `PENDULUM_LOCAL_APP_ID` to match it by), counts as a run of unknown cost: its stage shows, never its dollars, and the total says "+ unknown". Their plan, review, notice and finish markers count for nothing, and anyone else's count for nothing at all. When the card finds no stage at all, its cost shows as unknown, never $0:

- **Times:** the clock starts at the `pendulum:objective` label (as the scorecard's does) and stops at the merge, or at the Block, the Question or the close. Each stage's bar runs from its progress comment's first write to its last; each merge queue entry from its addition to its removal or the merge; time on hold from Pendulum's Blocked or Question notice to the next stage's start (a notice no stage follows yet holds nothing). Times are in the Objective's zone (INSTALL.md, Time zone), whose short name the timeline's heading and the run log carry, with dates when the run crosses midnight; the summary line keeps them in UTC. The timeline's bars use the zone's offset at the Objective's start throughout, so across a daylight-saving change the later bars' clock reads an hour off while every bar keeps its true length.
- **Stages:** named from their records only: the Objective's first work stage is its build ("Plan + build" with a plan comment), the first after a split part merged is that part ("Part 2"), one with a rebase line is a rebase, any other work stage is "Work", and a review stage is a review; a name that repeats is numbered ("Review 2"). A stage ended Blocked or on a Question when Pendulum's notice of it falls within its span. Past 20 stage rows, like stages in a row (kind, model, result) fold into one ("Review ×3"), each stage listed in Run details; past 20 timeline rows the chart is left out. Over GitHub's 65,536 characters the card leaves out its run log, then that list, then the cost chart.
- **Dollars:** each stage's own figure: the spend line in its progress comment, which every stage writes on every route, else its usage artifact (`pendulum-usage-<issue>` and `-review`, read with the job token's `actions: read` for a stage with no spend line, and for the model alone of a stage whose harness line names none (Copilot at its default model) and that has no per-pass ledger line beside its spend line to name it ([REPORT.md](REPORT.md), The per-pass ledger), and only that stage's own workflow run's, matched by the run id its progress comment names; a run on another repository's code, a fork's pull request, is never read). A stage with neither (an artifact that cannot be downloaded included), or one whose harness did not report its cost, shows as unknown, and the totals say "+ unknown"; a stage that ran no harness pass is $0. A cloud sandbox's own cost is a row of its own, its vendor comment counted whenever it was written; a sandbox whose usage the vendor did not report is a run of unknown cost, its dollars or none; a vendor comment someone else wrote of one of the Objective's stages is that stage's, and one of no stage is a run of unknown cost; a sandbox stage that wrote no progress comment is a row too. The rows' cents add up to the total's; a row under a cent reads "<$0.01", never $0.00. Your CI minutes are not included. What the dollars are comes from the usage records' and spend lines' dollars by billing (`usdByBilling`), said once on the headline's second line; a mix gives each kind's share. Dollars whose billing was not recorded (the `unknown` kind, or a record or sandbox cost that names none) read "billing not recorded", never as API-equivalent.
- **Where the money went:** shown for a split Objective, for any overhead, or when a stage ran answer or fix passes. A bar chart of the recorded dollars (one amber series, each bar's figure in its label; a row with only unknown cost gets no bar, and the notes line names what is not drawn) above two tables, their rows' cents adding up to the total's. Every item comes from a stage's own record, never from what the card works out:
  - *What the issue asked for*, per split part ("Part 2: review"; a stage is in the part after the PRs merged before it started) and per kind: work, review, answering the review, fixing CI, AI judge calls. A stage's dollars by pass kind come from its spend line or usage artifact (`usdByPass`, each pass named by its label: `work-<n>`, the reviewer's passes, `answer`, a validation loop's fix passes; its decision calls under `decision`); the rest of the stage (its exit record) stays under the stage's own kind. A stage whose kinds do not fit inside its own figure, or whose figure is unknown, stays whole. The cloud sandbox's own cost is a row of its own.
  - *Overhead Pendulum caused*, with how many stages each came from: a send-back's rebase after other PRs merged, the whole stage (its rebase line; conflict or clean, by the line's `conflict`); a work stage's catch-up pass after the default branch changed a workflow during the run (its `conflict` passes); the runs a stage records it ran again after a Block (its `rerun`: the first stage after one of Pendulum's Blocked notices records the notice and, for a work stage that ran its prompt in a fresh session over the PR an earlier stage made, that prompt; a review runs its reviewer once per PR, so it names none); and a review stage that records it was started only to judge answers already made (its `judgeOnly`, from the answer-rounds record of its own PR since the last re-entry), all of it but its answer and fix passes. A Blocked notice or an answer-rounds record on the issue names nothing by itself; anything else stays in its stage, as that stage, never as overhead.
- **People:** "You wrote the issue and added the label" when the issue's author applied the label that started the clock; otherwise each is named.
- **The change:** commits, lines added and removed and files changed, from the merged PR (every merged part of a split Objective, added up); said as what Pendulum opened when Pendulum's login opened the PRs, else as what the PRs have.
- **CI checks:** the check runs on the commit that gated the merge (the merge queue's merge commit, or without a queue the PR's head): for each app and name, the latest attempt completed by the merge; when the default branch requires checks, those alone. For a split Objective, the last part's.
- **Review:** Pendulum's reviews of the PR and their findings: its line comments that open a thread and the findings set out in a review body; its "no findings" placeholder counts none.

The card shows no count of human actions: the scorecard's count needs the whole issue and PR history ([bench/README.md](../bench/README.md)), so the card leaves it out rather than guess. Neither does it count tests added: a test file is not something a PR's fields say. The scorecard reads every edit of the issue and PR bodies, so Pendulum's finish block on the PR body neither counts as a person's edit nor hides one made before it.

The timeline and the bar chart are Mermaid diagrams (`gantt`, `xychart-beta`) in amber with dark text, labels in a mid-tone ink that reads on GitHub's light and dark pages; every figure in them is in a table beside them. A viewer that ignores a diagram's own colours draws them in its own theme: the bars are then Mermaid's stock colours.

## Siblings that touch the same files

Two Objectives running at once that edit the same lines can conflict: when one merges, the other goes back to its worker for a rebase, an extra run that costs model time, again each time another sibling merges, up to 5 rebases in 24 hours (`rebase_limit`: the workflow's `PENDULUM_REBASE_LIMIT`, or a repository variable of that name; INSTALL.md); then it Blocks naming the files. Without a merge queue, a PR that only fell behind is brought up to date by GitHub's update-branch, with no worker run.

Pendulum compares siblings whose files it knows. An Objective's known files are its open PR's changed files (the first 100, from this repository's own `pendulum/<issue>` branch) and the `Files:` lines of its plan comment, one per checklist item (the plan skill writes them); prose is never read for paths, and a placeholder (`none`, `n/a`, `TBD`, a dash), a glob or a directory on a `Files:` line is no file. An Objective with neither (a first run, before its plan) has unknown files and overlaps nothing; a running sibling counts once its plan comment is posted. Whether two PRs **conflict** is a trial merge of their heads against the default branch: Pendulum fetches the default branch and the two heads into a scratch mirror and asks `git merge-tree` whether, once one has merged, the other still merges cleanly, and which files clash. Two PRs that share many files but change different lines of them do not conflict. When a head conflicts with the default branch itself (it needs a rebase whatever its siblings do), the two PRs' own changes are merged on one base (one PR's base, the other's changes made again there, its own lines winning over the default branch's changes between the two bases), so a PR on an old base does not conflict with a sibling over a change of the default branch's that the sibling never made, and git's merge follows renames and line regions on both sides. When neither PR's changes can be made on the other's base (a file deleted or renamed against a change, both ways), whether they clash cannot be told, and they count as conflicting.

- **Starting:** every Queued Objective starts as slots allow, whatever it shares. One with known files has a plan, so its work stage has work of its own to write (an answer to act on, a draft resumed after a Block, the next part of a split); started beside a sibling, it costs at most one rebase later, while waiting would hold the whole stage. When it shares files with a Running sibling, or an In-review one when Pendulum merges (`auto_merge`), a comment on its issue names them and the shared files and, when Pendulum merges, says that where their changes conflict the one handed to review second waits.
- **Handing off to review:** when a work stage delivers a head no review has seen, and it conflicts with the PR of a sibling ahead of it, its PR is ready but gets no `pendulum:review` label (with `auto_merge`; without it a person merges In-review PRs, so nothing waits for them). A comment on the issue and a record on the PR name the sibling, the files the trial merge conflicts in and, when that sibling is held itself, why (its own wait); the Objective is In review with its slot free. A sibling is ahead when it is In review with no wait of its own, when it went to review and is now rebasing because another PR merged, when it went through such a wait and is now rebasing or in review, or when it waits too but began waiting earlier (then priority, then number); one that can run no stage (two account labels, as Blocked), one a person took out of the merge queue (from the dispatcher tick that sees it until they put it back; the work stage's own hand-off still waits for it, and that tick ends the wait), one whose own review waits for a third-party reviewer or one account label (it will not merge soon), or one with no open ready PR, is not. The rebase of a PR that was ahead goes to review without waiting. A Running sibling that has not handed off holds nothing: the first to hand off goes first. Nothing runs on a waiting PR, no rebase either. The first tick no sibling is ahead of it (they merged, Blocked, asked a Question or were stopped), the dispatcher puts the label on, or, when the PR conflicts by then, first sends it back for its rebase, whose hand-off goes to review without waiting again; while GitHub has not worked out whether it conflicts, it waits one more tick. So waiting PRs go one at a time, in the order they began waiting, and each rebases once, onto every merge before it, however many waited. Two PRs that conflict are never reviewed or in the merge queue at once, except when a person took one out of the merge queue and the other went to review meanwhile: put back, it holds that one no more, so the two can be in the merge queue together. A wait lasts 6 hours at most (`sibling_wait_hours`), counted from the start of the Objective's first wait within that bound (a hold later than that starts a new wait), then the review goes on beside the sibling and the issue's comment says it stopped waiting. A waiting PR made a draft (a stop, a Block) loses its record.
- **Sending back:** when other PRs merged and several In-review PRs conflict at once, Pendulum (with `auto_merge`) sends them back for their rebase in the release order, priority then number. One waits, with no run, while a sibling earlier in that order that will merge first conflicts with it: one In review with no wait of its own, or rebasing after its review. A sibling that will not merge soon does not count: two account labels, a usage-limit hold while it still needs a stage (Running, its review label on, or sent back to review by the merge pass; the hold a local loop's, or on GitHub Actions and the cloud sandbox the account it is pinned to, or every account automatic choice picks among, held), red checks, a person who took it out of the merge queue, or a review of its own that waits for a third-party reviewer or one account label. A rebase now would be undone by that merge. A record on the PR and a comment on the issue name the sibling and the files, and the wait lasts 6 hours at most (`sibling_wait_hours`), counted from the start of the Objective's hand-off wait when that ended within that bound (one bound covers both), then the PR goes back. A wait that ends otherwise (a person resolves the conflict, the PR becomes a draft or Blocks) loses its record and its note, and ends its bound: a later conflict starts its own. So the first in the order goes back, each later one goes back once the siblings ahead of it that it conflicts with have merged, and one that conflicts with none of them goes back at once. Six PRs that each add a line to one registry rebase once each, one after another, instead of all of them after every merge. Without `auto_merge` a person merges in an order of their own, so each conflicting PR goes back at once.

The comparison at the start reads each pick's and each active sibling's comments (a call per 100 comments) and PR's changed files, and one listing of the open PRs per tick, reusing the PRs the merge pass read; a local loop keeps what it read while an issue's update time and comment count, and a PR's head, stay the same. It compares nothing when no sibling is active and at most one Objective starts. A hand-off reads the In-review and Running Objectives (two listings) and, when there are any, its own PR's comments, one listing of the open PRs, and the comments of each sibling's PR it conflicts with; a waiting PR costs its own label history and those reads each tick it waits, and so does ordering the send-backs. A waiting PR is decided after the tick's merge pass, and its PR is read again when that pass merged a PR after its first read. The trial merges are git, not API calls: the default branch and each head compared are fetched once into a scratch mirror, each PR's judgement (a hand-off, or a waiting PR's tick) computes at most 50 new merges of its own, so early PRs never use up a later one's, and a process keeps each pair's answer while the default branch stays (an Actions tick starts with none). On `clockgrove/pendulum` the default branch takes about half a second to fetch, a pair with a new head about a second, and a pair of heads already fetched about 0.3 seconds. Sibling heads the server does not have (a push in flight) count as conflicting once, and the record on the waiting PR names every one of them; the next tick that cannot fetch them either goes on without them. Trial merges that cannot be computed otherwise (a fetch fails, or past that bound) hold no hand-off, keep a waiting hand-off waiting until the next tick, and leave the release order alone to decide the send-backs: the first conflicting PR goes back, and the later ones wait.

Putting `pendulum:review` on a waiting PR yourself starts its review now, and so does `pendulum run <issue>` on its Objective. To turn the hand-off wait off for the repository, set `sibling_hold` to `off` (the workflow's `PENDULUM_SIBLING_HOLD`, or a repository variable of that name; INSTALL.md): no hand-off then waits and nothing is said, a waiting PR gets its review label at the next tick, and overlapping PRs rebase when they conflict, sent back in the release order as above. Each send-back notice on the PR says which rebase it is (of at most 5 in 24 hours), and each rebase stage's progress comment says what it cost and what all of the Objective's rebases cost so far; the scorecard's Rebases column carries the same. When you know two fresh Objectives share an area, say so: add the GitHub issue dependency (`blocked_by`) and the dispatcher orders them; or set `max_concurrent: 1` for the stretch.

## One repository per Objective

Pendulum works in one repository per Objective. An Objective that needs a change in another repository stops with a Question on the issue before any code is written (after its plan, or before the worker starts when the issue names another repository on a `Pendulum-Repository:` line): split it into one Objective per repository and re-apply the label. When the Question came from the plan, you can instead answer in a comment on the issue how to do the work in this repository alone: the next tick runs it again with that answer.

## Workflow changes

Pendulum never pushes a change under `.github/workflows/`, on any route: its token has no Workflows permission. When an Objective needs one, the run hands that part over and the rest lands as usual:

- **Before any model spend,** an issue that names a path under `.github/workflows/` gets a comment saying so. Name the workflow files you know of in the issue to get it then. A need the issue does not name shows in the plan (a `Needs-Workflow:` line), with the same comment, or only in the PR.
- **In the PR,** the first line points to Pendulum's comment on the issue, which holds the exact change, and the PR's Undone section says why. The issue carries the `pendulum:handover` label. That comment with the label is the hand-over, never text in a PR body, and the only command to run for it is `pendulum handover <issue>`: after the PR merges, run it in a clone (or ask your agent: "Apply the Pendulum workflow hand-over for Objective 12"). It takes the comment only from the Pendulum App you name with `--app <id>` (the repository's `PENDULUM_APP_ID`, shown on the App's settings page; or `PENDULUM_LOCAL_APP_ID`) or from someone who can write to the repository, and says whose it is. It puts the change on a new branch from the default branch, shows you the diff and stops. Read it before you push: a workflow runs with the repository's secrets, and one that runs `on: push` runs as soon as its branch is pushed. Then `pendulum handover <issue> --push` commits it, pushes the branch and opens its pull request. Remove the `pendulum:handover` label once it merges: a removal by someone who can write marks the hand-over applied, and Pendulum leaves the label off from then on. Until then the Objective is done with that step pending.
- **When the workflow change is all there is,** there is no PR: the comment on the issue holds it, and the Objective is Blocked until you apply it the same way and close the issue.
- **On the scorecard,** the hand-over counts as normal work, the same for every repository: file the Objective whole, workflow part included, rather than splitting that part off by hand. It can still walk away, and applying the hand-over is an owner step shown apart, with its own minutes: time it, and give it to the scorer as `--owner-minutes <issue>=<minutes>` (bench/README.md, Workflow hand-over).

To have Pendulum build on a workflow change instead, land that change yourself first, then start the Objective.

## Commands

Pendulum is a plugin of [Agent Skills](https://agentskills.io): one folder per skill under [`plugin/skills/`](../plugin/skills/), each a `SKILL.md` that Claude Code, Codex and GitHub Copilot CLI load the same way. With the plugin installed, ask in plain words: each request below loads the Pendulum skill that does it. If your agent takes "Pendulum" for something else of that name, such as the Python date-time library, use the command instead. In Claude Code each skill is also a slash command, `/pendulum:<skill>`; Codex and Copilot list them among their own skills. Each command below links to its skill.

| Say | Command | What it does |
| --- | --- | --- |
| "Set up Pendulum for this repository." | [`/pendulum:pendulum-setup`](../plugin/skills/pendulum-setup/SKILL.md) | Installs Pendulum one consented step at a time, and opens the pull request that adds the workflow file |
| "Is Pendulum set up correctly here?" | [`/pendulum:pendulum-doctor`](../plugin/skills/pendulum-doctor/SKILL.md) | Checks the repository, its settings, the credential and the runner; changes nothing |
| "File a Pendulum Objective: ..." | [`/pendulum:pendulum-file`](../plugin/skills/pendulum-file/SKILL.md) | Writes what you describe as an Objective issue, shows it, and on your yes creates it started (`pendulum:objective`) or as a draft (`pendulum:draft`) |
| "Let's keep working on Pendulum Objective 12." | `/pendulum:pendulum-file <issue>` | Loads the draft from GitHub to refine it with you, and saves the changes back on your yes |
| "Start Pendulum Objective 12." | `/pendulum:pendulum-file <issue>` | Starts a draft on your yes, after the trust check: takes `pendulum:draft` off and applies `pendulum:objective` |
| "What is Pendulum doing here?", "Why is Pendulum Objective 12 Blocked?" | [`/pendulum:pendulum-status`](../plugin/skills/pendulum-status/SKILL.md) `[issue]` | Shows each Objective's state; for a Blocked one or a Question, the reason and the way on (resume, answer or restart), taken on your yes (Blocked and Question, above) |
| "Stop Pendulum Objective 12." | [`/pendulum:pendulum-stop`](../plugin/skills/pendulum-stop/SKILL.md) `<issue>` | Removes the Objective's label on your yes: its running stage ends and nothing picks it up again (An Objective's lifecycle, above) |
| "Restart Pendulum Objective 12." | [`/pendulum:pendulum-restart`](../plugin/skills/pendulum-restart/SKILL.md) `<issue>` | Applies `pendulum:restart` on your yes: the Objective starts over from the issue's current text (An Objective's lifecycle, above) |
| "Run Pendulum Objective 42 here." | [`/pendulum:pendulum-run`](../plugin/skills/pendulum-run/SKILL.md) `<issue>` | Runs one Objective on this machine, in local mode or in the session itself |
| "Review Pendulum PR 57." | [`/pendulum:pendulum-review-here`](../plugin/skills/pendulum-review-here/SKILL.md) `<pr>` | Runs the reviewer on one Pendulum PR in your session |
| "Start the Pendulum local loop." | [`/pendulum:pendulum-serve`](../plugin/skills/pendulum-serve/SKILL.md) | Starts the local loop ([LOCAL.md](LOCAL.md)) |
| "Kick the Pendulum dispatcher." | [`/pendulum:pendulum-kick`](../plugin/skills/pendulum-kick/SKILL.md) `[issue]` | Runs the Action's dispatcher now, which starts the Objectives that are ready, or one Objective |
| "Apply the Pendulum workflow hand-over for Objective 12." | [`/pendulum:pendulum-handover`](../plugin/skills/pendulum-handover/SKILL.md) `<issue>` | Puts the workflow change Pendulum handed over on a new branch and shows it; pushes it and opens its PR only after you read it and say yes |
| "Show the Pendulum scorecard." | [`/pendulum:pendulum-score`](../plugin/skills/pendulum-score/SKILL.md) | Prints the scorecard: whether each Objective merged with no one stepping in, quality, operator minutes, cost |
| "What did Pendulum cost this month?", "Chart where its tokens went." | [`/pendulum:pendulum-report`](../plugin/skills/pendulum-report/SKILL.md) `[scope]` | Runs `pendulum report --json` and presents its figures as you ask: totals by billing kind, runs of unknown cost with their reasons, breakdowns and hot spots ([REPORT.md](REPORT.md)); when you ask which model to try where, a named model's proposals, each an observation citing the report's rows, a hypothesis, an experiment and its command, with no counterfactual dollars |

Five more skills are loaded for you. The worker follows [`pendulum-objective-plan`](../plugin/skills/pendulum-objective-plan/SKILL.md), [`pendulum-implement-split`](../plugin/skills/pendulum-implement-split/SKILL.md), [`pendulum-prove-acceptance`](../plugin/skills/pendulum-prove-acceptance/SKILL.md) and [`pendulum-deliver-pr`](../plugin/skills/pendulum-deliver-pr/SKILL.md), in that order; and the reviewer follows [`pendulum-review-pr`](../plugin/skills/pendulum-review-pr/SKILL.md).

Install Pendulum as a plugin (the README's [Quick start](../README.md#quick-start)). Skill-only installers such as `npx skills add` and `gh skill install` copy the skill folders but not the plugin's scripts, which the setup, doctor, run, serve, kick, review-here, handover and score skills run, so those skills do not work installed that way.

On the command line, `gh workflow run pendulum.yml -f issue=<number>` starts one Objective now, local mode has `pendulum serve`, `pendulum run <issue>` and `pendulum review <pr>`, and `pendulum wait` waits for the queue's next event on any route ([LOCAL.md](LOCAL.md), Run it).
