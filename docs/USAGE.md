# Using Factory

How to write an Objective, what you see while it runs, and what to do when Factory hands one back to you Blocked or with a Question. [INSTALL.md](INSTALL.md) covers setup; [PLAN.md](PLAN.md) has the full contracts.

## Write an Objective

An Objective is a GitHub issue with the `factory:objective` label. The issue is the whole specification: write everything the work needs into it. The worker asks you something only when the work depends on a decision that should be yours (a Question, below). Ask a session to file one for you ("File a Clockgrove Factory Objective: ...", the factory-file skill), which starts it or saves it as a draft to refine and start later (An Objective's lifecycle, below), or write the issue yourself:

- **State the goal and what must be true when it is done.** Put the acceptance entries in a list under a heading such as `Acceptance` (`Done when`, `Definition of done`, `Must be true` and `Criteria` are read the same way). The reviewer judges each entry, met or not, with the line that shows it. Without such a section, the reviewer names the entries from the issue text itself.
- **Say what you have decided.** Where the issue admits more than one reading, the worker takes the simplest one that satisfies every acceptance entry and records it as an assumption in its plan and in the PR.
- **File it yourself, or have someone who can push file it.** Factory acts on an issue only when its author and, once the body was edited, its last editor can push to the repository or are maintainers the workflow names. Otherwise the run Blocks before any model sees the text. A maintainer labelling someone else's issue is not enough: who applies the label is not checked, and the author is checked on every run, so such an issue needs refiling by someone who can push.
- **Keep it to one repository** (below).

```markdown
## Goal

`mytool --version` prints the version.

## Acceptance

- `mytool --version` prints the version from package.json and exits 0.
- A test covers it.
```

Ready Objectives start in priority order (`P0` to `P2`, then the lowest issue number), up to `max_concurrent` at once; one started by hand with `gh workflow run factory.yml -f issue=<number>` runs even when that limit is reached. An Objective too large for one session is delivered as up to six pull requests in sequence, one open at a time.

## Choose the harness and models

The workflow file's `FACTORY_HARNESS`, `FACTORY_MODEL`, `FACTORY_SUBAGENT_MODEL` and `FACTORY_REVIEWER_MODEL` are the repository's defaults, and doctor lists them. A label on the issue overrides one of them for that Objective alone; an issue with none runs on the defaults.

| Label | Overrides |
| --- | --- |
| `factory:harness:<name>`: `claude`, `codex` or `copilot` | `FACTORY_HARNESS`. The models no label names become that harness's own defaults, as with any switch of harness. |
| `factory:model:<id>` | `FACTORY_MODEL`: the worker, and its fix and answer passes. |
| `factory:subagent-model:<id>` | `FACTORY_SUBAGENT_MODEL`: the implementer sub-agents. |
| `factory:reviewer-model:<id>` | `FACTORY_REVIEWER_MODEL`: the reviewer. |

- **Apply them when you file the issue,** with `factory:objective` (`gh issue create … --label factory:objective --label factory:model:claude-sonnet-5-5`; `gh label create <name>` first makes a label the repository lacks). The factory-file skill offers them.
- **Who applied a label counts.** Factory acts on one only when the person who last applied it, by the issue's timeline, can push or is a maintainer the workflow names, since GitHub lets anyone with triage access apply labels. Otherwise the Objective Blocks before any spend, naming the label. Taking a label off is not checked, since GitHub does not ask who may: before the plan, a label anyone with triage access removes sends the Objective back to the repository's default; after the plan, a removal Blocks it as an edit (below).
- **A choice it cannot run Blocks before any spend,** naming the label and the fix: two labels of one kind, a harness Factory does not run, or a model the harness cannot run. Claude Code runs Claude models (a `claude-` id, or its aliases `fable`, `opus`, `sonnet` and `haiku`). Codex runs a model with a row in Factory's Codex price table (`plugin/scripts/lib/codex-prices.json`), since without one `max_usd` could not stop its runs; a provider prefix (`openai/`) is taken only with the AI Gateway key, and Factory adds it itself. Copilot's model names come from its own catalog, which varies by account and which Factory cannot read before a run, so Factory checks only the form (no provider prefix or spaces): a name the account's Copilot does not offer is not caught before Copilot starts. `max_usd` and `daily_usd` apply whatever the model.
- **GitHub caps a label name at 50 characters,** so an id fits in 36 characters after `factory:model:` and in 27 after `factory:subagent-model:` or `factory:reviewer-model:`. Every model in Factory's price tables and defaults fits; GitHub refuses a longer name, so use the model's id without its date suffix, or make it the repository's default.
- **Every route honours it.** The Action's work and review jobs read the harness label before they install a harness, and install that one; the workflow hands each job every harness's secret, so the chosen harness needs its own secret (a missing one Blocks the Objective, naming it). The cloud-sandbox launcher hands the stage that harness's credential and the repository's defaults, so the stage reads the labels again, and Blocks before any sandbox call when the launch job holds none. `harness_version` pins the harness the workflow's env block names only: a harness a label, a run's override or a repository variable chooses installs its latest. Local mode (`factory serve`, `factory run`) runs another harness than its own when this machine can (its CLI and its sandbox, and for Copilot its token, as `factory serve` checks its own at start), else Blocks the Objective, and the loop's log names what is missing. A stage that finds its labels name another harness than the one its job, sandbox or loop prepared for Blocks; re-apply `factory:objective`. `/factory:factory-run --here` runs in your own session, on its harness and model, whatever the labels say.
- **A manual run's `harness` input** (`gh workflow run factory.yml -f issue=<number> -f harness=codex`) overrides the default for that run; a harness label on the issue wins over it.
- **A label added, removed or changed after the plan is an edit** (Edit an Objective, below): the next stage Blocks, re-applying `factory:objective` plans again on the new choice, and `factory:restart` starts over with it.
- **What ran is on the record:** the progress comment's harness line, the usage record's `ran` and the scorecard's Harness column name the harness, the worker, sub-agent and reviewer models, and the labels that chose them, and the account each stage ran on (LOCAL.md, Accounts; INSTALL.md, Several accounts).
- **The account too:** `factory:account:<name>` moves an Objective to another account of its harness: in local mode one the machine that runs it declares, for instance when a usage limit pauses it (LOCAL.md, Accounts); on Actions and the cloud sandbox one the workflow declares (INSTALL.md, Several accounts), where with none declared it does nothing and the progress comment says so. It is trusted like the labels above, but it is no edit: adding or removing it after the plan Blocks nothing.

## Ask for a foundation review

Label an Objective `factory:foundation` when later work builds on what it adds: a shared type or schema, an error table, a command registry, a file format, a test fixture other tests import. Its review then runs a second reviewer call, the foundation pass, after the usual one.

- **What it checks:** each shared contract the diff adds or changes (an exported function, type, schema, error code, CLI flag, file format, shared fixture) against its callers and readers in the repository: every value it can produce reaches the caller meant to handle it, every caller uses what it now says, and a shared test fixture keeps tests off the developer's real home, state and proxy settings (the factory-review-pr skill's reference.md, "Foundation review").
- **One review:** its findings are line-tied comments in the same comment-only review as the usual pass's, and the worker's answer pass answers them all. The review body counts them.
- **Within `max_usd`:** the pass is one more call on the reviewer model, as its own `foundation-reviewer` agent definition, so a foundation review costs about one more reviewer call. It starts only with budget and time left; at the cap or the time cap the stage Blocks before it, and nothing is posted, as for the usual pass. A call that fails is run once more; when neither answers, nothing is posted and the Objective Blocks with how each call ended.
- **Trusted like the harness and model labels:** it counts only when the person who last applied it can push or is a maintainer the workflow names; otherwise the Objective Blocks naming the label.
- **Not an edit:** it changes only the review, so adding or removing it after the plan Blocks nothing; the review reads it when it starts. A PR reviewed before the label was added gets the foundation pass alone, as its own review, at its next review stage (re-apply `factory:review`, or the rebase or resume that brings one). Add it before the PR is delivered: a PR already waiting for its checks to merge merges on its earlier review. An Objective without it is reviewed in one pass.

## Open a network host for one Objective

Every Objective's sandboxes reach GitHub, the npm and Yarn registries and the hosts the repository allows for all of them (the `allowed_domains` input; `FACTORY_LOCAL_DOMAINS` in local mode). An Objective that needs one more host (a model hub, a vendor's API) gets it for itself with a label, `factory:host:<host>`: `factory:host:huggingface.co`, or `factory:host:*.hf.co` for that domain's subdomains. One label per host; apply as many as it needs.

- **It opens that host to this Objective's sandboxes alone,** on every route: the work stage, the reviewer and the fix and answer passes, on Actions, in a cloud sandbox and in local mode. No other Objective's sandbox gets it, and `/factory:factory-run --here` runs in your own session, outside Factory's sandboxes.
- **Who applied it counts,** as for a harness or model label: Factory opens the host only when the person who last applied the label can push or is a maintainer the workflow names. A label anyone else applied Blocks the Objective before any spend, naming it.
- **A host name, nothing else:** a name such as `example.com`, or `*.` and one; no scheme, port, path, IP address or `localhost`. A label naming anything else Blocks, naming it. GitHub caps a label at 50 characters, which leaves 37 for the host; a longer one goes in the repository's setting.
- **What the rule does not catch, so the person applying the label must:** the check is on the name alone. `*.` is refused only over a bare top-level domain (`*.com`), so `*.co.uk` or `*.github.io` passes and opens every site under it; a name that resolves to a loopback or link-local address (a service on the machine, a cloud metadata endpoint) is not refused. In local mode the label lets anyone who can push open a host from your machine, without a change to your `FACTORY_LOCAL_DOMAINS`. Apply the narrowest host the work needs.
- **A host label added, removed or changed after the plan is an edit,** as for the other labels (Edit an Objective, below).
- **The Block for a denied host names both fixes:** the host label for this Objective, and the repository's setting for every Objective.
- **Where to see them:** the progress comment's Network line, the usage record's `ran.hosts`, and doctor's `objective hosts` line, which lists each open Objective's hosts.

## What you see on the issue

While a job runs, one comment on the issue (edited in place, one per run) carries a bold status line and the phases with clocks: setup, install, harness, each validation pass, reviewer, answer pass, exit. The review starts while the PR's first required-check run is still going: its reviewer line then ends `beside the required checks on <sha>`, and a later line says when the checks ended (`... while the reviewer runs`) or that the stage waits for them after the reviewer. The status line comes from the harness's own event stream, not from its prose: elapsed minutes, turns, tool calls, the sub-agents running and what each was asked to do, when the last event arrived, tokens so far, the last tool it ran. A harness that prints nothing for 30 minutes is killed and retried once, and the line says so. The labels (`factory:running`, `factory:in-review`, `factory:blocked`, `factory:question`) and the board column are the state; the plan comment is the harness's own checklist, ticked as it goes; the PR carries the validation marker (or, while its first required-check run goes on beside the review, the hand-off marker) and the review.

## An Objective's lifecycle

Each step is one action on GitHub. Where a skill is named, a plain-words request to your agent takes that action after asking you.

- **Draft.** An issue with the `factory:draft` label is a draft: Factory never runs it, on any route, even with `factory:objective` on it too (the draft label wins: the dispatcher's log lists it as a draft, and a launch, `factory run` or a session's `factory issue` refuses it). Nothing is dispatched, claimed or spent for it. The factory-file skill offers it beside starting at once: it shows the issue and asks whether to start it now, save it as a draft, or keep discussing. "Let's keep working on Clockgrove Factory Objective #12" (the factory-draft skill) loads the draft from GitHub to refine it with you and saves the changes back to the issue only on your yes. Edit a draft freely: before its first plan, an edit is simply the text the run starts from.

- **Start.** Applying `factory:objective` starts the Objective: the dispatcher picks it up on the label's own event, else on its ten-minute cron, and in local mode on `factory serve`'s next tick. To start a draft, take `factory:draft` off and apply `factory:objective`, or ask "Start Clockgrove Factory Objective #12" (the factory-start skill): on your yes it does both, after the trust check a new Objective gets (its author and its last editor can push, or are maintainers the workflow names; otherwise it refuses and says who). Starting a draft counts as re-applying the label, whichever way it is done: an edit made while it was a draft, even after an earlier plan, is planned from. A draft started, then edited, follows the edit rules below once its plan exists.

- **Edit.** Edit the issue freely until the first work stage reads it. After its plan, an edit Blocks the Objective at its next stage, and re-applying `factory:objective` plans again from the new text (Edit an Objective, below).

- **Restart.** Apply `factory:restart` to start over from the issue's current text, in any state: Queued, Running, In review, Blocked or a Question ("Restart Clockgrove Factory Objective #12", the factory-restart skill, applies it on your yes). Only someone who can push, or a maintainer the workflow names, restarts an Objective: anyone else's label is taken off with a comment (a running stage may already have stopped on seeing it; re-applying `factory:objective` resumes the Objective). A running stage stops first, as for a stop, its spend so far recorded, and nothing merges or starts meanwhile. Then the dispatcher writes a restart record on the issue (when the label was applied, who applied it, and what the restart discards: the earlier PR with its review, and the deleted branch's commits, whose last one `git push origin <sha>:refs/heads/factory/<issue>` restores), deletes the `factory/<issue>` branch, closes the earlier PR with a comment linking the record (its commits and review stay readable on it), sets the earlier plan and a split's part record aside, removes the state labels and the restart label, and queues the Objective; it starts from the default branch, and comments made before the label was applied do not feed it. When a ruleset keeps GitHub from deleting the branch, the Objective is Blocked with the fix instead: nothing is discarded, and its earlier PR, plan and comments stay as they were. The retry and rebase counts start over, and the scorecard counts the restart as a human action. On a stopped Objective the restart waits until `factory:objective` is back. A workflow file rendered before this release sees a restart only on the ten-minute cron until it is re-rendered ([INSTALL.md](INSTALL.md), Upgrade). To go on after a fix or an answer instead, re-apply `factory:objective`: that continues from the branch and PR.

- **Stop.** Remove the `factory:objective` label, or close the issue ("Stop Clockgrove Factory Objective #12", the factory-stop skill, removes the label on your yes). No dispatcher tick, local loop or sandbox launch picks up a stopped Objective, and your other Objectives keep running. What happens depends on its state:
  - **Running, or a review running:** the stage reads its issue once a minute. On the stop it ends its harness run, records the spend so far in its usage record (locally and in a cloud sandbox also in its progress comment's spend line, as every stage does) and exits, normally within two minutes; its progress comment's last line reads `exit: stopped`. Its PR, if it has one, becomes a draft without the `factory:review` label; its state label comes off and its card goes back to Queued. With the cloud sandbox the launcher then stops the sandbox. A Running Objective whose stage died before it saw the stop is tidied the same way by the dispatcher, ten minutes after the label came off.
  - **In review with no stage running:** on its next tick the dispatcher takes the PR out of the merge queue, makes it a draft without the `factory:review` label, removes the state label and moves the card to Queued, so neither a review nor the merge queue takes it. On Actions the label's removal ticks it (a workflow file rendered before this release waits for the ten-minute cron until it is re-rendered: [INSTALL.md](INSTALL.md), Upgrade); locally `factory serve` ticks every 30 seconds.
  - **Queued, Blocked or a Question:** it stays as it is.

  Applying `factory:draft` to an Objective stops it the same way, whatever its state, and keeps it a draft until it is started again.

  Re-apply the label to start it again: it continues from its branch and PR, as after a Block. Closing the issue stops it the same way and then counts as done: the dispatcher's Done pass removes its state label, moves its card to Done and makes a PR it left open a draft, and with the cloud sandbox the sweep destroys its sandbox.

## Edit an Objective

Edit the issue as much as you like until the worker reads it: the first work stage makes its plan from the title, the body and the harness, model and host labels as they are when it starts. After that, the plan and the code follow that text, and an edit to the title or body, or a harness, model or host label added, removed or changed, does not reach the run halfway:

- The stage running when you edit finishes on the text it read. The next one (the review, the merge, or a work stage Factory starts on its own, such as a rebase) stops the Objective as Blocked, saying the Objective changed after its plan was made, and the PR, if there is one, becomes a draft. A PR already in the merge queue is taken out of it. Nothing goes on with a plan made from one text and an issue that says another.
- Saving the issue without changing it is no edit: line endings and trailing spaces do not count. That needs the record of its text Factory keeps on the plan comment: a plan comment without one (an older plan) gets it at the next work stage, and until then any save after the plan counts as an edit.
- Re-apply `factory:objective` to work from the new text: the work stage that starts after it makes its plan again from the text as it then is, on the same branch and PR. An edit made while the Objective is Blocked or has a Question is used the same way once you re-apply the label. Only the label counts: starting the Objective by hand (`gh workflow run factory.yml -f issue=<number>`, or `factory run <number>` in local mode) after such an edit Blocks it again. To start over from the new text instead, with the earlier PR closed and a new branch from the default one, apply `factory:restart` (An Objective's lifecycle, above).
- Comments are not edits. A comment that answers a Question, or records a decision, leaves the plan as it is.
- An edit is checked like the text you first wrote: when its editor cannot push and is not a maintainer the workflow names, the run Blocks (above).

## Blocked and Question

A run that goes well needs nothing from you. When one needs you, Factory does all the work it can first and then hands the Objective back to you in one of two states. Neither holds up the queue: your other Objectives keep running.

- **Blocked** means Factory could not finish. One comment on the issue gives the reason, the fix and whether to resume or restart; the issue's card moves to the Blocked column (on a repository a user owns there is no board; the `factory:blocked` label says it), and the PR, if it opened one, becomes a draft.
- **Question** means the work depends on a decision that should be yours: one that would change or remove an existing public contract, contradict a recorded decision or grant new access. The worker takes the simplest reading, finishes everything else, and leaves a draft PR whose body asks what a human must decide. A Question about working in another repository comes earlier, on the issue itself, with no PR (One repository per Objective, below).

What to do with each:

- **Blocked:** fix what the comment names, then re-apply `factory:objective` to run the Objective again: that resumes from its branch and PR. When your fix was an edit to the issue, the worker makes its plan again from the new text. Apply `factory:restart` only when the work itself must be redone: it discards the PR, its review, the branch's commits and the spend on them. The comment says which fits: resume whenever the stop was outside the work. When the red was CI's, its quoted output leads with the required checks that are red, by name; failing jobs no required check counts are marked `not required`.
- **Red checks a fix pass could not change:** when a fix pass commits nothing and the required checks stay red for a reason in the code, Factory first gives the Objective one fresh worker pass: a new session handed the failing output, once per head in a stage, and only when what is left of `max_usd` covers what the fix pass cost and the stage has time for another pass and its checks. A Block that names both passes means a fresh session could not fix it either. One that says `no fresh worker pass` or that the fresh pass reached a cap gives the reason. Read the failing job on GitHub, fix the cause on the branch, then re-apply the label.
- **Lost to the network:** on GitHub Actions and the cloud sandbox, a stage whose runner or sandbox lost its network (its outage notice, which mentions no one, names the host) or vanished without a word is relaunched on its own, at most twice since you last started the Objective, its work resuming from its branch and PR; a Factory comment on the issue counts them. A relaunch waits while today's spend has reached `daily_usd` or `max_concurrent` Objectives run, and each stage spends within `max_usd`, so a start can spend up to three times `max_usd` before you hear of it. Only then is it Blocked, the notice saying how many relaunches were tried; re-apply the label once the network is back, and the count starts over. A stage cancelled on Actions (by a person or its timeout), or a sandbox stage that recorded its end, is not a network loss: it is Blocked as before. The local route pauses and resumes such a stage instead ([LOCAL.md](LOCAL.md)).
- **Question:** comment the decision on the issue or the PR (a review or a line comment works too) and mark the PR ready: the review job applies it, and with no answer since the question the PR goes back to a Question rather than merging. A Question asked on the issue (one with no PR, or the plan-time Question; its notice says to answer on the issue) needs only the comment on the issue: on every route the Objective goes back to the queue at the dispatcher's next tick (local mode: `serve`'s), and the worker runs again with the answer. Re-applying `factory:objective` instead reruns the worker with it.

A comment counts when its author has write access to the repository or is a maintainer the workflow names (`notify`, and the optional `maintainers` list), since an App cannot always see an organization member's access.

An agent that supervises the queue for you can wait on it instead of watching logs: `factory wait` exits with one JSON line per Objective that Blocked, asked a Question, went In review, merged or closed since the last read, or when the queue drains, within a poll (30 seconds) of the change, on every route ([LOCAL.md](LOCAL.md), Run it). The @mention to a person stays as it is.

## Factory merges on its own

Code lands with no human read. The gate is your CI workflow's checks on the reviewed head and the integrated commit, the comment-only reviewer pass, and the merge queue's own re-run where you have one. Set `FACTORY_AUTO_MERGE: false` for ready-for-review PRs instead.

The reviewer reads the PR while its first CI run is still going. A red found then is not a separate fix pass: the answer pass fixes it with the reviewer's comments. A red merge-queue run whose failure is in the PR's own change gets one fix pass too, before any Block (at most two per start of the Objective), so your CI can run a light check on the PR and the full suite only in the merge queue. Without red-check triage (no AI Gateway key) a queue failure counts as the PR's own only when it names a file or test the PR changed. A flaky or infrastructure red in the queue, or one Factory cannot read, is enqueued again once, as any drop; the same failure red again after its fix pass Blocks, naming the failed job and its first failing line.

## Siblings that touch the same files

Two Objectives running at once that edit the same lines can conflict: when one merges, the other goes back to its worker for a rebase, an extra run that costs model time, again each time another sibling merges, up to 5 rebases in 24 hours; then it Blocks naming the files. Without a merge queue, a PR that only fell behind is brought up to date by GitHub's update-branch, with no worker run.

Factory compares siblings whose files it knows. An Objective's known files are its open PR's changed files (the first 100, from this repository's own `factory/<issue>` branch) and the `Files:` lines of its plan comment, one per checklist item (the plan skill writes them); prose is never read for paths, and a placeholder (`none`, `n/a`, `TBD`, a dash), a glob or a directory on a `Files:` line is no file. An Objective with neither (a first run, before its plan) has unknown files and overlaps nothing; a running sibling counts once its plan comment is posted. Whether two PRs **conflict** is a trial merge of their heads against the default branch: Factory fetches the default branch and the two heads into a scratch mirror and asks `git merge-tree` whether, once one has merged, the other still merges cleanly, and which files clash. Two PRs that share many files but change different lines of them do not conflict. When a head conflicts with the default branch itself (it needs a rebase whatever its siblings do), the two heads are merged with each other and a file counts only when both PRs' own changes touch it, so a PR on an old base does not conflict with a sibling over a change of the default branch's that the sibling never made.

- **Starting:** every Queued Objective starts as slots allow, whatever it shares. One with known files has a plan, so its work stage has work of its own to write (an answer to act on, a draft resumed after a Block, the next part of a split); started beside a sibling, it costs at most one rebase later, while waiting would hold the whole stage. When it shares files with a Running sibling, or an In-review one when Factory merges (`auto_merge`), a comment on its issue names them and the shared files and, when Factory merges, says that where their changes conflict the one handed to review second waits.
- **Handing off to review:** when a work stage delivers a head no review has seen, and it conflicts with the PR of a sibling ahead of it, its PR is ready but gets no `factory:review` label (with `auto_merge`; without it a person merges In-review PRs, so nothing waits for them). A comment on the issue and a record on the PR name the sibling, the files the trial merge conflicts in and, when that sibling is held itself, why (a third-party reviewer, an account label, a person who took it out of the merge queue, or its own wait); the Objective is In review with its slot free. A sibling is ahead when it is In review with no wait of its own, when it went to review and is now rebasing because another PR merged, when it went through such a wait and is now rebasing or in review, or when it waits too but began waiting earlier (then priority, then number); one that can run no stage (two account labels, as Blocked), or has no open ready PR, is not. The rebase of a PR that was ahead goes to review without waiting. A Running sibling that has not handed off holds nothing: the first to hand off goes first. Nothing runs on a waiting PR, no rebase either. The first tick no sibling is ahead of it (they merged, Blocked, asked a Question or were stopped), the dispatcher puts the label on, or, when the PR conflicts by then, first sends it back for its rebase, whose hand-off goes to review without waiting again; while GitHub has not worked out whether it conflicts, it waits one more tick. So waiting PRs go one at a time, in the order they began waiting, and each rebases once, onto every merge before it, however many waited. Two PRs that conflict are never reviewed or in the merge queue at once. A wait lasts 6 hours at most, counted from the start of the Objective's first wait within the last 6 hours (a hold later than that starts a new wait), then the review goes on beside the sibling and the issue's comment says it stopped waiting. A waiting PR made a draft (a stop, a Block) loses its record.
- **Sending back:** when other PRs merged and several In-review PRs conflict at once, Factory (with `auto_merge`) sends them back for their rebase in the release order, priority then number. One waits, with no run, while a sibling earlier in that order that will merge first conflicts with it: one In review with no wait of its own, or rebasing after its review. A sibling that will not merge soon does not count: two account labels, a usage-limit hold, red checks, a person who took it out of the merge queue, or a review of its own that waits for a third-party reviewer or one account label. A rebase now would be undone by that merge. A record on the PR and a comment on the issue name the sibling and the files, and the wait lasts 6 hours at most, counted from the start of the Objective's hand-off wait when that ended within the last 6 hours (one bound covers both), then the PR goes back. So the first in the order goes back, each later one goes back once the siblings ahead of it that it conflicts with have merged, and one that conflicts with none of them goes back at once. Six PRs that each add a line to one registry rebase once each, one after another, instead of all of them after every merge. Without `auto_merge` a person merges in an order of their own, so each conflicting PR goes back at once.

The comparison at the start reads each pick's and each active sibling's comments (a call per 100 comments) and PR's changed files, and one listing of the open PRs per tick, reusing the PRs the merge pass read; a local loop keeps what it read while an issue's update time and comment count, and a PR's head, stay the same. It compares nothing when no sibling is active and at most one Objective starts. A hand-off reads the In-review and Running Objectives (two listings) and, when there are any, its own PR's comments, one listing of the open PRs, and the comments of each sibling's PR it conflicts with; a waiting PR costs its own label history and those reads each tick it waits, and so does ordering the send-backs. The trial merges are git, not API calls: the default branch and each head compared are fetched once into a scratch mirror, a hand-off or a tick computes at most 50 new merges, and a process keeps each pair's answer while the default branch stays (an Actions tick starts with none). On `clockgrove/factory` the default branch takes about half a second to fetch, a pair with a new head about a second, and a pair of heads already fetched about 0.3 seconds. A sibling head the server does not have (a push in flight) counts as conflicting once, and the record on the waiting PR names it; the next tick that cannot fetch it either goes on without it. Trial merges that cannot be computed otherwise (a fetch fails, or past that bound) hold no hand-off, keep a waiting hand-off waiting until the next tick, and leave the release order alone to decide the send-backs: the first conflicting PR goes back, and the later ones wait.

Putting `factory:review` on a waiting PR yourself starts its review now, and so does `factory run <issue>` on its Objective. To turn the hand-off wait off for the repository, set `sibling_hold` to `off` (the workflow's `FACTORY_SIBLING_HOLD`, or a repository variable of that name; INSTALL.md): no hand-off then waits and nothing is said, a waiting PR gets its review label at the next tick, and overlapping PRs rebase when they conflict, sent back in the release order as above. Each send-back notice on the PR says which rebase it is (of at most 5 in 24 hours), and each rebase stage's progress comment says what it cost and what all of the Objective's rebases cost so far; the scorecard's Rebases column carries the same. When you know two fresh Objectives share an area, say so: add the GitHub issue dependency (`blocked_by`) and the dispatcher orders them; or set `max_concurrent: 1` for the stretch.

## One repository per Objective

Factory works in one repository per Objective. An Objective that needs a change in another repository stops with a Question on the issue before any code is written (after its plan, or before the worker starts when the issue names another repository on a `Factory-Repository:` line): split it into one Objective per repository and re-apply the label. When the Question came from the plan, you can instead answer in a comment on the issue how to do the work in this repository alone: the next tick runs it again with that answer.

## Workflow changes

Factory never pushes a change under `.github/workflows/`, on any route: its token has no Workflows permission. When an Objective needs one, the run hands that part over and the rest lands as usual:

- **Before any model spend,** an issue that names a path under `.github/workflows/` gets a comment saying so. Name the workflow files you know of in the issue to get it then. A need the issue does not name shows in the plan (a `Needs-Workflow:` line), with the same comment, or only in the PR.
- **In the PR,** the first line points to Factory's comment on the issue, which holds the exact change, and the PR's Undone section says why. The issue carries the `factory:handover` label. That comment with the label is the hand-over, never text in a PR body, and the only command to run for it is `factory handover <issue>`: after the PR merges, run it in a clone (or ask your agent: "Apply the Clockgrove Factory workflow hand-over for Objective 12"). It takes the comment only from the Factory App you name with `--app <id>` (the repository's `FACTORY_APP_ID`, shown on the App's settings page; or `FACTORY_LOCAL_APP_ID`) or from someone who can write to the repository, and says whose it is. It puts the change on a new branch from the default branch, shows you the diff and stops. Read it before you push: a workflow runs with the repository's secrets, and one that runs `on: push` runs as soon as its branch is pushed. Then `factory handover <issue> --push` commits it, pushes the branch and opens its pull request. Remove the `factory:handover` label once it merges: a removal by someone who can write marks the hand-over applied, and Factory leaves the label off from then on. Until then the Objective is done with that step pending.
- **When the workflow change is all there is,** there is no PR: the comment on the issue holds it, and the Objective is Blocked until you apply it the same way and close the issue.
- **On the scorecard,** the hand-over counts as normal work, the same for every repository: file the Objective whole, workflow part included, rather than splitting that part off by hand. It can still walk away, and applying the hand-over is an owner step shown apart, with its own minutes: time it, and give it to the scorer as `--owner-minutes <issue>=<minutes>` (bench/README.md, Workflow hand-over).

To have Factory build on a workflow change instead, land that change yourself first, then start the Objective.

## Commands

With the plugin installed in Claude Code, Codex or GitHub Copilot CLI, ask in plain words and use the full name, Clockgrove Factory: each request below loads the Factory skill that does it, and the full name keeps your agent from picking up another product called Factory. Where your agent offers skills as slash commands, the command works too.

| Say | Command | What it does |
| --- | --- | --- |
| "Set up Clockgrove Factory for this repository." | `/factory:factory-setup` | Installs Factory one consented step at a time, and opens the pull request that adds the workflow file |
| "Is Clockgrove Factory set up correctly here?" | `/factory:factory-doctor` | Checks the repository, its settings, the credential and the runner; changes nothing |
| "File a Clockgrove Factory Objective: ..." | `/factory:factory-file` | Writes what you describe as an Objective issue, shows it, and on your yes creates it started (`factory:objective`) or as a draft (`factory:draft`) |
| "Let's keep working on Clockgrove Factory Objective 12." | `/factory:factory-draft <issue>` | Loads the draft from GitHub to refine it with you, and saves the changes back on your yes |
| "Start Clockgrove Factory Objective 12." | `/factory:factory-start <issue>` | Starts a draft on your yes, after the trust check: takes `factory:draft` off and applies `factory:objective` |
| "Stop Clockgrove Factory Objective 12." | `/factory:factory-stop <issue>` | Removes the Objective's label on your yes: its running stage ends and nothing picks it up again (An Objective's lifecycle, above) |
| "Restart Clockgrove Factory Objective 12." | `/factory:factory-restart <issue>` | Applies `factory:restart` on your yes: the Objective starts over from the issue's current text (An Objective's lifecycle, above) |
| "Run Clockgrove Factory Objective 42 here." | `/factory:factory-run <issue>` | Runs one Objective on this machine, in local mode or in the session itself |
