# v0.1.21 compilation and telemetry postmortem

## Outcome and context

The [accepted public gate](V0.1.21-ACCEPTANCE.md) compiled a clean plan on its first attempt and automatically accepted every Work Item and final criterion. Two items were the right granularity: establish target LFS policy, then stage a byte-identical candidate for controller selection and migration. The policy dependency and intentional selection pause warranted separate items. No missing requirement or ambiguous acceptance criterion blocked this run.

The migration worker was nevertheless inefficient. Its brief instructed it to use the installed Factory CLI and supplied controller-facing resources. The observed worker discovered the installation, inspected configuration/status, and inspected its own harness logs. The brief's contribution to that exploration is a hypothesis, not a proven causal attribution. The worker's actual responsibility was only to copy the source into staging and declare its manifest; the controller owned capture, selection, destination mutation and publication. Of 18 tool calls, only a small subset performed that staging task. This suggests excess operational context, not insufficient product context. No evidence shows an unauthorized controller mutation.

Overall cached input was 81.6%; migration worker caching was 91.5%. Those ratios did not make the workflow efficient: unnecessary repeated exploration still consumed substantial input and time. Compilation and graph review shared source context but reported zero cached input; the evidence does not establish why. The final review reported 13,696 cached input tokens. No cost or latency claim can be derived from these counters alone.

## Why diagnostics were insufficient

The model summary reported five planner/reviewer calls and 89,961 input tokens. It excluded the two workers, although their durable harness results contained usage. Consequently it understated this run's total input by roughly 8.6 times. Raw private worker records were needed to identify the 18-call exploration pattern. A production-quality report should distinguish phase and role, correlate invocation/attempt/run, account for known worker usage, mark unavailable values rather than zero, and label usage scope and caching denominators.

The existing diagnostics also had no separate LFS upload span. Upload-before-publication acceptance is supported by the pinned publisher contract plus successful remote hydration, not an invented upload timing receipt. Diagnostics must remain observational and privacy-safe, never a lifecycle journal or continuation authority.

## Broader testing and bounded follow-ups

The earlier review-evidence gaps were real acceptance blockers: passing commands could not justify a reviewer inferring missing controller provenance or Git attribution. The process nevertheless discovered them too serially. A permanent deterministic two-item same-path LFS rehearsal now exercises policy, capture, selection, materialization, automatic review and final validation together. Future evidence changes should test complete reviewer-facing packets and failure cases in that rehearsal before publishing another artifact; unit tests alone cannot establish cross-component evidence sufficiency.

Queued bounded follow-ups are [#122](https://github.com/clockgrove/factory-rebuild/issues/122) for role-complete usage accounting and [#123](https://github.com/clockgrove/factory-rebuild/issues/123) for worker/controller responsibility isolation with packet-level regressions. Existing #108 owns citation compactness, #114 owns materialization text budgets, and #121 owns safe interrupted-delivery continuation. None requires replaying a failed run or expanding #81. Private pilots and live second-provider qualification remain separate workstreams.
