# Capabilities

Part of [the design](../DESIGN.md).

## Capabilities

A capability is a module that plugs into one of these seams:

| Seam               | Used by                                                                      | Examples                                                                                        |
| ------------------ | ---------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------- |
| `Planner`          | plan, plan review, result and final review, repair diagnosis, Dream, propose | Codex, Claude and Copilot; a review is a call in the `reviewer` role (providers/planner.ts)     |
| `Worker`           | the work step                                                                | Codex, Claude, Copilot local; OpenAI Agents, Claude Managed Agents (parked: not live-qualified) |
| `Delivery`         | publish, ci, merge                                                           | regular PRs, native linear stacks, LFS assets                                                   |
| `Planning options` | the plan step                                                                | planner lookups, quality checkpoint, package-manager update, amendments                         |
| `Knowledge`        | planning, plan review, work prompts and review                               | curated playbook (planning and plan review), repository memory, Dream proposals, peers' notes   |
| `Observers`        | the run log                                                                  | diagnostics, accounting, scorecard, capture export                                              |

`Planner` (providers/planner.ts) and `Worker` (work/worker.ts) are interfaces with one adapter per provider. The other seams are modules.

Rules for modules:

- A module returns step outcomes. It never writes state directly, takes a lock, starts a background loop, or keeps its own archive.
- A step keeps its result in `done` and what must outlive a repair in `kept`, under its own step or item keys (work/facts.ts). Only the GitHub sync keeps module data (`modules.github`). Large bodies go in the run log.
- A module validates its input once, where the input enters, and doesn't re-verify it later.
- **Configuration** is checked once, when it loads, by one helper (checked.ts `section`): each section lists its known keys with their types and defaults. An unknown key is refused by name. All problems are reported in one message. The sections are `repository`, `checkout`, `queue`, `providers` and `defaultProvider` (providers/config.ts), `planning` (with `planning.context`, knowledge/settings.ts), `execution`, `policy`, `validation`, `finalValidation`, `delivery`, `reviewArtifacts` (review/artifacts.ts), `sandbox`, `media`, `autonomy` (the allowances, the spend ceiling and `requiredEnvironment`), `progress`, `tracking`, `capture` and `sessions`. The configuration file, the state directory and `policy.secretlintConfig` must lie outside the target checkout, and the configuration must not name Factory's own repository.

Review and knowledge see what the worker saw:

- **Review inputs.** Result review and final review get a controller input receipt for each item: every read-only input its worker got (source assets and bound selections) with kind, path, visibility, media type, size and sha256, and Factory's digest-checked copy under `inputs/` in the evidence root, within the candidate copy bounds.
- **Files a change left unreachable.** Result review and final review get a controller row listing the files, within the item's owned paths (final review: every item's), that a file the change edits or removes imported at the base, that the result still holds, and that no tracked source file of the result imports (review/result.ts `UNREACHABLE_GUIDANCE`, review/orphans.ts, #2253). Each must be removed, kept with a reason a handoff note records, or refused as dead code. It reads static relative imports (JS/TS, CSS, Python) from Git; a form it can't resolve keeps a file off the list.
- **Git LFS in the evidence root.** Result, QA and final review export Git objects, so `candidate/`, `base/` and `changes/` hold a Git LFS file as its pointer, and the exact-tree inventory gives the pointer's size, while every validation checkout restores the real bytes of each pointer at a `filter=lfs` path before any command runs (media.ts `hydrateTree`). Review is told so (review/result.ts `LFS_GUIDANCE`): pointer text at a `filter=lfs` path is no defect, pointer text at any other path is the file's real content, which validation read as it is, and an LFS file's content is judged from the validation that passed and any digest-checked copy, such as a candidate set member's `reviewCopy`. A Work Item's result review gets the candidate receipt of its own selection and of each dependency's whose delivered result the reviewed base holds (work/step-review.ts `reviewCandidates`, #2193), so an item that only uses another item's media, such as its test, has the same copies of the selected bytes. A dependency's receipt lists and copies its selected set only (its `deliveredDependency` field says so); that dependency's own review judged its alternatives, which never reach the dependent's review. Every receipt's selected members are copied before any alternative's, so alternatives never spend the 64 MiB copy bound a delivered member needs. The export is not hydrated: that would fetch from origin inside review, which has no retry or hold route for it, and media over the export's 1 MiB per-file bound would still be left out.
- **Images in the evidence root.** Every reviewer that reads a tree can look at an image file in it, a PNG under `candidate/` or a review copy under `media-sets/` alike: Claude's Read, Copilot's `view` (which returns an image as image data) and Codex's `view_image` (#2193). Codex's is on only for a call with a tree, beside its read-only shell, and reads through the same read-only, network-less permission profile, so it sees no file the shell can't; a planning call without a tree has neither. Images a review-artifact selector captured are attached to the request besides ([Review artifacts](#review-artifacts)).
- **Questions the evidence root answers.** A result, QA or final review whose answer asks the operator (needs-human) about a criterion whose text, finding detail or question names a file the evidence root holds, or whose finding cites a receipt with a review copy there, goes back to the reviewer once before the step holds (review/result.ts `heldEvidence`, #2124): Factory names those files (at most 12 a criterion) and the reviewer answers just those criteria again. A file is named by its repository path, a path suffix, a basename with an extension, a backticked identifier or call whose name is its basename's stem (`sharedQwfwq("ab")` names `candidate/src/sharedQwfwq.js`; the directory and file names inside a backticked path are not stems), or, for a review copy under `media-sets/` or `inputs/`, the destination or source path its receipt gives. A finding that cites a controller candidate or input receipt among its evidence also names every review copy that receipt lists and the evidence root holds (a member over the copy bounds has none), so a question about how the offered sets differ goes back with every set's copies even when it names no file. The 12 are the most directly named: exact path matches (receipt destinations included) before path suffixes (`src/index.ts` names `candidate/src/index.ts` exactly and each `packages/*/src/index.ts` by suffix), suffixes before basenames, basenames before stems, and within each the candidate and review copies before `base/`; a cited receipt's copies come after every file the text names, in the receipt's order. When candidate media sets were supplied, the send-back also says the operator's selection settles their appearance. A new valid finding replaces the question, and a valid refusal in the send-back's answer also replaces the earlier finding of a criterion that was not sent back, since that round is the one told to read the files, unless that finding is a question: a question not sent back named or cited nothing the root holds, so it still reaches the operator. A question still asked, or an invalid answer to the send-back, reaches the operator as before, so questions about authority, product decisions and absent facts still hold. Only the answer's own needs-human findings are sent back: a criterion the operator decided, or that an earlier review of the same tree asked about, never is, and a question Factory asks for an invalid answer is no finding. It is provider-neutral: Codex, Claude and Copilot reviewers get the same send-back, logged as `result-review-evidence-sendback` (or `objective-review-evidence-sendback`) with the criteria and the number of files named.
- **Peers' notes.** A worker gets the advisory notes of accepted earlier items it depends on, that name it as a consumer or that touch its owned paths (planning/schedule.ts `peerNotes`), with each cited path in its checkout or staged read-only. Result review gets those notes beside the item's own, and final review every accepted item's notes (`objectiveNotes`; review/result.ts `knowledgeRows`), each cited path compared with the reviewed commit.
- **Worker Validate.** A Claude, Copilot or Codex worker can run the item's declared validation commands itself before it hands off (work/self-validate.ts, one implementation for all three; Copilot and Codex serve it as the tool `run_validation`, Codex through an MCP server Factory registers in the worker's private Codex configuration, providers/codex-validate.ts): the exact locked install, then the repository's formatter when `validation.formatCommand` is set (every worker kind gets it, #2166), then the commands, on a snapshot commit in a fresh checkout, through the sandbox. It is the worker's check only: the validate step still runs every command. The tool takes `commands`, the indices of declared commands for a targeted run (#2281): those, and the earlier ones their plan `after` lists (#2290), in declared order, after the exact install and the formatter, so a worker fixing one failure gets its verdict in seconds, not the minutes of a full run; every command's scripts are still pinned. A targeted run never counts: it covers no tree for handoff, and its result says to finish only after a full run passes. It skips every other command, so the worker names any earlier command the failing one needs that no `after` lists (a build, code generation); a failure names its command's index and, after a targeted run, the earlier commands it skipped. A selection that runs every command is a full run. Claude's and Copilot's permission checks admit that argument and nothing else, as Codex's server does. A full run after a failure starts with the failed command and the earlier commands it needs, then runs the rest in declared order (`runOrder`, #2290): each run is a fresh checkout that stops at its first failure, so it fails fast where the last one did. A reordered run that fails at the command it started with is followed by one in declared order (and if that fails at the same command, the run after it is reordered again), so an `after` that leaves out what a command needs costs one run and never keeps a full run from passing. A command that declares no `after` may need every earlier one, so its run keeps the declared order: run first, a command that needs one that makes its inputs would fail however the worker fixed it. The validate step and final validation always run in declared order. Commands whose `after` puts them in independent groups run at once, each group in a checkout of its own, in the worker's runs and in those (see Independent commands at once in [Steps](steps.md)). Each call's `worker-validate` event records `targeted`, `first` (the earlier failure a full run started from), `durationMs`, `passedMs` (what its passing commands took of it) and `sinceEditMs` (from the newest file the result changes to the verdict), which the benchmark's `totals.workerValidation` aggregates. A Claude or Codex worker whose turn ends with no passing run on its final files is asked once, in the same conversation, to run it (`FinishRequests`). A Codex or Claude worker's prompt also says what its own shell lacks (installed dependencies, a writable .git, and the network unless it is `host`; a Codex shell also has no /tmp) and that Factory validates a new commit of its uncommitted result (#2156). On Codex's production models (`tool_mode` code_mode_only) an MCP tool is by default a deferred nested tool of `exec`, named nowhere in the model's request, so Factory's server sets `omit_tools_from = ["deferred"]`, which declares the tool in exec's description, and a Codex worker's prompt and its request to validate give the exact call, `await tools.mcp__factory_validation__run_validation({})` inside exec (`CODEX_VALIDATE_CALL`). An exec cell yields to the model when its script still runs after its yield time (about 30 s by default), and the model then polls the cell with `wait`, each call a round over its whole context. So the same configuration sets `features.code_mode.default_exec_yield_time_ms` to the tool's timeout: the cell blocks until Validate answers, as a Claude worker's Validate does, and a running Validate costs no model round (#2167). A result is at most 30,000 characters for every worker (`VALIDATE_RESULT_CHARS`), under the 10,000 tokens of tool output Codex keeps: past it the criterion map shortens its note excerpts, then names the criteria it can't show whole, never cutting one. A failed run's result is bounded in UTF-8 bytes, since Codex counts bytes and a command's output (a linter's code frames, say) can take several a character: its command's output gets the bytes the rest of the result leaves (at least 8,000), cut to keep its start, its end and the lines between them that say why it failed (a compiler's or linter's error, a thrown error, a failed test, a non-zero exit), each with the lines around it, then, with the room left, lines that only mention an error or a failure; a code frame's source line or a passing test is never taken for a failure. It says how much it left out (`failureExcerpt`, #2201); the validate step's repair finding and the diagnosis cut a long output the same way. The excerpt is only a preview: the failed command's complete output (its attempt file, streams in order, within 8 MiB, its first and last 4 MiB past that, the cut stated) is written read-only to `.factory-validate/run-<n>-<command>.log` in the worker's checkout, which the result names, so no pattern decides what the worker can see (`writeValidateLog`). The worker's instructions say that the log, or running the command in its checkout, shows everything, including what a tool leaves out of its own report; Factory passes no tool's flags. `.factory-validate` is private staging: Validate's snapshot, collection, the no-change check and so the published diff leave it out whatever the target's `.gitignore` says, each Validate run removes it first, and collection removes it. The validate step keeps a failed command's output longer than a repair's brief (8,000 characters) in a file named by its content: the next worker attempt gets a copy at `.factory-validate/validate-step.log`, its brief says so, and the diagnosis can name that path in `requestedFiles` to read it (whole within 256,000 characters, else its excerpt). A media item's selected set is never in that snapshot, so for such an item the tool, a failed run, the request to validate and a turn-limit continuation all say that a failure caused only by its absence is expected, no fix and no discovery (`SELECTED_MEDIA_VALIDATE`, #2116), as the worker prompt's media contract does.
- **Worker edits.** A worker is told to edit through its provider's structured edit tool, which fails when its target text doesn't match instead of changing nothing (#2283): a Codex worker through Codex's apply_patch, a nested tool of code mode's `exec` that exec's description declares, with the exact call `text(await tools.apply_patch("*** Begin Patch\n..."))` (codex-worker.ts `CODEX_EDIT_CALL`), and a Claude worker with a shell through Edit and Write (claude-worker.ts `CLAUDE_EDITS`). Both are told to change files through a shell script only for a mechanical change across many files, and to make the script fail when a pattern matches nothing (work/scripted-edits.ts `SCRIPTED_EDITS`). A command that reads as a scripted rewrite (a string or regular-expression replace and a file write, or an in-place `sed` or `perl`) and leaves every worktree file it names unchanged gets a note: for Claude, Factory's `run_command` hashes those files before the command and appends the note to its result; Codex runs its own commands, so Factory compares the files with the checkout's HEAD once the command finishes and, while they still match HEAD when the turn ends, asks the worker on the same thread before its result is taken (at most twice an attempt). The command is never parsed as a program. On Codex a file matching HEAD may have been changed back to it, so the tree is read as the attempt begins and after each command, and a rewrite naming a file seen changed since HEAD in the attempt (then, or through apply_patch) goes unnoticed; a rewrite that changed any named file, including back to HEAD, is never noted. A worker's `edits` count from the worktree as well as from its edit tools' reports, so a shell's edits count (run-log.md `counts`).
- **Best effort for the lifecycle.** Admission, withdrawal and retirement never open the knowledge store, so a store that can't open or is slow (no `node:sqlite`, a corrupt or unwritable database) never holds them back. A run's end (its records, its episode once terminal, and the release of its playbook pin) is its settled observation: for a run that settles, or that a re-queue or a withdrawal replaces, one that hasn't landed is kept and retried in the background with backoff, and logged: an episode may be recorded late, but the queue never waits. Each is saved as `finished/<issue>@<run>.observe.json` (before the state file moves, for a retirement) and removed once it lands, and startup lists and retries these files, so a restart never loses one.
- **Bounded store.** The store keeps the newest 1,000 episodes and the newest 10,000 other memory records; a write past either cap drops the oldest. Dream reads the newest episodes first and planning bounds what it shows, so neither reaches the dropped ones. An episode a Dream approval still checks stays past the cap: every episode given to the newest playbook, to an undecided proposal, or to a Dream call still running within its deadline.
- **Repository memory** shows a record that cites any path inside the planning selectors, with only its admitted paths; its staleness still comes from every cited file's digest, and a changed file outside the selectors is counted, not named. A reference record carries its Source's text, so it needs every path admitted. An episode counts a native stack's lower layer as merged when the stack merged.
- **Memory in every role.** Planning, the worker, the repair diagnosis, result review and final review read repository memory through one query (memory.ts queryMemory): a role, the paths it works on and a byte bound per role (knowledge/index.ts roleMemory), for every Objective unless the installation sets `planning.context.memory` to false. The worker and its result review ask the same query, so review sees what the worker saw. Memory is a header that frames it as advisory data, never instructions, then the records as one JSON array, the whole text within the role's byte bound. Review gets it as an incomplete `memory` row: it never supports a pass, and a finding that cites only it is invalid. The read is one read transaction; a store that can't be read, or is busy past a second, gives empty memory and a log line, never a hold.
- **Planner lookups.** For every Objective, the planner (and the amendment planner) may answer with context lookups instead of a plan, on every provider: a memory search (the same query, memoryLookup), a tracked file or one of its sections, or the tracked paths under a prefix, all read-only at the base and inside the planning selectors (planning/lookup.ts). Factory answers them in a structured turn, keeps the round in `state.kept` with the base and issue digest it was answered for (a re-read that moved either starts fresh) until the step is done or replanned, and asks again with every answer, so a crash re-asks only the planner call. The frozen `planning.context.bounds` cap it: rounds at min(`maxRounds`, `maxProviderCalls`), `maxRequestsPerRound` requests a round and `maxBytes` of answers per step. A request past them, outside the selectors or with traversal is refused to the planner with its reason (requests past the per-round cap as one entry, echoed fields cut to 256 characters); answers are redacted of secret values and framed as data.
- Provider APIs stay inside their adapter.

### Review artifacts

`reviewArtifacts` is written by hand and empty by default: a list of at most 8 selectors, each keeping evidence from a passing validation command for review (review/artifacts.ts, checked once at load). `command` is the validation command exactly as the plan runs it, one line. A selector is one of two kinds:

- **Image:** `{"command", "receipt": {"stdoutPathField", "stdoutSha256Field", "maxBytes"}, "image": {"file", "sha256Field", "maxBytes"}, "candidate": {"file", "sha256Field"}}`. The command's last stdout line is a JSON object: its `stdoutPathField` names a receipt file in the checkout and its `stdoutSha256Field` holds the receipt's SHA-256. The receipt is a JSON object: its `image.sha256Field` holds the SHA-256 of `image.file`, a complete PNG beside the receipt, and its `candidate.sha256Field` the SHA-256 of `candidate.file`, a file tracked in the validated tree (for a Git LFS pointer, the object it points to). Field names are direct JSON fields (letters, digits and `_`); `receipt.maxBytes` is at most 1 MiB and `image.maxBytes` at most 16 MiB. Reviews get the PNG as an image.
- **Text:** `{"command", "text": {"source", "stdout", "stderr", "files", "locator"}}`, with `source` and at least one of the others. `source` is the tracked file that declares this proof. `stdout` and `stderr` are `{"maxBytes"}`. `files` is a list of checkout files, each `{"file", "mediaType", "maxBytes"}` with `mediaType` `text/plain` or `application/json`. `locator` is `{"stdoutPathPrefix", "files"}` or `{"stdoutPathPrefix", "match"}`: the command prints the literal prefix once, followed by an absolute directory inside its own TMPDIR, and the named files there, or every file whose name matches `match` (`{"pattern", "mediaType", "maxBytes", "maxTotalBytes", "maxFiles"}`, `pattern` a file name with exactly one `*`), are kept. Each body is at most 16 MiB, and a match at most 64 MiB and 256 files in all.

Paths are relative to the checkout, without `.`, `..` or `.git`. Final validation and QA items apply every selector; a coding Work Item applies only the text selectors whose `source` it owns. One validation keeps at most 8 images and 64 MiB. A command whose output doesn't match its selector fails like any validation command. Planning and plan review see the selectors, so a brief can route proof through one. Selectors are operational (see [Frozen configuration](state.md#frozen-configuration)) and grant no command authority, but a plan's validation holds when the installation no longer has a selector the plan was made with, with `retry` (after restoring it and restarting the service), `replan` and `cancel`; an added selector is fine.
