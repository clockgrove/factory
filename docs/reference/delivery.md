# Delivery and cancel

Part of [the design](../DESIGN.md).

## Delivery

`delivery.kind` in the installation's configuration picks how Work Items reach the default branch. The service reads it once at start.

- **`regular`** (default): one PR per Work Item, merged with a merge commit once its checks pass.
- **`native-stack`**: each linear chain of the plan is one GitHub native stack. Each layer's PR targets the branch below it, but GitHub judges every layer by the default branch's rules (the stack's base), so Factory reads each layer's required checks and review-thread rule there. Factory makes the GitHub stack as soon as every layer is published, in the CI step of a layer above the bottom; from then on, that step reads ready only with the stack there. Making it runs the `pull_request` workflows filtered to the default branch on every layer above the bottom (GitHub sends `stacked`, with `base_ref` the default branch, and later pushes and reopens carry it too; an unfiltered workflow that already ran on the layer does not run again), so a workflow filtered to `branches: [main]` reports there, and GitHub requires the default branch's checks there. The PR's own base stays the layer below. Until the stack exists, a check that hasn't registered on such a layer is a wait on the layers above (a gate no person holds, which never asks), not the 15-minute question; from then on, the 15 minutes run from when Factory began waiting, not from the layer's push (see [Waits](steps.md#waits)). The top layer's merge step merges the whole stack with one shared merge commit, after finding the stack again (or making it, if it is gone). An item off a chain is an ordinary PR. When GitHub updates the layer below with the default branch, GitHub merges its new head into the layer above too, with no worker; only a conflict is that layer's repair. When a layer is repaired, every layer above it is cleared: Factory replays each one's change onto the new head below it (with no worker when the replay applies cleanly, except for a media item), then validates, reviews and publishes it again.
- **A failed check.** A check that fails on the PR's head, required or not, is the item's repair, with the failed checks' annotations, failed steps and Actions log tails as its finding; a cancelled or stale one is a question. First, Factory compares the failed checks with the default branch's current head, as GitHub already shows them; it runs nothing there, since a rerun on the default branch can start what follows a run on it (a release, a deployment). A check that failed there too, with any failing conclusion but cancelled or stale, fails every PR into it whatever the change, so no repair can fix it: the step holds at once, before any rerun, and spends no repair. A failed run there that a later run of the same check on that head passed, or still runs (a workflow run again by hand), doesn't count. The question says the default branch is red for that check, with its failed step and log excerpt there, and names the PR's other failed checks, which are repaired once it passes. Fix the check on the default branch (another Objective can), then answer `retry`, which compares again; `repair` when the Work Item's change is meant to fix that check there too, which repairs it at once (no rerun) and counts as a repair; or `cancel`. On the operator's `retry` to the CI step, the PR's failures may be the old base's: while the default branch's runs of the failed checks still run, the step waits for them; once they all pass there and the delivered head lacks the default branch's head, GitHub brings the PR up to date with it (update-branch, no worker, as for strict protection) and its checks run again, instead of a rerun or a repair. Otherwise the finding says what the default branch's head shows of each failed check (no run, one still running, or how it ended and when), and that a pass a day or more before the failure may not hold now: a check that depends on when it runs, such as an audit of locked dependencies, can start failing on the default branch after it passed there. Then, when every failed check is a GitHub Actions job that failed or timed out in its workflow run's first attempt, Factory waits for that workflow run to finish, then reruns its failed jobs once (`rerun-failed-jobs`, logged `ci-rerun`) and waits for them. A pass goes on to merge, logged `ci-flaky`, and the Objective's report names the checks as possibly flaky; a failure on the rerun is the repair, and its finding says the rerun failed too. A run is rerun at most once per head: GitHub's run attempt and the item's kept rerun (`ciRerun`) both bound it, so a restart or GitHub's lag never reruns it twice, and a rerun GitHub still doesn't show after 2 min is a question. Without Actions read access, or when GitHub won't rerun the run (404, 409, 422), the repair comes at once; a 403 asks for Actions: write. The repair's finding also lists the artifacts the failed checks' workflow runs uploaded, each name's latest upload with its size, and holds the UTF-8 text files (JSON, logs, reports) of up to 64 KiB each of the 5 smallest whose download is at most 1 MiB, 64 KiB in all, so the repair diagnosis needn't ask for them. They are read in memory as text and never run; a zip entry is inflated only to the size it declares, and every entry inflated counts toward the 64 KiB. A rate limit while reading them is waited out; any other failure leaves them out.
- **Strict protection.** A PR BEHIND the default branch is updated by GitHub (update-branch), not by a worker; a conflict is the item's repair. A repair that only replays the refused change onto a moved base, and applies cleanly, runs no worker either.
- **`accept`.** A stack that merged by other means (layer by layer, or with different merge commits) is a question with `accept`, `retry` and `cancel`. `accept` takes the unit as delivered once every layer is merged at Factory's head with its merge commit on the default branch; otherwise the question names what is missing.
- **Media in Git LFS.** Selected media of any format is committed through Git LFS. The destinations are Factory's: before the work step collects a media item's result, it restores each candidate destination as the base has it (removing one the base lacks), so a worker's write there never reaches the result, and it refuses a result that still changes one. The select step writes the chosen set only when the repository's `.gitattributes` routes every destination through Git LFS (`filter=lfs`). Otherwise it is the item's repair when the item owns `.gitattributes`, and a question with `repair` (new candidates at routed destinations), `replan` and `cancel` when it doesn't. The plan check makes that rare: a media item must own `.gitattributes`, depend on an item that does, or own destinations the base already routes (one exact file per role, or a directory a rule covers whole), and the planner is shown the base's `filter=lfs` rules. Validation and final hold when a destination is not its member's LFS pointer. Publish uploads the objects before it pushes, and final checks that origin serves them at the integrated commit.
- **After the last merge.** Final validation and final review run on the default branch head, so every Objective gets QA on the default branch, with or without commands (see [QA on the default branch](steps.md#steps)).
- **Changing it.** A plan is split by the setting its Objective froze, so once it has a plan, a retry, `adopt` or `switch` never switches it: a changed `delivery.kind` holds it with only `retry` (after setting it back and restarting) and `cancel` (selection.ts `changed`), and the engine refuses a `switch` that would freeze the other kind (planning/plan.ts `deliveryChange`). Before its plan, `adopt` and `switch` take the new kind. To deliver an Objective with the other kind: cancel it, set `delivery.kind`, restart the service and queue it again.

## Cancel

`/factory cancel`, `factory cancel <issue>`, or the Objective's deadline (see [Deadlines](steps.md#deadlines)):

1. Abort the Objective's running steps. This kills the process groups the service started for those steps; it tracks them in memory, and they die with the service anyway.
2. Close every open Factory PR of the Objective (each branch under `factory/<issue>/`, whatever plan made it) with a comment, delete those branches Factory made (see [Idempotence](steps.md#idempotence)), close the issue as not planned, and set Status to Cancelled.
3. Mark the state cancelled, recording who cancelled and when (`ended`).
4. Once the cleanup has settled, post one closing comment on the issue (github-sync.ts, marker `cancelled:<run>`): who cancelled it, or that its deadline passed, and what the cleanup left if it settled without finishing, then the operators' @mentions (see [GitHub identity](setup.md#github-identity)). Only a `/factory cancel` comment's author is named (`ended.source: github`); a CLI cancel says "the operator", never the host's user name. A cancelled Objective settles once it is posted, or GitHub refused it (`cancel-comment-given-up`). None for a dequeued run withdrawn before it started, or while `progress.enabled` is false. Crash points: `sync:cancel:before` and `sync:cancel:after`.

Cancel reads only the Objective's state file and its open PRs, so its cost doesn't depend on history. It can't be refused. The cleanup (`cancel:cleanup`) never asks: each attempt tries every part (the PRs, then the branches of PRs it closed, the issue, the work files), so one that fails never stops the others, and a failed attempt names what it left. It retries in the background with the usual backoff (from a rate limit's reset, when one says), and only after 5 failed attempts in a row over at least `maxWaitMs` (3 h) since the first does it settle anyway, so an outage or a rate limit alone never leaves PRs open: its result records what was left (`{ left, failures }`, engine.ts `Left`), the log has a `cleanup-left` event, the closing comment and `factory status` name it, and the Objective can be queued again. Until it settles, `factory run N` is refused (`cleanup_running`) and names `factory reset N`. An issue GitHub no longer has here (404 or 410: deleted; a redirect, while the repository itself has not moved: transferred away) has nothing to close: the PRs, branches and work files still go, and the Objective settles.
