# Delivery and cancel

Part of [the design](../DESIGN.md).

## Delivery

`delivery.kind` in the installation's configuration picks how Work Items reach the default branch. The service reads it once at start.

- **`regular`** (default): one PR per Work Item, merged with a merge commit once its checks pass.
- **`native-stack`**: each linear chain of the plan is one GitHub native stack. Each layer's PR targets the branch below it, but GitHub judges every layer by the default branch's rules (the stack's base), so Factory reads each layer's required checks and review-thread rule there. Factory makes the GitHub stack as soon as every layer is published, in the CI step of a layer above the bottom; from then on, that step reads ready only with the stack there. Making it runs the `pull_request` workflows filtered to the default branch on every layer above the bottom (GitHub sends `stacked`, with `base_ref` the default branch, and later pushes and reopens carry it too; an unfiltered workflow that already ran on the layer does not run again), so a workflow filtered to `branches: [main]` reports there, and GitHub requires the default branch's checks there. The PR's own base stays the layer below. Until the stack exists, a check that hasn't registered on such a layer is a wait on the layers above (a gate no person holds, which never asks), not the 15-minute question; from then on, the 15 minutes run from when Factory began waiting, not from the layer's push (see [Waits](steps.md#waits)). The top layer's merge step merges the whole stack with one shared merge commit, after finding the stack again (or making it, if it is gone). An item off a chain is an ordinary PR. When GitHub updates the layer below with the default branch, GitHub merges its new head into the layer above too, with no worker; only a conflict is that layer's repair. When a layer is repaired, every layer above it is cleared: Factory replays each one's change onto the new head below it (with no worker when the replay applies cleanly, except for a media item), then validates, reviews and publishes it again.
- **A failed check.** A check that fails on the PR's head, required or not, is the item's repair, with the failed checks' annotations, failed steps and logs as its finding; a cancelled or stale one is a question. For an Actions job the log is each failed step's own (up to 2 steps): the lines the job's log (its last 64 KiB) holds from the second GitHub says the step started to the end of the second it completed, the last 60 lines or 4000 characters of them (delivery.ts `stepLog`). Its neighbours can write within those seconds, so Actions' own step markers bound it there: in the start second it begins at the first `##[group]Run` line (what comes before is the step before's), or, when failed steps before it ended in that second, at the one after their `##[error]` lines, in the completion second a `##[group]Run` line after an `##[error]` line is the next step's (one that runs after a failure, which may fail too) and ends it, and it ends at its last `##[error]` line. The failed checks' excerpts (their failed steps, annotations and logs, up to 3 checks) share 6000 characters, the logs at least half of each check's share, so every excerpted check's error reaches the repair diagnosis, which keeps a finding's last 7000. The job's own tail is mostly what runs after a failure (artifact uploads, post-job cleanup), so it is used only when GitHub gives no step times or the log holds none of the step's lines (#2120). First, Factory compares the failed checks with the default branch's current head, as GitHub already shows them; it runs nothing there, since a rerun on the default branch can start what follows a run on it (a release, a deployment), unless the operator named one workflow it may run there (`delivery.baseRerun`, see A fresh run on the default branch below). A check that failed there too, with any failing conclusion but cancelled or stale, fails every PR into it whatever the change, so no repair can fix it: the step holds at once, before any rerun, and spends no repair. A failed run there that a later run of the same check on that head passed, or still runs (a workflow run again by hand), doesn't count. The question says the default branch is red for that check, with its failed step and log excerpt there, and names the PR's other failed checks, which are repaired once it passes. Fix the check on the default branch (another Objective can), then answer `retry`, which compares again; `repair` when the Work Item's change is meant to fix that check there too, which repairs it at once (no rerun) and counts as a repair; or `cancel`. On the operator's `retry` to the CI step, and while the item's result is one the operator's `revalidate` checked again (a result rereview, see Result rereview in [Holds](holds.md#holds-and-answers)), the PR's failures may be the old base's: while the default branch's runs of the failed checks still run, the step waits for them; once they all pass there and the delivered head lacks the default branch's head, GitHub brings the PR up to date with it (update-branch, no worker, as for strict protection) and its checks run again, instead of a rerun or a repair. After a result rereview, a delivered head whose failed checks all ended before the operator's `revalidate` landed, once nothing is left to rerun there (its failed jobs were rerun already, or can't be), is a question, not a repair that would only repeat the one the rereview answered, unless the default branch passed every one of them after it failed on the PR in the run of `delivery.baseRerun`'s workflow Factory made or waited for (see below), which repairs as usual: it says what the default branch's head shows of them, and offers `retry` (compare again: run them again on the default branch or fix them there first), `repair` and `cancel`. That covers the default branch unmoved since a pass from before the failure, and a native-stack layer above the bottom, which isn't brought up to date with the default branch itself. Otherwise the finding says what the default branch's head shows of each failed check (no run, one still running, or how it ended and when), and that a pass a day or more before the failure may not hold now: a check that depends on when it runs, such as an audit of locked dependencies, can start failing on the default branch after it passed there. Then, when every failed check is a GitHub Actions job that failed or timed out in its workflow run's first attempt, Factory waits for that workflow run to finish, then reruns its failed jobs once (`rerun-failed-jobs`, logged `ci-rerun`) and waits for them. A pass goes on to merge, logged `ci-flaky`, and the Objective's report names the checks as possibly flaky; a failure on the rerun is the repair, and its finding says the rerun failed too. A run is rerun at most once per head: GitHub's run attempt and the item's kept rerun (`ciRerun`) both bound it, so a restart or GitHub's lag never reruns it twice, and a rerun GitHub still doesn't show after 2 min is a question. Without Actions read access, or when GitHub won't rerun the run (404, 409, 422), the repair comes at once; a 403 asks for Actions: write. The repair's finding also lists the artifacts the failed checks' workflow runs uploaded, each name's latest upload with its size, and holds the UTF-8 text files (JSON, logs, reports) of up to 64 KiB each of the 5 smallest whose download is at most 1 MiB, 64 KiB in all, so the repair diagnosis needn't ask for them. They are read in memory as text and never run; a zip entry is inflated only to the size it declares, and every entry inflated counts toward the 64 KiB. A rate limit while reading them is waited out; any other failure leaves them out.
- **A fresh run on the default branch.** Off unless the operator sets `delivery.baseRerun: { "workflow": "quality.yml" }` (or `factory setup --base-rerun-workflow quality.yml`): the file name of one workflow in the top level of `.github/workflows` that runs on `workflow_dispatch` with no required input, which the operator declares free of side effects: nothing releases or deploys from it, and nothing that does runs after it. Readiness checks both and warns of a workflow that runs after it (see [Setup](setup.md)). A pass on the default branch from a day or more before the PR's failure says nothing about a check that depends on when it runs (new advisories against locked dependencies, as on Clockgrove #821), so, when the default branch's latest run of a failed check passed that long before and that run was this workflow's (its workflow run ran that file, as GitHub says; without Actions read access it is unknown, and nothing runs), Factory dispatches the workflow on the default branch (`workflow_dispatch` on its head, logged `base-rerun`) before any rerun or repair, and waits for its run. While a run of the workflow is already in progress there for any failed check, Factory waits for that one instead, with no dispatch (a dispatch would start a second run there and, in a cancel-in-progress concurrency group, cancel that one), and dispatches for a failed check still stale once it ended. Its result is then the default branch's latest for those checks, so the comparison above uses it: a failure there holds with no repair (the default branch is red), and a pass goes on to the rerun and the repair as usual, the finding saying which run passed; after a result rereview too, once the default branch passed every failed check after the PR's failure. A run that ended with no result (cancelled, as by a newer run in a cancel-in-progress concurrency group, or skipped) is no fresh pass: the failure is judged on what the default branch showed before, and the finding says the run gave no result and that the pass before it may not hold now. Factory runs it at most once a day per default-branch head for a Work Item (the item's kept `baseRerun`); a native stack's merge, which judges every layer, dispatches it at most once between them, and each layer keeps and logs that run and waits for it. It waits up to 60 minutes for its result; past that, or when GitHub refuses the dispatch (404, 422), the failure is judged on what the default branch shows, and the finding says why; the operator's `retry` and a result rereview, which otherwise wait for the default branch's runs of the failed checks, no longer wait for that one. A 403 asks for Actions: write. Factory runs no other workflow there, never for a check whose stale pass came from another workflow or that has no run there, and never when the operator answered `repair` to the main-is-red question. The setting is frozen with each Objective (it grants Factory authority on the default branch), so changing it holds a running Objective once with `adopt`.
- **Strict protection.** A PR BEHIND the default branch is updated by GitHub (update-branch), not by a worker; a conflict is the item's repair. A repair that only replays the refused change onto a moved base, and applies cleanly, runs no worker either.
- **`accept`.** A stack that merged by other means (layer by layer, or with different merge commits) is a question with `accept`, `retry` and `cancel`. `accept` takes the unit as delivered once every layer is merged at Factory's head with its merge commit on the default branch; otherwise the question names what is missing.
- **Media in Git LFS.** Selected media of any format is committed through Git LFS. The destinations are Factory's: before the work step collects a media item's result, it restores each candidate destination as the base has it (removing one the base lacks), so a worker's write there never reaches the result, and it refuses a result that still changes one. The select step writes the chosen set only when the repository's `.gitattributes` routes every destination through Git LFS (`filter=lfs`). Otherwise it is the item's repair when the item owns `.gitattributes`, and a question with `repair` (new candidates at routed destinations), `replan` and `cancel` when it doesn't. The plan check makes that rare: a media item must own `.gitattributes`, depend on an item that does, or own destinations the base already routes (one exact file per role, or a directory a rule covers whole), and the planner is shown the base's `filter=lfs` rules. The plan check also refuses a plan that declares no media roles when an item owns a file the Objective names, the base lacks and a base rule routes through LFS: such a file is new media, and as ordinary work it would skip capture and selection. Whether an Objective asks for a choice among candidates is only in its prose, so the check reads these structured facts instead and refuses nothing once any item declares media (planning/checks.ts `undeclaredMediaFindings`). Validation and final hold when a destination is not its member's LFS pointer. Publish uploads the objects before it pushes, and final checks that origin serves them at the integrated commit.
- **After the last merge.** Final validation and final review run on the default branch head, so every Objective gets QA on the default branch, with or without commands (see [QA on the default branch](steps.md#steps)).
- **Changing it.** A plan is split by the setting its Objective froze, so once it has a plan, a retry, `adopt` or `switch` never switches it: a changed `delivery.kind` holds it with only `retry` (after setting it back and restarting) and `cancel` (selection.ts `changed`), and the engine refuses a `switch` that would freeze the other kind (planning/plan.ts `deliveryChange`). Before its plan, `adopt` and `switch` take the new kind. To deliver an Objective with the other kind: cancel it, set `delivery.kind`, restart the service and queue it again.

## Cancel

`/factory cancel`, `factory cancel <issue>`, or the Objective's deadline (see [Deadlines](steps.md#deadlines)):

1. Abort the Objective's running steps. This kills the process groups the service started for those steps; it tracks them in memory, and they die with the service anyway.
2. Close every open Factory PR of the Objective (each branch under `factory/<issue>/`, whatever plan made it) with a comment, delete those branches Factory made (see [Idempotence](steps.md#idempotence)), close the issue as not planned, and set Status to Cancelled.
3. Mark the state cancelled, recording who cancelled and when (`ended`).
4. Once the cleanup has settled, post one closing comment on the issue (github-sync.ts, marker `cancelled:<run>`): who cancelled it, or that its deadline passed, and what the cleanup left if it settled without finishing, then the operators' @mentions (see [GitHub identity](setup.md#github-identity)). Only a `/factory cancel` comment's author is named (`ended.source: github`); a CLI cancel says "the operator", never the host's user name. A cancelled Objective settles once it is posted, or GitHub refused it (`cancel-comment-given-up`). None for a dequeued run withdrawn before it started, or while `progress.enabled` is false. Crash points: `sync:cancel:before` and `sync:cancel:after`.

Cancel reads only the Objective's state file and its open PRs, so its cost doesn't depend on history. It can't be refused. The cleanup (`cancel:cleanup`) never asks: each attempt tries every part (the PRs, then the branches of PRs it closed, the issue, the work files), so one that fails never stops the others, and a failed attempt names what it left. It retries in the background with the usual backoff (from a rate limit's reset, when one says), and only after 5 failed attempts in a row over at least `maxWaitMs` (3 h) since the first does it settle anyway, so an outage or a rate limit alone never leaves PRs open: its result records what was left (`{ left, failures }`, engine.ts `Left`), the log has a `cleanup-left` event, the closing comment and `factory status` name it, and the Objective can be queued again. Until it settles, `factory run N` is refused (`cleanup_running`) and names `factory reset N`. An issue GitHub no longer has here (404 or 410: deleted; a redirect, while the repository itself has not moved: transferred away) has nothing to close: the PRs, branches and work files still go, and the Objective settles.
