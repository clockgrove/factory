# GitHub displays

Part of [the design](../DESIGN.md).

## Live status comment

Each Objective run has one live status comment on its issue (progress.ts), posted once and then edited in place. Its marker names the run (`status:<run>`). github-sync.ts writes it as a background job, so it never blocks a step, and a failed write retries with the job's backoff.

- **Body.** The `factory status` model (status.ts `statusOf`), redacted with the configuration's secrets before it is rendered: the phase and the next action, the Work Item table, each running item's worker (active, or quiet for 5 min or more, from its latest `worker-activity` event), each planner or reviewer call running now (its role, phase and Work Item, provider, model and effort, when it started, its turns and the input tokens in its context, from its `model-call` and latest `model-progress` events; see [Live calls](run-log.md#live-calls)), waits, open questions with their answers, the decisions taken (planning decisions and step answers), and run details: admission, provider, the frozen configuration's digest and the model calls so far (`model-usage` events, by role, with their reported tokens). Its last line is the run's record, hidden: the operator's criterion decisions and final command retirements under the plan accepted now (a rebuilt plan's until it lands), as JSON with `<` and `>` escaped, then the JSON's SHA-256, which `factory reset` rebuilds them from (progress.ts `StatusRecord`, see [State](state.md#state)). Each reason is cut to 1,000 characters; past 16,000 characters entries are left out oldest first, accepts before refusals and both before retirements, and `dropped` counts them. A record that doesn't match its digest is taken as none. While a reset stands, the resetting record writes no status comment. Times show in the host's zone, or in `FACTORY_DISPLAY_TIMEZONE` (display.ts `displayTime`, as in `status`), with "N min ago" as of the edit. So do the times in the waiting note, a limit's reset in its question and the deadline note. It lists the first 50 Work Items, 20 questions and the newest 20 decisions, then "+N more" and `factory status N`, and cuts whole lines to stay under the plan comment's size limit. Untrusted text is escaped: inline code takes a fence longer than any backtick run inside (markdown.ts `code`), and prose escapes `<`, `>` and `@` (`prose`); the hold comments use the same helpers.
- **Edits.** At most one per Objective per 60 s, and only when the body's stable part changed, by its hash. The stable part leaves out the ages, the edit time, each worker's last report and counts, and a running call's start, turns and tokens, so liveness moves only with the 10 min refresh while a step runs. Edits share an installation-wide budget of 300 an hour; over it an edit waits, except the one that shows a finished Objective's final status. The run log is read forward from where the last render stopped, and files last written before the run began are skipped.
- **Settling.** A finished Objective settles only once the comment shows its final status. A lasting refusal (a 4xx that isn't a rate limit), or any other failure three times in a row (a render that keeps throwing), gives the comment up for the run (`statusGivenUp`, logged as `status-given-up`), and it then counts as shown. A run withdrawn before planning goes only once its comment, if one exists, is edited to the final "Withdrawn before planning; queue it again to start afresh." line and its open question comments say they no longer apply (`statusWithdrawn`); or once the comments are given up, or the issue is gone. With progress comments off, only the question comments are edited. None is posted for it.
- **Questions.** `progress.includeQuestions` (default true) lists the open questions with their answers. False shows only how many are open and `factory status N`; the question comments still post.
- **Off.** `progress.enabled: false` turns off Factory's progress comments: this one, a failure's evidence and the open-question reminder (see [Holds](holds.md#holds-and-answers)), the status note and gate reminder (see [Waits](steps.md#waits)) and the cancel comment (see [Cancel](delivery.md#cancel)). Question comments and replies always post, because they are how a question is answered on GitHub. The section is operational, so changing it never holds a started Objective.
- Crash points: `sync:status:before` and `sync:status:after`.

## Work Item issues

Each Work Item of the plan in force (`currentPlan`) gets one display-only issue (tracking.ts): a sub-issue of the Objective, with the `factory:work-item` label, the Objective's priority labels (`P<n>`), `tracking.issueType.workItem` as its native type (default `Task`), a card on the Project the Objective's card is on, blocked-by links that mirror the item's dependencies, and one live comment (marker `item-status:<item>`) showing its phase, PR, repairs and open question. Questions and answers stay on the Objective; the issue never drives anything, and the queue never takes a Work Item issue as an Objective: the Project items query leaves out the `factory:work-item` label, and an issue read by number is skipped when its body starts with Factory's item marker.

- **Roles.** github-roles.ts makes the role labels `factory:objective` and `factory:work-item` once per installation, found by name before one is created, and resolves each role's type against the types the repository offers. It never changes repository settings or creates a type: a type the repository doesn't offer is a setup prerequisite (`factory setup` readiness warns), the run logs `issue-type-missing`, and the issues go without it. Once per run, the first tracking pass gives the Objective issue the `factory:objective` label and `tracking.issueType.objective` (default `Feature`) when it has no type yet (a type someone set is kept), and reads its `P<n>` labels: its items get those labels, and a priority dropped from the Objective is removed from them. These are the only labels Factory adds.
- **Cards.** Each item's issue is added to the Project the Objective's card is on, and its Factory field shows the item's phase as the Objective's card shows its own: Building while a step runs or waits, Needs you while a question holds it, Done once merged, and Cancelled when the Objective ends without it or it leaves the plan; a pending item's card has none. Only the option last written is recorded (`status`), so a write happens only on a change. It never reaches the queue: the queue's reads leave out the Work Item label. A card on another Project, or a field that refuses the write, shows no phase for the run (`statusless`, logged `item-status-refused`); the issue's other writes go on. The Project returns the card an issue already has, so a replay adds none. A refused card is logged (`item-card-refused`) and not tried again this run.
- **Written in the background.** github-sync.ts runs one tracking job per Objective on the keyed job runner, with its backoff and deadline: at most once per 60 s while the Objective runs, at once after it ends, and only when the state shows a write is due. What was written (issue numbers, body and comment hashes, links, closed) is kept in `modules.github.tracking`, so an unchanged plan costs no GitHub call, and a lookup (one sub-issue list, not one per item, plus one label list only while a creation isn't recorded) runs only when an item has no issue recorded. A run again of the same Objective keeps the issues recorded by the run before, so it finds them and their links (even one created but never linked), and reopens an issue whose item is planned again once its plan is accepted.
- **Text.** The body is the marker, then the item's goal, acceptance and dependencies; the title is the item's title. Model text is escaped (markdown.ts `prose`, `code`; `[` and `]` too), so nothing in an issue or its comment is hidden but Factory's marker. Everything is redacted on its way to GitHub.
- **Closing.** A merged item's issue closes as completed: the PR body says `Closes #N` once the issue exists, and the job closes it otherwise (a native-stack layer). An item that leaves the plan (replan or amendment) or is left when the Objective is cancelled or finishes closes as not planned, its comment first naming why. A finished Objective settles only once every item issue shows its end, or GitHub refused its close (it is never counted closed).
- **Duplicates.** A create repeated because GitHub's label list hadn't shown the first yet (a crash or a lost response between the create and its record) can make a second issue for one item. The time the first create began is kept (`tracking.duplicates`). One sweep runs 10 min later, or when the Objective ends but no sooner than 2 min after (GitHub's list lag), whichever is first: one label list since then, and every open issue carrying an item's marker that isn't its recorded issue, and whose title and body still read as Factory wrote them, is closed as not planned, with a comment naming the issue Factory keeps (marker `duplicate:<issue>`; logged `item-issue-duplicate-closed`). A copy someone edited may be in use, so it only gets a "Possible duplicate of #N" comment and stays open (marker `possible-duplicate:<issue>`; logged `item-issue-duplicate-left-open`). A run with no repeated create makes no extra call.
- **Refusals.** A native type the repository refuses is logged (`item-issue-untyped`) and not tried again this run. A refusal of a write to one item's issue (deleted, locked, transferred; a 4xx that isn't a rate limit) is kept on that item (`item-issue-refused`): its other writes stop for the run, its close is still tried, and every other item's issue is still written and closed. Only a refusal of the Objective-wide calls (the lists, a create: issues off, no access, repository gone), or three other failures in a row, gives tracking up for the run (`tracking-given-up`); it then counts as shown.
- **Off.** `tracking.enabled: false` creates nothing. Like `progress`, the section is operational.
- Crash points: `sync:item-issue:<create|edit|label|card|status|link|comment|reopen|close>:<before|after>`, `sync:item-duplicate:<comment|close>:<before|after>`, `sync:objective-role:<before|after>` and `sync:roles:label:<before|after>`.
