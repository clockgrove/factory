# Holds and answers

Part of [the design](../DESIGN.md).

## Holds and answers

A hold is a question with named answers. Each answer is an option, Factory data that says what it does:

```jsonc
{
  "id": "plan-1",
  "question": "...",
  "options": [
    {
      "answer": "answer",
      "family": "answer",
      "consequence": "Sends your decision back to the planner.",
      "needsText": true,
      "recommended": true,
    },
    {
      "answer": "switch",
      "family": "switch",
      "arg": "claude",
      "consequence": "Runs this Objective on provider claude from now on.",
    },
    {
      "answer": "cancel",
      "family": "cancel",
      "consequence": "Ends the Objective at once and closes its PRs and the issue.",
    },
  ],
}
```

- **Options.** `answer` is the literal token (`/factory <answer>`); `arg` is what follows it for a parameterized answer (`switch NAME`); `family` groups options (retry, replan, cancel, wait, switch, adopt, accept, refuse, select, answer, repair, retire, reset); `consequence` is one short sentence; `needsText` marks an answer that needs text after it; exactly one option is `recommended`. Every place that raises a hold supplies its options through one helper (engine.ts `hold`), which writes the consequences of the common answers (retry, replan, cancel, wait, switch, adopt, answer, fresh) once. The engine expands `switch` into one option per configured provider, this Objective's own included (it re-freezes that provider to its current configuration), and names those options in the question, so the text and the options can't disagree; a limit's hold offers only the other providers. A recommended `switch` with several targets recommends the Objective's own provider, else the next other answer, never an arbitrary provider. The engine adds `cancel`, `replan` to a failure where the workflow can plan again, `fresh` to a Work Item's question (see Fresh start), and `revalidate` where the item has a refused result to check again (see Result rereview).

- **Scope.** A hold outcome declares its scope, `item` (the default) or `objective`. An `item` hold from a Work Item's step (`item:<id>:…`) stops only that item, the items that depend on it (they aren't runnable until it merges), and the native-stack layers above it (they run once the layer below is published, so the workflow names a layer's predecessors and their holds stop it too: work/steps.ts `layersBelow`). Other items keep starting and finishing. An `objective` hold stops every step. A cause that is installation-, account- or provider-wide is `objective` wherever it is raised: the issue closed or edited after planning, a non-writer's Objective awaiting approval, a full disk, repository or origin access (a GitHub login, permission or missing-repository refusal, a push the login or the repository refuses, merge commits or native stacks the repository doesn't allow, the checkout's Git refusal or origin problem), a provider's login, billing, quota or model, its setup or missing SDK package, running as root, the package or offline-install environment, an unavailable sandbox, the installation's configuration (reviewArtifacts, delivery kind, Secretlint), and a limit that resets too far away (`wait`/`switch`: the limit is the account's). Provider holds are classified in one place, for every provider: a `PlannerError` that holds is Objective-wide unless the cause is one Work Item's own (its files, review images or session budget: `PlannerError.itemHold`), and `providerOutcome` maps it for the planner and every worker (providers/planner.ts). Every hold from a step that isn't a Work Item's stops the Objective too: planning, final, final review, report, cleanup and unreadable state. Final and report wait until every item is settled, so they wait for every item hold. The engine's error, transient-wait and human-gate questions, the per-path repair allowance and crash-loop suspect questions, and media, select, revalidate, review and secret-scan questions take the scope of the step that asks; the Objective's implementation repairs question is Objective-wide.
- **Several at once.** At most one hold per Work Item and one for the Objective are open. A step that asks while a hold covering its scope is open (the Objective's, or its own item's) opens nothing; its retry comes due at once, so it runs again right after that answer and asks then if the cause remains, so an Objective-wide cause is asked once. A crash-loop suspect is asked as soon as no open hold stops its step, before the step runs again: its count stays on the interrupted attempt until then (see [Steps](steps.md)), and a repair or replan that clears the step drops it. Answering `wait` to a limit grants the wait to every step waiting on that limit; `switch` runs every step waiting on a provider's limit again at once on the new provider. Each hold has its own id, question and answers. The Objective shows `holding` (Status "Needs you") while any hold is open. A held Objective takes no queue slot only when its holds stop every step it could start.
- **Saved.** Open holds are in the state file, so a restart restores them. A repair that clears a held step drops its hold (the question is about work that is gone); cancel drops them all.
- Each hold is posted as one issue comment with its own marker (`hold:<id>`), and it lists the options, each with its consequence. It ends with the operators' @mentions (`operators`, see [GitHub identity](setup.md#github-identity)), so GitHub notifies them of each new hold; an edit to the bound form keeps them, and the reminder and the live status comment mention no one. Its text is redacted with the configuration's secrets and escaped, and only then measured: a question over 20,000 characters loses its middle, never its last 4,000 (where the engine's notes are: the switch answers and the deadline), and the cut names `factory status N` and never splits an escape. If GitHub refuses the comment (a 4xx, such as a 422 for its size) or it fails three times in a row other than transiently, it is written compact from then on (the question cut to 4,000 the same way, logged as `question-compacted`) and keeps retrying, so a hold is never left unshown.
- **Failures.** A hold with the cause `failure` is that same one comment, opening with the failed step and its Work Item, then the question (which says what failed), then its evidence when the step errored before it asked: the count of errors in a row, since when, and the first and last error, each redacted and cut to 1,000 characters. A failed Work Item's live comment on its own issue says so and points to the Objective, where it is answered. With `progress.enabled: false` it reads like any other question.
- **Reminder.** A question shown on the issue and still open 24 h after it was asked gets one reminder comment that links its question comment (marker `remind:hold:<id>`). The hold's id carries its step and `askedAt`, so a restart never posts it twice and a question asked again is a new one with its own day. `FACTORY_REMIND_MS` shortens the 24 h for tests, as for a human gate. None while `progress.enabled` is false. Crash points: `sync:remind:before` and `sync:remind:after`.
- **Answering:** a comment `/factory <answer> [--question <id>] [arg] [text]` from a user with write access to the repository, or `factory answer <issue> <answer> [arg] --question <id> [--text ... | --text-file PATH]` (an absolute path to a regular UTF-8 file, opened once without following a link). An answer's text is at most 64 KiB (a comment's limit), however it comes: the engine refuses a longer one (`invalid_answer`). `fresh` isn't offered on a merge step's question, which may come after GitHub merged the PR, nor on an aggregate or QA item's, which keep no worker result or worktree (their `retry` checks again). `arg` names the option of a parameterized answer (`switch NAME`): the CLI passes it apart from the text, and in a comment it is the first word after the answer; plain `switch` works when it has one option. The engine applies the option's own `arg`. An answer must never land on a question its author didn't read:
  - The CLI always names the question. `factory retry <issue> --question <id>` answers `retry` to it. Without `--question`, `factory retry` never answers a hold: it runs now the waiting steps no open hold stops, and is refused while an Objective hold is open (or when every waiting step waits on a hold).
  - A bound answer (`--question <id>`) is checked against nothing else: the id names one asking, and a re-ask gets a new id.
  - A comment that names no question applies only when exactly one hold is open, its comment showed the short form before the answer comment was written, and no other question's comment was shown after it. Otherwise it is refused, and the reply lists the open question ids and the bound form. Every time compared is GitHub's: the answer comment's `created_at`, the hold's `shownAt` (the `created_at` or `updated_at` of the question comment Factory posted or edited), and `lastShownAt`. A host clock never enters, so skew can neither misapply nor refuse an answer. Until GitHub shows a hold's comment, only the bound form answers it.
  - A hold's comment shows the short form `/factory <answer>` only while it is the one open hold. When another opens, or another question's comment was shown after it (so its short form would be refused), Factory edits the comment to show `/factory <answer> --question <id>`.
  - An answer that names a hold that isn't open is refused, naming the open ones. `factory status` lists every open hold with its id and the command that answers it.
- **Comments are read by GitHub's clock.** A run reads comments from when its card was queued (the option's `updatedAt`), and an unreadable state's from its question; the cursor only moves forward. GitHub's `since` filters on `updated_at`, so only a comment created at or after the cursor counts: an earlier run's comment, or an old one edited later, never acts.
- The service checks for comments every 30 s while it is holding. If someone without write access answers (or the user doesn't exist), that's ignored and logged. A comment whose author's access GitHub can't report now waits in a list of up to 20 per Objective and is checked again with backoff; the comments after it go on.
- **In an agent host.** The director skill shows each open hold with the host's question tool (Claude Code's AskUserQuestion, or its Codex equivalent): the question, and each option with the recommended one first and its consequence. A hold with more than 4 options (the tool's limit) is asked in two steps: the family, then the option. That gives the operator an app notification. The chosen answer runs `factory answer`. `factory status --json` lists open holds in this shape, so the skill needs no answer table and no parsing; the text status lists the options too.
- An answer that matches none of its hold's options gets a reply naming the valid answers. Nothing else changes. So does an answer whose option needs text (`needsText`, such as planning's `answer`) when it has none.
- `cancel` is valid at every hold and at any time.
- **Fresh start.** A Work Item's question also offers `fresh` (the workflow's, like `replan`: work/steps.ts `freshable`), except an allowance's question, whose way past is `more`. It discards the item's result and work: its base, refused result, finding, diagnosis and media selection go, and the next attempt starts a fresh worktree on the current base, with no repair context. It is a repair (work/steps.ts `repairOutcome`), so it counts against `perPath` and `implementationRepairs`, and the native-stack layers above move onto its new head. The engine applies it from one place, in the same save that spends the answer, so its hold id takes effect once.
- **Provider model.** A model the provider's login can't serve holds with `switch NAME` and `cancel`. Copilot checks its model list before it opens a session, so this hold costs no request, and it also offers `retry`: the retry reads the list again before any session, so it bills nothing and succeeds once an admin enables the model. A session that served another model offers no `retry`, because each one bills a request. The operator sets the model and restarts the service, then answers `switch` with the same provider's name, which re-freezes its changed configuration, or with another configured provider's name.
- **Configuration changed.** An Objective whose frozen configuration differs from the service's holds once with `adopt`, `switch NAME` (when another provider is configured) and `cancel` (see Frozen configuration); once it has a plan, a changed `delivery.kind` offers only `retry` and `cancel`. The `switch` options are then every configured provider: another one moves the Objective there, and this one re-freezes its changed configuration.
- **Final review.** `retry` to final review's refusal means the default branch was fixed: final validation runs again on the new head, then the review. A `retry` to an error or wait question on final review only runs the review again.
- **Criterion decisions.** A result, QA or final review that asks about criteria it can't judge (needs-human) holds with `accept <n> <reason>` and `refuse <n> <reason>` for each one, n being the criterion's number in the question, from 1 (the option's `arg`). Before it holds, a needs-human finding whose criterion, detail or question names files the evidence root holds goes back to the reviewer once with those files (see Questions the evidence root answers in [Capabilities](capabilities.md)), so the operator is asked only what the reviewer still can't judge from them. A refusal that holds for a person also offers `accept <n> <reason>` for each criterion the reviewer refused: final review's refusal, and a Work Item's repair diagnosis question and repair-allowance question when a result review refusal drives its repairs (see Accept a refused criterion). There is no cap: more than 4 options are asked in two steps. The reason is required. Each answer decides one criterion and is kept for its review's scope (`item:<id>:decisions`, `final-review:decisions`), keyed by its question's id so a rerun records it once, and tied to the accepted plan, so a replan drops it (a reset carries it to the rebuilt plan). A decision applies only to reviews of the exact tree it was made on: `accept` counts the criterion as passed there, and a later tree (after a repair, or a new integrated result) judges it again, with the earlier decision as evidence. `refuse` counts it as unmet on that tree: a Work Item's result goes to repair with the refusal as its finding (a repair like any other, counted against the allowances), a QA item holds as refused, and final review takes its refusal path. While open criteria remain, the step asks again about only those. The review the operator is answering is kept (`held`), so its verdicts on the same tree stand and the reviewer is called again only for criteria neither it nor the operator decided: once every open criterion is accepted, the step goes on with no model call. Every review sees the decisions as a controller row; final review sees the Work Items' as evidence and decides with its own. The report and status (`Decided:` lines; `decisions` in `--json`) list each with its reason and tree (planning/plan.ts `decisionsOf`), and repository memory records each as a human decision with its criterion, outcome, reason, tree and item.
- **Accept a refused criterion.** On a Work Item's repair diagnosis or repair-allowance question after its result review refused, `accept <n> <reason>` records the operator's decision that criterion n is met by the refused result (`item:<id>:decisions`, like any criterion decision, so it applies only to that exact tree). When no refused criterion still stands, the refused result is checked again unchanged (no repair or rereview is charged); if it can no longer be checked as it is, the step holds with `fresh` and `cancel`. Otherwise what still stands is diagnosed again. On the repair-allowance question the engine runs the step once past the allowance to record the decision (`Workflow.unspent`), and a further repair asks for `more` again. The item's review then counts the accepted criterion as passed on that tree, and a later tree judges it again.
- **Can't be planned.** The planner may answer `cannotPlan` instead of a plan (planning/wire.ts): the Objective as written can't be met, with the concrete obstacle and what the operator must change. The plan step logs `planner-cannot-plan` and saves the round with no plan (`cannot`, marked `refusalReview`), and the plan review step judges the refusal instead of a plan, against the planner's rule for `cannotPlan`, the Objective, the pinned sources and the repository (planning/prompts.ts `renderRefusalReviewCall`). A review with no findings confirms it: the decide step holds with the planner's reason, says the review confirmed it, and offers `replan` (recommended: plan again from the issue after editing it), `answer <guidance>` (one more round with the guidance; it plans in full, as there is no plan to revise) and `cancel`. A fix finding names the rule or evidence that allows a plan, and the decide step sends it to the planner as another round, like a plan's fix findings: that round plans in full, told that its refusal was overturned and why. An operator-decision finding holds with the refusal and the review's question, offering `answer`, `replan` and `cancel`. A refusal whose review finds the same as the round before holds with the refusal and those findings. Each round counts against `planningRevisions` like any other, so past the allowance the review's fix findings, or an `answer`, wait for `more`. The review of a refusal is given the corrections the planner was given in the round before it, from Factory's checks or the review, with that round's refusal when it was one, and when that round wasn't reviewed, the findings the last review sent the planner too (not an operator question the decide step dropped or the operator answered), so it rules consistently with them (`REFUSAL_REVIEW_LATER_ROUND`): it reports an earlier review finding that a plan is allowed again unless the new refusal names an obstacle that finding didn't weigh, and when a refusal rests on earlier findings (they conflict, say) it judges those findings again and withdraws a wrong review finding rather than confirming the refusal; a check finding stands. Its answer names no item, as there is no plan, so the items an earlier finding named are shown apart (`earlierItemIds`) and a finding it restates is a valid answer. A plan after a reviewed refusal gets the full first review, as there is no reviewed plan it revises; when the refusal's review overturned it, that review is also given the refusal and the findings the planner planned from (`GRAPH_REVIEW_AFTER_REFUSAL`), so an objection a finding withdrew isn't raised again without a new reason. A plan review answer Factory refuses as invalid is retried with the reason. Why: live, a planner refused after a reviewer's contradictory objections, and the refusal went to the operator unreviewed (#2111). A refusal an earlier Factory saved without the mark asks at once, as it did then. In an amendment the refusal is a plan round with no draft (`cannot` in `amend:<id>:plan`), and the independent review judges it against the rules the planner was given, the started-item rule among them (planning/prompts.ts `renderRefusalReviewCall`). A review with no findings confirms it: acceptance rejects the amendment with the planner's reason, which then asks with `replace` and `continue`. A fix finding names the rule or evidence that allows a plan and sends the round back to the planner like any other (kept with `refused` in `amend:<id>:revisions`, charged to `planningRevisions`), and the next round is told its refusal was overturned. An operator-decision finding, or the same findings twice, rejects the amendment with the refusal and the review's finding; any other rejection by its review (an answer invalid twice, say) also starts with the refusal. A refusal in a whole answer (a plan with no planner answer to revise) keeps no answer, so its next round answers in full again. A later refusal's review is given the findings of the last round sent back, and when those hold no review finding, the last review's that sent one back, in the same way; its answer names previousPlan's items, so a new item of an earlier round's draft is shown apart (amendments.ts `earlierReview`). Its one retry after an invalid answer is told why.
- **Edited during planning.** `continue` to the question about an Objective edited while it was planned keeps the plan and accepts the text GitHub shows then, so building asks again only after a later edit.
- **Configuration.** The service reads its configuration once at start. A hold that asks for a configuration change says to restart the service before answering.
- **Media selection.** When the work step staged two or more candidate sets, select asks; a single set is selected without asking and bound to every direct dependent, recorded with `by` `factory` and logged as `media-auto-selected`, with no dependents bound. The select question's answer is a candidate set id, then optionally `bind ITEM...` (direct dependents that get the set as read-only input), then any text: the text is recorded with the selection as the operator's reason and shown to review. `repair`, optionally with text, sends the sets back for new ones: the work step runs again with the text as its finding and read-only copies of the sent-back sets (origin `sent-back` under `.factory-inputs/assets`), since that attempt's staging is gone; it stages new sets (capture refuses one with a sent-back set's content), and select asks again (or selects the set, if there is only one). The chosen set is written only through Git LFS (see [Media in Git LFS](delivery.md#delivery)).
- **Repair diagnosis.** When diagnosing a refused result needs a decision, the work step holds with `answer <text>`, `retry` (diagnose again) and `cancel`. The text reaches the next attempt as the operator's guidance, framed as the operator's words, never as Factory's diagnosis. It is keyed by its question's id: the correction it becomes is saved with that id, so a rerun or a replayed answer never applies it twice, and a newer answer replaces it. When that guidance is the attempt's only correction (the diagnosis saved for its repair is the operator's, with none of Factory's) and the worker resubmits the refused result unchanged (it followed guidance to keep it), that is no repair (work/step-work.ts `guidedOnly`): the result is checked again as `revalidate` would check it. The engine answers `revalidate` for the step itself where the item can take it and a result rereview is left, charged as one (engine.ts `rereview`, logged as `rereview-kept`); otherwise the step asks with the worker's final response, offering `answer`, `replan`, `fresh`, `revalidate` where it is taken (past the rereview allowance it asks for `more`) and `cancel`. Why: live, guidance to keep a change whose CI failed only on the default branch's locked dependencies was refused as no repository change and charged as a repair past both repair allowances (#2131). Any other attempt that resubmits the refused result, or changes nothing, is still refused. It also offers `revalidate` (see Result rereview), and after a result review refusal `accept <n> <reason>` (see Accept a refused criterion). A diagnosed repair names one file the item owns; a media item's may instead name its candidate staging (`.factory-media/`, `.factory-assets.json`) or its candidate receipt, since its candidate sets live outside its owned paths, so a review that refuses a candidate set is repaired with new candidates within the repair allowances, like any refused result. A fix that needs files no Work Item in the plan owns (a module an existing test imports, say) is decided `discover`, accepted only when no item's owned paths cover any of them: the correction is Factory's own, telling the worker not to change them but to write an in-scope `.factory-discovery.json` naming them, which is proposed like any worker's discovery (see Amendments). A fix to a file another item owns, other than a blamed predecessor's, is still a question. A question is only for what a person alone can decide (their intent, an external fact, an authorization or prerequisite), never how the plan should change: amendment planning decides that. So a diagnosis that answers with a question about files no Work Item owns (named in its `ownership`) is decided `discover` instead, checked the same way, and its `diagnosis` event says `rerouted: "operator"`. The question stands when its `ownership` names only files Work Items own, or when a diagnosis already asked the worker to propose those same files (whatever the failure's or the evidence's wording), since the plan still lacks them after that. A decision only a person can make that the plan change needs (product, scope or authority) is still asked: amendment review's operator-decision finding rejects the amendment, and the Objective holds (see Amendments). A repair drops the media selection, so select asks again, only when it comes from select or publish's Git LFS check, a refused criterion cites a selected destination as evidence, or cites the candidate receipt and no change to a file the item owns (review judges a criterion about the alternatives from the receipt, so a refusal that also cites the worker's change to its own file, a change row's `file` such as its test's, is a gap there and the selection stands; a pinned source's row, such as an owned README.md's, is no change the worker made and never counts; work/step-deliver.ts `aboutMedia`), or its diagnosed correction's structured path (never its prose) names a selected destination, the candidate staging or the candidate receipt (work/step-deliver.ts `correctsMedia`). Factory writes a kept set as it captured it, so no repair can make that correction to it: the work step drops the selection (or the candidate sets kept from capture, on the same test) with the worker's result, gives the worker read-only copies of the dropped sets' members (origin `replaced` under `.factory-inputs/assets`), and tells it to make the correction in new sets; select asks again. A question or retry before the worker finishes keeps the selection, so its rerun decides the same from the saved diagnosis. Only a repair that refuses the result itself (validate, review, CI, merge, a secret the result writes) records it as refused, so the next result must differ. A select or publish media repair (new candidates, a selection that couldn't be written, missing LFS objects) records nothing: its correct fix may leave the tracked tree unchanged.
- **Predecessor blame.** The diagnosis may decide `predecessor` (repair.ts): the failure comes from the result of a Work Item this one builds on, not its own work. It names that predecessor and one of its owned files, with the evidence and the predecessor's correction; the diagnosis also gets the predecessors' files the failure names, the review cites or it asks for. Like a repair, a blame never repeats a correction that already failed for the same failure: the blame joins the blamed item's tried corrections, and one the predecessor already tried asks instead. A native-stack layer below, not yet merged, is repaired with that correction as its saved diagnosis (work/steps.ts `blameOutcome`): its repair counts, the layers above move onto its new head as for any layer repair, and the blamed item keeps its change to replay there, with its own repair `free`. A merged predecessor is never reopened: the item holds with the evidence and the predecessor's PR, offering `amend` (recommended), `replan`, `answer <text>`, `retry` (diagnose again) and `cancel`; the blamed repair is `free` (the hold outcome's `free`), so it counts against no allowance. `amend` proposes amendment `blame-<item>-<repair>`: a Work Item after the predecessor that owns the blamed file and makes its correction (see Amendments).
- **Amendments.** A proposal of work the accepted plan lacks becomes an amendment (planning/amendments.ts): the planner revises the current plan, Factory's plan checks and the amendment fence check it, an independent review judges it, and an accepted one is the plan from then on, posted as the plan comment (crash points `amend:post:*`, and `amend:data:*` for a plan in parts). The planner and the review get the files its discovery cites (amendments.ts `citedFiles`): every regular file its reason, evidence or acceptance names, then its ownership paths, read from Git, never a worktree, at the commit it was proposed from (a worker's collected result, the refused result it resubmitted unchanged, or its item's start when it left no change; a blame's refused result or item start; the plan's base for an operator's proposal or a commit Git no longer has). They are whole within the 256000-byte bound repair diagnosis puts on named files; a file past what is left of it, a binary file or a path the commit lacks is listed with a note instead. Each proposal is kept as `amend:<id>:proposal` and charges one `planningRevisions`, shared with the plan's own revision rounds, never refunded. The fence holds an amendment to the started-item rule (amendments.ts `startedItemRule`), which the planner and the review are both told with the items it binds: a started Work Item keeps its spec; only a reattempt item (the proposing worker's own unpublished item at its current attempt, or for an operator's proposal a failed, unpublished one) may grow its owned paths or dependencies, keeping every entry, or replace or drop a validation command the validate step failed its result on under the plan accepted now (the item's `validationFailed` fact, which the validate step keeps; the planner and the review get them as `replaceableValidation`), keeping every other command in its order (a list that only adds commands, or reorders the ones it keeps, replaces nothing), and only then restate its acceptance, brief and non-goals; further work goes in a new item. Whether a replaced command really can't pass on any correct result, and whether its replacement proves what it proved, is the review's to judge (#2107). The planner and both reviews (of a plan round and of a `cannotPlan`) are also told that a media item's worker checkout never holds its selected set and that Factory validates the item after selection, so a discovery resting on a missing destination the item's own media roles fill shows no gap (rubric.ts `SELECTED_MEDIA_ABSENT`, #2116). The planner answers a discovery that shows no gap with no change to the plan, never `cannotPlan` (`NO_GAP_ANSWER`); the plan review reports a change made only for one as a defect, and the refusal review sends a `cannotPlan` resting on one back with a fix finding asking for no change (`NO_GAP_REFUSAL`). A reviewed round that leaves the plan unchanged (amendments.ts `unchangedPlan`: the same items, coverage, pre-integration checks and source exclusions) settles the amendment as continued, saved as `unchanged` in `amend:<id>` and logged as `amendment-unchanged`: nothing is posted, and the proposing item carries on with its result as collected, as after `decline-discovery` (a blame's item asks again without `amend`), with no new attempt. Factory applies the rule itself before it checks a plan round (amendments.ts `restoreStarted`): each started item keeps the accepted spec, with every owned path and dependency it had plus those the answer adds, and a reattempt item whose owned paths or dependencies grew, or whose validation replaces only such commands, takes the answer's validation, acceptance, brief and non-goals. Every other change to a started item is set back, in the round's answer (against the accepted plan's own answer) and its draft, and never goes back to the planner on its own. A round whose draft was set back beyond its answer (a plan with no answer of its own) keeps no answer, so that a started item as the planner changed it is never shown again as the plan: its next round, and once it is accepted the next amendment, answers in full with the plan as it stands. The fields set back, by item, are kept with the round as `restored` (in `amend:<id>:plan`, or with the round in `amend:<id>:revisions`), logged as `amendment-restored`, shown to the review as `FACTORY_AMENDMENT`'s `restoredFields`, and, when the round goes back, told to the planner. The review judges the draft as set back: a started item left with acceptance or validation it can't meet is its fix finding. The fence then finds what that can't settle: a started item removed, or grown though it isn't a reattempt item. It also keeps every item, coverage entry and source exclusion, and a started native stack's layers. A plan round the plan checks (an ownership overlap a grown item makes included), the fence or the independent review refuse goes back to the planner, as in first planning: it revises its own answer with the findings (the review's as `review` corrections, the fence's naming the started item's changed fields), the next round is checked and reviewed again, and each such round is kept in `amend:<id>:revisions` and charges one more revision. An operator-decision finding, or a round with the same findings as the one before, rejects the amendment instead. The planner's `cannotPlan` is a round its review judges too (see Can't be planned). Intake never refuses a proposal for the allowance. Past it, the amendment's planning step asks before the planner runs, with `more` (grants as much again and plans it), `refuse` and `cancel`. Each `more` is kept once per question (`amend:<id>:grants`, with who and when), and every grant, to planning or to an amendment, adds to the same allowance. While one is pending, or rejected and not yet settled, no other step starts (workflow.ts); the steps after it read the amended plan, so an item it widened runs with its new owned paths and dependencies. One is in flight at a time: one that lands together with another is rejected at once, and each rejection stays open until its own answer settles it. The fence is checked again at acceptance, against the state then: a round it refuses there (an item started while the amendment was planned) goes back to the planner the same way, kept with `atAcceptance`, and the revised round is reviewed again (each review result names the round it reviewed). A plan with no planner answer to revise (one `factory reset` rebuilt) is amended by a whole plan: the planner answers in full, with the plan as it stands. Every amendment step offers `refuse` on its questions, its errors-in-a-row question included (`Step.redo`). Proposals come from:
  - a worker's in-scope `.factory-discovery.json` (checked by `workDiscoveryProblem`, as at intake), on its own or as a repair diagnosis's `discover` asked (see Repair diagnosis): it is proposed at once as `worker-<item>-<attempt>`, and the item waits for the amendment's outcome with no question. `factory decline-discovery N --item ITEM --reason R` is the operator's override while it is pending, until the review of its current plan round is done (once acceptance sends a round back, it can be declined while it is planned again): the amendment settles as declined (still charged), its planning steps' open questions go, and the item carries on with its result as collected, the reason recorded. Only when intake refuses the proposal (`proposalProblems`: say, an unsettled rejection) does the item ask, offering `decline-discovery <reason>` and `cancel`. Past the allowance, the amendment's own `more` question asks instead, and `decline-discovery` still works while it is open. A backlog discovery is only logged;
  - a merged predecessor's blame answered `amend` (see Predecessor blame);
  - `factory propose-amendment N --file F`, a JSON file with the six discovery fields, checked by the service where it enters and refused with `amendment_refused` naming each problem; there is no comment form.

  The item that proposed starts a new attempt once its amendment is accepted: a repair counted against no allowance (`free`), with its correction saved so no diagnosis runs, moved onto the current start with its change so far replayed. A rejected amendment holds the Objective with `replace <correction>` (a replacement that repeats its discovery, with the rejection as its diagnosis; it charges a revision and is reviewed again), `continue` (the plan runs without it; the item that proposed carries on as if declined) and `cancel`.

- **Result rereview.** `revalidate` says a refused result was correct and Factory's check was at fault. The engine offers it on a Work Item's question wherever the workflow can check a refused result again (work/steps.ts `revalidatable`): on a coding item's work step while its refused result is kept and (for media) its selection stands, while no finished worker run waits for collection and no replay onto a new start is due, and until a work-step question finds it can no longer be checked (gone, off its base, or its selection gone: the refused fact is marked `unrecheckable`), which covers the repair diagnosis question, the repair allowance question and the work step's other questions after a refusal; and on a read-only QA item's question after its review refused. The engine writes the sentence that offers it too, where it adds the option (engine.ts `hold`, allowances.ts `rereviewNote`, with the rereviews used of the allowance), so a question names `revalidate` exactly when its answers take it; a step never offers it in its own text. The service routes each Objective to its frozen provider's workflow (providers/selection.ts `providerWorkflow`), which passes on every Work Item answer the engine offers and applies itself (`revalidate`, `fresh`, a repair allowance's `accept`, diagnosis first) to that workflow, and offers none while the configuration isn't the one it froze (#2120). A coding item's work step then finishes with that same result, unchanged, if it still sits on the item's base (else it asks `retry` or cancel), without the worker or collection, and selection, validation, review and delivery run again. Its CI and merge steps judge failed checks on that result as on the operator's `retry` to the CI step (work/facts.ts `rereviewed`, see [A failed check](delivery.md#delivery)): a check the default branch fails too holds with no repair, and once the default branch's runs of the failed checks pass and the delivered head lacks the default branch's head, GitHub brings the PR up to date with it (update-branch, no worker) instead of a repair; and while no check has run on the PR since the answer landed and nothing is left to rerun there, the step asks (`retry`, `repair`, `cancel`) instead of repeating the repair the rereview answered (work/facts.ts `rereviewed` keeps when it landed), unless the default branch passed every failed check after it failed on the PR in the run of `delivery.baseRerun`'s workflow Factory made or waited for, which repairs (see A fresh run on the default branch in [Delivery](delivery.md#delivery)). That is the case of a delivered result refused only by a check whose result depends on when it runs (new advisories against locked dependencies), which the default branch has fixed since. A QA item validates and reviews again on the default-branch commit as it is now. It isn't a repair and counts against no repair allowance: it is charged against `resultRereviews` when the answer lands (see Allowances); past the allowance it holds with `more`, which grants as much again and checks the result. A rerun after a crash does the same. A result the worker kept unchanged on the operator's guidance is checked again the same way, the engine answering `revalidate` for it (see Repair diagnosis).
- **Retire a final validation command.** Final validation's failure offers `retire-command <n> <reason>` for the command n it failed on (its position, from 1, in the sequence that ran), with a required reason. It never retires a command the installation requires (`finalValidation.requiredCommands`), a readiness probe or preparation command, a package bootstrap, or final validation's last check; the question names why instead, and an answer that names one anyway holds with the reason. Only a real check counts as one left: a readiness probe, its preparation or a package bootstrap doesn't. The retirement is recorded like an amendment, against the plan accepted then and keyed by the question's id, so a rerun records it once: the final step keeps it (work/facts.ts `final:retired`), and currentPlan (planning/plan.ts) returns it in the plan's `retired`, where final validation and final review read it. The command no longer runs in final validation, and the same head is validated again. Final review gets a controller row of retired commands, which only no longer run: what they proved is still judged on other evidence. The report and status list each with its reason and the obligations it proved, now judged by review. A reset keeps the retirements of a readable saved state.
