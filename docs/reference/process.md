# Process model

Part of [the design](../DESIGN.md).

## Process model

There is one process, `factory serve`, per installation, run by systemd. It is the only writer of state.

- **Lock.** `serve` binds a Linux abstract socket named for the installation. The kernel releases it when the process dies, so there are no owner records, PID proofs or handoffs. A second `serve` exits at once with "already running".
- **The lock is per network namespace.** A host CLI asks whether the service runs by connecting to that socket, and abstract sockets belong to a network namespace. So the CLI can't see a service inside another one (a container, `pasta`, `unshare --net`): it says "isn't running", and its request file still applies, because files are shared. Run the CLI in the service's namespace to see it.
- **CLI.** Commands that read (`status`, `log`, `watch`, `queue list`, `dream --show`, `dream --preview`, `recipe --file`) read the state files, GitHub, the checkout or the knowledge store read-only, directly. `setup` writes the configuration, never state. Commands that change something (`run`, `answer`, `cancel`, `retry`, `reset`, `pause`, `drain`, `resume`, `queue`, `dream`'s writes and `propose --enqueue`) write one request file to `requests/`; `propose --approve` creates its issue on GitHub itself. A refusal prints `{"kind":"lifecycle-refusal","code":"..."}` on stderr with a stable code, then the message. The service picks it up within a second and deletes it when the request is applied. Its shape is checked where it is read (requests.ts `pendingRequests`): a file that doesn't parse or isn't a request moves to `requests/rejected/` (removed after an hour, like results), is logged (`request-rejected`) and is refused with `invalid_request`; one that can't be read now (EIO, EACCES) waits for the next tick. A request whose apply throws is refused with `request_failed` and the error after that one try, never retried; one whose change was saved stands even if an effect after the save fails. Neither stops the other requests. A `/factory` comment's refusal is kept in the Objective's applied requests when it has a run, so it gets one reply and is never applied again. If the service isn't running, the request waits there and the CLI says so; a `dream` write is refused instead (`service_not_running`), before any model call.
- **Dream.** `factory dream` reads the store and makes its model call in the CLI, so the service's loop never waits on a model; the call's start and end (with its proposal), `--record` (whose records the CLI reads from Git) and an approval or rejection reach the service as requests, which it applies to the store (knowledge/dream.ts applyDream). Each applies again harmlessly after a crash; a refusal is `dream_refused`. Only a call's end skips the `service_not_running` check: it waits in `requests/` for the service, so a finished model call is never lost to a restart. A call still submitted past its 45-minute deadline is marked interrupted when the next call starts; `--show` lists running and interrupted calls.
- **Propose.** `factory propose "INTENT"`, or `factory propose --source DOC#HEADING [--source DOC#HEADING]...`, with `[--file ABSOLUTE_NEW_FILE] [--provider NAME]`, drafts Objectives in the CLI (proposals.ts) with one planner call (phase `propose`) over a read-only export of the default branch: one Objective from an intent, or one per roadmap item of the first `--source` section, read at the default branch (a further `--source` is context), each with a key and the keys of earlier ones it depends on. The model answers with each Objective's fields (title, goal, acceptance, commands, context, sources, constraints, non-goals); a roadmap Objective also pins its section as a Source. Factory writes each body from them, each entry one line through markdown.ts `prose` or `code`, so no field can open a heading, list, HTML or a mention, renders it with GitHub's renderer (`POST /markdown`, a read) and runs the check step's Objective checks on it (planning/steps.ts `objectiveProblems`). A draft with problems is asked again once with them (each named by its key), then refused (`proposal_refused`). A good one is saved as one JSON file under the installation's `proposals/` (or `--file`, outside the checkout) and previewed, redacted; nothing goes to GitHub. `--file DRAFT --approve SHA256` takes the reviewed file's exact bytes and publishes every Objective in it: each body's first line is its marker `<!-- factory:0:proposal:<id>:<key> -->`, and each approval first looks for them among the issues Factory's login opened since the draft was made (its `createdAt`), so a create whose answer was lost is adopted and no state is kept (a found issue with other text is refused); the missing ones are checked again and created in order. Once every issue exists, each dependency becomes a blocked-by link, read before it is added. Crash points `propose:create:before`/`:after` and `propose:link:before`/`:after`, so a partial batch finishes on the next approval. One approval of a draft runs at a time. `--enqueue` then writes `factory run`'s request for each issue (fixed id `propose-<issue>`), so the service queues their cards and the predecessors step orders them by their links.
- **`factory run N [--provider NAME] [--deadline WHEN]`** is a request plus a follower. The service sets the issue's card to the queued option (adding the issue to the Project, or unarchiving its card, when it has none there; queue.ts `queueIssue`) and reads the queue at once, so the normal queue admission admits it: the card's level, the check, a slot. The request file stays until that admission, which takes its provider (frozen with `selectedBy: "--provider"`) and its deadline (an ISO time, or a duration the CLI turns into one: state.ts `deadlineAt`'s `requested`) in place of the defaults; a restart reads it again. An Objective already running answers at once: no second admission. The operator's latest action wins: a dequeue of the card before the admission (a later queue read, or, after a restart, a card moved off queued after the request, to an option other than the one Factory last showed) drops the request (`superseded`), and so does a cancel, which also moves a card still reading queued to Cancelled. A paused or draining queue refuses (`queue_not_running`), as do a closed issue Factory never ran (`issue_closed`), a missing one (`no_such_issue`) a provider the service lacks (`unknown_provider`), a `--deadline` that passed before the admission (`deadline_passed`), an older `run` of the same issue once a newer one waits (`superseded`), and a cancelled Objective whose cleanup hasn't settled (`cleanup_running`: run again once it has, or `factory reset N`). The CLI then follows the new run log events until the Objective ends (exit 0 done, 1 cancelled), needs a person (exit 2: a question is open, its state can't be read, or the service isn't running; it prints the next command), or Ctrl-C, which stops only the following (130). With the service stopped, the request waits in `requests/` and the CLI exits 2. The service does the work, so there is only one code path and no foreground run.
- **Stop.** SIGTERM or SIGINT ends the loop. Every running step is stopped and never saves again, and every observation and sync job is aborted; the run then writes its `run-end`, marks a clean stop and releases the lock. `factory serve` waits at most 20 s for those steps and jobs to end (a step that ignores its abort could otherwise hold the stop until its deadline, two hours for a worker), logs `stop-drain-timeout` if they haven't, and exits: the process's exit ends what still runs.
- **One installation per repository** (holder.ts). The serving installation is recorded in `refs/factory/holder` in the target: an empty-tree commit whose message names the installation (a random id its state directory keeps, `installation-id`, hashed with the machine's id), host and user. Every change is a lease push, git's compare-and-swap. `serve` takes the record before anything reaches GitHub, refuses (exit 78) while it names another installation, and resumes when it names this one. A clean stop deletes it; a crash keeps it. `serve --take-over` replaces another installation's record. Every queue poll checks the record with `ls-remote`, which costs no REST rate limit, and a service whose record changed stops (exit 78). A record it can't check for 10 polls in a row (Git fails while REST works) also stops it, keeping the record, with exit 75, which systemd restarts; the restart waits until it confirms the record. There is no heartbeat or expiry. A take-over assumes the other installation is stopped: the poll is a backstop.
- **Upgrade.** Stop the service, install, start. Restart is the normal recovery path, so an upgrade needs nothing more.
