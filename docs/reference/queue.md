# Queue

Part of [the design](../DESIGN.md).

## Queue

The GitHub Project is the source of truth for what is queued.

- **Queued** means the item's Factory field (`queue.field`, default `Factory`; called Status below) equals the configured "queued" option. **Order** comes from the Project's number field (`queue.orderField`, default `Factory order`), lowest first, then issue number; a card with no order number goes after every numbered one.
- **Read-only, and retried.** Every 30 s the service reads the Project's queued cards, filtered by GitHub (the items `query`, `<field>:"<queued option>"`, closed issues included), plus, from the issue side, the issues it already knows and the most recently updated open issues, since the Project's item list can lag. So a read costs one page per 100 queued cards, not per card ever added; past 1,000 queued cards the rest wait for a later read, and the log says how many. A known issue GitHub no longer has here (deleted, transferred, converted) is dropped from later reads with a log line; an issue read by number that comes back from another repository, or with another number, is gone too. The rest of the read stands. GitHub's error for one entry leaves out that entry alone, logged once while it lasts (`queue-entry-skipped`): a Project item (say, an issue in a repository the login can't read) or one of the recent issues is dropped, and a known issue keeps its last good card and is left alone by intake until a read succeeds for it. `factory queue list` names the cards it left out. Any other failed read keeps the last good view and tries again; after 10 min of failed reads (the login lost the Project, or `queue.projectId` is wrong) `factory status` shows it under "Intake" with the fix (or, when GitHub's rate limit is spent, when it resets: a rate-limited read waits for the reset), and the log says `intake-stopped`, then `intake-resumed` at the next good read. A known issue whose card has errored for 10 min is listed there too ("#N's card unreadable for 12 min: …; card changes aren't seen"). A read failure never fails a run.
- **Status is a display.** The service sets Status as the run moves, from the tick it admits the Objective: Planning, Building, Needs you, Done, Cancelled; while it is checked, and while it waits for its first slot, Factory writes nothing and the operator's Queued stands. After a hold is answered, an Objective that waits for a slot shows its status (Planning or Building). The list of options is Queued (the operator's), Planning, Building, Needs you, Done, Cancelled. Every sync job (a card, a comment, a reply, the queue read) runs in the background on the one keyed job runner (jobs.ts `Jobs`, which the knowledge observations use too), one at a time per job and Objective. A failed one is logged and tried again after a backoff of its own (from 10 s, doubling to 10 min), so one Objective's bad card never spends the rate limit the others need; one past its 10 min deadline is aborted and counts as failed. Factory's changes to one Project (adding a card, unarchiving one, setting an option) take turns within the service, since GitHub refuses concurrent changes to a Project; one GitHub still refuses with a temporary conflict, or "Something went wrong" (another service on the same Project), is tried again after 1 s and 2 s, keeping its turn, and then fails as transient. Different Projects never wait on each other. A run that is replaced or let go of drops its jobs and their backoffs, except a reply already being posted, which still lands. A finished Objective stays in memory, across restarts too, until its final Status and its replies are written. An issue that any sync job finds gone here (404, 410, or a redirect while the repository still answers under its configured name: moved; see Security: No redirects) gets no more card, comment or reply writes, whether or not a queue read still asks for it; a finished one's unsent replies are dropped with a `reply-dropped` log line, and its sync settles.
- **Levels.** Factory never writes the queued option on its own: only `factory run N` sets it (or `propose --enqueue`, through the same request), as the operator's request. So a card that reads queued is always the operator's input. An unfinished Objective that hasn't started planning (it is waiting, in its check, or in a re-run's cleanup) dequeues on a change to any option but queued (cleared, Cancelled, off the Project, or another option set by hand) away from the option Factory last saw on the card or wrote (`seen`, saved in state): from queued, or from what Factory showed for it, such as "Needs you" for a held re-run cleanup. A change from an option Factory wrote counts only if GitHub set it after Factory's write landed (`shownAt`), so a lagging read of an earlier write never dequeues; cleared or off the Project always counts, since Factory never writes those. A finished Objective queues again once all of these hold:
  - its final Status is on the card: Factory wrote it, or stood back from someone else's change, and an operator's re-queue before Factory wrote it counts;
  - its replies are written;
  - a read that began after Factory's last write shows the card queued, with an option time (GitHub's clock) later than the queue that started the run (`queuedAt`).

  So a stale or lagging read of the first queue never runs a finished, cancelled or withdrawn run again. A read that started before Factory's last write is skipped for that card.

- **Never over the operator.** Factory reads the card before each Status write and writes only over what it last saw or wrote itself. Someone else's change is the operator's input: to anything but queued, it dequeues an Objective that hasn't started planning; any other change stands until the Objective's status moves on. Factory saves the option it is about to write, so after a crash a card showing it still reads as Factory's own.
- **Operator controls:** set an item's Factory field to the queued option to queue it (again, for a finished Objective: set it after its final Status shows), move it out of the queued option (or out of what Factory showed for its check or a re-run's cleanup: clear it, set Cancelled, or remove it from the Project) to dequeue it if it hasn't started planning, and set the order number to reorder. Dequeuing before planning starts withdraws the Objective: its state is removed, as if it was never admitted, so queuing it again checks it afresh. It is withdrawn once its live status comment shows it: the comment, if one was posted, is first edited to a final "Withdrawn before planning; queue it again to start afresh." line, and each open question's comment to say it no longer applies (each found by its marker, so a crash before the state goes edits them again). A reset that found nothing to rebuild waits for the same edit before it goes. A dequeue while the check runs, or once a re-run's cleanup has begun, is saved (`withdrawing`): nothing past them starts, Factory writes no Status and asks nothing for it, so the operator's option stands, and the Objective is withdrawn as soon as they end. A re-run's cleanup that hasn't begun never runs (the earlier run's finished record stands), and one that holds or errors is withdrawn at once instead of asking. Order is read on every queue read until the Objective starts. There is no control card and no managed metadata field.
- **Pause the whole queue.** The queue has one mode, saved in the installation root (`queue.json`, state.ts `loadQueueControl`) so it survives restarts: running, paused (no Objective is admitted and no step starts anywhere; running steps and their calls finish, an interrupted step still resumes, and nothing is lost) or draining (nothing new is admitted; admitted Objectives carry on). Two places set it, with the same words:
  - `factory queue pause | drain | resume` on the machine;
  - a comment `/factory queue pause`, `/factory queue drain` or `/factory queue resume` on the issue of any running Objective (one Factory has started and not finished), from the GitHub app on a phone too. It counts only from a user with write access to the repository, checked like every `/factory` comment (see [Security](security.md)), and is read on the queue poll (`queue.pollSeconds`), so it applies within that.

  Both write the same request, so the latest one, from either place, sets the mode: a comment resumes what the CLI paused, and the other way round. A comment's reply on its issue says it applied, and while the queue is paused every running Objective's live status comment says so as its next action, naming who paused it and both ways to resume ([GitHub](github.md#live-status-comment)); `factory status` and `factory queue list` show the mode too. With no Objective running, a comment has nowhere to be read, so `factory queue resume` on the machine resumes the queue.

- **Several at once.** Up to `queue.maxActiveObjectives` Objectives plan or build at once (default 3), in queue order. An Objective builds only when no unfinished Objective ahead of it in the owned-path order owns an overlapping path; planning never waits. The check holds however busy the Objective is: while it waits on another's paths it starts no Work Item step (its running steps finish, and one the service's death interrupted resumes), but an amendment still plans, and a step answered `replan` or `fresh` applies the answer at once; any other answer stands and takes effect when the wait ends. Owned paths are the current plan's, so an accepted amendment's paths count from the next tick. Each path ranks by when the Objective came to own it (service.ts `pathOwners`): its plan's acceptance (`plan:acceptedAt`), or, for a path an accepted amendment added, that amendment's acceptance, kept in the plan as `ownedSince` and posted with it in the plan comment, so a reset keeps it. Of two Objectives whose paths overlap, the one that owned its side of their first overlap first goes first (the earlier issue on a tie), except that one that has started a Work Item never waits on one that hasn't. A plan's acceptance is stamped before its plan comment posts, and the service sees the plan only once it is saved, so a slow post can give a plan that shows up after the other Objective began building the earlier time. So an amendment that adds paths a later Objective already owns waits on that one for them, and that one's started Work Items go on; it can't wait back, because it only built while its paths didn't overlap the earlier plan's. Paths the Objective owned before the amendment keep their place, also inside a path the amendment narrows or widens, so a later amendment never reverses an order that stands. Should three or more Objectives' amendments make waits that close a circle, the waits are taken oldest overlap first and the one that would close it is left out: the Objective it would wait on is waiting already, so no two build overlapping paths at once, and one of the circle builds. The order is worked out afresh every tick, so one gap stays: once a member of the circle stops waiting (it is cancelled, reset, or has every item built), the wait left out is taken again, and the Objective that built because it was left out waits with its started Work Items unmerged on their branches, which go stale until its turn. That holds when the one it waits on has started a Work Item too; when it hasn't, that one waits instead. An Objective owns its paths until it is done or cancelled: through final validation, final review and the report, not just until its last Work Item merges, and through a reset of a readable state: while it stands, its old plan's paths, and once rebuilt, the rebuilt plan's under its own acceptance until planning lands it or drops it (reset.ts `ownedPlan`; a dropped plan's replacement is accepted anew). An unreadable state owns nothing until its reset rebuilds a plan, so an Objective accepted meanwhile may have started on those paths: the rebuilt plan owns every path from the rebuild (`ownedSince`), so it waits on that one instead. A step a wait on paths stopped doesn't count the wait against its retry clock, as with an open question ([Steps](steps.md)). An Objective whose open holds stop every step it could start, one whose every remaining step waits on a human gate or a hold, and one waiting on another's paths with only building left take no slot; a gated or holding Objective still owns its paths. Host-wide caps limit, across every Objective (capacity.ts, engine.ts HostLimiter):
  - worker runs (`execution.workers`, default half the CPUs);
  - validations (`execution.validations`, a quarter of the CPUs);
  - planner calls, meaning planning rounds and reviews (`execution.planners`, two per worker);
  - checks and re-run cleanups (`queue.maxActiveObjectives` at once).

  Each running step also reserves memory, and a step starts only when its slot and its reservation both fit within `execution.memoryMiB` (default: the host's memory less 4 GiB). Default reservations, in `execution.reservations`: a worker 1536 MiB and a validation 3584 MiB. A planner call reserves nothing by default. Steps at once are bounded by `queue.maxActiveObjectives` × `execution.concurrency` (24 by default), so at most 6 planner calls (about 3.3 GiB) run beside 12 workers and 6 validations, within the spare memory. A planner reservation the operator sets takes only memory that no free worker or validation slot needs, so memory never holds workers and validations below their caps. They come from measurements on a 24-thread, 46 GiB host against a TypeScript monorepo:
  - a full test suite peaked at 6.8 GiB on about 3 cores;
  - a package's tests used 0.5 to 1.5 GiB;
  - an agent process used 0.4 to 0.7 GiB.

  At the defaults, every worker and validation fits at once, and memory makes the next step wait instead of letting the kernel kill one. `status --capacity` shows the slots and memory in use, and how the configured capacity fits the host. Setup reports the same recommendation, and neither changes it. Every fetch in the shared checkout runs one at a time: a caller joins the fetch that starts after the running one, shared by everyone who asked meanwhile, because concurrent fetches fail against each other when the default branch moves.

- **Again.** Queuing a finished Objective again stops its old run (its steps, saves and GitHub jobs) once its cleanup is done, and starts a new one. The new run first reopens the issue if it is closed (the earlier run closed it, or the Project's "Auto-close issue" workflow closed it again); if GitHub refuses, it holds with `retry` and `cancel`. Just before that reopen, and only then, Factory touches the Project's built-in single-select "Status" field (not its own queue field): if the card's Status reads "Done", Factory moves it to "In Progress", else "Todo", else the first option not named "Done", because that workflow closes an issue whose Status reads Done. The check that follows reads the issue again: if something closed it again anyway, it holds with a question naming who closed it, with `retry` and `cancel`, and never plans on a closed issue. A closed issue that never ran isn't queued. The new run then closes the old run's open PRs and removes its worktrees, as `replan` does after a plan was accepted. Factory resets a Work Item branch only when it made every commit the branch has beyond the default branch: each is committed as Factory (Factory commits with a clean Git environment as `factory@users.noreply.github.com`; an amend, rebase or cherry-pick by anyone else changes the committer), or is GitHub's update-branch merge from the default branch or the item's base (a stack layer's predecessor branch). Otherwise it holds with `retry` (after moving the commits off), `reset` (replace the branch anyway) and `cancel`.
- **No approval step.** A clean, reviewed plan runs straight away. Factory asks only when review finds a decision for the operator.

## Check at queue time

When the service first sees a queued Objective, it waits for its predecessors (see [Predecessors](#predecessors)), then runs the Objective checks at once (first, that every `autonomy.requiredEnvironment` variable is set: see [Allowances](state.md#allowances)), whether or not a slot is free, within the host-wide `github` cap (`queue.maxActiveObjectives` checks and re-run cleanups at once, in queue order): template sections, pinned Sources that resolve at the default branch, no duplicate headings, declarations that parse, and the final commands' programs on the host: each is on the PATH, a pinned npm or pnpm is that exact version, and, for a command that runs node, npm, npx or pnpm, the host's node satisfies the Node pin at the default branch (see [Setup](setup.md)). Planning uses the same function. A checked Objective then waits for a slot.

A failed check is a hold. It names each problem and how to fix it, and Status goes to "Needs you". Edit the issue and answer `recheck` to check it again.

## Predecessors

An Objective issue can be blocked by other Objective issues through GitHub's native blocked-by links. The `predecessors` step (planning/predecessors.ts) runs before the check, so the check and planning read a default branch that has the predecessors' work (a Source a predecessor adds resolves). Each run reads the links again:

- **Wait.** While a blocker is open, or closed as completed while its Objective isn't done here, the Objective waits with no question. It is a gate wait (see [Waits](steps.md#waits)): no deadline, no slot (like the check, it runs slot or not, within the `github` cap), status shows "Waiting on predecessor #N (why)", and one reminder follows after 24 h. A dequeue while it waits withdraws it, as before the check.
- **Ended.** A blocker closed as not planned or duplicate, one whose Objective was cancelled, one closed that Factory never ran here, one in another repository, and one whose issue (title or body) was edited after Factory accepted it hold the Objective with `replan` (read the links again, after editing them), `ignore N <reason>` (go on without that predecessor; `owner/repo#N` names another repository's issue, and an ignore matches only that repository's issue; the reason is kept with the answer's author and time) and `cancel`.
- **Cycle.** A cycle of open blocked-by links through the Objective holds, naming it, with `retry` (after removing a link), `ignore N <reason>` and `cancel`.
- **Evidence.** Once every predecessor is done or ignored, each done one's accepted result (its title as accepted, the commit final validation and review passed on, its tree, its final commands, and each Work Item's PR and merge commit) is saved as the step's result. The check (and a replan's re-read) checks it against Git: the commit must exist with that tree, and it and every merge must be on the base planning reads; otherwise it holds with `retry` and `cancel`. Planning, plan review and amendments get it as the native prerequisites.

A replan after acceptance runs the step again.
