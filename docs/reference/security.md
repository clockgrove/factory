# Security

Part of [the design](../DESIGN.md).

## Security

These always hold:

- Credentials stay with the service. Workers never see them.
- Workers run in the OS sandbox with the configured network policy. The one exception is an explicit operator opt-out, `sandbox.required: false`, written by hand: on a host without bubblewrap, validation commands (a Work Item's validate step, final validation, QA and a Claude, Copilot or Codex worker's Validate) then run unsandboxed, with the operator's file access, and the readiness check reports it as a warning (sandbox mode `unsandboxed`). Where bubblewrap is installed but can't start, commands are still refused. The same setting lets Factory run as root, except a Claude worker's own `run_command`, which never runs without the sandbox or as root.
- Secrets are named by reference. The configuration derives the secret values once: those named in `policy.allowedSecretNames`, from the environment; and, from the environment or a service credential, each managed provider's credential (`apiKeyEnv`, `credentialEnv`) and, with Copilot configured, its tokens, keys and `COPILOT_PROVIDER_BASE_URL`. Everything Factory writes to GitHub, its run log and captures, Dream input and the Codex worker's reported commands and errors are redacted of them, of GitHub and `sk-` tokens, of JWT-shaped tokens, of bearer and basic headers and of PEM private keys. Only the named ones reach a worker's environment.
- Factory acts on GitHub as its own GitHub App, registered and installed as setup's required preflight step: its installation tokens last an hour and carry only the permissions Factory needs, where the GitHub CLI's login, the recorded opt-out (`github.login`), carries the operator's long-lived and broader token. Readiness blocks a configuration that names neither, and the service refuses to start on it (see [GitHub identity](setup.md#github-identity)).
- The App's private key is a service credential (`FACTORY_GITHUB_APP_KEY`), never in the configuration, and its installation tokens and JWTs stay in the service: a remote Git call gets the token in its own environment only. Recording the opt-out removes setup's copy of the key.
- `sandbox.environment` is not for secrets: its values are not redacted, and names that look like secrets (`TOKEN`, `SECRET`, `PASSWORD`, `CREDENTIAL`, `KEY`) are refused at load. A secret a command needs goes in `policy.allowedSecretNames`.
- Deploys stay in the target's own GitHub Actions, behind environment approvals.

In detail:

- **Issue bodies.** Factory reads an Objective from GitHub's rendering of the issue (`body_html`, read with the body, full+json), never from its Markdown; nothing GitHub doesn't show reaches a model or a check. shown.ts parses it once with a real HTML parser (hast-util-from-html) and gives two views of the shown tree. **Structure** (`blocks`) comes from the elements: sections are GitHub's headings (`h1`–`h6`, text content, a `<br>` read as a space), bullets are its `li` elements, Goal and other prose are paragraph text, and backticked commands, paths and pins are `code` elements. Every check reads it: Goal, Acceptance (criteria only: Factory reads no command from an Objective), Sources, and the Package manager update, Quality checkpoint and Workspace package additions declarations (objective.ts checkObjective, validate.ts declarationProblems). Shown text is text with its emphasis markers: strong is written `__text__`, emphasis `_text_` and struck text `~~text~~`, so an unbackticked path reads as written (`src/_internal.ts`, `pkg/__init__.py`, `src/__tests__/a.ts`, `docs/A&B.md`; a `**` or `*` in a path comes back as `__` or `_`, so backtick it), a heading anchor keeps its markers (Sources heading matching treats `*` and `_` as one marker, so `#Step *y*` finds `Step *y*` or `Step _y_`), and a struck criterion stays visibly struck. A writer's inline math is text (`$…$`), never code. A paragraph line that reads ``- `cmd` `` is never a bullet. A blank issue-form field (`<p><em>No response</em></p>`) is an empty entry. **The planner text** (`body`) is the same tree as GFM Markdown (hast-util-to-mdast, mdast-util-to-markdown, default escapes): prose for a model, never parsed. Both keep text, headings, lists and task lists, tables, code blocks and links as their text plus href; an image or video is `[image: <file name>]`, a diagram other than mermaid `[<type> diagram]`. An approver sees only a diagram's drawing, so mermaid and math sources stay as code only when the author can write; a non-writer's mermaid diagram is `[mermaid diagram]`and each math block`[math]`. Every other attribute (alt, title, data-*), every comment, invisible characters and whatever GitHub's sanitizer removed are gone. Footnotes stay as GitHub's rendered section. A non-empty body without `body_html` is a transient error and retries; the raw body never stands in. Edit detection (planning and build) and the author approval compare one digest of the structure and the planner text (shownDigest), stable between reads. When the issue's author has no write access, the check holds once: approve or cancel; the question names the digest and says diagram and math sources aren't planner input. The approval is kept against that digest, so any later edit asks again. Until then nothing in the body counts. Queue consent stays the Project field.
- **Write access** (`/factory` answers, issue authors) is asked of GitHub again after 10 minutes.
- **No redirects.** The GitHub client never follows a redirect (`redirect: "manual"`). GitHub redirects an issue transferred to another repository, and a renamed repository; following would act outside the configured repository (a PATCH keeps its method and body on a 301). A redirect is an answer, and a 301 under the repository is first told apart from a moved repository by its identity: `GET /repos/{owner}/{repo}`, never redirected, read at service start and on every such 301; a 301 there, or a GraphQL `repository { nameWithOwner }` (the queue, the re-run's Status move) that differs from the configuration, means the repository was renamed or transferred. Then no issue is gone: the client refuses every request, the service runs no step and no sync job (no card, comment, reply, close, push or merge) and settles nothing, steps keep their state, `status` shows "repository <old> is now <new>; update the configuration's repository and restart", and the run log says so once; after that fix and a restart, everything resumes. While the repository still answers under its configured name, an issue redirected away is gone: cancel cleanup and the sync count it as gone, and any other step holds with `cancel` (recommended) and `retry`, naming the move. Reads that resolve an issue by number over GraphQL check its repository and number. An Actions job log, which GitHub serves from a signed storage link, is read from that link without Factory's login and with no further redirect.
- **GitHub attachments** are fetched with the service's token sent only on the first request, to the attachment URL itself, and only for a `user-attachments` URL or one under the configured repository (`github.com/<repository>/assets/…`), read from the parsed URL's path. The plan check takes an attachment URL only in its normalized form. Another repository's attachment URL holds with `replan` and `cancel` before the token is read. That first request goes to github.com over https, so where it redirects is GitHub's choice (its storage, which it may move); every redirect must be https, and one that isn't is refused, as are more than 5. The size bound and the digest apply wherever the bytes come from.
- **Local source assets** come only from directories listed in `media.localAssetRoots` (empty by default: off), by real path, and never from anything the sandbox seals: HOME as a whole, logins, Factory's config and state, runtime sockets or shared temporary directories. The plan check and the copy both check.
- **Pushed content.** Before publish pushes, every blob the result adds or changes, and every LFS object it uploads, is searched for the secret values, as written and base64: each whole value of 8 or more characters, and the pieces of a multi-line secret that are key material (16 or more characters, high entropy, never PEM armor or lowercase JSON keys and URLs). Redaction still hides values from 4 characters. A match pushes nothing and holds with `repair`, `publish` and `cancel`. `publish` lets exactly that finding on that commit through: its digest is kept when the hold is raised and the answer is checked against that, never against the question's text, which quotes worker-chosen paths.
- **Model text on GitHub.** A PR title, a PR body's goal, a collected commit's subject and a tracking issue's title and lines are model-written. In each, every closing keyword, every `#N`, `GH-N` and `owner/repo#N` reference, every issue or pull request URL (bare, `www.`, autolinked or a link's target) and every @mention gets a zero-width joiner (markdown.ts `inert`), so none links, closes an issue or notifies anyone; Markdown also goes through `prose`. Factory's own `Closes #<item issue>` is the PR's only closing reference.
- **Protected paths.** Collection refuses a worker's change to anything under `.github/`, to a CODEOWNERS file anywhere, to another CI system's configuration (`.circleci/`, `.buildkite/`, `.woodpecker/`, `.gitea/workflows/`, `.forgejo/workflows/`, `.gitlab-ci.yml`/`.yaml`, `.woodpecker.yml`/`.yaml`, `.travis.yml`, `.drone.yml`, `appveyor.yml`, `.appveyor.yml`, `azure-pipelines.yml`/`.yaml`, `bitbucket-pipelines.yml`, `Jenkinsfile`), or to the curated playbook (`planning.playbook`, `.factory/playbook.md` by default), which planning reads from the target, unless the accepted Objective's **May change** section lists that exact path: each entry a bullet that is exactly one backticked path (objective.ts `mayChange`; any other entry is a check problem). A path named anywhere else in the Objective, or owned by the item, allows nothing. The refusal goes back to the worker as a repair finding. Scripts and files that CI runs but that live elsewhere (a `scripts/ci.sh`, a `Makefile`, package scripts) are not protected. The approved Dream playbook lives in the knowledge store, in Factory's state, which the sandbox seals from workers.
- **Workflow pushes.** Factory pushes as its GitHub App with its installation token, or, with the opt-out or an SSH origin, with the operator's Git credential, which it can't inspect. If that credential may push workflow files (a `gh` login has the `workflow` scope by default, and the App has Workflows: write, so a branch that merged the base can carry its workflow files), only the protected-path check stops a worker's workflow change. Where Objectives never change workflows, give the service a credential without workflow access.
- **Runs on the default branch.** Factory reruns failed Actions jobs only on its own PRs' heads, and runs nothing on the default branch, where a run can start what follows it (a release, a deployment), except the one workflow the operator names in `delivery.baseRerun`, declaring it free of side effects. It dispatches only that file, by name, with no inputs, only for a failed check whose stale pass on the default branch was that workflow's own run, at most once a day per default-branch head for a Work Item, at most once for a native stack's layers judged together, and never while a run of it is in progress there, as any of its jobs GitHub shows (see [Delivery](delivery.md#delivery)). The setting is the operator's alone (no Objective, plan or worker sets it) and is frozen with each Objective. Factory can't tell from a workflow file what its steps do, so the declaration is the operator's; readiness warns of another workflow that runs after it (`on: workflow_run`), or after such a follower, which each dispatch starts too, unless every job of that workflow is certainly skipped for a dispatched run (see [Setup](setup.md)).
- **Worker network.** `sandbox.network` is `off` by default: sandboxed commands have their own network namespace with only loopback, and `package-install` gives the verified dependency install outbound network in a namespace of its own, through pasta. Factory's own lockfile resolution for a dependency change ([Steps](steps.md)) gets the same grant, as Factory's command, never a worker's: only when the install's would hold, and only when every `package.json` the candidate changed that it reads (with pnpm, the root's and the workspace members'; with npm, which reads the manifest of every directory a `file:` dependency links, every one) names its dependencies and overrides from the registry, and so does every `overrides`, `catalog` and `catalogs` entry of a `pnpm-workspace.yaml` the candidate changed, since it has no lockfile to verify and fetches what the manifests name. When that resolution reports a version it found no match for, Factory's metadata lookup (`pnpm view`/`npm view <name> versions time --json`) runs with exactly the resolution's grant, in the same checkout under the base's package configuration, and only for a name the resolution already sent and the candidate declares, so it widens nothing; what it returns reaches the worker only as reprinted release versions, digits and dots (`major.minor.patch`, never a prerelease's free-text tag), at most 10 ([Steps](steps.md)). Those dependency keys and the Objective's declared package membership are all a candidate may change in `pnpm-workspace.yaml`; its other settings (registries, minimum release age, trust policy, build approvals, hooks, patches) must keep the base's values for the install's grant, and validation's pins refuse a change to them. The repository's formatter (`validation.formatCommand`, [Steps](steps.md)) never has the network, under `host` too; what it changes is committed only for files the result changed inside the item's owned paths. `host` (opt-in, for validation that needs a service on the host such as a database or a browser) runs every sandboxed command, a Work Item's validation, final validation, QA, the dependency install and a Claude worker's `run_command`, in the host's network namespace. Those commands, which run code the worker wrote, then reach every service listening on the host's loopback (databases, dev servers, local admin interfaces, the Docker API if it listens on TCP), the local network, cloud metadata endpoints and the internet, so they can send out the checkout and any secret in `policy.allowedSecretNames`. They also reach abstract Unix sockets, which belong to the network namespace (some X11 and D-Bus sockets, and Factory's own lock socket); socket files stay sealed, since the filesystem sandbox is unchanged. The planner sees the Claude worker's network as `host`. A Codex worker's own shell follows its provider's `worker.network` (`--codex-network`), not this setting.
- **Checkout Git configuration.** Sandboxed commands can read the checkout's shared Git configuration and, with `extensions.worktreeConfig` on, their Work Item worktree's own `config.worktree` (the sandbox mounts that worktree's admin directory). Readiness (git.ts `checkoutCredentialEntries`) reads, with their includes: the checkout's local configuration and, when `extensions.worktreeConfig` is on, its `config.worktree`; for every linked worktree `<common>/worktrees/<id>/`, the shared configuration again and, with the extension on, its `config.worktree`, each through that worktree's own Git directory, so an `includeIf` `gitdir:` or `onbranch:` condition is met or not as it is for that worktree's Git, never by running Git in a worker's tree; and, on its own, every file an include in the shared configuration or a `config.worktree` reaches, at any depth (an include inside an included file too) and whatever its condition, since a Work Item started later may meet it. It blocks the checkout when any of them holds `http.*.extraheader` (as CI checkouts write), a `credential.*helper` that runs inline shell (`!…`), a `credential.*username` or `password`, a remote URL with a password or an http(s) user part, or a `url.*` rewrite whose base has one. Each entry is named with the file it is actually in (an included file by its own path), any credential in the name's URL (everything up to the last `@` of its authority) shown as `***`, and the fix is to remove it with `git config --file <file> --unset-all <name>`, or remove the include that reaches the file, and keep credentials in the user's global configuration. A worktree removed while readiness reads is skipped. When Git can't read one of them, readiness warns that it can't tell, naming that file and the Git command that shows why.
- **Workers.** A Claude worker never loads project or local settings (their hooks would run on the host). A Codex worker's shell gets proxy URLs without credentials (a URL without a scheme is read as http://, and one that doesn't parse is left out), or none when it has no network. OPENAI_API_KEY and CODEX_API_KEY never reach a Codex worker's shell. A Codex worker has the shell, unified exec and view_image, and no web search, apps, plugins, hooks, memories, browser or computer use, image generation, skill search or instructions, tool suggestions or sleep. When the item has validation commands and no gitlink, it also has Factory's Validate, the one MCP server its private configuration registers: Codex starts it itself, outside the shell's sandbox, as a Node relay to a Unix socket Factory listens on in a private (0700) directory under the host's temporary directory, which the shell is never granted, so the worker's commands can't reach it. The tool takes no arguments and runs only the item's declared commands, as the Claude and Copilot workers' does (providers/codex-validate.ts). Readiness runs a command in a Codex worker's sandbox with no model call: it must write its worktree, be refused writes outside it, fail to read a sealed file outside its grants and, with the network off, fail to connect to a listener on the host's loopback. The probe's whole process group is killed after 30 seconds. A Codex worker, and a Codex planning or review call, runs codex as the init of its own PID namespace (`unshare --user --map-current-user --pid --fork --kill-child --mount-proc`, under `setsid`; sandbox.ts `namespacedLauncher`). Codex starts each command in a process group of its own, so killing codex's group would miss them; ending the namespace kills every process in it, so an abort, a timeout or the end of a turn leaves no command editing the reused worktree. Readiness tries the launch for every role that uses Codex, and a launch the host refuses holds, naming unprivileged user namespaces. The launcher itself tries the namespace before codex and exits 125 when the host refuses it, which holds the same way. A managed worker's archive is read without following links, and its download is streamed to disk and refused past 200 MiB.
- **Interrupted Git.** Factory's Git leads a process group of its own. A Git that times out or is aborted gets SIGTERM for its whole group, so it and its children remove their lock files, and SIGKILL after 2 s; the call ends only once the group is gone. A remote Git never starts gc or maintenance in the background. A lock a killed Git left anyway is removed before a worktree is reused and before a ref change in the checkout (worktree.ts `clearStaleLocks`), once it is older than 10 min, longer than any Factory Git that takes a lock runs, and checked again just before it goes: `packed-refs.lock`, `shallow.lock`, `config.lock`, reftable's `tables.list.lock` and `refs/**/*.lock` in the common directory, the checkout's and the worktree's `index.lock` and `HEAD.lock`, and the `locked` marker an interrupted `worktree add` leaves. Each removal, and each younger lock kept, is logged once (`git-lock-removed`, `git-lock-kept`). The paths come from the checkout's own Git directory, never from a worktree's `.git` file.
- **Origin binding.** Every remote Git call (fetch, push, ls-remote, `remote set-head`, LFS transfer) first passes one origin check (git.ts `originBound`; `remoteGit` wraps it, and delivery and media call it before their call's `try`), which checks that origin's fetch and push URLs, after insteadOf, name the configured repository and that LFS uses origin's default route. A changed origin fetches and pushes nothing: the step holds for the whole Objective with the fix.
- **mise pins.** A mise configuration can run code: templates, `[env]` sources and hooks run when mise loads a configuration the operator trusted. So Factory reads the pins only at setup, only from the configured checkout, whose working tree Factory never changes (workers write linked worktrees, never the checkout), and only through `mise ls --current --json` and `mise bin-paths`, which install nothing and run no hook. It runs them with `MISE_YES=0`, because `MISE_YES=1` or the `yes` setting would make mise trust an untrusted configuration on its own and run its templates. It never runs `mise trust` or `mise install`: trusting a configuration and installing what it pins are the operator's choices, which readiness names. mise trusts a path, not its contents: a trusted configuration that changed runs at the next setup without asking, a change a merged PR brought to the default branch included, so review a change to the checkout's mise configuration before bringing the checkout up to date. It never runs mise in a worktree, and the service never asks mise again: the unit's PATH holds plain bin directories, which the sandbox mounts read-only like any PATH directory. A shims directory on that PATH would let a worktree's configuration pick a version, so readiness warns of one.
- **Not on itself.** Factory refuses its own repository, by name or by a checkout in a Factory clone, checked at the checkout and at its Git top level (read from Factory's own package.json): the configuration doesn't load, so setup and the service refuse, and the check at admission holds.
- **Factory's branches.** A web-flow merge counts as Factory's only when its first parent is Factory's head, its second is on the PR's base, and its tree is what `git merge-tree` makes of the two.

## Trust boundaries

- A same-user process is trusted: it can already change Factory's code and credentials.
- Anyone who can edit the queue's Project can queue work. Give Project access the same care as repository write.
