# State

Part of [the design](../DESIGN.md).

## State

Each Objective has one JSON file: `objectives/<issue>.json` under the installation's state directory. Once a finished Objective's cleanup and final sync are done and no observation of it is in flight, the file moves to `objectives/finished/<issue>.json`. Startup never reads the finished states (rule 6); it reads only `finished/*.observe.json`, the settled observations that haven't landed (see Capabilities). A request, a re-queue or `status` reads a file there when it names the Objective, and a later save writes the active file again until it moves back.

```jsonc
{
  "version": 9,
  "issue": 123,
  "status": "checking | planning | building | finishing | holding | resetting | done | cancelled",
  "frozen": { "provider", "selectedBy", "digest", "config": {/* see Frozen configuration */} },
  "done": { "<step key>": "<its result>" }, // finished steps; the check's result holds the base, `plan` the accepted plan
  "kept": { "<fact key>": "<value>" }, // facts that outlive repairs, such as item:<id>:base and item:<id>:pushed
  "attempts": { "<step key>": { "startedAt", "run", "interrupted"? } }, // started, not finished; `run` is the service run; `interrupted`: deaths it ran at in a row (crash loop)
  "retries": { "<step key>": { "count", "attempts", "since", "nextAt", "lastError", "cause", "wait"?, "grantedUntil"? } },
  "repairs": { "<target step>": { "count", "findings": [...], "from"? } }, // the latest repaired last; from: the step whose failure sent it
  "answers": { "<step key>": { "holdId", "question", "answer", "text"?, "by", "at" } },
  "holds": [], // open questions, oldest first: { "id", "step", "item"?, "question", "options": [...], "cause", "askedAt", "shownAt"?, "shortForm"? }
  "lastShownAt": "<latest GitHub time any question's comment was shown>",
  "appliedRequests": [/* the latest applied requests, so none applies twice */],
  "control": { "mode": "paused | draining", "by", "at" }, // optional: the operator's pause or drain
  "withdrawing": true, // optional: dequeued while its check or a re-run's cleanup ran
  "modules": { "github": {/* the card and the comment cursor */} },
  "startedAt": "<admission time: with the issue, it names the run>",
  "deadline": "<optional: the absolute deadline, saved at admission; only a reset with no readable state sets it again>",
  "finishedRun": "<the service run that last finished a step>",
  "updatedAt": "<time>",
  "ended": { "at": "<first save at a terminal status>", "by": "<who cancelled; `deadline` at the deadline>", "source"?: "github" },
}
```

- **A step store.** The state records steps, not Work Items. A Work Item's progress is its step keys, `item:<id>:<phase>`, in `done`, `attempts` and `retries`. What it keeps across repairs (its base, pushed heads, the refused result) is the kept facts `item:<id>:<name>`. The plan in force is read only through planning/plan.ts `currentPlan`: the newest accepted amendment's plan, else `done.plan`. Its acceptance time, `kept["plan:acceptedAt"]`, names the plan (proposals, criterion decisions and retirements count only under it) and orders owned-path waits ([Queue](queue.md)); an amendment keeps it. The paths an amendment adds are owned from its acceptance instead: the plan it saves (and posts) records each one's time in `ownedSince`, so an Objective whose plan was accepted earlier waits on a later one that already owns them.
- **Saved after every step**, by writing a temporary file, calling `fsync`, then renaming it. A crash leaves either the old file or the new one.
- **Trusted.** The state belongs to the installation's user, as do Factory's code and credentials. There are no digests, seals, witnesses or tamper checks.
- **Small.** Large bodies (prompts, worker transcripts, review packets) go in the run log directory, never in state.
- **Rebuildable.** `factory reset N` rebuilds the state from what Factory left on GitHub: the plan comment (and its `plan-data` continuations), the PRs whose head is a Work Item branch, the live status comment's record and the report. It's how a corrupt file, an incompatible version or a new machine is recovered: it needs no local state. `factory queue list` (commands/queue.ts) lists a card that shows Planning, Building or Needs you with no state here as inert, naming `factory reset N`: only a run writes those options, so its state is on another machine or lost, and intake, `status` and `/factory` comments see only Objectives with state. The service saves a resetting record at once (status `resetting`; the old state kept inside it), and one step, `rebuild`, reads GitHub and replaces the record with the rebuilt state, so its deadline, retries and questions are the engine's and cancel (either form) replaces it at once. The old run's steps are stopped, and the rebuild starts only once they have ended (each by its deadline at the latest), so an effect already in flight (a merge) can't land after the rebuild read GitHub. A reset that replaces a run still waiting this way waits for the same steps, and a dequeue meanwhile withdraws only once they have ended; a cancel meanwhile doesn't wait.
  - **Bound by identity, never by a time.** Only comments and PRs by Factory's own login count (a GitHub App's is `<slug>[bot]`). The run is the old state's when it is readable, else the newest run Factory's comments name, in their order on the issue (the live status comment `status:<run>`, the report `report:<run>`, the cancel comment `cancelled:<run>`), or the plan comment's when it names a later run none of them does; the resetting record's own run is never one, and while a reset stands the record writes no status comment. The plan comment's line after its marker names the run, the accepted plan and the SHA-256 of its plan data's JSON (`factory-run:<run>`, `factory-plan:<accepted>`, `factory-data:<sha256>`, markdown.ts `planMarks`; an amendment keeps its plan's acceptance), and every PR body ends with the run and plan (`runMarks`); a PR reused after a replan gets the new marks when its item publishes. The plan counts only when it names that run (and a readable old state had accepted a plan or kept a rebuilt one); its data only from Factory's own data block at the end of the plan comment, or the continuations it names. Data that isn't shaped as a plan refuses with `plan_unreadable`; data that doesn't match its digest is taken as edited, as if there were no plan, so the run plans afresh, and the answer says so. A PR counts only when it names that run and plan (the newest wins); a merged PR whose merge commit GitHub doesn't show yet is read again, never taken as unmerged. The report or cancel comment counts only for that run. A card's time, which Factory moves itself, never decides.
  - **Never trusted as it is.** Anyone who can write to the repository can edit Factory's comments: a digest catches a casual edit, and everything read back is checked as a fresh answer would be. A reported Objective comes back done, one with its cancel comment comes back cancelled (its cleanup had settled), and a closed, unreported one comes back cancelled (its cleanup runs again); each shows its plan and merges, and no work runs, and a card set to the queued option queues it again. A run that ended while its card shows Planning, Building or Needs you (an option Factory writes only while a run goes on) asks: a later run may have started and written nothing yet, as with progress comments off. `ended` rebuilds it as the run ended; `retry` reads again (set the card to queued first to run it again); or cancel. Any other run with a plan of its own checks the Objective again, then runs the plan through the plan checks (`checkPlan`) against the Objective as GitHub shows it now (round `plan:1:1`, with the plan's own planning decisions) and through plan review, like any draft. Only when planning accepts that round as it is does the plan stand again, under its own acceptance and on its own base: merged items stay merged, every other item starts fresh on the current start, and an open PR is reused when its item publishes again. Once planning goes past that round, the rebuilt plan is dropped: a new plan, and nothing of the old one carries over but what is on the default branch. The operator's criterion decisions (`accept <n>`, `refuse <n>`) and final command retirements (`retire-command <n>`) come back from the status record when it matches its digest (and from a readable old state). A decision counts only for a Work Item of the plan and a criterion its review judges, or for final review and a criterion of the plan's coverage, and still only on its own tree; retirements are replayed oldest first and each only when final validation would take it now (work/retire.ts `commandRefusal`). Anything dropped is named in the answer and asked again when it comes up. A run with no plan of its own plans afresh. When the old state was readable, the Objective keeps its place in the owned-path order throughout: it owns the old state's paths while the reset stands, then the rebuilt plan's under its own acceptance, each path keeping the time the old state owned it from (`ownedSince`, also a rebuilt plan's the old state kept), until planning lands it or drops it. An unreadable state owns no paths until the rebuilt plan comes back, so an Objective accepted later may have started building them: the rebuilt plan owns every path from the rebuild (`ownedSince`), so it waits on that one rather than stopping it.
  - **What starts again.** Repair, error and planning-round counts start again, the Objective deadline is kept only from a readable old state and otherwise starts again from `queue.objectiveDeadlineSeconds` (a `run --deadline` time is not kept), and worker results and sessions that are not on GitHub are made again. Open questions are asked again by the steps that asked them, if they still apply; comments from before the rebuild never act again. With progress comments off there is no status record, and an edited record is taken as none, so criterion decisions and retirements are asked for again; so are the entries a long record left out (`dropped`).
  - The operator's pause or drain, a provider switch, the card and the comment cursor carry over. A reset with no state, no run on GitHub and no queued card is refused (`no_factory_state`), and one that would create an Objective follows the queue's mode (`queue_not_running`). A refused reset restores the old state; the request is answered when the rebuild lands, with what it found.
- **One version.** If the file's version isn't the current one, it doesn't parse, or its shape isn't a state's (state.ts `stateProblem`: another issue, an unknown status, a missing or mistyped top-level field, a question without its id, step, text or answers, or an accepted plan or amendment's plan without the items, coverage and final commands the service reads on every tick), the Objective holds with the answers `reset` and `cancel`; it never stops the service. The hold is posted on the issue and shown as "Needs you" like any other, and `/factory reset` or `/factory cancel` answers it. The question belongs to one incident: its marker names the unreadable file's digest, and only comments created after that question count, so an earlier incident's question and its `/factory cancel` never act on a later one. Nothing overwrites the file except that answer. There are no migrations: the state is version 9, every other version is unreadable, and `reset` rebuilds it. A read that fails for a moment (EMFILE, EIO) is tried again every tick, never taken as unreadable.
- **Set aside at run time.** A state that loads but whose work throws in the service's tick (its deadline, scheduling, steps, sync, observation or retirement) affects only that Objective: the first throw of a streak is logged as `objective-error`, the Objective sits out the rest of each tick, and the others go on. After 10 ticks in a row of throws it is set aside (`objective-set-aside`). A system call's error (a save or read failing with ENOSPC, EMFILE, EIO) may pass by itself, since the failed save left memory as on disk and the next tick tries again, so ticks failed only by one count toward 100 in a row instead. Set aside, its steps stop, and it holds as unreadable with `retry` (recommended: the cause is usually a code bug, and `retry` after the fix keeps its local progress), `reset` and `cancel`, its incident named by the digest of its state, and `factory status` shows it so while the service runs (`service.json` `setAside`). `retry` reads its file again and runs on, with the card and comment cursor its question moved on; a reset or cancel rebuilds or replaces it. Each waits for the stopped steps. A restart reads the file again too.

### Frozen configuration

An Objective runs on the configuration it was admitted with. `frozen` holds its provider (and what chose it: `defaultProvider`, `--provider` or `switch`), the effective configuration and that configuration's SHA-256 `digest`. The configuration is frozen whole, with every adapter default filled in (selection.ts `resolvedProvider`, which the planner and worker are built from too), less an explicit list of operational keys (providers/selection.ts `OPERATIONAL`), never an allow-list, so a key added later is frozen too. The Objective's own provider's settings stand in for `providers` and `defaultProvider`, which only choose a new Objective's provider.

- **Operational keys** may change under a running Objective: they operate the host or present the run, never decide the work. They are the derived secret values (never written to state), `queue` (polling, slots, the Project fields), `execution.concurrency`, `execution.workers`, `execution.validations`, `execution.planners`, `execution.memoryMiB`, `execution.reservations`, `sandbox.limits`, `sandbox.packageStore`, `reviewArtifacts`, `validation.commandTimeoutSeconds`, `github` (who Factory acts as), `operators`, and a worker's `timeoutSeconds`, `idleSeconds` and `settings.maxTurns`.
- **A change holds once.** The service reads its configuration at start. When it differs from an Objective's frozen configuration in any other key, the Objective holds, and the question names the changed keys and both digests. `adopt` freezes the configuration as it is now and continues; `switch NAME` freezes it on another configured provider; `cancel` ends it. To keep the frozen values, restore them, restart the service and answer `adopt`. `adopt` freezes only the configuration its question named: after a further change and restart it is refused (`stale_question`) and the question is asked again with the current changes. A frozen provider the configuration no longer names offers `switch NAME`, `retry` (after restoring it and restarting) and `cancel`. Once the Objective has a plan, a changed `delivery.kind` offers only `retry` (after setting it back and restarting) and `cancel`, and a `switch NAME` answer that would freeze another kind is refused: the plan is split by the kind it froze (see [Delivery](delivery.md#delivery)). It is asked before a removed provider's question, since every provider has the same `delivery.kind`.
- **Execution profiles** freeze with it: each `execution.profiles.<id>` with its provider's resolved settings as `settings`, the same operational keys excluded. A change to a profile, or to the provider it names, holds like any change. A profile the current plan runs on that the configuration no longer names offers only `retry` (after restoring it and restarting) and `cancel`, since `adopt` or `switch` would freeze a configuration without it; this is asked before a removed provider's question, and a `switch NAME` answer to a configuration without it is refused. A removed profile the plan doesn't use (or an Objective still planning) holds like any change, with `adopt`.
- `status` shows the provider, `selectedBy` and the digest.

### Allowances

How much an Objective may correct itself unattended is `autonomy.allowances` (allowances.ts), frozen with the rest of its configuration. The defaults:

| Allowance               | Default | What it counts                                                                                                       |
| ----------------------- | ------- | -------------------------------------------------------------------------------------------------------------------- |
| `planningRevisions`     | 4       | Planning revision rounds of one generation, and amendments of the accepted plan with their revision rounds.          |
| `implementationRepairs` | 6       | Repairs of Work Items' work, across the Objective; a mechanical merge conflict counts only against `perPath`.        |
| `perPath`               | 3       | Repairs of one repair path: one target step, such as a Work Item's work or its publish.                              |
| `resultRereviews`       | 1       | `revalidate` answers across the Objective: a refused result checked again, unchanged (see Result rereview in Holds). |

- **Running out holds.** A repair past `perPath` or `implementationRepairs` asks before the step that would repair runs again: the engine reads the counts (`state.repairs`), and keeps only the question's id, so its `more` is the engine's. An interrupted attempt passed the check when it started, so it runs again without asking. A Work Item's work step whose pending repair isn't diagnosed yet runs once first (`diagnoseFirst`): a diagnosis that blames a predecessor spends no repair, so the blame is decided before `more` is asked; any other diagnosis is saved, the step goes on (`progress`), and the question follows, and `more` then reuses the saved diagnosis. Its cause is `failure`, with `more`, `replan` and `cancel`. Past the Objective's allowance the question is Objective-wide, so every step waits and it is asked once. The engine also charges each `revalidate` against `resultRereviews` when the answer lands, against the live state, so two at once can't both pass; past it, the step holds the same way instead of taking the answer, and that `more` grants as much again and revalidates. Planning counts every round of a generation against `planningRevisions`, whatever started it: a plan problem, an answer to a planner or review question, or a `more`. Past it, the decide step asks before the next round, with `more` among its answers. An `answer` that would start that round never passes the check: the step keeps it (`decide:g:n:answered`, saved with the question) and asks again, quoting the answer and its question, with only `more`, `replan` and `cancel`. `more` grants as much again, sends the kept answer and records itself next to it; `replan` clears the kept answer. Amendments share this allowance and its grants (see [Amendments](holds.md#holds-and-answers)). The count comes from the saved rounds, and a crash before the step saves its outcome runs the same check again with the same answer, so no round is counted twice or skips the check.
- **`more` grants as much again** (at least one) of each allowance the question names, recorded with the counts in `state.kept`. The engine applies `more` to its own repair questions, and the step never sees it; any other `more` is its step's (a planning round, a rereview, a managed worker's spend).
- **A blamed repair is free.** When the diagnosis blames a predecessor (see Predecessor blame in Holds), the predecessor's repair counts as usual, and the blamed item's repair counts against neither `perPath` nor `implementationRepairs` (the repair or hold outcome's `free`, kept in `state.repairs`).
- **A replan starts afresh.** It clears the repairs, the grants and the rereview counts with the plan.
- `status` shows each allowance as used/allowed, with grants, and repairs per repair path.
- **`autonomy.requiredEnvironment`** names operator variables (each also in `policy.allowedSecretNames`, and none starting `GH_`, `GITHUB_`, `GIT_` or `SSH_`, which workers never receive) that must be set, non-empty, in the service's environment before planning. The check step tests them first; a missing one holds the whole Objective, naming only the missing names, with `retry` (after setting it and restarting the service) and `cancel`. Values are never read past that test, logged or shown.

### Spend ceiling

How much model spend an Objective may reach unattended is `autonomy.spend` (spend.ts), frozen with the rest of its configuration. No limit is set by default.

| Setting (`autonomy.spend`) | What it counts                                                                  |
| -------------------------- | ------------------------------------------------------------------------------- |
| `perObjective.tokens`      | Tokens of every model call of this Objective.                                   |
| `perObjective.cents`       | List cost of those calls, in whole cents.                                       |
| `perDay.tokens`            | Tokens of every model call of every Objective of the installation, per UTC day. |
| `perDay.cents`             | List cost of those calls, in whole cents, per UTC day.                          |

- **Charged per call.** Each model call's `model-usage` event (see [Model usage](run-log.md#model-usage)) adds its total tokens and its reported cost to the Objective's `state.spend` and to the installation's day, `spend.json` in the state directory, which starts again at 0 on a new UTC day. A count the provider doesn't report adds nothing, so a cost limit counts only the calls of providers that report cost; a token limit counts every call that reports tokens. A replan keeps the spend.
- **Reaching a limit holds.** Before a model step starts (a planner, reviewer or worker step: `resource` `planner` or `worker`), the engine compares each configured limit with what it has used. At or past one, the Objective holds before that step, Objective-wide, so no other step starts either; calls already running finish and are charged. The question names each limit reached with what it has used, and offers `more` (as much again of each limit reached) and `cancel`. The engine applies `more` itself: an Objective limit's grant lasts for the Objective, a day limit's for that day only (`state.spend.granted`, `state.spend.dayGranted`). An interrupted attempt passed the check when it started, so it runs again without asking. On a new UTC day an Objective held at the day limit stays held until answered; `more` then grants nothing and it goes on.
- `status` shows each Objective's spend, and each limit as used of allowed with grants; and the installation's spend today.

### Execution profiles

`execution.profiles.<id> = {provider, description, selectionHints?}` names a configured provider's worker the planner may assign to a Work Item. The planner and the plan review are offered the ids with their descriptions and each worker's kind, model, effort, tools and network (planning/steps.ts `offeredProfiles`, providers/selection.ts `profileWorker`), and every work item gets one with a reason. The item's worker runs on that provider's worker settings; planning, reviews and the rest stay on the Objective's provider, and a usage-limit `switch` moves only those, so a limit on a provider the Objective doesn't run on (a profile's) offers only `wait` and `cancel`. Without profiles every item runs on the Objective's provider.

A profile may add two things to its provider's worker, both frozen with the profile, so a change holds a running Objective:

- **`instructions`**: the operator's standing instructions (at most 8,000 characters, no secret value), appended to the worker prompt for its items (work/prompt.ts) as subordinate to Factory's rules and the Work Item, granting nothing.
- **`worktreeRead: true`**: a Claude worker also gets `read_file`, an in-process MCP tool that reads one regular file in its worktree as text (at most 256 KiB). It applies Read's path check (no escape, no `.git`, links only inside), then opens the resolved path by held descriptors with no link followed, and both permission callbacks check it. It needs a Claude worker with `Read` in its tools and allowedTools, so it reads nothing Read couldn't.
