# Steps

Part of [the design](../DESIGN.md).

## Steps

The service loop:

```text
every second:   apply request files
every 30 s:     read the queue (on failure, keep the last good view)
for each active Objective (up to queue.maxActiveObjectives):
    pick the next runnable steps (up to execution.concurrency at once)
    run each step with its deadline → outcome → save state → log
```

One Objective's part of a tick (its deadline, scheduling, steps, sync, observation and retirement) runs under its own guard (service.ts `guarded`): a throw there leaves that Objective alone for the rest of the tick, never the others, and the first of a streak is logged as `objective-error`. Ten such ticks in a row (a hundred when a system call's error, such as a failed save, threw in the rest) set it aside as unreadable, with `retry`, `reset` and `cancel` (see Set aside at run time in [State](state.md)).

The steps:

```text
predecessors → check → per planning round g:n: plan:g:n → review:g:n → decide:g:n [hold: plan question?]
  → plan (accept, post the plan comment) → build:units
  → while an amendment is pending: amend:<id>:plan → amend:<id>:review → amend:<id> (accept, post the plan comment)
  → per Work Item, in dependency order:
      item:<id>:work → select (media items) → validate → review → publish (push, PR) → ci → merge
      read-only QA: item:<id>:validate → review → merge (settles, delivers nothing)
  → final (final validation) → final-review → report → done
```

**QA on the default branch.** Every Objective is checked on the merged default branch, after its last merge:

- **Final validation** (`final`) runs on the default branch head, in a fresh sandboxed checkout. It runs the final commands, the installation's `finalValidation.requiredCommands`, each once. When there are none, it runs each Work Item's own validation commands instead, as the item's validate step ran them: the whole list in order, in a fresh checkout of its own, items in dependency order (planning/plan.ts `fallbackRuns`). A list identical to one already run runs once. Two kinds of command are skipped there, since their own item validated them: one that names `$FACTORY_BASE_SHA` or the plan base's SHA (planning/facts.ts `namedBase`), which checks only its own item's change while the head holds every merge since the base, and one whose package script (or its lifecycle hook) a later merge of this Objective changed, which the later item owns. The run log records a `final-check-skipped` event with the item, the command and `baseRelative` or the items that changed it (`changedBy`), and the final result keeps the same in `skipped`, so final review's evidence, `factory status` and the report name each command that didn't run and why. The plan check requires a validation command on every Work Item once the repository has one. A failed command runs once more on the same tree before the step holds, as a Work Item's validate step does when the worker's own Validate passed that tree.
- **Read-only QA** (a `qa` item) adds checks the plan names: its named CI checks, then its commands, on the default-branch commit once every dependency has merged, then a review. An Objective made only of QA checks the commit it was planned on.
- **Final review** (`final-review`) judges every Objective criterion against the commit final validation checked. For a plan with no command at all (the repository has none), it is the only QA.

Other steps: `cancel:cleanup` after cancel, `rerun:cleanup` before a re-run, `config` when the frozen configuration no longer matches, and `rebuild` for `factory reset`.

Every step returns exactly one outcome:

| Outcome                 | Meaning                                                                                            | What Factory does                                                                                              |
| ----------------------- | -------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------- |
| `done(data)`            | The step finished.                                                                                 | Save the data and move on.                                                                                     |
| `retry(reason, after?)` | A wait classed by its cause, an error among them (see [Waits](#waits)).                            | Back off (30 s doubling to 15 min, or the reset time) and run the step again.                                  |
| `repair(finding)`       | The work is wrong: validation, review or CI failed.                                                | Run the item's work step again with the finding, within the [allowances](state.md#allowances).                 |
| `hold(question)`        | Only a person can decide (cause `question`), or the step can't succeed as it is (cause `failure`). | Post the question on the issue, set Status to "Needs you", and wait (see [Holds](holds.md#holds-and-answers)). |
| `replace(build)`        | Only `factory reset`'s `rebuild` step: the state rebuilt from GitHub.                              | Stop the old record's steps and save the rebuilt state whole.                                                  |

A failure is a hold with the cause `failure`: errors in a row, an allowance spent, a crash-loop suspect, a call too large for the model, or a result the step can't produce. Where the workflow can plan again (a planning round before acceptance; a Work Item, final, final review or report step after it), the engine adds `replan` to its answers.

A step that kept its progress and goes on at once (captured media to collect, a staged repair, one rerun of a flaky command, an approval or an accepted edit) returns `retry` with `progress`: that is not a wait, so it ends the step's run of retries and no status note or wait clock counts it. A repair consumes the answer of the step that returned it, so the step never acts on that answer again. Past a repair allowance, the step that would repair asks before it runs again (see [Allowances](state.md#allowances)).

`replan` is the workflow's, never a step's: the engine applies it from one place (`Workflow.replan`) instead of running the step that asked. Before the plan is accepted it records the operator's decision on the planning round, and a new planning generation re-reads the issue. After acceptance it forgets the plan and the build and checks the Objective again (a repair of `check` whose cleared steps' repair history goes with them). A replan never counts against a repair allowance, `check`'s included, and the answer is spent once applied.

An exception that escapes a step is classified in one place (workflow.ts `errorOutcome`, the workflow's `outcomeOf`, which the engine calls when a step throws): a full disk and the checkout's Git refusal (an origin that no longer names the target) hold for the whole Objective; a planning or review call too large for the model is a failure hold for the whole Objective, with `replan` (`refuse` for an amendment), `retry` and `cancel`; a provider's other classified failures (providers/planner.ts `providerOutcome`) and GitHub's answers (github.ts `githubOutcome`) map as [Waits](#waits) says; anything else is an error, as are a missed deadline, an idle model and an invalid model answer. After three errors in a row on the same step, it becomes a failure hold: the error, plus `retry` and `cancel` (and `replan` where the workflow can plan again). Cleanup after cancel never asks (the step flag `neverAsks`): any outcome but done, a Git refusal included, retries in the background, and after 5 failures in a row over at least `maxWaitMs` (3 h) it settles with what it left (see [Cancel](delivery.md#cancel)). A step can't crash the service, block another Objective, or leave an Objective without an answer that works.

### Interrupted steps

A step the service's death cut off (a crash, an OOM kill, a reboot) is not that step's error. Each saved attempt names the service run that started it, and after a restart the step runs again at once, with no backoff and no error count, cleanup after cancel included. Crash-loop protection is the service's:

- **Crash loop.** `service.json` keeps one list of the latest deaths (`deaths`, at most 20; a clean stop empties it). Each death records how long that run lived after resuming its steps. The crash streak is the trailing deaths that lived less than 10 min. From the third start in a streak (two deaths), interrupted steps resume after 30 s, doubling to 30 min; other steps run as usual. `factory status` shows the deaths in a row and the resume time. A clean stop ends the streak.
- **A step that kills the service.** Each interrupted attempt counts the deaths it ran at (`attempts.<step>.interrupted`, counted at the start after the death, once that start's record is saved, so no death counts twice). A death counts on from the attempt's last one only when the dead run finished a step (its heartbeat count, or an Objective's state saved with a step's outcome naming that run, so a death right after a step still counts); otherwise the count starts again at one. At three, the step holds instead of running again, with its own question: "The service died 3 times in a row while step … ran", with `retry` and `cancel`, asked as soon as no other question stops the step. So a crash streak ends in questions within three deaths however many steps keep being interrupted together, each holding. The count goes with the attempt, so another hold needs three more deaths. Cleanup after cancel never holds; the crash loop's delay covers it.

### Waits

Any other retry is a wait. Waiting more than a few hours is never right, so a wait is classed by its cause, not by how long it has gone on:

| Cause                            | Examples                                                                                                                                                                                                                                                                                           | What Factory does                                                                                                                                                                                                                                                                                                                                                                             |
| -------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Fatal until a person acts        | An expired or invalid gh or provider login; GitHub 401, or a 403 refusal still refused after 2 min; a missing repository or issue (404), except what Factory made within the last 2 min; a full disk; a required check with no run or status 15 min after the push; a workflow that didn't trigger | Hold at once, with a question naming the fix.                                                                                                                                                                                                                                                                                                                                                 |
| A known reset time               | A GitHub rate limit; a provider usage limit that reports its reset                                                                                                                                                                                                                                 | Wait until the reset when it is at most 3 h away. Further away or unknown (a weekly limit): hold with `wait` (keep waiting until it resets), `switch NAME` (run this Objective on another configured provider, which becomes its frozen provider; plain `switch` when there is only one other) and `cancel`.                                                                                  |
| A human gate Factory doesn't own | An environment approval; a review the branch requires; a predecessor Objective (see [Predecessors](queue.md#predecessors))                                                                                                                                                                         | Status shows "waiting on" the gate, and one reminder comment follows after 24 h. A person's gate (an approval, a review) holds after 48 h, so it shows as needing you: `wait` (another 24 h, then it asks again) or `cancel`. The step keeps polling while the question is open, and the question closes by itself once the gate clears. Another Objective's gate (a predecessor) never asks. |
| An unknown transient cause       | The network down; a body that breaks off after its headers; 5xx or an outage at GitHub or the provider; 409, 410, 422 or a GraphQL error from GitHub; CI queued or running                                                                                                                         | Retry with backoff. After 1 h, post one status note on the issue (edited in place). After 3 h, hold with a question naming the cause and the last error: `wait` (another 3 h), `retry` and `cancel`.                                                                                                                                                                                          |

A problem on the host counts as fatal when it is certain (disk, login) and as transient otherwise. Times are wall-clock times saved in the state, so a restart doesn't reset a budget, and the question comes only after the step ran again and still had to wait.

- **An open question pauses the clocks of the steps it stops.** While a question is open, no step it stops starts (see [Holds](holds.md#holds-and-answers) for its scope), so their waits don't count; other items' clocks run on. When the question closes, each waiting step it stopped moves its wait start and any granted `wait` forward by the time it was due but blocked, up to when another open question that also stops it was asked (that one's close moves the rest), so overlapping questions never count the same time twice. A human gate's start stays: its one reminder and its question are timed from that start, and a human gate's own question never stops its step. A wait on another Objective's owned paths ([Queue](queue.md)) moves the clocks of the steps it stopped the same way when it ends, and caps a question's the same way, so a question and a wait on paths never count the same time twice either; the service times it in memory, so a restart counts the wait before it. A step with an open attempt was running, not stopped, so neither moves its clocks. No status note or gate reminder is posted for a step an open question or a wait on paths stops. A step that asks while a question covering its scope is open doesn't wait past the answer: its retry comes due at once, so it runs again right after the answer and asks then, even when its own wait (a reset hours away) would end later.

- **One budget per class.** A step's wait start, first cause, backoff and any granted `wait` belong to one run of one class: a reset, a gate, or an unknown cause (errors count as unknown). When the class changes, they start again, so eight hours on a review never spend the transient budget. The error count covers one run of consecutive errors; any other outcome resets it.
- **GitHub's lag is not a refusal.** For 2 min after Factory creates something through the API (an issue, a PR, a comment: the created resource's URL) or pushes a branch, a 403 or 404 on that resource, under it, or on a path naming the pushed branch or commit is an unknown transient (github.ts `GitHub.made`). Past that window, the same answer holds as above. A response whose body fails after its headers (a reset socket, the deadline, truncated JSON) is a transient too.
- **Only a real rate limit is a reset.** A 429, or a 403 with GitHub's rate-limit headers (`x-ratelimit-remaining: 0` or a `retry-after`), waits for its reset. Any other 403 retries as an unknown transient and asks its refusal question, for the whole Objective, once it has gone on 2 min, so a secondary limit GitHub sent without headers passes by itself. A push or branch delete the remote refuses while the branch still holds the head Factory read does the same, so a passing `[remote rejected]` (two pushes at once, an Internal Server Error) neither asks nor leaves a merged item's branch behind. A 5xx is an unknown transient even when it carries rate-limit headers; its `retry-after` only sets the backoff. A reset at or before now (a skewed clock) still waits at least the normal backoff.
- **Required checks before gates.** A required check with no run or status counts as pending whatever GitHub's readiness says, and it holds 15 min after the push. A review the branch requires is a gate only once every required check is there.
- **Unresolved review threads.** A review thread doesn't resolve by waiting. When the PR's base requires review threads to be resolved (a ruleset's `pull_request` rule, or classic protection's conversation resolution, as the login may read them) and the PR has unresolved ones, a PR GitHub reports `BLOCKED` with every check there, or whose merge GitHub refuses, holds at once. The question links each thread: resolve them, then `retry`; or `cancel`.
- **No checks to wait for.** A PR head with no Actions check run (a repository with no PR CI, or a path filter that skips the item's files) waits 15 min from the push for checks to register. Past that, with every required and plan-named check passed and no Actions workflow run on the head unfinished or failed, it merges on Factory's validated head, with or without checks from other apps. Factory asks only when GitHub doesn't show the head's push time or its Actions runs, and a workflow run that ended without jobs or success is a question too.
- **Deadlines of a wait are the engine's.** A step that waits on something GitHub may not show yet (a merge it made, a PR state) retries with a question for later; the engine asks it once the run of retries has gone on 2 min. A required check that never registers is asked about the same way, 15 min from the push (or from when Factory began waiting, when GitHub doesn't say). An answer to the step (`retry`) starts that time again from the answer. A module never reads the engine's retry records.

### Idempotence

Every step is safe to run again. Before it does anything with an outside effect, it looks for that effect on GitHub:

| Effect          | How the step finds it                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                     |
| --------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Branch          | Fixed name: `factory/<issue>/<item>`.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                     |
| PR              | Open or merged PR whose head is that branch.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                              |
| Merge           | That PR's merged state.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                   |
| Comment         | A hidden marker, `<!-- factory:<issue>:<kind>:<id> -->`, in a comment by Factory's own login (anyone else's marked comment is ignored). An existing comment is edited, not posted again. The report's marker and the live status comment's name the run (`report:<run>`, `status:<run>`, the run being its admission time, state.ts `runOf`), so a later run of the same issue posts its own report and status and checks for edits again. A plan too large for one comment continues in numbered `plan-data` comments. The plan comment and every PR body also name the run and the accepted plan (`factory-run:<run>`, `factory-plan:<accepted>`), and the plan comment its data's SHA-256 (`factory-data:<sha256>`), which `factory reset` binds what it finds to; a PR reused after a replan gets the new marks (`deliver:pr-marks`). |
| Issue close     | The issue's state.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                        |
| Work Item issue | The marker on its body's first line, on an issue by Factory's own login: looked up among the Objective's sub-issues and, only while a creation isn't recorded in state (`creating` is saved, with its time, before the create), Factory's `factory:work-item` issues updated since that creation began.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                   |
| Issue link      | The issue's sub-issues or blocked-by links, read before one is added.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                     |
| Branch delete   | The branch's absence. After its PR merges (a native stack's layers once the whole unit merged), and on cancel, a branch is deleted only when Factory made every commit it has beyond the default branch (GitHub's update-branch merges from the item's base count, a stack layer's predecessor branch included), by a push with a lease on the head it read.                                                                                                                                                                                                                                                                                                                                                                                                                                                                              |
| Project field   | Read before each write, and written only over the option Factory last saw or wrote (see [Queue](queue.md#queue)); it is a display.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                        |

So an effect whose result was lost is never "unknown". The next run of the step finds it on GitHub and carries on.

A model call has no outside effect. If the process dies mid-call, the call runs again, fresh: a retained conversation whose turn was cut off is never continued (see [Retained conversations](run-log.md#retained-conversations)). A worker's worktree is kept and reused on the base the item kept, so a repeated work step continues from its files. A worktree from an attempt that never kept its base (it died before its outcome) is reset onto the base the rerun picks.

A step's kept facts (`state.kept`) outlive repairs. Every read and write goes through one typed helper (work/facts.ts `fact` and `facts`), which builds the keys (`item:<id>:<name>`, or an Objective step's own name) and types the values. A step forgets one by keeping `null`, and the engine then removes it, so a reader never sees `null`. A replan after acceptance forgets them all.

### Deadlines

| Wait                   | Deadline                                                            | At the deadline        |
| ---------------------- | ------------------------------------------------------------------- | ---------------------- |
| GitHub request         | 60 s                                                                | retry                  |
| Plan, plan review      | 45 min each, 15 min idle                                            | retry; hold after 3    |
| Worker turn            | 2 h total, 15 min idle (Copilot: `idleSeconds`)                     | retry; hold after 3    |
| Worker's own Validate  | silent up to the item's validation deadline                         | retry; hold after 3    |
| One validation command | `validation.commandTimeoutSeconds` (30 min)                         | repair                 |
| Validation step        | its commands × the command timeout, + 15 min                        | retry; hold after 3    |
| Final validation       | its commands × the command timeout, + 15 min per checkout, + 15 min | retry; hold after 3    |
| Result or final review | 45 min, 15 min idle                                                 | retry; hold after 3    |
| CI on a PR             | a needed check registers within 15 min of the push                  | hold                   |
| CI queued or running   | 3 h of transient waiting (see [Waits](#waits))                      | hold with `wait`       |
| Hold                   | none: it waits for a person                                         | one reminder (at 24 h) |
| Objective              | `queue.objectiveDeadlineSeconds` from admission                     | cancel                 |

The Objective deadline is optional (no default) and absolute: admission saves it in the state as a time (`deadline`), so a restart or a later configuration never moves it (`factory run N --deadline` sets its own time in place of the default). A reset keeps or restarts it as What starts again in [State](state.md) says. On every tick, for every Objective, whatever it waits on (a question, a pause, a human gate, a slot), the engine checks it (engine.ts `expire`); past it, it cancels through the normal cancel, recording `ended.by: "deadline"`, so cleanup runs; a restart past it cancels at once. Status shows the deadline and the time left, and a question asked within its last hour says when it falls. Crash points `engine:deadline:before-cancel` and `engine:deadline:cancelled` bracket the save.

Step deadlines are fixed in the code, with two configured bounds (final validation's grows with its sequence, capped only by the host's `FACTORY_DEADLINE_MS`): `validation.commandTimeoutSeconds` (default 1800) limits each validation command and sets the validation deadlines above, so a plan with many commands never outlasts its step, and a Copilot provider's `worker.idleSeconds` (default 900) is its worker's idle bound. A managed worker's `timeoutSeconds` (default 3600, at most 6000) fits inside the worker deadline. Idle bounds are the adapter's: 15 min for Codex planning and workers (5 min for a Codex review at medium effort or lower; the same bound while a Codex planning call's read-only command runs), 2 or 5 min by effort for a Claude call, and 45 min while a Claude or Copilot model's tool runs; a Claude or Copilot worker's running Validate or shell command may be silent for the item's whole validation deadline, if longer, still inside the 2 h turn. The only reminders after 24 h are a human gate's (see [Waits](#waits), which asks after 48 h) and an open question's (see [Holds](holds.md#holds-and-answers)). The engine's limits take shorter test timings from the environment (`FACTORY_DEADLINE_MS`, `FACTORY_WAIT_MS`, `FACTORY_NOTE_MS`, `FACTORY_REMIND_MS`, `FACTORY_BACKOFF_MS`).
