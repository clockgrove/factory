# Steps

Part of [the design](../DESIGN.md).

## Steps

The service loop:

```text
every second:   apply request files
every 30 s:     read the queue (on failure, keep the last good view)
for each active Objective (up to queue.maxActiveObjectives):
    pick the next runnable steps (up to execution.concurrency at once)
    run each step with its deadline → outcome → save state → log
```

One Objective's part of a tick (its deadline, scheduling, steps, sync, observation and retirement) runs under its own guard (service.ts `guarded`): a throw there leaves that Objective alone for the rest of the tick, never the others, and the first of a streak is logged as `objective-error`. Ten such ticks in a row (a hundred when a system call's error, such as a failed save, threw in the rest) set it aside as unreadable, with `retry`, `reset` and `cancel` (see Set aside at run time in [State](state.md)).

The steps:

```text
predecessors → check → per planning round g:n: plan:g:n → review:g:n → decide:g:n [hold: plan question?]
  → plan (accept, post the plan comment) → build:units
  → while an amendment is pending: amend:<id>:plan → amend:<id>:review → amend:<id> (accept, post the plan comment)
  → per Work Item, in dependency order:
      item:<id>:work → select (media items) → validate → review → publish (push, PR) → ci → merge
      read-only QA: item:<id>:validate → review → merge (settles, delivers nothing)
  → final (final validation) → final-review → report → done
```

**A failed validation command** (work/step-validate.ts `failedCommandKept`). When a Work Item's validate step fails its result on a command and repairs it, the item keeps that command in its `validationFailed` fact, stamped with the acceptance of the plan it ran under. A finished worker run likewise keeps, in its `workerValidateFailed` fact (work/step-work.ts `workerFailedKept`), the commands its own Validate failed and no later run of it passed, with how each ended and its output (#2199): the worker's Validate runs the declared commands as the validate step does, so a broken command it finds needn't wait for the validate step. These two are the only validation commands an amendment may replace or drop on its reattempt item, and the review judges whether one really can't pass, with the worker's output before it (see Amendments in [Holds](holds.md)). Beside them, the operator may authorize replacing named commands of any Work Item or QA item that hasn't merged, reattempt item or not, published or not, with `replace-validation <item> <index>[,<index>...] <reason>` on an amendment's question, a repair diagnosis question or a read-only QA item's refusal: the authorization is recorded against the plan accepted then (the `validation:authorized` fact), and the review judges the replacement on the operator's reason. A QA item has no worker and no `validationFailed` fact, so this is how its broken command is replaced before a replan (see Authorize replacing a validation command in [Holds](holds.md)).

**The install's kept package store** (validate.ts `installStore`, `installKey`, `keptStore`; #2169). Every validation runs in a fresh checkout and its commands start with the exact frozen install, which used to fetch every package into an empty store each time: about a minute per run in clockgrove/clockgrove#800, six times in one worker turn. A Work Item's validations (its validate step, the worker's own `Validate` with any provider, and a QA item's validate step) now keep the install's package store beside the item's worktree, in `<worktree>.packages`:

- **Keyed by the install's inputs.** The key is a SHA-256 of the install command and of every dependency input of the commit being validated (each lockfile, `package.json`, `package.json5` or `package.yaml`, `pnpm-workspace.yaml` and `.npmrc`, by path, mode and blob). Each key has its own store, `<worktree>.packages/<key>/cache`, reused by the next install of that key; a new key starts from an empty one, so a result that changes its dependencies installs from nothing, as before. The item keeps the stores of its two most recently installed keys (`keys` beside them, newest first) and removes older ones: a candidate whose lockfile Factory resolves (below) installs under two keys on every validation, its own, refused as out of date, and Factory's commit's, and the worker's Validate never commits the resolved lockfile, so each validation repeats both. With one store an item would empty it at each of the two, and fetch everything every time (#2280). A package from the checkout itself (a `file:` tarball or directory) is fetched from the commit's files, and pnpm and npm serve it from a store by the integrity the lockfile records without reading the file again, so when any dependency input names `file:` the key covers every file of the commit: only the very same tree reuses the store, and a result that changed only a vendored tarball installs it from nothing. `file:` counts only as a protocol (`foo@file:`, `"file:vendor/foo.tgz"`, `tarball: file:`, `git+file:`): until #2280 every pnpm lockfile's own `excludeLinksFromLockfile:` setting counted too, so each source change keyed a pnpm install anew and its store was reused only on the very tree that filled it.
- **The install still runs, frozen, every time**, so each validation proves it works on the result; with a reused store it fetches nothing and takes about a second where it took about ten on a 52-package fixture (pnpm 12.6, real sandbox).
- **Only the install writes it.** The store (`<worktree>.packages/<key>/cache`, holding pnpm's store and metadata cache and npm's cache) is mounted writable for the exact install alone, never for another command, and the keys sit outside it, beyond the mount. It is its own mount, so pnpm copies packages into `node_modules` rather than linking store files a later command could rewrite. Only sandboxed: with `sandbox.required: false` and no bubblewrap, every install starts empty, as before.
- **Within the install's disk budget.** The store takes the place of the install's HOME caches, so the sandbox disk budget counts it with that HOME: together at most `sandbox.limits.homeMiB`, and their entries within `sandbox.limits.files`. An install over the budget fails as before, and its key's store is removed rather than kept. The budget is per install, so an item's two kept keys can hold up to twice it on the host.
- **Not with `sandbox.packageStore`.** The operator's store is shared by every install already, and stays as it is. Final validation keeps none either: each install there starts from its own empty HOME.
- **Shared by the installation** (validate.ts `sharedInstallStore`, shared-install-store.ts `sharedStore`; #2280, #2353). An install whose key is the one the item started from (its base, a QA item's the plan's) has every dependency input as there, as most items' do, so it uses the installation's store for that key, `<work root>/.packages/<key>/cache`, rather than the item's own: the first such install of any Objective fetches, and every later one, of any item of any Objective, reuses it, so an Objective's first install is not cold. A store of each key is made whole under a temporary name and renamed into place, never emptied for another key, so installs of one key at once never remove each other's; the same rules hold (only the exact install writes it, within its disk budget, removed when over it). An item that changed a dependency input keeps its own `<worktree>.packages`, as above.
- **Pruned by last use.** Each use of a key marks it used (the key directory's modification time) and holds a claim on it for the install (`claims/<process id>-<n>`, beside `cache`; a claim of a dead process counts for nothing). When an install makes a new key, the keys unused for `sandbox.limits.installStoreDays` (14) days are removed, and then the least recently used until the keys hold at most `sandbox.limits.installStoreMiB` (20480) MiB in all. A key used in the last hour, or with a live claim, is never removed, so pruning is safe while another install uses the store; a removed key is rebuilt by its next install. Temporary directories a crash left are removed with them.
- **Removed with the worktree.** Cleanup removes `<worktree>.packages` with the worktree and its `.shell` and `.validation` directories, when the Objective completes, is cancelled or is replanned; until then each item keeps at most two stores, of two keys, each within that budget. The installation's store outlives the Objective. The run log's `validation-command` event for the install says `installStore`: `reused` or `new`, and `installStoreShared: true` on the installation's store.

**The worker's kept Validate checkout** (validate.ts `KeptCheckout`, work/self-validate.ts; #2352). A worker's own `Validate` made a fresh checkout for every run, so it ran the install again and every tool cache (TypeScript's incremental build info, lint and test runner caches) started empty: on one repository's two Objectives, 102 worker runs of its 24 s `check` script took most of 51 minutes. A worker attempt now keeps one checkout for its runs, `<worktree>.worker-validation`:

- **Brought to each snapshot.** Its first run makes it fresh. Each later run resets it to that run's snapshot commit and removes every untracked file Git doesn't ignore (`git clean -ffd`, so no `.gitattributes` a command left changes how the reset writes tracked files, `git reset --hard`, and `git clean -ffd` again; worktree.ts `refreshWorktree`), and goes on only when its status is then clean: its tracked and untracked files are a fresh checkout's, and only the files Git ignores (installed dependencies, build output, caches) stay from the last run. A file the new snapshot deletes is gone. Host Git there is pinned as everywhere: no repository-configured program runs (hooks, `core.fsmonitor`, filters other than Git LFS's own), and it refuses a `.git` that no longer names the registered admin directory, which the sandbox mounts read-only anyway. When Git can't refresh it, or refuses, the run makes it fresh instead.
- **The install skipped while its key holds.** The exact install is skipped when its `installKey` is that of the last install that passed in this checkout; its result says so, and its `validation-command` event says `installSkipped: true`. Any other install runs, and until it passes the checkout counts as installed by none.
- **Made fresh after a doubtful run.** After a run that goes over the disk budget, or ends in a retry, a hold or an error, the next run makes it fresh; so does the first group's (below) after that group was stopped mid-command. Only the attempt's memory says the checkout is its own, so a later attempt, or the service's restart after a crash, makes its own.
- **The attempt's alone.** The work step removes it, with what its groups left, before the worker starts (what a crashed attempt left) and after the worker ends, cancelled too; cleanup removes any left with the item's worktree. Its commands run in the same sandbox, with the same network, services and pinned scripts as before.
- **Groups.** With independent groups (below), the first group keeps a checkout of its own the same way, at `<worktree>.worker-validation.kept-group`; every other group's is fresh, as before.
- **Feedback only.** A file a command produced is returned to the worker only when this run modified it. A targeted run sees what the last full run built, so it may pass on build output a fresh checkout wouldn't have; it never counts. The validate step, QA, the integrated validation and final validation keep their fresh checkouts and decide the result.
- **Measured.** Each `worker-validate` event says `checkout` (`kept` or `fresh`), `checkoutMs` and `installSkipped`. On a 1,500-module TypeScript fixture (pnpm 12.6, `tsc` with incremental build info, real sandbox), each worker run after the first took 2.6 s instead of 6.0 s: `check` 1.5 s instead of 4.0 s, the install (0.8 s on the warm store) skipped, and the refresh 35 ms where a fresh checkout took 95 ms.

**An install the network failed** (install-outage.ts; #2340). A DNS or connection failure that lasts seconds is the host's, not the candidate's. When the exact install had the network (`package-install`'s verified grant, or `host`) and failed for it, validation runs it again before any other command: waits of 5 s doubling, while at most 2 min have passed since its first run. Factory reads only the package manager's structure, never its prose:

- **npm 11** fails with an error code on its `npm error code` line: `EAI_AGAIN`, `ENOTFOUND`, `ECONNRESET`, `ECONNREFUSED`, `ETIMEDOUT`, `ENETUNREACH`, `EHOSTUNREACH` or `ERR_SOCKET_TIMEOUT`.
- **pnpm 12** fails with `ERR_PNPM_META_FETCH_FAIL` (metadata it could not fetch) or `ERR_PNPM_TARBALL_FETCH_TARBALL` (a tarball request that broke off). pnpm 12 gives a metadata answer of 404 or 500 the same code; the registry's ping tells them apart below.
- **An optional package pnpm dropped.** pnpm 12 skips an optional package whose fetch fails and still exits 0, so a formatter's platform binary can go missing and a later command fail with 127. After an install that exited 0, a snapshot of `pnpm-lock.yaml` that pnpm's current lockfile (`node_modules/.pnpm/lock.yaml`) lacks fails it; a package skipped for the platform stays in that lockfile. npm 11 drops such a package too, but records nothing that tells the drop from a platform skip, so an npm install that exits 0 passes.

Still failing when the window ends, Factory pings the registry the base's `.npmrc` sets with `registry=` (else the public one) from the host: `GET <registry>/-/ping`, 10 s at most. Any HTTP answer means the registry is reachable, so the failure is the result's and goes on as below (a metadata 404 among them). No answer (DNS, connection, timeout), or a registry Factory can't read exactly, is the environment's: the step retries as an unknown transient cause (see [Waits](#waits)), whatever the candidate changed, so no diagnosis runs, no repair is counted, and it asks only after 3 h. The install's `validation-result` event says `registry`: `answered`, `unreachable` or `unknown`. Every other install failure, such as an out-of-date lockfile, goes on as below. The run log has a `validation-install-retry` event for each retry, with the cause and the wait.

**A dependency change's lockfile** (validate.ts `resolveLockfile`). No worker has the network to resolve a lockfile, so a Work Item that changes its dependencies leaves `pnpm-lock.yaml` (or `package-lock.json`) out of date, and the bootstrap refuses it (`ERR_PNPM_OUTDATED_LOCKFILE`, `ERR_PNPM_LOCKFILE_CONFIG_MISMATCH` for changed overrides, or npm's "can only install packages when your package.json and package-lock.json ... are in sync"). When a Work Item's validation (its validate step, or the worker's own `Validate`) meets that refusal and the candidate changed a dependency input (a `package.json`, `pnpm-workspace.yaml`, `.npmrc` or lockfile), Factory resolves the lockfile itself, once:

- **How it runs.** `pnpm install --lockfile-only --no-frozen-lockfile --ignore-scripts`, or `npm install --package-lock-only --ignore-scripts --no-audit --no-fund` (planning/facts.ts `LOCKFILE_RESOLUTION`), in the validation checkout, run as the bootstrap's install runs: an empty HOME of its own, scripts, hooks and pnpmfiles off, the package store writable, and the network only as the install would get it. With `package-install` that is pasta's namespace, and only when the install's own grant holds (its lockfile always verified, even when the candidate changed only a member's manifest) and every `package.json` the candidate changed that the resolution reads names its dependencies and overrides from the registry alone, never a URL, git, `file:`, `owner/repo` or a specifier npm reads as a local folder or tarball though it names no protocol or slash (starting with `.`, as `..` does, or ending in `.tgz`, `.tar.gz` or `.tar`), and so does every `overrides`, `catalog` and `catalogs` entry of a `pnpm-workspace.yaml` it changed (package-network.ts `resolutionNetworkRefusal`); with `host`, the host's. With pnpm, the manifests it reads are the root's and each workspace member's by `pnpm-workspace.yaml` `packages`: a manifest elsewhere, such as a test fixture's, fetches nothing, since the verified lockfile refuses a `file:` dependency that could link it in. Factory reads a `packages` pattern only as `*`, `?` and `**`; with any other pattern, `package.json` `workspaces` or a symbolic link in the tree, every changed manifest counts. With npm every changed manifest counts, since npm reads the `package.json` of each directory it links (a `file:` dependency) and fetches what it names; so for npm's install too, each linked directory must have a tracked `package.json` whose dependencies name the registry alone. A changed project whose manifest is `package.yaml` or `package.json5` (pnpm reads both; Factory doesn't) keeps the resolution offline. The repository's own policy (its registries, minimum release age, provenance and build settings) applies unchanged: the candidate can't change its package configuration. Of `pnpm-workspace.yaml` the candidate may change only the package membership the Objective declares (Workspace package additions) and the dependency keys `overrides`, `catalog` and `catalogs` (validate.ts `checkWorkspaceChange`); the install keeps its network across those changes too, since the lockfile it then verifies records them (package-network.ts `installNetworkRefusal`). Every other setting, build approvals (`allowBuilds`, `onlyBuiltDependencies`) included, stays the operator's.
- **What it makes.** When the resolution changed only the lockfile, Factory commits it on the candidate as its own change (`Factory: resolve pnpm-lock.yaml for the dependency change`, authored like a collected result), pins the commit at `refs/factory/<issue>/<item>/lockfile` until cleanup, and runs the whole sequence again on that commit, the frozen install first. The validate step's result keeps the commit and the lockfile's path (`regenerated`), so review, publication and the PR use that commit (work/steps.ts `candidate`), and result review's validation row names the lockfile as Factory's change, which needs no owned path. The worker's own `Validate` keeps nothing, and tells the worker Factory resolves the lockfile again after it finishes. The run log records `lockfile-resolution`, `lockfile-resolution-result` and `lockfile-resolved` events, and a failed resolution's whole output in its `validation-lockfile` attempt file.
- **When it holds.** With `sandbox.network: off` nothing can resolve it: a hold with `retry`, `replan` and `cancel` that names `factory setup --sandbox-network package-install`. A resolution the package manager refuses (the repository's minimum release age, the registry) holds with its message and the same answers; Factory never relaxes the policy. A version the registry has never published is the exception below. One that ran offline because the candidate's own inputs refused it the network (a dependency from outside the registry, a changed package configuration) fails the candidate, however the offline run failed, and goes back to the worker with why.
- **A version that doesn't exist** (validate.ts `missingVersion`, missing-version.ts; #2099). pnpm 12 reports a missing version as `ERR_PNPM_NO_MATCHING_VERSION` and npm as `ETARGET`, and npm reports a release-age refusal with the same code, so the message alone can't say whose it is. When a resolution that had the network (`package-install`'s verified grant, or `host`) fails that way, Factory:
  1. Reads the package and the requested range from the message (pnpm's line wrapping undone). It looks nothing up if the output isn't exactly one such refusal, or is pnpm's release-age refusal (`ERR_PNPM_NO_MATURE_MATCHING_VERSION`). Under a release-age policy (`min-release-age`, `before`) npm adds `with a date before <date>` to every `ETARGET`, a version that was never published included, so Factory reads the request through that suffix and leaves telling them apart to the lookup.
  2. Requires that to be exactly one specifier the candidate itself declares in the package inputs it changed: a `package.json`'s dependencies or overrides, or `pnpm-workspace.yaml` `overrides`, `catalog` or `catalogs`. A version a dependency asks for, or one Factory can't match exactly, holds.
  3. Requires a package name it can pass to the lookup and a plain semver range: a dist-tag, an `npm:` alias, a protocol (`workspace:`, `catalog:`, git, `file:`, a URL) or a prerelease range holds. It requires the checkout's package configuration (`.npmrc`, pnpmfiles, `pnpm-workspace.yaml` settings, `packageManager`/`devEngines`) to be the base's (package-network.ts `configurationRefusal`).
  4. Runs `pnpm view '<name>' versions time --json` (or `npm view`) exactly as the resolution ran: the same sandbox, the same network grant and namespace, the same checkout and configuration, so the same registry and release-age settings. It sends the registry only the name the resolution already asked for.
  5. Reads the published versions as `versions` and the keys of `time` together, and tests each against the range with the `semver` package (loose, prereleases included, so every doubt counts as satisfying).

  If no published version satisfies the range, the candidate fails and goes back to the worker. Its message is Factory's own text: the package, the range, how many versions are published and at most the 10 newest releases, each reprinted from its parsed semver as `major.minor.patch` (digits and dots only; a prerelease, whose tag is free text its publisher chose, is never named), so nothing the registry sends reaches the worker as text. If a version satisfies the range (one the minimum release age keeps out, say), the hold stands and names it with its publish time. So does a lookup that fails, times out, is cut off, prints an `error` object (pnpm prints one and exits 0 for a package the registry lacks) or anything but versions. The run log records a `lockfile-resolution-lookup` event with the verdict, and the lookup's output in its `validation-lockfile-lookup` attempt file. These stay the operator's and out of scope: `packageExtensions`, `peerDependencyRules`, `patchedDependencies`, `package.json` `pnpm.overrides` (the `pnpm` key stays pinned; use `pnpm-workspace.yaml`), and npm workspaces.

- **When it doesn't run.** A stale lockfile whose inputs the candidate left as at the base is the environment's failure (retry), never resolved. QA and final validation, on the default branch, never resolve a lockfile. npm's bootstrap needs `package.json` and `package-lock.json` tracked at the base and in the result, and no `workspaces`; a dependency change may change both files, as with pnpm.

**The repository's formatter** (validate.ts `applyFormatter`; #2159). Formatting is deterministic, so no model spends tokens on it. With `validation.formatCommand` set (`factory setup --format-command CMD`, frozen with the Objective; absent, nothing is formatted), a Work Item's validation (its validate step, or the worker's own `Validate`) runs that command once, as Factory's own step, like a lockfile resolution:

- **When and how it runs.** In the validation checkout, after the exact locked install when the item's commands start with one (the formatter is usually a dependency), else before the first command; after a lockfile resolution, so on its commit. It runs as a validation command runs, in the sandbox with a private HOME and TMPDIR, but with no network whatever `sandbox.network` says, and no model.
- **What it may change.** Only files the result changed (from the commit the item was built on) inside the item's owned paths, in place. A change to another file the result changed (one outside the owned paths), or a file it adds, deletes or renames, fails the candidate (a repair, as the mutation check below) naming the changes, with their diff (bounded: at most 20 files, 4,000 characters from its start and 2,000 from its end). A change to a file the result left as it was means the commit the item was built on isn't formatted, which no repair can fix: that holds the Objective with the changes and their diff, to format the default branch and replan, or cancel. A formatter that exits non-zero, outlasts `validation.commandTimeoutSeconds` or overflows the disk budget fails the candidate with its output, as a failed command does, and the item's commands after it don't run. With no install before it (the item's commands don't start with the exact install), a formatter that failed and changed nothing may only lack the dependencies the install brings, which the worker can't add to the item's commands: Factory logs `format-skipped` and runs the item's commands on the result unformatted, charging nothing.
- **What it makes.** When it changed anything, Factory commits it on the candidate as its own change (`Factory: apply the repository's formatter`, authored like a collected result), pins the commit at `refs/factory/<issue>/<item>/format` until cleanup, and runs the item's commands on that commit. The validate step's result keeps the commit, the command and the files (`formatted`), so review, publication and the PR use that commit (work/steps.ts `candidate`; the formatting commit is on top of a resolved lockfile's), and result review's validation row names it as Factory's change, which needs no owned path. The formatter reads the result's own configuration, so when the result changed a file that configures a formatter or fixer (`biome.json`, `.prettierrc*`, `.editorconfig`, `eslint.config.*`, `pyproject.toml` and the like, or a `package.json` whose `prettier`, `eslintConfig`, `stylelint` or `biome` key changed; validate.ts `formatterConfiguration`), the formatting commit can be more than layout (a lint rule with a fix): `formatted.configuration` lists those files, and the review row then asks the reviewer to judge the commit's diff as the worker's change instead of calling it layout only and never a finding. No repair is charged and no model is called for it. The worker's own `Validate` keeps nothing, leaves the worker's files as they are, and tells the worker Factory formats the result again after it finishes. A failed validation keeps the candidate's own tree (`candidateTree`) beside the tree Factory's last commit made, so a failure on a result the worker's `Validate` passed is still run once more before it counts (the flaky rerun). The run log records `format`, `format-result`, `format-skipped` and `format-applied` events, and a failed formatter's whole output in its `validation-format` attempt file.
- **Planning and workers.** The planner and plan review are told Factory formats each result, and that every validation command only checks. The plan check refuses a validation command it can see rewrites tracked files, directly or through root package scripts: a formatter or linter with `--write`, `--fix`, `--apply` or `--apply-unsafe`, `prettier -w`, `gofmt -w`, `clang-format -i`, or `cargo fmt`, `rustfmt`, `black`, `ruff format`, `deno fmt`, `dprint fmt`, `terraform fmt`, `tofu fmt` or `isort` without their check flag (planning/facts.ts `writingToolOfCommand`); without a format command too, since such a command fails the mutation check on any result it reformats. The worker prompt says formatting is applied after the worker finishes, so it never formats by hand. Every provider hears the same: a worker with Factory's `Validate` tool (Claude, Copilot or Codex) gets the formatter applied there, every worker kind from the same configured command (providers/selection.ts `providerWorker` builds one set of Validate settings for all of them; #2166), and its time counts in that `Validate`'s deadline; one that runs the validation commands in its own shell instead (a worker without `Validate`) runs exactly the configured format command first, one deterministic command, so a check script that starts with a format check (`biome check . && tsc`) still reaches the checks after it.

**Independent commands at once** (validate.ts `inGroups`; #2290). A Work Item's commands split into groups by their `after`: a command joins the group of each earlier command it lists, or, with `after` null, of every earlier one, so such a command keeps the declared order. When there are two or more groups, each runs at once in a checkout of its own after the exact install and the formatter, in a Work Item's validate step, a QA item's, the integrated validation, the worker's own `Validate` and final validation's runs of Work Item commands (final commands declare no `after`, so they run in order, as does an item list that final validation or the integrated validation shortened, since its indices moved). A run that starts with the exact install splits only where that install has a warm store to reuse: a Work Item's kept or shared store, or the operator's `sandbox.packageStore`; final validation without one runs in order:

- **What a group starts from.** A fresh worktree (beside a worker's kept Validate checkout, the first group's is kept too, as above) of the commit the formatter and a lockfile resolution left (Factory's commit when it made one, so both run once, before the split), its Git LFS files restored, and the same exact install again, on the same store, so a group shares no file with another or with the first checkout. Its own sandbox, TMPDIR, gh configuration and services (`sandbox.services`, started fresh for it and stopped when it ends), and a copy of the HOME the formatter left. The mutation check names the group's own command.
- **Capacity.** The step's own validation slot runs one group; each other group running at the same time takes one more validation slot (`execution.validations`, with its memory reservation) while one is free, and gives it back when no group is left for it. With none free, the commands run one after another in one checkout, as before. In a fixture of an install of 30,000 files (0.9 s) and three groups (8.5 s, 6.5 s and 8.5 s + 0.5 s of commands), the run took 14 s instead of 26.5 s; each group's install started 0.5 to 1 s after the first one ended.
- **Results.** The first group to stop ends the others. Results, review artifacts and the files returned to a worker come back in run order, as one checkout would give them. A failure is the run's only when no command of another group comes before it in run order, so its checkout had everything the declared order gives it. Any other failure could come from an `after` that leaves out what the command needs, and so could a group's own install failing, so the commands run again in run order in the first checkout, which no group touched, with services started fresh for that run, and that run decides (`validation-groups-rerun`). So groups are never less correct than the declared order: a failure there costs one more run.

**The mutation check.** Validation runs on the result as committed, so after each command that passes, Factory compares the checkout's status with what it was before the commands ran (and HEAD with the commit). A command that changed it fails the candidate at once, before the next command runs: `Validation command modified the result tree:` names the command and the status records it changed, and attaches their diff, bounded as above (a new file larger than 64 KiB, or one that isn't a regular file, is only named). A command may write only files Git ignores. With the repository's formatter applied first, a formatter listed among the item's commands finds nothing to change.

**What a Work Item's validation counts against** (validate.ts `base`, work/step-validate.ts `integratedValidation`; #2240). A check that compares with a base (a budget, a size limit, a coverage delta) let each Work Item use the whole allowance against its own base, and the Objective's sum failed only at final validation, after the last merge. So a Work Item's validation now runs each command as final validation will:

- **Its base.** A command final validation runs itself on the default branch (planning/plan.ts `checkedAtFinal`: a final command, or with none, each Work Item command that doesn't name its base) gets the plan's base as `FACTORY_BASE_SHA`, as final validation gives it, so a repository script that reads `FACTORY_BASE_SHA` itself counts the Objective's change so far. Every other command still gets the commit the item was built on: one that names its base (`$FACTORY_BASE_SHA` or the plan base's SHA, planning/facts.ts `namedBase`) checks only its own item's change, and final validation skips it; and with final commands, final validation never runs a Work Item command that isn't one, so the plan's base would only count other Objectives' merges since it, which no worker can repair. Setup (the install, the formatter) keeps the item's base too. This holds for the validate step and the worker's own `Validate` alike.
- **Its tree.** An item builds on the default branch as it is when it starts, which holds its merged dependencies, but another Work Item of the Objective may merge after it started. When the candidate lacks such a merge, its validate step, once the candidate's own validation passed, merges the validated commit into the Objective's integrated head (the latest merge, which holds every earlier one) as Factory's own commit, pinned at `refs/factory/<issue>/<item>/integrated` until cleanup and never published, and runs there, with the plan's base, the item's commands final validation runs itself, leaving out the rest (one that names its base, any but a final command when the plan has those, one whose package script an earlier merge changed). A command that fails there is the item's validation failure like any other, with its complete output (#2201), and the repair moves the item onto the current default branch, so the worker sees what the earlier merges left. A merge that conflicts is left to the merge step, and a failure no command made (a pin, the mutation check) to final validation. The run log records `integrated-validation` (or `integrated-validation-skipped`, with why), and the kept validation's key names the merges. The step's deadline counts the item's commands twice for it. Items run side by side are often each validated before the other merges, so the merge step checks again: the item keeps the other Work Items' merges its validation counted (`item:<id>:validatedOn`), and when another merged since, its merge step, before merging, runs the same check on the current integrated head (work/step-validate.ts `validateBeforeMerge`), with a CPU slot and the item's validation deadline added to its own. A failure there is the same repair, so the aggregate failure is caught before the last merge; a pass adds the merges to the fact, so the step's retries run nothing again. A PR GitHub already merged (the step resumed after the merge) is past checking, and state 0.5.11 saved has no fact, so every merge counts as since. A native-stack layer is not checked this way: it builds on the layer below and merges with its unit.

**Same commit, same validation.** A Work Item's validate step keeps its latest result, passed or failed, with the candidate commit and a digest of what it ran under (`item:<id>:validation`, work/step-validate.ts `validationKey`): the accepted plan, the item's commands, the base, the Objective's merges the candidate was built without, the Objective's blocks, the media, the review artifact selectors, `validation.formatCommand`, the sandbox, the command timeout, and the environment, which is Factory's build (version and source digest) and the service process. When the step comes back to that same commit under the same digest, after a question answered with no new commit (Factory's own `revalidate` after the worker resubmitted its refused result unchanged, or an `accept <n>` that leaves nothing standing), it runs nothing: the kept result stands again, a pass as the step's result and a failure as the same repair, logged `validation-reused` with the item, the commit and when it ran (#2174). In Clockgrove #800 (0.5.7), the same 15-file formatter refusal was validated again for 7.2 minutes that way. The operator's own `revalidate` (or the `more` that grants one) drops the kept result, so the commands run again, as does a service restart (a new process), an amendment or replan, or a changed configuration. A run that ends without a result (an error, a hold) or runs a failed command once more (the flaky rerun) keeps none.

**Result review** (review/item.ts). A Work Item's result review sends the result back only for a failure Factory reproduces. After validation passed (a failed command is a repair with no review), two things start at once:

1. **The workspace.** One fresh validation checkout of the reviewed commit (`<worktree>.scratch`), with the exact install alone run, on the item's kept or shared package store, so it installs warm, under validation's sandbox (required here, whatever `sandbox.required` says), network and environment, with no secrets. Every other checkout of the review is a copy of it (`<worktree>.scratch.copies/`): a linked worktree of the same commit with the files Git doesn't hold (the install's output, restored Git LFS bytes) copied in, and its own HOME and TMPDIR, so nothing installs twice. Its commands see it at the workspace's path (each sandbox mounts its copy there), with the tracked files' times kept, so the absolute paths and times the install recorded (pnpm's workspace state) hold as in the workspace. Only the proofs use it.
2. **The finder**, the result reviewer Factory used before reproduced refusals (review/finder.ts), in a fresh session: a stored review conversation is never resumed. It judges the item's own acceptance, then each Objective criterion or source exit item the plan says this item's review proves, quoted verbatim (`resultCriteria`), with its own instructions (the shared review guidance, the engineering standard, the design checklist, protected existing tests and command-proven criteria, about 17,000 characters: they only find, so the 5,000-character bound is the proofs') and the usual evidence root and rows (result.ts `runReview`, which also sends a question about held evidence back once). It runs no command. Each criterion gets `pass`, `needs-human` (a question for the operator) or `refuse`. A criterion its answer leaves without a valid verdict is never met: when the answer refused nothing, it is asked again whole, once; when it refused, the criteria it left so are asked again alone, once (`result-review-missing`). One still without a verdict is the operator's question, in the review's one hold. A refusal is not a verdict: it is one suspicion, its detail the case and its criterion the expectation.

Then:

- **Merged suspicions.** Refusals of different criteria whose details cite overlapping lines of a file with the same basename (`path:N`, `path:N-M`, `path:N-M,P-Q` or `path#LN-LM`) are one suspicion, its case and expectation each member's, transitively. Its proof stands for all of them.
- **Proofs.** Each suspicion, at most `review.proofs` (4) a review, gets its own short task, as many at once as the proof pool has slots free (`execution.proofs`, apart from the planner slots, beside the review's own): a fresh reviewer call that gets only the criterion (each member's, for a merged suspicion), the suspicion, the workspace's checkout to read and `run_command` in a copy of the workspace of its own, within `review.proofCommands` (8) commands and `review.proofSeconds` (120) in all. Its instructions, identical for every provider, fit in 5,000 characters with its tool. On Codex, the finder and the proofs ask for the priority service tier unless the provider's `models.reviewServiceTier` sets another (see [Setup](setup.md)). It writes a repro (an input, the expected and the actual output, and a command that exits non-zero on the candidate because of that failure) and runs it, or answers that it doesn't reproduce. An invalid answer is asked again once. A suspicion past the review's proofs is dropped.
- **Refusal check**, with no model, for each proof's repro as it comes. Factory runs the command in a fresh copy of the workspace. It confirms the suspicion when the command exits non-zero by itself (not 126 or 127, and not at its limit) and its output holds the claimed actual output, whitespace aside. A confirmed suspicion refuses its criterion, each member's for a merged one, with that repro. Any other suspicion is dropped: the run log has it (`result-review-suspicion`), nobody else sees it, and its criterion counts as met. A dropped suspicion costs nothing.
- **Outcome.** Confirmed refusals go to repair, each with its repro, and count against the allowances. The item keeps their commands (`item:<id>:repros`), and every later validation of its results, the validate step's and the worker's own Validate, runs them after the item's commands and the install alone, so a repair passes only when they pass. An operator's `accept <n>` on the refused tree drops that criterion's repro, and a replan drops them all. Otherwise the questions ask the operator in one hold. Otherwise the item is accepted.

A re-review after a repair gets, instead of a conversation, the refusals confirmed on the previous result and the diff from that result to this one (at most 48 KB). The review's `result-review` event counts the finder's verdicts by kind, the suspicions raised, proved and dropped with the proofs' tokens, repros confirmed and dropped and questions, with each phase's time (the workspace's install, the finder, the proofs); `factory status N --item ID` shows them with the review calls' tokens (see [Run log](run-log.md)). In-flight items keep the verdicts they have; a review session an earlier version kept is ignored.

**QA on the default branch.** Every Objective is checked on the merged default branch, after its last merge:

- **Final validation** (`final`) runs on the default branch head, in a fresh sandboxed checkout. It runs the final commands, the installation's `finalValidation.requiredCommands`, each once. When there are none, it runs each Work Item's own validation commands instead, as the item's validate step ran them: the whole list in order, in a fresh checkout of its own, items in dependency order (planning/plan.ts `fallbackRuns`). A list identical to one already run runs once. Two kinds of command are skipped there, since their own item validated them: one that names `$FACTORY_BASE_SHA` or the plan base's SHA (planning/facts.ts `namedBase`), which checks only its own item's change while the head holds every merge since the base, and one whose package script (or its lifecycle hook) a later merge of this Objective changed, which the later item owns. The run log records a `final-check-skipped` event with the item, the command and `baseRelative` or the items that changed it (`changedBy`), and the final result keeps the same in `skipped`, so final review's evidence, `factory status` and the report name each command that didn't run and why. The plan check requires a validation command on every Work Item once the repository has one, and the final command itself on a Work Item that owns a test file or runner configuration only that command runs (planning/checks.ts `finalProofFindings`, #2170), so the item's own review sees that proof before it merges, not final validation after. A failed command runs once more on the same tree before the step holds, as a Work Item's validate step does when the worker's own Validate passed that tree. Its failure asks with `repair` where a merged Work Item can take it, `retry` and `replan` (see Final validation in [Holds and answers](holds.md#holds-and-answers)).
- **Read-only QA** (a `qa` item) adds checks the plan names: its named CI checks, then its commands, on the default-branch commit once every dependency has merged, then a review. An Objective made only of QA checks the commit it was planned on. A QA item changes nothing, so the plan check refuses a QA command that requires a string of a document the base lacks unless a Work Item it depends on owns that file and is asked for the string, in an acceptance entry that names the file and quotes it (planning/checks.ts `qaRequirementFindings`, #2170).
- **Final review** (`final-review`) judges every Objective criterion against the commit final validation checked. For a plan with no command at all (the repository has none), it is the only QA. Its refusal asks with `repair` where one Work Item owns the refused criteria, `retry` and `replan` (see Final review in [Holds and answers](holds.md#holds-and-answers)).
- **The report** (`report`) posts the outcome on the issue (marker `report:<run>`): each Work Item's PR and merge, final validation and review, the operator's decisions and retirements, then the operators' @mentions (see [GitHub identity](setup.md#github-identity)). Then it closes the issue as completed.

Other steps: `cancel:cleanup` after cancel, `rerun:cleanup` before a re-run, `config` when the frozen configuration no longer matches, and `rebuild` for `factory reset`.

Every step returns exactly one outcome:

| Outcome                 | Meaning                                                                                            | What Factory does                                                                                              |
| ----------------------- | -------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------- |
| `done(data)`            | The step finished.                                                                                 | Save the data and move on.                                                                                     |
| `retry(reason, after?)` | A wait classed by its cause, an error among them (see [Waits](#waits)).                            | Back off (30 s doubling to 15 min, or the reset time) and run the step again.                                  |
| `repair(finding)`       | The work is wrong: validation, review or CI failed.                                                | Run the item's work step again with the finding, within the [allowances](state.md#allowances).                 |
| `hold(question)`        | Only a person can decide (cause `question`), or the step can't succeed as it is (cause `failure`). | Post the question on the issue, set Status to "Needs you", and wait (see [Holds](holds.md#holds-and-answers)). |
| `replace(build)`        | Only `factory reset`'s `rebuild` step: the state rebuilt from GitHub.                              | Stop the old record's steps and save the rebuilt state whole.                                                  |

A failure is a hold with the cause `failure`: errors in a row, an allowance spent, a crash-loop suspect, a call too large for the model, or a result the step can't produce. Where the workflow can plan again (a planning round before acceptance; a Work Item, final, final review or report step after it), the engine adds `replan` to its answers.

A step that kept its progress and goes on at once (captured media to collect, a staged repair, one rerun of a flaky command, an approval or an accepted edit) returns `retry` with `progress`: that is not a wait, so it ends the step's run of retries and no status note or wait clock counts it. A repair consumes the answer of the step that returned it, so the step never acts on that answer again. Past a repair allowance, the step that would repair asks before it runs again (see [Allowances](state.md#allowances)).

`replan` is the workflow's, never a step's: the engine applies it from one place (`Workflow.replan`) instead of running the step that asked. Before the plan is accepted it records the operator's decision on the planning round, and a new planning generation re-reads the issue. After acceptance it forgets the plan and the build and checks the Objective again (a repair of `check` whose cleared steps' repair history goes with them). A replan never counts against a repair allowance, `check`'s included, and the answer is spent once applied.

An exception that escapes a step is classified in one place (workflow.ts `errorOutcome`, the workflow's `outcomeOf`, which the engine calls when a step throws): a full disk and the checkout's Git refusal (an origin that no longer names the target) hold for the whole Objective; a planning or review call too large for the model is a failure hold for the whole Objective, with `replan` (`refuse` for an amendment), `retry` and `cancel`; a provider's other classified failures (providers/planner.ts `providerOutcome`) and GitHub's answers (github.ts `githubOutcome`) map as [Waits](#waits) says; anything else is an error, as are a missed deadline, an idle model and an invalid model answer. After three errors in a row on the same step, it becomes a failure hold: the error, plus `retry` and `cancel` (and `replan` where the workflow can plan again). Cleanup after cancel never asks (the step flag `neverAsks`): any outcome but done, a Git refusal included, retries in the background, and after 5 failures in a row over at least `maxWaitMs` (3 h) it settles with what it left (see [Cancel](delivery.md#cancel)). A step can't crash the service, block another Objective, or leave an Objective without an answer that works.

### Interrupted steps

A step the service's death cut off (a crash, an OOM kill, a reboot) is not that step's error. Each saved attempt names the service run that started it, and after a restart the step runs again at once, with no backoff and no error count, cleanup after cancel included. Crash-loop protection is the service's:

- **Crash loop.** `service.json` keeps one list of the latest deaths (`deaths`, at most 20; a clean stop empties it). Each death records how long that run lived after resuming its steps, and `crashPoint` when a test killed it at a crash point (`FACTORY_CRASH_AT`: the service writes the point and its run to `crash-point.json` just before the kill, and the next start moves it into the death). The crash streak is the trailing deaths that lived less than 10 min. From the third start in a streak (two deaths), interrupted steps resume after 30 s, doubling to 30 min; other steps run as usual. `factory status` shows the deaths in a row and the resume time. A clean stop ends the streak.
- **A step that kills the service.** Each interrupted attempt counts the deaths it ran at (`attempts.<step>.interrupted`, counted at the start after the death, once that start's record is saved, so no death counts twice). A death counts on from the attempt's last one only when the dead run finished a step (its heartbeat count, or an Objective's state saved with a step's outcome naming that run, so a death right after a step still counts); otherwise the count starts again at one. A death with a `crashPoint` counts for no attempt and leaves each count as it was: the test caused it, so it is no evidence against a step (it still continues the crash streak). At three, the step holds instead of running again, with its own question: "The service died 3 times in a row while step … ran", with `retry` and `cancel`, asked as soon as no other question stops the step. So a crash streak ends in questions within three deaths however many steps keep being interrupted together, each holding. The count goes with the attempt, so another hold needs three more deaths. Cleanup after cancel never holds; the crash loop's delay covers it.

### Waits

Any other retry is a wait. Waiting more than a few hours is never right, so a wait is classed by its cause, not by how long it has gone on:

| Cause                            | Examples                                                                                                                                                                                                                                                                                                                                                 | What Factory does                                                                                                                                                                                                                                                                                                                                                                                             |
| -------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Fatal until a person acts        | An expired or invalid gh or provider login; GitHub 401, or a 403 refusal still refused after 2 min; a missing repository or issue (404), except what Factory made within the last 2 min; a full disk; a required check with no run or status 15 min after the push that no workflow run under way on the head can report; a workflow that didn't trigger | Hold at once, with a question naming the fix.                                                                                                                                                                                                                                                                                                                                                                 |
| A known reset time               | A GitHub rate limit; a provider usage limit that reports its reset                                                                                                                                                                                                                                                                                       | Wait until the reset when it is at most 3 h away. Further away or unknown (a weekly limit): hold with `wait` (keep waiting until it resets), `switch NAME` (run this Objective on another configured provider, which becomes its frozen provider; plain `switch` when there is only one other) and `cancel`.                                                                                                  |
| A human gate Factory doesn't own | An environment approval; a review the branch requires; a predecessor Objective (see [Predecessors](queue.md#predecessors)); the native-stack layers above a layer, before its stack exists (see [Delivery](delivery.md#delivery))                                                                                                                        | Status shows "waiting on" the gate, and one reminder comment follows after 24 h. A person's gate (an approval, a review) holds after 48 h, so it shows as needing you: `wait` (another 24 h, then it asks again) or `cancel`. The step keeps polling while the question is open, and the question closes by itself once the gate clears. A gate no person holds (a predecessor, the layers above) never asks. |
| An unknown transient cause       | The network down; a body that breaks off after its headers; 5xx or an outage at GitHub or the provider; 409, 410, 422 or a GraphQL error from GitHub; CI queued or running                                                                                                                                                                               | Retry with backoff. After 1 h, post one status note on the issue (edited in place). After 3 h, hold with a question naming the cause and the last error: `wait` (another 3 h), `retry` and `cancel`.                                                                                                                                                                                                          |

A problem on the host counts as fatal when it is certain (disk, login) and as transient otherwise. Times are wall-clock times saved in the state, so a restart doesn't reset a budget, and the question comes only after the step ran again and still had to wait.

- **An open question pauses the clocks of the steps it stops.** While a question is open, no step it stops starts (see [Holds](holds.md#holds-and-answers) for its scope), so their waits don't count; other items' clocks run on. When the question closes, each waiting step it stopped moves its wait start and any granted `wait` forward by the time it was due but blocked, up to when another open question that also stops it was asked (that one's close moves the rest), so overlapping questions never count the same time twice. A human gate's start stays: its one reminder and its question are timed from that start, and a human gate's own question never stops its step. A wait on another Objective's owned paths ([Queue](queue.md)) moves the clocks of the steps it stopped the same way when it ends, and caps a question's the same way, so a question and a wait on paths never count the same time twice either; the service times it in memory, so a restart counts the wait before it. A step with an open attempt was running, not stopped, so neither moves its clocks. No status note or gate reminder is posted for a step an open question or a wait on paths stops. A step that asks while a question covering its scope is open doesn't wait past the answer: its retry comes due at once, so it runs again right after the answer and asks then, even when its own wait (a reset hours away) would end later.

- **One budget per class.** A step's wait start, first cause, backoff and any granted `wait` belong to one run of one class: a reset, a gate, or an unknown cause (errors count as unknown). When the class changes, they start again, so eight hours on a review never spend the transient budget. The error count covers one run of consecutive errors; any other outcome resets it.
- **GitHub's lag is not a refusal.** For 2 min after Factory creates something through the API (an issue, a PR, a comment: the created resource's URL) or pushes a branch, a 403 or 404 on that resource, under it, or on a path naming the pushed branch or commit is an unknown transient (github.ts `GitHub.made`). Past that window, the same answer holds as above. A response whose body fails after its headers (a reset socket, the deadline, truncated JSON) is a transient too.
- **Only a real rate limit is a reset.** A 429, or a 403 with GitHub's rate-limit headers (`x-ratelimit-remaining: 0` or a `retry-after`) or a message saying it is a rate limit (a secondary limit sent without headers), waits for its reset: the `retry-after`, else `x-ratelimit-reset`, else a minute (github.ts `rateLimitOf`). The limit is the installation's (or the login's), so one limited answer holds back every request it covers until then, whatever sends it (a step, a sync job, readiness): the primary limit holds its resource (`x-ratelimit-resource`: core, graphql, search), a secondary limit holds all of them. A held request isn't sent; it fails at once as the same rate limit, with the time left, so its step waits for the reset like the one that met it, and a sync job waits for it plus up to 15 s at random. A rate limit never counts as an error toward a question or toward giving a sync job up. Any other 403 retries as an unknown transient and asks its refusal question, for the whole Objective, once it has gone on 2 min, so a secondary limit GitHub sent with neither its headers nor its message passes by itself. A push or branch delete the remote refuses while the branch still holds the head Factory read does the same, so a passing `[remote rejected]` (two pushes at once, an Internal Server Error) neither asks nor leaves a merged item's branch behind. A 5xx is an unknown transient even when it carries rate-limit headers; its `retry-after` only sets the backoff. A reset at or before now (a skewed clock) still waits at least the normal backoff.
- **Required checks before gates.** A required check with no run or status counts as pending whatever GitHub's readiness says, and it holds 15 min after the push, unless a workflow run still under way on the head can report it. GitHub creates a job's check run only once the jobs it `needs:` end, which can be long after the push, so while the head has a workflow run that is queued, in progress, waiting, pending or requested, and whose workflow defines the check as a job in its file at the head (a `needs:` job too), the check is a wait on that run with no question, bounded by the 3 h limit on an unknown transient wait. The wait's reason, in the run log and status, names the run: `"quality" has not registered yet; workflow run 40703915553 (Quality, in_progress) on this head defines it and is under way`. Factory reads the head's workflow runs once a poll while a check is missing, and the head's workflow files from the checkout once per head. The question comes, 15 min after the push or at once when that is past, only for a check no run on the head can report, and says which case it is: no workflow run on the head is of a workflow that defines it, every run whose workflow defines it completed without it (naming those runs), or GitHub doesn't show the head's workflow runs (no Actions read access). The same applies to a check the plan names. The required checks are the default branch's, for every layer of a native stack too: GitHub judges each layer by the stack's base, not the layer below. A workflow that runs only on PRs into the default branch starts on a layer above the bottom once the stack exists, which Factory makes as soon as every layer is published (see [Delivery](delivery.md#delivery)). So on such a layer a missing check waits on the layers above, with no question, until they are published, and from then holds 15 min after Factory began waiting, not after the push. A review the branch requires is a gate only once every required check is there.
- **Unresolved review threads.** A review thread doesn't resolve by waiting. When the default branch requires review threads to be resolved (a ruleset's `pull_request` rule, or classic protection's conversation resolution, as the login may read them; GitHub judges every layer of a native stack by the stack's base) and the PR has unresolved ones, a PR GitHub reports `BLOCKED` with every check there, or whose merge GitHub refuses, holds at once. The question links each thread: resolve them, then `retry`; or `cancel`.
- **No checks to wait for.** A PR head with no Actions check run (a repository with no PR CI, or a path filter that skips the item's files) waits 15 min from the push for checks to register. Past that, with every required and plan-named check passed and no Actions workflow run on the head unfinished or failed, it merges on Factory's validated head, with or without checks from other apps. Factory asks only when GitHub doesn't show the head's push time or its Actions runs, and a workflow run that ended without jobs or success is a question too.
- **Deadlines of a wait are the engine's.** A step that waits on something GitHub may not show yet (a merge it made, a PR state) retries with a question for later; the engine asks it once the run of retries has gone on 2 min. A required check that never registers is asked about the same way, 15 min from the push (or from when Factory began waiting, when GitHub doesn't say and on a native-stack layer above the bottom), except while a workflow run under way on the head can still report it (see Required checks before gates). An answer to the step (`retry`) starts that time again from the answer. A module never reads the engine's retry records.

| Branch delete   | The branch's absence. After its PR merges (a native stack's layers once the whole unit merged), and on cancel, a branch is deleted only when Factory made every commit it has beyond the default branch (GitHub's update-branch merges from the item's base count, a stack layer's predecessor branch included), by a push with a lease on the head it read.                                                                                                                                                                                                                                                                                                                                                                                                                                                                              |
| Project field   | Read before each write, and written only over the option Factory last saw or wrote (see [Queue](queue.md#queue)); it is a display.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                        |

So an effect whose result was lost is never "unknown". The next run of the step finds it on GitHub and carries on.

A model call has no outside effect. If the process dies mid-call, the call runs again, fresh: a retained conversation whose turn was cut off is never continued (see [Retained conversations](run-log.md#retained-conversations)). A worker's worktree is kept and reused on the base the item kept, so a repeated work step continues from its files. A worktree from an attempt that never kept its base (it died before its outcome) is reset onto the base the rerun picks.

A step's kept facts (`state.kept`) outlive repairs. Every read and write goes through one typed helper (work/facts.ts `fact` and `facts`), which builds the keys (`item:<id>:<name>`, or an Objective step's own name) and types the values. A step forgets one by keeping `null`, and the engine then removes it, so a reader never sees `null`. A replan after acceptance forgets them all.

### Deadlines

| Wait                   | Deadline                                                                                                                                        | At the deadline        |
| ---------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------- | ---------------------- |
| GitHub request         | 60 s                                                                                                                                            | retry                  |
| Plan, plan review      | 45 min each, 15 min idle                                                                                                                        | retry; hold after 3    |
| Worker turn            | 2 h total, 15 min idle (Copilot: `idleSeconds`)                                                                                                 | retry; hold after 3    |
| Worker's own Validate  | silent up to the item's validation deadline                                                                                                     | retry; hold after 3    |
| One validation command | `validation.commandTimeoutSeconds` (30 min)                                                                                                     | repair                 |
| Validation step        | its commands × the command timeout, + 15 min; a Work Item's outside a native stack count twice (#2240), + one timeout per criterion (repros)    | retry; hold after 3    |
| Final validation       | its commands × the command timeout, + 15 min per checkout, + 15 min                                                                             | retry; hold after 3    |
| Result review          | 45 min, + 2 command timeouts and 15 min (the workspace), + `review.proofs` × (10 min, `review.proofSeconds` and a command timeout), 15 min idle | retry; hold after 3    |
| Final review           | 45 min, 15 min idle                                                                                                                             | retry; hold after 3    |
| CI on a PR             | a needed check registers within 15 min of the push, or a run under way on the head can report it                                                | hold                   |
| CI queued or running   | 3 h of transient waiting (see [Waits](#waits))                                                                                                  | hold with `wait`       |
| Hold                   | none: it waits for a person                                                                                                                     | one reminder (at 24 h) |
| Objective              | `queue.objectiveDeadlineSeconds` from admission                                                                                                 | cancel                 |

The Objective deadline is optional (no default) and absolute: admission saves it in the state as a time (`deadline`), so a restart or a later configuration never moves it (`factory run N --deadline` sets its own time in place of the default). A reset keeps or restarts it as What starts again in [State](state.md) says. On every tick, for every Objective, whatever it waits on (a question, a pause, a human gate, a slot), the engine checks it (engine.ts `expire`); past it, it cancels through the normal cancel, recording `ended.by: "deadline"`, so cleanup runs; a restart past it cancels at once. Status shows the deadline and the time left, and a question asked within its last hour says when it falls. Crash points `engine:deadline:before-cancel` and `engine:deadline:cancelled` bracket the save.

Step deadlines are fixed in the code, with two configured bounds (final validation's grows with its sequence, capped only by the host's `FACTORY_DEADLINE_MS`): `validation.commandTimeoutSeconds` (default 1800) limits each validation command and sets the validation deadlines above, so a plan with many commands never outlasts its step, and a Copilot provider's `worker.idleSeconds` (default 900) is its worker's idle bound. A managed worker's `timeoutSeconds` (default 3600, at most 6000) fits inside the worker deadline. Idle bounds are the adapter's: 15 min for Codex planning and workers (5 min for a Codex review at medium effort or lower; the same bound while a Codex planning call's read-only command runs), 2 or 5 min by effort for a Claude call, and 45 min while a Claude or Copilot model's tool runs; while a result reviewer's `run_command` runs, any provider's idle bound is at least that tool's limit, and such a call is never hedged; a Claude, Copilot or Codex worker's running Validate, or a Claude worker's shell command, may be silent for the item's whole validation deadline (one more command's limit with the repository's formatter), if longer, still inside the 2 h turn (Codex's own limit on the call, `tool_timeout_sec`, is that deadline too). The only reminders after 24 h are a human gate's (see [Waits](#waits), which asks after 48 h) and an open question's (see [Holds](holds.md#holds-and-answers)). The engine's limits take shorter test timings from the environment (`FACTORY_DEADLINE_MS`, `FACTORY_WAIT_MS`, `FACTORY_NOTE_MS`, `FACTORY_REMIND_MS`, `FACTORY_BACKOFF_MS`), and validation's install retry window from `FACTORY_INSTALL_RETRY_MS`.
