# Integration tests

Factory has two kinds of tests:

- **CI tests** (`npm test`, `test/`) are quick. They run the real `factory serve` on real Git repositories, processes and files, with no mocks and no GitHub.
- **Integration tests** (this directory) run real Objectives with real providers against scratch GitHub repositories, on demand, never in CI. They cover what needs real GitHub and real models to prove: delivery end to end, the queue, holds, sampled crash points, one installation per repository, a network cut and a killed model.

## Run

```sh
npm run build                                   # the suite runs dist/cli.js
npm run integration -- --dry-run                     # every case, what it checks, its minutes and the run's budget
npm run integration                                  # the main suite
npm run integration -- --suite edge                  # the edge suite: PRD requirements no main case covers, and GitHub rules on repositories of their own
npm run integration -- --suite prd                   # the PRD suite: the requirements docs/PRD.md's Done still needs shown live
npm run integration -- --provider claude             # the main suite on Claude (default: --provider codex)
npm run integration -- --only claude,queue           # some cases
npm run integration -- --build ../other-checkout     # test another build (its dist/cli.js)
npm run integration -- --replay 2026-10-25T101058PDT --suite prd --only prod   # a kept run's checks again, nothing live
```

`--dry-run` is the one list of cases. Each case runs its own Objectives; every case of a suite starts at once and they run concurrently.

**Identity.** A live run acts as the suite's GitHub App, `FACTORY_SUITE_APP_ID` and `FACTORY_SUITE_APP_KEY` (see [Prerequisites](#prerequisites)), and without them stops at setup, unless `FACTORY_SUITE_GITHUB_LOGIN=1` opts out to the `gh` login.

**Provider.** `--provider codex|claude` (default `codex`) is the run's default provider: every case except the cross-provider `claude` case runs on it, and the cases whose check is a planner decision use its `-plan` variant (`codex-plan` or `claude-plan`). The `codex` case (`happy.codex`, `stack.strict`, `model-kill.*`) is the chosen provider's end-to-end stack run, and `model-kill.*` kills that provider's own child: `codex` by its `--cd`, `claude` (the Agent SDK's native binary) by its working directory. The `claude` case (`happy.claude`, `queue.run-command`) runs `factory run N --provider` with the other one, so a Claude run proves Codex there. Dry runs and the results file name the provider. A minor version qualifies only when main, edge and prd pass on both (see [RELEASING.md](../docs/RELEASING.md)).

**Time limit.** A suite has 60 minutes of wall clock: at 55 minutes it stops its cases, cancels unsettled Objectives concurrently, then runs the end checks, cleanup and report. Each case also has its own budget, its minutes in the cases table (`--dry-run` shows them): its deadline is its start plus those minutes, never past the 55-minute stop, and every wait, CLI call and polling loop in the case ends there. A case out of time records its unfinished checks as failed or leaves them unrecorded (`incomplete.*`), as at the suite's stop, and its unsettled Objectives are cancelled; the other cases keep their time. A wait for an Objective to end returns at once (`held:<step>`) when it holds on a question the case's hold policy can't answer; waits that expect a question still return it. Remote calls share the suite's deadline. The crash lane advances through exact hooks against its budget, with time reserved for terminal checks.

**Results.** `/tmp/factory-integration-runs/results/<run id>.md` has the total wall time, each case's start, end and duration, and every check with its result and evidence. The matching run directory holds serve logs, configurations, rendered Objectives and the journal. The suite exits 0 only when every selected check has exactly one PASS and every case completed. Failed, missing, duplicate or unreachable checks fail the run. Exit 1 means qualification failed, 2 means bad usage, and 3 means a prerequisite prevented a start.

**Replay.** `--replay RUN_ID` (with that run's `--suite`, and optionally `--only`) proves a check fixed in code in seconds instead of a new live run. It re-evaluates the kept run's checks with this checkout's code over what the run left in `/tmp/factory-integration/RUN_ID/` (state, logs) and `/tmp/factory-integration-runs/RUN_ID/` (issues, journal), and writes a new results file headed "Replay of RUN_ID" with the same check names. It creates no repository, starts no serve, runs no CLI command, makes no GitHub call and no model call, and changes nothing in the kept run. A replayable check is one function over those files that the live case calls too, so the two can't drift apart; a case's `replay_<case>` finds its Objectives in the kept `issues` file (in filing order) and journal and calls it:

- `model-kill.plan`, `model-kill.work`: the killed attempt's retry outcomes and charged errors (the attempt from the journal).
- `netcut.plan`, `netcut.ci`: holds after each cut, over the window the live check used (the journal's cut and restore lines, written from this change on; an older run's serve `cuts.log` has the cut itself, but not the moment the suite saw the restore, so it isn't used).
- `queue.order`, `queue.concurrency-3`, `exec.parallel-items`, `knowledge.memory`.
- `plan.discovery`: the worker amendment's plan and review, each work attempt (outcome, whether the worker left `.factory-discovery.json`, files it changed outside its owned paths, transcript), and whether the discovering item's kept base holds the person's test commit, which the case lands on main once the drained Objective's plan is accepted (its sha in the run's `discovery-person.N`, checked in the run's kept checkout).
- `toolchain.pin`: installation T's plan-check hold (kept by the case as `toolchain-hold.N`, with the host's node and pnpm versions in `toolchain-host.N`): the check step, before any planning, offering `recheck`, naming the `.nvmrc` pin, the host's node and the fix; then the Objective done, with `pnpm run toolchain` among final validation's commands on a final head whose `.nvmrc` and `packageManager` are the host's node and pnpm (read in the run's kept checkout `checkout-t`).
- `prod.no-holds`, `queue.paths-take-turns`: their state part (holds, the turns, every Objective done). Their end checks read GitHub, so a replay can fail them but never pass them: a passing state part is NOT-REPLAYABLE.
- `delivery.ci-rerun`, `holds.review-threads`: their state part, the same way. `delivery.ci-rerun`: installation F's Objective done, with its failed checks rerun (`ci-rerun`), every published Work Item's checks passed on the rerun (`ci-flaky`) and no Work Item repair. `holds.review-threads`: the hold installation R's Objective met after the suite's review comment (kept by the case as `threads-hold.<owner>_<repo>.N`, the comment as `threads-comment.<owner>_<repo>.N`): a Work Item's ci or merge step, asked within 10 min of the comment, naming unresolved review threads with a link to the suite's and offering `retry`; then the Objective done.

Every other check is NOT-REPLAYABLE, never PASS: it reads live GitHub (PRs, comments, markers, cards, branch protection), drives the run (answers, crash points, the moment of a pause or a reset) or reads a command's exit. A replay reads the files as the run left them, after its own end-of-run cancellations, not as they stood when the live check ran. It exits 1 on any FAIL, and refuses (exit 2) a `--suite` other than the kept run's, which would find none of its lanes and pass empty.

## Prerequisites

- No standing scratch repository. Each run creates its own private repositories under the scratch owner (`REPO_OWNER` in `run-suite.sh`), `fd-<time>-m` (installation M, or E in the edge suite) and, in the main suite, `fd-<time>-c` (the crash lane), where `<time>` is the run's start time and its id's random suffix (`fd-20261026-174258-3f9a-m`). Each one's main is `fixtures/baseline/` as one commit: a small Node.js project whose CI runs `npm test`, Git LFS rules for media, strict branch protection on main ("require branches to be up to date", check `test`) and no required review. A passing run deletes them; a failed run keeps them to inspect (as does `--keep-repos`), and a later run deletes those after 24 hours.
- No standing Project. One installation serves a Project, so each repository a run creates queues on a Project the run creates for it, with Factory's single-select field `Factory` (Queued, Planning, Building, Needs you, Done, Cancelled) and number field `Factory order`, titled like its repositories and deleted (or kept) with them. The crash lane's installation X is configured on repository M's Project, this run's own.
- Two runs at once share nothing (a Codex and a Claude lane, say, started in the same second): a run's id, which names its run and state directories, results file, repositories, Projects and service units, is its PDT start time and a random suffix (`2026-10-26T174258PDT-3f9a`), claimed by creating its run directory, and its fault proxies and the `hostnet` case's loopback service listen on ports the OS picks.
- Within a run, a file the suite keeps for an issue names its repository and number (`run.clockgrove_fd-20261026-174258-3f9a-c.1.out`, lib/common.sh `issue_key`): issue numbers restart in every repository, so lanes on different repositories never share one (#2190). The suite's changes to a Project's cards (add, edit, archive) take turns on a lock per Project, and GitHub's "temporary conflict" on one is waited out and tried again (lib/gh.sh `project_write`): a wave's cases queue at once, and GitHub refuses concurrent changes to one Project (#2191).
- A `gh` login that is an owner of the scratch owner organization, with the `delete_repo` scope (`gh auth refresh -s delete_repo`); Codex and Claude logins (subscription, no API key); `pasta` and `unshare` for the network namespace; `git-lfs`. The `gh` login is the suite's own, whoever Factory acts as: it creates, changes and deletes the run's repositories and posts the cases' issues and comments.
- Factory's GitHub App, setup's preflight step ([GitHub identity](../docs/reference/setup.md#github-identity)): `FACTORY_SUITE_APP_ID` and `FACTORY_SUITE_APP_KEY` (the path of the App's private key) in the environment, for an App installed on All repositories of the scratch owner with the permissions `factory setup --github-app-link` prefills. Each installation's `factory setup` (the prod case's own setup too) gets `--github-app-id`, `--github-app-key` and the `gh` login as `--operator` (lib/common.sh `identity_setup`). Without them a run stops before it creates anything (exit 3), naming them and the opt-out: `FACTORY_SUITE_GITHUB_LOGIN=1` runs Factory as the `gh` login, each setup given `--github-login`. A setup that refuses, or whose GitHub App check is blocked (or missing, as the App), fails the run (`suite.github-identity`) and stops it there, so no installation acts as an identity the run didn't choose. `--dry-run` names the run's identity.
- For the prd suite: systemd user services (its `prod` case runs repository C's installation with `factory setup --background` at production models and concurrency, then uninstalls it), `curl`, and the Project's `Factory order` number field. Lane Q queues on repository C's own Project, which the run creates. Its setup commits `fixtures/repo/drill-issue.yml`, `drill-comment.yml` (to file issues and comments as github-actions[bot], a non-writer) and `ROADMAP.md` (for `propose --source`) to repository M's main.
- For the prd suite's `toolchain` case: `pnpm` on the PATH (any exact version; the case pins the host's). The case makes its own repository `fd-<time>-t` and a Project for it, deleted with the run's others: its main pins Node in `.nvmrc` and pnpm in `packageManager`, has the `toolchain` script (`fixtures/repo/toolchain.mjs`, which fails unless pnpm at the pinned version runs it on a node matching `.nvmrc`) and CI without a package-manager cache (`fixtures/repo/toolchain-ci.yml`). Installation T requires `pnpm run toolchain` as its final command (`finalValidation.requiredCommands`), which lane P's installation can't: its repository is shared and requires none.
- The prd suite's `nocheck` case (35 min, `delivery.no-check-merge`, #1967) makes a third repository, `fd-<time>-n`, with its own Project and installation N: the baseline without `.github/workflows/ci.yml`, and a protected main that requires no check. Its Objective's Work Item PR gets no check, so Factory waits 15 min from GitHub's push time, then merges. The check takes the push time from Factory's own wait ("Awaiting checks to register … none since its push at …") and the merge time from Factory's merge result. It passes when the merge lands 15 to 20 min after the push, with no hold on the ci or merge step, and GitHub shows no check run, status or Actions run on the merged head. The case starts with the rest of the wave, so its wait runs beside the other cases.
- The edge suite's `flake` and `threads` cases (30 min each) each make their own repository, `fd-<time>-f` or `fd-<time>-r`, with its own Project and installation (F, R), since every PR of repository M would meet its CI or its rule. Each is the baseline with its own CI workflow; main still requires `test`, strict.
  - `flake` (`delivery.ci-rerun`, #2054): `fixtures/repo/flaky-ci.yml`, whose `test` job fails on a pull request's first attempt only, after `npm test` passed. Factory must rerun the failed job once, the check must pass on attempt 2, and the PR must merge with no repair. The check reads GitHub for each merged head's `ci` run (attempt 1 failed, a later one passed) and the report's "Possibly flaky CI checks" list. Factory's login needs Actions write access to rerun (a GitHub App: `Actions: write`, which `factory setup --github-app-link` prefills).
  - `threads` (`holds.review-threads`, #2053): `fixtures/repo/slow-ci.yml`, whose `test` job takes a minute longer, and an active ruleset on the default branch whose `pull_request` rule requires review thread resolution and no approving review (a ruleset, not classic protection, which a GitHub App without Administration access can't read). As soon as Factory's PR opens, the suite's `gh` login (Factory's own login, or not) posts a review comment on its first added line, while the check is still pending. Factory must hold within 10 min, on the Work Item's ci or merge step, linking the thread and offering `retry`, where it used to wait silently for its generic 3 h question. The suite then resolves the thread (GraphQL `resolveReviewThread`), answers `retry`, and the PR must merge.

Each run makes fresh state directories under `/tmp/factory-integration/<run id>/` and writes its own configuration there. An existing `--state-base` is refused. Plumbing runs on the fastest model and lowest effort each provider offers, and the cases whose check is a planner decision use the production planner.

## Safety

- The suite refuses to start while any `cli.js serve` for a scratch repository runs.
- Processes are killed by exact PID after checking their start time, never by pattern. Children of a crashed serve are snapshotted while it runs and killed if they outlive it.
- The EXIT/INT/TERM trap stops the cases, cancels unsettled Objectives, stops serves and proxies, checks the end state (the repository keeps its name, no required review, no open PR, no serve or Factory unit left), deletes the run's repositories when it passed, and writes the results.
- The suite deletes only a repository whose description starts with "Factory integration run (transient)", the mark it gives the ones it creates, and changes branch protection and rulesets only on those. The fault proxy (`lib/gh-fault-proxy.mjs`) never logs headers or bodies; every secret the suite uses is a generated dummy. The suite never reads credential files or other processes' environments.

## Layout

- `run-suite.sh`: the cases table, setup, the wave, the 55-minute stop, cleanup and the results.
- `cases/main.sh`: the cases on repository M's shared serve. `cases/crash.sh`: the repository C lane. `cases/edge.sh`: the edge suite (repository M, with the `flake` and `threads` cases' own repositories F and R). `cases/prd.sh`: the PRD suite (lane P on repository M, with its `nocheck` case on repository N and the `toolchain` case's own repository T; lane Q on repository C at production settings).
- `lib/common.sh`: installations, results, CLI, answers, waits, proxy rules, templates. `lib/serve.sh`: serves. `lib/gh.sh`: the Project, markers, PRs and end checks. `lib/repos.sh`: the run's repositories (create, delete, sweep). `lib/st.py` reads state and run logs by structure only. `lib/crashpoints.mjs` finds a build's `crashPoint()` sites. `lib/scope-roles.mjs` reads the scope case's base, top and solo Work Items from a plan. `lib/netns-serve.sh` runs a serve in a network namespace.
- `objectives/`: Objective templates. `fixtures/baseline/`: the run repositories' starting tree.
