# Factory setup

Use this skill to operate the installed Factory plugin on a target repository. For adding features or fixing bugs in Factory itself, follow its contributor instructions instead.

Confirm the target is a Git repository outside all Factory source, rebuild, and archive repositories. Obtain the operator's positive concurrency choice, repository `OWNER/REPO`, absolute checkout path, regular or native-stack delivery choice, and any requested planner, reviewer, or worker Codex model/reasoning selections. Keep credentials outside repositories. Use `factory install --repository OWNER/REPO --checkout ABSOLUTE_PATH --concurrency N` with `--delivery native-stack` only when requested. Pass role selections with `--planning-model`, `--planning-reasoning`, `--review-model`, `--review-reasoning`, `--worker-model`, and `--worker-reasoning`. If the operator does not choose them, state that Factory will persist explicit role defaults: planner `gpt-5.6-sol` with `medium` reasoning, reviewer `gpt-5.6-sol` with `medium` reasoning, and worker `gpt-5.6-luna` with `medium` reasoning. Report the installed binding and configuration path printed by the CLI. Do not start work during setup.

Factory requires an empty configuration and state root at installation; use a fresh `XDG_CONFIG_HOME` and `XDG_STATE_HOME` for an isolated trial. Preserve GitHub CLI authentication by setting `GH_CONFIG_DIR` to its existing configuration directory before changing `XDG_CONFIG_HOME`. `factory install` validates and persists every selected model and reasoning value; it does not inherit the operator's ambient Codex model settings. `factory plan` requires an authenticated Codex SDK environment. Local execution through the Codex SDK is the implemented production shape. Managed-agent and sandbox shapes are reserved; report their unsupported result until their branches ship. The target repository remains authoritative for its instructions and validation.

Prepare the controller for an authorized ordinary host launch; backgrounding or detaching a process inside an agent command sandbox retains its enclosing restrictions. Preserve worker sandbox, approval, credential and network safeguards. Installation, login and planning do not prove worker tools work. Before initial execution, use the installed harness's model-free readiness checks described in the [plugin user guide](https://github.com/clockgrove/factory/blob/main/docs/USER-GUIDE.md#host-and-worker-readiness). Setup itself does not execute an Objective or authorize provider spending. Release-fixture qualification is a contributor workflow, not an ordinary plugin setup step.

Autonomous admission is separate from installation. If the installed version exposes it, bind only the operator's finite Objective selection, explicit execution/service consent and numeric limits through the [admission workflow](https://github.com/clockgrove/factory/blob/main/docs/USER-GUIDE.md#admit-an-exact-plan-for-autonomous-work). Do not invent allowance or spending defaults. An install-only request still stops before admission or execution; a service-consent field alone does not start background work.

When the installed CLI exposes `readiness`, run `factory readiness --outside-directory ABSOLUTE_EXISTING_SIBLING --config CONFIG` from the same authorized host environment intended for the configured default Codex worker. Inspect `factory help` first: older releases lack this surface. It uses the bundled model-free app-server diagnostic with the worker's effective workspace-write, never-approval, network settings and filtered environment. It does not call a model or weaken managed requirements. An unavailable result is unresolved readiness. Do not substitute a guessed permission profile, legacy `sandbox linux` syntax, or a different Codex home and claim the original worker is ready. Other harnesses and profiles require their own supported probe. Controller validation remains separately verified by the real acceptance commands in their declared environment.

If separately authorized by the Objective's admission, `factory supervisor install` registers the exact installed package for the bound target; `status` reports user-manager support and existing logout persistence. Registration does not immediately run work. Use explicit `start` only with existing service consent. Explain host sleep, shutdown and logout limits without altering login persistence. Stop, upgrade, disable and uninstall use the packaged drain/compatibility operations; retain evidence and never treat an unresolved drain as stopped.
